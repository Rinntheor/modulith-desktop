# 设计规范

本文记录项目当前的视觉约定。内容是从既有代码中归纳的实际做法，用于保持新增界面的一致性，而非强制约束。

## 1. 样式基础设施

| 项目 | 说明 |
| --- | --- |
| 框架 | Tailwind CSS 4，通过 `@tailwindcss/vite` 插件接入 |
| 配置文件 | 无 `tailwind.config.js`，Tailwind 4 使用 CSS 优先配置 |
| 全局样式 | `src/styles/global/index.css` |
| 深色映射 | `src/styles/global/dark-theme.css` |
| 配色变量 | `src/styles/global/accent.css` |
| 打印样式 | `src/styles/global/index.css` 末尾的 `@media print` 段 |
| 组件样式 | 直接写在 JSX 的 `className` 中 |
| 插件样式 | 插件自带 CSS 文件，加载时注入 |

导入顺序是**有约束的**，不能随意调整：

```
@import 'tailwindcss';        ← 先有工具类
@import './dark-theme.css';   ← 覆盖工具类，必须在其后
@import './accent.css';       ← 定义并消费配色变量，放在最后
```

后两者**不能放进 `@layer`**：分层样式的优先级低于未分层样式，一旦包进 `@layer`，它们对 Tailwind 工具类的覆盖会整体失效。原因见第 2.4 与 2.5 节。

`index.css` 的基础部分是：

```css
@layer base {
  *, ::before, ::after {
    border-color: var(--color-gray-200);
  }
  body {
    @apply bg-gray-50 text-gray-900 antialiased;
  }
}
```

页面底色为 `gray-50`，标题文字为 `gray-900`，全局启用字体抗锯齿。

## 2. 色彩

### 2.1 主色与强调色

主色用于主要操作、选中状态与品牌标识。**默认是 `indigo`，但用户可以更换**（见 2.5 节），因此组件里写的 `bg-indigo-600` 等类名只是一个**占位**——它们在运行期被重定向到当前配色。

| 用途 | 类名（写法固定） | 实际取值 |
| --- | --- | --- |
| 主要按钮背景 | `bg-indigo-600` | `var(--accent-600)` |
| 主要按钮悬停 | `hover:bg-indigo-700` | `var(--accent-700)` |
| 图标与强调元素 | `text-indigo-500` / `text-indigo-600` | `var(--accent-500)` / `var(--accent-600)` |
| 浅色底（标签、徽标） | `bg-indigo-50` / `bg-indigo-100` | `var(--accent-50)` / `var(--accent-100)` |
| 边框强调 | `border-indigo-200` | `var(--accent-200)` |
| 阴影着色 | `shadow-indigo-500/20` | `rgb(from var(--accent-500) r g b / 0.2)` |

**写新界面时仍然写 `indigo` 类名。** 这是刻意的：`accent.css` 把品牌色系（indigo / purple / violet / fuchsia）统一重定向到变量，因此写哪个色相名都一样，而 `indigo` 是既有代码最一致的写法。不要写 `bg-[var(--accent-600)]` 之类的自定义值——那会绕开映射层，在换配色时不受影响（或者更糟，出现半新半旧）。

品牌渐变（原先 `indigo-500` → `violet-600`）在重定向后两端指向同一套变量，因此**实际呈现为单色**。这是预期结果：主色只有一个。

### 2.2 语义色

| 语义 | 色系 | 典型用法 |
| --- | --- | --- |
| 成功 | `emerald` | 状态标识、完成提示 |
| 警告 | `amber` | 非致命告警条、注意事项 |
| 危险 | `red` | 破坏性操作、错误、卸载 |
| 中性提示 | `gray` | 次要说明 |

破坏性操作（卸载插件、移除设备、清空日志）统一使用 `red` 系，并在界面上与常规操作保持距离。

**语义色不参与主题配色。** 这意味着选择红色系配色时，红色既表示品牌又表示危险，会削弱警示作用——这是配色功能的固有取舍，已在设置页向用户说明，而不是通过限制可选配色来回避。

### 2.3 中性阶

| 层 | 类名 | 用途 |
| --- | --- | --- |
| 标题 | `text-gray-900` | 面板与区块标题 |
| 正文 | `text-gray-700` | 主要文本 |
| 次要 | `text-gray-600` / `text-gray-500` | 描述、辅助信息 |
| 弱化 | `text-gray-400` | 占位、空状态 |

背景层次依靠 `white` 与 `gray-50` 的对比建立。浮层（标题栏、侧边栏、对话框）使用半透明白加毛玻璃：

```
bg-white/90 backdrop-blur-xl
```

### 2.4 深色模式

深色模式已实现，但与常见做法不同：**不在组件里写 `dark:` 变体**，而是由 `src/styles/global/dark-theme.css` 用属性选择器匹配工具类名，把浅色取值映射到深色取值。当前代码库中没有任何 `dark:` 用法。

**为什么不写 `dark:` —— 这不只是风格偏好，写错会出实际缺陷。** Tailwind v4 的 `dark:` 变体默认编译为 `@media (prefers-color-scheme: dark)`，即跟随**操作系统**；而本项目的深色由 `:root.dark` 类驱动，即跟随**应用内设置**。两者是两套独立信号：

| 用户设置 | 系统外观 | `:root.dark` | `dark:` 媒体查询 |
| --- | --- | --- | --- |
| 跟随系统 | 深色 | 命中 | 命中 |
| 跟随系统 | 浅色 | 不命中 | 不命中 |
| **显式深色** | **浅色** | **命中** | **不命中** |
| **显式浅色** | **深色** | **不命中** | **命中** |

最后两行是分歧点。侧边栏的浅/深色快捷开关 `src/components/Sidebar/ThemeToggle.tsx` 曾经写过 `dark:text-gray-300 dark:hover:text-white`，于是在「用户在系统深色下显式选择浅色」时：`dark-theme.css` 的映射不生效，但媒体查询仍然命中，浅色侧边栏里出现浅灰文字——几乎看不清。该用法已移除，深色取值由 `dark-theme.css` 对 `text-gray-600` / `hover:text-gray-900` 的映射承担。

因此判断标准是：**只要一个颜色应该跟随应用内主题设置，就必须走全局映射**；`dark:` 在本项目里没有正确的使用场景。

```css
:root.dark [class~='bg-white'] {
  background-color: #1a1e2b;
}
```

`[class~="bg-white"]` 与 `.bg-white` 等价，但**不会**命中 `bg-white/90` 这类带透明度修饰符的类。

**这一点曾经被误读成「正好避免误伤半透明浮层」，实际相反：它是这套方案最容易漏的地方。** `bg-white` 与 `bg-white/90` 是两个不同的类名 token，前者被映射不代表后者被映射。因此**每一个实际用到的不透明度档位都必须在 `dark-theme.css` 中单独列出**，漏掉任何一档，那个元素在深色下就原样保留浅色 —— 不报错，只表现为「深色界面里出现一块灰白」。

这个坑真实发生过：标题栏用 `bg-white/90`（已映射），而二级标题栏（标签栏）用 `bg-white/85`、全局搜索框用 `bg-gray-50/80`，两档都不在表里，于是二者在深色下渲染成灰色。修法与核对方式见[已知问题与技术债](../06-项目/已知问题与技术债.md)第 7.9 节。

**新增界面时请用差集自查**：把「代码里用到的 `bg-*` / `border-*` 类」与「`dark-theme.css` 已映射的类」做一次差集，未映射的逐个人工判断 —— 多数可能是有意为之（强调色由主题变量驱动、语义色两模式通用），但任何**大面积表面**漏了都必须补。

深色层次（由深到浅）：

| 层 | 取值 | 对应浅色类 |
| --- | --- | --- |
| 应用底 | `#0f1117` | `bg-gray-50` |
| 窗口亚层（标题栏 / 标签栏） | `#151823` | `bg-white/90`、`bg-white/85` 配 `backdrop-blur-xl` |
| 面板 | `#151823` | `bg-gray-800` |
| 卡片 | `#1a1e2b` | `bg-white` |
| 下沉区 | `#11141d` | `bg-gray-50` |
| 下沉输入区（搜索框） | `#0e111a` | `bg-gray-50/80` 配 `rounded-lg` |
| 悬浮 / 选中 | `#222736` | `bg-gray-100` |
| 浮层（菜单 / 抽屉） | `#262c3b` | `bg-gray-700` |
| 边框（弱） | `#252a38` | `border-gray-100` |
| 边框（常规） | `#2c3242` | `border-gray-200` |
| 亚层接缝（标题栏/标签栏底边） | `#0a0c12` | `border-gray-200/50`、`/70` 配 `backdrop-blur-xl` |

**亚层接缝为什么是"更暗"而不是"更亮"。** 深色界面里用亮线勾边，会让每个亚层像被描了一圈白框 —— 既突兀，也与「层次靠明度差表达」的取向冲突。因此亚层的分界改为"压下去"：用比面板更暗的 `#0a0c12` 表示"这里断开"。

取值刻意保持安静：与亚层的对比约 **1.10:1**，参照的是既有的层次基准 —— 应用底与亚层之间本来也只有 **1.066:1**。比这个更暗会显得脏，更亮就又回到"勾白边"的问题。

**只对窗口亚层生效。** `/50`、`/70` 也被浮层（右键菜单、插件卡片、下拉面板）使用，浮层需要的是常规边框色 `#2c3242` —— 给它描一道近黑边会让它看起来像硬边框的补丁，而不是浮在内容之上。判据用 `backdrop-blur-xl`：本项目里只有窗口亚层用它。

**窗口亚层为什么要用不透明色。** 标题栏与标签栏是**相邻**的两块亚层，背后就是应用底色。若保持半透明，底色会透上来，两块亚层的深浅取决于背后内容，容易出现色带分界。统一为同一个不透明值 `#151823` 之后，它们在视觉上连成一整块 —— 这是「好看且不突兀」的关键：亚层要看起来是一整块，而不是两段。层次则靠底色（`#0f1117`）与亚层之间的明度差表达。

**输入区为什么比所在面板更深。** 深色下表达「凹进去」要靠**明度更低**，而不是降低饱和度 —— 后者正是「灰」的来源，在深色界面里读起来像禁用态。因此搜索框取 `#0e111a`（比标题栏更暗），再配一道可见描边（`border-gray-200` → `#2c3242`），让「可以打字的地方」与「只是深色底」区分开。

文字在深色下整体反转：`text-gray-900`/`text-gray-800` 变 `#f3f4f6`，`text-gray-700` 变 `#d1d5db`，依此类推；强调色需要提亮（`text-indigo-600` 在深色下指向 `var(--accent-400)`），否则在深底上对比度不足。

**为什么用全局映射而不是 `dark:` 变体。** 决定性因素是插件：插件由第三方编写，不可能配合补 `dark:` 变体。若深色只靠组件内的变体实现，任何插件界面在深色模式下都会是白底黑字，与宿主割裂。因此宿主用一张全局映射表，把**宿主自己用到过的**工具类名重定向到深色取值。

需要说清这张表**不覆盖插件**：插件在运行时才注入，它的类名不在宿主构建期的扫描范围内，Tailwind 根本不会为它们生成规则，映射表也就无类可映射。**插件必须自带 `index.css` 并自行处理深色**，见[示例插件](../02-开发指南/插件开发/示例插件.md)第 5.6 节。本节此前写着「全局映射让插件只要使用常规 Tailwind 工具类就能自动跟随主题」——**那句话是错的**。

**约束。**

| 约束 | 说明 |
| --- | --- |
| 导入顺序 | `dark-theme.css` 必须在 `tailwindcss` 之后导入，且**不能放进 `@layer`**——分层样式优先级低于未分层样式，放进去会整体失效 |
| 新类名需同步 | 引入新的颜色工具类（如 `bg-slate-50`）时必须在映射表中补一条，否则深色下会漏掉 |
| hover 等变体需单独列出 | `hover:bg-gray-100` 是**独立的类名 token**，不会被 `[class~='bg-gray-100']` 命中，必须写 `[class~='hover:bg-gray-100']:hover` |
| 启动/授权界面 | 这两个界面本就是深色设计，映射会误伤它们的渐变，因此在该文件中显式还原 |
| 品牌色改指向变量 | 该文件中所有 indigo 相关规则都指向 `--accent-*`，不能硬编码色值，否则配色功能在深色模式下失效 |

主题由 `src/services/theme.ts` 管理，设置项为 `theme`（`light` / `dark` / `system`）。首帧配色由 `index.html` 的内联脚本读 `localStorage` 缓存决定，避免「先渲染再纠正」的闪烁。

### 2.5 主题配色（强调色）

主色**不是固定的**，用户可在「设置 → 通用 → 外观 → 主题配色」中更换。深浅模式与配色是两个正交的维度：前者决定明暗，后者决定色相。

**内置配色**（`src/config/accentTheme.ts`，10 套）：

| id | 名称 | 基色 | 备注 |
| --- | --- | --- | --- |
| `indigo` | 靛蓝 | `#4f46e5` | 默认 |
| `violet` | 紫罗兰 | `#7c3aed` | |
| `blue` | 蓝色 | `#2563eb` | |
| `cyan` | 青色 | `#0891b2` | |
| `teal` | 蓝绿 | `#0d9488` | |
| `emerald` | 翠绿 | `#059669` | |
| `amber` | 琥珀 | `#d97706` | 与警告语义色相近 |
| `orange` | 橙色 | `#ea580c` | |
| `rose` | 玫红 | `#e11d48` | 与危险语义色相近 |
| `gray` | 灰白 | `#4b5563` | 无彩色，浅底改用中性灰 |

**实现方式：变量重定向，而非改组件类名。**

```
组件：bg-indigo-600（写法固定，不随配色变）
  ↓
accent.css：[class~='bg-indigo-600'] { background-color: var(--accent-600); }
  ↓
accent.ts：由基色推导出 --accent-50 … --accent-900
```

选这个方案的原因：项目有 50 种品牌色工具类、约 178 处使用。逐个改成 `bg-accent-600` 之类的自定义类，改动面大、评审困难，且以后再换方案还要再改一遍。变量重定向让组件保持原样，**新增一套配色只需在 `accentTheme.ts` 加一行**。

**色阶推导。** 每套配色只声明一个基色，其余档位在运行期按 HSL 明度规律推导（`src/services/accent.ts` 的 `buildAccentVariables`）。理由：界面用到 `-50` 到 `-700` 以及深色模式的 `-200` 到 `-900` 共十余档，若每套配色手写这些值，配色表会膨胀到数百行且极易出现某档不一致，实际不会有人认真维护。只给基色则各档必然协调。

推导时的明度表与 Tailwind 官方调色板的构造方式一致，因此视觉上不会有违和感。无彩色主题（`gray`）单独处理：饱和度归零，浅底改用中性灰，否则会与界面自身的灰阶撞色。

**覆盖范围。** `accent.css` 覆盖**实际用到的全部** 50 种品牌色工具类（含 `hover:` / `focus:` / `group-hover:` 变体、带透明度修饰符的类、渐变 `from-*`/`to-*`、阴影与 ring）。引入新的品牌色工具类时必须同步补一条 —— 这一点与深色映射表的要求相同。

**同步点。** 首帧脚本（`index.html` 内联）为了让配色不闪，内联了一份基色表与明度表。**它与 `accentTheme.ts` / `accent.ts` 是两份实现，改一处必须改两处**，否则首帧与后续渲染会出现色差。

## 7. 动效

动效使用 framer-motion。时长集中在三档：

| 时长 | 用途 |
| --- | --- |
| `0.1` 至 `0.15` 秒 | 即时的状态反馈，如悬停、按下 |
| `0.2` 秒 | 元素的出现与消失 |
| `0.4` 至 `0.6` 秒 | 页面级过渡，如启动界面、解锁界面的出入场 |

常见模式：

```tsx
// 悬停与按下反馈
<motion.button
  whileHover={{ scale: 1.05 }}
  whileTap={{ scale: 0.95 }}
/>

// 进出场
<AnimatePresence>
  {open && (
    <motion.div
      initial={{ opacity: 0, y: 8 }}
      animate={{ opacity: 1, y: 0 }}
      exit={{ opacity: 0, y: 8 }}
      transition={{ duration: 0.2 }}
    />
  )}
</AnimatePresence>
```

两点注意事项：

`AnimatePresence` 只跟踪**直接子元素**的退出动画。若要为条件渲染的元素添加退出动画，该元素必须是 `AnimatePresence` 的直接子节点，不能包在额外的 `div` 中。

`container-type` 的元素会成为 `fixed` 定位后代的包含块。使用容器查询时需注意对话框中 `fixed` 定位元素的定位基准。

### 7.1 关闭动画与性能模式

设置中的「关闭界面动画」通过两条路径生效，缺一不可：

| 路径 | 覆盖范围 | 实现 |
| --- | --- | --- |
| CSS | CSS 动画与过渡 | 根元素加 `.lc-reduce-motion`，把 `animation-duration`/`transition-duration` 压到 `0.001ms`，并把两者的 `delay` 归零（选择器同时含根元素自身） |
| JS | framer-motion 动画（含 spring 与 layout 动画） | `<MotionConfig reducedMotion="always">`，位于 `src/components/ThemeProvider.tsx` |

只做其中一件都会留下明显还在动的部分：只关 CSS 则所有 `motion.*` 照旧，只关 motion 则 CSS 过渡照旧。

用 `0.001ms` 而不是 `0` 或 `transition: none`：部分浏览器在 `transition: none` 下不会触发 `transitionend`，会让依赖该事件结束的逻辑卡住。

**这条路径有两个已知盲区，必须知道：**

1. **`reducedMotion` 只对位置类属性短路。** framer-motion 12 的 `positionalKeys` 只包含 transform 系列与 width/height/inset，**`opacity`、`backdrop-filter`、`box-shadow`、`filter` 都不在其中**。因此一个 `repeat: Infinity` 的透明度循环不会被它停掉（授权界面的粒子背景就是这种情况，改为由代码显式不挂载）。
2. **嵌套的 `MotionConfig` 会覆盖外层。** framer-motion 的合并规则是子层取胜，所以 `Home` 给每个标签面板套的那一层必须把全局状态取进来，否则全局开关在最该生效的那个标签上失效。详见[性能与内存](../02-开发指南/性能与内存.md)第 1 节。

**性能模式**（`performanceMode`）是这条设置之上的第二档：它包含关闭动画，并额外去掉不表现为动画、但让每一帧都要重新合成的开销 —— 三个常驻全屏表面的毛玻璃（`backdrop-blur-xl`，即上表中「窗口亚层」的半透明加模糊）、装饰性大半径模糊、以及成片的 `will-change` 合成层提示。打开它之后界面会失去毛玻璃层次与粒子背景，这是刻意的代价。

**不覆盖**的范围：手写的 `setTimeout` / `setInterval` 驱动的变化（提示条自动消失、启动界面计时刷新）。这是有意保留的——那些是功能行为，不是装饰动画。

## 8. 布局尺寸

主界面自顶向下分三层，尺寸互为约束（任何一层高度变化都必须同步内容区的 `top`）：

| 元素 | 尺寸 | 说明 |
| --- | --- | --- |
| 标题栏高度 | `h-10`（40px） | 主界面与启动阶段一致 |
| 标签栏高度 | `h-9`（36px） | 仅主界面有 |
| 侧边栏宽度 | `w-64`（256px） | 展开状态 |
| 内容区左边距 | `ml-64` / `ml-0` | 标签栏与内容区各自留白，随侧边栏开合过渡 |
| 内容区上边距 | `top-[76px]` | = 标题栏 40 + 标签栏 36 |

标签栏与内容区**不是**横跨整个窗口的：它们的左边距同样随侧边栏开合，只占内容区宽度。这样侧边栏保留完整高度，标签栏属于内容区的一部分，与 VS Code 的编辑器标签一致。

标题栏与侧边栏均为 `fixed` 定位，内容区通过外边距避让。层叠顺序是一个必须保持的栈（数值越大越靠上）：

| 层 | z-index | 说明 |
| --- | --- | --- |
| 启动与解锁阶段的标题栏 | `z-[60]` | 盖住主界面的一切 |
| 标签栏 | `z-40` | 低于标题栏，避免盖住搜索框的下拉结果 |
| 标题栏 | `z-50` | |
| 浮层遮罩 | `z-[65]` | 通知中心与搜索面板的点击外部关闭层 |
| 通知中心 / 搜索面板 | `z-[66]` | |
| 浮层提示（Toast） | `z-[70]` | 最高，任何情况下都应可见 |

### 8.1 标签栏

| 属性 | 取值 | 说明 |
| --- | --- | --- |
| 单个标签宽度上限 | 200px | 超出用省略号，保证一排能放下多个 |
| 激活标签强调 | 底部 2px 强调条（`--accent-500`） | 用绝对定位的内阴影而不是 `border`，避免切换时高度抖动 |
| 关闭按钮 | 悬停或激活时出现 | 一排 × 会把标题挤没；同时支持中键关闭 |
| 溢出 | 横向滚动，隐藏滚动条（`.no-scrollbar`） | 36px 的条里放一条滚动条会吃掉近三分之一并让标签上下错位；纵向滚轮被转成横向滚动 |

标签上的未读徽标与侧边栏一致：强调色底、白字、`99+` 封顶。`99+` 是为了不让三位数把模块名挤没。

### 8.2 浮层提示（Toast）

右下角堆叠，宽度固定 320px，最多同时 5 条，超出丢弃最旧的。左侧有一条 4px 的级别色条，配色用语义色（红/琥珀/翠绿/强调色）而不参与主题配色替换。

停留时长：`info` 4 秒、`success` 3.5 秒、`warning` 6 秒、**`error` 不自动消失**。错误时用户需要读完再决定怎么办，3 秒后自己跑掉会让人怀疑「刚才是不是弹了什么」。

鼠标悬停时暂停，并且是**按剩余时间继续**而不是重新计时 —— 后者等于没暂停。

### 8.3 通知中心与搜索面板

两者都是标题栏下方的浮层，共用「一层透明遮罩点击外部关闭」的交互（而不是监听 `window`：遮罩同时阻止点击穿透到下面的界面）。

| 属性 | 通知中心 | 搜索面板 |
| --- | --- | --- |
| 宽度 | 380px | 与输入框同宽（`max-w-md`） |
| 位置 | `top-11 right-3` | 输入框正下方 |
| 最大高度 | `70vh` | `60vh` |
| 滚动 | 结果区独立滚动（`custom-scrollbar`） | 同 |

### 8.4 全局搜索框

位于标题栏正中，高 28px（`h-7`），宽 `max-w-md`，左侧放大镜图标、右侧 `Ctrl K` 提示。提示不是装饰：那是让用户发现这个快捷键的唯一途径。

居中方式用 `flex-1 + justify-center`（居于**剩余空间**的中央），而不是绝对居中。右侧有四个按钮、左侧只有标题，绝对居中会让搜索框压到右侧按钮上。

输入框**不带** `data-tauri-drag-region`，否则点击会变成拖动窗口而不是获得焦点。

### 8.5 窗口装饰

窗口以 `decorations: false` 创建，标题栏与窗口按钮由应用自行绘制：

| 组件 | 阶段 |
| --- | --- |
| `components/Titlebar/Titlebar.tsx` | 主界面 |
| `features/boot/BootChrome.tsx` | 启动与解锁阶段 |

两者都提供拖拽区域与最小化、最大化、关闭按钮。

关于拖拽区域的实现：`data-tauri-drag-region` 属性会使元素及其子元素参与窗口拖动，因此**不要把它放在包含按钮的父元素上**，否则按钮的点击会被拖动行为吞掉。正确做法是单独放置一个用于拖拽的元素，或用 `flex-1` 的占位元素承担拖拽。

主界面标题栏把该属性放在最外层与左右两个分组上，但搜索框与所有按钮都不带 —— Tauri 按事件目标是否带该属性来判断，因此它们仍能正常获得点击与焦点。

## 9. 容器查询

对话框内的栅格应使用容器查询而非视口断点。原因是对话框宽度受限于窗口，而视口断点描述的是窗口宽度，两者不一致：在宽窗口中对话框仍可能很窄，此时视口断点会错误地触发多列布局。

```tsx
// 外层声明容器
<div className="@container">
  {/* 内层按容器宽度响应 */}
  <div className="grid grid-cols-[repeat(auto-fill,minmax(16rem,1fr))] gap-4">
    {/* ... */}
  </div>
</div>
```

Tailwind 4 的容器断点：`@2xl` 为 42rem，`@3xl` 为 48rem，`@4xl` 为 56rem。

## 10. 组件约定

| 组件类型 | 约定 |
| --- | --- |

| 主要按钮 | `bg-indigo-600 text-white rounded-xl hover:bg-indigo-700` |

## 12. 图标

图标统一使用 lucide-react。

### 12.1 尺寸约定

| 尺寸 | 用途 |
| --- | --- |
| `w-3.5 h-3.5` | 极小标注 |
| `w-4 h-4` | 正文内联 |
| `w-5 h-5` | 按钮内 |
| `w-6 h-6` | 标题旁 |

### 12.2 解析规则

所有模块图标（侧边栏、子项、仪表盘）都必须通过 `src/components/ModuleIcon.tsx` 渲染，不要自己去查 `generated/iconMap`。它按以下顺序解析：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 1 | 内联 SVG（`iconSvg`） | 插件声明的 `icon.svg` 在加载期已读出，随模块描述符传递 |
| 2 | `src/generated/iconMap.ts` | 构建期映射，内置模块走这条，静态导入无异步开销 |
| 3 | lucide 按需加载 | 覆盖插件在运行期注册的任意 lucide 图标名 |
| 4 | 通用 `Box` 图标 | 兜底，保证不会出现空白占位 |

第 2 步的存在是因为 `iconMap.ts` 由生成器在**构建期**根据 `src/modules/*/module.toml` 产出，只包含内建模块用过的图标；插件模块在运行期注册，其图标名或图标文件路径都不在其中。第 3 步通过 lucide 的 `lucide-react/dynamic` 入口按需拉取，代价是每个额外图标多一个 chunk（本地磁盘加载，可接受）。

判定规则：`icon` 值若以 `.svg` / `.png` / `.jpg` / `.webp` / `.gif` 结尾，或包含 `/`，会被视为**文件路径**而跳过第 2、3 步，直接落到兜底——避免拿一个路径去查图标映射表。

### 12.3 插件图标

| 声明方式 | 效果 |
| --- | --- |
| `manifest.icon = "icon.svg"` | 宿主在加载插件时读取该文件并内联渲染 |
| `manifest.iconSvg = "<svg …>"` | 清单内直接内联 SVG 源码（与 `icon` 同时存在时优先） |
| `manifest.icon = "StickyNote"` | 按 lucide 图标名解析 |

注入到 DOM 的 SVG 只接受以 `<svg` 开头的内容（严格的开头匹配，不是「包含」），避免把任意文件当 SVG 注入。

### 12.4 应用标识

标识源文件有两份，**必须同步修改**：

| 文件 | 形态 | 用途 |
| --- | --- | --- |
| `public/modulith.svg` | 裸标记（三枚方块，无底色，`currentColor`） | favicon；界面内嵌 |
| `src-tauri/icons/source.svg` | 带黑底（`tauri icon` 的输入） | 生成 `src-tauri/icons/` 下的平台图标 |
| `src/components/icons/AppLogo.tsx` | 上述裸标记的 React 实现 | 界面内使用（唯一实现） |

标识的含义（品牌名 Modulith = module + monolith）：

| 元素 | 含义 |
| --- | --- |
| 三枚方块 | 已装入的 module |
| 右下角空位 | 还没装的那个插槽（「需要什么功能就加什么模块」） |

**空位是刻意的。** 四格填满就只是一个通用的「网格 / 启动器」图标，留一个缺口才说明「这是可以扩展的」，这是它与常见方块图标的决定性区别。

**为什么拆成两份。** 界面里嵌入标识时，不透明的底色等于在已有背景上又贴了一层背景，显得笨重；而**应用程序图标必须自带背景**——任务栏、桌面会把它直接贴在各种壁纸上，白色方块遇到浅色壁纸会完全看不见。

**底板为什么带一圈描边。** 近黑底板在深色环境里会与背景融为一体，实测对比度：`#18181b` 底板 vs `#101322` 界面底 = **1.04:1**，vs Windows 深色任务栏 `#202020` = **1.09:1**。不加处理时图标会变成「三枚悬空的白方块」。描边取白色 22% 透明度，在浅色背景上几乎不可见、在深色背景上给出清晰轮廓。

### 12.5 图标底板（IconPlate）

非标识类的「图标块」（插件页页头、空状态等）统一使用 `src/components/icons/IconPlate.tsx`：

```
黑底（#18181b）+ 白色图标 + ring-1 ring-inset ring-white/20
```

抽成组件的原因：这类「渐变底 + 白图标」的写法原先散落在多处，配色硬编码在各自身上，改一次要找一遍。现在配色集中在 `PLATE_CLASS` 常量。

用 `ring` 而不是 `border`：`ring` 不占布局尺寸，不会让不同尺寸的底板出现像素级错位。

## 13. 打印

唯一需要打印的场景是**恢复码**（生成后让用户存成 PDF 或纸质件）。实现方式：

| 项目 | 说明 |
| --- | --- |
| 打印视图 | `src/features/auth/RecoveryPrintSheet.tsx`，渲染在 `.lc-print-sheet` 容器内 |
| 触发 | `window.print()`，由用户在系统对话框里选「另存为 PDF」 |
| 样式 | `index.css` 末尾的 `@media print` 段 |

**不引入 PDF 依赖**：项目没有 PDF 库，装一个属于新增第三方依赖；而系统打印对话框本来就能产出 PDF，零新增代码路径。

三个必须记住的约束：

| 约束 | 原因 |
| --- | --- |
| `@media print` **不能放进 `@layer`** | 分层样式优先级低于未分层样式，它要覆盖 `dark-theme.css` 里未分层的深色映射；包进 `@layer` 后打印件会带着深色底输出（费墨且难读） |
| 必须在 `dark-theme.css` 之后（文件末尾） | 两者优先级相同，靠后加载取胜 |
| 显式强制浅色 | 打印是静态输出，不能指望深色模式下自动输出白底 |

机制上是「屏上隐藏一切、只显示打印容器」：`body * { visibility: hidden }` + `.lc-print-sheet, .lc-print-sheet * { visibility: visible }`。因此打印容器平时对用户完全不可见，不需要维护显隐状态。
