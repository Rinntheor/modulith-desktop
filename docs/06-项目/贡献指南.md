# 贡献指南

本文说明向 Modulith 提交改动时需遵守的约定。

## 1. 提交信息

提交信息使用 Conventional Commits 格式，因为 `CHANGELOG.md` 由脚本依据提交信息自动生成。

```
<类型>(<作用域>): <描述>
```

| 类型 | 归类到 CHANGELOG |
| --- | --- |
| `feat` | Added |
| `fix` | Fixed |
| `perf` | Changed |
| `refactor` | Changed |
| `chore` | Changed |
| `docs` | Documentation |
| `test` | Tests |
| `remove` / `revert` | Removed |

作用域可选，通常填写模块名或受影响区域：

```
feat(sidebar): 支持拖拽调整模块顺序
fix(plugins): 修复首次启动时插件模块不显示
docs(plugin): 补充宿主 API 参考
```

描述部分可以使用中文。生成 CHANGELOG 时会剥离类型与作用域前缀，只保留描述。

不带类型前缀的提交会被归入 Changed，但无法体现改动性质，建议避免。

## 2. 代码风格

### 2.1 TypeScript

| 约定 | 说明 |
| --- | --- |
| 严格模式 | `tsconfig.json` 已开启 `strict` |
| 未使用变量 | 开启 `noUnusedLocals` 与 `noUnusedParameters`，提交前必须清理 |
| 组件 | 函数组件，文件名使用大驼峰 |
| 类型导入 | 仅用于类型的导入使用 `import type` |
| 相对导入 | `src/` 内可省略扩展名（由 Vite 解析） |

`src/` 目录下的导入由打包器处理，可省略扩展名。`scripts/` 目录下的导入**必须带 `.ts` 扩展名**，因为脚本由 Node 直接运行。两者规则不同，修改脚本时需注意。

### 2.2 Rust

| 约定 | 说明 |
| --- | --- |
| 命名 | 类型大驼峰，函数与变量蛇形 |
| 模块目录 | 蛇形命名，与模块 `id` 一致 |
| 命令返回值 | `Result<T, String>`，错误信息为可直接展示的中文 |
| 状态 | 通过 `app.manage()` 托管，命令用 `State` 取出 |
| 日志 | 使用 `log` crate，不使用 `println!` |

模块目录名必须为蛇形，因为它会被转换为 Rust 类型名。

### 2.3 注释

注释用于说明**为什么**，而不是**做什么**。代码本身能表达的内容不需要注释。

项目中高质量的注释示例：

```rust
// 配置损坏时 load() 会回落到「需要授权 + 未初始化」，
// 也就是把门锁上并要求重新设置密钥，绝不会静默放行。
```

这条注释解释的是一个容易被误认为 bug 的行为，属于必要说明。

## 3. 生成文件

以下文件由脚本产出，**不要手工编辑**：

| 文件 | 生成器 |
| --- | --- |
| `src-tauri/src/lib.rs` | `scripts/generate-backend-module.ts` |
| `src-tauri/src/modules/mod.rs` | 同上 |
| `src/generated/*` | `scripts/generate-modules.ts` |

需要修改它们时，应修改生成器中的模板字符串，再运行生成命令。手工改动会在下一次构建时被覆盖，造成难以察觉的丢失。

若发现生成结果不符合预期，请修改生成器而不是直接改产物。

## 4. 提交前检查

```bash
# 1. 版本一致性（构建门禁，必须通过）
pnpm ver check

# 2. 生成前端模块注册表
#    src/generated/ 是构建期产物，不纳入版本控制，而 tsc 依赖它。
#    全新 clone 之后必须先跑这一步，否则第 3 步必然报
#    「Cannot find module '../generated/moduleRegistry'」。
pnpm gen:modules

# 3. 前端类型检查
npx tsc -p tsconfig.json --noEmit

# 4. 后端编译与测试
cd src-tauri && cargo test --offline --lib

# 5. 示例插件的清单与代码是否一致（改了 samples/ 才需要）
pnpm check:samples

# 6. 前端纯逻辑的断言脚本（改了 src/utils/ 下被它们覆盖的文件才需要）
pnpm check:semver
pnpm check:update
pnpm check:network
pnpm check:memory
pnpm check:performance
```

前四项都通过后再提交；改了 `samples/` 则第五项也要过；改了 `src/utils/` 下被断言覆盖的
文件（`semver.ts`、`updateCheck.ts`、`networkSettings.ts`、`motionPreference.ts`）、
`src/config/pluginRegistry.ts` 或性能与缓存的接线（`services/theme.ts`、
`services/moduleComponentCache.ts`、`services/pluginMarket.ts`、`pages/Home.tsx`、
`styles/global/index.css`）则第六项也要过。

**第 4 项里有一条与示例插件直接相关的检查**：它会解压那个 `.lcp`，逐个文件与源码目录
比对。改完插件忘记重新打包，用户装到的就还是旧代码 —— 这条测试会直接说出来。

**第 5 项检查两件容易漏的事**：代码用到了某项能力却没在清单里声明（运行到那一步才失败），
以及清单多声明了用不到的能力（让用户看到一条并不存在的能力）。顺带检查窗口级监听
是否配合了 `useModuleActive()`。

**第 6 项里的 `check:network` 与另外两个不同**：它不只断言纯逻辑，还会**直接读 Rust 源文件**
（`src-tauri/src/modules/settings/network.rs` 与 `settings.rs`）来核对前后端的取值、长度上限、
GitHub 宿主表与字段默认值有没有漂移。网络方式的取值与宿主表在两处各有一份（后端是权威，
前端是镜像），漂移的后果是界面给出与实际行为不符的解释 —— 那种错误没有任何其他测试能发现。

`pnpm build` 与 `pnpm dev` 会自动执行版本检查、后端生成与模块生成，因此正常构建路径不需要手动跑上面这些。**只有当你直接调用 `npx tsc` 时才要留意第 2 步的先后顺序。**

CI 会按同样顺序执行，并额外用 `git diff --exit-code` 检查生成器是否与源码一致（改了模块却忘记重新生成会让 CI 失败）。

## 5. 新增代码的检查点

**新增模块**

- 前端 `module.toml` 的字段是否完整，`component` 是否指向真实文件。
- 后端模块目录名是否为蛇形。
- 是否运行了 `pnpm gen:modules` 与 `pnpm gen:backend update`。

**新增后端命令**

- 返回值是否为 `Result<T, String>`。
- 错误信息是否可直接展示给用户。
- 是否运行 `pnpm gen:backend update` 刷新注册。
- 敏感操作是否要求 `token` 参数。

**新增插件相关能力**

- 清单字段是否与 `PluginManifest` 定义一致。
- 权限名是否使用 kebab-case。
- `engines.loopcore` 是否使用后端支持的单个比较符语法。

**修改界面**

- 是否符合[设计规范](../05-设计系统/设计规范.md)中的色彩、圆角与间距约定。
- 是否处理了空状态、加载状态与错误状态。
- 图标按钮是否提供了 `aria-label`。

## 6. 版本管理

发布版本时：

```bash
pnpm ver bump <类型>     # 同步配置文件、生成 CHANGELOG 段落
pnpm ver check
git add -A && git commit -m "chore(release): 版本升至 <版本>"
pnpm ver tag             # tag 必须在提交之后打
git push --follow-tags
pnpm release             # 签名构建 + 生成更新清单
```

`bump` 会自动同步四个配置文件并生成 CHANGELOG 段落，但**不打 tag** —— 打完 tag 再提交的话，tag 会指向升级前的提交（见[版本管理](../02-开发指南/版本管理.md) 4.3 与 4.6）。

注意不要手工编辑 `version.toml` 中的 `full_version`，它必须与 `version`、`release_type`、`build_number` 保持一致，否则 `check` 会报错。

## 7. 测试

**后端**

后端已有单元测试，覆盖认证加密、插件包解压安全、设置校验等模块：

```bash
cd src-tauri && cargo test --offline --lib
```

新增安全相关的逻辑时应当补充测试。现有测试中值得参考的是插件解压的路径安全测试，它包含真实样本包的回归用例。

**前端**

前端当前**没有测试框架**，`package.json` 中没有测试脚本，也未引入 Vitest 等依赖。因此涉及前端纯函数的改动需要通过以下方式验证：

- 类型检查（`tsc`）
- 临时脚本直接运行纯函数并断言结果
- 手工验证界面行为

已有测试的后端逻辑无需重复在前端测试。

## 8. 提交粒度

每个提交应表达一件完整的改动。具体的实践建议：

- 不要把格式化改动与逻辑改动混在同一个提交中。
- 重命名文件与修改其内容分开提交，便于通过 `git log --follow` 追溯。
- 修复缺陷时，若该缺陷此前未被记录，在提交信息中说明触发条件。

### 8.1 分支与合并

- 功能与修复各自开一个分支（`feat/…`、`fix/…`、`chore/…`、`refactor/…`），不在 `main` 上直接提交。
- 合并回 `main` 时使用 `--no-ff`，让合并提交本身带上分支名。
- **合并后不要删除分支。** 保留它有两个具体用途：事后回答「这个问题是在哪个分支解决的」时不必依赖提交信息的措辞；以及在需要重新审视某个改动时，分支名本身就是一个可检索的索引。本地分支不占远端空间，代价只有一个更长的 `git branch` 列表 —— 那比丢失可追溯性便宜得多。

## 9. 报告问题

提交问题时请提供：

| 项目 | 说明 |
| --- | --- |
| 复现步骤 | 尽可能具体 |
| 期望行为与实际行为 | 分别说明 |
| 环境 | 操作系统、Node 版本、是否开发模式 |
| 日志 | **优先附上「设置 → 日志」里的 `modulith.log` 与 `crash.log`**（路径在同页显示，可直接打开文件夹）。这两份是唯一能还原现场的材料。开发模式下也可以附控制台输出 |

若问题出现在启动阶段，启动界面会显示失败的步骤名称与原因，请一并提供。

若要反馈「市场打不开 / 检查更新失败」，请先在同一页用「设置 → 网络 → 网络诊断」测一次，把结果表一并附上 —— 它能区分 DNS、证书、加速源与目标本身的问题，比任何描述都准确。

**安全问题请勿开公开 issue。** 见[版权与授权](../07-法务/版权与授权.md)与仓库的 `SECURITY.md`。

## 10. 贡献者的授权约定

本项目采用 **DCO（Developer Certificate of Origin）** 的简化形式：**提交即表示你同意以本项目的许可证发布你的贡献。**

具体要求：请在提交时使用 `-s` 签名，声明你确实有权提交这些代码。

```bash
git commit -s -m "fix(sidebar): 修正折叠按钮位置"
```

这会在提交信息末尾加一行：

```
Signed-off-by: 你的名字 <你的邮箱>
```

**为什么需要这一步。** 本项目的授权安排是「框架 GPL-3.0 + 插件例外」（见[版权与授权](../07-法务/版权与授权.md)）。如果一份贡献的版权归属不清，日后若要调整授权安排，就必须逐一征得每位贡献者同意 —— 那会非常麻烦。`Signed-off-by` 是最轻量的解决方式：不要求你签任何额外协议，只要求你声明代码来源合法。

作为贡献者，你保留自己贡献部分的著作权，只是同时按项目许可证授权他人使用。

## 11. 编辑器配置

建议启用保存时格式化与 `tsc` 的类型检查。项目未强制使用特定的格式化工具，但应当遵循既有代码的排版风格：两空格缩进、单引号、语句末尾分号。
