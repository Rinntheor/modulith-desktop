## 一、内存基线（实测）

测量环境：Windows，`src-tauri/target/release/modulith-desktop.exe`（9/21 21:47 构建，v1.3.2）。
方法：先记录已有 `msedgewebview2` 进程 id 集合，启动应用后取差集，只统计本应用新建的进程。

### 1.1 启动到解锁界面（尚未加载任何模块）

| 子进程（按私有内存降序） | 工作集 | 私有内存 |
| --- | --- | --- |
| WebView2 主进程 | 205.1 MB | 189.4 MB |
| WebView2 子进程 2 | 133.4 MB | 83.6 MB |
| **WebView2 GPU 进程** | 130.4 MB | 40.4 MB |
| WebView2 子进程 4 | 38.6 MB | 12.6 MB |
| WebView2 子进程 5 | 24.3 MB | 9.3 MB |
| WebView2 子进程 6 | 20.6 MB | 9.0 MB |
| WebView2 子进程 7 | 13.3 MB | 3.0 MB |
| **合计（7 个进程）** | **565.6 MB** | **347.4 MB** |
| 宿主进程本身 | 24.3 MB | 4.0 MB |

### 1.2 关键观察

1. **宿主 Rust 进程几乎不占内存**（4 MB 私有）。这 347 MB 全部来自 WebView2 的进程树，
   也就是**渲染引擎 + 我们送进去的前端**。优化对象是后者，不是 Rust 侧。
2. **7 个进程是 WebView2 的默认进程模型**，不是我们创建的第二个 WebView。
   微软文档明确：每个 WebView2 控件都会拉起自己的 browser / renderer / GPU 进程组
   （[WebView2 性能最佳实践](https://learn.microsoft.com/zh-cn/microsoft-edge/webview2/concepts/performance)）。
   因此"进程数多"本身不可优化，可优化的只有**单个进程的占用**与**空闲时能否被压下去**。
3. **GPU 进程 40 MB 私有 / 130 MB 工作集是正常量级**，且微软明确要求**不要**用
   `--disable-gpu` 关掉它（那会牺牲渲染性能，只用于排障）。用户看到的"GPU 进程占用高"
   属于 WebView2 固有结构。
4. 之前误把别的应用（DSH Desktop 自身）的 6 个 `msedgewebview2` 进程算进来过，
   所以**必须用差集测量**，否则数字会虚高一倍。

### 1.3 尚缺的数据（下一步要补）

- 最小化窗口、全屏、收回侧边栏各状态下的内存，用于验证下面的假设。
- DevTools 堆快照：区分 **JS 堆**、**DOM 节点数**、**游离节点**。
- 插件全部加载 vs 全部禁用时的差值。

## 二、可用的官方杠杆（已核实存在）

### 2.1 WebView2 内存目标等级（最重要的一条）

`wry` 提供 `WebViewExtWindows::set_memory_usage_level(MemoryUsageLevel)`：

- 依赖 crate：`wry 0.55.1`（本仓库 `Cargo.lock` 已锁定）。
- 定义位置：`wry-0.55.1/src/lib.rs:2215`（枚举）、`:2254`（trait 方法）、
  `webview2/mod.rs:1741`（实现，映射到 `SetMemoryUsageTargetLevel`）。
- Tauri 侧入口：`WebviewWindow::with_webview(|w| ...)` →
  `PlatformWebview::controller()` 返回 `ICoreWebView2Controller`
  （`tauri-2.11.5/src/webview/mod.rs:180`）。`webview2-com-sys 0.38.2`
  的 `bindings.rs` 已包含 `SetMemoryUsageTargetLevel` / `TrySuspendAsync` / `Resume`。
- 语义：应用**变为非活跃时**把等级设为 `Low`，可显著降低内存占用
  （引擎会丢弃缓存或换出到磁盘）；重新活跃时设回 `Normal` 恢复性能。
- 兼容性：需要 WebView2 Runtime ≥ 114.0.1823.32，低版本上是 no-op，不会报错。

**待确认的呈现问题**：在全屏、无边框、无系统标题栏的应用里，"活跃/非活跃"的判据是什么？
必须由窗口 `focused` / `minimized` / `visible` 三个状态共同定义，不能靠操作系统默认行为。

### 2.2 挂起渲染进程

`CoreWebView2::TrySuspendAsync()` 会在窗口长时间隐藏时**暂停脚本执行**并进一步降低占用，
`Resume()` 恢复。两者都是 best-effort。

**这条与"插件后台保活"直接冲突** —— 如果窗口被挂起，界面插件的定时器就不再运行。
因此挂起策略必须与后台服务分层设计，而不能无条件启用。

### 2.3 环境共享

微软建议用**同一个** `CoreWebView2Environment` 服务多个控件以省内存。
我们目前只有一个主窗口；未来若为后台服务开隐藏窗口，**必须共用同一个 UDF 与参数**，
否则会再拉起一整套进程组（+几百 MB）。

### 2.4 明确无效的方向

- **不要** `--disable-gpu`：牺牲渲染，微软明确反对。
- **不要**盲目 `--single-process`：WebView2 官方不支持该开关的稳定语义，
  会导致渲染进程与浏览器进程合一、崩溃面扩大。
- **不要**指望靠"更多窗口"分摊：每多一个 WebView2 实例就是一套新进程组。

## 三、问题结构（我的判断）

用户报告了三个现象，它们指向**三个不同的根因**，不能用一个补丁一起解决：

| 现象 | 我的判断（待验证） | 归类 |
| --- | --- | --- |
| 启动即 300+ MB | WebView2 固有基线 + 前端首屏体积 + 插件资源常驻 | 基线，只能压低不能消除 |
| **收回侧边栏内存不降** | 侧边栏折叠与否和内存无关；真正的持有者是**标签保活**与各服务缓存 | 前端持有链 |
| **全屏后内存不降，退出全屏也不降** | 窗口状态变化时**没有任何内存回调**：没人通知 WebView2"你可以降级了" | 缺少生命周期挂钩 |

第二、三条是本项目**能真正解决的**，第一条里能压缩的部分是插件资源与首屏。

## 四、方案骨架（待与用户确认优先级后细化）

### 阶段 0：可观测性（先做，否则无法验收）

- Rust 侧新增"内存快照"能力：枚举本应用的 WebView2 子进程并汇总私有内存/工作集；
  一并回报窗口状态（focused / minimized / visible / fullscreen）。
- 前端侧回报：已挂载标签数、缓存条目数、插件激活数、命令数、通知数、DOM 节点数。
- 提供一个诊断入口（设置 → 性能 或日志文件周期性采样），**采样本身要便宜**。
- 加一条门禁脚本 `check:memory-budget`，把"空闲 N 分钟后内存不得超过阈值"变成断言。

### 阶段 1：立即可得的收益（不改架构）

1. 窗口失焦 / 最小化 / 隐藏 → `MemoryUsageLevel::Low`；恢复 → `Normal`。
2. 标签保活**加可配置上限与淘汰策略**：LRU 淘汰最久未显示的**非固定**标签
   （淘汰 = 卸载组件 + 释放 DOM + 释放组件缓存 + 通知模块 `onDeactivate`）。
3. 插件资源按需化：图标、README、bundle 文本不在目录加载期全量常驻。
4. 空闲时的前端回收：非活跃标签暂停定时器、释放大对象、清空可重建缓存。
5. 修正 `isSvgMarkup` 之类的重复实现时顺手收敛，避免内联 SVG 重复驻留。

### 阶段 2：架构级生命周期重写

- 统一的 **AppLifecycle** 状态机：`启动 / 活跃 / 空闲 / 最小化 / 隐藏 / 退出中`，
  每一档定义：窗口是否挂起、插件哪些能力继续运行、内存目标等级、UI 回收强度。
- 模块与插件的生命周期契约重写：显式 `activate / deactivate / suspend / resume / dispose`，
  宿主**拥有**暂停与回收的权力，而不是依赖模块自律（当前 `useModuleActive()` 只是感知）。
- 分屏、多窗口、托盘共存时的单一事实来源。

### 阶段 3：插件配额与分页游标

- **配额**：每插件的存储字节数 / 键数量 / 内存估算 / 定时器与订阅数量 / 网络与通知速率，
  超限给出明确错误与降级行为，而不是静默变慢。
- **分页游标**：`ctx.storage` 的枚举与 `ctx.notifications`、通知中心、插件列表等
  统一为游标分页，避免"一次全量读进内存"。
- **每插件的资源账本**：可查询、可在设置里展示、可被用户清零。

### 阶段 4：系统托盘 + 后台保活 + 桌面通知

> **⚠️ 这一阶段的交付范围后来缩小了。** 托盘与后台保活**已交付**；
> **桌面通知与定时提醒已被删除**（用户实测不满意，见 §16）。
> 下面那两条关于通知的问题因此只作为历史记录保留。

这三件原是**同一个决定**：插件要脱离"当前窗口"存活。需要先定的架构问题是：

- 后台插件运行在**隐藏 WebView**（与主窗口共享环境）还是**独立宿主进程**？
  → 已定为**独立 Node 宿主进程**，已交付。
- 桌面通知由 **Tauri notification 插件** 还是**自研 Rust（直连 Windows Toast）**发出？
  → 曾定为**自绘通知窗口**；该实现已被删除（§16）。
- 窗口关闭 → 隐藏到托盘 → 后台插件继续运行；**退出**要成为显式动作。
  → 已交付。
- 无边框 + 托盘 + 后台通知 + 单实例：必须一起定，否则会出现"两个实例抢托盘"。

## 五、已确认的决策（用户已定，不再变更）

1. **推进方式**：内存与架构**一次大改**，但**分次交付** —— 每完成一块就报告、等确认。
   分支：`feat/memory-and-runtime-architecture`（自 `main` 的 `da8caf3` 切出）。
   提交、合并、推送**都需要用户明确许可**（推送由用户自己做）。
2. **标签淘汰**：允许淘汰，**只淘汰最久未显示且非用户固定的标签**。
   —— 注意这与「关闭即释放」是两件事，见下表。
3. **后台插件运行位置**：**独立宿主进程**；插件逻辑走 RPC。
   **JS 运行时已定为捆绑 Node.js sidecar** —— 插件代码（IIFE）可直接运行，
   现有 9 个插件基本无需重写。代价：安装包增大约 60-80 MB；需自行负责
   进程生命周期、崩溃重拉、通信通道与安全。
4. **桌面通知**：**不使用 Windows 系统通知**。理由：需要专属样式与动画。
   → 实现为**自绘的通知窗口**（无边框 / 置顶 / 不进任务栏 / 可叠放 / 有进出场动画）。
   `tauri-plugin-notification` 不引入。
   > **⚠️ 已撤销（后来的决定）。** 自绘通知窗口实现出来之后用户实测不满意，
   > 连同定时提醒一起要求删除。因此当前代码里**没有**任何桌面通知窗口。
   > 保留下来的**只有那条约束本身**：将来若重做，仍然不要用 Windows 系统通知 ——
   > 要专属样式与动画。见 §16。
   > 顶上的「后台插件运行位置」那条**保留**：Node 后台宿主还在。
5. **关闭语义**：默认「关闭窗口 = 隐藏到托盘，后台继续运行」，
   但**由用户决定**是「直接退出」还是「隐藏到托盘」。退出是托盘菜单里的显式动作。

### 5.1 「保活」与「淘汰」的边界（重要，别混为一谈）

| 机制 | 触发条件 | 是否可配置 | 丢不丢现场 |
| --- | --- | --- | --- |
| **保活**（现有核心承诺） | 标签**仍然打开**、只是当前未被激活 | 不可关闭 | 不丢 |
| **关闭即释放**（本次已修） | 标签**从标签栏消失** | 不可关闭（语义正确性） | 丢（本来就该丢） |
| **LRU 淘汰**（后续） | 打开着但**太久没显示**，且非用户固定 | 可配置 | 丢（这是代价） |

### 8.1 三条设计决定（都有理由，不是随手写的）

1. **按进程树取，不按进程名枚举。** 本机实测有 13 个 `msedgewebview2` 进程分属
   两个应用；按名字枚举会让数字虚高一倍。反证方式是一条测试：结果里除宿主外的
   每个 pid 都必须能在父关系表里回溯到本进程。
2. **失败不算错误。** 取内存要 `OpenProcess`，权限不足时跳过并计入 `unreadable`，
   而不是让整条命令返回 `Err` —— 少一个进程的数字远好过整个面板空白。
3. **进程角色一并给出。** 只报"进程数"会让用户以为进程多是缺陷，而 WebView2
   的多进程是引擎固有结构。界面必须能说清"GPU 进程占几十 MB 正常，不能关"。

### 8.2 测试覆盖（15 条，其中 4 条是真实调用）

- 纯逻辑 11 条：分类（含大小写/引号归一化）、树遍历（嵌套、无关进程排除、
  菱形去重、排序确定性、不可达进程不收）。
- 真实调用 4 条：自洽性、pid 不重复、**不含无关进程**、**真的拉起子进程并找到它**。

最后两条是互补的：反证能排除"混入无关进程"，但一个永远返回空列表的实现也能
通过它 —— 所以另加一条正向证据，真的 `spawn` 一个子进程确认它能被找到。

### 8.3 过程中发现的两处问题（都已修，但值得记下）

1. **命令写在子模块里会被静默忽略。** 我最初把命令属性放在
   `process_memory/mod.rs`，生成器报的仍是"101 条命令"——因为
   `generate-backend-module.ts` **只扫描 `<模块>/commands.rs`**。
   这与文档里反复警告的"看起来接通了、实际从未通电"是同一类问题。
   命令外壳现已移到 `settings/commands.rs`。
2. **生成器的属性计数不看注释。** 我在文档注释里写了那个属性的字面量，
   生成器的 `extractCommandFunctions` 把它当成真实属性，于是报"14 处属性但
   只有 13 个函数"。那条对账本身是对的（它抓的就是"有属性没解析出函数"），
   只是它分不清代码与注释。当前按它配合（注释里不写那个字面量）；
   让它跳过注释是后续可做的小改进。

### 9.1 这一条为什么由**前端**驱动（不是实现偏好，是硬约束）

写这个模块时踩到两处**会直接死锁或编译失败**的坑，都值得记下：

1. **`with_webview` 会阻塞等待事件循环。** 它的实现是"把闭包投递给事件循环，
   然后等它执行完"，因此只能在**事件循环之外**的线程上调用。Rust 侧的窗口事件回调、
   托盘菜单回调都跑在事件循环线程上 —— 在那里调用它就是"事件循环等闭包、
   闭包等事件循环"。同理 `Window::is_minimized()` 这类读取也经过事件循环
   （`dispatcher.is_minimized()` 发消息并等回复），在事件回调里同样死锁。
   **结论：Rust 侧的窗口事件策略先天不可行。**
2. **`ICoreWebView2_19` 不是 `Send`**（它包着 `NonNull<c_void>`），
   所以"先取接口、再投递一次去调用"会在编译期直接报
   `NonNull<c_void> cannot be sent between threads safely`。
   这不是限制而是好事：COM 接口本就只能在创建它的线程（STA）上使用。
   于是 `with_webview` 只用**一次**，闭包在界面线程上自己取接口、自己调用。

于是分工是：**前端决定**什么时候降级（它能看到 `document.hidden`，而且托盘隐藏
窗口时 webview 同样会收到 `visibilitychange`，所以不必两处各写一遍），
**后端只提供机制**并如实回报是否生效。

### 9.2 「失焦不降级」是刻意的取舍

失焦在桌面应用里太频繁：切到浏览器查一句话、切到编辑器复制一段，窗口仍在屏幕上、
仍被看着。把它当成"不再需要"，换来的是切回来时的卡顿，而用户会归因为"这软件很卡"。

因此判据只有一条：**文档是否可见**。这条取舍被两处门禁钉住 ——
前后端策略函数都只接受一个布尔量，签名里没有焦点概念；改它必须显式改签名。

### 9.3 尚未验证的部分（必须在你的实例里确认）

- **实际的降幅**。`Low` 到底能回收多少，取决于当时的缓存量。我无法在沙箱里启动
  应用来测（独立启动被残留的 WebView2 用户数据目录锁挡住），因此**预期可观但未经证实**。
- **恢复的代价**。设回 `Normal` 之后引擎可能需要重新解码/换入内容。如果切回来的
  卡顿可感知，就要把策略收紧到"只在隐藏到托盘时降级"，或引入延迟降级。
- **当前 WebView2 运行时是否 ≥ 114**。低于它时接口取不到，界面会显示
  "当前环境不支持" —— 那是一句如实的话，不是错误。

验证方法：打开设置 → 性能，看「空闲时的降级」是否显示"已启用"，
然后点「立即降级试一次」，观察上方进程明细里渲染进程的私有内存变化。

### 10.1 为什么现在才引入托盘（README 曾写"刻意不引入"）

README 里写过"目前只有应用内通知，没有系统级通知 —— 那需要新增 Tauri 插件依赖，
当前版本刻意不引入"。这句话针对的是**通知**，但它背后的取舍（不轻易加依赖）
对托盘同样成立，因此值得说明为什么这次开了口子：

**因为托盘成了后台保活的前提，而不是一个装饰。** 应用接下来要有在窗口之外继续
工作的能力（后台插件、桌面通知）。一旦有了那种能力，"关掉窗口"就再也不能等于
"退出程序"——否则用户点一下关闭，后台任务跟着一起死，那些功能从一开始就是假的。

而"隐藏到托盘"要成立，缺一不可的两件事是：关掉窗口之后**仍有入口**把界面叫回来，
以及**退出**是一个显式的用户动作。前者需要托盘，后者需要托盘菜单。

`tray-icon` 是 Tauri 自己的特性（不是第三方插件），且只在桌面平台编译，
因此它是这一类需求里最小的那个口子。通知则**不走**官方插件 ——
用户要求专属样式与动画，那要靠自绘的通知窗口实现（见步骤 7）。

### 10.2 唯一可能让应用"再也叫不回来"的路径

托盘在部分环境里装不上（没有桌面会话、被系统策略禁用）。而关闭行为默认是
"隐藏到托盘"——两者叠加的后果是：**用户点关闭，窗口消失到一个不存在的托盘里，
只能去任务管理器结束进程。**

因此 `DesktopModule::setup` 在托盘安装失败时会**强制把关闭行为回落成"直接退出"
并写回设置**。写回这一步不是多余的：界面读的是设置，若只改内存里的判断而不写回，
设置页仍会显示"隐藏到托盘"，用户会照着一个假的选项去推断行为。

`check:tray` 里专为这条路径留了三条断言（回落存在、写回存在、有日志）。

### 10.3 关闭行为的两个入口改的是同一个字段

设置页与托盘右键菜单都能改这一项。两处若各存一份状态必然漂移，表现是
"菜单里勾了、设置页没勾"——而界面与真实行为相反是最难察觉的一类错误。
因此两处都直接读写 `close_to_tray` 这一个字段，并且**设置页改过之后会同步
托盘菜单的勾选状态**（少了它，勾会与实际行为相反）。

### 10.4 尚未验证的部分

- **托盘图标是否真的出现、关闭是否真的隐藏**。机器上有一个**先于本应用任何代码**
  的启动阻塞：进程起来后停在 4.6 MB，日志文件一行都不写，而
  `logging::install_early()` 是启动最先执行的。这与我引入的改动无关
  （改动全部在其后），但因此我无法在本机跑通端到端验证。
- **托盘图标在浅色/深色任务栏下的可见度**。用的是应用自己的窗口图标，

### 11.1 三档配额，以及为什么是这三档

| 档位 | 上限 | 对应的失控方式 |
| --- | --- | --- |
| 单个值 | 1 MB | 一次写进一个巨大的 base64，内存与磁盘各翻一倍 |
| 键数量 | 2000 | "一条记录一个键"，键数随使用时间线性增长 |
| 总量 | 8 MB | 每项都不大但一直在加 —— 缓慢增长，最难察觉 |

此前**一条上限都没有**：`storage_set` 只看"是不是合法 JSON"。而 `storage_keys`
一次返回全部键、`ctx.storage.all()` 再把每个键的值逐个读出来拼成对象 ——
也就是说**插件的存储量直接决定它能让我们一次吃进多少内存**。
对一个以内存为目标的项目来说，这条路径不能只靠"插件作者会自律"。

### 11.2 判定必须在写盘之前

这是这一块唯一真正重要的顺序：判定写在后面的话，那个大文件已经落盘了，
报错只是一句安慰的话，而内存与磁盘都已经付出代价。
`check:quota` 里有一条专门的断言盯这个顺序（`check_write` 必须出现在
`std::fs::write` 之前）。

### 11.3 总量档判的是**增量**，不是新值本身

用 `new_value_bytes > MAX_TOTAL_BYTES` 会把"把一个 5 MB 的键覆盖成 1 MB"这种
**缩小**写入误拦下来，于是插件连自救都做不到。因此判定要先取该键原来的字节数，
按 `current - existing + new` 投影。这一条有专门的回归测试。

### 11.4 为什么用游标而不是页码

页码在**下标会变**的列表上是错的：插件在翻页过程中删掉一个键，第二页就会漏掉
一条记录。而"从某个键之后继续"对增删都稳 —— 键的排序是确定的。

游标是不透明的（URL 安全的 base64），因此将来改编码不会破坏调用方。
它同时携带了 `prefix` 与 `page_size`：**游标与本次前缀不一致时报错**，
而不是静默给一份缺数据的结果 —— 缺数据是最难发现的一类错误。

游标指向的键**已经被删除**时，用 `binary_search` 的 `Err(index)`（它本该在的位置）
继续，而不是退化成"从头开始"。退化的话用户看到的是"点下一页却回到了第一页"，
而且永远不会结束。这一条也有专门的回归测试。

### 11.5 用量统计不缓存

缓存一份用量意味着它与磁盘上的事实之间有一个窗口，而插件正好可以在那个窗口里
写满磁盘 —— 于是配额就变成了一个"有时候生效"的东西。统计的代价是每个键一次
`metadata`（不读内容），在 2000 个键的上限下是毫秒级。
`check:quota` 有一条断言盯这一点。

### 11.6 明确没有做的事

- **没有把 `keys()` 改成分页**。它是既有插件的公开接口，改动会破坏兼容。
  配额（2000 键）已经把最坏情况关进笼子，因此 4a 只**新增** `list()`。
- **没有改 typing-practice 插件**。它用 `keys()` 取"最新 50 条记录"
  （`sort().reverse()`），而游标只能向前翻 —— 拿最新的一批必须扫到最后，
  反而更贵。它的历史本来就封顶 50 条，全量枚举在这个规模下是合理的，
  硬改会把"恰好最近 50 条"变成"最多 N 条"这种语义漂移。
  要让它用上分页，得先决定历史记录的排序方向（例如键名里带上倒序前缀），
  那是插件侧的改动，不该塞进宿主这次变更里。
- **没有做按插件的"资源账本"界面**（配额用量在设置里展示）。
  后端已经给出 `storage_usage`，界面侧等 4b 一起做。

### 12.1 三级机制的分工（这是这块最容易混的地方）

| 机制 | 触发条件 | 可配置 | 丢不丢现场 |
| --- | --- | --- | --- |
| **保活** | 标签仍打开、只是未被激活 | 不可关闭 | 不丢 |
| **关闭即释放** | 标签从标签栏消失 | 不可关闭（语义正确性） | 丢（本来就该丢） |
| **淘汰**（本次） | 达到上限且该标签最久未被显示 | 受保护集合决定 | 丢（这是代价） |

### 12.2 四级保护，而不是两级

"不淘汰用户固定的标签"是最低要求，但只做两级会在两种常见情形下淘汰掉用户
根本不想丢的东西：

1. **正在显示的两个标签永不淘汰**。淘汰它等于当着用户的面把界面关掉 ——
   那不是省内存，那是故障。
2. **收藏**（`favorite_modules`）表达"我常用的东西"。它比置顶弱一等（收藏可能很多），
   但比"随手开过"强得多。

因此顺序是：**激活中 > 置顶 > 收藏 > 最久未见**。这个顺序还有一条实际好处：
越靠前的集合越小、判定越便宜，而它们同时是"用户最在意"的那些。

### 12.3 淘汰的是"最久未被**显示**"，不是"最久未被打开"

用户开着 A 打字、切到 B 查资料、又切回 A 继续打 —— A 是"最久未打开"的吗？
不是，它刚刚才在用。按打开时间淘汰会先把 A 干掉，而 A 正是用户在反复使用的那一个。

### 12.4 一个被自己的断言纠正的设计决定

初版把"最近使用"表达成**数组位置**（最旧在前）。问题在于"没有使用记录"的标签
没有位置，只能靠 `sort` 的稳定性碰巧排在某处 —— 那是一个**隐式**结果，
改一次排序实现就会变。

写成断言之后立刻暴露了：测试期望"无记录的排在已知最旧之后淘汰"，
而实现给出的是"排在最前"。核对之后判定**实现更对、注释更错** ——
没有记录意味着用户从没看过它，因此比"有记录但很旧"更该先回收。

修法不是改期望，而是**改数据结构**：改用单调整数时间戳 `lastSeen`，
"没有记录"于是显式为 `0`（最低优先级），不再依赖排序稳定性。

### 12.5 没有可淘汰对象时返回空，而不是硬挤一个

这是这条规则里最容易被"顺手优化"掉的一处：既然要腾位置，那就总能凑出一个来。
**不能。** 硬挤一个的代价是用户丢掉现场，而正确行为是让调用方如实拒绝并说明原因。
那一侧的提示措辞也一并改了 —— 它此前写"不会自动帮你关掉"，而那句话现在只在
这一种情况下才成立。让提示与真实行为相反，比没有提示更糟。

### 12.6 尚未验证的部分

- **端到端行为**。淘汰的触发条件是"打开第 13 个标签"，我无法在沙箱里跑应用
  来实测（本机有一个先于应用任何代码的启动阻塞，见 §10.4）。
  规则本身有 36 条断言，但"它在真实的标签操作序列里被正确触发"没有实测。
- **12 这个上限是否仍然合适**。加入淘汰之后，上限的语义从"硬性拒绝"变成了
  "开始回收"。也许它应该更小（回收更积极）或更大（少打扰用户）——
  这需要真实使用之后才能判断，我不打算凭猜测定这个数字。
- **淘汰是否会让用户困惑**。提示会说明原因，但"我的标签自己消失了"这种观感
  是否被那条提示消解，要看实际使用。

### 13.1 三个此前真实存在的生命周期缺陷

1. **`start` 不按拓扑序。** `setup_all` 一直是按拓扑序的，而 `start` 直接遍历
   `registry.all()` —— 也就是 `HashMap::values()`，**哈希顺序**。两者不一致的后果
   不是"顺序看起来乱"，而是一个模块的 `start` 可能早于它依赖的模块的 `start`，
   于是它在启动阶段读到对方**半初始化**的状态。这种缺陷只在恰好读到那个状态时
   才显形，平时完全不报错。
2. **`stop` 从来没有被调用过。** `registry.stop_all` 甚至不存在，`lib.rs` 里也
   没有任何退出收尾。而 `logging` 模块确实有需要落盘的东西 ——
   `FileLogger::flush()` 是一个**从未被调用过的公开方法**。
3. **`dependencies()` 一直是空的。** `logging.setup` 直接读设置，`desktop` 也要读
   设置与日志，但这些都没声明 —— 于是拓扑排序拿到一张空图，
   顺序完全由注册顺序决定。**碰巧正确的顺序不是顺序，是运气**：
   `logging` 恰好排在 `settings` 之后，只是因为生成器按字母序注册。

### 13.2 顺序为什么必须抽成纯函数

生命周期里最容易错、也最难在运行期发现的就是顺序，而它此前无法被验证
（要验证就得启动一个应用）。抽成 `plan_lifecycle(ids, dependencies_of)` 之后，
顺序可以被直接断言：依赖先启动、停止是严格逆序、菱形依赖只出现一次、
深链不爆栈、顺序**只取决于输入顺序**而不取决于任何哈希容器。

`registry.plan()` 是执行顺序的**唯一来源**，`setup_all` 与 `start_all` 都用它
—— 两处各算一次必然漂移。

### 13.3 为什么用 `run_return`，以及它的代价

拿到退出事件的唯一途径是 `App::run_return`。代价是它**替换**掉 Tauri 内部的回调，
而那个默认实现除了跑事件循环还做了 `cleanup_before_exit`。漏掉它不会立刻报错，
但托盘图标与窗口资源表都不会被清理。因此生成器模板里显式补上了它，
并把退出码原样传出去。`check:modules` 有一条断言专门盯这个"补全"。

停止挂在 `RunEvent::Exit` 上，且必须在 `cleanup_before_exit` **之前** ——
后者会清掉窗口与资源表，之后模块再想用 Tauri 的 API 收尾就拿不到东西了。

### 13.4 `stop_all` 的语义

- **严格逆序**：依赖方先停，这样它在收尾时还能用到被依赖方提供的服务。
  正序会让"负责落盘的模块"在它依赖的设置已经关掉之后才收到通知。
- **只停成功启动过的模块**：一个连 `start` 都没跑过的模块，让它执行 `stop`
  等于在没初始化的情况下清理。
- **单个失败不中止**：清理阶段最怕的就是"第一个失败之后后面全不执行"——
  那会让本该落盘的数据因为一个无关模块的错误而丢掉。
- **幂等**（原子交换）：退出路径可能被触发两次（窗口关闭事件与进程退出）。
  用原子布尔而不是"记下停过哪些模块"，是因为 `app.state::<T>()` 只给共享引用，
  `stop_all` 必须是 `&self`。

### 13.5 一个我无法在测试里覆盖的点（以及如何处理）

我最初写了一条"用真实 `modules::register_all` 检查依赖图无环"的测试。
它会让 **`cargo test --lib` 整个进程起不来**（`STATUS_ENTRYPOINT_NOT_FOUND`）：
调用 `register_all` 把 `desktop`（托盘）与 `plugins`（WebView2）的代码链进了
测试二进制，而那两个 crate 拉进的导入里有当前系统解析不了的符号。
注意这不是"测试失败"，是**测试进程根本无法启动**。

处理方式是**换一层验证**，而不是删掉覆盖：
- Rust 侧保留一份手抄的依赖表做快速回归锁（并注明它会漂移）；
- **完整的真实形状交给 `check:modules`** —— 它读源码而不跑链接，
  因此没有那个限制，而且能覆盖"磁盘上的模块是否都被注册"这种 Rust 测试
  做不到的事。

### 13.6 尚未验证的部分

- **`RunEvent::Exit` 是否在所有退出路径上都触发**。窗口关闭（自己隐藏到托盘那条
  路径不退出）、托盘菜单退出、以及进程被外部结束这几种情况里，
  前两种走的是 Tauri 的正常退出流程，应当会触发；**外部强制结束不会**，
  那时 `stop_all` 不会执行 —— 这是无法通过改我们的代码解决的，
  因此 `logging` 平时每次写入都 flush，不把落盘全押在退出那一刻。
- **实测**。本机有一个先于应用任何代码的启动阻塞（见 §10.4），因此
  "退出时日志真的被冲到磁盘"这条没有实测。

### 14.1 为什么是独立进程，而不是"再开一个隐藏 WebView"

界面插件跑在主窗口的 WebView 里，而那个环境会被**降级**（内存目标等级设为 Low）、
会被隐藏、脚本会被浏览器冻结。把"凌晨三点准时提醒"托付给它，等于托付给一个
随时可能被挂起的执行环境。

隐藏 WebView 依然是**一整套浏览器进程**（本机实测 6~8 个、私有内存 300+ MB），
而 Node 是一个进程、且能在不需要时被完全关掉。在一个以内存为目标的改动里，
这个差别是决定性的。

### 14.2 「按需拉起 + 空闲回收」而不是常驻

这个模块存在的理由是"让能力脱离窗口存活"，而它自己要付的代价是一个额外进程。
无条件常驻会把这笔开销加到**每一个**用户身上 —— 包括从不使用后台功能的那些。

因此：托管状态在 `setup` 里建立，但**不在那里启动子进程**；真正的启动发生在
第一次调用时。`check:background` 有一条断言专门盯这件事的注释与实现一致。

### 14.3 协议为什么是「stdio + 行分隔 JSON」

三个候选的代价：命名管道/本地 socket 多一套路径与权限处理、跨平台差异大；
长度前缀的二进制帧要自己处理粘包与编码；**行分隔的 JSON 用的是进程本来就有的
stdin/stdout**，可读、可直接用管道调试、不需要任何额外资源。

这条通道只在宿主与自己的子进程之间使用，没有第三方会往里写东西 ——
因此不需要防伪造，只需要防**解析错误**。上限（单行 1 MB）存在的理由是
内容来自**插件**，"一行有多长"完全不受我们控制。

### 14.4 启动时先读一行问候

协议版本错配的默认表现是"某个方法返回了预期之外的字段"这类难以归因的故障 ——
因为子进程与宿主是两个**可以分别更新**的东西（应用升级了，而用户机器上
残留着旧脚本）。

因此脚本启动第一件事是打印一行问候，宿主**先读它再投入使用**：
版本不匹配在启动那一刻就明确失败并说清原因，而不是在某个具体调用上以
一个奇怪的字段缺失暴露。脚本还会**逐条**校验每个请求的版本 ——
应用可能在使用中被升级。

### 14.5 三处刻意的"不猜"

| 情况 | 处理 | 为什么不能猜 |
| --- | --- | --- |
| 响应既无 result 也无 error | 拒绝 | 放行会让调用方把"什么都没说"当成"结果是 null"，于是静默做错决定 |
| 响应同时有 result 与 error | 拒绝 | 说明对面实现有歧义，此时"取哪一个"是猜 |
| 请求超时 | **不重试** | 重试一个可能已经在执行的方法会带来重复副作用（提醒响两次）；"没响"与"响两次"之间后者更难解释 |

另外，`result: null` 与"没有 result"在 `Option<Value>` 上**无法区分**，
因此后台方法不应当用 `null` 表示成功 —— 要表达"成功但没有内容"就返回 `{}`。
这条已写成测试。

### 14.6 沙箱里真的跑通了（这次不是"只写代码"）

本机有可用的 Node（v24.9.0，85.6 MB），因此这条链路**真的被验证过**：

1. **单独跑脚本**（用管道喂 JSON）：
   - 问候先出，随后 hello / ping / status 各自正确响应；
   - 未知方法返回 `未知方法：nonexistent`；
   - 版本 99 的请求被逐条拒绝；
   - 一行非 JSON 只记日志、**不中断**后续响应；
   - `shutdown` 先回响应再退出。
2. **Rust 侧真实启动子进程**：`live_tests::a_real_node_host_answers_a_ping`
   真的 spawn 了一个 Node、走完一次请求-响应并校验 `pong`。

### 14.7 明确没有做的事

**插件在后台的执行没有实现。** 那需要先定"后台插件能用哪些能力"：
界面插件的 `ctx` 里有 DOM 相关的东西（fileDrop、通知浮层），后台环境里没有；
而定时器、存储、通知是可以有的。把这条边界定清楚之前照搬 `ctx`，
只会让插件在后台**静默地半可用** —— 那比明确不支持更糟。

因此这一版刻意只把**通道**做完整、可验证。前端服务模块里也**没有**暴露
任何不存在的插件执行接口（`check:background` 有断言盯这一点），
这样插件作者不会照着假接口白写代码。

### 14.8 尚未验证的部分

- **空闲回收的自动触发没有接。** `IDLE_TIMEOUT`（5 分钟）与 `reap_if_idle`
  都存在且逻辑完整，但**没有任何东西定期调用它** —— 因此目前的回收是手动的
  （设置页那个按钮）。理由：后台插件还没能跑起来，此时自动回收只会让
  "它到底在不在跑"更难观察。等插件执行做出来之后再接定时器。
- **Node 运行时随包分发尚未落地。** 查找顺序是"环境变量 → 可执行文件旁的
  `runtime/node.exe` → 报错"，而 `runtime/node.exe` 需要发布流程把 Node 二进制
  放进去。**我没有把 85.6 MB 的 Node 提交进仓库** —— 那会让仓库体积翻几十倍。
  这是一个需要你决定的发布问题（见下方）。
- **子进程的内存占用没有实测。** 这是唯一会**增加**内存占用的一块，
  而"按需拉起 + 空闲回收"正是为了把它控制住。具体数值要等有空跑起来之后再量。
- **`run_return` 的退出路径与子进程收尾的配合没有实测。**

### 15.1 补的是一个真实缺口，不是"顺手加的"

此前 `push_notification` **不发任何事件**，前端只在自己调用了通知命令之后才刷新
缓存。于是任何**不是由界面发起**的通知都不会出现在通知中心里：

- 后台宿主的定时提醒（**该功能后来被删除**，见 §16 —— 但「非界面发起的通知」
  这条链路本身仍然有效，插件的通知走的就是它）；
- 启动阶段插件加载失败的那条告警；
- 将来模块的后台任务。

具体表现是：通知已经落盘、`get_notification_summary` 也会把它算进未读数，
但**铃铛徽标不变、列表里也看不到** —— 直到用户碰巧触发了某次刷新。
这是"看起来接通了、实际从未通电"的又一例，而且它只在"通知不是用户自己触发"
的时候才显形，正好是后台能力最需要它的场景。

### 15.2 为什么用事件而不是轮询

轮询要为一件大多数时候什么都不发生的事情持续付出代价（IPC + 序列化整份列表），
而事件只在真的变化时发一次。项目里其它跨进程通知（网络询问）也是这么做的。

事件**不带负载**：列表本身仍然从后端读。把列表放进事件负载会让"哪一份是权威"
变成两个可能不一致的来源，而通知列表本来就有一条明确的读取路径。

### 15.3 一个值得记下来的过程：三次假阳性

`check:notifications` 里有一条检查想问"广播时锁有没有释放"。我写了三版，
**三版都是假阳性**，而且都是同一个毛病 —— 用文本模式去推断运行时状态：

1. 跨函数的正则：把"前一个函数的 `lock`"与"后一个函数的 `broadcast`"连了起来；
2. 比较"最后一个 `.lock()` 与最后一个 `{` 的先后"：那个 `{` 属于更外层的函数体，
   于是永远判为"没释放"；
3. 找"广播之前的 `};`"：函数体自身的闭括号与快照块的闭括号形状多样，骗得过它。

假阳性比漏报更糟：**它逼人去"调正则直到通过"，而调完之后这条检查就不再拦得住
真正的错误了。** 因此我停在那里，把这条降级成它真正能可靠判断的事
（广播确实在函数体内），把守卫释放交给两条基于**具体写法**的检查
（"写入与快照在一个作用域里完成"、"`.lock()` 只出现在那个作用域里"），
而"广播必须在锁之外"这个意图写在 `commands.rs` 的注释里、由评审守住。

承认某件事靠人看，好过用一个不可靠的检查假装它被守住了。

### 15.4 尚未验证的部分

- **端到端没有实测。** "后台真的推一条通知 → 界面铃铛立刻出现未读"这条链路
  需要跑应用才能验证，而本机有那个先于应用任何代码的启动阻塞（见 §10.4）。
  可验证的部分是：事件名两侧一致、五个命令都广播、前端装上了订阅 ——
  这三条由 `check:notifications` 的 28 条断言守着。
- **事件在窗口隐藏（托盘）时是否仍被前端收到。** 按 Tauri 的行为应当会
  （事件走 IPC，与窗口可见性无关），但没有实测。

## 十六、第 6b-2 步与后续两步：**已移除**

这一章记录一件被删掉的东西，保留它是因为删除的理由比实现细节更值得记住。

### 16.1 曾经做了什么

第 6b-2 步在 Node 后台宿主里实现了一套**定时任务**（间隔 / 每日 / 一次性），
并为此给协议加了**出站事件**（子进程主动发 `schedule.fired`）；应用侧配上一整套
提醒的定义、校验、持久化、去重，以及设置 → 提醒 的界面。

随后两步又在其上加了**桌面通知窗口**与**全屏提醒**：两个额外的无边框 WebView
窗口，以及它们的定位逻辑。

### 16.2 为什么删掉

用户实测之后的原话是「不算太好」，并要求删除定时提醒与桌面通知。

这个判断值得尊重，而它也有可复核的技术依据 —— 那套东西的复杂度是实打实的：

| 它带来的 | 具体在哪 |
|---|---|
| 协议多出一半 | 事件与响应共用一条 stdout，靠有没有 `id` 区分 |
| 读循环多一个分派分支 | `Frame::Response` / `Frame::Event` |
| 应用侧一整套定义链 | 校验、原子落盘、去重键、`specs_for_host` 推送形态 |
| 子进程无状态的补偿 | 每次新拉起都要重推一遍定义 |
| 两个额外 WebView 窗口 | 各自的 HTML 入口、定位、就绪握手 |

而它换来的能力（"关掉窗口也能提醒"）**在体验上没有被验证过能让人满意** ——
本机那个先于应用任何代码的启动阻塞（见 §10.4）让我们始终没能真正跑起来看它，
所以那套复杂度一直在**没有被验证**的前提下累积。

**通道本身保留。** Node 后台宿主、协议、按需拉起、空闲回收、
「找不到运行时是状态而不是异常」全都在 —— 只有建立在它之上的那一层被拿掉了。
要重新加回"后台能做事"，值得先想清楚它到底要提供什么能力，再动手。

### 16.3 删掉了什么（清单）

- Rust：`desktop/events.rs`、`desktop/notification_window.rs`、
  `background/schedules.rs` 三个文件整删；`protocol.rs` 回到只有请求/响应
  （版本号从 2 降回 1）；`background/mod.rs` 去掉事件处理器与定时任务字段；
  `desktop/commands.rs` 去掉提醒相关的六条命令与全屏提醒的三条；
  `desktop/mod.rs` 去掉 `notifications` 依赖。
- 前端：`services/reminders.ts`、`services/desktopNotify.ts`、
  `components/Settings/ReminderSettings.tsx`、整个 `src/notification-window/`
  目录、两个 HTML 入口。
- 设置页：「提醒」分页整页移除（「通知」分页保留 —— 那是插件用的通知中心，
  与桌面通知窗口是两回事）。
- 门禁：`check-background-scheduler.mjs` 删除；`check-background` 与
  `check-settings-layout` 里对应的断言移除。

### 16.4 一个值得记下的过程教训

剥掉宿主脚本里的调度器时，我是**按行号区间整段剪**的，结果连续三次把不该删的
东西一起删掉了：`handleLine`、`respond`、以及定义在调度常量之间的
`startedAt` / `handled`。

三次都**通过了 `node --check`** —— 因为它们只是"未定义"而不是语法错误，
只有在真的发一条请求时才会抛 `ReferenceError`。抓到它们的是那个
"往 stdin 灌几行 JSON 再看 stdout"的管道自测。

教训是两条，都很具体：

1. **按行号切割是危险的**，尤其当文件里"要实现的东西"与"要删的东西"交错时。
   改成按**函数边界**切、并且切完立刻做一次端到端自测，才是安全的顺序。
2. **`node --check` 证明不了脚本能用。** 一个后台脚本的正确性判据是
   "发一条请求能拿回一条响应"，而那必须真的跑一次。

## 十七、Node 运行时：用户报告的一个真实缺陷

用户的原话：「我打开 cmd，输入 node --version 能出版本，但是软件中无法调用」。

### 20.1 原因不是用户的环境变量

复核后的账很干脆：**`resolve_node()` 只看了两个地方**（环境变量 `MODULITH_NODE`
与 exe 旁边的 `runtime/node.exe`），**没有查 `PATH`**。而 cmd 会查 `PATH`。

```
cmd:  node --version  →  v24.9.0        （走 PATH）
旧版: 后台宿主探测     →  未找到 Node   （只看了前两条）
```

用户会以为是自己环境变量没配好，而其实是应用少找了一个地方。这是一个**我的疏漏**，
不是配置问题。

### 20.2 顺带发现的那个 Windows 坑

查用户机器时发现 `where node` 给出的是**多行**，第一行是：

```
C:\Users\...\dsh-desktop\harness\.desktop-bin\node.cmd     ← .cmd 包装脚本
```

`.cmd` 是批处理脚本，不是可执行文件，`Command::new()` 不能直接跑它。因此查找代码
必须**逐目录确认 `node.exe` 存在**，而不能把裸 `node` 交给系统去解析 ——
后者在 Windows 上会命中那个 `.cmd`。

### 20.3 改成了什么

查找顺序（`plan_node_search`，纯函数可单测）：

| 顺序 | 位置 |
|---|---|
| 1 | 设置 → 性能 里手工指定的路径 |
| 2 | 环境变量 `MODULITH_NODE` |
| 3 | `<应用目录>/runtime/node.exe` 与 `<应用目录>/resources/runtime/node.exe` |
| 4 | 常见安装位置（`ProgramFiles`、`LOCALAPPDATA`、`APPDATA` 下的 `nodejs`） |
| 5 | 系统 `PATH` 的每一个目录 |

第 4 条可以用 `MODULITH_NODE_SEARCH_BASES` **替换** —— 它是给两种情况准备的：
测试要造出"哪里都没有"的前提；用户把 Node 装在非常规前缀下。

界面上加了「Node 运行时」一节（设置 → 性能）：显示找到没有、用的是哪个路径、
失败原因，并提供**手工指定**（选一次就记住，不必改环境变量）。手工指定会
**真的拉起一次后台宿主来验证**，失败时**回滚**设置 —— 留下一个跑不起来的路径
比一次明确的失败糟得多。

### 20.4 一个被门禁抓住的测试缺陷

加了 PATH 查找之后，`a_missing_runtime_yields_a_readable_reason` 立刻失败，
而失败信息是"居然找到了 `C:\Program Files\nodejs\node.exe`"。

这不是实现坏了，是**测试没有造出它的前提**：它只清了 `PATH`，而第 4 条读的是
`ProgramFiles` 等变量，与 `PATH` 无关。修法是让 `plan_node_search` **完全纯粹**
（平台目录作为参数传入，不在它内部读环境变量），测试才能确定地清空它。

顺带修了另一个：断言失败 panic 之后 `ENV_LOCK` 中毒，导致**另外四条无关测试**
都报 `PoisonError`，看起来像四处都坏了。取锁改成 `unwrap_or_else(into_inner)` ——
中毒对这里没有影响（这把锁不保护数据，只做互斥），但它会把一次真实失败放大成
一片虚假失败，真正的原因被埋起来。

### 20.5 Node 怎么"集成进软件"：单文件就够（实测）

`node.exe` 在 Windows 上是**自包含**的。实测：空目录里只放它一个文件，
照样能跑起来并正确加载宿主机脚本：

```
空目录 + 只有一个 node.exe：
  --version                     → v24.15.0
  管道喂一行握手 + background-host.mjs
    → {"v":2,"runtime":"node/v24.15.0", ...}
    → [background] 宿主已启动
```

因此**不需要**同目录的 `npm` / `npx` / `node_modules`（完整目录 200 MB 以上，
单个 `node.exe` 约 87 MB）。

随包分发的机制已经就绪：`bundle.resources` 里有一条 `"runtime/*": "resources/runtime/"`。
**`*` 通配是刻意的** —— 目录为空时构建照常成功。用 fixed 路径会让"没有放 Node"
变成构建错误，那与"它是可选的"矛盾。发布前把 `node.exe` 放进 `src-tauri/runtime/`
即可（87 MB 的二进制不进 git，由发布流程放入）。

详细说明（含三种分发策略的取舍、排查表、手工验证命令）见
`docs/02-开发指南/Node运行时与后台功能.md`。
