### 7.6 产品改名、版本转正、标识重做与主题配色

**产品改名 LoopCore → Modulith Desktop（1.0.0）。**

| 项目 | 旧 | 新 |
| --- | --- | --- |
| 显示名 | `Loop Core` / `LoopCore` | `Modulith Desktop`（简称 `Modulith`） |
| 版本 | `0.3.0`（`dev`） | `1.0.0`（`stable`） |
| 应用标识符 | `com.metazero_tsip.loopcore` | `com.metazero-tsip.modulith` |
| npm / Cargo 包名 | `loopcore` | `modulith-desktop` |
| Rust lib 名 | `loopcore` | `modulith_desktop_lib` |
| 插件宿主对象 | `window.LoopCore` | `window.Modulith` |
| 常量 | `LOOPCORE_VERSION` | `MODULITH_VERSION` |
| 存储键 | `loopcore.theme` / `loopcore.auth.token` | `modulith.theme` / `modulith.auth.token` |

**`engines.loopcore` 当时刻意保持不变**（插件清单的契约字段名，不是产品名）。此处原本写的理由是"改它会让所有已发布插件的清单解析失败、安装被拒"—— **那是错的**：`PluginEngines` 没有 `deny_unknown_fields`，未知键只是被静默忽略，而引擎范围不匹配本来也不阻止安装。这个错误的顾虑让旧产品名多留了六个版本，1.6.0 才改成 `engines.modulith`（见 §7.41 末尾）。

**应用标识符变更会导致既有数据「消失」。** Tauri 不会在 identifier 变化时迁移数据，新目录是空的。因此访问密钥、恢复码、已装插件、侧边栏配置都需要重建。数据仍留在旧目录里，可手动找回。这是改名的一次性代价，已经用户知情同意。

**标识符里的下划线是非法字符，会让打包直接失败。** 改名时曾写成 `com.metazero_tsip.modulith`，保留了下划线，结果 `pnpm tauri build` 在读取配置阶段就报错：

```
The bundle identifier "com.metazero_tsip.modulith" set in `"tauri.conf.json" identifier`.
The bundle identifier string must contain only alphanumeric characters (A-Z, a-z, and 0-9),
hyphens(-), and periods (.).
```

Tauri 对 identifier 只允许**字母数字、连字符、句点**三种字符。下划线不在其中，而它在反向域名式写法里看起来很自然（`metazero_tsip` 是用户名），因此容易写错。这个校验发生在构建早期，`pnpm tauri dev` 同样会失败。

现取值 `com.metazero-tsip.modulith`，即把下划线换成连字符。附带的一次性后果：数据目录从 `%APPDATA%\com.metazero_tsip.modulith` 变为 `%APPDATA%\com.metazero-tsip.modulith`，需要重新设置访问密钥。这也是本次改名周期内第二次因 identifier 变动清空数据 —— 属于命名问题的连带成本，不是设计取舍。

**标识重做（三次迭代，前两版都推翻了）。**

| 版本 | 方案 | 为什么不要 |
| --- | --- | --- |
| v1 | 四格填满 + 中间十字 | 就是个通用的「网格 / 启动器」图标，与产品名无关 |

| v3（采纳） | 整块底 + 三枚方块，**右上角留空** | 空位表达「还可以继续装」，正是「需要什么功能就加什么模块」的字面含义；不对称使它区别于通用网格图标 |

配套处理：

- 三个界面的占位 logo（原先各自内联一份「渐变方块 + 字母 L」，尺寸圆角都不一致）统一到 `src/components/icons/AppLogo.tsx`。

### 7.11 发布前的仓库整备

本轮为首次公开发布做准备。**第一项是真实缺陷，会让任何新 clone 的人构建失败。**

#### `pnpm build` 在全新 clone 上必然失败

| 项目 | 说明 |
| --- | --- |
| 现象 | `pnpm build`（以及 `pnpm tauri build`）在刚 clone 的仓库上失败，`tsc` 报 4 条 `Cannot find module '../generated/...'` |
| 根因 | **两个事实叠加**：① `src/generated/` 是构建期产物，被 `.gitignore` 排除，因此新 clone 里不存在；② 生成它的 `scripts/generate-modules.ts` 原本只在 **Vite 插件**里被调用，也就是只在 `vite build` 阶段运行。而 `build` 脚本把 `tsc` 排在 `vite build` **之前** —— `tsc` 面对一个还没生成的目录 |
| 影响 | 这是开源项目最糟的一类问题：**第一个想试用的人就卡住**。而且它对本机开发者不可见，因为本地 `src/generated/` 一直存在 |
| 处理 | `build` 与 `dev` 脚本都在 `tsc` / `vite` 之前插入 `pnpm gen:modules` |
| 验证 | **实测复现再验证**：先移走 `src/generated/` 复现失败（`tsc` 退出码 2，4 条 TS2307），应用修复后在同一状态下按 `ver check → gen:backend → gen:modules → tsc` 顺序执行，`tsc` 退出码 0 |

**同一个陷阱还有第二个入口。** README 与贡献指南的「提交前检查」都让贡献者直接运行 `npx tsc`，而新 clone 下同样会失败。两处文档都已补上 `pnpm gen:modules` 这一步，并说明「只有直接调用 `tsc` 时才需要留意这个顺序，`pnpm build` / `pnpm dev` 会自动处理」。

#### 其它发布整备

| 项目 | 处理 |
| --- | --- |
| `tsconfig.node.tsbuildinfo` 被跟踪（57.6 KB） | 这是 TypeScript 增量编译缓存，属构建产物。已 `git rm --cached`（保留磁盘文件）并在 `.gitignore` 加入 `*.tsbuildinfo` |
| `.gitignore` 里 `!src/generated/.gitkeep` 指向不存在的文件 | 该例外规则没有对象，且 `src/generated/` 本就不需要入库（生成器会自行 `mkdirSync`）。已改为整体排除 `src/generated/`，并注明不要为它留占位文件 |
| 缺少 `.gitattributes` | Git for Windows 默认 `core.autocrlf=true`，而仓库现有文本文件全是 LF。没有 `.gitattributes` 时，Linux/macOS 贡献者与 CI 会与本地产生换行符不一致，表现为 PR 里整文件 diff。已新增：统一 `eol=lf`，二进制与 `.bat`/`.ps1` 单独声明，锁文件与生成文件标记 `linguist-generated`（GitHub 默认折叠其差异、不计入语言统计） |
| 缺少 `.editorconfig` | 与 `.gitattributes` 分工不同：前者管「仓库里怎么存」，后者管「编辑器写出什么」。已按既有代码风格补齐（两空格、LF、末行换行） |

**这两件事合起来说明一个模式**：`.gitignore` / `.gitattributes` / `.editorconfig` 这类文件平时没有存在感，问题只在**别人第一次接触仓库**时才暴露 —— 与 7.10 节的结论一致。

### 7.13 生成器写时间戳导致不可重复生成

| 项目 | 说明 |
| --- | --- |
| 现象 | 每运行一次 `pnpm gen:backend update`，`src-tauri/src/lib.rs` 与 `modules/mod.rs` 都会显示为已修改，而**内容其实只有一行「生成时间」不同** |
| 根因 | 两个生成器模板的头部写入了 `// 生成时间: ${new Date().toISOString()}`，而这两个文件是**入库**的（不像 `src/generated/` 那样被 gitignore） |
| 影响一 | **每次都弄脏工作区**。任何贡献者构建一次就会看到两个「已修改」文件，容易误提交、也干扰 `git status` 的判断 |
| 影响二 | **让「生成器一致性」的 CI 检查无法成立。**该项检查的做法是「跑一遍生成器，然后 `git diff --exit-code`」；只要输出含时间戳，这个 diff 必然非空，检查会永远失败 —— 也就是说它会变成一个没人能修的红色门禁 |
| 处理 | 从两个模板头部移除生成时间行，改为说明「刻意不写时间戳」的原因。生成结果因此**可重复**：同一份源码无论生成多少次，产物逐字节一致 |
| 验证 | 连续生成两次并比对文件哈希，结果一致；生成后 `git status` 对这两个文件为干净 |
| 追溯方式 | 需要知道生成时间时查 git 历史即可。前端生成产物仍有 `generation.log.json` 记录（它被 gitignore，不受此问题影响） |

**这个问题值得记住的地方在于它是我自己引入的。**「生成后 diff 为空」这道检查是可靠的 CI 门禁设计，但在**生成不可重复**的前提下它只会制造一个永远修不好的红灯。检查与生成器的可重复性是**配套要求**：只加检查而不保证幂等，等于给项目装了一个必然失败的闸门。

### 7.20 开发模式下「检查更新」必然失败一次

| 项目 | 说明 |
| --- | --- |
| 现象 | `pnpm tauri dev` 里点「设置 → 关于 → 检查更新」，报 `None of the fallback platforms ["windows-x86_64"] were found in the response platforms object`。看起来像发布清单坏了 |
| 根因 | Tauri 在**打包**时把包类型就地写进可执行文件（`__TAURI_BUNDLE_TYPE`，取值 `UNK` / `MSI` / `NSS` 等，都是定长三字符所以能原地改）。dev 跑的是未打包产物，标记仍是 `UNK`，`bundle_type()` 返回 `None` → updater 只去清单里找**裸键** `windows-x86_64`。而发布清单按设计只写 `windows-x86_64-msi` / `windows-x86_64-nsis`（带包类型的键），两者对不上 |
| 佐证 | 报错里打印的是**完整候选列表**，不是只有兜底项（`updater.rs` 的 `get_urls` 在全部候选都失败后 `Err(TargetsNotFound(targets))`）。列表只有**一个**元素 ⇒ `installer` 是 `None` ⇒ 进程没有包类型标记 ⇒ 一定不是安装版。安装版的 `modulith-desktop.exe` 里该字符串是 `__TAURI_BUNDLE_TYPE_VAR_NSS`，与未打包产物的 `..._VAR_UNK` 在同一偏移上只差三个字符 |
| 处理 | `describeUpdateError()`（`src/services/appUpdater.ts`）在**开发模式下**为这条报错追加一句说明与「本地清单请用 `windows-x86_64` 键」的提示 |
| 为什么只在开发模式下追加 | 正式版出现同一条报错说明清单**真的**缺了键，那时任何「这是正常的」都是误导。这个错必须保持刺眼 |
| 教训 | 「只在开发模式出现的失败」必须以开发模式的方式解释。否则它会以「更新功能坏了」的形式消耗排查时间 —— 尤其当它出现在一个刚做完、还没来得及验证的功能上时，最自然的结论就是自己写错了 |

### 7.23 用户配置的下载源改不到应用更新：官方前端插件的结构性限制

| 项目 | 说明 |
| --- | --- |
| 背景 | 有用户报告内网/受限网络下「检查更新能查到新版本，下载却卡住/失败」。上一个版本刚修过另一个地址问题（清单里的资产名与 GitHub 实际存储的名字差一个转义），因此第一反应是清单又坏了 |
| 根因 | 与清单无关。官方前端 API（`@tauri-apps/plugin-updater`）的两处地址都不可配：**清单地址**来自 `tauri.conf.json` 的 `plugins.updater.endpoints`，在插件初始化时固定；**安装包地址**根本不在插件配置里，而是清单文件自己写的 `platforms.<target>.url`（指向 `github.com/.../releases/download/...`）。因此「清单能换个地址取、安装包不能」是这个结构的必然结果 |
| 处理 | 检查与安装都搬到 `src-tauri/src/modules/updater/commands.rs`：清单地址经 `UpdaterBuilder::endpoints()` 传入，安装包地址在 `check()` 之后改写公开字段 `update.download_url`。下载、签名校验与调起安装程序仍然全部由官方插件完成，公钥仍然取自同一个 `plugins.updater` 块 |
| 配套的加固 | `capabilities/default.json` 移除了 `updater:default`。插件与宿主共用同一个 JS 上下文，若官方插件的命令仍然可达，插件代码就能绕开下载源直接调用它 —— 那样这个设置项就只对守规矩的调用者生效 |
| 残留的不一致 | 加速源地址允许 http 的唯一情形是本机回环（本地调试），但**官方更新器在 release 版拒绝非 https 的清单地址**，因此 http 回环加速源只对插件市场有效。这条不一致在更新失败时会给出明确提示，而不是一个看起来像清单坏了的报错 |
| 另一个残留 | `@tauri-apps/plugin-updater` 仍留在 `package.json` 的依赖里（不再被 import）。删除依赖需要重新生成 `pnpm-lock.yaml`，那次改动单独做更清楚 |
| 教训 | **「哪些地址可以被用户配置」不是界面上的事，而是调用栈的事。** 只要有一处地址由第三方代码在初始化时固定，用户设置就必然在其中某一段上失效 —— 而失效的那一段恰好是最容易失败的一段（大文件下载） |

### 7.29 发行版毛玻璃失效、插件说明的 Markdown 渲染，以及一处新发现的注入面

#### 只在发行版复现：毛玻璃开关完全失效

**类别：** 缺陷（已修复）

**现象。** `pnpm tauri dev` 里开关毛玻璃一切正常；**打包出来的安装版**里，开启或关闭它都没有任何反应。

**根因在构建阶段，不在运行逻辑。** `index.css` 里那一对声明原本写作：

```css
backdrop-filter: none !important;
-webkit-backdrop-filter: none !important;
```

CSS 压缩器把它们判定为"同一件事的两种写法"并去重，而它删掉的是**标准的那一份**。产物里于是只剩 `-webkit-backdrop-filter`：

```css
:root.lc-no-glass *,:root.lc-no-glass :before,:root.lc-no-glass :after{-webkit-backdrop-filter:none!important}
```

开发服务器不做这层压缩，两份都在，所以开发时看不出任何问题。

**为什么是"我手写前缀"导致的。** 压缩器本来就会按目标浏览器自己补前缀 —— 产物里 Tailwind 的工具类两份都在（各 6 处），就是它补的。**手写前缀等于替工具做决定，而工具会因此删掉另一份。** 去掉手写的那一行之后，产物里两行都回来了：

```css
:root.lc-no-glass *,:root.lc-no-glass :before,:root.lc-no-glass :after{-webkit-backdrop-filter:none!important;backdrop-filter:none!important}
```

**处理。** 源码里只写标准声明；新增两个断言：`check:performance` 要求源码里**不出现**手写的 `-webkit-backdrop-filter`，`check:theme` 的第 7 节**直接读 `dist/assets/*.css`**，要求产物里两份声明都在。

**这条教训比修复本身更值得记住：「源码里写了」不等于「产物里有」。** 压缩、tree-shaking、按目标浏览器降级都会改写产物，而它们失败时是静默的 —— 不报错、类型检查也过。因此 `check:theme` 成了全项目第一处对 **Vite 的 `dist/` 产物**做断言的检查（`check:samples` 检查的 `.lcp` 是仓库里手工打包的示例，不是构建产物）。它的代价是必须先 `pnpm build`（否则那一节会显式打印"跳过"，不会伪装成成功）。

#### 插件说明改为 Markdown 渲染

**类别：** 已实现

市场（以及已安装插件的详情页）此前把 README 直接铺在 `<pre>` 里，`#`、`**`、`- `、表格竖线全部原样露出，长说明基本没法读。现在按 Markdown 渲染。

**安全模型是这次的要点，而不是顺手做的样式改动。** README 是从插件仓库按 tag 取回的**远程内容**，而插件与宿主运行在同一个 WebView、同一个 JS 上下文里（第 4.4 节）。因此这里**没有**采用"把 Markdown 拼成 HTML 再交给消毒库"的常见做法，而是：

- 解析成 AST，由 React 渲染成元素。源码里的 `<script>`、`<img onerror=…>` 之类**在结构上只能作为文本显示** —— 不是"记得消毒"的约定，而是类型上没有那条通路。
- 只承认 `http` / `https` / `mailto`，其余协议（`javascript:`、`data:`、`file:`…）按原文显示：既可读，也不可点。
- 链接点击一律 `preventDefault()` 后交给系统浏览器。否则点一下说明里的链接会让**整个应用界面被替换掉**，比打不开更糟。
- 说明里的图片不自动加载，而是显示为可点击的链接 —— 直接渲染 `<img>` 等于让"打开插件详情"这个动作隐式向第三方主机发一次请求。

**子集是按实测数据划的**（9 个 README、53.7 KB）：标题 86、粗体 81、行内代码 113、围栏代码块 18、表格 106 行、无序列表 29、有序列表 9、引用 6、链接 11、图片 0，**没有嵌套列表、没有列表续行**。因此不支持嵌套列表与引用块内的多段落 —— 遇到时会降级为纯文本显示，而不是消失。**内联 HTML 有意不支持**（理由见上）。

**为什么自己写而不是引库。** 一是安全：常见库的产物是 HTML 字符串，等于把上面那条结构性保证换成一条需要长期维护的消毒链路。二是子集足够小。`scripts/check-markdown.ts` 有 86 项断言盯着它，其中最重要的一组针对的是**"静默吞掉一段文字"**这类失败 —— 例如 `plugin_storage_get`、`sidebar_config.json` 这类标识符绝不能被下划线强调规则吃掉（插件 README 里到处是这种名字）。

（顺带一提，解析器**没有增大入口 chunk**：它只被市场与插件页引用，而那两个模块本身是懒加载的，因此自然落进一个 8.9 KB 的独立 chunk。）

#### 顺带修掉：一个 `private_interfaces` 警告

`backup::archive` 的 `collect_entries` 是 `pub` 而返回类型 `CollectedEntry` 是私有的。这个警告指出的其实是真实的设计问题：一个只在本模块内使用、且带着磁盘绝对路径的内部表示，被暴露在了模块边界上。已改为私有。

#### 新发现、**未处理**：图标的内联 SVG 注入

**类别：** 设计取舍（当前模型下不构成提权，但有值得处理的理由）

`ModuleIcon.tsx` 与 `PluginIcon.tsx` 各有一次 `dangerouslySetInnerHTML`，用来注入模块与插件的**内联 SVG 图标**。唯一的判据是 `isSvgMarkup`，而它只检查字符串是否以 `<svg` 开头 —— **不检查 `<script>`、`on*=` 事件属性或 SVG 内的外部引用**。

**为什么当前不算提权。** 这两处注入的内容来自内建模块的 `module.toml`（随应用发布）与**已安装**插件的清单。而已安装插件的 bundle 本来就已经在这个 JS 上下文里执行过了（4.4 节），给它一个注入点并不增加它能做的事。市场（**未安装**的插件）刻意绕开了这条路：把 SVG 转成 `data:` URL 交给 `<img>`，而 `<img>` 里的 SVG 不执行脚本。

**但有两条理由值得处理：**

1. **这个判据有 4 份副本，且已经漂移了。** `ModuleIcon.tsx`、`pluginRuntime.ts`、`pluginMarket.ts` 都是 `trimStart().toLowerCase().startsWith('<svg')`，而 `PluginIcon.tsx` 那份**漏了 `toLowerCase()`**。后果是同一个插件图标在插件卡片与侧边栏的表现可能不一致（大写 `<SVG` 在一处被识别、在另一处不被识别）。这与项目自己反复记录过的「复制一份必然漂移」是同一件事。
2. **这条注入面一旦被新路径复用就会变成真问题**：只要将来有一处让**未安装**插件的 `iconSvg` 走到这两个组件，它就是一个可执行的注入点。`scripts/check-markdown.ts` 现在把「注入 HTML 的文件集合恰好是这两处」钉成了断言，因此**新增**的注入会失败；但这两处**已有**的注入仍只受一个弱判据保护。

**建议。** 把 4 份 `isSvgMarkup` 收敛成一处共享实现，并在那里把判据从"以 `<svg` 开头"加强为"以 `<svg` 开头，且不含 `<script`、`<foreignObject`、`on<字母>=`、`javascript:`"。这不改变当前模型的信任边界，但把"图标渲染"从"依赖调用方自觉"变成"判据自己就够用"。属于独立的一小轮。
