### 7.8 审阅修复：构建链路、插件 ID 路径穿越与外壳依赖

本轮由一次独立审阅触发：逐条核对「文档声称」与「代码实际」，把不符的部分修掉或如实记录。**其中前两项是真实缺陷，不只是文档问题。**

#### 前端类型检查失败，发布构建链路是断的

| 项目 | 说明 |
| --- | --- |
| 现象 | `npx tsc -p tsconfig.json --noEmit` 退出码 2，`src/services/commandRegistry.ts` 有 8 处 `TS6133`（未使用导入）：`activateRelativeTab`、`setAccentId`、`getAppDataDir`、`getCachedSettings`、`ACCENT_THEMES`、`requestSearchFocus`、`registerShortcuts`、`openPath` |
| 影响 | `package.json` 的 `build` 是 `tsc && vite build`，而 `tauri.conf.json` 的 `beforeBuildCommand` 是 `pnpm build` —— **`pnpm tauri build` 必然失败**。README 的「提交前检查」第一条命令当时就是红的 |
| 根因 | `commandRegistry.ts` 在 `tsconfig` 的 `noUnusedLocals: true` 下遗留了重构后的死导入 |
| 处理 | 删除这 8 个导入，`tsc` 恢复退出码 0 |

**这条值得记住的教训**：类型检查不是「没报错就没事」，而是「不跑就不知道」。这些导入在 `vite dev` 下完全无害（打包器会摇树掉），因此日常开发不会暴露，只有真正执行 `tsc` 才看得见。

#### 插件 ID 未校验导致路径穿越（安全问题）

| 项目 | 说明 |
| --- | --- |
| 现象 | `PluginManager::storage_clear` **完全没有** ID 守卫，直接 `remove_dir_all(plugin_data_dir(id))`；而 `plugin_data_dir` 是未校验的 `data_dir.join(id)`。命令层 `plugin_storage_clear` 也不校验 |
| 利用路径 | `id = ".."` → 目标解析为 `<app_data>/plugin_data/..`，即应用数据目录本身 → `remove_dir_all` 会把 `settings.json` / `auth.json` / `notifications.json` / `sidebar_config.json` 连同全部插件数据一起删掉 |
| 第二条路径 | `uninstall` 的守卫是 `validator::is_within(&plugins_dir, &plugins_dir.join(id))`，而 `is_within` 是纯前缀比较，`candidate == root` 时返回 **true**。`id = "."`（或 `plugin_data/..`）使目标规范化后等于 `plugins_dir`，守卫放行 → 整个 `plugins/` 目录被删，**包括 `registry.json`** |
| 为何危险 | docs 自己承认「插件可以直接 `invoke` 任意后端命令」，而这几个命令**不带 token 参数**。因此一个插件无需经 `ctx.storage` 就能直接触发，不需要任何权限声明 |
| 处理 | ① `validator::is_valid_plugin_name` 提升为 `pub`，并新增 `manager::validate_plugin_id`；② `plugin_data_dir` 改为**带校验**的入口（返回 `PluginResult<PathBuf>`），所有调用点因此自动受保护 —— 校验收在一处，漏掉任一调用点就等于没有防护；③ `uninstall` 开头显式校验 ID，`storage_clear` 增加「目标必须严格位于 `data_dir` 之下」的不变量检查；④ `is_within` 改为要求 `candidate != root` |
| 回归测试 | 新增 `plugin_name_rejects_path_traversal_inputs`（14 个穿越取值）与 `is_within_rejects_root_itself`。**后者已验证过有效性**：临时还原旧的纯前缀比较后该测试确实 FAILED，恢复修复后转绿 |

**`is_within` 的语义修正值得单独记住。** 它的两个调用点都是**删除**语义，而 `root` 自身作为删除目标一定是误用 —— 调用方要的是「root 里的某个条目」。只比较前缀是这类守卫最典型的错误写法，因为它同时放行了 `root` 本身与所有 `root/../...` 绕回 `root` 的路径。

#### 外壳对业务模块的静态依赖（架构不变式不成立）

| 项目 | 说明 |
| --- | --- |
| 现象 | 架构总览第 1 节主张「框架代码中不存在任何对具体业务模块的引用」，据此推出「删除任意内建模块，框架仍能编译并运行」。但 `SettingsDialog.tsx` **静态导入**了 `../../modules/plugins/Plugins` 并在「插件」分页渲染它 |
| 影响 | 删掉 `src/modules/plugins/` 会让外壳编译失败，上面两条结论都不成立 |
| 处理 | 新增 `src/components/ModuleEmbed.tsx`，设置页改用它内嵌 |

**实测得到的、与直觉相反的结论：把静态 import 改成动态 `import('../modules/plugins/Plugins')` 并不够。** TypeScript 仍会对字面量说明符做静态解析，模块缺失时报的仍是 `TS2307`。实测过程：移走 `src/modules/plugins/` 并重新生成注册表（生成器正确产出「2 modules」）后，报错只剩这一条。**把说明符换成变量**（`import(specifier)` 配 `/* @vite-ignore */`）之后才真正编译通过。

验证方式（两个方向都实测过，不是推断）：

| 场景 | 结果 |
| --- | --- |
| 保留模块 → `tsc` | 通过 |
| 移走模块 + 重新生成注册表 → `tsc` | **通过**（不变式成立） |

代价如实记录：该模块不再被 Vite 预打包，改为首次打开「设置 → 插件」时按需加载；模块真的被删除时，错误发生在**打开设置页的那一刻**而不是构建期，因此 `ModuleEmbed` 用错误边界把它降级成一条可读提示，而不是冒到顶层变成整窗错误页。

### 7.14 插件 storage 权限补强制

| 项目 | 说明 |
| --- | --- |
| 背景 | 权限枚举有 11 个取值，但只有 `network`、`network-external`、`notification`、`plugin-communicate` 四项真的生效。`storage` 属于「写进清单也不改变行为」的一类 |
| 触发原因 | 计划新增的「快捷启动」插件会执行外部程序，必然要配一条新权限。若清单里的权限不产生任何约束，那条新权限同样是空话 —— 因此先补齐强制机制，再加能力 |
| 处理 | ① 新增 `PluginManager::require_permission`，作为权限检查的**唯一入口**；② 新增 `checked_storage_dir`，五个 `plugin_storage_*` 方法（`get`/`set`/`delete` 经 `storage_path`，`keys`/`clear` 直接调用）全部经它取目录，因此 `storage` 检查只有一个执行点；③ 新增 `PluginPermission::as_str()`，用于生成可读的错误信息 |
| 为何收在一处 | 与 7.8 的 `plugin_data_dir` 同理：检查散落在各个命令里时，漏掉任何一处就等于没有防护，而且漏掉的那处**没有任何症状**。`uninstall` 仍直接使用 `plugin_data_dir` —— 内部清理不该受插件自身权限声明约束 |
| 行为变化 | **未声明 `storage` 的插件，调用 `ctx.storage` 任意方法都会被拒绝**（错误信息为「插件 X 未声明 storage 权限」）。此前是静默可用。仓库内示例插件一直声明着该权限，不受影响 |
| 判定规则 | 纯函数 `ensure_permission`：**没声明就是拒绝**，不做默认放行、也不按 `sandboxLevel` 推断 |
| 为何抽成纯函数 | `PluginManager` 持有 `AppHandle`，单测里造不出来。判定与 IO 分离后，规则本身可以被测试锁定 |
| 测试 | 新增 5 条：未声明被拒、已声明放行、**只声明 `network` 不放行 `storage`**（防止把检查写成「有任意权限就放行」）、错误信息包含权限名、`as_str()` 与 serde 的 kebab-case 序列化逐个一致 |
| 验证方式 | 用临时改动把 `ensure_permission` 改成恒返回 `Ok(())`（等价于修复前的行为），确认其中 3 条测试**确实失败**，再还原 —— 否则无法证明这些测试不是在空过 |
| 边界（重要） | 这**不是**插件之间的隔离边界。命令的 `id` 来自调用方，插件仍可直接 `invoke` 指定他人 ID 读取其存储。本次修的是「声明是否生效」，不是「越权访问」（见 4.1 节） |
| 文档同步 | [插件系统架构](../02-开发指南/插件开发/插件系统架构.md) 6.1 与 6.2、[清单文件参考](../02-开发指南/插件开发/清单文件参考.md) 第 4 节、[宿主API参考](../02-开发指南/插件开发/宿主API参考.md) 第 2 节 |

**一句话总结这次改动的性质**：它让权限列表从「意图声明」变成「有效声明」，但**没有**把插件之间隔开 —— 那需要进程级隔离，不是加几行检查能做到的。把这两件事混为一谈，才是真正危险的地方。

### 7.15 快捷启动插件与 process-spawn 权限

| 项目 | 说明 |
| --- | --- |
| 目标 | 做一个「把常用程序收在一处、点一下就打开」的插件。它是第一个**需要宿主提供原生能力**的插件，因此也是插件体系的一次真实检验 |
| 为何先补权限强制 | 该插件要执行外部程序，必须配一条新权限。若清单里的权限不产生约束，那条新权限同样是空话 —— 因此 7.14 先行 |
| 新增权限 | `process-spawn`。语义比 `open-external` 更准确，也更该在安装时让人停下来看一眼 |
| 新增命令 | `plugin_launch_program(id, program, args?)`，注册后后端命令数 60 → 61（plugins 模块 18 → 19） |
| 权限检查位置 | Rust 侧 `launch_program` 的首行，复用 7.14 的 `require_permission`。前端 `ctx.launcher` **不做**重复判断 —— 检查应落在动作真正发生的一侧，两边各判一次只会多出一套可能分叉的规则 |
| 路径规则 | 必须绝对路径、必须已存在、必须是文件；经 `canonicalize` 归一化后使用 |
| 这条规则的边界 | 它**拦不住** `C:\Windows\System32\cmd.exe`（同样是绝对路径）。目的不是沙箱，而是让「要执行什么」在代码与清单里显式可见，而不是藏在一个短名字后面。插件本就被视为本机程序（见第 8 节威胁模型） |
| 参数处理 | 作为独立 argv 项传给 `Command::args`，不拼命令行字符串，因此不存在引号 / `&&` / `|` 注入。限制为最多 64 个、单个不超过 4096 字符 |
| 生命周期 | `spawn` 后不 `wait`。快捷启动的语义就是「把它叫起来」，宿主没有理由陪着子进程活着 |
| 为何不用 opener 插件 | 宿主已装 `tauri-plugin-opener`，但它当前的能力范围被有意限制在 `$APPDATA` / `$APPLOCALDATA`（见 `capabilities/default.json`，用于「打开数据目录」等两处调用）。为快捷启动放开到任意路径，会同时削弱那两处既有限制。改为自建命令后，限制落在插件权限模型里，是用户能在插件详情页看到的那一条 |
| 示例插件 | `samples/quick-launch`：手写 IIFE（无构建步骤，示例的核心价值是可读可复制）、自带 `index.css`（Tailwind 在构建宿主时扫描源码，运行时注入的类名不会被生成）、`main` 指向根目录的 `index.js`（避开被 gitignore 的 `dist/`） |
| 测试 | 新增 9 条：权限未声明被拒、已声明放行、相对路径/裸程序名被拒、空值与 NUL 被拒、不存在的路径被拒、目录被拒、真实绝对路径通过、参数规模受限、示例清单能通过 `validate_manifest` 且声明了它实际用到的两项权限 |
| 最后一条测试的意义 | 权限被真正强制之后，「代码用了 `ctx.storage` / `ctx.launcher`，清单却忘了声明」会变成**运行时才暴露**的错误。把它提前到测试里，改示例时不会漏 |

**这件事验证了什么。** 插件体系此前只有 `hello-plugin` 一个示范，它不需要任何原生能力，因此「宿主给插件提供能力」这条路径从未被真正走过。走完之后暴露出一个此前只在文档里写着的约束：**插件能做什么，取决于宿主是否愿意为它开一个口子，而每个口子都必须配一条能被强制、且用户能看见的权限。** 先补强制再加能力，顺序不能反。

（那个示范插件后来被 `samples/notes` 取代 —— 它只是个测试件，功能却还值得留下，见 7.17。）

### 7.16 快捷启动插件完整化：三项宿主能力

| 项目 | 说明 |
| --- | --- |
| 背景 | 7.15 交付的版本只有「添加/打开/删除」，形态过于简陋。这一轮按完整的产品要求重做，并补上它需要的三项宿主能力 |
| 新增命令 | `plugin_extract_icon`、`plugin_reveal_in_folder`。后端命令数 61 → 63（plugins 模块 19 → 21） |
| 新增前端服务 | 宿主侧 `src/services/fileDrop.ts`（订阅 Tauri 窗口级拖放并向多个订阅者扇出）；插件上下文新增 `ctx.icons` / `ctx.shell` / `ctx.fileDrop` |
| 权限归属 | 三项能力**同归 `filesystem-read`**，没有新增权限枚举值。理由：它们获取的都是「本机文件是什么、在哪里」这一类信息，语义上属于同一层；拆成三个新权限只会让插件详情页更难读，而用户并不会因此获得更细的控制力。副作用是 `filesystem-read` 从「声明了也不生效」变成了真正生效的一项 |
| 新增依赖 | `windows-sys = "0.61"`，且只在 `[target.'cfg(windows)'.dependencies]` 下。选它而不是 `windows`：只需要几个 Win32 函数的裸声明，不需要 COM 包装与 Result 化 |
| 图标提取实现 | `PrivateExtractIconsW`（可取任意尺寸，这里用 64×64）→ `GetIconInfo` → `GetDIBits` 取 32bpp BGRA → 转 RGBA → 自写 PNG 编码。**alpha 有两套来源**：32bpp 数据里可能是全 0，此时必须回退到 1bpp 的 AND 掩码，否则图标会变成黑色方块 |
| 为什么不引 PNG 库 | 本项目一贯刻意不引依赖。PNG 的最小可用子集很小 —— 只用 zlib 的**非压缩存储块**，因此不需要 deflate 实现，代价是文件偏大（64×64 约 16 KB）。crc32 / adler32 / 块结构都由测试锁住 |
| GDI 资源泄漏 | `GetIconInfo` 借出的 `hbmColor` / `hbmMask`、以及 `CreateCompatibleDC` 的 DC、`PrivateExtractIconsW` 的 HICON **全部**要在同一函数内释放。GDI 对象有进程级上限，泄漏足够多次会让整个应用画不出东西 —— 因此释放路径刻意写成「无论哪一步失败都会走到」 |
| 拖放为何必须宿主转发 | Tauri 的 `dragDropEnabled` 默认 `true` 时会拦截系统拖放（此时 WebView 内 HTML5 拖放整体不可用），而 `withGlobalTauri` 未开启，插件拿不到 `window.__TAURI__`。两条相加 ⇒ **插件无法自行接收拖入路径**，只能由宿主订阅 `onDragDropEvent` 再转发 |
| 拖放的副作用（未做） | 同一个拦截导致**卡片不能拖到分组上** —— HTML5 `draggable` / `drop` 不可用，要做得自己用指针事件实现一遍。本轮改用右键菜单归类，并在插件 README 与宿主 API 参考里如实标注，没有把「拖拽整理」算作已实现 |
| 拖放的权限边界 | `fileDrop` 的检查在前端（事件不产生 IPC 之外的动作），但它送来的是本机路径，因此与图标、定位同归 `filesystem-read`；未声明时降级为空订阅 + 一次告警，与 `notifications` 的处理一致 |
| 插件重做 | 视图三档（网格/列表/紧凑）、分组筛选与增删改、右键菜单（打开/定位/编辑/复制路径/移入分组/删除）、备注与悬浮显示、编辑对话框；卡片上不放任何按钮 |
| 图标存储策略 | 每个条目的图标单独存 `icon.<条目ID>`，不塞进主状态数组 —— 否则「改个名字」也要重写几十 KB × N 的图标数据。键名用 `.` 而非 `:`，因为存储键只允许字母数字与 `.` `_` `-` |
| 存储向前兼容 | `normalizeState()` 兼容最早那版「直接把数组存在 `shortcuts` 下」的格式。用户数据只有一份，读的时候容错比写的时候谨慎更重要 |
| 测试 | 新增 9 条（总数 138 → 147），全部在 `icon.rs`：crc32 与 adler32 的标准向量、块结构逐块重算 CRC、IHDR 字段、IDAT 的 zlib 头与尾部 Adler-32、存储块 LEN/NLEN 互补、BFINAL 置位、**从真实 exe 取图标**、无图标资源文件明确失败 |
| 最后两条为何关键 | 前面七条只覆盖 PNG 编码 —— 即使 Win32 那段全写错，它们照样全绿。`extracts_icon_from_a_real_executable` 是唯一真正走通 FFI 的测试，它还额外断言像素缓冲**非全零**（全零通常意味着 `GetDIBits` 没写进去） |

**这轮的教训与 7.14 一脉相承**：加能力之前先问「它的权限检查落在哪一侧」。三项能力里有两项的动作发生在 Rust（图标由 GDI 取、定位由 Shell 做），一项发生在窗口事件上；分不清这一点就会把检查放错层，而在前端放一个「看起来在检查」的判断，比不检查更糟 —— 它给人已经管住了的错觉。

| 项目 | 说明 |
| --- | --- |

| 新增测试 | 音频扩展名白名单 2 条（大小写不敏感 + 拒绝非音频；过滤器与校验一致）。总数 147 → 151 |
| 示例包校验扩到全部三个 | `extracts_and_validates_real_sample_lcps` 逐个解压、校验清单，并**逐字节比对源码目录与包内文件** |
| 为什么加逐字节比对 | 「改完插件忘记重新打包」这个错误**我自己犯过两次**，两次都是靠肉眼发现。现在源码一改而包没重打，测试立刻红并直接说出「忘记重新打包了」 |
| 已知限制（快捷键） | 宿主有 `services/shortcutRegistry.ts`，但**没有暴露给插件**。因此 notes 的快捷键是自己挂 `window` 监听实现的，靠 `useModuleActive()` 判断可见性来避免抢键。让插件贡献快捷键是明确该做但尚未做的事 |
| 已知限制（运行时机） | 插件代码在**插件加载时**执行，模块是否挂载不影响它。因此 pomodoro 的计时只要插件处于启用状态就会运行；反过来，插件被禁用时任何后台行为都不会发生 |

**这轮补上的是「示例的可用性与可信度」。** 之前的示例能跑，但它证明不了「一个真实插件该怎么组织数据、怎么处理保存时机、怎么在后台活着」。三份示例现在各占一个难度台阶，且都被测试守着 —— 包括那个「包与源码必须一致」的检查，它防的正是我自己反复犯的错。

### 7.30 插件不再是模块：贡献模型与按需激活

**类别：** 架构调整（兼容，MINOR）

#### 解决的具体问题

**「功能性插件」此前不可能存在。** 加载成功的判据是「至少注册了一个模块」（`pluginRuntime.ts`），于是：

- 一个只往命令面板加几条动作的插件；
- 一个只做后台监听、没有任何界面的插件；
- 一个只贡献设置项的插件；

都会被判为**加载失败**，在插件页显示为「异常」。侧边栏因此等于插件列表 —— 装 500 个插件就是 500 行。

#### 做法：把「声明」与「执行」分开

`contributes` 与 `activationEvents` 两个字段**此前已被解析、但没有任何消费方**（见 4.6 节）。这一轮把它们变成真：

| 阶段 | 做什么 | 是否执行插件代码 |
| --- | --- | --- |
| 第一趟 | 读清单 → 模块条目进目录、命令条目进面板、设置项登记、右键菜单项登记 | **否** |
| 第二趟 | 只对 `eager` 的插件执行 bundle | 是 |

`eager` 的判据：旧式插件（没有 `contributes`）、显式声明 `onStartup`、或声明了 `contributes` 但没有可用激活事件。

#### 兼容规则（为什么它是 MINOR 而不是 MAJOR）

| 清单 | 结果 |
| --- | --- |
| 没有 `contributes` | **与 1.2.0 之前逐字一致** |
| 有 `contributes` + `activationEvents` | 声明式 + 按需激活 |
| 有 `contributes` + 没有 `activationEvents` | 声明式，但**降级为加载期激活** |

第三行是刻意的取舍：**忘写激活事件只应该损失「懒」，不应该让插件坏掉。** 反过来（默认不激活）会把一个配置疏漏放大成「点开是空白」。

这一条由 `scripts/check-contributions.ts` 第 8 节对着**已有插件仓库里的全部 9 个 manifest** 实测：全部归类为「旧式 / 加载期执行」。

#### 落地的四个贡献点

| 贡献点 | 宿主消费位置 | 需要新 API 吗 |
| --- | --- | --- |
| `modules` | 侧边栏、搜索、深链 | 否 —— `registerModule({ id, component })` 只是把组件交给已声明的 ID |
| `commands` | 全局搜索（Ctrl+K） | 否 —— 声明期登记条目，激活期 `registerCommand` 绑定 handler |
| `settings` | 设置 →「插件设置」 | **否，零代码贡献** —— 宿主照声明渲染，值走已有的 `plugin_storage_*` |
| `contextMenus` | 外壳右键菜单 | 否 —— 菜单项执行的是**一条已声明的命令** |

新增的宿主 API 只有两样：**`ctx.disposables` / `Modulith.onDeactivate()`**（收尾）与 **`Modulith.capabilities`**（特性探测）。

#### 顺带补上的一个真空：卸载时的收尾

此前项目里**没有任何 teardown 路径**：`types/plugin.ts` 的 `activate`/`deactivate` 是明写的草案、Rust 的 `Module::stop()` 从未被调用、`cleanupPluginResources` 只清宿主**知道**的东西。

这对模块型插件无所谓，对功能型插件是致命的：后台服务创建的定时器、窗口监听、观察者、连接，宿主一个都不知道，禁用之后全部泄漏。现在它们由 `ctx.disposables.add()` 登记，宿主在卸载时**逆序**执行、单个抛错不牵连其余、每个只执行一次。

#### 为架构级更新做了什么准备

这一轮**不是**沙箱，但它解掉了沙箱的结构性阻塞点：

1. **`registerModule` 传的是 React 组件对象，`registerCommand` 传的是函数对象 —— 这两样跨不了 realm。** 声明式贡献把它们变成「清单里的 ID + 按 ID 调用的 handler」，这是它们能跨进程的唯一形态。
2. **宿主不再需要「先执行插件才知道它有什么」。** 隔离之后「执行」是一次远程调用，而界面必须在它之前就画得出来。
3. **离真正隔离只剩两处需要动：** 把这两个函数改成 RPC、把 `ctx` 服务改成可序列化调用。其余 API（storage / http / notifications / events / launcher / icons / shell / fileDrop / audio / settings）本来就是「传值进来、返回值出去」的形态。

#### 仍未做的（如实记录）

- **顶层同步死循环仍然无法被中断。** 错峰激活只是把执行摊开，不是沙箱。这条要等独立进程 / Web Worker。
- **稳定性夹具已建立，但只覆盖了机制、没有覆盖规模。** 见 7.31 节 —— 它验证的是「未激活就不执行」「按需激活」「收尾」「冲突拒绝」这些**机制**；「500 个插件装上去会怎样」需要一套**生成出来**的夹具，而不是手写的 8 个。
- **声明式模块的 SVG 图标是后台补的。** 建立目录时不读图标文件（500 个插件就是 500 次 IPC），改由错峰 pass 读回并通知目录。在此之前侧边栏显示回退图标。
- **`isSvgMarkup` 的 4 份副本**（见 7.29 节）仍未收敛 —— 这一轮没有碰它。

#### 一处被顺手修正的文档不实

`清单文件参考` 此前写 `activationEvents` / `contributes` 是「预留字段，当前无消费方」，`插件系统架构` 的宿主 API 表也漏了 `registerCommand` 与 `useModuleActive`。两处都已按代码事实更新，并由 `check-contributions` 对源码断言以防再次漂移。

### 7.31 插件运行时稳定性夹具

**类别：** 测试基础设施（新增）

#### 背景：此前没有一条途径能验证「插件代码到底跑没跑」

1.2.0 的贡献模型把「插件存在」与「插件执行」拆成了两件事，而这件事**只能靠运行来验证**：目录里有没有某个条目、命令面板里有没有某条命令、卸载之后定时器还在不在。静态阅读看不出，纯逻辑断言（`check-contributions.ts`）也够不到。

因此新增 `scripts/check-plugin-runtime.ts`：把**真实的** `pluginRuntime` 装进 Node，配一套手写的浏览器垫片与桩后端，用 9 个合成插件去撞边界。共 66 项断言。

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 解析 | `scripts/harness/loader.mjs` + `resolve-hook.mjs` | 给省略扩展名的相对 import 补 `.ts` |
| 环境 | `scripts/harness/dom-shim.ts` | 最小浏览器环境；**`<script>` 的 textContent 会被真正执行** |
| 后端 | `scripts/harness/plugin-host.ts` | `list_plugins` / `read_plugin_asset` / `plugin_storage_*` 的桩 |
| 夹具 | `scripts/fixtures/plugins/*` | 9 个合成插件（清单 + 代码） |

#### 三条值得单独记下来的决定

**一、不用 jsdom / vitest，而是手写垫片。** 依赖里没有它们，而夹具的价值恰恰在于能在零网络、零安装动作的环境里跑起来。**代价必须说清楚：夹具测的是「运行时在这套垫片上的行为」，不是「在真实浏览器里的行为」。** 因此垫片刻意照抄浏览器语义 —— 最典型的一处是 `<script>` 里的异常**不会**从 `appendChild` 抛出，而是走 `window` 的 error 事件；插件运行时正是靠那条路径把"插件坏了"反映到界面上，若垫片让异常直接冒出来，那条路径就永远测不到，而那恰恰是它存在的唯一理由。

**二、桩后端必须如实拒绝。** `plugin_storage_*` 的桩照 Rust 侧的 `require_permission("storage")` 拒绝没有声明该权限的插件。**一个比真实宿主更宽松的桩比没有桩更糟** —— 它会让夹具显示"没有权限也能读写设置"，而那正是真实运行时不成立的事。这条纪律对将来接入网络出站管控同样成立：那时网络桩要照抄的是**策略**，而不是放行。

**三、（为夹具拆了一处源码）`ModuleRuntimeContext.tsx` 拆成两个文件。** `pluginRuntime` 经 `useModuleActive` 静态依赖到它，而 Node 无法擦除 JSX，于是整条运行时依赖图都没法在无构建步骤的环境里加载。拆开之后类型与 Hook 在 `contexts/moduleRuntime.ts`（无 JSX），Provider 留在原文件并再导出全部既有名字 —— 因此**没有任何调用方需要改 import**。这不是为测试而测试：它把「读取模块可见性」与「把可见性放进 React 树」分成了两件事。

#### 覆盖与未覆盖

覆盖的边界（详见 `scripts/harness/README.md`）：旧式插件行为不变、声明式按需激活（含"未激活时一个 bundle 都没执行"）、纯命令插件、后台服务插件的收尾三保证、顶层抛错的隔离、空贡献仍判失败、模块 ID 抢占被拒、卸载后命令声明仍在、设置读取时机与权限、以及 8 个插件里只有 5 个被执行。

**未覆盖：**

- **React 渲染。** 断言止于「拿到了组件」，没有真的渲染 —— 那需要 DOM 与 React 渲染器。模块崩溃会不会被错误边界接住，不在这里验。
- **规模。** 9 个手写夹具证明的是机制，不是「500 个插件」的行为。后者需要一套生成的夹具。
- **顶层同步死循环。** 它无法被中断，因此不可能"测过去"。

### 7.32 图标在目录重建后丢失，与残留在缓存里的旧图标

**类别：** 缺陷（已修）＋ 夹具覆盖

#### 两个症状

1. **插件删除重装后，侧边栏图标不出现** —— 时好时坏，有时要刷新。
2. **侧边栏用的图标不是插件自带的那个**。

#### 根因：一处「后补」的机制没有覆盖所有入口

模块图标是**后补**进目录的：清单期只拿得到图标**路径**（`icon.svg`），内容要用 `read_plugin_asset` 异步读回来，再由 `setModuleIconSvg` 写进目录条目。

而目录在**每一次** `reloadPluginRuntime()` 时都被 `clearDynamicModules()` 清空重建。于是"图标已经补过一次"这个状态，在下一次重建之后就失效了。三处叠加：

**一、补图标的入口只有一个。** `prefetchDeclaredIcons()` 原先只在 `loadPluginsInBackground()` 里被调用，而「安装 / 卸载 / 启用 / 禁用」这四条路径只调 `reloadPluginRuntime()` —— 重建完目录就没有下文。这是症状 1。

**二、缓存被当成了目录状态。** `prefetchDeclaredIcons()` 里有一句"已经有图标就整个跳过"。它想省的是**读盘**，结果把 `setModuleIconSvg` 一起省了 —— 而后者才是让新建的目录条目拿到图标的那一步。只要进程内还留着这份缓存，重建后的条目就永远补不上。这也是症状 1 的一部分。

**三、卸载时漏清缓存。** 清理循环原先只遍历 `injectedAssets`，而那张表**只有执行过代码的插件**才有条目。声明式插件在按需激活之前不写它，但它的图标已经被预取进了 `pluginIcons`。卸载时缓存留了下来，重装后这份**旧图标**被当成"已经有了"继续用 —— 这就是症状 2。

#### 修法与验证

- 补图标移进 `reloadPluginRuntime()` 的末尾（`listOnly` 除外），四条生命周期路径自动覆盖；`loadPluginsInBackground` 里那次重复调用删掉。
- 缓存只用来省读盘：`pluginIcons.has()` 短路的是 `prefetchPluginIcon`，不是 `setModuleIconSvg`。
- 清理改成拿「所有已知插件 ID」（`injectedAssets` ∪ `pluginIcons` ∪ `loadStates` ∪ `activationStates`）与活跃集合做差。
- 顺带删掉一段**死代码**：那个遍历 `contracts.keys()` 的清理循环，其上方几行刚刚 `contracts.clear()`，条件永远不成立。它唯一的效果是让 `unregisterPluginSettings` 看起来有调用方 —— 那个函数其实是死导出，一并删除。也就是说，「按插件清理设置」这个粒度**从来没有真正生效过**，一直被 `clearPluginSettings()` 的全清掩盖着。

新增夹具 `declarative-icon`（声明式 + 按需激活 + `icon.svg`）与 6 项断言。**两个半边都单独验证过会红**：临时注释掉补图标调用 → 4 项失败；临时去掉清理里的三个来源 → 恰好 1 项失败（"重新启用后重新读了图标文件"），而后者正是症状 2 的机制。

**未覆盖：** 真实浏览器里的渲染。夹具断言的是"目录条目的 `iconSvg` 是对的"，不是"侧边栏画出来的像素是对的"。

### 7.33 出站管控漏掉了插件市场：一条必须靠"记得写"才生效的纪律

**类别：** 功能缺陷（已修）＋ 架构收口

#### 现象

「设置 → 网络」把出站策略改成「禁止出站」、或打开离线模式，刷新之后**插件市场照样能正常加载**。界面上那个开关看起来完全没生效。

#### 根因：判定被手写在调用点上，而调用点不止一个

第一版的出站策略与流量日志是**手写**在 `plugins/manager.rs` 的 `plugin_http_request` 里的（判一次 `decide`、记一条日志、再发请求）。而同一个文件里的 `fetch_once` —— 插件索引、索引签名、README、市场图标、`.lcp` 包下载全都走它 —— 一个字的判定都没有。

所以真实情况是：**插件的 `network` 请求受管控，而插件市场不受管控**。后者恰恰是用户最常触发联网的那条路，也是他最容易用来验证开关是否生效的那条路。

问题不在于"谁忘了写那一段"。**那种写法要求每一个新调用点都记得写一次**，而它当时看起来是对的 —— 手写的那一处功能完整、注释齐全、还带了测试。真正缺的是一条让"漏掉"变得不可能的机制。

#### 做法：把裸客户端收进唯一门面

新增 `modules/net/client.rs`：

- `NetClient` **私有持有** `reqwest::Client`，且**不提供任何把它交出去的方法**；
- 判定（`policy::decide`）、记录（`log::record`）与发送（`Client::execute`）只在 `execute()` 一处发生；
- 调用方拿到的唯一入口是 `get_and_send()` / `execute()`。

于是"绕过策略发一个请求"不再是纪律问题，而是类型问题：拿不到裸客户端就发不出去。`PluginManager` 的 `client` 字段直接删除，`probe.rs` 与 `updater` 一并改用门面。

**顺带修掉的两处不一致：**

1. **`decide` 从来没有看过地址。** 而「禁止出站」的档位说明里写着"本地回环地址不受影响" —— 文案说的是行为，实现里没有。现在 `decide(mode, offline, loopback)` 收下这个维度，回环在任何档位（含离线）下放行，并有断言钉死。第一次跑这条断言时它是红的。
2. **更新的检查与下载根本不经过门面。** `tauri-plugin-updater` 用自己的传输，我们无法在传输层拦它。能覆盖的是命令入口：离线或禁止出站时 `check_app_update` / `install_app_update` 在发起前直接拒绝，并记一条日志。**这是入口拦截，不是传输层拦截，两者不能混为一谈。**

#### 门禁：让"绕过"编译不过，也让文本检查兜住

`pnpm check:network` 新增两条静态断言（已在真实违规上验证过会红）：

- `reqwest::Client` 的持有者**恰好**是 `net/client.rs`（断言"恰好"而不是"其它地方没有"：后者在有人换用别的 HTTP 库时会安静通过）；
- `.send()` **不允许出现在任何地方** —— 门面用的是 `Client::execute`，所以它一旦出现就意味着有人自己建了客户端。

#### 仍未覆盖（必须说清楚）

- **WebView 里插件自己发的 `fetch`。** 插件与宿主共享同一个 JS 上下文，它可以直接调 `fetch()`，那条路根本不经过 Rust。约束它只能靠 CSP 的 `connect-src`。**在这一条补上之前，"所有出站都被记录"是不成立的。**
- **应用更新的传输层。** 见上：只有入口拦截，流量日志里不会出现更新的请求。
- **本机代理是绕道。** 回环地址不受管控是刻意的（原因见文档），代价是：如果用户把下载源/代理指向本机，流量会经由它出去，而策略与离线模式都不会拦。

完整说明见[网络访问与下载源](../02-开发指南/网络访问与代理.md)第 8 节。

### 7.35 插件能自己联网：CSP 与前端门面

**类别：** 安全边界（新增）＋ 可观测性

#### 问题

`plugin_http_request` 那套管控（权限、策略、日志）只覆盖**走后端**的请求。插件与宿主共享同一个 JavaScript 上下文，它可以直接 `fetch('https://…')` —— 权限检查、出站策略、流量日志，三者一起被绕过去，而且连"是谁发的"都无从知道。

在 7.32 那次收口之后，这是"所有出站都被记录"唯一还站着不成立的地方。

#### 两层，分工不同

| 层 | 位置 | 作用 |
| --- | --- | --- |
| CSP `connect-src` | `tauri.conf.json` | **真正的边界**。由浏览器引擎执行，JS 改不掉 |
| 前端门面 | `src/services/netGuard.ts` | **可读性与可观测性**。包装 `fetch` / `XMLHttpRequest` / `WebSocket` / `sendBeacon`，给出"是谁、要去哪、为什么"并落进流量日志 |

`connect-src` 只留 IPC 与回环。**回环是刻意的**：它不出本机，而"插件连本地开发服务器"是正当场景。门面与 CSP 的口径必须一致，否则会出现"门面放行、CSP 挡下"这种最难解释的组合。

#### 为什么门面不是安全边界（写在它自己的文件头上）

同一个 realm 里还有 `<img src>`、`<script src>`、`<link rel=preload>`、`import()`、`EventSource` —— 它们不经过任何被包装的函数。被包装的函数本身也挡不住刻意绕行。

所以门面的定位是：**让老实插件守规矩，并且让"不守规矩"这件事在日志里看得见**。真正的边界只有 CSP。这一点写进了 `netGuard.ts` 的文件头、`网络访问与代理.md` 的 §8.6，以及宿主 API 参考里 `ctx.http` 的开头 —— 因为"我们加了防护"这句话最容易被读成"我们是安全的"。

#### 一处真实缺陷：`new URL(url, location.href)` 把拼错的地址变成放行

门面第一版用 `new URL(url, window.location.href)` 解析地址。后果是 `new URL('不是地址', base)` **不会抛错** —— 它把任何相对路径或拼错的东西解析成同源地址，而应用的宿主正是 `localhost`，于是它们全部落进"回环放行"那一支。**拼错等于放行。**

夹具里那条"解析不了的地址一律拒绝"第一次跑就是红的，改法是去掉 base、只认绝对地址（`ctx.http` 本来也只接受完整地址）。这条断言现在留着。

#### 唯一无法自动化验证的改动

CSP 的失败模式是运行期的：构建、类型检查、全部 13 个 check 脚本都不会因为它变红。因此 `网络访问与代理.md` §8.7 有一份**必须人工跑的八项清单**（IPC、插件加载、插件样式、提示音、图标、HMR、`ctx.http`、门面拒绝），并写明"1 至 5 中任何一条失败都说明那条指令需要放宽，放宽时只动相关的那一条并在这里补一句为什么"。

已知的脆弱点：`dangerousDisableAssetCspModification` 里钉死了 `script-src` 与 `style-src` —— 插件是宿主在运行期注入的 `<script>` / `<style>`，拿不到 Tauri 在编译期追加的 nonce/hash。不钉死它们，`'unsafe-inline'` 会因为同策略里出现 nonce 而**整体失效**，症状是插件一个都加载不了。

### 7.36 插件仓库的多文件源码链路：一处静默的严格模式回退，与一条把产物绑在配置文件上的耦合

**类别：** 开发体验（新增）＋ 构建确定性（新增）

#### 背景

插件仓库此前只有一条路：手写单文件 IIFE。看板的 `index.js` 因此长到 3575 行，而它的文件头自己写着「手写 IIFE，不使用构建工具，因此不能写 JSX」—— 需求与手段的错配摆在那里很久了。

本轮给它补了一条**可选的**快车道：源码放**仓库根**的 `src/<插件名>/`，`scripts/build.ts` 用 esbuild 打包成 `plugins/<插件名>/index.js`。产物仍是单文件 IIFE，因此宿主这一侧、打包 zip、生成索引的流程一个字都没改。看板是第一个走这条路的插件。

#### 一处真实回退：产物静默掉回宽松模式

原文件是 `(function () { 'use strict'; … })()` —— 严格模式。而 esbuild 产出的是 `(()=>{…})()`，**箭头函数不建立自己的严格模式**，它继承外层；宿主又用 `document.createElement('script')` 注入（经典脚本，不是 module），默认正是宽松模式。

后果是静默的：给未声明的名字赋值会创建全局变量而不是抛错，给只读属性赋值会无声失败。构建、类型检查、所有 check 脚本都不会因此变红。修法是在 banner 里显式补一条指令序言。

**这条指令现在会在产物里出现两次**（banner 补的一条、esbuild 自己发的一条）。发不发取决于它怎么判定输入模块类型：源码是 `.ts` 时它不发，是 `.js`（且 `package.json` 里 `type: module`）时它会发。**不要去重** —— 删掉 banner 那条，用 `.ts` 写源码的插件就会掉回宽松模式。理由写在 `bundle.ts` 的注释里。

#### 一条耦合：`tsconfig.json` 会改变产物的字节

esbuild 会自己去读仓库根的 `tsconfig.json`。为了给插件源码配类型检查而加上这个文件之后，**同样的源码构建出了不同的字节**（多出一行指令序言）—— 索引里的哈希随之对不上，重新生成索引又意味着重新签名，代价是一次多余的签名往返。

也就是说：**产物哈希不只取决于 `src/` 下的代码，还取决于仓库根有没有这个文件。** 这违反「索引里的 sha256 证明这个包就是这份源码构建出来的」。已知问题与可能的修法（把类型配置放到 esbuild 不会自动读取的位置，代价是编辑器不再自动识别它）写在插件仓库的 `src/README.md` 与 `docs/发布流程.md` 第 4 节。**尚未修。**

#### 顺带修掉的一处类型缺陷

插件仓库的 `types/modulith.d.ts` 把宿主对象声明为 `const Modulith`。但 JS 语义下 `const` **不会**成为 `globalThis` 的属性（只有 `var` 会），而宿主正是靠给全局对象挂属性注入的 —— 因此 `globalThis.Modulith` 是类型错误。已改为 `var Modulith: ModulithHost | undefined`，并如实标注它可能没有被注入。

同一轮还发现该类型文件 `import type * as React from 'react'`，而插件仓库没有装 react 的类型，打开它就会看到 `Cannot find module 'react'`；「可以用 TypeScript，类型检查那一步自己跑 tsc」这句话里的那一步其实无从跑起。已补上 `typescript` 与 `@types/react`（大版本与宿主的 React 19 对齐）并加了 `npm run typecheck`。

#### 仍未验证

看板的 React 渲染、拖拽与持久化**没有**在这次迁移中被验证 —— 插件没有自动化测试覆盖这些。已验证的是：11 个分节与原文逐字节一致、97 个导出名与 494 个字符串字面量都出现在产物中、以及在模拟宿主里真实执行产物时注册与清单一致。**交互行为需要在应用里人工跑一遍。**

### 7.39 插件沙箱的第一步：一条能自己证明成立的边界

**类别：** 安全边界（新增）＋ 可验证性（新增）

#### 做法（与最初的设想不同）

最初打算让插件 webview 通过 Tauri 的**事件通道**（`emit` / `listen`）与宿主通信。
研究中途换掉了，理由是一条 API 事实：

**`UriSchemeContext::webview_label()`**（`tauri/src/app.rs:2481`）——
自定义协议的处理器能拿到**发起这次请求的那个 webview 的标签**。
而运行时给**每一个** webview 各注册一遍协议（`tauri-runtime-wry/src/lib.rs:5177`），
子 webview 因此用的是同一条协议。

这一条把方案从"够用"变成了"更强"：

| | 事件通道 | 自定义协议（采用） |
| --- | --- | --- |
| 插件 webview 需要的 IPC 权限 | `core:event:allow-emit` / `allow-listen` | **一条都不需要** |
| 插件能监听/伪造的事件名 | 任意，包括宿主内部的 | 不存在事件面 |
| 身份来源 | 消息里插件自报的 id | **webview 标签，由引擎给出** |
| 网络是否可约束 | 否 | 是，见下 |

因此 `plugin-<id>` 这些 webview **不匹配任何 capability**，Tauri 在 IPC 入口拒绝
它们的每一次 invoke —— 包括全部 120 条应用命令。这一条由 `pnpm check:acl`
第 3b 节断言（"没有任何 capability 把插件 webview 纳入作用域"）。

**路径与标签必须一致。** 处理器把 URL 的第一段与 webview 标签反推出的插件 id 比对，
不一致就拒绝并记日志。理由是：插件控制得了自己发的 URL，控制不了自己被挂在哪个
webview 上 —— 于是 `plugin-kanban` 里发出的 `/notes/...` 请求既读不到别的插件的数据，
也借不到它的权限。

#### 网络第一次成为真的边界

插件文档由**宿主**提供，并附上一条由宿主写死的 CSP：

```
default-src 'none'; script-src 'unsafe-inline'; connect-src http://modulith-plugin.localhost;
img-src 'none'; font-src 'none'; frame-src 'none'; object-src 'none';
base-uri 'none'; form-action 'none'
```

`connect-src` 只留插件自己的来源，于是插件**无法直接 `fetch('https://…')`** ——
由浏览器引擎执行，JS 改不掉。要联网只能走宿主的通道，而那一路有权限判定与流量记录。

这与宿主界面今天的情况是本质区别：那里 `netGuard.ts` 自己在文件头承认"不是安全边界"
（§7.35 已记）。这里的 `connect-src` 是。

#### 自检：让边界自己证明自己

`src-tauri/src/modules/plugins/sandbox.rs` 的 `spawn_self_test()` 在 **debug 构建**
里建一个真的插件 webview，加载 `modulith-plugin://localhost/selftest/`，由页面跑四项
检查并逐条把结果投回宿主写进日志：

| # | 检查 | 预期 | 为什么必须有这一条 |
| --- | --- | --- | --- |
| 1 | `__TAURI_INTERNALS__` 是否被注入 | 存在 | 缺了它，"被拒绝"可能只是入口没注入，后面所有结论都不成立 |
| 2 | 调 `get_app_info` | **被拒绝**，且消息里有 `not allowed by ACL` | ACL 真的生效的正面证据 |
| 3 | `fetch('/selftest/rpc/ping')` | 成功，且宿主回话里的 webview 标签是 `plugin-selftest` | 通道可用 + 宿主认得出是谁 |
| 4 | `fetch('https://example.com/')` | 被 CSP 挡下 | 网络边界是引擎执行的 |

第 4 条**不看 `fetch` 是否失败**，而看有没有触发 `securitypolicyviolation` 事件：
断网时 `fetch` 同样会失败，那样这条检查就没有信息量。第 2 条同样**不看是否被拒绝**，
而看拒绝消息里有没有那句 ACL 原文 —— 命令不存在、参数写错也会被拒绝。

#### 一个必须点名的构建陷阱

`src-tauri/src/lib.rs` 的首行写着"此文件由 `scripts/generate-backend-module.ts`
自动生成，请勿手动编辑"，而 `pnpm dev` 与 `pnpm build` 都会跑 `gen:backend update`
**重写它**。因此协议注册与自检调用写进了**生成器**的模板，不是写进 `lib.rs` ——
直接改 `lib.rs` 会在下一次构建时被静默抹掉，且没有任何门禁会因此变红。

#### 明确没做的（不要读成已完成）

- **插件资源还没有通过协议提供**（真插件的入口文档、样式、脚本都还没有合成）。
  自检页是 `include_str!` 进去的一份固定 HTML。
- **RPC 还没有承载任何 `ctx.*` 能力**，只有一个 `ping` 与一个结果上报端点。
- **插件界面还没有接进标签页布局**：自检面板的位置与尺寸是写死的，真插件要跟着
  标签栏与侧边栏走（`set_bounds` + 前端量矩形）。
- **`api: 3`（插件声明界面入口）不存在**，9 个已发布插件一个都没动。
- **驻留上限与淘汰没有做。** 每个活跃插件一个渲染进程，没有 LRU，也没有量过成本。
- **仍然不是 OS 级沙箱**：插件在同一个进程树、同一个用户下。它挡的是"插件在应用内的
  权限"，不是"插件对这台机器的权限"。

#### 第一次真机运行的结果：四项全部通过

代理的沙箱环境创建不了窗口（对照实验：`notepad.exe` 在那里启动后
`MainWindowHandle` 也是 0），因此自检由人启动应用来跑。结果：

| 检查 | 结果 | 日志里的实际内容 |
| --- | --- | --- |
| `internals` | ✅ 通过 | 已注入，且带 invoke：true |
| `invoke_denied` | ✅ 通过 | `get_app_info not allowed on window "main", webview "plugin-selftest", URL: local` / `allowed on: [webviews: "main", URL: local]` / `referenced by: capability: app-commands, permission: allow-get-app-info` |
| `rpc` | ✅ 通过 | `{"ok":true,"webview":"plugin-selftest","plugin":"selftest"}` |
| `csp_active` | ✅ 通过 | `connect-src 拦下了 http://ipc.localhost/get_app_info`；`connect-src 拦下了 data`；`img-src 拦下了 data` |

第二行是**能想象到的最强确认**：引擎明确说出了这条命令在 `plugin-selftest` 上不被
允许、在 `webviews: "main"` 上才被允许、依据是 `app-commands` 里的
`allow-get-app-info`。

#### 而第四行纠正了一个我自己的错误判断

`connect-src 拦下了 http://ipc.localhost/get_app_info` 说明 CSP 与 ACL **都**开火了。
看上去 CSP 是第一道，但**它不是承重的那一道**。

Tauri 的 IPC 有两条传输（`tauri/scripts/ipc-protocol.js`）：

| 传输 | 受不受 CSP 管 | 本次运行里的表现 |
| --- | --- | --- |
| `fetch('http://ipc.localhost/<命令>')` | **受** | 被 `connect-src` 拦下并记下违规事件 |
| `window.ipc.postMessage(...)`（原生桥，fetch 失败后回退） | **不受** —— 它不是网络请求 | 请求照样到达 Rust，在那里被 ACL 拒绝 |

也就是说：**CSP 挡不住 Tauri IPC。** 插件那次 invoke 之所以失败，是因为第二道
（ACL）拦下了它 —— 而 ACL 只在应用声明过 app manifest 时，才对**应用自己的**命令生效。

这条区别的后果很具体：**若有人认为"CSP 已经够了"而把 `build.rs` 里的
`AppManifest::commands` 拿掉，插件会重新拿到全部 120 条命令**，而构建、类型检查与
其余门禁都不会变红。因此 `check:acl` 里那段解析失败的处理不是"报个错"，而是把那句话
原样打印出来；**并且已经实测它会失败** —— 把 `AppManifest::new().commands` 改成别的
名字，脚本打印上面这段话并以 1 退出。

#### 两次判据写错（都不是沙箱错，值得单独记）

**一、`invoke_denied` 只认了 release 的文案。** release 给的是
`Command <名字> not allowed by ACL`，而 debug 给的是带归属的详细版
（上面那一行）。断言只匹配了前者，于是**一次完全正确的拒绝被判成失败**。
现在两种文案都认。

**二、`csp_active` 的判据依赖外网。** 最初测的是"`fetch('https://example.com/')`
是否被挡下"，而**断网时它同样会被挡下** —— 那台机器直连外网本来就不通
（访问 GitHub 要走 `v4.gh-proxy.org`）。于是"CSP 生效"与"这台机器没有直连外网"
分不出来，这条检查没有信息量。

改成 `data:` 地址探针（`connect-src` 与 `img-src` 各一次）：它在**没有 CSP 时必定
成功**，因此"它被拦下"只有一个解释。两次判据属于同一类错误 ——
**用一个有歧义的观察去判定一件确定的事**，这比没有检查更糟：它会把"不知道"
读成"没通过"。

#### 已验证 / 未验证

已验证：四项自检在真实运行里**全部通过**（含宿主侧完整链路：创建 webview → 页面跑
检查 → 逐条投回 → 写进日志 → 关闭按钮生效）；`cargo check`、`pnpm check:acl` 的
28 项断言、其余 23 个门禁。

未验证：下面那份"未做清单"里的每一项。

### 7.40 沙箱的第二步：让一个插件真的跑在里面

**类别：** 安全边界（继续）＋ 门禁（新增）

§7.39 立起来的是**边界**（自检页证明四项）。这一步做的是**通道**：
让一个用普通方式写的插件，从资源加载到读写存储，整条路走通。

#### 交付物

| 文件 | 作用 |
| --- | --- |
| `modules/plugins/sandbox.rs` | 注册表、入口文档合成、资源服务、RPC 分发 |
| `resources/sandbox-bridge.js`（新） | 桥接层：把 `ctx.*` 变成对宿主的 RPC |
| `resources/sandbox-demo/`（新） | 内置演示插件（清单 + `plugin.js` + `plugin.css`） |
| `scripts/check-sandbox.ts`（新，`pnpm check:sandbox`） | 42 项断言 |

#### 三个值得单独记下的决定

**一、标签不是身份，注册表才是。** 插件 id 允许含 `.` `_` `-`（见 `validator.rs`），
而 webview 标签的字符集更窄，把 id 直接拼进去会在 `a.b` 与 `a-b` 之间产生歧义。
因此标签只是**去重用的名字**（`plugin-<净化后的 id>`），真身份是注册表里那条
`标签 → 插件 id` 的记录；注册时检测标签冲突并**显式报错** ——
否则两个插件抢同一个 webview 名字时，其中一个会静默失效。

**二、桥接层按身份重新渲染，而不是自己去问"我是谁"。** `sandbox-bridge.js` 是静态
文件，但每次响应都由宿主把 id / 名称 / 权限替换进去。这样插件在**顶层同步**就能读到
身份与权限，不必先 await 一次握手 —— 而"顶层同步可用"正是 v1.5 花一整轮保住的性质。

**三、入口文档由宿主合成，插件包不必自带 HTML。** 三个理由：CSP 必须由宿主写死
（让插件自带 HTML 等于让它自己声明自己的边界）；已有的 `main` / `style` 清单字段直接
可用；桥接层的加载顺序由宿主控制，插件无法插到它前面。

真插件的 `script-src` 是 `'self'`，自检页是 `'unsafe-inline'`（它只有一段内联脚本）。
**这个差别是有意的，不要统一。**

#### 资源路径：不用"字符串里有没有 `..`"那种判据

`serve_asset` 先百分号解码，再用 `resolve_within` 判断。判据是两条，缺一不可：

1. `canonicalize` **之后**必须仍在插件目录之下 —— 它会解开符号链接，因此指向目录
   之外的软链也会被挡下；
2. 只吐普通文件。

不用字符串包含检查：它在 Windows 上会被 `\`、短名、UNC 路径绕过，而这类判据的失效
方式恰好是"看起来正常但读到了别的文件"。

#### 两个自己写出来的错误，都值得留在记录里

**一、占位符在注释里也出现了一次。** `sandbox-bridge.js` 的文件头注释里原样写了一遍
`__PLUGIN_ID__`，而替换只针对**带引号**的形式。后果是 `bridge_script` 里那条
`debug_assert!` **在 debug 构建里直接 panic** —— 桥接层整个发不出去，演示插件一行都
跑不起来。抓到它的是"先数一遍占位符出现几次"，不是运行。

修法是注释里改写成 `__PLUGIN_*__`，而断言保持严格（替换后一个原始占位符都不许剩，
**包括注释里**）。`check:sandbox` 里有一条对应的断言，因为 Rust 那条只在 debug 生效。

**二、一条永远为真的门禁。** CSP 那条断言第一版写的是
`!/script-src 'unsafe-inline'/`。而退化后的写法是
`script-src 'self' 'unsafe-inline'` —— 两个记号**并不相邻**，于是这条断言恒为真。
实测确认过：把那行真的改坏，门禁照样全绿。

现在改成按**指令**解析（取出 `script-src` 到下一个 `;` 之间的内容再判断），并且
**两个方向都试过会失败**：真插件退回 `'unsafe-inline'` 会红，自检页被误改成
`'self'` 也会红。

这与 §7.37 记的是同一类问题 —— **一条不会失败的检查比没有检查更糟**，因为它会被
当成"已经有人看着了"。凡新增断言，都要真的把它弄坏一次。

#### 明确没做的（不要读成已完成）

- **真插件还没迁移。** 演示插件是宿主内置的，不随发布包分发；9 个已发布插件一个都没动，
  走的仍是老路（同 realm）。
- **界面没有接进标签页。** 演示面板的位置与尺寸是写死的，真插件要跟着标签栏与侧边栏走
  （`set_bounds` + 前端量矩形）。
- **`ctx.*` 只有 `log` 与 `storage`。** `http` / `notifications` / `events` / `settings` /
  `disposables` 都还没有对应的 RPC。
- **`api: 3` 与 `Modulith.run` 在沙箱里不存在。** 桥接层给的是一个新的、更小的表面。
- **没有驻留上限与淘汰**，也**没有量过**单个插件 webview 的真实内存增量。
- **仍然不是 OS 级沙箱**：插件在同一个进程树、同一个用户下。

#### 第一次真机运行的结果

| 检查 | 结果 | 日志里的实际内容 |
| --- | --- | --- |
| 身份 | ✅ | `宿主给出的 id 是 com.modulith.sandbox-demo` |
| 权限可见性 | ✅ | `has("storage")=true，has("process-spawn")=false` |
| 资源加载 | ✅ | `plugin.js 与 plugin.css 都从插件目录里读出来了` |
| fail-closed | ✅ | `被拒绝了：插件不存在: com.modulith.sandbox-demo` |

这四条合起来说明**整条通道成立**：沙箱 webview 建起来了、入口文档由宿主合成、
资源从插件目录读到、桥接层按身份渲染、RPC 真的到达宿主并写进了日志 ——
`[plugin:com.modulith.sandbox-demo] [沙箱演示] 通过 身份：…` 那一行就是走完这条路的。

#### 第四行暴露的：**两个真源**

演示插件调存储时被拒绝，理由是 `插件不存在`。**这个拒绝本身是对的**，但它同时说明：

> 现在有两套"什么插件存在、它能做什么"：`PluginManager`（已安装插件的真源，存储的
> 权限与配额判定都在它那里）与 `SandboxRegistry`（沙箱界面用的那份同步缓存）。
> 对**已安装的插件**两者描述同一个东西；而演示插件只登记在后者里。

为什么这个拒绝值得当成一项检查，而不是"改成能写":

**一条沙箱对未知身份"放行、但换个默认目录兜住"才是真正的漏洞形态** ——
它看起来能用，而配额、备份、卸载清理**全都绕过去了**。所以"拒绝"必须被钉住。
演示插件因此检查的是 **fail-closed**，面板上写的是"被拒绝了：插件不存在"。

真做真插件迁移时（增量 C），**`SandboxRegistry` 必须由 `PluginManager` 派生**，
而不是各记一份 —— 两套清单一定会漂，而漂开的方向恰好是"沙箱以为这个插件存在、
存储那边不认"。这一点已经写进 `sandbox.rs` 的文件头。

#### 尚未验证

- **存储的正常路径。** 演示插件不是已安装的插件，因此只有"被拒绝"这一支被验过；
  已安装插件读写自己的数据（含权限判定与配额）**没有**跑过。它要在增量 C 里
  用一个真插件来验。
- `ctx.*` 的其余 RPC —— 目前只有 `log` 一条是完整的。
- 界面接进标签页、`api: 3`、驻留上限与淘汰、单插件 webview 的真实内存增量。

### 7.41 沙箱的第三步：把"两个真源"从设计上消掉，并迁移第一个真插件

**类别：** 安全边界（继续）＋ 架构（单一真源）

#### 上一轮留下的问题，这一轮在结构上解决

§7.40 记下的是：宿主里有两套"什么插件存在、它能做什么" —— `PluginManager` 与
沙箱自己的注册表。当时**没有**给它加检查，而是把结构改掉：

| | 之前 | 现在 |
| --- | --- | --- |
| 沙箱记什么 | `标签 → {根目录, 入口, 样式, 权限}` | `标签 → 插件 id`，**仅此** |
| 插件的事实从哪来 | 沙箱注册时读一次清单 | `PluginManager::sandbox_view(id)` |
| 未安装的插件能拿到界面吗 | 能（演示插件就是这样） | **构造上不能** —— 建界面必须先过 `sandbox_view` |

也就是说：**"没安装的插件拿不到界面"不再是一条检查，而是它没有别的路径可走。**
内置演示插件因此被删掉 —— 它**就是**那个第二真源。

`create_surface` 的三步顺序也是为失效方式兜底的，每条都由 `check:sandbox` 断言：

1. 先经 `PluginManager` 核实（拿不到就什么都不建）；
2. 再占标签（**先占位再建 webview**：反过来的话，webview 起来了而首条协议请求先到，
   那一刻表里还没有这条记录，请求会被判成"不是插件界面"）；
3. 最后建 webview，失败就撤掉占位。

#### `runtime` 字段：位置，不是等级

清单新增 `runtime`，取值 `"in-process"`（缺省）或 `"sandboxed"`。

它与被删掉的 `sandboxLevel` 的区别不是措辞：**等级是宿主无法核实的量，位置是可以核实的** ——
`plugin-<id>` 这些 webview 不匹配任何 capability，这一点由引擎与 ACL 执行，不是插件自述。

**这里刻意不做"未知值退化成缺省"。** 一个写了 `sandboxed`、却被旧宿主当成 `in-process`
跑起来的插件，是一次**声明了隔离而实际没有**的降级 —— 比安装失败危险得多。
因此枚举反序列化失败会让整份清单不合法。`check:sandbox` 有一条断言专门盯
`#[serde(other)]` 这类"顺手加个兜底"的改动（它会让这条性质静默消失）。

#### 迁移第一个真插件：`hello` → 1.0.2

`hello` 是本仓库的参考插件，它的职责就是示范"当前推荐的写法"，因此由它先走。
迁移暴露了三件**只有真迁移才会暴露**的事：

| 暴露的 | 说明 |
| --- | --- |
| **宿主 CSS 到不了插件** | 旧 `index.css` 用宿主的 `--accent-*` 变量与 `.dark` 类做深色 —— 插件是独立文档，两者都不存在。改用 `prefers-color-scheme`，颜色自带 |
| **没有 React** | 旧写法靠 `Modulith.React`。现在用 DOM API。这不是退步：插件因此可以自带框架，与宿主的版本解耦 |
| **联网被 CSP 挡住** | `connect-src` 只留插件自己的来源。`fetch('https://…')` 由引擎挡下 |

代价是与宿主的视觉不再自动一致。这是真实的取舍，不是"迁移的麻烦" ——
**插件自带样式意味着宿主换配色不会让插件看起来坏掉，也意味着它不会自动跟上。**

同时清掉一个死字段：`hello` 的清单里还留着 `"sandboxLevel": 1`。`SandboxLevel`
早在 v1.5 就被判为"不要在阶段一就假装拥有了阶段三的保障"并删除
（见 `types.rs` 里那段说明），但已发布插件的清单里仍带着它，宿主静默忽略 ——
**一个死字段留在参考插件里，会被后来的人当成还能用的东西。** 已删除。

#### 顺带发现，已处理（1.6.0）

`engines` 的键名是 **`loopcore`** —— 旧产品名。9 个插件的清单、宿主的
`PluginEngines` 结构、校验器与文档全都在用它。

当时记为独立的债、不在那一轮处理，理由是不想与沙箱那一串改动混在一起。
**1.6.0 已把它改成 `engines.modulith`**，跨仓库一次性完成：宿主的
`PluginEngines` / `validator`、前端类型与界面、`scripts/`（version-manager、
夹具、样例）、插件仓的 9 份清单与 `index.json`、以及全部文档。同时把引擎下限
从习惯性的 `>=1.0.0` 提到 `>=1.6.0` —— 本平台的沙箱运行时、`ctx.db`、
`ctx.http.download`、多界面都是 1.6.0 才有的，写 `>=1.0.0` 会让 1.0~1.5 的宿主
**收不到任何提示**，而那正是最需要提示的情况。

改名之所以代价不高：`PluginEngines` 没有 `deny_unknown_fields`，老清单里的
`engines.loopcore` 会被**静默忽略**（等价于未声明引擎范围），而 `engines`
不匹配本来**不阻止安装**，只给一条提示。

#### 尚未验证

真机还没跑过这一版。要跑需要一个**已安装**的、清单里写了 `runtime: "sandboxed"` 的插件 ——
`hello` 1.0.2 就是它。装法：应用的「从目录安装」指向 `modulith-plugins/plugins/hello`
（dev-linked，之后改完刷新即生效）。

预期日志：`[sandbox自检] 已创建 webview plugin-com-rinntheor-modulith-hello`，
面板上是那个按钮，点几下关掉应用再打开，次数还在 —— **那才是"存储的正常路径"第一次被验到**。

### 7.42 第一次真人使用暴露的三个缺陷，以及界面接线

**类别：** 缺陷（都已修）＋ 缺失功能（补上）

#### 用户的实际反馈

装上迁移后的 `hello` 之后，四条：

> 我在侧边栏使用它却无法加载；那个沙箱自检的 Webview 窗口无法关闭；
> 重启软件后 Hello 的界面直接出现在左侧，但我没有使用这个插件，还无法关闭；
> 不过功能是正常了

#### 逐条

**一、自检面板关不掉。** 拆 `handle_selftest` 时我把 `close` 分支**丢了**。
按钮发的是无 body 的 `POST /rpc/close`，于是落进"结果上报"分支，被当成 JSON 解析 ——
日志里那条 `报告无法解析（EOF while parsing a value）` 就是它，而面板纹丝不动。

修法不只是补回分支：`close` 现在是**独立的**一条路径，不再挂在上报分支下面。
当时自检页在四项全过之后会自己关掉（理由见下"五"）；**那条自动关闭后来被去掉了**，
因为自检不再自动运行，点开它的人正等着看结果。

**二、`favicon.ico` 被当成跨插件攻击。** 浏览器会自动请求文档根路径的 favicon，
而那个路径的第一段不是任何插件 id，于是撞上"路径必须与 webview 所属插件相符"这条判断，
留下一条**看起来像攻击的告警**。修法是在宿主合成的文档里加
`<link rel="icon" href="data:,">` —— 把那次请求彻底消掉，而不是去放宽那条判断。

**三、debug 自检无条件给插件建界面。** 用户没打开任何插件，界面上却多出一块挡在那里的
面板，而且没有任何方式关掉它。**真插件那一半现在走真实路径**（见下），
自检只建它自己那一页。`check:sandbox` 加了一条断言盯住"别再把它加回启动路径"。

**四、侧边栏点了没反应 —— 因为界面接线还没做。**

#### 补上的：界面接线

沙箱插件的界面是**独立 webview**，不是 DOM 节点，因此它需要有人告诉宿主"摆在哪"。
分工是：

| 谁 | 做什么 |
| --- | --- |
| 前端 | 量出内容区矩形，交给宿主。**只有它知道**标签栏、分屏、侧边栏各占多少 |
| Rust | `sandbox_surface_open` / `_close` / `_bounds` 三条命令，建、关、摆 |
| 渲染层 | `ModuleDescriptor.sandboxed` 为真时，`ModuleRenderer` 渲染 `SandboxSurface` 占位，不渲染那个 React 组件 |

三条命令**登记进了应用 ACL**（`build.rs` + `app-commands.json`）—— 这一步是 `check:acl`
逼出来的：不登记，它们对所有人都不可用，而这**只在运行期暴露**。

两处状态必须成对动：`open_surface_at` 建失败时要撤销占位，`close_surface` 关界面时
也要撤销占位。只关 webview 而留着记录，下一次建界面会以为"已经建过了"，
而 webview 其实已经不在 —— **于是这个插件永远建不出来**。

#### 它现在仍然是错的（写清楚，别当成已解决）

- **原生 webview 盖住宿主自己的浮层。** 命令面板、通知浮层落在内容区上时会被挡住。
  要做对，需要在浮层出现时把 webview `hide()` 起来。
- **它不随内容滚动**，用的是内容视口而不是可滚动内容的高度。
- **`ModuleDescriptor.sandboxed` 只对"清单式"插件生效。** 旧式插件（在宿主 realm 里
  `registerModule`）在定义上就是 in-process，那条路径恒为 `false`。

#### 尚未验证

这一版还没跑过。要看的四件事：点侧边栏能不能出界面、切走标签界面消不消失、
侧边栏折叠时界面跟不跟着变、自检面板会不会自己关掉。

### 7.43 主窗口有了第二个 webview 之后，`get_webview_window` 就再也找不到它

**类别：** 缺陷（已修）＋ 门禁（新增）

#### 现象

用户报："在标题栏中点击关闭也无法关闭软件。"

日志里只有孤零零的一句：

```
[modules::desktop::tray] 托盘：找不到主窗口，无法显示
```

#### 根因

`Manager::get_webview_window(label)` 在返回之前会再判一次 `is_webview_window()`，
而那个判据是**"这个窗口下的所有 webview 的标签都等于窗口标签"**。
只要窗口里多出一个 webview —— 沙箱插件的界面就是 —— 它就变成 `false`，
于是 `get_webview_window` 返回 `None`。

关闭路径因此断成两截，而两截的表现合起来正好是"点了关闭没反应"：

1. `api.prevent_close()` 已经调用了 —— 窗口**确实不会被关掉**；
2. 紧接着的 `get_webview_window(MAIN_WINDOW)` 返回 `None` → 提前 `return` →
   **隐藏那一步也没执行**。

于是窗口既没关也没藏，卡在中间。托盘那条路径同理：叫不回窗口。
内存目标等级也设不上（`memory_level.rs` 用的同一个 API）。

#### 修法

不修调用点，而是**掐掉这条路**：新增 `core/window.rs`，宿主取窗口一律走它
（`main()` / `main_webview()` / `get()` / `webview()`）。改完之后
`check:sandbox` 有一条断言：**宿主源码里不许再出现 `get_webview_window`**
（比较前先剥掉注释，因为 `core/window.rs` 自己就在解释它为什么不能用）。

放在 `core` 而不是沙箱模块旁边，是因为**它与沙箱无关** —— 任何让主窗口拥有第二个
webview 的改动都会踩到它。放在沙箱旁边会让下一个人以为"这是插件的事"。

#### 值得记下的：我**写过这个坑，却没去查别处**

`open_surface` 里有一条注释：

> 注意这里用 `get_window` 而不是 `get_webview_window`：后者内部的
> `is_webview_window()` 会在一个窗口拥有多个 webview 之后变成 false

我避开了自己那一处，却没有搜一遍别处还有谁在用 —— 而这个仓库里还有 5 处。
**记下一条陷阱不等于做过一次排查。** 这一条是这次真正的教训，
它比那个 API 缺陷更值得记住。

#### 当时未定的另一条症状

用户同时报了"之前插件用不了"。当时没有直接证据可判 —— 那一次会话的日志里既没有
`[frontend/plugin:…] 加载完成`，也没有任何沙箱界面被创建过的痕迹。

**答案在下一节（§7.44）**：那不是第二个问题，而是同一个事件的另一面。窗口按钮、
托盘、其余插件的 IPC 全都在主线程上，主线程一旦不回来，它们就一起失效。
这一条恰好解释了为什么"修好了 `get_webview_window` 之后症状依旧"。

### 7.44 点开一个沙箱插件，整个应用假死（而它一处错误都不报）

**类别：** 缺陷（已修，本轮最严重）＋ 架构约束（新增）＋ 门禁（新增）＋ 观测手段（新增）

#### 现象

修完 §7.43 之后，用户的复现描述是：

> 只要不打开沙箱插件，那么将一切正常，只要打开沙箱插件，那么原来的非沙箱插件
> 将无法使用，且**应用无法正常关闭、放大、缩小，在托盘中也是一样**。

四个看起来互不相干的故障同时出现，而日志里**一条 ERROR 都没有**。

#### 日志给出的两条硬证据

**第一，日志停止的位置。** 最后一次会话的最后四行是：

```
2026-09-25 12:01:34.632 INFO [frontend/plugin:…typing-practice] 打字练习插件加载完成
2026-09-25 12:01:37.895 INFO [frontend/plugin:…encode-lab] 编码与哈希工具箱加载完成
2026-09-25 12:01:38.723 INFO [frontend/plugin:…color-lab] 颜色与对比度工具加载完成
        ←—— 到这里为止，之后再无任何一行
```

`open_surface` 里 `add_child` 之后的**下一句**就是一条 `已创建 webview` 的
`log::info!`。它没有出现，说明 `add_child` **从来没有返回**。

这不是"日志缓冲没刷出去"：`logging/logger.rs` 直接对 `File` 做 `write_all`
（第 515 行），没有 `BufWriter`，写一行到一行。

**第二，日志里其实早就跑过一次对照实验。**

同一个 `open_surface` → `add_child`，两条调用路径，结果是分裂的：

| 调用路径 | 调用线程 | 结果 |
| --- | --- | --- |
| `spawn_debug_harness` 建自检界面 | 一条 spawn 出来的线程 | **连续三个会话都成功** |
| 前端命令 `sandbox_surface_open` 建插件界面 | IPC 回调线程 | 直接断在那里 |

唯一变量就是**调用线程**。这不是猜测，是已经跑出来的对照 —— 只是当时没人把它当
实验读。

#### 根因：三条事实叠在一起

1. `Window::add_child` 的实现是 `run_on_main_thread(闭包)` 再 `rx.recv().unwrap()`
   —— **它阻塞调用它的那个线程**，直到主线程把闭包跑完
   （`tauri-2.11.5/src/window/mod.rs:1129`）。
2. `run_on_main_thread` 在**已经身处主线程**时短路成直接调用
   （`tauri-runtime-wry-2.11.4/src/lib.rs` 的 `send_user_message`：
   `if current_thread().id() == context.main_thread_id`）。
3. `#[tauri::command]` 默认是 `ExecutionContext::Blocking`
   （`tauri-macros-2.6.3/src/command/wrapper.rs:404`），**函数体就地执行**；
   而 IPC 是在 webview 的协议/消息回调里被调的，那个回调跑在主线程上。

于是：主线程 → IPC 回调 → 同步命令 → `add_child` → 短路成"就地" →
**在 WebView2 自己的事件回调里同步创建另一个 WebView2 控制器**。wry 的
`create_controller` 用 `webview2_com::wait_with_pump` 等 `ControllerCompleted`
（`wry-0.55.1/src/webview2/mod.rs:414`）—— 在被回调占据的调用栈里，去等一个要靠
消息泵送达的完成通知，而那个泵正是我们此刻占住的这一层。

主线程从此不再回到事件循环。而**关闭按钮、最大化/最小化、托盘菜单、其余插件的
IPC，全部都在那条线程上** —— 这就是为什么四个故障会同时出现，也是为什么没有一个
会报错：它们本身都没坏。

#### 修法：把动窗口的代码收进一条专属线程

新增 `src-tauri/src/modules/plugins/surface.rs`。它起一条名为 `modulith-surface`
的线程，**这是全宿主唯一能动沙箱 webview 的地方**。命令不再自己动手，只把作业
投进去并等回话：

* 四条界面命令全部改成 `async`，跑在 tokio 线程上，因此碰不到主线程；
* `add_child` 的阻塞发生在所有者线程上，主线程照常泵消息 ——
  这正是自检界面一直能成功的那个条件；
* 所有界面操作按到达顺序**串行**，不会出现"关闭与摆放交错"；
* 阻塞的 `add_child` 不落在 tokio 的工作线程上。

顺带清掉的两处同类隐患：

* `open_surface_at` 里的 `tauri::async_runtime::block_on(...)` 换成 `.await`
  —— 它同样会把调用线程钉住，而调用线程可能是主线程；
* `close_off_main_thread` 那次"为了躲开主线程而随手 spawn 一个线程"的做法取消，
  销毁也走所有者线程，不再每次关面板都创建一个线程。

#### 门禁（`check:sandbox` 第 9 节，12 条）

每一条都验证过**能失败**（改坏 → 断言红 → 还原 → 断言绿）：

* `add_child` 全仓只允许出现在 `surface.rs`，且在里面只有一个调用点；
* `surface.rs` 必须真的起一条线程来执行作业；
* `plugins/` 下不许出现 `block_on`，也不许出现 `run_on_main_thread`；
* 四条 `sandbox_surface_*` 命令必须是 `pub async fn`
  —— 写成同步就是这次假死的形状；
* `lib.rs`（及其生成模板）必须托管 `SurfaceActor`；
* 注册表读锁必须在把活交给界面线程之前放掉。

#### 顺带装上的观测手段：主线程停滞看门狗

这次最贵的不是修，是**读不出卡在哪**：没有任何一处报错，日志只是停了。

`core/watchdog.rs`（debug 构建）起一条线程，每 5 秒往主线程投一个"报个到"的
闭包。主线程只要还在跑事件循环，闭包就会被执行；它要是不再被执行，停滞就是事实
而不是猜测。停滞 ≥3 秒时写一条 ERROR，并明确指向"卡住的位置看这一条之前的
最后几条日志"。

它**不做任何恢复动作**：已经停滞的主线程不会因为一条日志复活，而在那种状态下
"救回来"只会破坏现场。同时它只在 debug 构建里编译 —— 它对用户没有价值，却会在
每一次正常的长任务（磁盘抖动、一次较大的序列化）上写一条吓人的 ERROR，
而让用户习惯忽略 ERROR 的代价是真实存在的。

#### 教训

**"没有日志"本身就是证据。** 前两轮一直在等一条解释故障的日志，而正确的读法是
"日志停在哪一句的**下一句**"。这是这次真正该记住的东西 —— 它比那个 API 形状更值钱。

### 7.45 沙箱插件"显示不出来"：量错了东西，量到 0 高度

**类别：** 缺陷（已修）＋ 门禁（新增）

#### 现象

修完 §7.44 之后，用户的反馈是"打开沙箱插件不会影响其他功能了，但沙箱插件无法正常
在界面中显示"，并判断"应当是插件的问题"。

#### 证据

日志里有一行把答案写死了：

```
[sandbox] 正在创建 webview plugin-com-rinntheor-modulith-hello（2240×1 @ 288,108)
```

**宽度 2240 是对的，高度是 1。** 高度本来量到的是 **0**，被
`SurfaceBounds::sanitized()` 夹成了 1（那个夹取本身是为了防 WebView2 不接受 0 尺寸，
它工作正常）。于是这块界面是一条 2240×1 的细缝。

所以它不是插件的问题：插件自己的脚本正常加载并执行（日志里有
`参考插件（沙箱版）加载完成`），是**我们把它放进了一个 1 像素高的窗口**。

#### 根因

`Home.tsx` 的结构是：

```html
<section class="lc-tab-panel absolute inset-y-0 overflow-y-auto">   <!-- 高度确定 -->
  <div class="p-8">                                                  <!-- 高度 auto -->
    <ModuleRenderer/> → <div class="h-full w-full">                  <!-- 占位块 -->
```

占位块用 `h-full` 表示"占满内容区"。但 `height: 100%` 是**父元素高度的百分比**，
而 `div.p-8` 的高度由内容决定；内容是一个空 div，于是父高为 0，百分比高度解析为
`auto`，占位块的高度也是 **0**。

宽度之所以是对的：块级元素的宽度是确定的，与父元素高度无关。

#### 修法：量内容视口，而不是量占位块

矩形改为从 `.lc-tab-panel` 算 —— 它是 `absolute inset-y-0`，高度确定，而且它**正是**
"内容视口"，也就是这个组件从一开始就声称要量的那个东西（文件头的注释一直这么写，
只是实现时量错了对象）。内边距从直接父级读 `getComputedStyle`，而不是写死 2rem，
这样将来 `p-8` 改成别的值时不会与同屏模块错开。

占位块随之改成**零尺寸的锚点**（`h-0 w-0`），只负责把插件界面挂进正确的标签面板。

顺带补上一条本可以更早生效的防线：**量不出视口时什么都不建**，并留一条能指路的
警告。原来的写法是让 0 一路走到 `sanitized()` 被夹成 1 —— 那把一个"我们量错了"
变成了一个"看起来像插件坏了"的界面。

#### 门禁（新增 5 条，全部验证过能失败）

* `.lc-tab-panel` 这个选择器在 `Home.tsx` 里真的存在（**跨文件契约**，
  改类名会让矩形重新变成 0 —— 这是最容易被无声改坏的一条）；
* 占位块不许再出现 `className="h-full w-full"`；
* 两处退化尺寸守卫（视口本身、扣掉内边距之后）；
* 调用方必须**因为** `measureSurface` 返回 `null` 而真的提前返回。

#### 教训：弱断言等于没断言

这几条断言的第一版写的是 `/return null;/`，而文件里还有别的 `return null;` ——
**把守卫删掉它照样通过**。用"删掉守卫"做反证时它没有变红，那一刻才知道它其实
什么都没守。现在上面每一条都具体到实际那几行，并逐条做过反证。

这是本项目第二次遇到"写了断言但它是恒真的"（上一次是 CSP 那条），因此值得记下来：
**一条没有做过反证的断言，不该被当成证据。**

### 7.46 沙箱自检不该出现在每次启动里

**类别：** 体验（已改）＋ 门禁（新增）

#### 现象

用户的原话只有一句：**"它很打扰。"**

自检在 setup 阶段起一个 4 秒后的异步任务，无条件弹出一块 560×420 的面板。
它验的是真东西（ACL 拒绝、身份来自引擎、协议通道、CSP 生效），但代价是
**每一次启动**都多出一块挡在界面上的面板，去验一件绝大多数时候都成立的事。

#### 改法：改的是"什么时候跑"，不是"跑不跑"

一开始想的是直接删掉。**没有那样做**，理由值得写下来：

自检页是仓库里**唯一会去故意违规的地方** —— 它主动调一条本该被拒绝的命令、主动发
一个本该被 CSP 拦下的请求。删掉它，这条边界就再也没有任何东西会去验一次了；
而"边界悄悄失效"正是这个项目花了好几轮在防的那类失败（见 §7.38、§7.44）。

所以它现在由「插件」页上的一个按钮触发（命令 `sandbox_self_test`），
面板**不再自动关闭** —— 点开它的人正在等结论，自动关掉等于把结论从眼前拿走。
之前的自动关闭是"它自己冒出来"那个阶段加的，前提已经变了。

#### 这是同一类错误的第二次

§7.42 记过一次：自检曾经无条件给**插件**开一块面板，用户没打开任何插件却多出一块
关不掉的东西。那次的结论是"自检只建它自己那一页"，但**没有接着问一句
"那它自己那一页该在什么时候出现"** —— 于是同一个毛病换了个对象又犯一次。

两次的共性是一句话：**启动路径上不该出现任何用户没有要求的东西。**
诊断工具要由人叫才动。

#### 门禁（新增 4 条，全部验证过能失败）

* 启动路径（`lib.rs` 与它的生成模板）里不许出现 `spawn_debug_harness`；
* `sandbox_self_test` 命令必须存在**且是 async**（去掉它等于把能力删了，
  而删掉不会报错 —— 只是这条边界再也没人验过）；
* 「插件」页上必须真的有触发它的按钮。

### 7.47 卸载插件会静默删掉它的数据

**类别：** 缺陷（已修）＋ 门禁（新增）＋ 单元测试（新增）

#### 现象

用户在设计数据层时提出的一条顾虑：

> 第一插件卸载时，数据会没；第二数据存放在 C 盘。

（他说"放插件所在的目录"——**那一半不成立**：`plugins` 与 `plugin_data` 一直是
兄弟目录，数据并不在插件目录里。但"卸载时数据会没"这一条是真的。）

#### 根因

`PluginManager::uninstall` 是这样写的：

```rust
std::fs::remove_dir_all(&plugin_dir)?;       // 插件代码
let data_dir = self.plugin_data_dir(id)?;
std::fs::remove_dir_all(&data_dir)?;         // 数据，无提示
```

而且前端的 `requestUninstall` 在「卸载前二次确认」这个设置**关掉**时，
`uninstallPlugin` 是直接调的 —— **连一个对话框都没有**。

也就是说：用户点一下卸载，插件攒了几个月的数据就没了。没有提示，不进回收站。

#### 为什么它一直没被当成缺陷

因为在"每个插件只有几 KB 配置"的时代，损失小到没人会注意到。同一个行为在
"插件开始存文档、图片、数据库"之后，就从"无所谓"变成"灾难" —— **缺陷的严重性
取决于它消费的数据，而这个前提变了**。

这也是这一条值得记下来的原因：它不是一段写错的代码，是一段**当时正确、后来
变得危险**的代码。判据从"删得多不多"变成"删的是不是用户的东西"，而后者没有
任何编译期或测试期信号。

#### 修法：卸载只删代码，数据默认留下

三条理由：

1. 卸载的意图是"我不要这个插件了"，不是"我要销毁它存的东西"。这是两件事，
   不该由一次点击一起完成。
2. 重装同一个插件能拿回数据 —— 这是"先卸了试试"这类常见用法的前提。
3. 真要删，有一个**独立的、要确认的**入口。

配套的三件东西缺一不可，否则只是把问题换了个位置：

| 加的东西 | 不做的后果 |
| --- | --- |
| `clear_data(id)` —— **不要求插件仍安装**的删除路径 | "数据不会丢"变成"数据删不掉"。`storage_clear` 走 `checked_storage_dir` → `require_permission` → 读清单，**卸载之后够不着** |
| `data_usage(id)` | 确认框里那个选择没有数字支撑，"会保留"是一句空话 |
| `orphan_data()` + 界面上的一块提示 | 保留数据变成**静默的空间泄漏**：占着磁盘，没人知道、没人能删 |

前端：确认框写明"数据会保留"，并给一个**当场删除**的复选框（每次打开都重置为
不删 —— 记住上一次的勾选等于让人在不知情的情况下销毁数据）；有残留时在列表上方
显示总占用与逐项明细，附一个要确认的清理入口。

#### 验证

* **3 条 Rust 单元测试**（把"哪些目录算残留"摘成纯函数 `scan_orphan_dirs` 才测得动）。
  其中一条的第一版写砸了，值得记：它造了几个"非法名"目录（`trailing.`、`a\b`），
  结果**文件系统把它们规范化成了合法名**（`trailing`、`a`），于是"非法名"这个前提
  根本不成立。现在它断言真正的不变量，并**先自检前提**（确实造出了非法名），
  免得一条什么都没造出来的测试安静地通过。
* **`check:quota` 新增 9 条**，逐条反证过。其中"卸载只删插件目录这一处"用的是
  **数数量**而不是找字符串 —— 因为保留数据那段注释里本来就写着
  `remove_dir_all(&data_dir)`（它在解释"以前是这样、现在不是"），
  只匹配字符串会被自己的注释骗过去。
* 另一条断言的第一版把一段**完全正确**的代码判成没接上：它只匹配
  `invoke('plugin_data_usage'`，而实际写的是 `invoke<number>('plugin_data_usage'`。

#### 仍然成立的限制

`ctx.dataDir` 与 `ctx.db` 还没有，因此现在所有插件数据仍收在
`plugin_data/<id>` 里，且仍位于 **Roaming**（`%APPDATA%`）。大数据不该留在漫游
配置目录里 —— 那一步在下一轮，见[插件沙箱与数据规划](../08-规划/插件沙箱与数据-v2.0范围.md) §4.4。

### 7.48 沙箱插件的四个体验问题：色差、留白、快捷键、右键菜单

**类别：** 缺陷（留白已修）＋ 待实现（色差、快捷键、右键菜单）＋ 设计

用户报的原文：

> 1. 插件与软件的色差，样式不统一，存在留白，未全屏；
> 2. 在沙盒插件，我发现无法使用任何快捷键，同时全局右键菜单也失效了。

四个问题的**根因分属三类**。混在一起谈会看不清哪一个是"我们的疏忽"、
哪一个是"架构的必然代价"。

#### 一、留白与未全屏（已修）——两个纯疏忽

40px 的缝隙来自两处，**两处都是我们自己写出来的**，与"独立 webview"无关：

| 来源 | 说明 |
| --- | --- |
| 8px | 宿主合成的插件文档里 `<body>` **从来没有重置 margin**。浏览器默认 `body { margin: 8px }` 原样生效 —— 插件界面四周因此多出一圈背景色缝隙 |
| 32px | `measureSurface` 主动减掉了父级 `p-8` 的 2rem 内边距，理由是"与同屏其它模块看起来一致" |

第二条的理由是**错的**：其它模块是一张卡片，四周留白是设计；插件界面是**一个应用**，
它该占满自己那一块，留白应当由插件自己决定。两处都已去掉，并给文档外壳补上了
`html, body { margin: 0; height: 100% }`。

> `height: 100%` 也归宿主提供：不提供的话每个插件都要自己写一遍，
> 而漏写的那个看起来就像"界面只有一半高"。

#### 二、色差（待实现）——架构的代价，但有正解

插件是**独立文档**，因此看不到宿主的 CSS 变量与 `.dark` 类，它的 `color-scheme`
跟随**操作系统**而不是应用的深浅色设置。所以"应用设成深色而系统是浅色"时必然不同色。
`hello` 用的是 `prefers-color-scheme` —— 那读的正是系统。这不是插件写错了，
是**宿主没把主题交给它**。

**设计：宿主把解析后的主题令牌推给插件**（宿主已经算过一遍，不该让插件再猜）：
命令交给后端 → `entry_document` 渲染成 `:root { --modulith-*: … }` 与匹配的
`color-scheme` → 桥接层暴露 `Modulith.theme` 供插件读取。

**未定**：主题在插件**已打开**时切换怎么办。文档是打开那一刻生成的，重新显示
不会重新加载。选项是"给活着的界面 eval 一段更新变量的脚本"（快，但要在所有者
线程上加一种新作业）或"主题变化时重建界面"（简单，但丢插件状态）。实现时定。

#### 三、快捷键失效（待实现）——架构的代价

`useGlobalShortcuts` / `shortcutRegistry` 挂在**宿主文档**上。插件是独立原生
webview，有自己的焦点；焦点在插件里时键盘事件进的是插件那个渲染进程，
**宿主文档的监听器根本收不到**。这不是 bug，是"独立 webview"的定义。

**设计：把宿主的快捷键表注入插件文档，由桥接层转发。**

* 宿主生成入口文档时把快捷键表（键位 → 动作 id）内联进去 —— 与权限列表同一套做法；
* 桥接层在插件文档里监听 `keydown`，**只匹配表中的组合才转发**
  （否则每次按键都过一次 RPC，而输入框里打字是最频繁的操作）；
* 插件自己的处理器先跑；它若 `preventDefault`，桥接层不转发 —— 编辑器类插件
  因此能保住自己的快捷键；
* 宿主收到转发后交给 `shortcutRegistry` 执行。

#### 四、全局右键菜单失效（**已实现**）——障碍一只剩一条

**障碍一**同快捷键：焦点在插件文档里，宿主的 `contextmenu` 监听收不到。

**障碍二已经不在了。** 这一节写的时候插件界面是**原生子 webview**，因此即使事件
被转发到宿主，菜单也会画在那层原生控件**底下** —— 用户看不见。当时给出的设计是
"把全局右键菜单做成它自己的窗口，复用托盘菜单那一套"。

**§7.50 把插件界面改成跨源 iframe 之后，这条设计不再需要**：iframe 是宿主文档里
的普通 DOM，`fixed z-50` 的菜单天然在它上面。于是只剩下障碍一，而它的解法与快捷键
那一条同构：**在插件文档里接住、转发给父文档**。

实现落在三处，缺一处这条链路就是断的（而且断得同样安静）：

| 位置 | 做什么 | 为什么只能在这里做 |
| --- | --- | --- |
| `resources/sandbox-bridge.js` | 在插件文档里接住 `contextmenu`，`postMessage` 给父文档 | 宿主够不到那个文档 |
| `components/SandboxSurface.tsx` | 加上那块 iframe 的矩形偏移 | 跨源 iframe 读不到父文档，插件那边算不出这个偏移 |
| `pages/Home.tsx` | 订阅并设置 `menuPos` | 菜单的唯一事实来源是它的 `menuPos` |
| `resources/sandbox-bridge.js` | 在插件文档里接住 `mousedown` / `Escape`，转成"关掉" | **同上 —— 而第一版漏了这一行**，见 §7.53 |

三处细节是刻意与既有的两条规则对齐的：

* **挂在冒泡阶段**，且 `event.defaultPrevented` 为真就不转发 —— 与快捷键同一条
  让位规则，也与宿主内部那条「模块自己的右键优先」一致。插件调 `ctx.ui.contextMenu`
  画的菜单因此仍然是它自己的。
* **输入框里不接管**（`isTypingTarget`）：浏览器原生菜单在文本框里是有用的。
* **先 `preventDefault` 再转发**：不拦的话引擎会同时弹出它自己的默认菜单，
  用户看到的是**两个**菜单叠在一起。

**为什么走 `postMessage` 而快捷键走 `rpc`。** 快捷键必须走 rpc，因为只有宿主能判断
那个组合是不是它自己的；右键不一样 —— 弹什么菜单、有哪些条目全由宿主决定，桥接层
递过去的只是"用户在这里按了右键"。于是 `postMessage` 是对的那条路：少一趟协议往返 +
一条 Tauri 事件，而它的来源由**父文档**用 `event.source` 核对（见那条监听器），
比任何字符串都硬。

**代价说清：** 三次实现都正确的必要性在于，"少了任何一处"的表现都是**右键之后什么
都不发生，而控制台里一个错都没有** —— 这正是它此前一直没被修的原因。`check:sandbox`
第 10 节因此为三处各钉了一条断言。

#### 教训

留白那两条是**我们自己的疏忽**，与沙箱无关，却在"沙箱插件看起来不对"这个笼统
印象里被一起算到了架构头上。把"架构的代价"与"我们的错"分开列出来，是这一节
最该留下的东西 —— 否则下一次会拿架构当借口，放过本来能修的东西。

### 7.49 `node:vm` **不是**安全边界（实测），后台插件真正的边界在引擎的权限模型

这一条不是"发现了一个 bug 然后修好"，而是**一次实测推翻了一个想当然的设计前提**，
因此必须写下来 —— 下一版方案很容易又会把它当成边界。

#### 背景

后台（无界面）插件跑在各自的 Node 子进程里，插件代码跑在一个 `node:vm` 上下文
中。方案里原本的措辞是"每个插件在自己的 global 里，拿不到 `require` / `import` /
`process`"。

#### 实测

写一段探针插件，它只做一件事：量一下自己能看到什么。

```
globalThis.constructor.constructor('return process')()   → 拿到了 process
process.getBuiltinModule('node:fs')                       → 拿到了 fs
```

**一行就出去了。** Node 官方文档也明确写着 `vm` 不是安全机制 —— 我们却先把它
当成了边界。同一次探针还量到：`process.env` 完整可读（60 个变量，含应用自己的
`DSH_*`）。

#### 真正兜住的是 `--permission`

把子进程改用 `--permission` 启动（只放开这个插件自己的代码目录）之后，**
在已经逃出 vm、拿到 `process` 与 `node:fs` 的前提下**再量一次：

| 尝试 | 结果 |
|---|---|
| 读插件目录之外的文件 | `ERR_ACCESS_DENIED` |
| 读自己的入口文件 | 允许 |
| 写任何地方 | `ERR_ACCESS_DENIED` |
| `child_process` | `ERR_ACCESS_DENIED` |
| `worker_threads` | `ERR_ACCESS_DENIED` |
| 原生 addon | `ERR_ACCESS_DENIED` |
| 网络 | `ERR_ACCESS_DENIED` |
| `process.env` | **仍然可读** ← 唯一的洞 |

#### 因此改了什么

1. 后台插件子进程一律用 `--permission` 启动，只放开**它自己的代码目录**
   （数据目录不放开：`ctx.dataDir.*` 全部经过宿主，子进程不需要碰那些文件）；
2. 子进程用 `env_clear` 启动，只留 `SystemRoot` / `TEMP` 这类启动必需的变量
   —— 补上上面那个洞；
3. Node 版本不够（< 23）时**降级运行**，并把 `isolated: false` 如实报给界面，
   由界面提示用户升级运行时，而不是假装隔离存在。

#### 教训

**"我们没给它 `require`" 与"它拿不到 `require`"是两件不同的事。** 前者是关于
我们写了什么的陈述，后者是关于它能不能做到的事实 —— 而只有后者是可以被验证的。
这次靠一段十行的探针插件把一个想当然的前提变成了事实，代价很小；如果等到
"用户报告某个插件读了别的东西"才发现，代价会大得多。

同样地，`check:sandbox` 与 `check:background` 里那些断言**只能守"我们写了什么"**。
它们守不住"它能不能做到" —— 后者需要这种真的跑一遍的探针。
`a_background_plugin_can_call_back_into_the_host` 就是那种探针。

### 7.50 插件界面盖住宿主自己的浮层 —— 那不是 bug，是原生子 webview 的合成模型

**这一条推翻了 §7.44 选定的那条路。**

用户报了两处：沙箱插件界面会盖住侧边栏边缘的模糊与标题栏展开的搜索框。

一开始按 §7.44 的姿势去修：把"每 150ms 做一次命中测试、被盖住就把插件 webview
收起来"的 `isCovered` 几何轮询从"只看中心点"改成 5×5 网格 + 覆盖率阈值。
**那是错的**：原生子 webview 由引擎合成在父窗口客户区**之上**，CSS 的 `z-index` /
`position: fixed` / `backdrop-filter` 对它**一律无效**。判据调得再准，也只是在
"插件界面被盖住"与"插件界面自己消失"之间换一个。

盘点之后受影响的远不止那两处：标题栏搜索展开、宿主右键菜单、通知中心、轻提示、
设置对话框 —— 宿主**每一块浮起来的界面**都在插件界面之下。其中"设置"与"通知中心"
看起来还能用，只是因为它们的覆盖率超过了阈值、插件界面被收起来了 —— 那不是修好，
那是用"插件界面消失"换来的。

**修法：插件界面改成跨源 iframe。** 它回到 DOM 里，层级由 CSS 决定，几何问题整类
消失。核对 Tauri 2.11.5 源码之后，隔离**没有变弱**，而是三重（子框架拿不到 IPC、
`invoke_key` 比对、同源策略）；另外 wry 注册自定义协议过滤器时用的本来就是
`SOURCE_KINDS_ALL` 那个**为 iframe 准备**的重载。

**风险与代价，一条都不藏：**

* 沙箱的安全性现在依赖"Tauri 继续不给子框架注入 IPC"这一件事，而它会**静默**失效。
  因此桥接层里加了一盏灯（`assertNoHostIpc`），自检页里加了一个同源 iframe 探针 ——
  只验自检窗口是不够的：那个窗口是主框架，Tauri 会给它注入引导脚本；
* 全部界面共享**一个来源**，因此 `localStorage` / `indexedDB` / `cookies` 是公用的。
  桥接层用**不可重定义**的抛错访问器把它们封掉（可重定义的属性插件自己能删，
  那样封了等于没封）；
* 界面在**主 webview 的进程里**，内存的账要重新算 —— §8 第 8 步因此更必要，
  而"驻留上限"这个概念本身也变了：从前淘汰的是原生 webview（每个一套控制器），
  现在卸载一个 iframe 会连插件界面状态一起丢掉。
* 身份模型必须跟着换。从前是 webview 标签，而 iframe 的标签**全是 `main`** ——
  不改的话所有插件会塌成同一个身份，插件 A 读得到插件 B 的数据。现在是
  **每个界面一个不可猜的令牌**（`uuid` v4，路径第一段）。

**删掉的：** `plugins/surface.rs`（628 行：所有者线程、几何测量、`add_child`、
驻留上限）、`SandboxSurface.tsx` 的测量与遮挡轮询、`sandbox_surface_hide` /
`sandbox_surface_bounds` 两条命令（命令总数 152 → 150）。

**没删的（更正同轮文档里的初稿）：** `desktop/overlay.rs` 一度被列进"要删的"，
理由是"它存在的唯一理由就是原生子 webview 盖得住宿主 DOM"。**那个理由不成立** ——
它是一个独立的 `alwaysOnTop` **窗口**，悬在主窗口整体之上：子 webview 在它下面，
iframe 也在它下面。它服务的是插件的 `ctx.ui.dialog` / `ctx.ui.contextMenu`，
与这次迁移正交。

**顺带解掉的：`ctx.fileDrop`。** 它长期记在"沙箱里补不了"那一栏，理由是"拖放是
窗口级事件、子 webview 收不到"。核对 wry 之后发现理由只对了一半：wry 把拖放处理器
注册在 webview **自己的 HWND 及其全部子窗口**上
（`wry-0.55.1/src/webview2/drag_drop.rs:50`）。子 webview 有自己的 HWND 且没注册
处理器，那条路从根上断掉；iframe 之下指针底下始终是主 webview 的 HWND，事件照常
触发且带指针位置。

补法分三段：宿主算出"这一界面能不能收"（`SurfaceHandle::file_drop`，判据是清单里
的 `filesystem-read`）、前端按**位置**筛（各标签面板在 DOM 里是叠在一起的，只按
前台判定会让下面那一摞都收到别人的拖放）、桥接层扇出
（`Modulith.fileDrop = { isAvailable, subscribe }`，形态与 in-process 逐字一致）。
**权限判定在宿主**，不在桥接层自查 `PERMISSIONS` —— 那正是这套设计反复强调不算
边界的东西。

### 7.51 一个只用于展示的字段，让插件市场对所有人打不开

**类别：** 缺陷（已修）＋ 判据（新增一条划线规则）＋ 门禁（新增 `check:market`）

#### 现象

用户报的是市场报错，而错误信息本身就说明了两件事：

```
无法获取插件索引。
raw.githubusercontent.com：plugins[0].versions[0].engines.modulith 必须是非空字符串
cdn.jsdelivr.net：plugins[0].versions[0].engines.modulith 必须是非空字符串
```

**两条来源给出同一句话**，这排除了网络：`fetch_registry_text` 真的把索引取回来了，
失败发生在解析。"插件列表取不到"这五个字与"某一项解析失败"是两种完全不同的故障。

#### 根因：索引还没推上去

`.lcp` 之外，插件仓库还有一件东西是**发布物**：`index.json`。而它上一次推到远端
是在**项目改名之前** —— 那份索引里写的是 `engines.loopcore`。

改名（`engines` 的键从 `loopcore` 改成 `modulith`）在本地提交里，索引也在本地
重新生成过（`engines.modulith` 在今天的 `index.json` 里），**但都没推**。
于是 GitHub 与 CDN 服务的仍是旧字节，而应用拿到的 `engines` 里没有 `modulith`。

#### 真正该记下来的是那条线划错了地方

`engines.modulith` 是**只用于展示**的字段：它出现在详情页的"需要宿主"一行。
已安装那一侧更是明确写着它"只提示、不阻断"（`pluginRuntime.ts` 的 `engineAdvisory`）
—— 后端遇到引擎范围不匹配连装都不拦。

然而在市场这一侧，它由一个 `asString` 读出来，缺失即 `fail()`；而 `parseIndex`
的既定策略是**结构错误一律整体失败，不做跳过坏条目**（那个策略本身是对的，
理由见它的注释：跳过坏条目会让问题以"少了一个插件"的形式安静存在）。
两者合起来：**一个纯展示字段把整个市场弄挂了。**

同一个字段在两处有相反的力量，这件事在仓库里没有任何地方被写下来 —— 直到它
以"所有人的市场都打不开"的形式出现。

#### 因此划了一条线（这是这一节唯一想留下的东西）

> **宿主据此行事的字段必须严格；只用于展示的字段不许拖垮整份索引。**

| 字段 | 宿主拿它做什么 | 缺失时 |
| --- | --- | --- |
| `id` / `version` / `tag` / `package.sha256` / `permissions` | 装什么、校验哪个哈希、显示什么风险 | **整份索引失败**（不变） |
| `engines.modulith` | 详情页的一行字 | `null`，界面显示「未声明」 |
| `kinds` / `background` / `runtime` | 形态、后台标记、隔离状态 | 各自的"未声明"档 |

`engines.modulith` **不认 `loopcore` 这个旧键**：改名那次提交的说明写得很清楚 ——
"`loopcore` 这个键既不会被读取、也不会报错，留着它的插件**看起来**声明了兼容范围，
实际上什么都没声明"。把它当成 `modulith` 等于替发布者说一句他没说过的话。

#### 顺带修掉的一处旧伤

同一份旧索引还缺 `runtime`（它比 `engines` 改名还新），而 `runtime` 决定
**安装策略放不放行**（见 §7.52）。因此 `parseRuntime` 有三档，而"不知道"是其中一档。
三档各自的说法与"不知道"为什么不就地拒绝，见
`src/services/pluginMarket.ts` 的 `installGate`。

#### 门禁：`check-market`

新脚本把**真实故障的形状**跑一遍（`node scripts/check-market.ts`）：构造一份
`engines.loopcore` 的索引，断言它**能解析**、`engines.modulith` 读成 `null`、
那个插件仍然出现在列表里。同时用一组"该严格的"（sha256 缺失/非法、permissions
不是数组、`latest` 指向不存在的版本、schemaVersion 比宿主新）作为**对照**，
防止下一次把"宽容"读成"随便放宽一点也无妨"的许可。

**每一条都验证过能失败**：把 `engines.modulith` 改回 `asString` 之后，31 条里红 7 条。

#### 还没做的一件事（部署，不是代码）

**插件仓库必须重新生成索引、重新签名、推上去。** 应用侧的容错让市场重新可用，
但用户看到的仍是几天前的版本号（`notes 1.0.1` 而不是 `1.0.3`），
因为远端那份索引本来就旧。步骤：

```
node scripts/build.ts          # 重新生成 index.json（含 runtime）
pnpm tauri signer sign -f <私钥> index.json
git add index.json index.json.sig && git commit && git push
```

`build.ts` 只会**提醒**该签名（它刻意不接触私钥），而忘了这一步的代价是
**验签失败、市场对所有人打不开** —— 与这次的现象一样，原因不同。

### 7.52 沙箱做完了，而用户可以装一个未隔离插件把它绕过去

**类别：** 设计（新增策略）＋ 缺陷（策略缺失）＋ 门禁（`check:sandbox` 第 7b 节）

用户的原话是：

> 虽然沙箱功能已经基本实现，但是用户可以添加未隔离的插件（也就是非沙箱插件），
> 那么沙箱就变成了摆设，但是这不能一刀切。

#### 问题比"少一道门"更具体

未隔离插件与宿主**共享同一个 JS 上下文**。因此对它来说：

* `permissions` 是**声明**，不是约束 —— 它可以直接调宿主这个 realm 里的任何东西，
  不需要走 `ctx.*`；
* 因此"这个插件申请了哪些权限"**不是一个可用于判断风险的量**，显示它是**误导**。

也就是说，装一个未隔离插件不是"装了一个更危险的插件"，而是**把沙箱对这个插件的
作用整体取消**。而这件事在界面上**没有任何症状**：插件照常出现在列表里，
权限徽章照常显示。

#### 不做一刀切，但也不把选择权藏起来

| 决定 | 理由 |
| --- | --- |
| 加一个设置项 `allowUnsandboxedPlugins`，**默认关** | 一刀切会永久挡住那些"只做纯计算"或必须先借宿主能力才能活的东西。默认关而不是默认开，是因为"点一下安装"不该顺带等于"放弃隔离" |
| **只管安装**，不碰已装上的 | 做成"关掉就禁用"会让一次应用升级变成一次静默的插件下线，用户只会以为插件坏了 |
| 设置放在「设置 → 插件」，不放在「安全」 | 安全页管的是登录与访问密钥。用户撞上这道门时人就在插件页 |
| 市场里**不隐藏**这些插件，只标出来 | 隐藏会让它们以"少了一个插件"的形式安静消失 —— 那是最难被发现的一种失败 |
| 被拦下时按钮**不灰掉**，改成「不允许安装」并可点击 | 灰按钮只给出一个"不能点"的事实，用户唯一能做的是猜。点下去给的是完整原因与下一步 |
| 打开开关之后，安装前**仍然确认一次**，且 `runtime` 参与"要不要确认" | 权限没变不代表风险没变：一个插件可以保持同样的权限声明，而把 `runtime` 从 `sandboxed` 改成 `in-process`。只看权限的话那次更新会被判成"无需确认"，于是一次点击就换掉了沙箱版本 |

#### 判据落在哪一层：索引是**预测**，包内清单才是**真相**

这是这一节里最需要想清楚的一处，因为它决定了"索引里没有 `runtime` 时怎么办"。

真正的强制在 `PluginManager::install_from_root` —— 那是四条安装路径
（`.lcp` / 目录 / URL / 市场）**唯一**的汇合点，判据取自**包内清单**，
因此它同时覆盖"绕过市场直接 invoke 安装命令"那条路（那条路确实存在：
后端分辨不出调用者是谁，见 `install_from_url` 的说明）。

前端（市场）那一层只是**体验**：它读的是索引，而索引是打包时从清单派生的一份**缓存**，
可能是旧的。于是当索引里没有 `runtime` 时，两种做法都说得通，而选择是：

> **放行到下一道门**，而不是就地拒绝。

理由：就地拒绝的代价落在一个无辜的对象上 —— 一份只是旧了点的索引会让**所有**
插件都装不了，而其中绝大多数本来写明了 `sandboxed`，用户看到的是"市场坏了"。
放行之后，结果要么装上（清单确实是 `sandboxed`，那本来就该装上），要么被后端
拒绝并给出一句准确的原因。**后者不比前者弱**，因为边界从来不在这份远端索引上：
索引可以被换掉，而包内清单与插件自己的代码在一起。

把"不知道"当成拒绝，是把一道体验层的判断当成了安全边界 —— 那恰好是这套设计
一直在避免的事。

#### 这条策略**管不到**的一条路（如实写下来）

「备份恢复」会把整个 `plugins/` 目录（含 `registry.json`）整份写回去，那条路
不经过 `install_from_root`，因此**不经过安装策略**。

刻意不去堵它，理由不是"懒得做"，而是它与这条策略管的事**不是同一件**：
它复现的是"用户自己机器上曾经的状态"，而不是"从一个来源装一个插件"。
而一个能往备份文件里塞东西的人，本来就能直接往应用数据目录里放文件 ——
在那条路上加检查不会多拦住任何人。

> 反过来说：**如果哪天真出现了一个"从外部导入一份插件状态"的入口**（导入别人的
> 配置包、从云端同步插件集），那它就是一条**新的安装路径**，必须接进
> `install_from_root` 或在那里调一次 `check_install_policy` —— 而不是像备份恢复
> 这样整份写盘。这一句是写给下一个加这类功能的人的。

**但"看不见"这件事必须补上。** 未隔离插件的危险恰恰在于**没有任何症状**，
所以它来自哪一条路都不重要 —— 重要的是它必须有一个能被看见的地方。
因此「设置 → 插件」那个策略卡片上**始终**列出已安装的未隔离插件
（开关关着时也列），并说清它们与这个开关无关。

#### 门禁

* `check:sandbox` 第 7b 节：策略落在 `install_from_root`、发生在**写盘之前**、
  判据用 `needs_own_webview()`、错误信息里有下一步、默认值前后端一致。
  **验证过能失败**：删掉那一行调用后，两条断言当场变红。
* `check:market`：`installGate` 三档的行为、默认值只认显式 `true`。
* Rust 单测 `manager::tests` 六条：缺省 `runtime` 与显式 `in-process` 都被拒、
  `sandboxed` 不受影响、打开设置后放行、错误信息同时给出原因与下一步、
  默认值在 `impl Default` 与 serde 两侧都是关。

### 7.53 菜单弹得出来，收不回去 —— 又是同一条边界，而这次只修了一半

**类别：** 缺陷（已修）＋ 判据（那条被否掉的优化）＋ 门禁（`check:sandbox` 第 10 节新增 8 条）

#### 现象

§7.48 那一节的修复上线之后，用户立刻给了下一条：

> 全局右键菜单确实可以在沙箱插件中弹出来了，但是有个问题在于我收不回去了，
> 我在空白处点左键，它无反应，但是在非沙箱插件中却是正常的。

#### 根因：`GlobalContextMenu` 的**关闭**比打开多两条路径，而两条都在宿主文档上

```js
document.addEventListener('mousedown', handleDown, true);  // 点到菜单外就关
document.addEventListener('keydown', handleKey);           // Escape 关
```

而插件界面是**跨源 iframe**，是一个独立文档 —— 在它里面点一下左键，那个
`mousedown` 只在插件文档里派发，宿主那条监听器**一次都不会触发**。非沙箱插件
没有这个问题，因为它们的界面就在宿主文档里（这也正是用户观察到的对比）。

#### 真正的教训：转发一个事件时，要把它**整条交互**都过一遍

§7.48 的修法把 `contextmenu` 转发了，然后停了。但"右键弹出一个菜单"这条交互
不是**一个**事件，而是**一对**：打开 + 取消。而取消那条路上跑的 `mousedown` /
`keydown` 属于**另一份文档** —— 于是"打开"跨过了那道边界，"取消"没有。

这不是疏忽了一个 `if`，是**在边界上只搬了一半的东西**。同一个 `docs` 里那句
"菜单本来就该出现在鼠标位置"提醒的是打开的位置，而没有人问过"那它怎么关"。

可复用的判据写在这里：**当一个交互由 N 个事件组成，而其中任何一个需要跨 iframe /
跨 realm / 跨进程转发时，N 个都要逐个过一遍** —— 转发点天然是"能跑通就够了"的
地方，而"跑通了"通常只证明了第一个事件通了。

#### 修法：开与关走**同一条**通道

`contextMenuBridge` 只有**一条**事件名，载荷是 `{x, y} | null`：

| 方向 | 载荷 | 含义 |
| --- | --- | --- |
| `requestGlobalContextMenu(x, y)` | `{x, y}` | 在这个位置打开 |
| `dismissGlobalContextMenu()` | `null` | 关掉 |

**这不是省事，是缺陷的直接产物。** 菜单的"开"由一条通道负责、"关"由另一条负责时，
只要一方漏了或者两边判据不一致，结果就是**一个关不掉的菜单**。让开与关成为同一个
通道上的两种取值之后，"谁负责关"这个问题在类型上就不存在了：只有一处会写菜单的
位置，而写 `null` 就是关闭。门禁里有一条断言直接钉住"只允许一条事件名"，
因此"再加一条关闭事件"这种改法在写出来的那一刻就会红。

#### 被否掉的那个优化（这一段比修法本身更值得留）

关闭信号**无条件**转发：每一次 `mousedown`、每一次 `Escape` 都发一条
`postMessage` 给宿主，宿主那边没有菜单要关时它是无操作。

我第一版写的不是这个，而是"只在刚把一次右键交给宿主之后才转发"——
桥接层记住"我刚交出去一次右键"，之后那次点击才转发。省掉"没有菜单时每一次点击
都过一遍 postMessage"。

**那个优化错在分屏上。** 两个面板并排时它们是**两份独立文档**：用户在左面板右键
（左桥接层被武装）、然后点右面板想取消 —— 右面板不知道有过那次右键，什么都不转发，
菜单照样留在屏幕上。**这与用户报的现象一模一样，只是路径更窄。**

要修它就得让"有一个菜单开着"跨 iframe 可见，也就是让宿主把状态推给每个界面 ——
多一条推送通道、多一份要同步的状态，而且**有竞态**：菜单打开与"插件知道菜单打开了"
之间那几毫秒里的一次点击会被漏掉，而漏掉的症状就是同一个"关不掉的菜单"。
**用一条竞态换一点流量，不划算。**

成本核算（写在代码注释里）：一次拖拽只发一次 `mousedown`，因此这是低频事件；
而同一份桥接层的 `keydown` 处理**每一次按键**都要跑一遍组合键规范化与查表。
这条转发的成本在整份桥接层里排在很后面。

门禁里因此有一条**反向**断言：`menuAwaitingDismiss` 这个词不许再出现在桥接层里
（注释剥掉之后）。**验证过能失败** —— 把它加回去，那条断言当场变红，其余 575 条
仍然是绿的。

#### 门禁（`check:sandbox` 第 10 节，新增 8 条，全部验过能失败）

* 桥接层真的会转发 `host-context-menu-dismiss`；
* 关闭信号**无条件**转发（那条被否掉的"武装"写法一出现就红）；
* 桥接层里没有"菜单是否开着"的本地标记；
* `mousedown` 那条不看 `defaultPrevented`（那次点击按定义在菜单之外）；
* `Escape` 走既有的 `keydown` 监听，且不 `return`（插件自己 `preventDefault` 时
  这次按键归它，那条早退在更前面）；
* `SandboxSurface` 把关闭信号交给桥接服务；
* 桥接服务只声明**一条**事件名，关闭复用同一条、用 `null` 表示；
* `Home` 把 `null` 写回 `menuPos` 的**同一处**状态。
