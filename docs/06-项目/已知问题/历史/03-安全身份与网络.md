### 7.4 恢复码的复制、打印与两步流程

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 复制出来的恢复码是一大串、看不出分组，而且只能选中某一段 | 分组被渲染成了**独立的 `<span>` 元素**，因此"选中一部分再复制"只能拿到一组；而复制按钮写入的又是去掉连字符的裸串（`ABCD…`），与屏幕上带连字符的呈现不一致 | 显示改为**一整段可自然选中的文本**，分组通过等宽字体与窄间隔体现，而不是独立可选元素；复制按钮改为写入**完整原文（含连字符）**，与屏幕所见一致。后端 `normalize_recovery_code` 本来就会忽略连字符，因此粘贴时带不带都可用 |
| 无法把恢复码保存成 PDF | 项目没有 PDF 依赖，装一个属于新增第三方依赖 | 改用系统打印对话框的「另存为 PDF」：新增 `RecoveryPrintSheet` 渲染一张打印件，`index.css` 的 `@media print` 段在打印时隐藏屏上一切、只显示它。不新增依赖，产出的是真正的 PDF |
| 用恢复码重置时，三个输入框放一起，出错却总聚焦第一个，用户以为恢复码抄错了 | 三步合一时错误提示与 `autoFocus` 都落在表单第一个输入框上 | 拆成两步（详见下） |

打印实现有三个必须记住的约束，都写在 `index.css` 的注释里：

1. `@media print` **不能放进 `@layer`**——分层样式优先级低于未分层样式，而这些规则要覆盖 `dark-theme.css` 里未分层的深色映射；一旦被包进 `@layer`，打印件会带着深色底色输出（费墨且难读）。
2. 必须放在 `dark-theme.css` 之后（文件末尾），两者优先级相同，靠后加载取胜。
3. 显式强制浅色（`color-scheme: light` + 重写颜色），不能指望深色模式下自动输出白底。

**两步恢复流程。** 新的交互是：进入恢复界面后**只有一个输入框**（恢复码），核验通过才进入第二步（两个新密钥输入框）。这样每个屏幕只有一个待完成的动作，错误提示必然指向真正出错的那项。

后端配套拆成两个命令：`verify_recovery_code` 只核验、**不修改任何状态**，通过后签发一个 10 分钟有效的一次性令牌；`reset_access_key_with_recovery_code` 消费令牌并设置新密钥。

令牌在内存中只保存**命中的那一枚恢复码的下标**（`matched_index`），不保存码原文，也不保存任何摘要。原因有两层：后端只存 Argon2id 哈希，每次哈希结果都不同，无法事后逐字节比对；而把原文留在内存里等于多存一份明文凭据。保存下标则足够——第二步只作废这一枚。令牌单次使用、10 分钟过期、签发时顺手清理过期条目，重置成功后用户改由新密钥进入。这**不构成额外攻击面**：拿到令牌需要先通过恢复码核验，而核验成功后本来就能直接重置。

（早期实现保存的是「归一化恢复码的 SHA-256 摘要」，但下游没有任何代码使用它——它既不能定位要作废哪一枚，也无法被校验。这是一处从旧设计残留下来的死数据，后来改为 `matched_index`。）

### 7.5 恢复码改为「多枚独立短码」+ 对比度与卡住问题

上一轮把恢复码做成**一枚 32 字符的长码、按 4 字符分组显示**。这个形态本身有歧义，本轮推翻重做。

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 用户把一整串长码读成"多个恢复码"，只输入其中一组，于是每次都报错 | **形态歧义**：一整串按组分隔的字符既像一个码，也像几个码，用户无法自行判断该输整串还是输一组 | 改成**互不相干的短码**（每枚 20 字符，分 4 组），列表里一行一枚、带序号、各带独立复制按钮。一行就是一个完整凭据，不存在"要不要全输"的疑问 |
| 「复制完整恢复码」「存为 PDF / 打印」和提示文字太淡，几乎看不见 | 这几个元素位于深色授权界面上，我用了 `text-gray-100` / `text-emerald-200` 这类低对比度颜色，且叠在已带透明度的底色上 | 全部提到 `text-white` / `text-gray-200` 以上，按钮改用实色底配 `font-semibold`，边框也加重 |
| 用恢复码真的重置成功后，点「我已保存，继续」直接卡在那个界面 | `finishIssuedCode` 只做了 `refreshAuth()`，把"界面该切到哪一屏"完全交给 boot 状态机。一旦 boot 因为任何原因没有推进（或 `refreshAuth` 抛错被静默吞掉），界面就停在 `created` 模式 —— 而这个模式只渲染恢复码面板，于是留下一个空白面板 | 补两件事：**显式把 mode 切回 `unlock`** 作为兜底，并对 `refreshAuth` 加 try/catch，失败时把原因显示出来而不是吞掉 |

**短码的语义**（与 GitHub / Google 的备份码一致）：

- 每枚各能用一次；忘记密钥时输入**任意一枚可用**的即可。
- 丢了几枚还有其余可用，不必因为抄漏一枚就作废全部。
- 单枚 100 bit 熵。多枚合计**不等于** 100×N bit —— 攻击者只需猜中任意一枚，因此有效强度由单枚决定，这仍远超暴力搜索能力。
- 审计日志记录命中的是第几枚（`recovery-reset#2`），便于排查同一张纸被反复使用。
- **用掉一枚只作废那一枚，其余保留**；重新生成才作废整套。原因见 4.7 节。

**枚数后来从 8 调整到 3。** 理由是枚数越多列表越长、收益递减，而 3 枚足以覆盖「抄漏一枚」与「分两处存放」这两件真实会发生的事。调整时有两个只在 8 枚下成立的测试硬编码了 `codes[3]` / `codes[5]` 之类下标，已改为取最后一枚，以后改数量不会再让测试误报。

**升级路径（必须记住的一点）。** `recoveryHash` 从 `Option<String>` 变成 `Vec<String>`，旧值无法解析。这里刻意**不让整个 `auth.json` 解析失败**——那会连访问密钥一起回落到默认值，用户会被要求重新设置密钥，等同于数据灾难。`config::load_from_with_reason` 的策略是：先尝试"只移除恢复码字段"后重新解析，成功则只清除恢复码、保留密钥/设备/日志，并立刻回写文件。因此升级后用户只需重新生成一套恢复码。

**顺带修正。** 归一化的最小输入长度从 16 降到 12：原来的阈值偏高，用户抄漏一组时会得到"格式不对"而不是"恢复码不正确"，后者才准确。

### 7.12 应用标识符变更与个人账号名脱钩

| 项目 | 说明 |
| --- | --- |
| 背景 | 标识符原为 `com.metazero-tsip.modulith`，其中 `metazero-tsip` 是开发者**旧**的 GitHub 账号名（后更名为 `Rinntheor`），且该值形式上假定拥有 `metazero-tsip.com` 这个并不存在的域名 |
| 问题 | 反向域名式标识符的语义前提是**控制对应的命名空间**。把个人账号名写进标识符，既会随账号改名而过时，也不构成有效的命名空间 |
| 现取值 | `com.rinntheor.modulith` |
| 时机说明 | **这是变更标识符的最后合理时机。** 未发布时改动只影响开发者本人（需重设访问密钥）；一旦有真实用户，标识符变更会让所有用户的数据目录换位置——Tauri **不做迁移**，表现为访问密钥、恢复码、设备白名单、已装插件、全部设置与通知一次性不可见。此外 Windows 安装包会把它当成另一个产品，旧版不会被升级而是并存 |
| 影响范围 | 数据目录：`%APPDATA%\com.metazero-tsip.modulith` → `%APPDATA%\com.rinntheor.modulith` |
| 如何保留旧数据 | 各数据文件的**格式不依赖标识符**，因此可直接把旧目录内容复制到新目录：把 `%APPDATA%\com.metazero-tsip.modulith` 下的 `settings.json`、`auth.json`、`notifications.json`、`sidebar_config.json`、`plugins/`、`plugin_data/` 复制到 `%APPDATA%\com.rinntheor.modulith`。这样访问密钥与已装插件都不会丢 |
| 同步位置 | `src-tauri/tauri.conf.json`（唯一实际配置）、`README.md` 的命名表、本条记录 |

**标识符自此冻结。** 它与产品名（`Modulith Desktop`）、包名（`modulith-desktop`）是三个不同的东西：包名可以随构建调整，产品名可以改显示文案，**只有标识符动不得**——它一旦随版本变化，用户数据就会"丢失"。`pnpm ver check` 会校验产品名一致性，但**不会**校验标识符（它不该变，因此没有可校验的基准）。

### 7.26 一次独立审阅触发的安全收口与文档校正

本轮由一次外部审阅触发。四处代码问题都是同一个形状 ——**能力存在，但检查只挂在一半调用点上**；另有一批是纯粹的文档漂移。

#### `export_plugin` 的 `dest` 曾是任意文件覆盖原语

| 项目 | 说明 |
| --- | --- |
| 现象 | `export_plugin(id, dest)` 无权限检查，`dest` 直接交给 `normalize_export_path`，最终 `File::create(dest)` **截断覆盖**目标文件；`export` 还会先 `create_dir_all(parent)`。插件因而可以覆盖 `auth.json`、`settings.json` 或任意路径的文件 |
| 为何危险 | 插件可直接 `invoke` 这条命令（同 JS 上下文、后端无从知道调用者），而它不需要任何权限声明。§4.1 曾断言 `filesystem-write`"完全没有对应的命令"——**那是不准确的**，这条命令正是它的语义 |
| 处理 | `dest` 收口为**默认导出目录内的裸文件名**（新增纯函数 `export_file_name`），且目标**已存在时拒绝覆盖**。默认导出目录是用户的下载目录、不是应用专有目录，所以"只允许新文件"这一条不能省 |
| 前端影响 | 无。`Plugins.tsx` 只传 `dest: null`（走原生保存对话框），没有任何既有调用受影响 |
| 测试 | `export_target_must_be_a_bare_file_name`（覆盖带目录、盘符、`..`、`.` 等写法） |

#### `install_plugin_url*` 不受 network 权限约束

| 项目 | 说明 |
| --- | --- |
| 现象 | `install_from_url_verified` 只做 `is_http_url`（前缀检查），**既没有宿主白名单，也没有 `require_permission`**；`install_plugin_url` 是它的无哈希包装 |
| 为何是矛盾 | `fetch_registry_text` 上写着一整段论证："插件与宿主同处一个 JS 上下文、能触达 IPC 桥，若这里放开宿主限制，一个没有声明 `network-external` 的插件就能借它发出任意外部请求。" 而**同一威胁模型下的另一个入口没有施加任何约束** |
| 处理（市场路径） | `install_from_url_verified` 现在施加 `ensure_registry_url_allowed`（宿主白名单 + https）。市场地址由 `registrySources` 生成，只可能是两个白名单宿主，因此不破坏功能；用户配置的加速源由后端在 `fetch_via_sources` 内部拼接，不在校验范围内 |
| 处理（用户粘贴路径） | `install_plugin_url` 保留任意宿主（用户可能从自建服务器或内网安装），但收紧为 `ensure_https_or_loopback`：**明文 http 一律拒绝** |
| **未解决，如实记录** | 这条命令**仍然无法识别调用者** —— 插件可以直接 invoke 它去下载任意地址的内容。命令签名里没有插件 id，而在同 JS 上下文的模型下后端无从知道调用者是谁。保留它是因为「从 URL 安装」是真实功能；这个缺口属于模型局限，不是靠加检查能消除的 |
| 顺带修正 | `Plugins.tsx` 的弹窗文案原写"应用会下载并校验后再安装"——这条路径**不校验哈希**，已改为如实说明"不会校验来源" |
| 测试 | `registry_url_requires_allowlisted_host`、`user_pasted_url_allows_any_https_host_but_not_plain_http` |

#### 解压体积上限用的是压缩包自己声明的值

| 项目 | 说明 |
| --- | --- |
| 现象 | 总量上限累加 `entry.size()`（中央目录**声明**值），而实际字节只按**单条目**比较。条目数上限 5000 ⇒ 可写到约 5000 × 64 MiB，且没有压缩比检查 |
| 处理 | 保留声明值作为廉价预检，**新增按实际写入字节累计的 `written_total`**，超限立即中止。解压炸弹不再能靠撒谎的中央目录绕过 |
| 测试 | 未新增。构造"声明小、实际大"的 zip 需要手工篡改中央目录，成本高于收益；实际累计是一段直读即可确认的线性逻辑 |

### 7.38 应用命令从来没有过门禁：一个"默认放行"的实现细节

**类别：** 安全边界（新增）＋ 门禁（新增）

#### 问题

做插件沙箱的前置调研时发现：**Tauri 对应用自己注册的命令默认不检查权限**。

官方文档把这件事写成一句话——"By default, all commands that you registered in your app
(using `invoke_handler`) are allowed to be used by all the windows and webviews of the app"
—— 而实现上它是判定条件里的一个分支（`tauri-2.11.5/src/webview/mod.rs:1823`）：

```rust
if (plugin_command.is_some() || has_app_acl_manifest || !is_local)
  && request.cmd != FETCH_CHANNEL_DATA_COMMAND
  && invoke.acl.is_none()
{ /* 拒绝 */ }
```

本应用的界面来自 `tauri://localhost`（`is_local` 为真），命令又不带 `plugin:` 前缀。
**三个条件都不成立时这条 if 整个被跳过** —— 于是 120 条后端命令对任何一个 webview 都是
敞开的，与 capability 怎么写、权限表怎么声明**完全无关**。

这个缺口有一个能直接看见的实例：**托盘菜单窗口 `tray-menu` 一条 capability 都没有，
但它一直在正常调用 `tray_menu_state` 与 `tray_menu_action`。** 按文档，
"没有匹配任何 capability 的 webview 根本没有 IPC 访问权"—— 而它有的是，
因为它走的根本不是需要检查的那条路。

#### 做法

`src-tauri/build.rs` 声明应用级 ACL 清单（`AppManifest::commands`）。这一句是
**开关**而不是配置：`tauri-build` 会为每条命令生成 `allow-<命令名>` / `deny-<命令名>`
两个权限，`acl-manifests.json` 里随之出现 `__app-acl__`，而
`has_app_acl_manifest` 正是由"这个键在不在"决定的（推导链在
[应用命令的访问控制](../04-安全/应用命令的访问控制.md)第 2 节逐行列出）。
声明之后语义**反转成默认拒绝**，授权按 window / webview 标签匹配。

顺带补齐：`tray-menu` 有了自己的 capability，只有它真正用到的那两条命令。

#### 一个必须写下来的坑：`windows` 与 `webviews` 不是同义词

capability 的 `windows` 键会把授权发给**该窗口下的所有 webview**，与 `webviews`
怎么写无关。今天只有两个 webview，两者看起来一样；**插件沙箱一旦落地就不再一样** ——
插件 webview 会在主窗口里，那一刻任何一处 `"windows": ["main"]` 都会把包括 120 条
应用命令在内的整份宿主授权送给插件，而构建、类型检查、其余门禁**全都不会变红**。

因此本仓库的约定是 capability 一律用 `webviews`，并由门禁断言：出现 `windows` 即失败。

#### 这一轮买到的是什么，以及**不是**什么

买到的是**宿主自身命令的默认拒绝**。它不是"插件已经安全了"：

插件仍与宿主跑在同一个 realm、同一个 `main` webview 里，因此它今天仍然能调用全部
120 条命令。这一层改变的是**将来**——插件被挪进自己的 webview 后，只要那个标签没有
授权，它才真的调不动。这是沙箱的前置条件，不是一个可以当成结论的成果。

把它单独交付、单独验证是可以的，但文档里必须写清这层区别，否则它会被读成一个
"安全修复"。

#### 门禁

`scripts/check-acl.ts`（`pnpm check:acl`，28 项断言）盯住四件事：

| 断言 | 防的是什么 |
| --- | --- |
| `generate_handler!` ↔ `AppManifest::commands` ↔ `capabilities/` 三处逐条一致 | 少一条 = 那条命令**对所有人不可用**，而这只在运行期暴露 |
| 任何 capability 都不许出现 `windows` 键 | 上面那个坑 |
| 每个窗口都被某个 capability 覆盖、且不指向不存在的标签 | 清单声明后，没有 capability 的窗口连 IPC 都用不了 |
| `tray-menu` 的授权**恰好等于**它在源码里真正 `invoke` 的命令 | 少给 = 开关点了没反应；多给 = 没有依据的能力 |

解析器刻意做成"块内出现任何不认识的行走法就报错"：读不全时静默给出一个偏小的集合，
正好会让"少了一条"这条断言**通过**——这是本项目在手写解析器上已经吃过两次的亏
（见 `check-plugin-boundary.ts` 文件头）。

#### 验证状态

**应用本身运行正常**，但**由 AI 代理的沙箱环境启动不了它** —— 那个环境创建不了窗口
（对照实验：`notepad.exe` 在那里启动后 `MainWindowHandle` 也是 0），Tauri 会在建窗口
处停住。此前把它记成"应用有一个先于任何代码的启动阻塞"是归因错误，更正见
[内存基线与架构升级方案](内存基线与架构升级方案.md) §10.5。

因此运行期验证由人来完成。构建期与静态层面已验证：capability 里的权限标识符由
`tauri-build` 在构建时校验（未知权限会让构建失败），`acl-manifests.json` 里确有
`__app-acl__`（240 条 = 120 `allow` + 120 `deny`），`capabilities.json` 里没有
`windows` 键，24 个 `check:*` 门禁、`tsc` 与 398 个 Rust 测试全绿。

**需要人工走一遍**：解锁、托盘右键菜单、设置页各分页、插件安装与存储。若某处报
`Command <命令名> not allowed by ACL`，说明那条命令没有被授权；若报 `core:...` 被拒，
说明需要补一条 `core:` 权限。清单与排查表在
[应用命令的访问控制](../04-安全/应用命令的访问控制.md)第 9 节。
