### 7.2 本轮（启动体验、外观、恢复与性能）

#### 启动体验

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 首次启动先白屏一段时间才出现加载动画 | WebView 在 `<head>` 解析时就开始绘制，而 React 挂载要等 JS bundle 求值完成；Tauri 窗口底色为白色，这段空窗就表现为白屏 | **初版方案已推翻**。当时的做法是在 `index.html` 内联一份纯 HTML 启动骨架，再用 `MutationObserver` 在 React 提交首帧后移除。问题见 7.3 节：同一次启动出现两套加载界面。现行做法是只保留内联的**背景色与主题预置**（不做任何可见内容），加载动画由 React 的 `BootScreen` 独家负责，因此不存在两块屏幕的交接 |
| 窗口首次出现在屏幕中央偏左 | 仅依赖系统默认放置 | `tauri.conf.json` 增加 `"center": true`，并在 `lib.rs` 的 `setup` 中显式 `window.center()` 兜底 |

#### 插件图标为空

| 项目 | 说明 |
| --- | --- |
| 现象 | 带图标的插件能正常加载，但侧边栏与仪表盘中的图标位置是空的；插件管理页里图标却正常 |
| 根因 | 侧边栏与仪表盘用 `(Icons as any)[module.icon]` 取图标，而 `Icons` 是构建期生成的 `generated/iconMap.ts`，**只包含 `src/modules/*/module.toml` 里出现过的图标**。插件模块在运行期注册，其图标名（`StickyNote`）或图标文件路径（`icon.svg`）都不在该映射中，于是查得 `undefined`，侧边栏渲染成空白占位。插件管理页走的是另一条路径（`PluginIcon`），它支持 `.svg` 与内联 SVG，所以那里是正常的——这个不一致正是问题的线索 |
| 处理 | 新增 `src/components/ModuleIcon.tsx` 作为**唯一**图标解析入口，按「内联 SVG → 构建期映射 → lucide 按需加载 → 通用图标兜底」的顺序解析；`pluginRuntime` 在加载插件时就把 `icon.svg` 读出并随模块描述符传递（渲染是同步路径，不能在渲染时异步取）；侧边栏、子项与仪表盘全部改用它 |

#### 忘记访问密钥

| 项目 | 说明 |
| --- | --- |
| 问题 | 访问密钥只存 Argon2id 哈希，遗忘后没有任何自救通道 |
| 处理 | 引入恢复码：32 字符 Crockford Base32（排除 `I`/`L`/`O`/`U`，共 160 bit 熵），按 `XXXX-XXXX-…` 分组展示；与访问密钥同样只存 Argon2id 哈希 |
| 流程 | 创建密钥时生成并**只返回一次**；解锁界面在有恢复码时出现「忘记访问密钥」入口；重置命令不需要会话（此时用户进不来），安全性由恢复码本身承担，并叠加限流、一次性使用、成功后清空全部会话 |
| 迁移 | 已设置密钥但无恢复码的老用户，解锁界面会明确提示无法自救，可在「设置 → 安全 → 密钥恢复」补生成 |

#### 性能与故障隔离

| 问题 | 处理 |
| --- | --- |
| 插件加载阻塞启动，插件变多后启动明显变慢 | 新增 `deferPluginLoading`（默认开启）：启动阶段只读取插件清单，bundle 执行推迟到应用可用之后在后台进行；加载完成的插件通过目录通知实时出现在侧边栏 |
| 一个坏插件会拖累其余插件的加载 | 新增 `pluginLoadTimeoutMs`（默认 5000ms，可配置 500–60000）：超时的插件被标记为失败并跳过。**注意**：JS 单线程无法中断插件顶层的同步死循环，超时只隔离影响范围，不能救回已卡住的主线程 |
| 插件未加载完时打开其模块会误报「模块不存在」 | 新增 `isPluginCatalogLoading()` 与 `PluginModulePending` 占位，区分「还没加载完」与「真的不存在」 |
| 根级渲染错误会导致整窗白屏 | 新增 `AppErrorBoundary`（最外层）与 `globalErrorHandlers`（事件处理器 / 定时器 / 未处理 Promise 拒绝） |

### 7.3 再次修正：首帧骨架、滚动容器、插件引擎门槛

**首帧做过一次错误的尝试，已回滚并换成正确的做法。**

| 项目 | 说明 |
| --- | --- |
| 上一轮的做法 | 在 `index.html` 内联一份纯 HTML 启动骨架（标记 + 文字 + 进度条），并在 `main.tsx` 用 `MutationObserver` 在 React 提交首帧后移除它 |
| 为什么是错的 | 同一次启动会出现**两套加载界面**：先静态骨架，再 React 的 `BootScreen`。标题栏「刷新」触发页面重载时最明显——静态骨架闪一下、接动态启动界面、最后才回到应用。比原来的白屏更糟：屏幕只有一块，加载指示器只应该有一个 |
| 现在的做法 | `index.html` **只预置底色**（把 WebView 默认白底刷成正确主题色），不渲染任何界面元素。启动界面唯一由运行期的 `BootScreen` 提供。`main.tsx` 中配套的移除逻辑一并删除 |

保留底色预置是因为它解决的是真问题：WebView 在解析 `<head>` 时就开始绘制，而 React 挂载要等 JS bundle 求值完成，中间那段空窗确实是白的。刷底色不产生任何可见内容，因此不会与 `BootScreen` 冲突。

**滚动容器。**

| 项目 | 说明 |
| --- | --- |
| 现象 | 仪表盘（以及任何内容超出窗口高度的模块页）无法滚动 |
| 根因 | `Home` 的内容区写的是 `min-h-screen pt-10`，即让内容把页面撑高、指望文档本身滚动；而 `index.html` 对 `html/body` 设了 `overflow: hidden`（窗口应用不该有文档级滚动条），于是没有任何元素滚动 |
| 修法 | 内容区改为视口内固定区域：`fixed inset-x-0 bottom-0 top-10 overflow-y-auto custom-scrollbar`。高度被钉死为「视口高 − 标题栏」，`overflow-y-auto` 必定生效 |

**插件引擎范围不再是安装门槛。**

| 项目 | 说明 |
| --- | --- |
| 现象 | 升级应用版本后，旧插件无法安装/重装，提示"插件要求 Modulith ^0.2.0，当前版本为 0.3.0"，看起来像升级把插件废掉了 |
| 根因 | `^0.2.0` 按 semver caret 规则等价于 `>=0.2.0 <0.3.0`（与 npm 一致），宿主升一个小版本就不再匹配；而 `validate_manifest` 把不匹配当作**硬错误**拒绝安装 |
| 需要澄清的一点 | 已安装的插件**没有失效**：`list()` 与加载路径都不做引擎校验，升级后照常加载。真正被阻断的是重装与安装新版本 |
| 修法 | 区分「语法错误」与「兼容性猜测」：范围语法不可解析仍拒绝安装；语法正确但不匹配只产生一条琥珀色提示（`EngineAdvisory`），安装与加载照常 |
| 提示的时效 | 每次 `list()` 按当前宿主版本重新计算，不落盘。因此升级后提示自动更新，也不需要改 `registry.json` 结构 |
| 示例与检查同步调整 | `samples/hello-plugin/manifest.json` 由 `^0.3.0` 改为 `>=0.3.0`（并重新打包 `.lcp`）；`ver check` 的过窄范围提示改为明确说明「不阻止安装，但会产生提示」。（该示例后来被 `samples/notes` 取代，见 7.17） |

「关于」页的两个外链卡片补齐了品牌图标与反馈动画：lucide 1.x 已移除全部品牌图标（`Github` 导出不存在），因此 GitHub 使用官方标准字形路径（`src/components/icons/BrandIcon.tsx`）；哔哩哔哩的官方标识是带描边的电视机形象，手工还原容易失真，因此保留电视机几何形状但**明确标注为通用图标而非品牌标识**，按钮上始终显示平台名称文字。点击后系统浏览器启动需要几百毫秒，按钮在此期间显示「正在打开浏览器…」并播放掠过高光，避免用户以为点击没生效。

### 7.7 标签页、全局搜索与通知系统

本轮针对的是一个此前没有被解决的目标：**防止注意力中断**。在多个功能之间切换的真正成本不是「点一下侧边栏」，而是切走再切回时必须重建现场 —— 滚动位置、未提交的表单、正在编辑的草稿全部丢失，而重建需要主动回忆「我刚才做到哪了」。把功能集中到一个外壳里只是必要条件，状态保持与注意力路由才是充分条件。

#### 模块标签页与保活

| 项目 | 说明 |
| --- | --- |
| 状态归属 | `tabStore` 是「当前显示哪个模块」的唯一来源；`SidebarContext` 不再自己持有 `activeModule`，而是读它 |
| 为什么改归属 | 同一个模块可能被侧边栏、标签栏、命令面板三条途径激活。各自维护一份必然漂移，表现为「点了侧边栏但标签高亮没变」 |
| 惰性挂载 | 标签只在其**首次被激活**时挂载，之后不再卸载。重启恢复十个标签不会一次挂载十个模块 |
| 隐藏方式 | `absolute inset-0 + visibility:hidden`，**不是** `display:none` —— 后者让元素失去盒子，多数浏览器随之丢掉 `scrollTop`，「滚动位置保留」这个目标就落空了 |
| 关闭语义 | 允许关到零标签并渲染空态，不自动回落。强行回落会让「关掉最后一个标签」看起来毫无反应 |
| 上限 | 12 个（前后端各有一份常量，必须一致）。达到上限时**拒绝并提示**，而不是淘汰已打开的标签 |
| 生命周期 | `openTabs` 与 `activeTab` 随设置持久化（`settings.json`），重启后恢复 |

`SidebarContext` 的历史栈与标签顺序是两回事，刻意分开：标签顺序是用户拖出来的排列，历史顺序是他实际去过的地方。混在一起会让「后退」跳到标签栏上的相邻位置，那不是用户期望的语义。

#### 后台存活管理

保活带来一个必须一起解决的问题：切走的标签不卸载，它的定时器、轮询与订阅会照常运行。宿主对此**提供感知，不提供强制**。

`useModuleActive()` 返回「该标签是否激活**且**窗口是否可见」。宿主无法代为暂停模块的后台工作 —— JS 里拿不到模块创建的 `setTimeout` / `setInterval` 句柄，重写全局定时器会影响包括宿主与 React 在内的所有代码。因此这是一个约定：模块自己在 `useModuleActive()` 为 false 时停掉后台工作。

这条约定目前**只对愿意遵守的模块生效**，没有强制机制。对插件同样如此，所以一个写得不负责任的插件可以在后台持续消耗资源。这一点在插件系统架构第 6.2 节标注为「资源限额：无内存或 CPU 限制」。

#### 全局搜索与命令面板

`commandRegistry` 提供命令注册表，`searchCommands` 负责匹配。模块类条目**不注册进表**，而是在搜索时从目录派生 —— 目录是动态的，镜像成命令列表就需要一套同步逻辑，而同步逻辑正是本项目反复踩坑的地方（见 `useModuleList` 的注释）。派生是纯函数，永远与目录一致。

打分规则与理由：完全相同 1000 分、前缀 800、包含 500、子序列 200 起。子序列匹配是模糊搜索的核心（输入 `dsh` 命中 `dashboard`），但它必须排在精确匹配之后，否则输入完整模块名时会被一堆松散匹配挤下去。最近使用过的命令额外加权，因为重复打开同一个模块时不该重新输完整名字。

#### 通知系统

后端新增 `notifications` 模块（7 个命令，`notifications.json`，上限 200 条）。写入、读取与裁剪策略见该模块源码注释。

三个值得记录的决定：

| 决定 | 理由 |
| --- | --- |
| 命令全部返回「当前完整列表」而不是被改动的那一条 | 只返回一条会让前端必须自己维护「新条目插到哪、合并键命中时改哪条、裁剪时删哪些」三处逻辑，与后端保持一致才能工作，一旦漂移就是界面与磁盘不一致。上限 200 条，多传几十 KB 换「前端整个替换缓存」是划算的 |
| `dedupeKey` 同键未读合并为一条并计数 | 模块很容易在重试循环里连续产生同一条通知（例如「网络不可用」），没有它通知中心会被同一条信息刷满，用户反而看不到真正重要的那条 |
| 错误级提示不自动消失 | 出错时用户需要读完再决定怎么办，3 秒后自己跑掉会让人怀疑「刚才是不是弹了什么」 |

`toast.ts`（不持久化的一次性反馈）与 `notifications.ts`（持久化的事件记录）刻意分成两个系统：把「已复制」写进磁盘并在通知中心留一条记录是明显的噪音；而把「插件加载失败」做成 3 秒就消失的提示则会让用户错过它。

**仍未实现：系统级通知。** 那需要引入 `tauri-plugin-notification` 依赖，当前版本不新增依赖，因此应用关闭时无法提醒。`notification` 权限的说明也已从「系统通知」改为「应用内通知」，避免名实不符。

#### 跨模块事件总线

`eventBus` 让模块之间可以协作（任务模块的待办出现在仪表盘上）。同步投递、按来源批量注销、主题名白名单字符集，理由都写在源码注释里。需要 `plugin-communicate` 权限。

它带来的是「模块之间可以协作」，**不是**「模块之间互相隔离」—— 总线上没有权限隔离，声明了权限的插件可以订阅任意主题。

#### 保活带来的行为变化

保活不只是「状态不丢」，它还改变了模块的生命周期语义，模块作者需要知道：

| 变化 | 说明 |
| --- | --- |
| 入场的错峰动画只播一次 | 以前每次切到模块都会重挂载，`framer-motion` 的 stagger 动画会重播；现在只在首次挂载时播一次。这消除了切换时的动画闪烁，但依赖「每次进入都播动画」来提示状态的模块需要改用别的方式 |
| 挂载副作用只执行一次 | `useEffect(..., [])` 里的初始化（拉数据、建订阅）不再随每次切换重跑。这对性能是好事，但「每次进入都刷新一遍」的旧假设不再成立 |
| 后台期间组件仍在运行 | 定时器、订阅、动画都会继续。需要暂停的后台工作要用 `useModuleActive()` |
| 卸载时机与关闭标签对齐 | 在此之前「离开模块」等于卸载；现在只有关闭标签或刷新才会卸载，因此清理逻辑（`useEffect` 的 return）会推迟到那时才执行 |

对插件而言，第二条与第三条影响最大：插件此前可以假设「用户每次打开模块都是一次全新的执行」，现在必须把初始化与刷新分开考虑。

#### 本轮仍未解决的问题

诚实记录，避免下一个人以为这些已经做过了：

| 问题 | 现状 |
| --- | --- |
| 模块保活没有内存上限之外的淘汰策略 | 上限 12 个标签，超过则拒绝；不会根据实际内存占用调整 |
| 后台工作依赖模块自律 | 无强制暂停机制，见上文 |
| 搜索不搜模块**内容** | 只搜模块名、子模块名与宿主/插件命令。功能多起来之后「我知道有这个功能但不知道在哪个模块」这类问题仍未完全解决 |
| 搜索无结果时面板直接消失 | 没有「无匹配项」的提示。当前的处理是「结果为空则不显示面板」，用户看到的是一片安静。补一个空态提示是明确可做的小改进 |
| 没有「工作场景」概念 | 收藏与置顶是模块级的，不是任务级的。做一件事需要同时开三四个模块时，无法把这一组存下来一键恢复（持久化的标签部分覆盖了这个需求，但只有一组） |
| 通知没有分类与优先级 | 只有 info/success/warning/error 四个级别与来源模块，不能按模块静音或分组折叠 |
| 无 OS 级通知 | 见上文 |

### 7.9 深色模式亚层配色与标签切换的动画残留

#### 深色下标题栏/标签栏/搜索框渲染成灰色

| 项目 | 说明 |
| --- | --- |
| 现象 | 深色模式下，二级标题栏（标签栏）整条渲染成灰白色，全局搜索框也是浅灰而不是深色 |
| 根因 | **`bg-white/90` 与 `bg-white` 是两个不同的类名 token**，`[class~='bg-white']` 不会命中前者，因此 `dark-theme.css` 必须**逐个列出**用到的不透明度档位。当时列了 `/90`、`/80`、`/70`、`/60`、`/50`，而标签栏用的是 **`bg-white/85`**、搜索框是 **`bg-gray-50/80`** —— 两档都不在表里，于是原样保留浅色。**漏一档不报错，只表现为深色界面里出现一块灰白** |
| 排查方式 | 把「项目里用到的 `bg-*` 类」与「dark-theme.css 已映射的类」做差集，共发现 35 个未映射项；其中多数是有意为之（`bg-indigo-500` 等强调色由主题变量驱动、`bg-red-500` 等语义色两种模式通用），真正属于「大面积表面漏映射」的就是上面两档 |
| 处理 | ① 把 `/85`、`/95`、`gray-50/80`、`gray-50/60` 补进映射表；② **标题栏与标签栏统一为同一不透明色 `#151823`** —— 二者是相邻的窗口亚层，背后就是应用底色，半透明只会让两块亚层深浅不一、出现色带分界，不透明之后它们在视觉上连成一整块；③ 搜索框按「下沉输入区」处理，用比面板更深一档的 `#0e111a` 表达「凹进去的输入位」，而不是靠灰 |
| 顺带修掉 | 搜索框原来的 `focus:bg-white` 是**变体**类，属性选择器同样命中不到，聚焦时会闪出一块白底。已移除该变体，聚焦只改描边与光环 —— 聚焦时底色跳变本身也是一种突兀 |
| 验证 | 用脚本计算了实际对比度（WCAG）：标题 16.08:1、激活标签 15.09:1、未激活标签 6.97:1、图标 6.97:1、搜索文字 17.13:1，全部高于 4.5:1（图标 3:1）；亚层分离度 1.066:1，可辨识而不过分 |

#### 切换模块时几个卡片短暂停留

| 项目 | 说明 |
| --- | --- |
| 现象 | 从仪表盘切到别的模块时，有三张卡片会在新页面上停留一小会儿才消失；理想情况下切换应当是瞬时的 |
| 根因 | **不是「没隐藏」，而是「隐藏之后动画还在跑」**。标签保活让切走的模块留在 DOM 中（刻意的），仪表盘的统计卡片带入场延迟 `delay: 0.15 + i*0.06`，即 index 2/3/4 分别延迟 0.27/0.33/0.39 秒 —— 用户切走时它们刚播到前几帧，**用户看到的「三张」正是延迟最长的那三张**。而 `visibility: hidden` 只让元素不参与最终绘制，**并不暂停动画**，合成器仍会把中间帧画出来 |
| 为什么不能简单换隐藏方式 | `display:none` 会让元素失去盒子、丢掉 `scrollTop`，而「切回来还在原处」正是保活的核心目标。`content-visibility: hidden` 更彻底，但 MDN 对其语义的说明是 "similar to giving the contents `display: none`"，与滚动位置保留存在冲突风险（CSSWG 也讨论过 skipped 子树的滚动位置恢复）。在不能实测的前提下，**不拿保活的核心不变量去换一个性能属性** |
| 处理 | 三层收口，都只作用于非激活标签：① CSS 暂停动画与过渡（`animation-play-state: paused`，停在当前帧而不是跳到终态，避免切回来时看到跳变）；② 宿主传入 `initial={false}`，让**包裹层**跳过初始态直接渲染终态；③ 用 `!important` 把非激活子树钉在 `opacity: 1` / `transform: none` 的终态 —— framer-motion 是写**行内样式**的（`element.style.opacity = …`），行内样式压不过 `!important` 的样式表规则，这是确定性的最后一道 |
| 一个必须记住的实测结论 | **`MotionConfig reducedMotion="always"` 不能解决这个问题。**我读了安装的 framer-motion 12 源码：`motion-dom` 的 `visual-element-target.mjs` 里是 `shouldReduceMotion && positionalKeys.has(key) ? { type: false } : valueTransition`，而 `positionalKeys` 只含 width/height/top/left/right/bottom 与 transform 系列 —— **`opacity` 不在其中**。卡片残留的可见表现恰恰是 opacity 淡入，因此单靠 reducedMotion 会留下这个 bug。这一点与「官方文档说 reducedMotion 会关闭动画」的直觉相反 |
| 验证 | CSS 结构与选择器一致性由脚本核对（花括号配平、规则存在性、选择器与 `data-active` 标记一致、且确认未退回 `content-visibility`/`display:none`），全部通过 |

**这两条都提示了同一个模式**：`dark-theme.css` 的「按类名映射」（5.2 节）和标签保活（7.7 节）都是**有明确代价的设计取舍**，而代价集中体现在「漏了一项不会报错，只会表现为某处看起来不对」。前者漏一档颜色就退回浅色，后者漏停一类动画就出现残留。这类问题无法靠类型系统发现，只能靠清单式核对与小心的收口规则 —— 这也是本轮把「映射漏项差集」写成可复跑脚本的原因。

### 7.10 亚层分隔线与折叠态「展开」入口的位置

#### 标签栏底边的浅色细线（深色下像白边）

| 项目 | 说明 |
| --- | --- |
| 现象 | 深色模式下标签栏底部有一条细白/浅色边线，与整体深色不协调 |
| 根因 | 标签栏用的是 `border-gray-200/70`，而 `/70` **不在** `dark-theme.css` 的映射表里（只列了 `/50`、`/60`），于是原样保留浅色。与 7.9 节的底色漏项是同一类错误，只是这次出在边框上 |
| 处理 | ① 把 `/70` 补进映射表；② 更关键的是**改掉勾边思路本身**：窗口亚层的分界应当"压下去"而不是"提起来"，因此标题栏与标签栏的底边改用比面板更暗的 `#0a0c12`，表达的是一道浅浅的接缝，而不是一条亮线 |

**这条与 7.9 节合起来是一个必须记住的模式**：`dark-theme.css` 按类名精确映射，**底色、边框、透明度档位各自都要单独列**，漏掉任何一维都不报错，只表现为「深色界面里某处颜色不对」。这轮两处缺陷（底色的 `/85`、边框的 `/70`）属于同一个根因的两个面。

#### 折叠侧边栏后「展开」按钮挡住标签栏

| 项目 | 说明 |
| --- | --- |
| 现象 | 侧边栏收起后，右上角（实际是窗口左上偏下）留着一个「展开」按钮，它挡住了二级标题栏 |
| 根因 | 按钮是 `fixed left-4 top-14 z-50`。`top-14` = 56px，而标签栏占据 **40~76px**，按钮（约 36px 高）横跨 56~92px；且它 `z-50` 高于标签栏的 `z-40`，于是直接盖住了标签栏左端与第一个标签 |
| 需求约束 | 用户明确指出**不接受**在折叠态加一个常驻的小型侧边栏 —— 那会永久吃掉内容区宽度，损害模块的全屏与沉浸式体验。这个约束是对的：常驻窄条换来的是"多一个入口"，付出的却是所有模块永久少一块画布 |

| 入口唯一性 | 展开入口仅在 `!isOpen` 时渲染；折叠入口在侧边栏头部（`PanelLeftClose`），而 `Sidebar` 在折叠态直接返回 `null`。因此任一状态下两个入口只有一个存在，不会重复或互相遮挡 |
| 验证 | 用脚本核对了：旧浮动按钮已消失、按钮位于标签栏内部（受 `items-stretch` + `h-9` 约束，不可能溢出 40~76px）、`shrink-0` 防止被标签挤压、折叠态 `ml-0` 未被挤占、两入口互斥 |

### 7.22 日志门面挂了，但从来没有后端：几十处 `log::*` 一次也没有输出过

| 项目 | 说明 |
| --- | --- |
| 现象 | 出问题（例如「检查更新失败」）时，我们手上没有任何证据。用户能提供的只有「不行」，而 release 版的表现与原因之间没有任何可查的中间层 |
| 根因 | `Cargo.toml` 一直有 `log = "0.4"`，代码里也一直有几十处 `log::info!` / `log::warn!` / `log::error!`，但**从来没有安装过任何 logger 后端**。`log` 只是一个门面：没有后端时它把每条记录直接丢掉，而且不会报错、不会有编译警告 —— 因为那些调用本身完全合法 |

| 教训 | **一个依赖了门面却没装后端的日志系统，比没有日志更糟**：它让「这里已经记了日志」成为一个写在代码里的事实，从而阻止任何人再去检查它是否真的在输出。引入 `log` / `tracing` 这类门面时，必须同时确认后端存在，并有一条能证明它确实输出了的路径 |

### 7.24 「关闭界面动画」只在没在看的标签上生效

| 项目 | 说明 |
| --- | --- |
| 现象 | 用户报告：已经打开「关闭界面动画」，界面仍然卡 |
| 根因一 | `ThemeProvider` 在应用根部按设置给出 `reducedMotion="always"`，而 `Home` 给每个标签面板又套了一层 `reducedMotion={isActive ? 'never' : 'always'}`。framer-motion 的合并规则是**子层覆盖父层**（`config = { ...parentConfig, ...config }`），于是激活标签永远拿到 `"never"` —— 而那恰好是用户唯一在看的标签。这个开关的真实效果是「关掉没在看的标签的动画」 |
| 根因二 | framer-motion 12 的短路只对**位置类**属性生效（`positionalKeys`：transform 系列与 width/height/inset），`opacity`、`backdrop-filter`、`box-shadow`、`filter` 不在其中。授权界面的粒子背景正是 18 条 `repeat: Infinity` 的 `y / opacity / scale` 循环：`y` 与 `scale` 停了，`opacity` 没停 —— 18 条 rAF 动画与 18 个合成层永远在跑，而授权界面默认每次启动都会出现 |
| 根因三 | CSS 开关本身不完整：选择器 `*` 匹配不到根元素自身（漏掉它的 `transition: background-color`），也没有归零 `animation-delay`（一个延迟 2 秒的动画仍会在 2 秒后闪一帧） |
| 处理 | 标签层取并集（`isActive && !reduceMotion`）；粒子的挂载由代码显式判断；CSS 规则补上根元素、delay 与 play-state；两个开关的合并收敛到 `utils/motionPreference.ts` 一处，并新增「性能模式」把非动画类的每帧开销（三个常驻全屏 `backdrop-filter`、装饰性大半径模糊、几十处 `will-change`）一并去掉 |
| 附带发现 | `Home.tsx` 的注释声称非激活标签用 `content-visibility: hidden` 隐藏，**代码从来没用过**（实际是 `visibility: hidden`）。已改正注释，并写明不用的理由：它会让子树内部的滚动容器失去布局，威胁「切回原处」这个保活的核心目标 |
| 教训 | **一个「看起来接上了」的开关比没有开关更糟**：它让「我已经关了动画」成为一个用户确信的事实，从而不会再去怀疑这一层；而嵌套配置的覆盖方向（子层取胜）恰恰是最不容易在代码里看出来的东西。这类缺陷只有把修复点本身钉成断言才防得住 —— 见 `scripts/check-performance.ts` |

### 7.25 两处没有上限的缓存

| 项目 | 说明 |
| --- | --- |
| 现象 | 模块多开、在市场里来回浏览之后，常驻内存只涨不落 |
| 根因 | 模块组件缓存只有全局 `clear()`，从不逐条释放（不变量应当是「条目数 = 当前挂载数」，实际是「曾经打开过的模块数」）；市场 README 与图标缓存各存几十 KB 的字符串与 base64 文本，**一条上限都没有**，每浏览一个新版本就多一条 |
| 处理 | 组件缓存的释放挂在 `tabStore` 的**唯一写入点** `setState` 上（六条关闭/对账路径都经过它 —— 逐条去调必然漏一个）；两个市场缓存加 32 条上限，按插入顺序先进先出 |
| 没有跟着改的 | 后端 `AttemptTracker.attempts` 与 `RateLimiter.requests` 用的是阈值扫描而不是硬上限，这是**刻意**的：它们记录登录失败标识，一个可被任意淘汰的表等于让攻击者用泛洪把自己的封锁记录挤出去 |
| 说清楚的部分 | 已加载的 JS chunk 不会释放（浏览器模块注册表在文档生命周期内保留求值结果，只有整页重载会重置）；插件模块是同域内联脚本，卸载后要等没有引用才会被回收。这两条不是泄漏，但会让人觉得「内存没降下来」 |
| 教训 | 「有没有上限」要逐个对象问一遍，而不是问「有没有回收机制」—— 后者很容易答"有"，因为回收机制确实存在，只是漏了几个对象 |

### 7.27 窗口内分屏、开机自启动与全屏

三个功能在同一轮加入。它们的共同点是**都不改动已有的核心抽象**，而是把已有能力往前推一步。

#### 窗口内分屏（两个标签组）

| 项目 | 说明 |
| --- | --- |
| 形态 | **两个标签组**：左（`primary`）与右（`split`），每组有自己的标签列表、自己的激活标签、**自己的标签栏**。分屏状态由 `splitTabs` 是否为空表达，没有额外的布尔量 —— 两者因此不会出现「标记为分屏但右边是空的」 |
| 为什么是「组」而不是「右边多显示一个」 | 第一版把分屏做成「共享一个标签列表 + 右边多渲染一个标签」，结果右边既不能切标签也不能关标签，用户的原话是「我还不能更改」。一个钉死的预览不算分屏 |
| 入口 | 标签右键菜单「在右侧分屏打开 / 移回左侧」、`Ctrl+\`（**把焦点组的当前标签搬走**；再按一次收回）、**把标签拖到内容区的另一半**（拖动期间左右两半都是落点区） |
| 拖拽 | **用指针事件自己实现，不用 HTML5 拖放** —— 后者在本应用里整体不可用（见本节第 3 条教训）。`tabDrag.ts` 跟踪 `pointermove`、按落点元素自己判定目标，并画一个跟随指针的幽灵标签（没有浏览器自带的拖动影像，不给反馈就看不出在拖东西） |
| 焦点组 | `focusedGroup` 记录"用户正在操作哪一半"。**点进哪一半就聚焦哪一半**（内容区按坐标判定，标签栏点击即聚焦）；它决定：侧边栏高亮、`Ctrl+W` 关哪个标签、`Ctrl+Tab` / `Ctrl+1..9` 在哪个组内轮转、以及**从侧边栏新开的模块落进哪一组**。没有它这些会固定作用在第一组，而用户可能在右半工作 —— 表现为「按 Ctrl+W 关掉了左边那个」「新开的模块跑到另一半去了」。没有焦点那一组的激活指示条调浅一档，作为可见线索。运行时状态，不持久化 |
| 分屏的方向 | 在标签 X 上分屏 = 把 X **移动**到右组（不是复制）：复制会带来两份组件实例、两套定时器与两套存储写入，而「同时看两个不同的东西」才是分屏的用途 |
| 第一组不能空 | `openInSplit` 拒绝把第一组搬空，`setState` 里还有反向兜底（第一组空了而第二组有内容时，把第二组的激活标签补回来）。入口与出口各挡一次 —— 左边空白、右边有内容不像分屏，像界面坏了 |
| 可调比例 | 分隔条用**指针事件 + 指针捕获**（HTML5 拖放只有离散的 dragover，做出来是跳的；捕获则保证拖出窗口也不断），比例夹在 `[0.2, 0.8]`，双击回 50%，并持久化 |
| 保活 | 所有面板仍在**同一个父容器**里，横向位置由「属于哪一组」算出。这一点是刻意的：跨组移动只改 `left` / `width`，React 复用同一个元素（key 与父节点都没动），滚动位置与未提交的表单因此不丢。若按组分两个容器渲染，跨组移动就会重新挂载 —— 而那正是最不该丢的东西 |
| 持久化 | `settings.json` 的 `splitTabs` / `splitActive` / `splitRatio`。上限按**两组之和**校验：每个标签都是一个常驻的模块实例，分屏不该成为绕过上限的口子 |

**这一节记录三次做错，比记一次成功更有用。**

1. **第一版**：`openInSplit` 复用了 `openTab()`，而后者会 `activate()` 目标 —— 目标被设为左格后 `splitTab === activeTab`，立刻被 `setState` 的不变量清洗成 `null`。**入口全都接上了，但每一次都被自己的不变量清掉**，表现为「点了没反应」而且不报错。教训与 §7.19 的「快捷键从未接线」同类：把不变量收在一处是对的，但**新加的写入路径必须验证它确实能通过那道不变量**。
2. **第二版**：不变量通过了，但**模型选错了** —— 把它理解成「共享标签列表 + 右边多显示一个」。用户随即指出右边不能切换、不能关闭，那半等于装饰。这一次是**没先确认「分屏」到底指什么就动手**，代价是整块重做。
3. **第三版**：拖动分屏只有落点提示能出现，`drop` 不触发、光标是"禁止"。我先把原因归到 `dragstart` 没声明 `effectAllowed` —— **那个归因是错的**：`宿主API参考.md` 与 §7.16 早就写明，本应用里 **WebView 内的 HTML5 拖放整体不可用**（Tauri 的 `dragDropEnabled` 默认 `true` 会拦截系统拖放）。那次修复改的是一个**永远不会被执行**的路径。正确做法是用**指针事件**自己实现（`services/tabDrag.ts`：跟踪 `pointermove`、自己算落点、自己画幽灵标签）。同一个原因还解释了为什么**标签拖拽排序此前从来没能用过** —— 它用的是同一套 HTML5 API，而没人试过。

**`useModuleActive()` 的语义在这一轮变准确了，插件作者需要注意。** 宿主传给模块的 `isActiveTab` 现在是「是否位于某个可见的组」而不是「是否为唯一被选中的标签」—— 分屏时两组各有一个可见标签，两个都为真。

#### 开机自启动

| 项目 | 说明 |
| --- | --- |
| 实现 | 自己写（`settings/autostart.rs`），不引 `tauri-plugin-autostart`：需要的是「当前用户、单个值、一条命令行」，而 `windows-sys` 已在依赖里（图标提取在用同一份）。与「为什么不用 tauri-plugin-log」是同一个判断 |
| 写入位置 | 只写 `HKCU\...\CurrentVersion\Run`，**不写 HKLM** —— 后者会让安装或首次运行要求提权，而自启动不需要那种权限 |
| 唯一真相 | **注册表**。`settings.json` 里刻意不存这份状态：用户能在任务管理器的「启动」页里直接改它，存一份副本必然与实际不符 |
| 命令行 | `"<exe>" --autostart`。引号防含空格的路径被系统按空格拆开；`--autostart` 标记用于区分「系统拉起」与「用户双击」—— 静默与全屏只该作用于前者 |
| 平台 | 目前仅 Windows。其他平台返回明确的「不支持」而不是假装成功 |
| 启动行为 | 「静默」（最小化）/「全屏」/「最大化」三选一，优先级 **静默 > 全屏 > 最大化**。三者都想决定「窗口一出来是什么样」，同时开两个必须有确定答案，否则用户面对的是「到底哪个生效」的不确定性。**它们只在自启动开启时可用**：关掉自启动后三项显示为关且不可选 —— 它们描述的是"被系统拉起时窗口怎么出现"，没有那次启动就无从谈起，摆着可点只会让人以为设置没生效 |
| **静默启动的语义收窄** | 实现为**最小化**，不是隐藏窗口：本应用没有托盘图标，隐藏之后用户只能靠任务管理器找回它。设置界面里也如实写作「最小化启动」。要做到真正的后台常驻需要引入托盘，属于另一件事 |

#### 全屏（F11）

| 项目 | 说明 |
| --- | --- |
| 入口 | **只有 F11**（与浏览器一致），不做界面按钮。全局右键菜单里另有一项，退出同样靠 F11 |
| 隐藏范围 | 全屏时标题栏与二级标题栏一并隐藏、内容区上沿归零 —— 留着一条 40px 的标题栏等于没全屏。**侧边栏保持显示但上移贴合**（`top-0 h-full`）：它的定位里写死了标题栏高度，不跟着变会在顶部留出空隙、底部溢出 40px。选择贴合而不是自动隐藏，是为了不改变用户原本的展开 / 折叠状态，且全屏时仍可导航（想更沉浸按 Ctrl+B 自己收起） |
| 代价（已知） | 窗口是无边框的（`decorations: false`），标题栏承载最小化 / 关闭按钮。全屏时它们不可见，退出方式是再按一次 F11。这是「只由 F11 进入全屏」的配套代价，已在设置界面与本文中说明 |
| 状态归属 | 全屏状态在**前端**（`Home`），因为它不只是窗口属性：还要同时隐藏两级标题栏。因此快捷键经 `fullscreenBridge` 转发，而不是直接调 Tauri —— 否则会得到「窗口全屏了、标题栏还在」 |
| 失败回滚 | `setFullscreen` 抛错时把界面状态回滚，避免界面显示「已全屏」而窗口其实没有 |

#### 顺带修掉的既有缺陷

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 解锁界面的两个装饰球在最大化窗口后「各据一角」，不再交叉重叠 | 尺寸是固定的（`w-96` = 384px），位置却是百分比（`top-1/4 left-1/4` 与 `bottom-1/4 right-1/4`）。两球重叠的条件是 `384 > 0.25 × 窗口宽`，而 1920 宽时需要 480 —— 窗口一大就分开 | 尺寸与模糊半径改为跟随窗口：`36vmax` / `3.5vmax`，重叠关系因此与窗口大小无关（960×560 上是 345px，3840×2160 上是 1382px，两端都保持部分重叠）。这是**既有**缺陷（非本轮引入），一并修掉 |
| 上面那条修复的第一次尝试反而把球弄没了 | 改用了 Tailwind 任意值 `w-[36vmax]` / `blur-[3.5vmax]`，而这两个类名**没有生效**。`absolute` 元素没有宽高就是 0×0，两个球因此等于被删掉（用户的原话是「你直接把我球删了」）。**根因只到「类名没生效」为止**：最可能是 Tailwind 没为这个单位生成规则，但当时没留下构建产物可查，因此不写成定论 | 改为**内联样式**（`style={{ width: '36vmax', … }}`）。尺寸这类「必须生效」的属性不该依赖类名扫描：类名缺失时没有任何报错，只表现为元素消失。**教训：用构建期扫描的工具类去承载「元素存在与否」，风险与收益不成比例。** |

#### 顺带修掉：「恢复上次打开的模块」只生效了一半

| 项目 | 说明 |
| --- | --- |
| 现象 | 该开关关着，重启后仍然回到关闭前那一刻（标签、当前标签、分屏都在） |
| 根因 | 这个开关**只被 `resolveInitialModule()` 读**（决定"默认打开哪个模块"），而 `tabStore` 无条件把 `openTabs` / `activeTab` / `splitTabs` 写进设置、又在启动时无条件恢复。于是"窗口状态"这条通路完全绕过了它 |
| 处理 | 把这个开关的语义扩成**窗口状态**（标签页 + 当前标签 + 分屏 + 上次停留的模块），并且**同时管"存"与"取"**：关闭时既不写、也不读。默认值由 `false` 改为 `true`（恢复现场是这个应用的主要卖点，替用户关掉它没有道理） |
| 一个必须一起处理的细节 | 只在"取"这一侧加判断是不够的：关闭期间不写盘，设置里留着的是更早的布局；用户重新打开开关后一重启就会回到**那个陈旧布局**，而他记得的是"我刚刚开着这几个标签"。因此开关**从关切到开**的那一刻会立刻写入当前状态（`persistWindowStateNow`） |
| 这是同一类错误的第四次 | 与 §7.19（快捷键从未接线）、§7.26（`filesystem-write` 没有强制点）、以及本节的分屏前两版一样：**检查/开关只覆盖了一部分通路**。判断标准应当是"这个设置影响哪些写入点与读取点"，而不是"在哪一处加个 if 就完事" |

#### 本轮没做（明确留给后续）

| --- | --- |
| 拖出标签 → 独立窗口 | 需要跨窗口状态同步（`tabStore` / `moduleCatalog` / `sessionStorage` 里的会话令牌都是单窗口单例），是把单例架构改成多实例架构，属架构级工作 |
| 托盘图标 | 「静默启动」要真正隐藏窗口就需要它。本轮只做到最小化并如实标注 |
| 分屏超过 2 格 | 同上，且每格会窄到不可用 |

### 7.28 毛玻璃开关、通知提示音、备份机制，以及一批深色模式缺口

五项改动在同一轮完成。它们的共同点是**都在既有结构上补一个出口**，而不是引入新的
架构：毛玻璃补的是一个被性能模式顺带管着的开关，提示音补的是通知缺失的听觉通道，
备份补的是"数据带不走"的缺口，另外两项是缺陷修复。

#### 毛玻璃：从"性能模式的一部分"变成它自己的开关

原状：`backdrop-filter` 的存废只由 `.lc-performance` 决定，也就是只有打开性能模式
才能去掉它 —— 而那要连带付出装饰模糊、合成层与动画三份代价。想只去毛玻璃的用户
没有这个选项。

改动：新增「毛玻璃效果」开关（`glassEffect`，默认开），只控制**浮层**；三个常驻
亚层（标题栏、标签栏、侧边栏）**永久**去掉 `backdrop-filter` 并改为半透明纯色。

**亚层为什么不做成选项。** 它们背后永远是应用的纯色底：内容区从 `top: 76px` 开始、
且带 `paddingLeft` 给侧边栏让位，没有任何内容会滚到它们下面。没有内容可以模糊，
`backdrop-filter` 就只剩每帧重新合成的开销；深色模式下这三处本来就被强制成不透明，
模糊连"看起来有区别"都做不到。一个"开着也没有收益"的开关只会让用户以为自己选错了。

合并仍然只发生在一处：新增 `utils/glassPreference.ts` 的 `isGlassEnabled`，与
`isMotionReduced` 同构；性能模式**包含**关闭毛玻璃，反向不成立。

#### 顺带修掉的四个真实缺陷

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 深色模式下设置界面（以及插件页、开发指南）的背景是**纯黑**，而浅色模式下是半透明 | `dark-theme.css` 把 `bg-gray-900` 与 `bg-gray-900/40` 合并成一条规则，一起映射成**不透明的** `#0b0d14`。前半段是对的（实心深色按钮），后半段把 40% 的遮罩变成了实心近黑板。插件市场用的是 `bg-gray-900/30`，恰好不在表里，所以那里反而是对的 —— 这就是为什么只有设置界面看得出来 | 拆成两条：`bg-gray-900` 保持实心色，`bg-gray-900/NN` 与 `bg-black/NN` 各档映射成**真正的半透明黑**（并保留档位之间的深浅差） |
| 分屏时两条标签栏之间的 1px 分隔线在深色下是一条**亮灰**竖线 | `bg-gray-200/70` 从未被映射 | 补进 `bg-gray-200` 组 |
| 关于页的外链 chip 在深色下悬停几乎没有反馈 | `group-hover:bg-gray-900/10` 是**另一个类名**，而映射表里只有 `hover:bg-gray-900/10` | 补上，且选择器用"祖先 hover"（` .group:hover [class~=...]`）与 Tailwind 生成的形态对齐 |
| 深色下浮层的底色比设计意图**更暗**，且被描了一道近黑边 | `dark-theme.css` 用 `[class~='backdrop-blur-xl']` 当"这是窗口亚层"的判据，而那个类并非亚层独有：全局右键菜单、模块右键菜单、隐藏模块面板、插件卡片下拉、插件页下拉全都同时带 `bg-white/95` 与它。同一个误判让它们拿到了亚层色 `#151823`（设计意图是浮层更亮的 `#1a1e2b`）与亚层描边 `#0a0c12`（而紧挨着的注释恰好写着"深色下给浮层描一道近黑边会让它看起来像一块硬邦邦的补丁"） | 引入语义类 `lc-chrome` 作为判据。规则与注释终于一致，且不再随类名改动而静默失效 |

**这四个是同一种失败：`dark-theme.css` 是一张按类名精确匹配的覆盖表，漏一档就退回浅色，不报错、类型检查也过。** 因此这一轮加了 `scripts/check-theme.ts`：它把 `src/` 里实际用到的半透明背景 token 全部扫出来逐个核对映射，并要求遮罩必须保持半透明。写这个脚本的过程中它当场又抓出上面第 2、3 条与两档 `bg-black` 遮罩。

#### 侧边栏折叠按钮"悬浮不上"

**现象。** 鼠标放在按钮上（尤其是图标上）没有任何反应，必须往下移一段才行。

**根因与全屏无关**，虽然现象看起来像：标签栏行是 `fixed left-0 right-0 z-40`，靠
`paddingLeft` 把**内容**推到侧边栏右边让位 —— 但 `padding` 不会缩小元素盒子，那个
透明盒子仍然横跨整窗，而一个没有背景的 div 照样参与命中测试。它与侧边栏同为 `z-40`
且在 DOM 里更靠后，于是正好压在侧边栏头部：折叠按钮 y∈[56,84)，其中 56~76 被这条
带子吃掉，只剩底部 8px 可点。全屏时本行整个不渲染，所以那个按钮在全屏下反而是好的
—— 这也解释了为什么它看起来"和全屏有关"。

**处理。** 容器加 `pointer-events-none`（它纯粹是布局壳），需要交互的 TabBar 自己
声明 `pointer-events-auto`。比"把侧边栏的 z-index 抬上去"更准：真正的错误是**透明的
布局盒子本就不该命中测试**，抬高 z 只是掩盖它，压在下面的其它元素还会再中一次。

#### 通知提示音

新增「设置 → 通知」分页：开关、五种内置音色（每种可当场试听）、自定义音效、音量。

三个决定：

- **音色用加性合成，不打包音频文件。** 项目此前刻意避免新增二进制资源与依赖，而
  敲击音（钟 / 马林巴）用几个非谐分音就能做出辨识度。分音峰值在 `strike()` 里
  按总数**自动归一化**，因此"换音色就换了音量"这件事在结构上不会发生。
  （**这条在 v1.3.2 被有选择地推翻了**：新增一个随应用发布的默认音效，其余五种
  仍是合成。见 7.37 节 —— 保留这一段是为了说明当时的取舍，不是当前行为的描述。）
- **自定义音效是被复制进来的。** 后端只认 `<app_data>/sounds/custom.<白名单扩展名>`
  这一个文件名，设置里存文件名而不是路径 —— 存路径会让"读取任意用户文件"变成一条
  常驻能力，而它只需要在用户主动选择的那一刻发生一次。
- **声音与浮层同进同出。** `presentNotification()` 里同时做这两件事，因此不存在
  "弹了但没响"或"响了却找不到是什么"。被合并计数的重复通知不响 —— 否则重试循环
  会把它变成骚扰。

**一个无法自动验证的地方，如实记下：** 音色"好不好听"没有人能替用户判断。因此
`scripts/check-sounds.ts` 用桩音频上下文**真的跑一遍**每种音色的合成，检查的是
可以判断的部分：包络从 0 起振（否则有"啪"声）、指数衰减目标不为 0（否则真实实现
会抛错）、每个振荡器都 start 且 stop、以及**每个音色的瞬时振幅峰值落在 [0.5, 1.0]**
—— 这条下限正是"别太轻"，上限则是"别把压缩器逼出来把起振压扁"。听感仍需要人听。

#### 备份机制

新增 `backup` 模块（后端 8 个模块之一）与「设置 → 备份」分页：按类别导出标准 zip，
或从备份按类别恢复。类别为软件设置、侧边栏与模块偏好、通知记录、已安装插件、
插件数据、运行日志，外加默认不勾选的授权与安全数据。

**安全模型是白名单，而且是唯一的一份。** 导出只可能产出白名单里的路径，导入只接受
白名单里的路径 —— 也就是**能被接受的名字恰好是导出能产生的名字**。这条不变量比
"做了路径校验"强：它不依赖任何路径规范化技巧的正确性，因为可构造出的合法名字本来
就只有一个有限集（形状是 `data/<appdata|logdir>/<白名单相对路径>`）。

其余四条：

- **前端从不把路径交给后端去读写。** 导出与打开都经过系统对话框，恢复只能作用于
  后端记住的那个刚打开的文件。否则白名单只能约束包内路径，约束不了包从哪来。
- **恢复是替换，且先校验后删除。** 校验通过之后才动手删，因此"包有问题"永远不会以
  "数据被删了但没恢复回来"收场。`restore_validates_before_deleting_anything` 测试
  专门构造了"第一条合法、第二条越界"的包来锁这个顺序。
- **体积与条目数按实际写出的字节判定。** 压缩包里声明的大小可以被伪造成"声明很小、
  实际很大"，声明值只用于廉价预检。
- **敏感数据要两道门。** 导出时要点开高级开关，恢复时**还要再点一次**；后端
  （`resolve_selection`）与界面各自执行同一条规则。"我导出时愿意"与"我现在愿意覆盖
  本机凭据"是两个不同的决定。

日志类别**只导出不恢复**：日志文件由日志器持有着打开的句柄，Windows 上删不掉打开
中的文件。与其做一套"先关日志器、恢复完再开"的编排（那会在恢复失败时把日志系统
留在不确定状态），不如让它的用途收窄到"拿到另一台机器上排查"。

#### 顺带修掉：`restoreLastModule` 的两处默认值不一致

**类别：** 缺陷（已修复）

`AppSettings` 有两条独立的默认值路径：字段缺失时走 `#[serde(default = "...")]`，

有人发现某个开关在两个本该相同的情形下一个开一个关。

### 7.34 界面文案里的 Markdown 星号

**类别：** 显示缺陷（已修）＋ 新增门禁

文案从文档里抄进 JSX 时，`**强调**` 会**原样显示**成一串星号 —— 更新卡片的纯文本说明早就有这条检查（`check-markdown.ts` 查 `release/notes.md`），但界面本身没有。

真实的笔误是三处：网络设置页的"本地回环地址不受影响"与"它是诊断用的，不是审计"，以及备份恢复页的"覆盖本机当前的凭据"。

### 7.37 v1.3.2：备份页的深色缺口与默认提示音改为打包音效

两项改动都在既有结构上落点很小，但各自暴露了一个**门禁的盲区** —— 值得记下来
的正是那两处盲区，而不是改动本身。

#### 深色模式下"一块发白的板子"：映射表漏了彩色档位，而门禁扫不到那一类

**类别：** 缺陷（已修复）＋ 门禁扩容

**现象。** 设置 → 备份里勾选一个类别，那一行在深色模式下变成一块发白的板子，
复选框衬在中间像一个白色方块。

**根因是两处不完整，而且它们互相掩盖。**

1. `dark-theme.css` 是按工具类名**精确匹配**的覆盖表。indigo-50 那一组只列了
   裸类名、`/30` 与 `/50`，amber-50 只列了裸类名、`/20` 与 `/30`。
   `BackupSettings.tsx` 用的却是 `bg-indigo-50/40`（选中行）、`bg-amber-50/40`
   （敏感行）、`bg-red-50/60`（恢复确认面板）与 `bg-emerald-50/50`（结果面板）
   —— **四个档位一个都没在表里**，深色下原样保留浅色。
2. `check-theme.ts` 的 token 正则只匹配 `bg-(white|black|gray-\d+)/\d+`，
   **彩色半透明背景整类都在覆盖范围之外**。于是它对这四个档位一个字都没说，
   而脚本报的是"每一个半透明背景 token 都有深色映射"。

**这是同一种失败的第五次**（前四次见 7.28 节）。区别在于：前四次是"表里漏了一档"，
这一次是"门禁只看三种颜色"。前四次修完都能靠同一个脚本守住，第五次不能 ——
**因为脚本自己就是盲的**。

**处理。**

- `dark-theme.css` 补上缺失的档位（indigo-50 的 `/20`、`/40`、`/60`，
  indigo-100 的 `/40`，amber-50 的 `/40`、`/70`，emerald-50 的 `/50`，
  red-50 的 `/60`）。**没有改动任何既有取值**：新档位按"档位越大越明显"排序，
  与已有的 0.16 / 0.24 同源。
- `check-theme.ts` 的 token 正则扩到 `bg-<颜色>-<档位>/<透明度>` 全族，
  于是覆盖数从 **23** 个涨到 **48** 个，当场多出 13 个待处理的 token。
- 那 13 个里，8 个补了映射，5 个进了豁免名单，**每条都写明理由**，分成两类：
  常驻深色界面（授权页、启动页的装饰件 —— 见 `dark-theme.css` 第 8 节）与
  中间明度的强调色（`bg-indigo-400/60`、`bg-indigo-600/10` 这类：它们在深色底上
  本来就可读，反相它们反而是错的）。
- 新增一条断言：**豁免名单里不许出现 `-50` / `-100` 的浅色底**。豁免规则本身是
  对的，但它可以被滥用成"这个漏映射我懒得补"，而浅色底在深色界面上必然发白 ——
  这一类没有豁免空间。判据只看类名，不需要解析颜色值。

**顺带改掉的复选框。** 那一行里的 `<input type="checkbox">` 原本用原生外观 +
`accent-indigo-600`。原生控件在深色下长什么样取决于渲染引擎如何解释
`color-scheme` 与 `accent-color`，而"未选中时是白底"正是被报告的现象之一。
现在保留真实的 `input`（键盘可达、屏幕阅读器正确、`<label>` 点击仍生效）但把它
藏起来，由旁边一个 `span` 负责画 —— 外观不再取决于任何平台默认值。

**仍未覆盖（如实记下）。** 扩容后的门禁守的是**半透明背景**。两类仍然没有覆盖：

- **实心浅色**：`bg-indigo-100` 这类没有透明度修饰符的类名不在扫描范围内。
  它当然也可能是浅色底，只是这一轮没有真实案例。
- **边框与文字**：`border-*` / `text-*` 的映射完整度同样没有门禁。这一轮顺带
  核对过备份页用到的四个 `border-*` 都有映射，但那是人工核对，不是断言。

#### 默认提示音改为随应用发布的音效

**类别：** 功能改动（推翻 7.28 节的一处取舍）

7.28 节写下的是"音色用加性合成，不打包音频文件"。这一轮把它改成：
**默认那一项是随应用发布的 `src/assets/notification.mp3`，另外五种仍是合成。**

**为什么值得为它新增一个二进制资产。** 提示音要解决的是"用户没在看这个窗口"，
而真实录音在嘈杂环境里的穿透力明显强于几个分音堆出来的敲击音。合成音色的优势
（无资产、无体积、参数可断言）在这一项上换不来"被听见"，而"被听见"正是它唯一
的职责。**保留另外五种合成音色**，因此这次不是替换，而是给默认值换了个来源。

**四个必须一起处理的点。**

| 点 | 处理 |
| --- | --- |
| 资产怎么进产物 | 放 `src/assets/` 并由 `services/sound.ts` 以 `import` 引用（不是运行期拼路径，也不是 `public/`）。路径写错会在构建期失败；`public/` 下的文件没人引用也照样打包，拼错只表现为运行时静默无声 |
| 怎么播放 | `<audio>`，**刻意不用 `fetch` + `decodeAudioData`**。那条路要发一次请求，而 `netGuard` 会把它当成出站尝试记进流量日志 —— 读一个随应用发布的本地文件既不是出站，也不该受出站策略约束。`<audio>` 走的是 CSP 的 `media-src 'self'`，本来就覆盖 |
| 前后端默认值 | `settings.rs` 的 `DEFAULT_NOTIFICATION_SOUND_ID` 与前端常量同时改为 `default`。**老设置文件里存着的 `chime` 仍然合法**，升级不会改变老用户听到的声音 —— 只改默认值，不改用户已经做出的选择 |
| `BUILTIN_SOUNDS` 的类型 | `notes` 变成可选，并新增 `bundled` 标记。于是"遍历 `BUILTIN_SOUNDS` 跑合成断言"这类代码必须显式处理没有音符的那一支，而不是安静地什么都不播 |

**分发与播放的分支收在一处。** `services/sound.ts` 的 `playById` 是唯一的分发点，
三支分别是打包音效、自定义音效（文件丢了回退到默认，而不是静默不出声）与现场
合成。`renderSound` 对打包音效静默返回 —— 它没有音符可合成，而把"选错了分支"
升级成"通知推送失败"是更糟的结果。

**未覆盖：打包音效的音量没有人能自动判断。** 合成音色的峰值被 `strike()` 归一化
到声明的 `gain`，`check-sounds` 因此能断言"每个音色都不偏轻"。打包音效的响度
完全由那个文件决定，脚本能验证的只有"文件在、体积可接受、被引用、走对了分支"。
**听感与响度需要人听一次。** 这一段是有意留白的，不假装已经覆盖。

#### 出站策略的「默认询问」：把一个预留了三个版本的档位填上

**类别：** 功能（补齐既有空位）

`policy.rs` 里 `MODE_ASK` 一直存在，判定函数也一直返回 `AllowPendingPrompt`，档位表里
`available: false`，并且有一条测试专门防止有人把它改成 `true` 却忘了实现。它的
`unavailable_reason` 自己写着这一档需要什么：**"一条请求级的往返（暂停请求、前端弹
确认、带回结果、超时兜底）"**。这一轮就是按那句话填的，没有另起设计。

| 层 | 落地 |
| --- | --- |
| `net/prompt.rs`（新增） | 询问状态、串行化、暂停/恢复、超时兜底、会话放行表 |
| `net/client.rs` | `AllowPendingPrompt` 分支：先去问，再决定发不发 |
| `net/commands.rs` | 三个命令：回答、列出本会话放行的主机、清空它们 |
| `components/NetPromptLayer.tsx`（新增） | 对话框。**挂在 `main.tsx`，在 `BootGate` 外面** |

**四个决定，以及为什么是它们。**

- **超时的方向是拒绝。** 放行是一次**没有发生过的同意**；拒绝是可见、可重试的。
  这与认证配置损坏时"退化为需要授权"是同一条取向。
- **「本会话内总是允许此主机」是必需的，不是便利。** 市场一次操作会连发索引、
  签名、README、图标与包下载五条请求。只给"允许一次"，用户要连点五次；选项
  不可用等于功能不可用。
- **不做"永久允许"。** 用户选的就是"每次问我"，替他永久放行等于静默削弱他自己
  选的策略。而且落盘要动 `settings.json` 的契约（MINOR 级别），不该塞进补丁版。
  重启即失效，语义干净。
- **一次只弹一个，其余排队。** 五个几乎相同的对话框互相盖住，比排一个队更糟。
  排队的那几条在**拿到队列许可之后会再查一次会话放行** —— 用户可能刚在排队期间
  为同一个主机点了"总是允许"，少了这一步它们会挨个再问一遍。

**界面为什么必须挂在 `BootGate` 外面。** 出站请求会发生在启动阶段（自动检查更新）
与解锁界面上，那时 `Home` 还没挂载。挂在 `Home` 里的后果不是"看不见"，而是
**那批请求无人可问、只能在 30 秒后超时** —— 用户会看到"更新检查失败"，而真正
的原因是他从没被问过。层级取 `z-90`：高于设置面板（z-60）与插件弹窗（z-70），
因为用户在设置里点一次网络诊断，诊断自己就会发请求，而对话框压在设置面板下面
时他点不到它。

**日志里多两个取值。** `allowed-by-prompt`（用户在询问里点头）与 `allowed-session`
（本会话内早就放行过这个主机）。把它们混成 `allowed` 之后，用户就再也看不出
**自己到底同意过什么** —— 而那正是这一档存在的全部意义。设置页因此也列出
"本会话已允许的主机"并给出一条全部撤销的路径：一个只增不减、又不在界面上的
状态，用户既不知道它存在，也无法收回自己给过的许可。

**仍未覆盖（如实记下）。**

- **`netGuard` 那一侧的判定没有变。** WebView 里的直接 `fetch` 在 ask 档下仍然
  一律拒绝（理由仍然是"走错了通道"，而不是"没被允许"）。因此这一档只覆盖
  走后端门面的请求 —— 与 7.35 节划的边界是同一条。
- **超时值 30 秒是判断，不是测量。** 它落在"用户可能在看别处、但还没走开"的量级上，
  有一条断言只锁住"别被人随手改成 5 秒或 10 分钟"，锁不住它是不是最优。
- **没有"拒绝并记住"**。反复拒绝同一个主机时用户每次都要再点一次。之所以不做：
  拒绝的语义是"这次不行"，把它记成长期规则会让"我总是拒绝它"和"我这次不想"
  混为一谈，而后者是更常见的意图。

#### 仪表盘重写与用户自定义的模块分类

**类别：** 功能（新增）＋ 界面重做

**为什么重做。** 上一版是一个"模块浏览器"：五张统计卡（总数 / 启用 / 收藏 /
隐藏 / 禁用）加一片模块网格。它的问题是**用户无法整理**：收藏与"最近使用"是
宿主给的两种排序，而"工作 / 工具 / 娱乐"这种分类维度只能由用户自己定。

（这一节最初还写了第二条理由 —— "五张卡里四张在回答没人问的问题" —— 并据此把
统计面板去掉了。**那条理由后来被证明是错的**，见下一节。）

**分类的模型（三条，都有理由）。**

| 决定 | 理由 |
| --- | --- |
| **一个模块最多属于一个分类**（划分，不是标签） | 分类在界面上是分区。一个模块同时出现在两个分区里时，"把它挪走"立刻变得没有答案：挪哪一个？另一个要不要跟着去掉？ |
| **分类成员里允许存在当前不存在的模块 ID**（插件被卸载） | 那是有意的：重装之后它回到原位置。清掉成员等于把用户的整理结果扔掉 —— 而这类"看起来是垃圾、实际上是状态"的数据，清理它从来不是无害的 |
| **删除分类不删模块**，成员回到「未分类」 | 删掉分类不等于让那些模块从界面上消失 |

落点：后端 `sidebar` 模块的 `SidebarPreferences` 多一个 `categories` 字段（**分类
随 `get_module_preferences` 一起返回**，因此前端没有第二个加载入口，也就没有
"这份数据加载了吗"这种状态），六个命令统一返回**整张分类表**（前端不必维护一份
乐观副本，也就不存在"乐观副本与后端真值分叉"）。读盘时 `sanitize_categories`
把手工编辑过的配置修回不变量：丢非法条目、去重复 id、**保证一个模块只在一个
分类里**、截到上限。

**「恢复默认偏好」不清分类。** `SidebarPreferences::reset` 刻意保留它们：那个按钮
的语义是"把显示偏好恢复成默认"，而分类是用户一条条创建的内容。顺手删掉用户创建
的东西，与本项目在别处一贯的取向相反。

**一个刻意没做的事：拖拽归类。** 本应用里 HTML5 拖放整体不可用（Tauri 的
`dragDropEnabled` 拦截系统拖放，而插件的 `ctx.fileDrop` 正依赖它）。标签拖拽与
分屏拖拽为此都用指针事件自己实现过一遍。这里没有再做第三遍，而是给了"移动到
分类"菜单：键盘可达、不依赖指针精度，而分类操作是低频动作。

**性能上只做了一件真事。** `useModuleActive()` 在这里的用途是**标签不可见时不播
入场动画** —— 上一版的长延迟 stagger（`0.15 + i*0.06` 秒）正是"切走仪表盘后卡片
还残留一会儿"的成因（7.27 节）。这一页没有轮询、没有定时器，因此没有别的需要
暂停的东西，也就不假装有。

**文案改为中文。** 全应用都是中文，只有这一页是英文（`Dashboard` /
`Discover, organize, and launch your modules`）—— 那是模板残留。

**顺带改掉的一个真实缺陷。** 隐藏模块此前会从仪表盘上**一起消失**：用户点一下
"从侧边栏隐藏"，模块就从这一页没了，既不记得自己做过什么，也没有一条回到它的路。
现在底部有一行如实提示"N 个模块被隐藏在侧边栏里，以及去哪里恢复"。

**仍未覆盖。** 分类只作用于仪表盘，**没有接进侧边栏** —— 侧边栏仍然是平铺的模块
列表。那是一个独立的产品决定（侧边栏是导航，分区会让它变长），因此没有顺手做。

#### 仪表盘的第二轮：一处判断失误，与四项修正

**类别：** 界面修正（其中一项是判断错误）

上一节把统计面板去掉了，理由是"五张卡里四张在回答没人问的问题"。**那个理由
不成立**：它对的是"用了三个月的人"，而仪表盘是**新用户第一次打开**看到的东西 ——
那几个数字回答的正是他此刻的问题："我装了多少东西、整理到哪一步了"。判断"它还有
没有用"该由用户做，不该由默认值替他做。

| 改动 | 为什么 |
| --- | --- |
| **统计面板回来，并且可关** | `dashboardStatsVisible`，默认显示。开关放在仪表盘上而不是设置页 —— 要收起的是眼前这一块 |
| **模块可以拖动归类** | 拖到某个分区上就移进去；拖到分区内某张卡片的前 / 后就插在那一位 |
| **图标不再带底色** | 模块图标自带形状与颜色（内建用 lucide、插件用自己的 SVG），再套一层彩色底板等于在每个图标后面放一个与它无关的色块 —— 同一片网格里十几块同色方块，看起来像没加载完的占位 |
| **收藏恢复黄色** | 上一节把分区标题的图标统一成了强调色，理由是"整页一套色更干净"。但那让收藏与普通分区在扫视时没有区别，而收藏恰恰是用户自己标出来的一类东西 |
| **「全部模块」换到二级面板** | 它回答的是与主视图**不同**的问题：主视图是"我整理过的分区"，面板是"一共有什么"。两个问题都需要答案，因此是两个界面。面板里每个模块都在（含隐藏在侧边栏里的），并提供搜索、五种筛选与"恢复"入口 |

**位置由前端算、后端只负责放。** 拖动表达的是"放在这两张卡片之间"，把它换算成
"上移一位"需要后端知道前端的当前顺序，而那个顺序可能已经过期（一次失败的写盘、
或另一个入口刚改过）。因此 `set_module_category` 收一个**目标分类内的下标**，
`place_module` 只做"摘掉再插入"，下标越界时**夹到末尾而不是报错** —— 拖动中算出
的下标因为并发变化越界一格，不是用户做错了什么。反过来，"分类不存在"是错误，
并且**在改动任何数据之前就返回**（有测试钉住这一点）。

**拖动仍然是指针事件自己实现。** 与标签拖拽、分屏拖拽同一套理由：本应用里
HTML5 拖放整体不可用。这是第三处，规则相同 —— `pointerdown` 记起点、超过阈值
才算拖动（否则会吃掉点击）、自己算落点、自己画一个跟随指针的幽灵。
**"移动到分类"菜单保留**：键盘用户拖不了，而两条路都通向同一个命令，因此不存在
行为不一致。

**它仍然不是操作系统的第二个窗口。** 这一点在动手前确认过：第二个 webview 有
**自己的 JS 上下文**，而 `tabStore` / `moduleCatalog` / 插件运行时 / 会话令牌都是
单窗口单例（令牌在 `sessionStorage` 里，不跨窗口共享）。要让它真实地显示**插件**
模块，就得在两个窗口之间建一条数据通道，或者把单例改成多实例 —— 也就是 7.27 节
记为"架构级工作"的那一项。面板是同一件事在应用内的形态；这一点如实写在这里，
而不是假装已经做到了。

#### 一条整整三个版本没有生效过的门禁

**类别：** 测试基础设施（修复）

`npx tsc -p tsconfig.node.json` 是提交前检查里的一项，而它**从 1.3.0 起就没有
真正跑过**：109 个错误、横跨 15 个文件，真实错误全被埋在下面。

根因不是笔误，而是**用"编译失败"去表达一条意图**。那个 project 原本只给
`lib: ["ES2022"]`，用意是"引到带 DOM 用法的模块就报错"，借此保证脚本只依赖能在
Node 里求值的纯逻辑模块。用意是对的，但它没有配套的守卫：当 `check-net-guard.ts`
开始 import `appSettings.ts`（后者 import `theme.ts`，用 `document`）之后，整次检查
就变成一堆与本意无关的错误 —— 于是没有人再跑它，`check-contributions` /
`check-plugin-runtime` / `check-net-guard` 三个脚本从未被类型检查覆盖过。

**修好之后它立刻抓出一个死断言**：`check-contributions.ts` 里
`issues.every((item) => item.kind !== 'themes')` 是**恒真**的 —— `ContributionIssue['kind']`
是一个闭合联合，`'themes'` 根本不在其中。这条断言永远不可能失败，而它看上去
完全正常。

现在的分工：

| 关注点 | 由谁负责 |
| --- | --- |
| 真实类型错误 | `tsc -p tsconfig.node.json`（显式声明 `lib: [..., "DOM"]` 与 `jsx`） |
| "脚本只依赖纯逻辑模块" | 新增的 `pnpm check:scripts` 文本断言 |
| 两个 project 的路径别名一致 | 同上（脚本会沿 import 走进 `src/modules/**`，少一条别名就是一条看不出原因的 TS2307） |
| `include` 完备性 | **不再要求**：`composite` 要求 program 里每个文件都列进 `include`，而脚本会拉进一长串 src 模块，手工维护必然漏（实测漏了 24 个），改用 `incremental` |

用断言而不是编译失败表达那条意图，差别是**断言能说出自己是哪一条**：编译失败给的
是 109 行噪声，`check:scripts` 给的是「`src/utils/xxx.ts` 引用了 `window` ——
它被脚本直接 import 并在 Node 里执行」。

**这一轮还有一处同源的问题被修掉：** `sound.ts` 新增的资源 import 让
`check-plugin-runtime` 与 `check-net-guard` 双双失败，而报的是一个与插件运行时
毫无关系的 `.mp3` 扩展名错误（Node 不认识它）。夹具的解析钩子现在把 Vite 会处理
成 URL 的资源统一变成一个占位地址 —— 这是夹具该做的事，因为 Vite 就是这么做的。
