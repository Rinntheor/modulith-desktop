## 为什么按状态拆而不是按主题拆

按主题拆过一版想法，否掉了：**同一个主题下"现行"与"已解决"混着放，读者仍然要逐条
判断哪条还算数**，而那正是这次要消掉的问题。因此第一刀切在状态上，第二刀才是主题。

**条目编号一律不变**（§1、§4.1、§7.44 这类）。外部文档是按编号引用的
（`插件系统架构.md` 写「§7.39、§7.40、§7.44」，`前端架构.md` 写「第 7.7 节」），
重新编号会静默打断它们。编号到文件的对照表就在下面。

## 记录纪律（从这次拆分里长出来的）

原文档之所以会混，是因为**没有人有理由去回头核对一条旧记录**。因此：

1. **已解决的条目一律不留在这里**，移进 `历史/`，并在原位留一条指针。
   标题里带「已解决」却躺在"已知问题"里，是最误导的一种写法。
2. **每条现行条目都要能被核对。** 写结论时给出**判据**（哪一处代码、哪一条门禁），
   而不是"目前看起来没问题"。
3. **历史条目里"顺带发现但没修"的东西要浮上来。** 原文里有七八处这样的内容
   （例如 §7.17 的"宿主没把快捷键暴露给插件"），它们藏在"已处理"的叙述里 ——
   已经在 `现行问题.md` 末尾单独列了一张表。

# 已知问题与技术债

本文记录当前代码中已确认的问题、未完成的能力与设计上的取舍。目的是让后续维护者不必重新发现它们。

分类说明：

| 类别 | 含义 |
| --- | --- |
| 缺陷 | 行为与预期不符，应当修复 |
| 未接入 | 代码存在但没有任何路径使用它 |
| 未实现 | 类型或界面已声明，但没有对应实现 |
| 设计取舍 | 有意的选择，需要时再重新评估 |
