## 1. 导航机制

### 1.1 状态驱动的导航与路由代码并存

**类别：** 未接入

**现状。** 打开模块时只调用 `tabStore.openTab()`，由它更新标签状态；`Home` 据此渲染 `mountedTabs` 中的全部模块（仅激活的那个可见）。`SidebarContext.activeModule` 读的是 `tabStore.activeTab`，不再自己持有。模块**切换**不修改地址栏，代码库中也没有任何 `useNavigate`、`navigate()`、`<Link>`、`useParams` 或 `useLocation` 调用。

与此同时，`src/router/` 下存在一套路由设施，其中**并非全部是死代码**：

| 文件 | 状态 |
| --- | --- |
| `Router.tsx` | 生效：声明 `/`、`/home`、由 `DynamicRouter.getRoutes()` 生成的动态路由，以及兜底 404 |
| `dynamicRouter.ts` | **活代码**：由 `Router.tsx` 以值导入方式引用。`getRoutes()` 被使用；其余六个静态方法（`getRouteByModuleId`/`getRouteTree`/`isValidRoute`/`addRoute`/`removeRoute`/`clearRoutes`）无调用方 |
| `contexts/RouteContext.tsx` | 死代码：`RouteProvider` 与 `useRoute` 没有任何引用方 |

**影响。**

- `Router.tsx` 中由 `DynamicRouter.getRoutes()` 生成的 `<Route>` 列表**确实被注册生效**，但它只包含启动时刻的内建模块快照，不含插件在运行期注册的模块。由于导航不经过 URL，这一点在日常使用中不会暴露；但若用户手动修改地址或依赖深链接，插件模块会落到 404。
- `RouteContext.tsx` 属于死代码。
- `window.history.back()` 出现在 `Router.tsx` 的 404 页与 `ModuleRenderer.tsx` 的「模块未找到」页。既然模块导航不进历史栈，这两个按钮的语义并不成立。

**建议。** 在两种方向中明确选择其一：

1. 让导航真正走路由：侧边栏切换时调用 `navigate(path)`，`DynamicRouter` 在编目变化时重新生成路由，并由 `RouteContext` 提供当前路由信息。这样深链接、前进后退可与浏览器行为统一。
2. 确认继续使用状态驱动：删除 `RouteContext.tsx`，并在 `Router.tsx` 中移除动态路由生成逻辑，避免两套机制并存造成误解。**注意顺序：** `dynamicRouter.ts` 不能先删 —— 它被 `Router.tsx` 以值导入方式引用，且被 `types/core.ts` 再导出（`RouteConfig`）。必须先摘掉 `Router.tsx` 里对 `getRoutes()` 的调用与 `types/core.ts` 的再导出，才能删除该文件。

在做出选择前，`SidebarContext` 中自建的前进后退历史栈（`goBack`、`goForward`）需要一并考虑：如果改用路由，这套历史管理应当交给路由层。注意它与标签页是两套独立的顺序 —— 历史栈记录**访问顺序**（用户实际去过哪里），标签顺序是**用户拖出来的排列**，二者刻意不合并。历史栈不持久化，重启后从空开始。

### 1.2 动态路由的初始化时机

**类别：** 缺陷（仅在采纳路由方案时成立）

`dynamicRouter.ts` 在模块顶层调用 `DynamicRouter.initialize()`。该文件在应用启动时被导入，此时插件尚未加载，因此生成的路由不含插件模块。即使采纳上述第 1 种方案，也需要把初始化改为在 `moduleCatalog` 变化时重新执行。

### 2.2 模块 ID 命名不统一

**类别：** 设计取舍

**现状。** 前端模块 `id` 使用小驼峰（`dashboard`、`plugins`），后端模块 `id` 使用蛇形（`sidebar`、`plugins`、`auth`、`settings`）。两者通过各自的目录独立管理，没有强制的同名要求。

**影响。** 同一功能的模块在前后端名称形式不同，排查问题时需要在两种命名间转换。

**建议。** 保持现状是可接受的，因为后端 `id` 必须满足蛇形以正确生成 Rust 类型名。若要统一，只能把前端改为蛇形，代价是 `module.toml` 中 `path` 与 `id` 的关系变得不直观。另一种选择是在文档中明确记录两者的映射关系，[模块开发](../02-开发指南/模块开发.md)第 4 节已作说明。

## 3. 未使用的框架能力

以下能力已实现但当前没有任何调用方。它们本身不是缺陷，但会让人误以为系统具备相应行为。

| 能力 | 位置 | 现状 |
| --- | --- | --- |
| `Module::stop()` | `core/module.rs` | `lib.rs` 只调用 `setup` 与 `start`，从不调用 `stop` |
| `Module::dependencies()` | `core/module.rs` | 无模块声明依赖，拓扑排序退化为任意顺序 |
| `Module::handle_event()` | `core/module.rs` | 无模块实现该回调 |
| `ModuleRegistry::broadcast_event()` | `core/registry.rs` | 无调用方 |
| `createLazyComponent().preload()` | `utils/lazyLoad.ts` | 由启动流程的 `preload` 步骤调用（已不再是死代码） |
| `src/types/core.ts` | 整个文件 | 无引用方 |

**类别：** 未接入

**建议。** 按用途分别处理：

- 生命周期钩子（`stop`、`handle_event`、`broadcast_event`）属于框架预留能力，若要保留应在文档中标注为「预留」，或补上实际调用点。其中 `stop` 的缺失值得注意：如果将来有模块需要在关闭前释放资源，当前框架没有执行时机。
- `preload` 若要发挥作用，应在模块首次渲染前调用，以减少切换时的等待。
- `types/core.ts` 建议删除，其内容与 `types/module.ts` 重叠。

### 3.1 模块启动顺序不确定

**类别：** 缺陷（潜在）

`ModuleRegistry` 用 `HashMap<String, Box<dyn Module>>` 存储模块，`all()` 返回 `self.modules.values()`。`lib.rs` 按该顺序调用各模块的 `start`，因此启动顺序取决于哈希布局，每次运行可能不同。

当前七个模块的 `start` 都是默认空实现，所有初始化都在 `setup` 里完成，因此没有实际影响。但一旦某个模块的启动逻辑依赖另一个模块已启动，就会出现难以复现的偶发故障。

这里还叠着一条**容易误判的次序约束**：`setup_all` 按注册表顺序调用，而注册表顺序取自目录名的字母序，因此 `auth` 排在 `logging` 前面 —— `auth` 在 `setup` 里打的那几行日志发生在日志器**已安装、但还没拿到日志目录**的窗口内。处理方式是把「安装日志器」与「配置落盘目录」分成两步（前者在 `main()` 最早期，后者在 `logging` 的 setup），中间用内存队列承接。见[日志系统](../02-开发指南/日志系统.md)第 3 节。这说明**即使每个模块的初始化都正确，模块之间的相对次序仍然会通过副作用被观察到**。

**建议。** 在 `setup_all` 中记录拓扑序并提供一个按序迭代的方法，让 `start` 也按依赖顺序调用。或者统一在 `setup` 中完成初始化，避免依赖 `start` 的顺序。

## 4. 插件系统

### 4.1 权限声明仍有过半未强制

**类别：** 部分实现

**现状。** `PluginManifest.permissions` 是 `Vec<PluginPermission>`，枚举包含 **13** 个取值。当前真正被检查的是 **10 个** —— 7 个在 Rust 侧、3 个在前端：

> 这两个数字在 2026-10 的拆分中核对过：`1.6.3` 的 `permissions.rs` 里
> `enforcement: F::Host` 出现 7 次、`F::Frontend` 3 次、`F::None` 3 次。
> 本节此前写的是「12 个取值 / 七个被检查」，那是 `filesystem-scoped` 补上强制点
> 之前的数字 —— **过时的统计比没有统计更容易误导**，因此更正并留下判据。

| 权限 | 检查位置 | 检查层 |
| --- | --- | --- |
| `storage` | 任一 `plugin_storage_*` 命令 | Rust |
| `network` | 发起 HTTP 请求前 | Rust |
| `network-external` | 目标不是回环地址时 | Rust |
| `process-spawn` | `plugin_launch_program` 命令 | Rust |
| `filesystem-read` | `plugin_extract_icon` / `plugin_reveal_in_folder` / `ctx.fileDrop` 订阅 | Rust（拖放另有前端一处） |
| `notification` | 调用 `ctx.notifications` 时 | 前端 |
| `plugin-communicate` | 调用 `ctx.events` 时 | 前端 |
| `clipboard` | 调用 `ctx.clipboard` 时 | 前端（**强制程度最弱的一项**，见下） |

其余取值（`filesystem-write`、`native-module`、`dev-tools`）不影响任何行为；`filesystem-scoped` **已经脱离这一列**，见下。

**进展（1.5.0）：这四项保留，但"为什么不影响行为"的原因被分开了。** 原先它们都以同一句话收尾 —— 那会抹平一件重要的事：**这四项的原因不一样，其中两项的读法恰好相反。**

| 取值 | 原因 | 插件实际能做什么 |
| --- | --- | --- |
| `filesystem-write` | 有语义、**缺检查点** | 没有任意写的通道。要写文件用 `filesystem-scoped` + `ctx.files` 的可写目录授权 |
| ~~`filesystem-scoped`~~ | ~~**缺授权模型**（不属于 1.5 范围）~~ —— **已解决，见本节末尾** | 现在有通道：`ctx.files`，Rust 侧强制 |
| `native-module` | **这一能力不存在** | 什么也做不了 —— Tauri 插件必须随应用编译 |
| `dev-tools` | **这一项是冗余的** | 什么也不需要做 —— 共享页面环境，插件本来就能开控制台 |

后两项尤其需要分开写：`native-module` 是**真的拿不到**，`dev-tools` 是**不需要授权**。把它们都写成"否"，用户就可能以为 `dev-tools` 声明了能得到什么。

**同时修掉了一处界面上的假承诺。** 安装确认页对每一项 `enforcement: none` 都显示「宿主**尚未**强制这一项」——「尚未」暗示以后会强制。对 `native-module` 那是让用户等一个永远不会来的东西；对 `dev-tools` 则更误导。文案已改为不带承诺的「宿主当前不强制这一项 —— 其原因见上面的说明」。

**为什么保留而不删除枚举值：** 删除会让声明了它的清单**整份反序列化失败**、插件装不上（`permissions` 是 `Vec<PluginPermission>`，未知**值**不会被忽略），用户看到的是一句 serde 错误。收益（列表短两行、且**没有任何安全收益**）不值得。

**仍然存在的债：** `enforcement` 只有 `host` / `frontend` / `none` 三个取值，**表达不了"为什么不强制"** —— 现在这个信息在描述文字里，不是结构化字段。要变成字段需要同时改 Rust 类型、前端类型与界面，当前不值得。

**本轮进展。** `notification` 与 `plugin-communicate` 从「声明了但无效」变成了真正生效 —— 前者原本连接口都不存在（`PluginNotificationAPI` 只有类型声明，`createContext()` 从未提供它），现在已实现；后者是新增的跨模块事件总线。两者的拒绝方式是**降级为空实现 + 控制台警告**，而不是抛错：它们是可选的附加能力，让插件因为一个没声明的选项而整体加载失败，代价大于收益。

**本轮进展（storage）。** `storage` 从「声明与否都不改变行为」变成了真正生效：五个 `plugin_storage_*` 命令现在都会先经 `PluginManager::require_permission` 检查清单是否声明了 `storage`，未声明则拒绝。检查点收在 `checked_storage_dir` 一处 —— 与 `plugin_data_dir` 的 ID 校验同理，校验散在多处时漏掉任何一处都等于没有防护。

**但要分清它买到了什么。** 这次修复让**权限列表变得诚实**：清单里「声明了 storage」与「真的能读写存储」从此一致。它**不是**插件之间的隔离边界 —— 命令的 `id` 参数来自调用方，插件直接 `invoke('plugin_storage_get', { id: '别的插件', key: 'x' })` 仍能读取他人数据。

此处原文曾写着「存储始终可用，因为按 ID 隔离，不存在越权访问别的插件数据的路径，因此没有强制点可加」—— **这个判断是错的**：隔离的是**命名空间**，不是**访问权**。命名空间隔离只保证两个插件的键不互相覆盖，不保证一个插件不去读另一个的键。要堵住它，后端必须知道「谁在调用」，而这在「插件与宿主共享同一个 WebView 与 JS 上下文」的模型下无法实现。因此本项**只解决了「声明不生效」，没有解决「越权读取」** —— 后者要等进程级隔离。

**仍未解决。** 文件系统与剪贴板相关权限依然只是**部分**强制，需要说清边界：

- ~~`filesystem-read` 现在管住了**图标提取、文件管理器定位、接收拖入路径**三件事，但**没有任何命令可以读取文件内容**~~ —— **这句在 `1.6.3` 之后不成立了**：`ctx.files` 现在能读用户选定的文件，而它由 `filesystem-read` 强制（`files.rs` 的读侧命令都过 `require_permission`）。因此这一项**已经不是缺口**；上面那张表把它列在"已强制"一侧是对的，此处原先的判断是它落地之前的。
- `filesystem-scoped` **也已不再是缺口**（`1.6.3` 起由 Rust 侧强制，见本节末尾与 §7.41 一带）。因此下面这句话现在只适用于 `filesystem-write` 一项。
- `filesystem-write` 与 `filesystem-scoped` 没有对应的**权限检查点**。但要注意这句话此前写作"完全没有对应的命令"——**那是不准确的**：`export_plugin` 在此前可以用 `dest` 覆盖任意路径的文件，正是 `filesystem-write` 的语义（现已收口为"导出目录内的新文件名"，见 7.26 节）。所以这两个取值的真实状态是「有能力、无检查点」，而不是「没有可检查的东西」。
- `clipboard` 同理：宿主没有暴露剪贴板接口，插件要写剪贴板得自己用浏览器的 `navigator.clipboard`。

**进展：`filesystem-scoped` 有强制点了（`ctx.files`），而它之所以能被接受，是因为换了一个更窄的授权模型。**

上面那条 `filesystem-scoped` 的"缺授权模型"是对的，规划里因此明确把它**推迟到 v2.0**，并给出理由：核心工作量在**授权模型与界面**，而且"授权模型一旦发布就难以更改"。那个判断没有被推翻 —— 这里做的是**绕开它**：

- **路径从来不由插件给出。** 唯一能产生一条授权的动作是用户在一次**宿主弹出的原生对话框**里选中了某个文件或目录。插件能提供的只有对话框标题与扩展名过滤器。因此没有 `files.open(path)` 这种接口。
- **授权是会话级的**，绑在 `(插件, 界面)` 上：界面一关、插件一停用、应用一退出就消失。于是"用户三年前授权过一个目录"这种状态不存在，**授权管理界面、撤销、撤销后的行为、跨版本迁移**——也就是被推迟的那一整摊——在这里全都不需要。
- **一次授权就是一个根**，相对路径按 chroot 语义锁在它之内，复用 `data_dir::resolve_labeled`（与 `ctx.dataDir` 同一份实现）；插件拿不到授权目标的绝对路径。
- **删不掉授权根**：`files.remove` 拒绝空路径。

于是 `permissions.rs` 里 `FilesystemScoped` 的 `enforcement` 从 `None` 变成 `Host`，`enforcement_groups_match_documented_counts` 那个锁定数字从 `6/3/4` 变成 `7/3/3`。**`filesystem-write` 仍然是 `None`，而且仍然没有通道** —— 任意写依旧被拒绝，这一点没有变化。

**仍然存在的、与本项相邻的缺口：**

- **`filesystem-write` 依旧不实现**，规划里"补它等于制造一个假的管控点"的判断不变。
- **`ctx.files` 只有沙箱侧有。** in-process 插件跑在宿主文档里、没有令牌，因此没有承载"这条授权属于谁"的凭据。`check:sandbox` 第 20 节的差异清单里显式列着它。
- **`enforcement` 仍然表达不了"为什么不强制"**（上一段那条债没变）。

**另发现一处与本节直接相关的严重缺陷（尚未修复）：`ctx.storage.clear()` 会删掉整个插件数据目录。**

`checked_storage_dir` 与 `checked_data_dir` 返回的是**同一个目录**（`manager.rs` 里两者都走 `plugin_data_dir`），而 `storage_clear` 的实现是 `remove_data_dir` → `std::fs::remove_dir_all`。因此一个只声明了 `storage` 的插件调一次 `clear()`，会连带删掉 `ctx.dataDir` 下的全部文件与 `ctx.db` 的 SQLite 库文件。桥接层 `sandbox-bridge.js` 的注释还写着"不动数据目录"，与实现相反。

根因是**存储键与数据目录文件共享同一个命名空间**（存储键落盘为 `<数据目录>/<键>.json`）。正确的修法是给键值存储一个独立子目录（`<数据目录>/storage/`）并按需迁移旧文件；`storage_usage` 目前把整个目录都算成"键值存储用量"也是同一个根因。这条与 `ctx.storage.clear()` 无关的插件（例如只声明 `plugin-data` 的）无关，但**任何同时用 `storage` 与 `dataDir`/`db` 的插件都可能丢数据**。

**进展（1.5.0）：`clipboard` 从「声明了但无效」变成真正生效，但它是八项里强制程度最弱的一项。**

宿主现在提供 `ctx.clipboard`（`readText` / `writeText` / `isAvailable`），未声明 `clipboard` 的插件调用会被降级为空实现并记录警告 —— 与 `notification` / `plugin-communicate` 同一处理方式。

**但这一项买到的和另外七项不一样，必须说清楚。** 剪贴板是浏览器 API：插件绕过 `ctx.clipboard` 直接调 `navigator.clipboard` **仍然完全可行**。因此这里**没有**得到"插件拿不到剪贴板"这一层保障，得到的只是"按约定走宿主通道时会被记录、且忘记声明的插件会被降级"。

上面那条原文说的正是这件事：**"插件要写剪贴板得自己用浏览器的 `navigator.clipboard`"** —— 这句话在 1.5.0 之后**依然成立**。因此这条债没有被消除，只是被如实标注了。

**为什么不在 Rust 侧加门。** 剪贴板没有"授权开关"可关：`navigator.clipboard` 只要是安全上下文就可达。对比 `capabilities/default.json` 里刻意不授权的 `updater:default` —— 那是对**宿主自己命令**的授权，前端不给就真的不可达。剪贴板加后端门只会制造一种"更难绕过"的假象，而那正是本文档反复记录过的那类问题。

**影响。** 用户可以声明任意权限而不获得相应能力。权限列表整体上仍更接近意图声明而非访问控制，对用户判断插件风险有误导性。

**建议。** 两种方向：

1. 为其余权限补上强制点。这需要先明确能力边界，例如 `filesystem-read` 允许访问哪些目录 —— 而这在当前「插件与宿主同进程」的架构下无法可靠实现（插件可直接用 `fetch` 或 `invoke` 绕过）。
2. 在界面与文档中明确标注当前哪些权限生效，避免用户高估隔离强度。文档已在[插件系统架构](../02-开发指南/插件开发/插件系统架构.md)第 6 节与[清单文件参考](../02-开发指南/插件开发/清单文件参考.md)第 4 节作此说明。

**为什么前端检查也是有效的。** `notification` 与 `plugin-communicate` 的实现完全在前端（通知要落盘、事件不出进程），没有对应的后端命令可以绕过，因此前端就是唯一执行点。这与网络、存储权限不同 —— 网络请求由 Rust 发起、存储文件由 Rust 读写，所以检查必须在 Rust 侧。

> **§4.2（已解决）** sandboxLevel（已删除） —— 全文见 [历史/05-已解决的现行条目.md](历史/05-已解决的现行条目.md)。

### 4.3 插件包本身无代码签名

**类别：** 未实现（范围已收窄）

插件包（`.lcp`）**本身**没有签名机制，清单中也没有签名字段。但「安装时无法验证来源与完整性」这句此前过于笼统，需要收窄到实际范围：

| 安装路径 | 完整性 / 来源校验 |
| --- | --- |
| 插件市场（`install_plugin_url_verified`） | 强制校验索引里记录的 `sha256`；索引本身有 minisign 签名（与应用更新同一把公钥），验签不过则整体拒绝索引 |
| 从 `.lcp` 文件安装 | 无签名、无哈希 |
| 从本地目录安装 | 无签名、无哈希 |

因此缺口集中在**本地路径**：用户手工下载的包、以及开发链接目录，都没有来源校验。

**影响（仍然成立的部分）。** 用户无法区分官方插件与第三方修改版。配合 4.4 所述的隔离缺失，安装来源不明的插件的风险等同于运行未知程序。

**建议。** 若要覆盖本地路径，需要先确定密钥分发与信任模型，属于较大的独立工作。在此之前，应在插件管理界面显著提示风险。

### 4.4 插件与宿主共享同一 JavaScript 上下文

**类别：** 设计取舍

插件代码通过注入 `<script>` 执行，与宿主处于同一个 WebView 与同一个 JavaScript 上下文。因此：

| 项目 | 说明 |
| --- | --- |
| 全局对象 | 插件可访问 `window` 上的任意内容 |
| 会话令牌 | 插件可读取 `sessionStorage` 中的 `modulith.auth.token` |
| 插件之间 | 没有相互隔离 |
| 宿主数据 | 插件可读取宿主已加载的数据 |
| 网络 | 权限检查只约束经由 `ctx.http` 的请求，插件可用常规 Web 手段绕过 |

**影响。** 认证模块的会话守卫能防止命令被随意调用，但无法在恶意插件面前保护令牌本身。因此当前模型中**插件的信任级别等同于应用本身**。

**已有与缺失的隔离手段。** 需要区分「故障隔离」与「安全隔离」两件不同的事：

| 层级 | 机制 | 位置 | 能防住什么 |
| --- | --- | --- | --- |
| 渲染 | `AppErrorBoundary` | `src/components/AppErrorBoundary.tsx` | 任何未被下层接住的渲染错误导致整窗白屏 |
| 渲染 | `ModuleErrorBoundary` | `src/components/ModuleRenderer.tsx` | 插件界面渲染崩溃影响宿主与其它模块 |
| 渲染 | `PluginModulePending` | `src/components/ModuleRenderer.tsx` | 把「插件尚未加载完」误报为「模块不存在」 |
| 异步 | 全局错误监听 | `src/services/globalErrorHandlers.ts` | 事件处理器 / 定时器 / 未处理 Promise 拒绝静默消失 |
| 加载 | 逐插件超时 | `src/services/pluginRuntime.ts` | 一个慢插件拖累其余插件的加载 |
| 加载 | 加载失败标记 | `src/services/pluginRuntime.ts` | 坏的插件静默失败（现在会显示为「异常」） |
| 存储 | 按插件 ID 命名空间 | `src-tauri/src/modules/plugins/manager.rs` | 插件之间互相读写存储数据 |
| 资源 | 插件目录内路径约束 | `src-tauri/src/modules/plugins/manager.rs` | 插件读取自己目录之外的文件 |

**仍然缺失的（安全隔离）。** 上述机制只解决「一个插件崩了不影响别人」，不解决「一个恶意插件能做什么」：

- 没有进程级或 WebView 级隔离——插件代码与宿主同线程同上下文，可以读写宿主的任何全局对象；
- 插件 bundle 顶层的同步死循环**无法被中断**。JS 是单线程的，超时只能保证后续插件不被拖累，无法救回已经卡住的主线程；
- 插件可以直接 `invoke` 任意后端命令，后端只能靠会话校验兜底，而这拦不住已经拿到令牌的同源 JS。

**建议。** 真正的安全隔离需要独立进程或独立 WebView 实例，属于架构级改动。在此之前，应把「只安装可信来源的插件」作为明确的产品约束告知用户，而不是依赖权限系统提供保护。

### 4.5 无多版本共存与回滚

**类别：** 未实现

插件按 `<app_data>/plugins/<id>/<version>/` 归档。同一 ID 安装相同版本时会直接覆盖，旧版本不会被回收，也没有切换版本的机制。

**影响。** 插件升级后若出现问题，用户无法回退，只能重新安装旧版本包（如果还留着）。

**建议。** 若需要该能力，应在安装流程中保留上一版本并增加回滚入口，同时定义清理策略避免磁盘无限增长。

### 4.7 恢复码：没有历史记录，也不记「用掉的是哪一枚」

**类别：** 设计取舍

当前一次生成 3 枚恢复码（`RECOVERY_CODE_COUNT`），`auth.json` 只保存它们的 Argon2id 哈希数组（`recoveryHash`）与生成时间（`recoveryCreatedAt`），**不保留任何历史**。

**行为与限制。**

| 项目 | 当前行为 |
| --- | --- |
| 重新生成 | 整套作废，换发新的 3 枚 |
| 用掉一枚 | **只删除那一枚**，其余保留（这是刻意的，见下） |
| 用掉后是否换发 | **不换发**。重置成功后只减少一枚 |
| 历史 | 不记。界面只能显示生成时间与剩余枚数 |
| 审计 | 登录日志记录命中的序号（`recovery-reset#2`），但那只在日志里，不是恢复码历史 |

**「只删除用掉的那一枚」是安全性质，不是偷懒。** 早期实现是「重置成功后整套换发」。它有致命缺陷：若攻击者先用一枚恢复码重置了访问密钥，整套就会换成**攻击者手里**的新码，而用户手中的纸全部作废——攻击者不仅拿到访问权，还把合法用户永久锁在门外。只删除被用掉的那一枚之后，用户**始终保留夺回控制权的能力**。

代价是：不再有「一次重置就自动清空所有旧纸」的行为。要主动作废旧纸，必须去「设置 → 安全 → 密钥恢复」点「重新生成」。这是**有权衡的选择**——主动作废优于被攻击者替你作废，但确实留下一段窗口：若攻击者拿到了纸却还没用，在你手动重新生成之前它们一直有效。

**另一个限制：** 若用户把多张历史纸质备份混在一起，只有最新那一批有效，而界面上看不出「哪张是旧批」——只能靠 `recoveryCreatedAt` 自行比对。

**老用户升级路径。** 在引入恢复码之前就已设置访问密钥的用户，其 `recoveryHash` 为空。此时解锁界面不会显示「忘记访问密钥」入口（那会是个死胡同），并明确提示「本机尚未生成恢复码」。已解锁的用户可在「设置 → 安全 → 密钥恢复」补生成。

**建议。** 没有历史记录这一点可以考虑改进：记录「已用掉的枚数与时间」能在用户怀疑凭证泄露时提供线索。当前不做，是因为它需要新增持久化字段与界面，收益不足以justify。

### 4.8 清单里声明的依赖没有任何解析器

**类别：** 未实现

**现状。** `PluginManifest` 声明了四个依赖字段 —— `dependencies` / `optionalDependencies` /
`peerDependencies` / `devDependencies`（`src/types/plugin.ts`）—— 而宿主**没有任何解析器**：
装一个声明了 `dependencies` 的插件不会去检查、不会去提示、不会去安装被依赖方。

**这与 §4.1 的权限问题是同一个形状**："类型与清单里写了，但没有任何东西读它"。
权限那一处的处理是**让清单变诚实**（要么强制、要么在说明里写清不强制），
这四个字段还没有做过这件事。

**影响。** 插件作者按类型定义写依赖，会以为宿主会处理它。装到用户机器上什么也不会发生，
而失败方式是**静默的** —— 被依赖的能力不存在时，插件自己在运行期报一句与依赖无关的错。

**建议。** 两条路，任选其一，但**不要停在中间态**：

1. **实现解析**：安装前检查 `dependencies` 是否满足、缺失时明确告知并给出安装入口；
   需要同时处理版本区间、循环依赖，以及"被依赖方被卸载"这个反向事件。
2. **从类型里删掉**（或标注为"保留字段，宿主不处理"）：成本几乎为零，且立刻消掉
   "写了却没人读"的误导。`contributes` 的未知键就是按这个思路处理的
   （运行期宽容，但那是**刻意的**宽容，不是遗漏）。

**顺带记一处相邻的类型缺口（同一类）：** `contributes.background` 是**真实存在**的
贡献点 —— Rust 侧解析它、`src/services/backgroundPlugins.ts` 读它、
`PluginSettingsSection.tsx` 据此把插件标成「无界面」，但共享类型
`PluginContributions` 只声明了 `modules` / `commands` / `settings` / `contextMenus`
四个。于是**只有用 TypeScript 写插件的作者拿不到提示与检查**。
类型头部那段注释（"宿主不校验未知的贡献点名称，这是有意的"）说的是**运行期**的宽容，
不该变成**类型**上的缺失 —— 这两件事方向相反。

### 4.9 `notification` 权限的强制程度与 `rpc.rs` 注释口径不一致

**类别：** 缺陷（元数据与注释，不影响运行行为）

**现状。** 这一项权限的**文案**已经与实现对齐（`permissions.rs` 的 `label` 是「应用内通知」、`description` 明说「**不是系统级通知** —— 应用关闭时无法提醒用户」），但**强制程度**两处说法仍然相反：

| 位置 | 写的是 | 事实 |
| --- | --- | --- |
| `permissions.rs` 的 `enforcement`（以及 `metadata_snapshot_is_locked` 钉住的快照） | `Frontend` | **只描述了 in-process 那一条路径**。in-process 确实只有前端降级（`pluginRuntime.ts` 的 `pluginNotifications`）；但沙箱路径上 `rpc.rs` 的 `notify` 分支**真的会调 `require_permission(…, Notification)`**，那是一条 Rust 侧强制 |
| `rpc.rs` 在 `notify` 分支上的注释（475–477 行） | 这一项「在权限表里标的是 `host` 强制（与 `clipboard` 的 `frontend` 强制相反）」 | 与元数据的 `Frontend` **直接矛盾**：注释把 `Frontend` 说成了 `host` |

**影响。** 界面上的「已强制 / 未强制」标注以元数据为准，因此用户在安装确认页看到的是一项"前端强制"的权限，而它在沙箱路径上其实由后端强制；反过来，读 `rpc.rs` 注释的人会得到一个与元数据相反的前提。两处都不影响运行行为，但**它是"一条权限有两个检查层"这个模型还没有表达法**的直接症状。

**建议。** 两条路任选其一，但**不要停在中间态**：①把 `rpc.rs` 的注释改成 `frontend`（并注明"沙箱路径另有 Rust 检查"）；②扩展 `enforcement`，让它能表达"一层前端 + 一层后端"（这会同时动 Rust 类型、`metadata_snapshot_is_locked`、前端类型与界面，与 §4.1 末尾那条债同源）。**本轮只改文档，代码未动。**

文档侧已就地标注：[插件系统架构](../02-开发指南/插件开发/插件系统架构.md) 第 6.1 节、[清单文件参考](../02-开发指南/插件开发/清单文件参考.md) 第 4 节。

### 4.10 沙箱与数据层本轮核对后仍然成立的缺口

**类别：** 混合（未接入 / 文档缺口）

> **核对时点。** 这一节是按**当前工作树**逐条读代码写下的（`data_root.rs`、`background/plugins.rs`、`permissions.rs`、`types/plugin.ts`、`pluginRuntime.ts`、`sandbox.rs`、`data_dir.rs`）。核对过程中发现同一批里已有几项被并行改动修掉（沙箱 bundle 的前端守卫、`dataDir` 读侧上限、`serve_asset` 的资源上限、前端 `PluginPermission` 缺 `plugin-data`、`notification` 的文案、`reap_if_idle` 的空闲回收定时器），因此**它们不再列在这里**。下面三条是核对时仍然成立的。

**1. 插件数据根的换根只有读路径、没有写路径 —— 已处置（删掉死代码，改为文档化的手改）。** `data_root.rs` 的 `configured_root()` 与 `resolve()` 会被 `PluginManager::new` 调用，因此"配置的根"读得到；而写侧 `set_configured_root()` 曾经**没有任何调用方**（全仓只有那一处定义），也没有对应命令与界面。**本轮把它删掉了**，而不是留着"等以后接"：一个有实现、无调用方的函数在代码里与"已实现的能力"无法区分，读者会以为换根是产品提供的功能 —— 这正是本文件开头那条"不要停在中间态"的纪律要拦的东西。

> **换根现在是手改，而那是完整的一条路，不是残缺的。** 改 `plugin_data_root.json`（在 `app_data_dir()` 下）；`configured_root()` 照常读它，`resolve()` 会 `probe_writable` **验证**它，不可用就进 `DataRootStatus` 的"不可用"状态（而不是被当成"这个插件还没有数据"），界面显示的是解析出来的真实路径。`CONFIG_FILE` 上那条注释原本就是这么写的（"搬家时改这个小文件"）。
>
> **加一个设置界面是独立的工作**：它要先定"目录授权"的交互 —— 让用户选一个目录就要回答"这份授权属于谁、什么时候失效"，与 v1.5 里 `filesystem-scoped` 被推迟是同一类问题。（与[插件沙箱与数据-v2.0范围](../08-规划/插件沙箱与数据-v2.0范围.md) §7.2 第 4 条记的是同一件事。）

**2. 后台 Node 宿主的网络权限不成立。** `background/plugins.rs:87` 定义的 `NET_SCOPE_FLAG = "--allow-net"` 只用于**探测**；拉起子进程时（同文件 224–225 行）只 push 了 `--permission` 与 `--allow-fs-read=<插件目录>`，**从不传 `--allow-net`**。因此 `network` / `network-external` 在后台插件那一侧没有强制力（Node ≥25 上"不授予"才等于拒绝，Node 24 上那个 scope 根本不存在）。

> **更正一处容易读反的地方：这不是"宿主忘了传旗标"。** `BackgroundPluginStatus.netRestricted` 由"权限模型开着 **且** 该 scope 存在"算出，没探测到时报 `false`（＝"没被管住"）；拉起子进程时若发现管不住网络会留一条警告日志，插件详情页与启动日志**分别**说"已隔离"与"网络不受管"。也就是说它**已被如实报出**，缺的是强制本身。

**3. `后端命令参考.md` 的模块分节停在 76 条命令的时代（文档缺口）。** 该页只列了 auth / plugins / settings / net / sidebar / notifications / logging / updater 八个模块，`background` / `tray` / `memory` / `sandbox` / `overlay` 以及 plugins 模块此后补上的数据层与网络能力都没有进目录。总数已更正为实测的 **153 条**（`pnpm check:acl` 的输出），但**分节与逐条表格本身没有补**。

**4. `ctx.settings.onChange` 只在 in-process 存在，两个隔离位置都没有。** in-process 的 `pluginSettingsAPI` 有 `onChange(handler)`，因为宿主与插件同处一个 realm、回调是直接的。沙箱桥接层与后台宿主都**没有**它：要它有就得有一条宿主 → 隔离位置的"设置变了"推送通道，而宿主目前不发这个事件。

> **这是刻意留着的差异，不是遗漏。** 造一个永远不触发的 `onChange` 比没有它更坏 —— 作者会写它、然后等一个永不到来的回调，而按不下去的回调不会以任何形式报错。两个位置的注释里都写明了这一点（`sandbox-bridge.js` 的 `settings`、`background-host.mjs` 的 `settings`）。要做的话，先定那条推送通道，三处一起加。

### 4.11 性能三步仍未做，且**依赖清理这一半被 lockfile 卡住**

**类别：** 未实现（其中一半是环境限制，见下）

[插件沙箱与数据-v2.0范围](../08-规划/插件沙箱与数据-v2.0范围.md) §7 的第 2、3 步（入口 chunk 拆包、图标 chunk 收敛 + 清掉未使用的运行时依赖）仍然未做。本轮把**第 3 步的依赖清单查实了**，结论如下 —— 下一个动手的人不必再查一遍。

**已查实的未使用运行时依赖（三处，都在 `package.json` 的 `dependencies` 里）：**

| 包 | 证据 | 结论 |
| --- | --- | --- |
| `@tauri-apps/plugin-updater` | 全仓 `*.{ts,tsx,js,mjs,json,toml,rs}` 里**只有注释**提到它，没有一行 import；`capabilities/default.json` 的文件头明确写着 `updater:default` **is deliberately NO LONGER granted**，更新走自己的 Rust 命令 | 前端侧死依赖 |
| `@tauri-apps/plugin-shell` | 全仓对该包的引用**只有 `package.json` 自身那一行**；`src-tauri/Cargo.toml` 里也没有 `tauri-plugin-shell` | 完全未使用 |
| `chalk` | 只在 `scripts/colors.ts`（**构建脚本**）里 import，却在 `dependencies` 里 | 位置错（应在 `devDependencies`） |

**为什么本轮没有动它：** 改 `package.json` 的依赖必须**同步重生成 `pnpm-lock.yaml`**（本仓库用 pnpm + `pnpm-workspace.yaml`），否则 `pnpm install --frozen-lockfile` 会失败 —— 而那时候的表现是"CI 或发版构建起不来"，比留着三个未使用的依赖严重得多。本轮的作业环境**无法重生成 lockfile**：pnpm 起不了子进程（`spawn EPERM`），而用 npm 代跑会写出一个与 `pnpm-lock.yaml` 冲突的 `package-lock.json`。**手改 lockfile 不在选项里** —— 它是一份哈希与依赖图，手改出来的东西只有在 `--frozen-lockfile` 失败时才被发现。

**正确做法**（在有正常 pnpm 的环境里，一条命令）：

```bash
pnpm remove @tauri-apps/plugin-shell @tauri-apps/plugin-updater
pnpm add -D chalk          # 从 dependencies 挪到 devDependencies
pnpm check:scripts && pnpm tsc --noEmit
```

**第 2 步（`manualChunks` + 把设置面板挪出静态导入图）同样未做，原因是它必须用真实构建验证。** 改 `vite.config.ts` 的 `manualChunks` 与把 `SettingsDialog.tsx` 里 9 个设置分页改成 `React.lazy`，都属于"看起来对、跑起来错"的类型（懒加载缺 Suspense 边界、`manualChunks` 配错会造出循环 chunk），而判据只有构建产物与点开设置页这两件事 —— 两者都需要能起构建、能开窗口。**不要在没有构建验证的情况下改它。** 改动范围与根因分析见 v2.0 范围 §6.2（"这是改配置 + 挪边框的活，不需要动任何业务逻辑"）。

> 顺带记下一件已修的事，避免读者按旧记录去找：**"同一份插件在两个运行位置上降级语义不同"这条已经不成立**。`sandbox-bridge.js` 现在对 `plugin-data` 走与 in-process 同形的降级（`available` false、`list` 空、读写抛一句能照做的话），`settings.set` 在缺 `storage` 时抛的也是"这一次写入没生效"而不是权限模型的话。方法名也统一了（三处的设置接口都用 `getAll`，`all` 只是兼容别名）。

### 5.2 深色模式由全局工具类映射实现，而非组件级 `dark:` 变体

**类别：** 设计取舍

**现状。** 深色模式已实现，但实现方式与常见做法不同：没有在组件里逐个补 `dark:` 变体，而是在 `src/styles/global/dark-theme.css` 中用属性选择器匹配工具类名（`[class~="bg-white"]` 等），把它们映射到深色取值。整套规则都在 `:root.dark` 下，与 Tailwind 生成的工具类同优先级，依靠 import 顺序（在 `tailwindcss` 之后）取胜。主题由 `src/services/theme.ts` 管理，设置项为 `theme`（`light` / `dark` / `system`）。

**为什么这样选。** 决定性因素是插件：插件由第三方编写，不可能配合补 `dark:` 变体。若深色只靠组件内的变体实现，任何插件界面在深色模式下都会是白底黑字，与宿主割裂。因此宿主用一张全局映射表把**宿主自己用到过的**类名重定向到深色取值。

**但这张表管不到插件。** 插件在运行时注入，它的类名不在宿主构建期的扫描范围内，Tailwind 不会为它们生成规则，映射表也就无类可映射。**插件必须自带 `index.css` 并自行处理深色**（见[示例插件](../02-开发指南/插件开发/示例插件.md)第 5.6 节）。本节此前写作「全局映射让插件只要使用常规 Tailwind 工具类就能自动跟随主题」——**那句话是错的**，而且与同一仓库 `示例插件.md` 5.6 节、插件仓库 `docs/目录规范.md` 5.2 节的正确表述直接冲突。

**代价与风险。**

| 问题 | 说明 |
| --- | --- |
| 依赖 import 顺序 | `dark-theme.css` 若被移到 `@layer` 内或提前导入，覆盖会整体失效 |
| 新工具类需同步 | 引入新的颜色工具类（例如 `bg-slate-50`）时，必须在映射表中补一条，否则深色下会漏掉 |
| 层次表达受限 | 只能做「浅色值 → 深色值」的对应，无法表达只在深色下出现的视觉层次 |

**建议。** 短期维持现状；若后续引入语义化色彩令牌（`--surface`、`--surface-raised` 等），可以逐步把映射表替换为令牌引用，两者并不冲突。

### 5.3 主题的首帧来源是 localStorage 缓存

**类别：** 设计取舍

后端 `settings.json` 是主题的权威来源，但 WebView 在 JS bundle 求值前就会绘制一次，等后端返回再决定配色会让用户看到「先深后浅」的闪烁。因此 `index.html` 内联脚本会先读 `localStorage` 缓存来渲染首帧，随后由设置加载结果覆盖并回写缓存。

**影响。** 缓存丢失（清空 WebView 数据）只会让首帧闪一下，不会丢设置。这一行为在 `src/services/theme.ts` 的文件头有说明。

### 5.4 动画开关无法停用 JS 里手写的定时动画

**类别：** 设计取舍

「关闭界面动画」通过两条路径生效：根元素加 `.lc-reduce-motion`（停用 CSS 动画与过渡）、`MotionConfig reducedMotion="always"`（停用 framer-motion 动画）。但代码中仍有手写的 `setTimeout` / `setInterval` 驱动的变化（例如提示条的自动消失、启动界面的计时刷新），这些不受影响。

**影响。** 关闭动画后，提示条仍会在若干秒后消失，只是不再有淡出过渡。这属于合理行为，但不应被理解为「所有随时间变化的东西都停了」。
