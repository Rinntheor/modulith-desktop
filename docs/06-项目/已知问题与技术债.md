# 已知问题与技术债

本文记录当前代码中已确认的问题、未完成的能力与设计上的取舍。目的是让后续维护者不必重新发现它们。

分类说明：

| 类别 | 含义 |
| --- | --- |
| 缺陷 | 行为与预期不符，应当修复 |
| 未接入 | 代码存在但没有任何路径使用它 |
| 未实现 | 类型或界面已声明，但没有对应实现 |
| 设计取舍 | 有意的选择，需要时再重新评估 |

## 1. 导航机制

### 1.1 状态驱动的导航与路由代码并存

**类别：** 未接入

**现状。** 打开模块时只调用 `tabStore.openTab()`，由它更新标签状态；`Home` 据此渲染 `mountedTabs` 中的全部模块（仅激活的那个可见）。`SidebarContext.activeModule` 读的是 `tabStore.activeTab`，不再自己持有。模块**切换**不修改地址栏，代码库中也没有任何 `useNavigate`、`navigate()`、`<Link>`、`useParams` 或 `useLocation` 调用。

与此同时，`src/router/` 下存在一套路由设施，其中**并非全部是死代码**：

| 文件 | 状态 |
| --- | --- |
| `Router.tsx` | 生效：声明 `/`、`/home`、由 `DynamicRouter.getRoutes()` 生成的动态路由，以及兜底 404 |
| `dynamicRouter.ts` | **活代码**：由 `Router.tsx` 以值导入方式引用。`getRoutes()` 被使用；其余六个静态方法（`getRouteByModuleId`/`getRouteTree`/`isValidRoute`/`addRoute`/`removeRoute`/`clearRoutes`）无调用方 |
| `contexts/RouteContext.tsx` | 死代码：`RouteProvider` 与 `useRoute` 没有任何引用方 |

**影响。**

- `Router.tsx` 中由 `DynamicRouter.getRoutes()` 生成的 `<Route>` 列表**确实被注册生效**，但它只包含启动时刻的内建模块快照，不含插件在运行期注册的模块。由于导航不经过 URL，这一点在日常使用中不会暴露；但若用户手动修改地址或依赖深链接，插件模块会落到 404。
- `RouteContext.tsx` 属于死代码。
- `window.history.back()` 出现在 `Router.tsx` 的 404 页与 `ModuleRenderer.tsx` 的「模块未找到」页。既然模块导航不进历史栈，这两个按钮的语义并不成立。

**建议。** 在两种方向中明确选择其一：

1. 让导航真正走路由：侧边栏切换时调用 `navigate(path)`，`DynamicRouter` 在编目变化时重新生成路由，并由 `RouteContext` 提供当前路由信息。这样深链接、前进后退可与浏览器行为统一。
2. 确认继续使用状态驱动：删除 `RouteContext.tsx`，并在 `Router.tsx` 中移除动态路由生成逻辑，避免两套机制并存造成误解。**注意顺序：** `dynamicRouter.ts` 不能先删 —— 它被 `Router.tsx` 以值导入方式引用，且被 `types/core.ts` 再导出（`RouteConfig`）。必须先摘掉 `Router.tsx` 里对 `getRoutes()` 的调用与 `types/core.ts` 的再导出，才能删除该文件。

在做出选择前，`SidebarContext` 中自建的前进后退历史栈（`goBack`、`goForward`）需要一并考虑：如果改用路由，这套历史管理应当交给路由层。注意它与标签页是两套独立的顺序 —— 历史栈记录**访问顺序**（用户实际去过哪里），标签顺序是**用户拖出来的排列**，二者刻意不合并。历史栈不持久化，重启后从空开始。

### 1.2 动态路由的初始化时机

**类别：** 缺陷（仅在采纳路由方案时成立）

`dynamicRouter.ts` 在模块顶层调用 `DynamicRouter.initialize()`。该文件在应用启动时被导入，此时插件尚未加载，因此生成的路由不含插件模块。即使采纳上述第 1 种方案，也需要把初始化改为在 `moduleCatalog` 变化时重新执行。

## 2. 后端遗留代码

### 2.1 两个不会被编译的目录

**类别：** 未接入

**现状。** 磁盘上存在以下目录：

```
src-tauri/src/sidebar/           commands.rs, config.rs, mod.rs
src-tauri/src/module_config/     commands.rs, mod.rs
```

`lib.rs` 只声明了 `prelude`、`core`、`modules` 三个模块，因此这两个目录不是编译单元的一部分，其中的代码永远不会被执行。

**影响。** 它们与 `modules/sidebar/` 功能重叠，容易让阅读者误以为存在多套实现。`sidebar/commands.rs` 中还保留着对 `crate::sidebar::config` 的引用，但该引用同样不会被编译。

**建议。** 确认没有外部脚本或工具依赖这些路径后删除。删除前建议先执行一次全局检索，确认没有构建脚本引用它们。

### 2.2 模块 ID 命名不统一

**类别：** 设计取舍

**现状。** 前端模块 `id` 使用小驼峰（`dashboard`、`plugins`），后端模块 `id` 使用蛇形（`sidebar`、`plugins`、`auth`、`settings`）。两者通过各自的目录独立管理，没有强制的同名要求。

**影响。** 同一功能的模块在前后端名称形式不同，排查问题时需要在两种命名间转换。

**建议。** 保持现状是可接受的，因为后端 `id` 必须满足蛇形以正确生成 Rust 类型名。若要统一，只能把前端改为蛇形，代价是 `module.toml` 中 `path` 与 `id` 的关系变得不直观。另一种选择是在文档中明确记录两者的映射关系，[模块开发](../02-开发指南/模块开发.md)第 4 节已作说明。

## 3. 未使用的框架能力

以下能力已实现但当前没有任何调用方。它们本身不是缺陷，但会让人误以为系统具备相应行为。

| 能力 | 位置 | 现状 |
| --- | --- | --- |
| `Module::stop()` | `core/module.rs` | `lib.rs` 只调用 `setup` 与 `start`，从不调用 `stop` |
| `Module::dependencies()` | `core/module.rs` | 无模块声明依赖，拓扑排序退化为任意顺序 |
| `Module::handle_event()` | `core/module.rs` | 无模块实现该回调 |
| `ModuleRegistry::broadcast_event()` | `core/registry.rs` | 无调用方 |
| `createLazyComponent().preload()` | `utils/lazyLoad.ts` | 由启动流程的 `preload` 步骤调用（已不再是死代码） |
| `src/types/core.ts` | 整个文件 | 无引用方 |

**类别：** 未接入

**建议。** 按用途分别处理：

- 生命周期钩子（`stop`、`handle_event`、`broadcast_event`）属于框架预留能力，若要保留应在文档中标注为「预留」，或补上实际调用点。其中 `stop` 的缺失值得注意：如果将来有模块需要在关闭前释放资源，当前框架没有执行时机。
- `preload` 若要发挥作用，应在模块首次渲染前调用，以减少切换时的等待。
- `types/core.ts` 建议删除，其内容与 `types/module.ts` 重叠。

### 3.1 模块启动顺序不确定

**类别：** 缺陷（潜在）

`ModuleRegistry` 用 `HashMap<String, Box<dyn Module>>` 存储模块，`all()` 返回 `self.modules.values()`。`lib.rs` 按该顺序调用各模块的 `start`，因此启动顺序取决于哈希布局，每次运行可能不同。

当前五个模块的 `start` 都是默认空实现，所有初始化都在 `setup` 里完成，因此没有实际影响。但一旦某个模块的启动逻辑依赖另一个模块已启动，就会出现难以复现的偶发故障。

**建议。** 在 `setup_all` 中记录拓扑序并提供一个按序迭代的方法，让 `start` 也按依赖顺序调用。或者统一在 `setup` 中完成初始化，避免依赖 `start` 的顺序。

## 4. 插件系统

### 4.1 权限声明仍有过半未强制

**类别：** 部分实现

**现状。** `PluginManifest.permissions` 是 `Vec<PluginPermission>`，枚举包含 11 个取值。当前真正被检查的是四个：

| 权限 | 检查位置 | 检查层 |
| --- | --- | --- |
| `network` | 发起 HTTP 请求前 | Rust |
| `network-external` | 目标不是回环地址时 | Rust |
| `notification` | 调用 `ctx.notifications` 时 | 前端 |
| `plugin-communicate` | 调用 `ctx.events` 时 | 前端 |

其余取值（`storage`、`clipboard`、`filesystem-read`、`filesystem-write`、`filesystem-scoped`、`native-module`、`dev-tools`）不影响任何行为。

**本轮进展。** `notification` 与 `plugin-communicate` 从「声明了但无效」变成了真正生效 —— 前者原本连接口都不存在（`PluginNotificationAPI` 只有类型声明，`createContext()` 从未提供它），现在已实现；后者是新增的跨模块事件总线。两者的拒绝方式是**降级为空实现 + 控制台警告**，而不是抛错：它们是可选的附加能力，让插件因为一个没声明的选项而整体加载失败，代价大于收益。

**仍未解决。** 文件系统与剪贴板相关权限依然只是意图声明。`storage` 的特殊情况值得单独说明：它始终可用，因为插件私有存储本身按 ID 隔离，不存在「越权访问别的插件数据」的路径，因此没有强制点可加。

**影响。** 用户可以声明任意权限而不获得相应能力。权限列表整体上仍更接近意图声明而非访问控制，对用户判断插件风险有误导性。

**建议。** 两种方向：

1. 为其余权限补上强制点。这需要先明确能力边界，例如 `filesystem-read` 允许访问哪些目录 —— 而这在当前「插件与宿主同进程」的架构下无法可靠实现（插件可直接用 `fetch` 或 `invoke` 绕过）。
2. 在界面与文档中明确标注当前哪些权限生效，避免用户高估隔离强度。文档已在[插件系统架构](../02-开发指南/插件开发/插件系统架构.md)第 6 节与[清单文件参考](../02-开发指南/插件开发/清单文件参考.md)第 4 节作此说明。

**为什么前端检查也是有效的。** `notification` 与 `plugin-communicate` 的实现完全在前端（通知要落盘、事件不出进程），没有对应的后端命令可以绕过，因此前端就是唯一执行点。这与网络权限不同 —— 网络请求由 Rust 发起，所以检查必须在 Rust 侧。

### 4.2 sandboxLevel 完全未执行

**类别：** 未实现

`SandboxLevel` 有 L0 至 L3 四档，包含从「无网络、无文件系统」到「完全访问」的描述。该字段会被解析、序列化并保留默认值 L1，但**没有任何代码读取它**。填写不同等级不会改变插件行为。

**建议。** 要么实现它（例如根据等级限制可用服务），要么在类型与清单文档中明确标注为预留字段，避免用户误以为可以对插件分级管控。

### 4.3 无代码签名

**类别：** 未实现

插件包没有签名机制，清单中也没有签名字段。安装时无法验证来源与完整性。

**影响。** 用户无法区分官方插件与第三方修改版。配合 4.4 所述的隔离缺失，安装插件的风险等同于运行未知程序。

**建议。** 引入签名需要先确定密钥分发与信任模型，属于较大的独立工作。在实现之前，应在插件管理界面显著提示风险。

### 4.4 插件与宿主共享同一 JavaScript 上下文

**类别：** 设计取舍

插件代码通过注入 `<script>` 执行，与宿主处于同一个 WebView 与同一个 JavaScript 上下文。因此：

| 项目 | 说明 |
| --- | --- |
| 全局对象 | 插件可访问 `window` 上的任意内容 |
| 会话令牌 | 插件可读取 `sessionStorage` 中的 `modulith.auth.token` |
| 插件之间 | 没有相互隔离 |
| 宿主数据 | 插件可读取宿主已加载的数据 |
| 网络 | 权限检查只约束经由 `ctx.http` 的请求，插件可用常规 Web 手段绕过 |

**影响。** 认证模块的会话守卫能防止命令被随意调用，但无法在恶意插件面前保护令牌本身。因此当前模型中**插件的信任级别等同于应用本身**。

**已有与缺失的隔离手段。** 需要区分「故障隔离」与「安全隔离」两件不同的事：

| 层级 | 机制 | 位置 | 能防住什么 |
| --- | --- | --- | --- |
| 渲染 | `AppErrorBoundary` | `src/components/AppErrorBoundary.tsx` | 任何未被下层接住的渲染错误导致整窗白屏 |
| 渲染 | `ModuleErrorBoundary` | `src/components/ModuleRenderer.tsx` | 插件界面渲染崩溃影响宿主与其它模块 |
| 渲染 | `PluginModulePending` | `src/components/ModuleRenderer.tsx` | 把「插件尚未加载完」误报为「模块不存在」 |
| 异步 | 全局错误监听 | `src/services/globalErrorHandlers.ts` | 事件处理器 / 定时器 / 未处理 Promise 拒绝静默消失 |
| 加载 | 逐插件超时 | `src/services/pluginRuntime.ts` | 一个慢插件拖累其余插件的加载 |
| 加载 | 加载失败标记 | `src/services/pluginRuntime.ts` | 坏的插件静默失败（现在会显示为「异常」） |
| 存储 | 按插件 ID 命名空间 | `src-tauri/src/modules/plugins/manager.rs` | 插件之间互相读写存储数据 |
| 资源 | 插件目录内路径约束 | `src-tauri/src/modules/plugins/manager.rs` | 插件读取自己目录之外的文件 |

**仍然缺失的（安全隔离）。** 上述机制只解决「一个插件崩了不影响别人」，不解决「一个恶意插件能做什么」：

- 没有进程级或 WebView 级隔离——插件代码与宿主同线程同上下文，可以读写宿主的任何全局对象；
- 插件 bundle 顶层的同步死循环**无法被中断**。JS 是单线程的，超时只能保证后续插件不被拖累，无法救回已经卡住的主线程；
- 插件可以直接 `invoke` 任意后端命令，后端只能靠会话校验兜底，而这拦不住已经拿到令牌的同源 JS。

**建议。** 真正的安全隔离需要独立进程或独立 WebView 实例，属于架构级改动。在此之前，应把「只安装可信来源的插件」作为明确的产品约束告知用户，而不是依赖权限系统提供保护。

### 4.5 无多版本共存与回滚

**类别：** 未实现

插件按 `<app_data>/plugins/<id>/<version>/` 归档。同一 ID 安装相同版本时会直接覆盖，旧版本不会被回收，也没有切换版本的机制。

**影响。** 插件升级后若出现问题，用户无法回退，只能重新安装旧版本包（如果还留着）。

**建议。** 若需要该能力，应在安装流程中保留上一版本并增加回滚入口，同时定义清理策略避免磁盘无限增长。

### 4.6 无市场与更新检查

**类别：** 未实现

`PluginRepository` 只是清单中作者自行填写的 `{type, url}` 元数据，没有仓库客户端、没有更新检查、没有在线检索。插件管理界面只有「全部 / 已启用 / 已禁用 / 异常」四个筛选，没有市场页。

`activationEvents` 与 `contributes` 字段会被解析并保留，但没有任何消费方。

**建议。** 这属于尚未开始的能力，不是缺陷。文档中不应把它描述为已实现——此前的插件文档曾这样描述，已在本轮整理中修正。

### 4.7 恢复码：没有历史记录，也不记「用掉的是哪一枚」

**类别：** 设计取舍

当前一次生成 3 枚恢复码（`RECOVERY_CODE_COUNT`），`auth.json` 只保存它们的 Argon2id 哈希数组（`recoveryHash`）与生成时间（`recoveryCreatedAt`），**不保留任何历史**。

**行为与限制。**

| 项目 | 当前行为 |
| --- | --- |
| 重新生成 | 整套作废，换发新的 3 枚 |
| 用掉一枚 | **只删除那一枚**，其余保留（这是刻意的，见下） |
| 用掉后是否换发 | **不换发**。重置成功后只减少一枚 |
| 历史 | 不记。界面只能显示生成时间与剩余枚数 |
| 审计 | 登录日志记录命中的序号（`recovery-reset#2`），但那只在日志里，不是恢复码历史 |

**「只删除用掉的那一枚」是安全性质，不是偷懒。** 早期实现是「重置成功后整套换发」。它有致命缺陷：若攻击者先用一枚恢复码重置了访问密钥，整套就会换成**攻击者手里**的新码，而用户手中的纸全部作废——攻击者不仅拿到访问权，还把合法用户永久锁在门外。只删除被用掉的那一枚之后，用户**始终保留夺回控制权的能力**。

代价是：不再有「一次重置就自动清空所有旧纸」的行为。要主动作废旧纸，必须去「设置 → 安全 → 密钥恢复」点「重新生成」。这是**有权衡的选择**——主动作废优于被攻击者替你作废，但确实留下一段窗口：若攻击者拿到了纸却还没用，在你手动重新生成之前它们一直有效。

**另一个限制：** 若用户把多张历史纸质备份混在一起，只有最新那一批有效，而界面上看不出「哪张是旧批」——只能靠 `recoveryCreatedAt` 自行比对。

**老用户升级路径。** 在引入恢复码之前就已设置访问密钥的用户，其 `recoveryHash` 为空。此时解锁界面不会显示「忘记访问密钥」入口（那会是个死胡同），并明确提示「本机尚未生成恢复码」。已解锁的用户可在「设置 → 安全 → 密钥恢复」补生成。

**建议。** 没有历史记录这一点可以考虑改进：记录「已用掉的枚数与时间」能在用户怀疑凭证泄露时提供线索。当前不做，是因为它需要新增持久化字段与界面，收益不足以justify。

## 5. 前端

### 5.1 没有测试框架

**类别：** 未实现

`package.json` 中没有测试脚本，也未引入 Vitest、Jest 或 Playwright。前端的验证手段目前是类型检查、临时脚本与手工验证。

后端有较为完整的单元测试（涵盖认证加密、插件解压安全、设置校验、应用信息等），因此缺口主要在前端的纯逻辑部分，例如启动进度计算、模块编目合并、插件资源注入与清理。

**建议。** 优先为无副作用或副作用易模拟的模块补测试：

| 目标 | 理由 |
| --- | --- |
| `bootProgress.ts` | 已是零依赖纯函数，测试成本最低 |
| `moduleCatalog.ts` | 注册与卸载逻辑有明确的输入输出 |
| `utils/validators.ts` | 纯函数 |

`bootProgress.ts` 的文件头注释提到「可以被独立验证」，但仓库中没有对应的测试文件，说明这一意图尚未落地。

### 5.2 深色模式由全局工具类映射实现，而非组件级 `dark:` 变体

**类别：** 设计取舍

**现状。** 深色模式已实现，但实现方式与常见做法不同：没有在组件里逐个补 `dark:` 变体，而是在 `src/styles/global/dark-theme.css` 中用属性选择器匹配工具类名（`[class~="bg-white"]` 等），把它们映射到深色取值。整套规则都在 `:root.dark` 下，与 Tailwind 生成的工具类同优先级，依靠 import 顺序（在 `tailwindcss` 之后）取胜。主题由 `src/services/theme.ts` 管理，设置项为 `theme`（`light` / `dark` / `system`）。

**为什么这样选。** 决定性因素是插件：插件由第三方编写，不可能配合补 `dark:` 变体。若深色只靠组件内的变体实现，任何插件界面在深色模式下都会是白底黑字，与宿主割裂。全局映射让插件只要使用常规 Tailwind 工具类就能自动跟随主题。

**代价与风险。**

| 问题 | 说明 |
| --- | --- |
| 依赖 import 顺序 | `dark-theme.css` 若被移到 `@layer` 内或提前导入，覆盖会整体失效 |
| 新工具类需同步 | 引入新的颜色工具类（例如 `bg-slate-50`）时，必须在映射表中补一条，否则深色下会漏掉 |
| 层次表达受限 | 只能做「浅色值 → 深色值」的对应，无法表达只在深色下出现的视觉层次 |

**建议。** 短期维持现状；若后续引入语义化色彩令牌（`--surface`、`--surface-raised` 等），可以逐步把映射表替换为令牌引用，两者并不冲突。

### 5.3 主题的首帧来源是 localStorage 缓存

**类别：** 设计取舍

后端 `settings.json` 是主题的权威来源，但 WebView 在 JS bundle 求值前就会绘制一次，等后端返回再决定配色会让用户看到「先深后浅」的闪烁。因此 `index.html` 内联脚本会先读 `localStorage` 缓存来渲染首帧，随后由设置加载结果覆盖并回写缓存。

**影响。** 缓存丢失（清空 WebView 数据）只会让首帧闪一下，不会丢设置。这一行为在 `src/services/theme.ts` 的文件头有说明。

### 5.4 动画开关无法停用 JS 里手写的定时动画

**类别：** 设计取舍

「关闭界面动画」通过两条路径生效：根元素加 `.lc-reduce-motion`（停用 CSS 动画与过渡）、`MotionConfig reducedMotion="always"`（停用 framer-motion 动画）。但代码中仍有手写的 `setTimeout` / `setInterval` 驱动的变化（例如提示条的自动消失、启动界面的计时刷新），这些不受影响。

**影响。** 关闭动画后，提示条仍会在若干秒后消失，只是不再有淡出过渡。这属于合理行为，但不应被理解为「所有随时间变化的东西都停了」。

### 7.4 恢复码的复制、打印与两步流程

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 复制出来的恢复码是一大串、看不出分组，而且只能选中某一段 | 分组被渲染成了**独立的 `<span>` 元素**，因此"选中一部分再复制"只能拿到一组；而复制按钮写入的又是去掉连字符的裸串（`ABCD…`），与屏幕上带连字符的呈现不一致 | 显示改为**一整段可自然选中的文本**，分组通过等宽字体与窄间隔体现，而不是独立可选元素；复制按钮改为写入**完整原文（含连字符）**，与屏幕所见一致。后端 `normalize_recovery_code` 本来就会忽略连字符，因此粘贴时带不带都可用 |
| 无法把恢复码保存成 PDF | 项目没有 PDF 依赖，装一个属于新增第三方依赖 | 改用系统打印对话框的「另存为 PDF」：新增 `RecoveryPrintSheet` 渲染一张打印件，`index.css` 的 `@media print` 段在打印时隐藏屏上一切、只显示它。不新增依赖，产出的是真正的 PDF |
| 用恢复码重置时，三个输入框放一起，出错却总聚焦第一个，用户以为恢复码抄错了 | 三步合一时错误提示与 `autoFocus` 都落在表单第一个输入框上 | 拆成两步（详见下） |

打印实现有三个必须记住的约束，都写在 `index.css` 的注释里：

1. `@media print` **不能放进 `@layer`**——分层样式优先级低于未分层样式，而这些规则要覆盖 `dark-theme.css` 里未分层的深色映射；一旦被包进 `@layer`，打印件会带着深色底色输出（费墨且难读）。
2. 必须放在 `dark-theme.css` 之后（文件末尾），两者优先级相同，靠后加载取胜。
3. 显式强制浅色（`color-scheme: light` + 重写颜色），不能指望深色模式下自动输出白底。

**两步恢复流程。** 新的交互是：进入恢复界面后**只有一个输入框**（恢复码），核验通过才进入第二步（两个新密钥输入框）。这样每个屏幕只有一个待完成的动作，错误提示必然指向真正出错的那项。

后端配套拆成两个命令：`verify_recovery_code` 只核验、**不修改任何状态**，通过后签发一个 10 分钟有效的一次性令牌；`reset_access_key_with_recovery_code` 消费令牌并设置新密钥。

令牌在内存中只保存**命中的那一枚恢复码的下标**（`matched_index`），不保存码原文，也不保存任何摘要。原因有两层：后端只存 Argon2id 哈希，每次哈希结果都不同，无法事后逐字节比对；而把原文留在内存里等于多存一份明文凭据。保存下标则足够——第二步只作废这一枚。令牌单次使用、10 分钟过期、签发时顺手清理过期条目，重置成功后用户改由新密钥进入。这**不构成额外攻击面**：拿到令牌需要先通过恢复码核验，而核验成功后本来就能直接重置。

（早期实现保存的是「归一化恢复码的 SHA-256 摘要」，但下游没有任何代码使用它——它既不能定位要作废哪一枚，也无法被校验。这是一处从旧设计残留下来的死数据，后来改为 `matched_index`。）

### 7.5 恢复码改为「多枚独立短码」+ 对比度与卡住问题

上一轮把恢复码做成**一枚 32 字符的长码、按 4 字符分组显示**。这个形态本身有歧义，本轮推翻重做。

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 用户把一整串长码读成"多个恢复码"，只输入其中一组，于是每次都报错 | **形态歧义**：一整串按组分隔的字符既像一个码，也像几个码，用户无法自行判断该输整串还是输一组 | 改成**互不相干的短码**（每枚 20 字符，分 4 组），列表里一行一枚、带序号、各带独立复制按钮。一行就是一个完整凭据，不存在"要不要全输"的疑问 |
| 「复制完整恢复码」「存为 PDF / 打印」和提示文字太淡，几乎看不见 | 这几个元素位于深色授权界面上，我用了 `text-gray-100` / `text-emerald-200` 这类低对比度颜色，且叠在已带透明度的底色上 | 全部提到 `text-white` / `text-gray-200` 以上，按钮改用实色底配 `font-semibold`，边框也加重 |
| 用恢复码真的重置成功后，点「我已保存，继续」直接卡在那个界面 | `finishIssuedCode` 只做了 `refreshAuth()`，把"界面该切到哪一屏"完全交给 boot 状态机。一旦 boot 因为任何原因没有推进（或 `refreshAuth` 抛错被静默吞掉），界面就停在 `created` 模式 —— 而这个模式只渲染恢复码面板，于是留下一个空白面板 | 补两件事：**显式把 mode 切回 `unlock`** 作为兜底，并对 `refreshAuth` 加 try/catch，失败时把原因显示出来而不是吞掉 |

**短码的语义**（与 GitHub / Google 的备份码一致）：

- 每枚各能用一次；忘记密钥时输入**任意一枚可用**的即可。
- 丢了几枚还有其余可用，不必因为抄漏一枚就作废全部。
- 单枚 100 bit 熵。多枚合计**不等于** 100×N bit —— 攻击者只需猜中任意一枚，因此有效强度由单枚决定，这仍远超暴力搜索能力。
- 审计日志记录命中的是第几枚（`recovery-reset#2`），便于排查同一张纸被反复使用。
- **用掉一枚只作废那一枚，其余保留**；重新生成才作废整套。原因见 4.7 节。

**枚数后来从 8 调整到 3。** 理由是枚数越多列表越长、收益递减，而 3 枚足以覆盖「抄漏一枚」与「分两处存放」这两件真实会发生的事。调整时有两个只在 8 枚下成立的测试硬编码了 `codes[3]` / `codes[5]` 之类下标，已改为取最后一枚，以后改数量不会再让测试误报。

**升级路径（必须记住的一点）。** `recoveryHash` 从 `Option<String>` 变成 `Vec<String>`，旧值无法解析。这里刻意**不让整个 `auth.json` 解析失败**——那会连访问密钥一起回落到默认值，用户会被要求重新设置密钥，等同于数据灾难。`config::load_from_with_reason` 的策略是：先尝试"只移除恢复码字段"后重新解析，成功则只清除恢复码、保留密钥/设备/日志，并立刻回写文件。因此升级后用户只需重新生成一套恢复码。

**顺带修正。** 归一化的最小输入长度从 16 降到 12：原来的阈值偏高，用户抄漏一组时会得到"格式不对"而不是"恢复码不正确"，后者才准确。

### 7.6 产品改名、版本转正、标识重做与主题配色

**产品改名 LoopCore → Modulith Desktop（1.0.0）。**

| 项目 | 旧 | 新 |
| --- | --- | --- |
| 显示名 | `Loop Core` / `LoopCore` | `Modulith Desktop`（简称 `Modulith`） |
| 版本 | `0.3.0`（`dev`） | `1.0.0`（`stable`） |

| npm / Cargo 包名 | `loopcore` | `modulith-desktop` |

| 插件宿主对象 | `window.LoopCore` | `window.Modulith` |
| 常量 | `LOOPCORE_VERSION` | `MODULITH_VERSION` |
| 存储键 | `loopcore.theme` / `loopcore.auth.token` | `modulith.theme` / `modulith.auth.token` |

**`engines.loopcore` 刻意保持不变**（插件清单的契约字段名，不是产品名）。改它会让所有已发布插件的清单解析失败、安装被拒。

**应用标识符变更会导致既有数据「消失」。** Tauri 不会在 identifier 变化时迁移数据，新目录是空的。因此访问密钥、恢复码、已装插件、侧边栏配置都需要重建。数据仍留在旧目录里，可手动找回。这是改名的一次性代价，已经用户知情同意。

**标识符里的下划线是非法字符，会让打包直接失败。** 改名时曾写成 `com.metazero_tsip.modulith`，保留了下划线，结果 `pnpm tauri build` 在读取配置阶段就报错：

```
The bundle identifier "com.metazero_tsip.modulith" set in `"tauri.conf.json" identifier`.
The bundle identifier string must contain only alphanumeric characters (A-Z, a-z, and 0-9),
hyphens(-), and periods (.).
```

Tauri 对 identifier 只允许**字母数字、连字符、句点**三种字符。下划线不在其中，而它在反向域名式写法里看起来很自然（`metazero_tsip` 是用户名），因此容易写错。这个校验发生在构建早期，`pnpm tauri dev` 同样会失败。

现取值 `com.metazero-tsip.modulith`，即把下划线换成连字符。附带的一次性后果：数据目录从 `%APPDATA%\com.metazero_tsip.modulith` 变为 `%APPDATA%\com.metazero-tsip.modulith`，需要重新设置访问密钥。这也是本次改名周期内第二次因 identifier 变动清空数据 —— 属于命名问题的连带成本，不是设计取舍。

**标识重做（三次迭代，前两版都推翻了）。**

### 7.7 标签页、全局搜索与通知系统

本轮针对的是一个此前没有被解决的目标：**防止注意力中断**。在多个功能之间切换的真正成本不是「点一下侧边栏」，而是切走再切回时必须重建现场 —— 滚动位置、未提交的表单、正在编辑的草稿全部丢失，而重建需要主动回忆「我刚才做到哪了」。把功能集中到一个外壳里只是必要条件，状态保持与注意力路由才是充分条件。

#### 模块标签页与保活

| 项目 | 说明 |
| --- | --- |
| 状态归属 | `tabStore` 是「当前显示哪个模块」的唯一来源；`SidebarContext` 不再自己持有 `activeModule`，而是读它 |
| 为什么改归属 | 同一个模块可能被侧边栏、标签栏、命令面板三条途径激活。各自维护一份必然漂移，表现为「点了侧边栏但标签高亮没变」 |
| 惰性挂载 | 标签只在其**首次被激活**时挂载，之后不再卸载。重启恢复十个标签不会一次挂载十个模块 |
| 隐藏方式 | `absolute inset-0 + visibility:hidden`，**不是** `display:none` —— 后者让元素失去盒子，多数浏览器随之丢掉 `scrollTop`，「滚动位置保留」这个目标就落空了 |
| 关闭语义 | 允许关到零标签并渲染空态，不自动回落。强行回落会让「关掉最后一个标签」看起来毫无反应 |
| 上限 | 12 个（前后端各有一份常量，必须一致）。达到上限时**拒绝并提示**，而不是淘汰已打开的标签 |
| 生命周期 | `openTabs` 与 `activeTab` 随设置持久化（`settings.json`），重启后恢复 |

`SidebarContext` 的历史栈与标签顺序是两回事，刻意分开：标签顺序是用户拖出来的排列，历史顺序是他实际去过的地方。混在一起会让「后退」跳到标签栏上的相邻位置，那不是用户期望的语义。

#### 后台存活管理

保活带来一个必须一起解决的问题：切走的标签不卸载，它的定时器、轮询与订阅会照常运行。宿主对此**提供感知，不提供强制**。

`useModuleActive()` 返回「该标签是否激活**且**窗口是否可见」。宿主无法代为暂停模块的后台工作 —— JS 里拿不到模块创建的 `setTimeout` / `setInterval` 句柄，重写全局定时器会影响包括宿主与 React 在内的所有代码。因此这是一个约定：模块自己在 `useModuleActive()` 为 false 时停掉后台工作。

这条约定目前**只对愿意遵守的模块生效**，没有强制机制。对插件同样如此，所以一个写得不负责任的插件可以在后台持续消耗资源。这一点在插件系统架构第 6.2 节标注为「资源限额：无内存或 CPU 限制」。

#### 全局搜索与命令面板

`commandRegistry` 提供命令注册表，`searchCommands` 负责匹配。模块类条目**不注册进表**，而是在搜索时从目录派生 —— 目录是动态的，镜像成命令列表就需要一套同步逻辑，而同步逻辑正是本项目反复踩坑的地方（见 `useModuleList` 的注释）。派生是纯函数，永远与目录一致。

打分规则与理由：完全相同 1000 分、前缀 800、包含 500、子序列 200 起。子序列匹配是模糊搜索的核心（输入 `dsh` 命中 `dashboard`），但它必须排在精确匹配之后，否则输入完整模块名时会被一堆松散匹配挤下去。最近使用过的命令额外加权，因为重复打开同一个模块时不该重新输完整名字。

#### 通知系统

后端新增 `notifications` 模块（7 个命令，`notifications.json`，上限 200 条）。写入、读取与裁剪策略见该模块源码注释。

三个值得记录的决定：

| 决定 | 理由 |
| --- | --- |
| 命令全部返回「当前完整列表」而不是被改动的那一条 | 只返回一条会让前端必须自己维护「新条目插到哪、合并键命中时改哪条、裁剪时删哪些」三处逻辑，与后端保持一致才能工作，一旦漂移就是界面与磁盘不一致。上限 200 条，多传几十 KB 换「前端整个替换缓存」是划算的 |
| `dedupeKey` 同键未读合并为一条并计数 | 模块很容易在重试循环里连续产生同一条通知（例如「网络不可用」），没有它通知中心会被同一条信息刷满，用户反而看不到真正重要的那条 |
| 错误级提示不自动消失 | 出错时用户需要读完再决定怎么办，3 秒后自己跑掉会让人怀疑「刚才是不是弹了什么」 |

`toast.ts`（不持久化的一次性反馈）与 `notifications.ts`（持久化的事件记录）刻意分成两个系统：把「已复制」写进磁盘并在通知中心留一条记录是明显的噪音；而把「插件加载失败」做成 3 秒就消失的提示则会让用户错过它。

**仍未实现：系统级通知。** 那需要引入 `tauri-plugin-notification` 依赖，当前版本不新增依赖，因此应用关闭时无法提醒。`notification` 权限的说明也已从「系统通知」改为「应用内通知」，避免名实不符。

#### 跨模块事件总线

`eventBus` 让模块之间可以协作（任务模块的待办出现在仪表盘上）。同步投递、按来源批量注销、主题名白名单字符集，理由都写在源码注释里。需要 `plugin-communicate` 权限。

它带来的是「模块之间可以协作」，**不是**「模块之间互相隔离」—— 总线上没有权限隔离，声明了权限的插件可以订阅任意主题。

#### 保活带来的行为变化

保活不只是「状态不丢」，它还改变了模块的生命周期语义，模块作者需要知道：

| 变化 | 说明 |
| --- | --- |
| 入场的错峰动画只播一次 | 以前每次切到模块都会重挂载，`framer-motion` 的 stagger 动画会重播；现在只在首次挂载时播一次。这消除了切换时的动画闪烁，但依赖「每次进入都播动画」来提示状态的模块需要改用别的方式 |
| 挂载副作用只执行一次 | `useEffect(..., [])` 里的初始化（拉数据、建订阅）不再随每次切换重跑。这对性能是好事，但「每次进入都刷新一遍」的旧假设不再成立 |
| 后台期间组件仍在运行 | 定时器、订阅、动画都会继续。需要暂停的后台工作要用 `useModuleActive()` |
| 卸载时机与关闭标签对齐 | 在此之前「离开模块」等于卸载；现在只有关闭标签或刷新才会卸载，因此清理逻辑（`useEffect` 的 return）会推迟到那时才执行 |

对插件而言，第二条与第三条影响最大：插件此前可以假设「用户每次打开模块都是一次全新的执行」，现在必须把初始化与刷新分开考虑。

#### 本轮仍未解决的问题

诚实记录，避免下一个人以为这些已经做过了：

| 问题 | 现状 |
| --- | --- |
| 模块保活没有内存上限之外的淘汰策略 | 上限 12 个标签，超过则拒绝；不会根据实际内存占用调整 |
| 后台工作依赖模块自律 | 无强制暂停机制，见上文 |
| 搜索不搜模块**内容** | 只搜模块名、子模块名与宿主/插件命令。功能多起来之后「我知道有这个功能但不知道在哪个模块」这类问题仍未完全解决 |
| 搜索无结果时面板直接消失 | 没有「无匹配项」的提示。当前的处理是「结果为空则不显示面板」，用户看到的是一片安静。补一个空态提示是明确可做的小改进 |

### 7.8 审阅修复：构建链路、插件 ID 路径穿越与外壳依赖

本轮由一次独立审阅触发：逐条核对「文档声称」与「代码实际」，把不符的部分修掉或如实记录。**其中前两项是真实缺陷，不只是文档问题。**

#### 前端类型检查失败，发布构建链路是断的

| 项目 | 说明 |
| --- | --- |
| 现象 | `npx tsc -p tsconfig.json --noEmit` 退出码 2，`src/services/commandRegistry.ts` 有 8 处 `TS6133`（未使用导入）：`activateRelativeTab`、`setAccentId`、`getAppDataDir`、`getCachedSettings`、`ACCENT_THEMES`、`requestSearchFocus`、`registerShortcuts`、`openPath` |
| 影响 | `package.json` 的 `build` 是 `tsc && vite build`，而 `tauri.conf.json` 的 `beforeBuildCommand` 是 `pnpm build` —— **`pnpm tauri build` 必然失败**。README 的「提交前检查」第一条命令当时就是红的 |
| 根因 | `commandRegistry.ts` 在 `tsconfig` 的 `noUnusedLocals: true` 下遗留了重构后的死导入 |
| 处理 | 删除这 8 个导入，`tsc` 恢复退出码 0 |

**这条值得记住的教训**：类型检查不是「没报错就没事」，而是「不跑就不知道」。这些导入在 `vite dev` 下完全无害（打包器会摇树掉），因此日常开发不会暴露，只有真正执行 `tsc` 才看得见。

#### 插件 ID 未校验导致路径穿越（安全问题）

| 项目 | 说明 |
| --- | --- |
| 现象 | `PluginManager::storage_clear` **完全没有** ID 守卫，直接 `remove_dir_all(plugin_data_dir(id))`；而 `plugin_data_dir` 是未校验的 `data_dir.join(id)`。命令层 `plugin_storage_clear` 也不校验 |
| 利用路径 | `id = ".."` → 目标解析为 `<app_data>/plugin_data/..`，即应用数据目录本身 → `remove_dir_all` 会把 `settings.json` / `auth.json` / `notifications.json` / `sidebar_config.json` 连同全部插件数据一起删掉 |
| 第二条路径 | `uninstall` 的守卫是 `validator::is_within(&plugins_dir, &plugins_dir.join(id))`，而 `is_within` 是纯前缀比较，`candidate == root` 时返回 **true**。`id = "."`（或 `plugin_data/..`）使目标规范化后等于 `plugins_dir`，守卫放行 → 整个 `plugins/` 目录被删，**包括 `registry.json`** |
| 为何危险 | docs 自己承认「插件可以直接 `invoke` 任意后端命令」，而这几个命令**不带 token 参数**。因此一个插件无需经 `ctx.storage` 就能直接触发，不需要任何权限声明 |
| 处理 | ① `validator::is_valid_plugin_name` 提升为 `pub`，并新增 `manager::validate_plugin_id`；② `plugin_data_dir` 改为**带校验**的入口（返回 `PluginResult<PathBuf>`），所有调用点因此自动受保护 —— 校验收在一处，漏掉任一调用点就等于没有防护；③ `uninstall` 开头显式校验 ID，`storage_clear` 增加「目标必须严格位于 `data_dir` 之下」的不变量检查；④ `is_within` 改为要求 `candidate != root` |
| 回归测试 | 新增 `plugin_name_rejects_path_traversal_inputs`（14 个穿越取值）与 `is_within_rejects_root_itself`。**后者已验证过有效性**：临时还原旧的纯前缀比较后该测试确实 FAILED，恢复修复后转绿 |

**`is_within` 的语义修正值得单独记住。** 它的两个调用点都是**删除**语义，而 `root` 自身作为删除目标一定是误用 —— 调用方要的是「root 里的某个条目」。只比较前缀是这类守卫最典型的错误写法，因为它同时放行了 `root` 本身与所有 `root/../...` 绕回 `root` 的路径。

#### 外壳对业务模块的静态依赖（架构不变式不成立）

| 项目 | 说明 |
| --- | --- |
| 现象 | 架构总览第 1 节主张「框架代码中不存在任何对具体业务模块的引用」，据此推出「删除任意内建模块，框架仍能编译并运行」。但 `SettingsDialog.tsx` **静态导入**了 `../../modules/plugins/Plugins` 并在「插件」分页渲染它 |
| 影响 | 删掉 `src/modules/plugins/` 会让外壳编译失败，上面两条结论都不成立 |
| 处理 | 新增 `src/components/ModuleEmbed.tsx`，设置页改用它内嵌 |

**实测得到的、与直觉相反的结论：把静态 import 改成动态 `import('../modules/plugins/Plugins')` 并不够。** TypeScript 仍会对字面量说明符做静态解析，模块缺失时报的仍是 `TS2307`。实测过程：移走 `src/modules/plugins/` 并重新生成注册表（生成器正确产出「2 modules」）后，报错只剩这一条。**把说明符换成变量**（`import(specifier)` 配 `/* @vite-ignore */`）之后才真正编译通过。

验证方式（两个方向都实测过，不是推断）：

| 场景 | 结果 |
| --- | --- |
| 保留模块 → `tsc` | 通过 |
| 移走模块 + 重新生成注册表 → `tsc` | **通过**（不变式成立） |

代价如实记录：该模块不再被 Vite 预打包，改为首次打开「设置 → 插件」时按需加载；模块真的被删除时，错误发生在**打开设置页的那一刻**而不是构建期，因此 `ModuleEmbed` 用错误边界把它降级成一条可读提示，而不是冒到顶层变成整窗错误页。

### 7.9 深色模式亚层配色与标签切换的动画残留

#### 深色下标题栏/标签栏/搜索框渲染成灰色

| 项目 | 说明 |
| --- | --- |
| 现象 | 深色模式下，二级标题栏（标签栏）整条渲染成灰白色，全局搜索框也是浅灰而不是深色 |
| 根因 | **`bg-white/90` 与 `bg-white` 是两个不同的类名 token**，`[class~='bg-white']` 不会命中前者，因此 `dark-theme.css` 必须**逐个列出**用到的不透明度档位。当时列了 `/90`、`/80`、`/70`、`/60`、`/50`，而标签栏用的是 **`bg-white/85`**、搜索框是 **`bg-gray-50/80`** —— 两档都不在表里，于是原样保留浅色。**漏一档不报错，只表现为深色界面里出现一块灰白** |
| 排查方式 | 把「项目里用到的 `bg-*` 类」与「dark-theme.css 已映射的类」做差集，共发现 35 个未映射项；其中多数是有意为之（`bg-indigo-500` 等强调色由主题变量驱动、`bg-red-500` 等语义色两种模式通用），真正属于「大面积表面漏映射」的就是上面两档 |
| 处理 | ① 把 `/85`、`/95`、`gray-50/80`、`gray-50/60` 补进映射表；② **标题栏与标签栏统一为同一不透明色 `#151823`** —— 二者是相邻的窗口亚层，背后就是应用底色，半透明只会让两块亚层深浅不一、出现色带分界，不透明之后它们在视觉上连成一整块；③ 搜索框按「下沉输入区」处理，用比面板更深一档的 `#0e111a` 表达「凹进去的输入位」，而不是靠灰 |
| 顺带修掉 | 搜索框原来的 `focus:bg-white` 是**变体**类，属性选择器同样命中不到，聚焦时会闪出一块白底。已移除该变体，聚焦只改描边与光环 —— 聚焦时底色跳变本身也是一种突兀 |
| 验证 | 用脚本计算了实际对比度（WCAG）：标题 16.08:1、激活标签 15.09:1、未激活标签 6.97:1、图标 6.97:1、搜索文字 17.13:1，全部高于 4.5:1（图标 3:1）；亚层分离度 1.066:1，可辨识而不过分 |

#### 切换模块时几个卡片短暂停留

| 项目 | 说明 |
| --- | --- |
| 现象 | 从仪表盘切到别的模块时，有三张卡片会在新页面上停留一小会儿才消失；理想情况下切换应当是瞬时的 |
| 根因 | **不是「没隐藏」，而是「隐藏之后动画还在跑」**。标签保活让切走的模块留在 DOM 中（刻意的），仪表盘的统计卡片带入场延迟 `delay: 0.15 + i*0.06`，即 index 2/3/4 分别延迟 0.27/0.33/0.39 秒 —— 用户切走时它们刚播到前几帧，**用户看到的「三张」正是延迟最长的那三张**。而 `visibility: hidden` 只让元素不参与最终绘制，**并不暂停动画**，合成器仍会把中间帧画出来 |
| 为什么不能简单换隐藏方式 | `display:none` 会让元素失去盒子、丢掉 `scrollTop`，而「切回来还在原处」正是保活的核心目标。`content-visibility: hidden` 更彻底，但 MDN 对其语义的说明是 "similar to giving the contents `display: none`"，与滚动位置保留存在冲突风险（CSSWG 也讨论过 skipped 子树的滚动位置恢复）。在不能实测的前提下，**不拿保活的核心不变量去换一个性能属性** |
| 处理 | 三层收口，都只作用于非激活标签：① CSS 暂停动画与过渡（`animation-play-state: paused`，停在当前帧而不是跳到终态，避免切回来时看到跳变）；② 宿主传入 `initial={false}`，让**包裹层**跳过初始态直接渲染终态；③ 用 `!important` 把非激活子树钉在 `opacity: 1` / `transform: none` 的终态 —— framer-motion 是写**行内样式**的（`element.style.opacity = …`），行内样式压不过 `!important` 的样式表规则，这是确定性的最后一道 |
| 一个必须记住的实测结论 | **`MotionConfig reducedMotion="always"` 不能解决这个问题。**我读了安装的 framer-motion 12 源码：`motion-dom` 的 `visual-element-target.mjs` 里是 `shouldReduceMotion && positionalKeys.has(key) ? { type: false } : valueTransition`，而 `positionalKeys` 只含 width/height/top/left/right/bottom 与 transform 系列 —— **`opacity` 不在其中**。卡片残留的可见表现恰恰是 opacity 淡入，因此单靠 reducedMotion 会留下这个 bug。这一点与「官方文档说 reducedMotion 会关闭动画」的直觉相反 |
| 验证 | CSS 结构与选择器一致性由脚本核对（花括号配平、规则存在性、选择器与 `data-active` 标记一致、且确认未退回 `content-visibility`/`display:none`），全部通过 |

**这两条都提示了同一个模式**：`dark-theme.css` 的「按类名映射」（5.2 节）和标签保活（7.7 节）都是**有明确代价的设计取舍**，而代价集中体现在「漏了一项不会报错，只会表现为某处看起来不对」。前者漏一档颜色就退回浅色，后者漏停一类动画就出现残留。这类问题无法靠类型系统发现，只能靠清单式核对与小心的收口规则 —— 这也是本轮把「映射漏项差集」写成可复跑脚本的原因。

### 7.10 亚层分隔线与折叠态「展开」入口的位置

#### 标签栏底边的浅色细线（深色下像白边）

| 项目 | 说明 |
| --- | --- |
| 现象 | 深色模式下标签栏底部有一条细白/浅色边线，与整体深色不协调 |
| 根因 | 标签栏用的是 `border-gray-200/70`，而 `/70` **不在** `dark-theme.css` 的映射表里（只列了 `/50`、`/60`），于是原样保留浅色。与 7.9 节的底色漏项是同一类错误，只是这次出在边框上 |
| 处理 | ① 把 `/70` 补进映射表；② 更关键的是**改掉勾边思路本身**：窗口亚层的分界应当"压下去"而不是"提起来"，因此标题栏与标签栏的底边改用比面板更暗的 `#0a0c12`，表达的是一道浅浅的接缝，而不是一条亮线 |
| 取值的依据 | `#0a0c12` 与亚层的对比约 **1.10:1**。这个量级是刻意选的：本项目既有的层次基准本身就很安静 —— 应用底与亚层之间只有 1.066:1。因此分隔线也应当落在这个量级，比它更暗会显得脏，更亮就又回到"勾白边"的问题 |
| 为什么只对窗口亚层生效 | `/50`、`/70` 也被浮层（右键菜单、插件卡片、下拉面板）使用，它们需要的是常规边框色 `#2c3242`。深色下给浮层描一道近黑边会让它看起来像一块硬邦邦的补丁，而不是浮在内容之上。判据用 `backdrop-blur-xl` —— 本项目里只有窗口亚层用它 |

**这条与 7.9 节合起来是一个必须记住的模式**：`dark-theme.css` 按类名精确映射，**底色、边框、透明度档位各自都要单独列**，漏掉任何一维都不报错，只表现为「深色界面里某处颜色不对」。这轮两处缺陷（底色的 `/85`、边框的 `/70`）属于同一个根因的两个面。

#### 折叠侧边栏后「展开」按钮挡住标签栏

| 项目 | 说明 |
| --- | --- |
| 现象 | 侧边栏收起后，右上角（实际是窗口左上偏下）留着一个「展开」按钮，它挡住了二级标题栏 |
| 根因 | 按钮是 `fixed left-4 top-14 z-50`。`top-14` = 56px，而标签栏占据 **40~76px**，按钮（约 36px 高）横跨 56~92px；且它 `z-50` 高于标签栏的 `z-40`，于是直接盖住了标签栏左端与第一个标签 |
| 需求约束 | 用户明确指出**不接受**在折叠态加一个常驻的小型侧边栏 —— 那会永久吃掉内容区宽度，损害模块的全屏与沉浸式体验。这个约束是对的：常驻窄条换来的是"多一个入口"，付出的却是所有模块永久少一块画布 |
| 处理 | 「展开」入口**并入标签栏左端**，作为标签栏内部的一个固定槽位（`shrink-0`），标签从它右侧开始排列。这样按钮与标签栏同层同高、不遮挡任何标签，也**不引入常驻窄条**，内容区在折叠态依然是满宽的（`ml-0`） |
| 入口唯一性 | 展开入口仅在 `!isOpen` 时渲染；折叠入口在侧边栏头部（`PanelLeftClose`），而 `Sidebar` 在折叠态直接返回 `null`。因此任一状态下两个入口只有一个存在，不会重复或互相遮挡 |
| 验证 | 用脚本核对了：旧浮动按钮已消失、按钮位于标签栏内部（受 `items-stretch` + `h-9` 约束，不可能溢出 40~76px）、`shrink-0` 防止被标签挤压、折叠态 `ml-0` 未被挤占、两入口互斥 |

### 7.11 发布前的仓库整备

本轮为首次公开发布做准备。**第一项是真实缺陷，会让任何新 clone 的人构建失败。**

#### `pnpm build` 在全新 clone 上必然失败

| 项目 | 说明 |
| --- | --- |
| 现象 | `pnpm build`（以及 `pnpm tauri build`）在刚 clone 的仓库上失败，`tsc` 报 4 条 `Cannot find module '../generated/...'` |
| 根因 | **两个事实叠加**：① `src/generated/` 是构建期产物，被 `.gitignore` 排除，因此新 clone 里不存在；② 生成它的 `scripts/generate-modules.ts` 原本只在 **Vite 插件**里被调用，也就是只在 `vite build` 阶段运行。而 `build` 脚本把 `tsc` 排在 `vite build` **之前** —— `tsc` 面对一个还没生成的目录 |
| 影响 | 这是开源项目最糟的一类问题：**第一个想试用的人就卡住**。而且它对本机开发者不可见，因为本地 `src/generated/` 一直存在 |
| 处理 | `build` 与 `dev` 脚本都在 `tsc` / `vite` 之前插入 `pnpm gen:modules` |
| 验证 | **实测复现再验证**：先移走 `src/generated/` 复现失败（`tsc` 退出码 2，4 条 TS2307），应用修复后在同一状态下按 `ver check → gen:backend → gen:modules → tsc` 顺序执行，`tsc` 退出码 0 |

**同一个陷阱还有第二个入口。** README 与贡献指南的「提交前检查」都让贡献者直接运行 `npx tsc`，而新 clone 下同样会失败。两处文档都已补上 `pnpm gen:modules` 这一步，并说明「只有直接调用 `tsc` 时才需要留意这个顺序，`pnpm build` / `pnpm dev` 会自动处理」。

#### 其它发布整备

| 项目 | 处理 |
| --- | --- |
| `tsconfig.node.tsbuildinfo` 被跟踪（57.6 KB） | 这是 TypeScript 增量编译缓存，属构建产物。已 `git rm --cached`（保留磁盘文件）并在 `.gitignore` 加入 `*.tsbuildinfo` |
| `.gitignore` 里 `!src/generated/.gitkeep` 指向不存在的文件 | 该例外规则没有对象，且 `src/generated/` 本就不需要入库（生成器会自行 `mkdirSync`）。已改为整体排除 `src/generated/`，并注明不要为它留占位文件 |
| 缺少 `.gitattributes` | Git for Windows 默认 `core.autocrlf=true`，而仓库现有文本文件全是 LF。没有 `.gitattributes` 时，Linux/macOS 贡献者与 CI 会与本地产生换行符不一致，表现为 PR 里整文件 diff。已新增：统一 `eol=lf`，二进制与 `.bat`/`.ps1` 单独声明，锁文件与生成文件标记 `linguist-generated`（GitHub 默认折叠其差异、不计入语言统计） |
| 缺少 `.editorconfig` | 与 `.gitattributes` 分工不同：前者管「仓库里怎么存」，后者管「编辑器写出什么」。已按既有代码风格补齐（两空格、LF、末行换行） |

**这两件事合起来说明一个模式**：`.gitignore` / `.gitattributes` / `.editorconfig` 这类文件平时没有存在感，问题只在**别人第一次接触仓库**时才暴露 —— 与 7.10 节的结论一致。

### 7.12 应用标识符变更与个人账号名脱钩

| 项目 | 说明 |
| --- | --- |
| 背景 | 标识符原为 `com.metazero-tsip.modulith`，其中 `metazero-tsip` 是开发者**旧**的 GitHub 账号名（后更名为 `Rinntheor`），且该值形式上假定拥有 `metazero-tsip.com` 这个并不存在的域名 |
| 问题 | 反向域名式标识符的语义前提是**控制对应的命名空间**。把个人账号名写进标识符，既会随账号改名而过时，也不构成有效的命名空间 |
| 现取值 | `com.rinntheor.modulith` |
| 时机说明 | **这是变更标识符的最后合理时机。** 未发布时改动只影响开发者本人（需重设访问密钥）；一旦有真实用户，标识符变更会让所有用户的数据目录换位置——Tauri **不做迁移**，表现为访问密钥、恢复码、设备白名单、已装插件、全部设置与通知一次性不可见。此外 Windows 安装包会把它当成另一个产品，旧版不会被升级而是并存 |
| 影响范围 | 数据目录：`%APPDATA%\com.metazero-tsip.modulith` → `%APPDATA%\com.rinntheor.modulith` |
| 如何保留旧数据 | 各数据文件的**格式不依赖标识符**，因此可直接把旧目录内容复制到新目录：把 `%APPDATA%\com.metazero-tsip.modulith` 下的 `settings.json`、`auth.json`、`notifications.json`、`sidebar_config.json`、`plugins/`、`plugin_data/` 复制到 `%APPDATA%\com.rinntheor.modulith`。这样访问密钥与已装插件都不会丢 |
| 同步位置 | `src-tauri/tauri.conf.json`（唯一实际配置）、`README.md` 的命名表、本条记录 |

**标识符自此冻结。** 它与产品名（`Modulith Desktop`）、包名（`modulith-desktop`）是三个不同的东西：包名可以随构建调整，产品名可以改显示文案，**只有标识符动不得**——它一旦随版本变化，用户数据就会"丢失"。`pnpm ver check` 会校验产品名一致性，但**不会**校验标识符（它不该变，因此没有可校验的基准）。

### 7.13 生成器写时间戳导致不可重复生成

| 项目 | 说明 |
| --- | --- |
| 现象 | 每运行一次 `pnpm gen:backend update`，`src-tauri/src/lib.rs` 与 `modules/mod.rs` 都会显示为已修改，而**内容其实只有一行「生成时间」不同** |
| 根因 | 两个生成器模板的头部写入了 `// 生成时间: ${new Date().toISOString()}`，而这两个文件是**入库**的（不像 `src/generated/` 那样被 gitignore） |
| 影响一 | **每次都弄脏工作区**。任何贡献者构建一次就会看到两个「已修改」文件，容易误提交、也干扰 `git status` 的判断 |
| 影响二 | **让「生成器一致性」的 CI 检查无法成立。**该项检查的做法是「跑一遍生成器，然后 `git diff --exit-code`」；只要输出含时间戳，这个 diff 必然非空，检查会永远失败 —— 也就是说它会变成一个没人能修的红色门禁 |
| 处理 | 从两个模板头部移除生成时间行，改为说明「刻意不写时间戳」的原因。生成结果因此**可重复**：同一份源码无论生成多少次，产物逐字节一致 |
| 验证 | 连续生成两次并比对文件哈希，结果一致；生成后 `git status` 对这两个文件为干净 |
| 追溯方式 | 需要知道生成时间时查 git 历史即可。前端生成产物仍有 `generation.log.json` 记录（它被 gitignore，不受此问题影响） |

**这个问题值得记住的地方在于它是我自己引入的。**「生成后 diff 为空」这道检查是可靠的 CI 门禁设计，但在**生成不可重复**的前提下它只会制造一个永远修不好的红灯。检查与生成器的可重复性是**配套要求**：只加检查而不保证幂等，等于给项目装了一个必然失败的闸门。
