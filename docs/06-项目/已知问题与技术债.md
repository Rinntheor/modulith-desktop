# 已知问题与技术债

本文记录当前代码中已确认的问题、未完成的能力与设计上的取舍。目的是让后续维护者不必重新发现它们。

分类说明：

| 类别 | 含义 |
| --- | --- |
| 缺陷 | 行为与预期不符，应当修复 |
| 未接入 | 代码存在但没有任何路径使用它 |
| 未实现 | 类型或界面已声明，但没有对应实现 |
| 设计取舍 | 有意的选择，需要时再重新评估 |

## 1. 导航机制

### 1.1 状态驱动的导航与路由代码并存

**类别：** 未接入

**现状。** 打开模块时只调用 `tabStore.openTab()`，由它更新标签状态；`Home` 据此渲染 `mountedTabs` 中的全部模块（仅激活的那个可见）。`SidebarContext.activeModule` 读的是 `tabStore.activeTab`，不再自己持有。模块**切换**不修改地址栏，代码库中也没有任何 `useNavigate`、`navigate()`、`<Link>`、`useParams` 或 `useLocation` 调用。

与此同时，`src/router/` 下存在一套路由设施，其中**并非全部是死代码**：

| 文件 | 状态 |
| --- | --- |
| `Router.tsx` | 生效：声明 `/`、`/home`、由 `DynamicRouter.getRoutes()` 生成的动态路由，以及兜底 404 |
| `dynamicRouter.ts` | **活代码**：由 `Router.tsx` 以值导入方式引用。`getRoutes()` 被使用；其余六个静态方法（`getRouteByModuleId`/`getRouteTree`/`isValidRoute`/`addRoute`/`removeRoute`/`clearRoutes`）无调用方 |
| `contexts/RouteContext.tsx` | 死代码：`RouteProvider` 与 `useRoute` 没有任何引用方 |

**影响。**

- `Router.tsx` 中由 `DynamicRouter.getRoutes()` 生成的 `<Route>` 列表**确实被注册生效**，但它只包含启动时刻的内建模块快照，不含插件在运行期注册的模块。由于导航不经过 URL，这一点在日常使用中不会暴露；但若用户手动修改地址或依赖深链接，插件模块会落到 404。
- `RouteContext.tsx` 属于死代码。
- `window.history.back()` 出现在 `Router.tsx` 的 404 页与 `ModuleRenderer.tsx` 的「模块未找到」页。既然模块导航不进历史栈，这两个按钮的语义并不成立。

**建议。** 在两种方向中明确选择其一：

1. 让导航真正走路由：侧边栏切换时调用 `navigate(path)`，`DynamicRouter` 在编目变化时重新生成路由，并由 `RouteContext` 提供当前路由信息。这样深链接、前进后退可与浏览器行为统一。
2. 确认继续使用状态驱动：删除 `RouteContext.tsx`，并在 `Router.tsx` 中移除动态路由生成逻辑，避免两套机制并存造成误解。**注意顺序：** `dynamicRouter.ts` 不能先删 —— 它被 `Router.tsx` 以值导入方式引用，且被 `types/core.ts` 再导出（`RouteConfig`）。必须先摘掉 `Router.tsx` 里对 `getRoutes()` 的调用与 `types/core.ts` 的再导出，才能删除该文件。

在做出选择前，`SidebarContext` 中自建的前进后退历史栈（`goBack`、`goForward`）需要一并考虑：如果改用路由，这套历史管理应当交给路由层。注意它与标签页是两套独立的顺序 —— 历史栈记录**访问顺序**（用户实际去过哪里），标签顺序是**用户拖出来的排列**，二者刻意不合并。历史栈不持久化，重启后从空开始。

### 1.2 动态路由的初始化时机

**类别：** 缺陷（仅在采纳路由方案时成立）

`dynamicRouter.ts` 在模块顶层调用 `DynamicRouter.initialize()`。该文件在应用启动时被导入，此时插件尚未加载，因此生成的路由不含插件模块。即使采纳上述第 1 种方案，也需要把初始化改为在 `moduleCatalog` 变化时重新执行。

## 2. 后端遗留代码

### 2.1 两个不会被编译的目录（已解决）

**类别：** 已解决

**原状。** 磁盘上曾经存在以下目录（**现已从仓库删除**；本节长期描述为"当前存在的问题"，属于文档滞后）：

```
src-tauri/src/sidebar/           commands.rs, config.rs, mod.rs
src-tauri/src/module_config/     commands.rs, mod.rs
```

`lib.rs` 只声明了 `prelude`、`core`、`modules` 三个模块，因此这两个目录不是编译单元的一部分，其中的代码永远不会被执行。

**影响。** 它们与 `modules/sidebar/` 功能重叠，容易让阅读者误以为存在多套实现。`sidebar/commands.rs` 中还保留着对 `crate::sidebar::config` 的引用，但该引用同样不会被编译。

**建议。** 确认没有外部脚本或工具依赖这些路径后删除。删除前建议先执行一次全局检索，确认没有构建脚本引用它们。

### 2.2 模块 ID 命名不统一

**类别：** 设计取舍

**现状。** 前端模块 `id` 使用小驼峰（`dashboard`、`plugins`），后端模块 `id` 使用蛇形（`sidebar`、`plugins`、`auth`、`settings`）。两者通过各自的目录独立管理，没有强制的同名要求。

**影响。** 同一功能的模块在前后端名称形式不同，排查问题时需要在两种命名间转换。

**建议。** 保持现状是可接受的，因为后端 `id` 必须满足蛇形以正确生成 Rust 类型名。若要统一，只能把前端改为蛇形，代价是 `module.toml` 中 `path` 与 `id` 的关系变得不直观。另一种选择是在文档中明确记录两者的映射关系，[模块开发](../02-开发指南/模块开发.md)第 4 节已作说明。

## 3. 未使用的框架能力

以下能力已实现但当前没有任何调用方。它们本身不是缺陷，但会让人误以为系统具备相应行为。

| 能力 | 位置 | 现状 |
| --- | --- | --- |
| `Module::stop()` | `core/module.rs` | `lib.rs` 只调用 `setup` 与 `start`，从不调用 `stop` |
| `Module::dependencies()` | `core/module.rs` | 无模块声明依赖，拓扑排序退化为任意顺序 |
| `Module::handle_event()` | `core/module.rs` | 无模块实现该回调 |
| `ModuleRegistry::broadcast_event()` | `core/registry.rs` | 无调用方 |
| `createLazyComponent().preload()` | `utils/lazyLoad.ts` | 由启动流程的 `preload` 步骤调用（已不再是死代码） |
| `src/types/core.ts` | 整个文件 | 无引用方 |

**类别：** 未接入

**建议。** 按用途分别处理：

- 生命周期钩子（`stop`、`handle_event`、`broadcast_event`）属于框架预留能力，若要保留应在文档中标注为「预留」，或补上实际调用点。其中 `stop` 的缺失值得注意：如果将来有模块需要在关闭前释放资源，当前框架没有执行时机。
- `preload` 若要发挥作用，应在模块首次渲染前调用，以减少切换时的等待。
- `types/core.ts` 建议删除，其内容与 `types/module.ts` 重叠。

### 3.1 模块启动顺序不确定

**类别：** 缺陷（潜在）

`ModuleRegistry` 用 `HashMap<String, Box<dyn Module>>` 存储模块，`all()` 返回 `self.modules.values()`。`lib.rs` 按该顺序调用各模块的 `start`，因此启动顺序取决于哈希布局，每次运行可能不同。

当前七个模块的 `start` 都是默认空实现，所有初始化都在 `setup` 里完成，因此没有实际影响。但一旦某个模块的启动逻辑依赖另一个模块已启动，就会出现难以复现的偶发故障。

这里还叠着一条**容易误判的次序约束**：`setup_all` 按注册表顺序调用，而注册表顺序取自目录名的字母序，因此 `auth` 排在 `logging` 前面 —— `auth` 在 `setup` 里打的那几行日志发生在日志器**已安装、但还没拿到日志目录**的窗口内。处理方式是把「安装日志器」与「配置落盘目录」分成两步（前者在 `main()` 最早期，后者在 `logging` 的 setup），中间用内存队列承接。见[日志系统](../02-开发指南/日志系统.md)第 3 节。这说明**即使每个模块的初始化都正确，模块之间的相对次序仍然会通过副作用被观察到**。

**建议。** 在 `setup_all` 中记录拓扑序并提供一个按序迭代的方法，让 `start` 也按依赖顺序调用。或者统一在 `setup` 中完成初始化，避免依赖 `start` 的顺序。

## 4. 插件系统

### 4.1 权限声明仍有过半未强制

**类别：** 部分实现

**现状。** `PluginManifest.permissions` 是 `Vec<PluginPermission>`，枚举包含 12 个取值。当前真正被检查的是七个：

| 权限 | 检查位置 | 检查层 |
| --- | --- | --- |
| `storage` | 任一 `plugin_storage_*` 命令 | Rust |
| `network` | 发起 HTTP 请求前 | Rust |
| `network-external` | 目标不是回环地址时 | Rust |
| `process-spawn` | `plugin_launch_program` 命令 | Rust |
| `filesystem-read` | `plugin_extract_icon` / `plugin_reveal_in_folder` / `ctx.fileDrop` 订阅 | Rust（拖放另有前端一处） |
| `notification` | 调用 `ctx.notifications` 时 | 前端 |
| `plugin-communicate` | 调用 `ctx.events` 时 | 前端 |

其余取值（`clipboard`、`filesystem-write`、`filesystem-scoped`、`native-module`、`dev-tools`）不影响任何行为。

**本轮进展。** `notification` 与 `plugin-communicate` 从「声明了但无效」变成了真正生效 —— 前者原本连接口都不存在（`PluginNotificationAPI` 只有类型声明，`createContext()` 从未提供它），现在已实现；后者是新增的跨模块事件总线。两者的拒绝方式是**降级为空实现 + 控制台警告**，而不是抛错：它们是可选的附加能力，让插件因为一个没声明的选项而整体加载失败，代价大于收益。

**本轮进展（storage）。** `storage` 从「声明与否都不改变行为」变成了真正生效：五个 `plugin_storage_*` 命令现在都会先经 `PluginManager::require_permission` 检查清单是否声明了 `storage`，未声明则拒绝。检查点收在 `checked_storage_dir` 一处 —— 与 `plugin_data_dir` 的 ID 校验同理，校验散在多处时漏掉任何一处都等于没有防护。

**但要分清它买到了什么。** 这次修复让**权限列表变得诚实**：清单里「声明了 storage」与「真的能读写存储」从此一致。它**不是**插件之间的隔离边界 —— 命令的 `id` 参数来自调用方，插件直接 `invoke('plugin_storage_get', { id: '别的插件', key: 'x' })` 仍能读取他人数据。

此处原文曾写着「存储始终可用，因为按 ID 隔离，不存在越权访问别的插件数据的路径，因此没有强制点可加」—— **这个判断是错的**：隔离的是**命名空间**，不是**访问权**。命名空间隔离只保证两个插件的键不互相覆盖，不保证一个插件不去读另一个的键。要堵住它，后端必须知道「谁在调用」，而这在「插件与宿主共享同一个 WebView 与 JS 上下文」的模型下无法实现。因此本项**只解决了「声明不生效」，没有解决「越权读取」** —— 后者要等进程级隔离。

**仍未解决。** 文件系统与剪贴板相关权限依然只是**部分**强制，需要说清边界：

- `filesystem-read` 现在管住了**图标提取、文件管理器定位、接收拖入路径**三件事，但**没有任何命令可以读取文件内容** —— 也就是说「读取文件内容」在当前架构下根本不是一项存在的能力，因此这半边的缺口不是「没检查」，而是「没有可检查的东西」。
- `filesystem-write` 与 `filesystem-scoped` 没有对应的**权限检查点**。但要注意这句话此前写作"完全没有对应的命令"——**那是不准确的**：`export_plugin` 在此前可以用 `dest` 覆盖任意路径的文件，正是 `filesystem-write` 的语义（现已收口为"导出目录内的新文件名"，见 7.26 节）。所以这两个取值的真实状态是「有能力、无检查点」，而不是「没有可检查的东西」。
- `clipboard` 同理：宿主没有暴露剪贴板接口，插件要写剪贴板得自己用浏览器的 `navigator.clipboard`。

**影响。** 用户可以声明任意权限而不获得相应能力。权限列表整体上仍更接近意图声明而非访问控制，对用户判断插件风险有误导性。

**建议。** 两种方向：

1. 为其余权限补上强制点。这需要先明确能力边界，例如 `filesystem-read` 允许访问哪些目录 —— 而这在当前「插件与宿主同进程」的架构下无法可靠实现（插件可直接用 `fetch` 或 `invoke` 绕过）。
2. 在界面与文档中明确标注当前哪些权限生效，避免用户高估隔离强度。文档已在[插件系统架构](../02-开发指南/插件开发/插件系统架构.md)第 6 节与[清单文件参考](../02-开发指南/插件开发/清单文件参考.md)第 4 节作此说明。

**为什么前端检查也是有效的。** `notification` 与 `plugin-communicate` 的实现完全在前端（通知要落盘、事件不出进程），没有对应的后端命令可以绕过，因此前端就是唯一执行点。这与网络、存储权限不同 —— 网络请求由 Rust 发起、存储文件由 Rust 读写，所以检查必须在 Rust 侧。

### 4.2 sandboxLevel（已删除）

**类别：** 已解决（改为删除）

`SandboxLevel` 曾有 L0 至 L3 四档，描述从「无网络、无文件系统」到「完全访问」。该字段会被解析、序列化并保留默认值 L1，但**没有任何代码读取它** —— 填写不同等级不会改变插件行为。

**最终的处理不是实现它，而是删掉它。** 理由是它描述的是**宿主做不到的事**：插件与宿主运行在同一个 WebView、同一个 JS 上下文里，宿主无法按等级限制它。这个字段由插件自己声明、宿主无法核实 —— 与权限风险同理，一个无法核实的自述不该被当作管控手段。

**决定性的证据是它不只是一个死字段。** 插件详情页此前真的把它渲染成一行「沙箱级别 L1」。也就是说它从"没人读的字段"升级成了**界面上的一句空话**：用户会据此以为宿主能对插件分级管控。这与项目自己的纪律直接冲突 —— *不要在阶段一就假装拥有了阶段三的保障*。

**删除是向后兼容的**，这一点当初决定了"删"比"留"便宜：`PluginManifest` 没有 `deny_unknown_fields`，因此插件仓库里现有清单残留的 `sandboxLevel` 会被**静默忽略**，安装照常 —— **不需要为它发一轮插件版本与重新签名**。

替代它的是两样真东西：`permissions`（声明式，正在逐步从"声明"变成"真强制"）与出站网络策略（`modules/net`）。**用一个真能生效的机制，替掉一个不能生效的字段。**

### 4.3 插件包本身无代码签名

**类别：** 未实现（范围已收窄）

插件包（`.lcp`）**本身**没有签名机制，清单中也没有签名字段。但「安装时无法验证来源与完整性」这句此前过于笼统，需要收窄到实际范围：

| 安装路径 | 完整性 / 来源校验 |
| --- | --- |
| 插件市场（`install_plugin_url_verified`） | 强制校验索引里记录的 `sha256`；索引本身有 minisign 签名（与应用更新同一把公钥），验签不过则整体拒绝索引 |
| 从 `.lcp` 文件安装 | 无签名、无哈希 |
| 从本地目录安装 | 无签名、无哈希 |

因此缺口集中在**本地路径**：用户手工下载的包、以及开发链接目录，都没有来源校验。

**影响（仍然成立的部分）。** 用户无法区分官方插件与第三方修改版。配合 4.4 所述的隔离缺失，安装来源不明的插件的风险等同于运行未知程序。

**建议。** 若要覆盖本地路径，需要先确定密钥分发与信任模型，属于较大的独立工作。在此之前，应在插件管理界面显著提示风险。

### 4.4 插件与宿主共享同一 JavaScript 上下文

**类别：** 设计取舍

插件代码通过注入 `<script>` 执行，与宿主处于同一个 WebView 与同一个 JavaScript 上下文。因此：

| 项目 | 说明 |
| --- | --- |
| 全局对象 | 插件可访问 `window` 上的任意内容 |
| 会话令牌 | 插件可读取 `sessionStorage` 中的 `modulith.auth.token` |
| 插件之间 | 没有相互隔离 |
| 宿主数据 | 插件可读取宿主已加载的数据 |
| 网络 | 权限检查只约束经由 `ctx.http` 的请求，插件可用常规 Web 手段绕过 |

**影响。** 认证模块的会话守卫能防止命令被随意调用，但无法在恶意插件面前保护令牌本身。因此当前模型中**插件的信任级别等同于应用本身**。

**已有与缺失的隔离手段。** 需要区分「故障隔离」与「安全隔离」两件不同的事：

| 层级 | 机制 | 位置 | 能防住什么 |
| --- | --- | --- | --- |
| 渲染 | `AppErrorBoundary` | `src/components/AppErrorBoundary.tsx` | 任何未被下层接住的渲染错误导致整窗白屏 |
| 渲染 | `ModuleErrorBoundary` | `src/components/ModuleRenderer.tsx` | 插件界面渲染崩溃影响宿主与其它模块 |
| 渲染 | `PluginModulePending` | `src/components/ModuleRenderer.tsx` | 把「插件尚未加载完」误报为「模块不存在」 |
| 异步 | 全局错误监听 | `src/services/globalErrorHandlers.ts` | 事件处理器 / 定时器 / 未处理 Promise 拒绝静默消失 |
| 加载 | 逐插件超时 | `src/services/pluginRuntime.ts` | 一个慢插件拖累其余插件的加载 |
| 加载 | 加载失败标记 | `src/services/pluginRuntime.ts` | 坏的插件静默失败（现在会显示为「异常」） |
| 存储 | 按插件 ID 命名空间 | `src-tauri/src/modules/plugins/manager.rs` | 插件之间互相读写存储数据 |
| 资源 | 插件目录内路径约束 | `src-tauri/src/modules/plugins/manager.rs` | 插件读取自己目录之外的文件 |

**仍然缺失的（安全隔离）。** 上述机制只解决「一个插件崩了不影响别人」，不解决「一个恶意插件能做什么」：

- 没有进程级或 WebView 级隔离——插件代码与宿主同线程同上下文，可以读写宿主的任何全局对象；
- 插件 bundle 顶层的同步死循环**无法被中断**。JS 是单线程的，超时只能保证后续插件不被拖累，无法救回已经卡住的主线程；
- 插件可以直接 `invoke` 任意后端命令，后端只能靠会话校验兜底，而这拦不住已经拿到令牌的同源 JS。

**建议。** 真正的安全隔离需要独立进程或独立 WebView 实例，属于架构级改动。在此之前，应把「只安装可信来源的插件」作为明确的产品约束告知用户，而不是依赖权限系统提供保护。

### 4.5 无多版本共存与回滚

**类别：** 未实现

**影响。** 插件升级后若出现问题，用户无法回退，只能重新安装旧版本包（如果还留着）。

**建议。** 若需要该能力，应在安装流程中保留上一版本并增加回滚入口，同时定义清理策略避免磁盘无限增长。

### 4.7 恢复码：没有历史记录，也不记「用掉的是哪一枚」

**类别：** 设计取舍

当前一次生成 3 枚恢复码（`RECOVERY_CODE_COUNT`），`auth.json` 只保存它们的 Argon2id 哈希数组（`recoveryHash`）与生成时间（`recoveryCreatedAt`），**不保留任何历史**。

**行为与限制。**

| 项目 | 当前行为 |
| --- | --- |
| 重新生成 | 整套作废，换发新的 3 枚 |
| 用掉一枚 | **只删除那一枚**，其余保留（这是刻意的，见下） |
| 用掉后是否换发 | **不换发**。重置成功后只减少一枚 |
| 历史 | 不记。界面只能显示生成时间与剩余枚数 |
| 审计 | 登录日志记录命中的序号（`recovery-reset#2`），但那只在日志里，不是恢复码历史 |

**「只删除用掉的那一枚」是安全性质，不是偷懒。** 早期实现是「重置成功后整套换发」。它有致命缺陷：若攻击者先用一枚恢复码重置了访问密钥，整套就会换成**攻击者手里**的新码，而用户手中的纸全部作废——攻击者不仅拿到访问权，还把合法用户永久锁在门外。只删除被用掉的那一枚之后，用户**始终保留夺回控制权的能力**。

代价是：不再有「一次重置就自动清空所有旧纸」的行为。要主动作废旧纸，必须去「设置 → 安全 → 密钥恢复」点「重新生成」。这是**有权衡的选择**——主动作废优于被攻击者替你作废，但确实留下一段窗口：若攻击者拿到了纸却还没用，在你手动重新生成之前它们一直有效。

**另一个限制：** 若用户把多张历史纸质备份混在一起，只有最新那一批有效，而界面上看不出「哪张是旧批」——只能靠 `recoveryCreatedAt` 自行比对。

**老用户升级路径。** 在引入恢复码之前就已设置访问密钥的用户，其 `recoveryHash` 为空。此时解锁界面不会显示「忘记访问密钥」入口（那会是个死胡同），并明确提示「本机尚未生成恢复码」。已解锁的用户可在「设置 → 安全 → 密钥恢复」补生成。

**建议。** 没有历史记录这一点可以考虑改进：记录「已用掉的枚数与时间」能在用户怀疑凭证泄露时提供线索。当前不做，是因为它需要新增持久化字段与界面，收益不足以justify。

### 5.2 深色模式由全局工具类映射实现，而非组件级 `dark:` 变体

**类别：** 设计取舍

**现状。** 深色模式已实现，但实现方式与常见做法不同：没有在组件里逐个补 `dark:` 变体，而是在 `src/styles/global/dark-theme.css` 中用属性选择器匹配工具类名（`[class~="bg-white"]` 等），把它们映射到深色取值。整套规则都在 `:root.dark` 下，与 Tailwind 生成的工具类同优先级，依靠 import 顺序（在 `tailwindcss` 之后）取胜。主题由 `src/services/theme.ts` 管理，设置项为 `theme`（`light` / `dark` / `system`）。

**为什么这样选。** 决定性因素是插件：插件由第三方编写，不可能配合补 `dark:` 变体。若深色只靠组件内的变体实现，任何插件界面在深色模式下都会是白底黑字，与宿主割裂。因此宿主用一张全局映射表把**宿主自己用到过的**类名重定向到深色取值。

**但这张表管不到插件。** 插件在运行时注入，它的类名不在宿主构建期的扫描范围内，Tailwind 不会为它们生成规则，映射表也就无类可映射。**插件必须自带 `index.css` 并自行处理深色**（见[示例插件](../02-开发指南/插件开发/示例插件.md)第 5.6 节）。本节此前写作「全局映射让插件只要使用常规 Tailwind 工具类就能自动跟随主题」——**那句话是错的**，而且与同一仓库 `示例插件.md` 5.6 节、插件仓库 `docs/目录规范.md` 5.2 节的正确表述直接冲突。

**代价与风险。**

| 问题 | 说明 |
| --- | --- |
| 依赖 import 顺序 | `dark-theme.css` 若被移到 `@layer` 内或提前导入，覆盖会整体失效 |
| 新工具类需同步 | 引入新的颜色工具类（例如 `bg-slate-50`）时，必须在映射表中补一条，否则深色下会漏掉 |
| 层次表达受限 | 只能做「浅色值 → 深色值」的对应，无法表达只在深色下出现的视觉层次 |

**建议。** 短期维持现状；若后续引入语义化色彩令牌（`--surface`、`--surface-raised` 等），可以逐步把映射表替换为令牌引用，两者并不冲突。

### 5.3 主题的首帧来源是 localStorage 缓存

**类别：** 设计取舍

后端 `settings.json` 是主题的权威来源，但 WebView 在 JS bundle 求值前就会绘制一次，等后端返回再决定配色会让用户看到「先深后浅」的闪烁。因此 `index.html` 内联脚本会先读 `localStorage` 缓存来渲染首帧，随后由设置加载结果覆盖并回写缓存。

**影响。** 缓存丢失（清空 WebView 数据）只会让首帧闪一下，不会丢设置。这一行为在 `src/services/theme.ts` 的文件头有说明。

### 5.4 动画开关无法停用 JS 里手写的定时动画

**类别：** 设计取舍

「关闭界面动画」通过两条路径生效：根元素加 `.lc-reduce-motion`（停用 CSS 动画与过渡）、`MotionConfig reducedMotion="always"`（停用 framer-motion 动画）。但代码中仍有手写的 `setTimeout` / `setInterval` 驱动的变化（例如提示条的自动消失、启动界面的计时刷新），这些不受影响。

**影响。** 关闭动画后，提示条仍会在若干秒后消失，只是不再有淡出过渡。这属于合理行为，但不应被理解为「所有随时间变化的东西都停了」。

**首帧做过一次错误的尝试，已回滚并换成正确的做法。**

| 项目 | 说明 |
| --- | --- |
| 上一轮的做法 | 在 `index.html` 内联一份纯 HTML 启动骨架（标记 + 文字 + 进度条），并在 `main.tsx` 用 `MutationObserver` 在 React 提交首帧后移除它 |

| 现象 | 仪表盘（以及任何内容超出窗口高度的模块页）无法滚动 |
| 根因 | `Home` 的内容区写的是 `min-h-screen pt-10`，即让内容把页面撑高、指望文档本身滚动；而 `index.html` 对 `html/body` 设了 `overflow: hidden`（窗口应用不该有文档级滚动条），于是没有任何元素滚动 |
| 修法 | 内容区改为视口内固定区域：`fixed inset-x-0 bottom-0 top-10 overflow-y-auto custom-scrollbar`。高度被钉死为「视口高 − 标题栏」，`overflow-y-auto` 必定生效 |

**插件引擎范围不再是安装门槛。**

| 项目 | 说明 |
| --- | --- |
| 现象 | 升级应用版本后，旧插件无法安装/重装，提示"插件要求 Modulith ^0.2.0，当前版本为 0.3.0"，看起来像升级把插件废掉了 |
| 根因 | `^0.2.0` 按 semver caret 规则等价于 `>=0.2.0 <0.3.0`（与 npm 一致），宿主升一个小版本就不再匹配；而 `validate_manifest` 把不匹配当作**硬错误**拒绝安装 |
| 需要澄清的一点 | 已安装的插件**没有失效**：`list()` 与加载路径都不做引擎校验，升级后照常加载。真正被阻断的是重装与安装新版本 |
| 修法 | 区分「语法错误」与「兼容性猜测」：范围语法不可解析仍拒绝安装；语法正确但不匹配只产生一条琥珀色提示（`EngineAdvisory`），安装与加载照常 |
| 提示的时效 | 每次 `list()` 按当前宿主版本重新计算，不落盘。因此升级后提示自动更新，也不需要改 `registry.json` 结构 |
| 示例与检查同步调整 | `samples/hello-plugin/manifest.json` 由 `^0.3.0` 改为 `>=0.3.0`（并重新打包 `.lcp`）；`ver check` 的过窄范围提示改为明确说明「不阻止安装，但会产生提示」。（该示例后来被 `samples/notes` 取代，见 7.17） |

「关于」页的两个外链卡片补齐了品牌图标与反馈动画：lucide 1.x 已移除全部品牌图标（`Github` 导出不存在），因此 GitHub 使用官方标准字形路径（`src/components/icons/BrandIcon.tsx`）；哔哩哔哩的官方标识是带描边的电视机形象，手工还原容易失真，因此保留电视机几何形状但**明确标注为通用图标而非品牌标识**，按钮上始终显示平台名称文字。点击后系统浏览器启动需要几百毫秒，按钮在此期间显示「正在打开浏览器…」并播放掠过高光，避免用户以为点击没生效。

### 7.4 恢复码的复制、打印与两步流程

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 复制出来的恢复码是一大串、看不出分组，而且只能选中某一段 | 分组被渲染成了**独立的 `<span>` 元素**，因此"选中一部分再复制"只能拿到一组；而复制按钮写入的又是去掉连字符的裸串（`ABCD…`），与屏幕上带连字符的呈现不一致 | 显示改为**一整段可自然选中的文本**，分组通过等宽字体与窄间隔体现，而不是独立可选元素；复制按钮改为写入**完整原文（含连字符）**，与屏幕所见一致。后端 `normalize_recovery_code` 本来就会忽略连字符，因此粘贴时带不带都可用 |
| 无法把恢复码保存成 PDF | 项目没有 PDF 依赖，装一个属于新增第三方依赖 | 改用系统打印对话框的「另存为 PDF」：新增 `RecoveryPrintSheet` 渲染一张打印件，`index.css` 的 `@media print` 段在打印时隐藏屏上一切、只显示它。不新增依赖，产出的是真正的 PDF |
| 用恢复码重置时，三个输入框放一起，出错却总聚焦第一个，用户以为恢复码抄错了 | 三步合一时错误提示与 `autoFocus` 都落在表单第一个输入框上 | 拆成两步（详见下） |

打印实现有三个必须记住的约束，都写在 `index.css` 的注释里：

1. `@media print` **不能放进 `@layer`**——分层样式优先级低于未分层样式，而这些规则要覆盖 `dark-theme.css` 里未分层的深色映射；一旦被包进 `@layer`，打印件会带着深色底色输出（费墨且难读）。
2. 必须放在 `dark-theme.css` 之后（文件末尾），两者优先级相同，靠后加载取胜。
3. 显式强制浅色（`color-scheme: light` + 重写颜色），不能指望深色模式下自动输出白底。

**两步恢复流程。** 新的交互是：进入恢复界面后**只有一个输入框**（恢复码），核验通过才进入第二步（两个新密钥输入框）。这样每个屏幕只有一个待完成的动作，错误提示必然指向真正出错的那项。

后端配套拆成两个命令：`verify_recovery_code` 只核验、**不修改任何状态**，通过后签发一个 10 分钟有效的一次性令牌；`reset_access_key_with_recovery_code` 消费令牌并设置新密钥。

令牌在内存中只保存**命中的那一枚恢复码的下标**（`matched_index`），不保存码原文，也不保存任何摘要。原因有两层：后端只存 Argon2id 哈希，每次哈希结果都不同，无法事后逐字节比对；而把原文留在内存里等于多存一份明文凭据。保存下标则足够——第二步只作废这一枚。令牌单次使用、10 分钟过期、签发时顺手清理过期条目，重置成功后用户改由新密钥进入。这**不构成额外攻击面**：拿到令牌需要先通过恢复码核验，而核验成功后本来就能直接重置。

（早期实现保存的是「归一化恢复码的 SHA-256 摘要」，但下游没有任何代码使用它——它既不能定位要作废哪一枚，也无法被校验。这是一处从旧设计残留下来的死数据，后来改为 `matched_index`。）

### 7.5 恢复码改为「多枚独立短码」+ 对比度与卡住问题

上一轮把恢复码做成**一枚 32 字符的长码、按 4 字符分组显示**。这个形态本身有歧义，本轮推翻重做。

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 用户把一整串长码读成"多个恢复码"，只输入其中一组，于是每次都报错 | **形态歧义**：一整串按组分隔的字符既像一个码，也像几个码，用户无法自行判断该输整串还是输一组 | 改成**互不相干的短码**（每枚 20 字符，分 4 组），列表里一行一枚、带序号、各带独立复制按钮。一行就是一个完整凭据，不存在"要不要全输"的疑问 |
| 「复制完整恢复码」「存为 PDF / 打印」和提示文字太淡，几乎看不见 | 这几个元素位于深色授权界面上，我用了 `text-gray-100` / `text-emerald-200` 这类低对比度颜色，且叠在已带透明度的底色上 | 全部提到 `text-white` / `text-gray-200` 以上，按钮改用实色底配 `font-semibold`，边框也加重 |
| 用恢复码真的重置成功后，点「我已保存，继续」直接卡在那个界面 | `finishIssuedCode` 只做了 `refreshAuth()`，把"界面该切到哪一屏"完全交给 boot 状态机。一旦 boot 因为任何原因没有推进（或 `refreshAuth` 抛错被静默吞掉），界面就停在 `created` 模式 —— 而这个模式只渲染恢复码面板，于是留下一个空白面板 | 补两件事：**显式把 mode 切回 `unlock`** 作为兜底，并对 `refreshAuth` 加 try/catch，失败时把原因显示出来而不是吞掉 |

**短码的语义**（与 GitHub / Google 的备份码一致）：

- 每枚各能用一次；忘记密钥时输入**任意一枚可用**的即可。
- 丢了几枚还有其余可用，不必因为抄漏一枚就作废全部。
- 单枚 100 bit 熵。多枚合计**不等于** 100×N bit —— 攻击者只需猜中任意一枚，因此有效强度由单枚决定，这仍远超暴力搜索能力。
- 审计日志记录命中的是第几枚（`recovery-reset#2`），便于排查同一张纸被反复使用。
- **用掉一枚只作废那一枚，其余保留**；重新生成才作废整套。原因见 4.7 节。

**枚数后来从 8 调整到 3。** 理由是枚数越多列表越长、收益递减，而 3 枚足以覆盖「抄漏一枚」与「分两处存放」这两件真实会发生的事。调整时有两个只在 8 枚下成立的测试硬编码了 `codes[3]` / `codes[5]` 之类下标，已改为取最后一枚，以后改数量不会再让测试误报。

**升级路径（必须记住的一点）。** `recoveryHash` 从 `Option<String>` 变成 `Vec<String>`，旧值无法解析。这里刻意**不让整个 `auth.json` 解析失败**——那会连访问密钥一起回落到默认值，用户会被要求重新设置密钥，等同于数据灾难。`config::load_from_with_reason` 的策略是：先尝试"只移除恢复码字段"后重新解析，成功则只清除恢复码、保留密钥/设备/日志，并立刻回写文件。因此升级后用户只需重新生成一套恢复码。

**顺带修正。** 归一化的最小输入长度从 16 降到 12：原来的阈值偏高，用户抄漏一组时会得到"格式不对"而不是"恢复码不正确"，后者才准确。

### 7.6 产品改名、版本转正、标识重做与主题配色

**产品改名 LoopCore → Modulith Desktop（1.0.0）。**

| 项目 | 旧 | 新 |
| --- | --- | --- |
| 显示名 | `Loop Core` / `LoopCore` | `Modulith Desktop`（简称 `Modulith`） |
| 版本 | `0.3.0`（`dev`） | `1.0.0`（`stable`） |
| 应用标识符 | `com.metazero_tsip.loopcore` | `com.metazero-tsip.modulith` |
| npm / Cargo 包名 | `loopcore` | `modulith-desktop` |
| Rust lib 名 | `loopcore` | `modulith_desktop_lib` |
| 插件宿主对象 | `window.LoopCore` | `window.Modulith` |
| 常量 | `LOOPCORE_VERSION` | `MODULITH_VERSION` |
| 存储键 | `loopcore.theme` / `loopcore.auth.token` | `modulith.theme` / `modulith.auth.token` |

**`engines.loopcore` 刻意保持不变**（插件清单的契约字段名，不是产品名）。改它会让所有已发布插件的清单解析失败、安装被拒。

**应用标识符变更会导致既有数据「消失」。** Tauri 不会在 identifier 变化时迁移数据，新目录是空的。因此访问密钥、恢复码、已装插件、侧边栏配置都需要重建。数据仍留在旧目录里，可手动找回。这是改名的一次性代价，已经用户知情同意。

**标识符里的下划线是非法字符，会让打包直接失败。** 改名时曾写成 `com.metazero_tsip.modulith`，保留了下划线，结果 `pnpm tauri build` 在读取配置阶段就报错：

```
The bundle identifier "com.metazero_tsip.modulith" set in `"tauri.conf.json" identifier`.
The bundle identifier string must contain only alphanumeric characters (A-Z, a-z, and 0-9),
hyphens(-), and periods (.).
```

Tauri 对 identifier 只允许**字母数字、连字符、句点**三种字符。下划线不在其中，而它在反向域名式写法里看起来很自然（`metazero_tsip` 是用户名），因此容易写错。这个校验发生在构建早期，`pnpm tauri dev` 同样会失败。

现取值 `com.metazero-tsip.modulith`，即把下划线换成连字符。附带的一次性后果：数据目录从 `%APPDATA%\com.metazero_tsip.modulith` 变为 `%APPDATA%\com.metazero-tsip.modulith`，需要重新设置访问密钥。这也是本次改名周期内第二次因 identifier 变动清空数据 —— 属于命名问题的连带成本，不是设计取舍。

**标识重做（三次迭代，前两版都推翻了）。**

| 版本 | 方案 | 为什么不要 |
| --- | --- | --- |
| v1 | 四格填满 + 中间十字 | 就是个通用的「网格 / 启动器」图标，与产品名无关 |
| v2 | 白色内嵌块 + 三个深色格 | 视觉重心散掉，读作「一个空的容器」 |
| v3（采纳） | 整块底 + 三枚方块，**右上角留空** | 空位表达「还可以继续装」，正是「需要什么功能就加什么模块」的字面含义；不对称使它区别于通用网格图标 |

配套处理：

- 三个界面的占位 logo（原先各自内联一份「渐变方块 + 字母 L」，尺寸圆角都不一致）统一到 `src/components/icons/AppLogo.tsx`。

| 已知问题与技术债的恢复码令牌说明 | 称保存「归一化恢复码的 SHA-256 摘要」 | 早已改为保存命中的下标 `matched_index`；摘要是一项无消费方的死数据 |

### 7.7 标签页、全局搜索与通知系统

本轮针对的是一个此前没有被解决的目标：**防止注意力中断**。在多个功能之间切换的真正成本不是「点一下侧边栏」，而是切走再切回时必须重建现场 —— 滚动位置、未提交的表单、正在编辑的草稿全部丢失，而重建需要主动回忆「我刚才做到哪了」。把功能集中到一个外壳里只是必要条件，状态保持与注意力路由才是充分条件。

#### 模块标签页与保活

| 项目 | 说明 |
| --- | --- |
| 状态归属 | `tabStore` 是「当前显示哪个模块」的唯一来源；`SidebarContext` 不再自己持有 `activeModule`，而是读它 |
| 为什么改归属 | 同一个模块可能被侧边栏、标签栏、命令面板三条途径激活。各自维护一份必然漂移，表现为「点了侧边栏但标签高亮没变」 |
| 惰性挂载 | 标签只在其**首次被激活**时挂载，之后不再卸载。重启恢复十个标签不会一次挂载十个模块 |
| 隐藏方式 | `absolute inset-0 + visibility:hidden`，**不是** `display:none` —— 后者让元素失去盒子，多数浏览器随之丢掉 `scrollTop`，「滚动位置保留」这个目标就落空了 |
| 关闭语义 | 允许关到零标签并渲染空态，不自动回落。强行回落会让「关掉最后一个标签」看起来毫无反应 |
| 上限 | 12 个（前后端各有一份常量，必须一致）。达到上限时**拒绝并提示**，而不是淘汰已打开的标签 |
| 生命周期 | `openTabs` 与 `activeTab` 随设置持久化（`settings.json`），重启后恢复 |

`SidebarContext` 的历史栈与标签顺序是两回事，刻意分开：标签顺序是用户拖出来的排列，历史顺序是他实际去过的地方。混在一起会让「后退」跳到标签栏上的相邻位置，那不是用户期望的语义。

#### 后台存活管理

保活带来一个必须一起解决的问题：切走的标签不卸载，它的定时器、轮询与订阅会照常运行。宿主对此**提供感知，不提供强制**。

`useModuleActive()` 返回「该标签是否激活**且**窗口是否可见」。宿主无法代为暂停模块的后台工作 —— JS 里拿不到模块创建的 `setTimeout` / `setInterval` 句柄，重写全局定时器会影响包括宿主与 React 在内的所有代码。因此这是一个约定：模块自己在 `useModuleActive()` 为 false 时停掉后台工作。

这条约定目前**只对愿意遵守的模块生效**，没有强制机制。对插件同样如此，所以一个写得不负责任的插件可以在后台持续消耗资源。这一点在插件系统架构第 6.2 节标注为「资源限额：无内存或 CPU 限制」。

#### 全局搜索与命令面板

`commandRegistry` 提供命令注册表，`searchCommands` 负责匹配。模块类条目**不注册进表**，而是在搜索时从目录派生 —— 目录是动态的，镜像成命令列表就需要一套同步逻辑，而同步逻辑正是本项目反复踩坑的地方（见 `useModuleList` 的注释）。派生是纯函数，永远与目录一致。

打分规则与理由：完全相同 1000 分、前缀 800、包含 500、子序列 200 起。子序列匹配是模糊搜索的核心（输入 `dsh` 命中 `dashboard`），但它必须排在精确匹配之后，否则输入完整模块名时会被一堆松散匹配挤下去。最近使用过的命令额外加权，因为重复打开同一个模块时不该重新输完整名字。

#### 通知系统

后端新增 `notifications` 模块（7 个命令，`notifications.json`，上限 200 条）。写入、读取与裁剪策略见该模块源码注释。

三个值得记录的决定：

| 决定 | 理由 |
| --- | --- |
| 命令全部返回「当前完整列表」而不是被改动的那一条 | 只返回一条会让前端必须自己维护「新条目插到哪、合并键命中时改哪条、裁剪时删哪些」三处逻辑，与后端保持一致才能工作，一旦漂移就是界面与磁盘不一致。上限 200 条，多传几十 KB 换「前端整个替换缓存」是划算的 |
| `dedupeKey` 同键未读合并为一条并计数 | 模块很容易在重试循环里连续产生同一条通知（例如「网络不可用」），没有它通知中心会被同一条信息刷满，用户反而看不到真正重要的那条 |
| 错误级提示不自动消失 | 出错时用户需要读完再决定怎么办，3 秒后自己跑掉会让人怀疑「刚才是不是弹了什么」 |

`toast.ts`（不持久化的一次性反馈）与 `notifications.ts`（持久化的事件记录）刻意分成两个系统：把「已复制」写进磁盘并在通知中心留一条记录是明显的噪音；而把「插件加载失败」做成 3 秒就消失的提示则会让用户错过它。

**仍未实现：系统级通知。** 那需要引入 `tauri-plugin-notification` 依赖，当前版本不新增依赖，因此应用关闭时无法提醒。`notification` 权限的说明也已从「系统通知」改为「应用内通知」，避免名实不符。

#### 跨模块事件总线

`eventBus` 让模块之间可以协作（任务模块的待办出现在仪表盘上）。同步投递、按来源批量注销、主题名白名单字符集，理由都写在源码注释里。需要 `plugin-communicate` 权限。

它带来的是「模块之间可以协作」，**不是**「模块之间互相隔离」—— 总线上没有权限隔离，声明了权限的插件可以订阅任意主题。

#### 保活带来的行为变化

保活不只是「状态不丢」，它还改变了模块的生命周期语义，模块作者需要知道：

| 变化 | 说明 |
| --- | --- |
| 入场的错峰动画只播一次 | 以前每次切到模块都会重挂载，`framer-motion` 的 stagger 动画会重播；现在只在首次挂载时播一次。这消除了切换时的动画闪烁，但依赖「每次进入都播动画」来提示状态的模块需要改用别的方式 |
| 挂载副作用只执行一次 | `useEffect(..., [])` 里的初始化（拉数据、建订阅）不再随每次切换重跑。这对性能是好事，但「每次进入都刷新一遍」的旧假设不再成立 |
| 后台期间组件仍在运行 | 定时器、订阅、动画都会继续。需要暂停的后台工作要用 `useModuleActive()` |
| 卸载时机与关闭标签对齐 | 在此之前「离开模块」等于卸载；现在只有关闭标签或刷新才会卸载，因此清理逻辑（`useEffect` 的 return）会推迟到那时才执行 |

对插件而言，第二条与第三条影响最大：插件此前可以假设「用户每次打开模块都是一次全新的执行」，现在必须把初始化与刷新分开考虑。

#### 本轮仍未解决的问题

诚实记录，避免下一个人以为这些已经做过了：

| 问题 | 现状 |
| --- | --- |
| 模块保活没有内存上限之外的淘汰策略 | 上限 12 个标签，超过则拒绝；不会根据实际内存占用调整 |
| 后台工作依赖模块自律 | 无强制暂停机制，见上文 |
| 搜索不搜模块**内容** | 只搜模块名、子模块名与宿主/插件命令。功能多起来之后「我知道有这个功能但不知道在哪个模块」这类问题仍未完全解决 |
| 搜索无结果时面板直接消失 | 没有「无匹配项」的提示。当前的处理是「结果为空则不显示面板」，用户看到的是一片安静。补一个空态提示是明确可做的小改进 |
| 没有「工作场景」概念 | 收藏与置顶是模块级的，不是任务级的。做一件事需要同时开三四个模块时，无法把这一组存下来一键恢复（持久化的标签部分覆盖了这个需求，但只有一组） |
| 通知没有分类与优先级 | 只有 info/success/warning/error 四个级别与来源模块，不能按模块静音或分组折叠 |
| 无 OS 级通知 | 见上文 |

### 7.8 审阅修复：构建链路、插件 ID 路径穿越与外壳依赖

本轮由一次独立审阅触发：逐条核对「文档声称」与「代码实际」，把不符的部分修掉或如实记录。**其中前两项是真实缺陷，不只是文档问题。**

#### 前端类型检查失败，发布构建链路是断的

| 项目 | 说明 |
| --- | --- |
| 现象 | `npx tsc -p tsconfig.json --noEmit` 退出码 2，`src/services/commandRegistry.ts` 有 8 处 `TS6133`（未使用导入）：`activateRelativeTab`、`setAccentId`、`getAppDataDir`、`getCachedSettings`、`ACCENT_THEMES`、`requestSearchFocus`、`registerShortcuts`、`openPath` |
| 影响 | `package.json` 的 `build` 是 `tsc && vite build`，而 `tauri.conf.json` 的 `beforeBuildCommand` 是 `pnpm build` —— **`pnpm tauri build` 必然失败**。README 的「提交前检查」第一条命令当时就是红的 |
| 根因 | `commandRegistry.ts` 在 `tsconfig` 的 `noUnusedLocals: true` 下遗留了重构后的死导入 |
| 处理 | 删除这 8 个导入，`tsc` 恢复退出码 0 |

**这条值得记住的教训**：类型检查不是「没报错就没事」，而是「不跑就不知道」。这些导入在 `vite dev` 下完全无害（打包器会摇树掉），因此日常开发不会暴露，只有真正执行 `tsc` 才看得见。

#### 插件 ID 未校验导致路径穿越（安全问题）

| 项目 | 说明 |
| --- | --- |
| 现象 | `PluginManager::storage_clear` **完全没有** ID 守卫，直接 `remove_dir_all(plugin_data_dir(id))`；而 `plugin_data_dir` 是未校验的 `data_dir.join(id)`。命令层 `plugin_storage_clear` 也不校验 |
| 利用路径 | `id = ".."` → 目标解析为 `<app_data>/plugin_data/..`，即应用数据目录本身 → `remove_dir_all` 会把 `settings.json` / `auth.json` / `notifications.json` / `sidebar_config.json` 连同全部插件数据一起删掉 |
| 第二条路径 | `uninstall` 的守卫是 `validator::is_within(&plugins_dir, &plugins_dir.join(id))`，而 `is_within` 是纯前缀比较，`candidate == root` 时返回 **true**。`id = "."`（或 `plugin_data/..`）使目标规范化后等于 `plugins_dir`，守卫放行 → 整个 `plugins/` 目录被删，**包括 `registry.json`** |
| 为何危险 | docs 自己承认「插件可以直接 `invoke` 任意后端命令」，而这几个命令**不带 token 参数**。因此一个插件无需经 `ctx.storage` 就能直接触发，不需要任何权限声明 |
| 处理 | ① `validator::is_valid_plugin_name` 提升为 `pub`，并新增 `manager::validate_plugin_id`；② `plugin_data_dir` 改为**带校验**的入口（返回 `PluginResult<PathBuf>`），所有调用点因此自动受保护 —— 校验收在一处，漏掉任一调用点就等于没有防护；③ `uninstall` 开头显式校验 ID，`storage_clear` 增加「目标必须严格位于 `data_dir` 之下」的不变量检查；④ `is_within` 改为要求 `candidate != root` |
| 回归测试 | 新增 `plugin_name_rejects_path_traversal_inputs`（14 个穿越取值）与 `is_within_rejects_root_itself`。**后者已验证过有效性**：临时还原旧的纯前缀比较后该测试确实 FAILED，恢复修复后转绿 |

**`is_within` 的语义修正值得单独记住。** 它的两个调用点都是**删除**语义，而 `root` 自身作为删除目标一定是误用 —— 调用方要的是「root 里的某个条目」。只比较前缀是这类守卫最典型的错误写法，因为它同时放行了 `root` 本身与所有 `root/../...` 绕回 `root` 的路径。

#### 外壳对业务模块的静态依赖（架构不变式不成立）

| 项目 | 说明 |
| --- | --- |
| 现象 | 架构总览第 1 节主张「框架代码中不存在任何对具体业务模块的引用」，据此推出「删除任意内建模块，框架仍能编译并运行」。但 `SettingsDialog.tsx` **静态导入**了 `../../modules/plugins/Plugins` 并在「插件」分页渲染它 |
| 影响 | 删掉 `src/modules/plugins/` 会让外壳编译失败，上面两条结论都不成立 |
| 处理 | 新增 `src/components/ModuleEmbed.tsx`，设置页改用它内嵌 |

**实测得到的、与直觉相反的结论：把静态 import 改成动态 `import('../modules/plugins/Plugins')` 并不够。** TypeScript 仍会对字面量说明符做静态解析，模块缺失时报的仍是 `TS2307`。实测过程：移走 `src/modules/plugins/` 并重新生成注册表（生成器正确产出「2 modules」）后，报错只剩这一条。**把说明符换成变量**（`import(specifier)` 配 `/* @vite-ignore */`）之后才真正编译通过。

验证方式（两个方向都实测过，不是推断）：

| 场景 | 结果 |
| --- | --- |
| 保留模块 → `tsc` | 通过 |
| 移走模块 + 重新生成注册表 → `tsc` | **通过**（不变式成立） |

代价如实记录：该模块不再被 Vite 预打包，改为首次打开「设置 → 插件」时按需加载；模块真的被删除时，错误发生在**打开设置页的那一刻**而不是构建期，因此 `ModuleEmbed` 用错误边界把它降级成一条可读提示，而不是冒到顶层变成整窗错误页。

### 7.9 深色模式亚层配色与标签切换的动画残留

#### 深色下标题栏/标签栏/搜索框渲染成灰色

| 项目 | 说明 |
| --- | --- |
| 现象 | 深色模式下，二级标题栏（标签栏）整条渲染成灰白色，全局搜索框也是浅灰而不是深色 |
| 根因 | **`bg-white/90` 与 `bg-white` 是两个不同的类名 token**，`[class~='bg-white']` 不会命中前者，因此 `dark-theme.css` 必须**逐个列出**用到的不透明度档位。当时列了 `/90`、`/80`、`/70`、`/60`、`/50`，而标签栏用的是 **`bg-white/85`**、搜索框是 **`bg-gray-50/80`** —— 两档都不在表里，于是原样保留浅色。**漏一档不报错，只表现为深色界面里出现一块灰白** |
| 排查方式 | 把「项目里用到的 `bg-*` 类」与「dark-theme.css 已映射的类」做差集，共发现 35 个未映射项；其中多数是有意为之（`bg-indigo-500` 等强调色由主题变量驱动、`bg-red-500` 等语义色两种模式通用），真正属于「大面积表面漏映射」的就是上面两档 |
| 处理 | ① 把 `/85`、`/95`、`gray-50/80`、`gray-50/60` 补进映射表；② **标题栏与标签栏统一为同一不透明色 `#151823`** —— 二者是相邻的窗口亚层，背后就是应用底色，半透明只会让两块亚层深浅不一、出现色带分界，不透明之后它们在视觉上连成一整块；③ 搜索框按「下沉输入区」处理，用比面板更深一档的 `#0e111a` 表达「凹进去的输入位」，而不是靠灰 |
| 顺带修掉 | 搜索框原来的 `focus:bg-white` 是**变体**类，属性选择器同样命中不到，聚焦时会闪出一块白底。已移除该变体，聚焦只改描边与光环 —— 聚焦时底色跳变本身也是一种突兀 |
| 验证 | 用脚本计算了实际对比度（WCAG）：标题 16.08:1、激活标签 15.09:1、未激活标签 6.97:1、图标 6.97:1、搜索文字 17.13:1，全部高于 4.5:1（图标 3:1）；亚层分离度 1.066:1，可辨识而不过分 |

#### 切换模块时几个卡片短暂停留

| 项目 | 说明 |
| --- | --- |
| 现象 | 从仪表盘切到别的模块时，有三张卡片会在新页面上停留一小会儿才消失；理想情况下切换应当是瞬时的 |
| 根因 | **不是「没隐藏」，而是「隐藏之后动画还在跑」**。标签保活让切走的模块留在 DOM 中（刻意的），仪表盘的统计卡片带入场延迟 `delay: 0.15 + i*0.06`，即 index 2/3/4 分别延迟 0.27/0.33/0.39 秒 —— 用户切走时它们刚播到前几帧，**用户看到的「三张」正是延迟最长的那三张**。而 `visibility: hidden` 只让元素不参与最终绘制，**并不暂停动画**，合成器仍会把中间帧画出来 |
| 为什么不能简单换隐藏方式 | `display:none` 会让元素失去盒子、丢掉 `scrollTop`，而「切回来还在原处」正是保活的核心目标。`content-visibility: hidden` 更彻底，但 MDN 对其语义的说明是 "similar to giving the contents `display: none`"，与滚动位置保留存在冲突风险（CSSWG 也讨论过 skipped 子树的滚动位置恢复）。在不能实测的前提下，**不拿保活的核心不变量去换一个性能属性** |
| 处理 | 三层收口，都只作用于非激活标签：① CSS 暂停动画与过渡（`animation-play-state: paused`，停在当前帧而不是跳到终态，避免切回来时看到跳变）；② 宿主传入 `initial={false}`，让**包裹层**跳过初始态直接渲染终态；③ 用 `!important` 把非激活子树钉在 `opacity: 1` / `transform: none` 的终态 —— framer-motion 是写**行内样式**的（`element.style.opacity = …`），行内样式压不过 `!important` 的样式表规则，这是确定性的最后一道 |
| 一个必须记住的实测结论 | **`MotionConfig reducedMotion="always"` 不能解决这个问题。**我读了安装的 framer-motion 12 源码：`motion-dom` 的 `visual-element-target.mjs` 里是 `shouldReduceMotion && positionalKeys.has(key) ? { type: false } : valueTransition`，而 `positionalKeys` 只含 width/height/top/left/right/bottom 与 transform 系列 —— **`opacity` 不在其中**。卡片残留的可见表现恰恰是 opacity 淡入，因此单靠 reducedMotion 会留下这个 bug。这一点与「官方文档说 reducedMotion 会关闭动画」的直觉相反 |
| 验证 | CSS 结构与选择器一致性由脚本核对（花括号配平、规则存在性、选择器与 `data-active` 标记一致、且确认未退回 `content-visibility`/`display:none`），全部通过 |

**这两条都提示了同一个模式**：`dark-theme.css` 的「按类名映射」（5.2 节）和标签保活（7.7 节）都是**有明确代价的设计取舍**，而代价集中体现在「漏了一项不会报错，只会表现为某处看起来不对」。前者漏一档颜色就退回浅色，后者漏停一类动画就出现残留。这类问题无法靠类型系统发现，只能靠清单式核对与小心的收口规则 —— 这也是本轮把「映射漏项差集」写成可复跑脚本的原因。

### 7.10 亚层分隔线与折叠态「展开」入口的位置

#### 标签栏底边的浅色细线（深色下像白边）

| 项目 | 说明 |
| --- | --- |
| 现象 | 深色模式下标签栏底部有一条细白/浅色边线，与整体深色不协调 |
| 根因 | 标签栏用的是 `border-gray-200/70`，而 `/70` **不在** `dark-theme.css` 的映射表里（只列了 `/50`、`/60`），于是原样保留浅色。与 7.9 节的底色漏项是同一类错误，只是这次出在边框上 |
| 处理 | ① 把 `/70` 补进映射表；② 更关键的是**改掉勾边思路本身**：窗口亚层的分界应当"压下去"而不是"提起来"，因此标题栏与标签栏的底边改用比面板更暗的 `#0a0c12`，表达的是一道浅浅的接缝，而不是一条亮线 |
| 取值的依据 | `#0a0c12` 与亚层的对比约 **1.10:1**。这个量级是刻意选的：本项目既有的层次基准本身就很安静 —— 应用底与亚层之间只有 1.066:1。因此分隔线也应当落在这个量级，比它更暗会显得脏，更亮就又回到"勾白边"的问题 |
| 为什么只对窗口亚层生效 | `/50`、`/70` 也被浮层（右键菜单、插件卡片、下拉面板）使用，它们需要的是常规边框色 `#2c3242`。深色下给浮层描一道近黑边会让它看起来像一块硬邦邦的补丁，而不是浮在内容之上。判据用 `backdrop-blur-xl` —— 本项目里只有窗口亚层用它 |

**这条与 7.9 节合起来是一个必须记住的模式**：`dark-theme.css` 按类名精确映射，**底色、边框、透明度档位各自都要单独列**，漏掉任何一维都不报错，只表现为「深色界面里某处颜色不对」。这轮两处缺陷（底色的 `/85`、边框的 `/70`）属于同一个根因的两个面。

#### 折叠侧边栏后「展开」按钮挡住标签栏

| 项目 | 说明 |
| --- | --- |
| 现象 | 侧边栏收起后，右上角（实际是窗口左上偏下）留着一个「展开」按钮，它挡住了二级标题栏 |
| 根因 | 按钮是 `fixed left-4 top-14 z-50`。`top-14` = 56px，而标签栏占据 **40~76px**，按钮（约 36px 高）横跨 56~92px；且它 `z-50` 高于标签栏的 `z-40`，于是直接盖住了标签栏左端与第一个标签 |
| 需求约束 | 用户明确指出**不接受**在折叠态加一个常驻的小型侧边栏 —— 那会永久吃掉内容区宽度，损害模块的全屏与沉浸式体验。这个约束是对的：常驻窄条换来的是"多一个入口"，付出的却是所有模块永久少一块画布 |
| 处理 | 「展开」入口**并入标签栏左端**，作为标签栏内部的一个固定槽位（`shrink-0`），标签从它右侧开始排列。这样按钮与标签栏同层同高、不遮挡任何标签，也**不引入常驻窄条**，内容区在折叠态依然是满宽的（`ml-0`） |
| 入口唯一性 | 展开入口仅在 `!isOpen` 时渲染；折叠入口在侧边栏头部（`PanelLeftClose`），而 `Sidebar` 在折叠态直接返回 `null`。因此任一状态下两个入口只有一个存在，不会重复或互相遮挡 |
| 验证 | 用脚本核对了：旧浮动按钮已消失、按钮位于标签栏内部（受 `items-stretch` + `h-9` 约束，不可能溢出 40~76px）、`shrink-0` 防止被标签挤压、折叠态 `ml-0` 未被挤占、两入口互斥 |

### 7.11 发布前的仓库整备

本轮为首次公开发布做准备。**第一项是真实缺陷，会让任何新 clone 的人构建失败。**

#### `pnpm build` 在全新 clone 上必然失败

| 项目 | 说明 |
| --- | --- |
| 现象 | `pnpm build`（以及 `pnpm tauri build`）在刚 clone 的仓库上失败，`tsc` 报 4 条 `Cannot find module '../generated/...'` |
| 根因 | **两个事实叠加**：① `src/generated/` 是构建期产物，被 `.gitignore` 排除，因此新 clone 里不存在；② 生成它的 `scripts/generate-modules.ts` 原本只在 **Vite 插件**里被调用，也就是只在 `vite build` 阶段运行。而 `build` 脚本把 `tsc` 排在 `vite build` **之前** —— `tsc` 面对一个还没生成的目录 |
| 影响 | 这是开源项目最糟的一类问题：**第一个想试用的人就卡住**。而且它对本机开发者不可见，因为本地 `src/generated/` 一直存在 |
| 处理 | `build` 与 `dev` 脚本都在 `tsc` / `vite` 之前插入 `pnpm gen:modules` |
| 验证 | **实测复现再验证**：先移走 `src/generated/` 复现失败（`tsc` 退出码 2，4 条 TS2307），应用修复后在同一状态下按 `ver check → gen:backend → gen:modules → tsc` 顺序执行，`tsc` 退出码 0 |

**同一个陷阱还有第二个入口。** README 与贡献指南的「提交前检查」都让贡献者直接运行 `npx tsc`，而新 clone 下同样会失败。两处文档都已补上 `pnpm gen:modules` 这一步，并说明「只有直接调用 `tsc` 时才需要留意这个顺序，`pnpm build` / `pnpm dev` 会自动处理」。

#### 其它发布整备

| 项目 | 处理 |
| --- | --- |
| `tsconfig.node.tsbuildinfo` 被跟踪（57.6 KB） | 这是 TypeScript 增量编译缓存，属构建产物。已 `git rm --cached`（保留磁盘文件）并在 `.gitignore` 加入 `*.tsbuildinfo` |
| `.gitignore` 里 `!src/generated/.gitkeep` 指向不存在的文件 | 该例外规则没有对象，且 `src/generated/` 本就不需要入库（生成器会自行 `mkdirSync`）。已改为整体排除 `src/generated/`，并注明不要为它留占位文件 |
| 缺少 `.gitattributes` | Git for Windows 默认 `core.autocrlf=true`，而仓库现有文本文件全是 LF。没有 `.gitattributes` 时，Linux/macOS 贡献者与 CI 会与本地产生换行符不一致，表现为 PR 里整文件 diff。已新增：统一 `eol=lf`，二进制与 `.bat`/`.ps1` 单独声明，锁文件与生成文件标记 `linguist-generated`（GitHub 默认折叠其差异、不计入语言统计） |
| 缺少 `.editorconfig` | 与 `.gitattributes` 分工不同：前者管「仓库里怎么存」，后者管「编辑器写出什么」。已按既有代码风格补齐（两空格、LF、末行换行） |

**这两件事合起来说明一个模式**：`.gitignore` / `.gitattributes` / `.editorconfig` 这类文件平时没有存在感，问题只在**别人第一次接触仓库**时才暴露 —— 与 7.10 节的结论一致。

### 7.12 应用标识符变更与个人账号名脱钩

| 项目 | 说明 |
| --- | --- |
| 背景 | 标识符原为 `com.metazero-tsip.modulith`，其中 `metazero-tsip` 是开发者**旧**的 GitHub 账号名（后更名为 `Rinntheor`），且该值形式上假定拥有 `metazero-tsip.com` 这个并不存在的域名 |
| 问题 | 反向域名式标识符的语义前提是**控制对应的命名空间**。把个人账号名写进标识符，既会随账号改名而过时，也不构成有效的命名空间 |
| 现取值 | `com.rinntheor.modulith` |
| 时机说明 | **这是变更标识符的最后合理时机。** 未发布时改动只影响开发者本人（需重设访问密钥）；一旦有真实用户，标识符变更会让所有用户的数据目录换位置——Tauri **不做迁移**，表现为访问密钥、恢复码、设备白名单、已装插件、全部设置与通知一次性不可见。此外 Windows 安装包会把它当成另一个产品，旧版不会被升级而是并存 |
| 影响范围 | 数据目录：`%APPDATA%\com.metazero-tsip.modulith` → `%APPDATA%\com.rinntheor.modulith` |
| 如何保留旧数据 | 各数据文件的**格式不依赖标识符**，因此可直接把旧目录内容复制到新目录：把 `%APPDATA%\com.metazero-tsip.modulith` 下的 `settings.json`、`auth.json`、`notifications.json`、`sidebar_config.json`、`plugins/`、`plugin_data/` 复制到 `%APPDATA%\com.rinntheor.modulith`。这样访问密钥与已装插件都不会丢 |
| 同步位置 | `src-tauri/tauri.conf.json`（唯一实际配置）、`README.md` 的命名表、本条记录 |

**标识符自此冻结。** 它与产品名（`Modulith Desktop`）、包名（`modulith-desktop`）是三个不同的东西：包名可以随构建调整，产品名可以改显示文案，**只有标识符动不得**——它一旦随版本变化，用户数据就会"丢失"。`pnpm ver check` 会校验产品名一致性，但**不会**校验标识符（它不该变，因此没有可校验的基准）。

### 7.13 生成器写时间戳导致不可重复生成

| 项目 | 说明 |
| --- | --- |
| 现象 | 每运行一次 `pnpm gen:backend update`，`src-tauri/src/lib.rs` 与 `modules/mod.rs` 都会显示为已修改，而**内容其实只有一行「生成时间」不同** |
| 根因 | 两个生成器模板的头部写入了 `// 生成时间: ${new Date().toISOString()}`，而这两个文件是**入库**的（不像 `src/generated/` 那样被 gitignore） |
| 影响一 | **每次都弄脏工作区**。任何贡献者构建一次就会看到两个「已修改」文件，容易误提交、也干扰 `git status` 的判断 |
| 影响二 | **让「生成器一致性」的 CI 检查无法成立。**该项检查的做法是「跑一遍生成器，然后 `git diff --exit-code`」；只要输出含时间戳，这个 diff 必然非空，检查会永远失败 —— 也就是说它会变成一个没人能修的红色门禁 |
| 处理 | 从两个模板头部移除生成时间行，改为说明「刻意不写时间戳」的原因。生成结果因此**可重复**：同一份源码无论生成多少次，产物逐字节一致 |
| 验证 | 连续生成两次并比对文件哈希，结果一致；生成后 `git status` 对这两个文件为干净 |
| 追溯方式 | 需要知道生成时间时查 git 历史即可。前端生成产物仍有 `generation.log.json` 记录（它被 gitignore，不受此问题影响） |

**这个问题值得记住的地方在于它是我自己引入的。**「生成后 diff 为空」这道检查是可靠的 CI 门禁设计，但在**生成不可重复**的前提下它只会制造一个永远修不好的红灯。检查与生成器的可重复性是**配套要求**：只加检查而不保证幂等，等于给项目装了一个必然失败的闸门。

### 7.14 插件 storage 权限补强制

| 项目 | 说明 |
| --- | --- |
| 背景 | 权限枚举有 11 个取值，但只有 `network`、`network-external`、`notification`、`plugin-communicate` 四项真的生效。`storage` 属于「写进清单也不改变行为」的一类 |
| 触发原因 | 计划新增的「快捷启动」插件会执行外部程序，必然要配一条新权限。若清单里的权限不产生任何约束，那条新权限同样是空话 —— 因此先补齐强制机制，再加能力 |
| 处理 | ① 新增 `PluginManager::require_permission`，作为权限检查的**唯一入口**；② 新增 `checked_storage_dir`，五个 `plugin_storage_*` 方法（`get`/`set`/`delete` 经 `storage_path`，`keys`/`clear` 直接调用）全部经它取目录，因此 `storage` 检查只有一个执行点；③ 新增 `PluginPermission::as_str()`，用于生成可读的错误信息 |
| 为何收在一处 | 与 7.8 的 `plugin_data_dir` 同理：检查散落在各个命令里时，漏掉任何一处就等于没有防护，而且漏掉的那处**没有任何症状**。`uninstall` 仍直接使用 `plugin_data_dir` —— 内部清理不该受插件自身权限声明约束 |
| 行为变化 | **未声明 `storage` 的插件，调用 `ctx.storage` 任意方法都会被拒绝**（错误信息为「插件 X 未声明 storage 权限」）。此前是静默可用。仓库内示例插件一直声明着该权限，不受影响 |
| 判定规则 | 纯函数 `ensure_permission`：**没声明就是拒绝**，不做默认放行、也不按 `sandboxLevel` 推断 |
| 为何抽成纯函数 | `PluginManager` 持有 `AppHandle`，单测里造不出来。判定与 IO 分离后，规则本身可以被测试锁定 |
| 测试 | 新增 5 条：未声明被拒、已声明放行、**只声明 `network` 不放行 `storage`**（防止把检查写成「有任意权限就放行」）、错误信息包含权限名、`as_str()` 与 serde 的 kebab-case 序列化逐个一致 |
| 验证方式 | 用临时改动把 `ensure_permission` 改成恒返回 `Ok(())`（等价于修复前的行为），确认其中 3 条测试**确实失败**，再还原 —— 否则无法证明这些测试不是在空过 |
| 边界（重要） | 这**不是**插件之间的隔离边界。命令的 `id` 来自调用方，插件仍可直接 `invoke` 指定他人 ID 读取其存储。本次修的是「声明是否生效」，不是「越权访问」（见 4.1 节） |
| 文档同步 | [插件系统架构](../02-开发指南/插件开发/插件系统架构.md) 6.1 与 6.2、[清单文件参考](../02-开发指南/插件开发/清单文件参考.md) 第 4 节、[宿主API参考](../02-开发指南/插件开发/宿主API参考.md) 第 2 节 |

**一句话总结这次改动的性质**：它让权限列表从「意图声明」变成「有效声明」，但**没有**把插件之间隔开 —— 那需要进程级隔离，不是加几行检查能做到的。把这两件事混为一谈，才是真正危险的地方。

### 7.15 快捷启动插件与 process-spawn 权限

| 项目 | 说明 |
| --- | --- |
| 目标 | 做一个「把常用程序收在一处、点一下就打开」的插件。它是第一个**需要宿主提供原生能力**的插件，因此也是插件体系的一次真实检验 |
| 为何先补权限强制 | 该插件要执行外部程序，必须配一条新权限。若清单里的权限不产生约束，那条新权限同样是空话 —— 因此 7.14 先行 |
| 新增权限 | `process-spawn`。语义比 `open-external` 更准确，也更该在安装时让人停下来看一眼 |
| 新增命令 | `plugin_launch_program(id, program, args?)`，注册后后端命令数 60 → 61（plugins 模块 18 → 19） |
| 权限检查位置 | Rust 侧 `launch_program` 的首行，复用 7.14 的 `require_permission`。前端 `ctx.launcher` **不做**重复判断 —— 检查应落在动作真正发生的一侧，两边各判一次只会多出一套可能分叉的规则 |
| 路径规则 | 必须绝对路径、必须已存在、必须是文件；经 `canonicalize` 归一化后使用 |
| 这条规则的边界 | 它**拦不住** `C:\Windows\System32\cmd.exe`（同样是绝对路径）。目的不是沙箱，而是让「要执行什么」在代码与清单里显式可见，而不是藏在一个短名字后面。插件本就被视为本机程序（见第 8 节威胁模型） |
| 参数处理 | 作为独立 argv 项传给 `Command::args`，不拼命令行字符串，因此不存在引号 / `&&` / `|` 注入。限制为最多 64 个、单个不超过 4096 字符 |
| 生命周期 | `spawn` 后不 `wait`。快捷启动的语义就是「把它叫起来」，宿主没有理由陪着子进程活着 |
| 为何不用 opener 插件 | 宿主已装 `tauri-plugin-opener`，但它当前的能力范围被有意限制在 `$APPDATA` / `$APPLOCALDATA`（见 `capabilities/default.json`，用于「打开数据目录」等两处调用）。为快捷启动放开到任意路径，会同时削弱那两处既有限制。改为自建命令后，限制落在插件权限模型里，是用户能在插件详情页看到的那一条 |
| 示例插件 | `samples/quick-launch`：手写 IIFE（无构建步骤，示例的核心价值是可读可复制）、自带 `index.css`（Tailwind 在构建宿主时扫描源码，运行时注入的类名不会被生成）、`main` 指向根目录的 `index.js`（避开被 gitignore 的 `dist/`） |
| 测试 | 新增 9 条：权限未声明被拒、已声明放行、相对路径/裸程序名被拒、空值与 NUL 被拒、不存在的路径被拒、目录被拒、真实绝对路径通过、参数规模受限、示例清单能通过 `validate_manifest` 且声明了它实际用到的两项权限 |
| 最后一条测试的意义 | 权限被真正强制之后，「代码用了 `ctx.storage` / `ctx.launcher`，清单却忘了声明」会变成**运行时才暴露**的错误。把它提前到测试里，改示例时不会漏 |

**这件事验证了什么。** 插件体系此前只有 `hello-plugin` 一个示范，它不需要任何原生能力，因此「宿主给插件提供能力」这条路径从未被真正走过。走完之后暴露出一个此前只在文档里写着的约束：**插件能做什么，取决于宿主是否愿意为它开一个口子，而每个口子都必须配一条能被强制、且用户能看见的权限。** 先补强制再加能力，顺序不能反。

（那个示范插件后来被 `samples/notes` 取代 —— 它只是个测试件，功能却还值得留下，见 7.17。）

### 7.16 快捷启动插件完整化：三项宿主能力

| 项目 | 说明 |
| --- | --- |
| 背景 | 7.15 交付的版本只有「添加/打开/删除」，形态过于简陋。这一轮按完整的产品要求重做，并补上它需要的三项宿主能力 |
| 新增命令 | `plugin_extract_icon`、`plugin_reveal_in_folder`。后端命令数 61 → 63（plugins 模块 19 → 21） |
| 新增前端服务 | 宿主侧 `src/services/fileDrop.ts`（订阅 Tauri 窗口级拖放并向多个订阅者扇出）；插件上下文新增 `ctx.icons` / `ctx.shell` / `ctx.fileDrop` |
| 权限归属 | 三项能力**同归 `filesystem-read`**，没有新增权限枚举值。理由：它们获取的都是「本机文件是什么、在哪里」这一类信息，语义上属于同一层；拆成三个新权限只会让插件详情页更难读，而用户并不会因此获得更细的控制力。副作用是 `filesystem-read` 从「声明了也不生效」变成了真正生效的一项 |
| 新增依赖 | `windows-sys = "0.61"`，且只在 `[target.'cfg(windows)'.dependencies]` 下。选它而不是 `windows`：只需要几个 Win32 函数的裸声明，不需要 COM 包装与 Result 化 |
| 图标提取实现 | `PrivateExtractIconsW`（可取任意尺寸，这里用 64×64）→ `GetIconInfo` → `GetDIBits` 取 32bpp BGRA → 转 RGBA → 自写 PNG 编码。**alpha 有两套来源**：32bpp 数据里可能是全 0，此时必须回退到 1bpp 的 AND 掩码，否则图标会变成黑色方块 |
| 为什么不引 PNG 库 | 本项目一贯刻意不引依赖。PNG 的最小可用子集很小 —— 只用 zlib 的**非压缩存储块**，因此不需要 deflate 实现，代价是文件偏大（64×64 约 16 KB）。crc32 / adler32 / 块结构都由测试锁住 |
| GDI 资源泄漏 | `GetIconInfo` 借出的 `hbmColor` / `hbmMask`、以及 `CreateCompatibleDC` 的 DC、`PrivateExtractIconsW` 的 HICON **全部**要在同一函数内释放。GDI 对象有进程级上限，泄漏足够多次会让整个应用画不出东西 —— 因此释放路径刻意写成「无论哪一步失败都会走到」 |
| 拖放为何必须宿主转发 | Tauri 的 `dragDropEnabled` 默认 `true` 时会拦截系统拖放（此时 WebView 内 HTML5 拖放整体不可用），而 `withGlobalTauri` 未开启，插件拿不到 `window.__TAURI__`。两条相加 ⇒ **插件无法自行接收拖入路径**，只能由宿主订阅 `onDragDropEvent` 再转发 |
| 拖放的副作用（未做） | 同一个拦截导致**卡片不能拖到分组上** —— HTML5 `draggable` / `drop` 不可用，要做得自己用指针事件实现一遍。本轮改用右键菜单归类，并在插件 README 与宿主 API 参考里如实标注，没有把「拖拽整理」算作已实现 |
| 拖放的权限边界 | `fileDrop` 的检查在前端（事件不产生 IPC 之外的动作），但它送来的是本机路径，因此与图标、定位同归 `filesystem-read`；未声明时降级为空订阅 + 一次告警，与 `notifications` 的处理一致 |
| 插件重做 | 视图三档（网格/列表/紧凑）、分组筛选与增删改、右键菜单（打开/定位/编辑/复制路径/移入分组/删除）、备注与悬浮显示、编辑对话框；卡片上不放任何按钮 |
| 图标存储策略 | 每个条目的图标单独存 `icon.<条目ID>`，不塞进主状态数组 —— 否则「改个名字」也要重写几十 KB × N 的图标数据。键名用 `.` 而非 `:`，因为存储键只允许字母数字与 `.` `_` `-` |
| 存储向前兼容 | `normalizeState()` 兼容最早那版「直接把数组存在 `shortcuts` 下」的格式。用户数据只有一份，读的时候容错比写的时候谨慎更重要 |
| 测试 | 新增 9 条（总数 138 → 147），全部在 `icon.rs`：crc32 与 adler32 的标准向量、块结构逐块重算 CRC、IHDR 字段、IDAT 的 zlib 头与尾部 Adler-32、存储块 LEN/NLEN 互补、BFINAL 置位、**从真实 exe 取图标**、无图标资源文件明确失败 |
| 最后两条为何关键 | 前面七条只覆盖 PNG 编码 —— 即使 Win32 那段全写错，它们照样全绿。`extracts_icon_from_a_real_executable` 是唯一真正走通 FFI 的测试，它还额外断言像素缓冲**非全零**（全零通常意味着 `GetDIBits` 没写进去） |

**这轮的教训与 7.14 一脉相承**：加能力之前先问「它的权限检查落在哪一侧」。三项能力里有两项的动作发生在 Rust（图标由 GDI 取、定位由 Shell 做），一项发生在窗口事件上；分不清这一点就会把检查放错层，而在前端放一个「看起来在检查」的判断，比不检查更糟 —— 它给人已经管住了的错觉。

### 7.17 示例插件重做：文本速记与番茄工作钟

| 项目 | 说明 |
| --- | --- |
| 背景 | `hello-plugin` 一直是个测试件 —— 功能方向不错（速记），但形态简陋，且它的 `dist/` 没有入库，等于**示例本身不可读**。这一轮把它做成真正的插件，并另写一个番茄工作钟 |
| 移除 | `samples/hello-plugin/` 与 `hello-plugin.lcp` 删除，由 `samples/notes` 取代（沿用同一个插件 ID `com.modulith.sample.notes`，因此对已装用户是一次升级而不是并存两个） |
| 新增命令 | `plugin_pick_audio`。后端命令数 63 → 64（plugins 模块 21 → 22） |
| 新增依赖 | 无。音频读取用已有的 `base64`，默认提示音用 WebAudio 现场合成 |
| 音频能力的设计 | 「选择 + 读取 + 编码」合成一步：插件拿到的是可直接播放的 data URL，**接触不到原始字节或路径**。扩展名白名单与 2 MB 上限因此只有一个执行点，没有绕过路径 —— 与图标提取同一思路（宿主给成品，不给原料） |
| 为什么不做通用文件读取 | 那会是一个远比「导入提示音」宽的口子，而当前没有任何真实需求。刻意不做，并在文档里写明这是边界而不是遗漏 |
| 扩展名校验的两个细节 | ① **不能只依赖对话框过滤器** —— 过滤器只是给用户的建议，选择框里仍可切到「所有文件」，因此真正的校验按扩展名白名单做；② 白名单常量与校验函数有测试钉在一起，避免「过滤器里列了、校验却不认」这种用户看得见却说不清的错 |
| notes 的设计要点 | 索引与正文**分开存**（否则改一个字就要重写全部正文）；自动保存**防抖 + 切走时立刻落盘**（保活让模块继续运行，但用户随时会关窗）；全文搜索**按需加载**正文，不为了让搜索好做而把正文塞回索引 |
| pomodoro 的设计要点 | 计时核心与心跳**放在 React 之外**，因此从未打开过这个模块也会到点提醒；剩余时间始终由 `endsAt` 与当前时间算出，而不是每 tick 减一次（否则窗口被节流或系统休眠时会越走越慢）；WebAudio 合成的默认提示音意味着插件包**不需要带音频资源** |
| 提示音的自动播放限制 | 浏览器要求音频由用户手势解锁。计时结束时用户往往没有新手势，因此在用户点「开始」时先建立并 `resume()` 一个 `AudioContext`，之后到点播放才不会被拒。这一点写进了宿主 API 参考 |
| 新增测试 | 音频扩展名白名单 2 条（大小写不敏感 + 拒绝非音频；过滤器与校验一致）。总数 147 → 151 |
| 示例包校验扩到全部三个 | `extracts_and_validates_real_sample_lcps` 逐个解压、校验清单，并**逐字节比对源码目录与包内文件** |
| 为什么加逐字节比对 | 「改完插件忘记重新打包」这个错误**我自己犯过两次**，两次都是靠肉眼发现。现在源码一改而包没重打，测试立刻红并直接说出「忘记重新打包了」 |
| 已知限制（快捷键） | 宿主有 `services/shortcutRegistry.ts`，但**没有暴露给插件**。因此 notes 的快捷键是自己挂 `window` 监听实现的，靠 `useModuleActive()` 判断可见性来避免抢键。让插件贡献快捷键是明确该做但尚未做的事 |
| 已知限制（运行时机） | 插件代码在**插件加载时**执行，模块是否挂载不影响它。因此 pomodoro 的计时只要插件处于启用状态就会运行；反过来，插件被禁用时任何后台行为都不会发生 |

**这轮补上的是「示例的可用性与可信度」。** 之前的示例能跑，但它证明不了「一个真实插件该怎么组织数据、怎么处理保存时机、怎么在后台活着」。三份示例现在各占一个难度台阶，且都被测试守着 —— 包括那个「包与源码必须一致」的检查，它防的正是我自己反复犯的错。

### 7.18 文本速记重新定位为极简收件箱

| 项目 | 说明 |
| --- | --- |
| 触发 | 7.17 交付的 `notes` 是「索引 + 正文分开存」的设计，配了标题字段、编辑器面板、全文搜索、置顶、三种排序。用户反馈：**「我为什么不直接创建一个文档呢？」** |
| 判断 | 那个形态是在做**文档管理**，而这件事系统里有更合适的工具。速记的价值在于**快** —— 想法出现时不该先决定「它该叫什么名字、放哪个分类」。多一个字段就多一次让用户做决定的机会 |
| 改动 | 去掉标题字段、编辑器面板、排序、置顶、分组、搜索；改为**单列：一个输入框 + 下方列表**。内容本身是唯一字段，列表里第一行加粗显示，其余作为摘要 |
| 交互 | 点「保存」或 `Ctrl+Enter` 入库；每条悬停时浮出「复制 / 修改 / 删除」。列表行平时不显示按钮，但也不必先选中再去别处找 |
| 保留的设计 | 草稿（未保存的输入）仍单独存并防抖落盘 —— 打了一半关窗不该丢；已保存条目**不做自动保存**，因为「点保存」正是这个交互的核心动作，把它变成自动的反而让人不确定存没存进去（因此保存后给一个明确的轻提示） |
| 数据兼容 | `normalizeItems()` 识别旧版 `{id, title, body}` 两字段格式并拼回一整段文本。**改版不该让老用户的数据消失** |
| 顺带修的 bug | 旧版快捷键监听挂在 `window` 上**没有可见性判断**，在别的模块按 `Ctrl+N` 也会新建速记。现已加 `useModuleActive()` 守卫 |
| 补上的文档 | `samples/notes/README.md` 之前**根本不存在**（上一轮只写了代码与 CSS）。现已补齐 |

**这条记录的教训不在代码里。** 我按「功能越全越好」的思路做了 `notes`，
而一句反问就指出了方向性错误：**当一个功能的定位是「快」，每增加一个字段都是在
削弱它。** 功能清单的长度不等于价值 —— 尤其是这类「顺手记一下」的工具，
减少决定次数比增加能力更重要。

### 7.19 快捷键从未接线、历史记录入口不全、全局右键与自适应

| 项目 | 说明 |
| --- | --- |
| 现象 1 | `Ctrl+K`（聚焦搜索）、`Ctrl+W`（关标签）、`Ctrl+Tab` / `Ctrl+Shift+Tab`、`Ctrl+1..9` **全部没有反应** |
| 根因 1 | `shortcutRegistry.ts` 把整套机制写好了（解析、规范化、冲突检测、按来源注销），`useGlobalShortcuts` 也早就把键盘事件交给它 —— 但**从来没有人往里注册任何东西**。注册表恒为空，`handleShortcutEvent` 遍历零个条目后返回 false |
| 佐证 | `useGlobalShortcuts` 的注释逐条列出了这些组合，`tabStore` 的 `activateRelativeTab` / `activateTabAt` 也明确写着「供 Ctrl+Tab / Ctrl+数字 使用」。**意图在各处都写清楚了，只有那一步接线没做。** 用 `git log -S` 确认：从首次提交起 `registerHostShortcuts` 就只存在于注释里，从未作为代码存在过 |
| 处理 1 | 新增 `src/services/hostShortcuts.ts` 实现并注册 13 个组合（4 个固定 + Ctrl+1..9），在 Home 的初始化里调用一次 |
| 教训 1 | **注释描述了一个不存在的实现，比没有注释更糟。** 它让后来读代码的人（包括我自己）以为这件事已经做完了。写完注释顺手确认一下被描述的东西真的存在 |
| 现象 2 | 前进 / 后退只记录从侧边栏与仪表盘切换的模块；从标签栏切换的不进历史 |
| 根因 2 | 历史只在 `setActiveModule` 里记录，而它是侧边栏 / 仪表盘专用入口；标签栏走的是 `tabStore.activate`，命令面板是另一条路 |
| 处理 2 | 改为**观察 `activeTab` 的变化**来记录（标签是「当前显示哪个模块」的唯一事实来源）。这样所有入口自动都有历史，将来新增入口也不必记得补一行；`setActiveModule` 里的记录逻辑随之删除，否则同一模块会入栈两次 |
| 顺带修 | 后退 / 前进此前**先移动指针再调用 `openTab`**，而 `openTab` 在标签数达上限时会拒绝且不改变当前标签 —— 指针因此停在一个用户没到过的位置（表现为「按了没反应，但前进/后退的可用状态变了」，再点一次还跳过一个）。改为**只在 `openTab` 成功后才移动指针** |
| 新增功能 3 | 全局右键菜单（`src/components/GlobalContextMenu.tsx`）：后退 / 前进 / 刷新 / 设置 / 通知中心 / 显示二级标题栏 |
| 为什么不与模块右键冲突 | 模块自己的处理器会先调用 `preventDefault()`（侧边栏与标签栏都是），冒泡到外壳时 `event.defaultPrevented` 为真，全局菜单直接让位；输入框里也刻意不接管，保留浏览器原生的复制 / 粘贴菜单 |
| 新增功能 4 | 二级标题栏可隐藏（沉浸浏览）。新增设置项 `tabBarVisible` / `tab_bar_visible`，默认可见并持久化 |
| 只隐藏标签栏的原因 | 窗口是无边框的（`decorations: false`），标题栏承载最小化 / 最大化 / 关闭按钮。隐藏标签栏只是少了一层导航；隐藏标题栏会让用户**没法关掉窗口** —— 那不是一个可以用设置项换取的体验 |

### 7.20 开发模式下「检查更新」必然失败一次

| 项目 | 说明 |
| --- | --- |
| 现象 | `pnpm tauri dev` 里点「设置 → 关于 → 检查更新」，报 `None of the fallback platforms ["windows-x86_64"] were found in the response platforms object`。看起来像发布清单坏了 |
| 根因 | Tauri 在**打包**时把包类型就地写进可执行文件（`__TAURI_BUNDLE_TYPE`，取值 `UNK` / `MSI` / `NSS` 等，都是定长三字符所以能原地改）。dev 跑的是未打包产物，标记仍是 `UNK`，`bundle_type()` 返回 `None` → updater 只去清单里找**裸键** `windows-x86_64`。而发布清单按设计只写 `windows-x86_64-msi` / `windows-x86_64-nsis`（带包类型的键），两者对不上 |
| 佐证 | 报错里打印的是**完整候选列表**，不是只有兜底项（`updater.rs` 的 `get_urls` 在全部候选都失败后 `Err(TargetsNotFound(targets))`）。列表只有**一个**元素 ⇒ `installer` 是 `None` ⇒ 进程没有包类型标记 ⇒ 一定不是安装版。安装版的 `modulith-desktop.exe` 里该字符串是 `__TAURI_BUNDLE_TYPE_VAR_NSS`，与未打包产物的 `..._VAR_UNK` 在同一偏移上只差三个字符 |

| 为什么只在开发模式下追加 | 正式版出现同一条报错说明清单**真的**缺了键，那时任何「这是正常的」都是误导。这个错必须保持刺眼 |
| 教训 | 「只在开发模式出现的失败」必须以开发模式的方式解释。否则它会以「更新功能坏了」的形式消耗排查时间 —— 尤其当它出现在一个刚做完、还没来得及验证的功能上时，最自然的结论就是自己写错了 |

### 7.21 示例插件拆分：参考件留在应用仓库，完整示例迁到插件仓库

| 项目 | 说明 |
| --- | --- |
| 背景 | `samples/` 一度同时承担两个角色：**可复制的参考**（短、能读完、只示范接口）与**可用的插件**（有功能、有 README、有样式）。三个完整示例把 `samples/` 变成了一个小型应用集 —— 每次改宿主接口都要顺带维护它们，而用户又装不到（它们不在任何索引里） |
| 处理 | 三个完整示例迁到插件仓库 `modulith-plugins/plugins/`，作为**可安装**的示例插件发布；应用仓库的 `samples/` 只留一个新的参考插件 `reference`，只示范不需要危险权限的核心接口，并把「刚才调用了什么、需要哪项权限」显示在界面上 |
| 为什么参考件要小 | 示例的首要用途是**被复制**。它一开始提供功能，就会长出设置项与边界处理 —— 那些是它作为「一个软件」的价值，却是它作为「一份说明书」的负担 |

| 迁移时改了什么 | 作者 / 主页 / 仓库指向插件仓库；跨仓库链接改成绝对 URL；补上每个插件自己的 `LICENSE`（`pomodoro` 还补了之前根本不存在的 `README.md`）；`index.css` 与 `LICENSE` 里写死的 `samples/...` 路径 |
| 版本归一 | 三个插件的版本从 `1.0.1` 改回 `1.0.0`：它们此前从未发布过，而索引里出现「首个版本是 1.0.1」只会让读者以为漏了一版 |
| 插件 ID 保持 `com.modulith.sample.*` | 目录规范写明 ID 一旦发布**不可更改**（它同时是安装目录名与存储命名空间）。「示例」是事实，保留这个命名空间比换成作者命名空间更诚实，也避免了与既有文档分叉 |
| 宿主侧跟着改的 | `manager.rs` 里三条按插件名逐个断言的测试合成一条面向 `reference` 的；`extracts_and_validates_real_sample_lcps` 的包列表缩到一个 —— 那条「包必须与源码逐字节一致」的断言仍然在守，它挡的是「改完插件忘记重新打包」 |
| 教训 | **示例的两种用途混在一起会两头都不讨好**：参考件要小到能读完，可用件要真的能用 —— 而后者应当走正常的分发渠道（索引 + 不可变 tag + 哈希校验），而不是躺在源码仓库里 |

### 7.22 日志门面挂了，但从来没有后端：几十处 `log::*` 一次也没有输出过

| 项目 | 说明 |
| --- | --- |
| 现象 | 出问题（例如「检查更新失败」）时，我们手上没有任何证据。用户能提供的只有「不行」，而 release 版的表现与原因之间没有任何可查的中间层 |
| 根因 | `Cargo.toml` 一直有 `log = "0.4"`，代码里也一直有几十处 `log::info!` / `log::warn!` / `log::error!`，但**从来没有安装过任何 logger 后端**。`log` 只是一个门面：没有后端时它把每条记录直接丢掉，而且不会报错、不会有编译警告 —— 因为那些调用本身完全合法 |
| 为什么格外隐蔽 | 三条通道同时失效：`log` 没有后端；release 版是 `windows_subsystem = "windows"`，`eprintln!` 也没有出口；前端的错误只进 WebView 的 devtools，而用户打不开它。于是「写了日志」与「没有日志」在任何一次运行里看起来完全一样 |
| 处理 | 新增 `logging` 模块：自实现的文件日志器（1 MB × 3 轮转、崩溃单独成文件、运行期开关、panic 钩子），前端通过 `log_frontend` / `report_frontend_crash` 把错误与插件日志送进同一个文件，设置里新增「日志」分页查看路径与内容 |
| 为什么不用 `tauri-plugin-log` | 两件需求通用插件给不了：**运行期开关**（插件的目标在启动时固定）与**崩溃记录独立成一个开关和一个文件**。自己写还顺带省掉一个依赖，并能精确处理「装 logger」与「拿到日志目录」之间的时间差（见 `logger.rs` 文件头） |
| 教训 | **一个依赖了门面却没装后端的日志系统，比没有日志更糟**：它让「这里已经记了日志」成为一个写在代码里的事实，从而阻止任何人再去检查它是否真的在输出。引入 `log` / `tracing` 这类门面时，必须同时确认后端存在，并有一条能证明它确实输出了的路径 |

### 7.23 用户配置的下载源改不到应用更新：官方前端插件的结构性限制

| 项目 | 说明 |
| --- | --- |
| 背景 | 有用户报告内网/受限网络下「检查更新能查到新版本，下载却卡住/失败」。上一个版本刚修过另一个地址问题（清单里的资产名与 GitHub 实际存储的名字差一个转义），因此第一反应是清单又坏了 |
| 根因 | 与清单无关。官方前端 API（`@tauri-apps/plugin-updater`）的两处地址都不可配：**清单地址**来自 `tauri.conf.json` 的 `plugins.updater.endpoints`，在插件初始化时固定；**安装包地址**根本不在插件配置里，而是清单文件自己写的 `platforms.<target>.url`（指向 `github.com/.../releases/download/...`）。因此「清单能换个地址取、安装包不能」是这个结构的必然结果 |
| 处理 | 检查与安装都搬到 `src-tauri/src/modules/updater/commands.rs`：清单地址经 `UpdaterBuilder::endpoints()` 传入，安装包地址在 `check()` 之后改写公开字段 `update.download_url`。下载、签名校验与调起安装程序仍然全部由官方插件完成，公钥仍然取自同一个 `plugins.updater` 块 |
| 配套的加固 | `capabilities/default.json` 移除了 `updater:default`。插件与宿主共用同一个 JS 上下文，若官方插件的命令仍然可达，插件代码就能绕开下载源直接调用它 —— 那样这个设置项就只对守规矩的调用者生效 |
| 残留的不一致 | 加速源地址允许 http 的唯一情形是本机回环（本地调试），但**官方更新器在 release 版拒绝非 https 的清单地址**，因此 http 回环加速源只对插件市场有效。这条不一致在更新失败时会给出明确提示，而不是一个看起来像清单坏了的报错 |
| 另一个残留 | `@tauri-apps/plugin-updater` 仍留在 `package.json` 的依赖里（不再被 import）。删除依赖需要重新生成 `pnpm-lock.yaml`，那次改动单独做更清楚 |
| 教训 | **「哪些地址可以被用户配置」不是界面上的事，而是调用栈的事。** 只要有一处地址由第三方代码在初始化时固定，用户设置就必然在其中某一段上失效 —— 而失效的那一段恰好是最容易失败的一段（大文件下载） |

### 7.24 「关闭界面动画」只在没在看的标签上生效

| 项目 | 说明 |
| --- | --- |
| 现象 | 用户报告：已经打开「关闭界面动画」，界面仍然卡 |
| 根因一 | `ThemeProvider` 在应用根部按设置给出 `reducedMotion="always"`，而 `Home` 给每个标签面板又套了一层 `reducedMotion={isActive ? 'never' : 'always'}`。framer-motion 的合并规则是**子层覆盖父层**（`config = { ...parentConfig, ...config }`），于是激活标签永远拿到 `"never"` —— 而那恰好是用户唯一在看的标签。这个开关的真实效果是「关掉没在看的标签的动画」 |
| 根因二 | framer-motion 12 的短路只对**位置类**属性生效（`positionalKeys`：transform 系列与 width/height/inset），`opacity`、`backdrop-filter`、`box-shadow`、`filter` 不在其中。授权界面的粒子背景正是 18 条 `repeat: Infinity` 的 `y / opacity / scale` 循环：`y` 与 `scale` 停了，`opacity` 没停 —— 18 条 rAF 动画与 18 个合成层永远在跑，而授权界面默认每次启动都会出现 |
| 根因三 | CSS 开关本身不完整：选择器 `*` 匹配不到根元素自身（漏掉它的 `transition: background-color`），也没有归零 `animation-delay`（一个延迟 2 秒的动画仍会在 2 秒后闪一帧） |
| 处理 | 标签层取并集（`isActive && !reduceMotion`）；粒子的挂载由代码显式判断；CSS 规则补上根元素、delay 与 play-state；两个开关的合并收敛到 `utils/motionPreference.ts` 一处，并新增「性能模式」把非动画类的每帧开销（三个常驻全屏 `backdrop-filter`、装饰性大半径模糊、几十处 `will-change`）一并去掉 |
| 附带发现 | `Home.tsx` 的注释声称非激活标签用 `content-visibility: hidden` 隐藏，**代码从来没用过**（实际是 `visibility: hidden`）。已改正注释，并写明不用的理由：它会让子树内部的滚动容器失去布局，威胁「切回原处」这个保活的核心目标 |
| 教训 | **一个「看起来接上了」的开关比没有开关更糟**：它让「我已经关了动画」成为一个用户确信的事实，从而不会再去怀疑这一层；而嵌套配置的覆盖方向（子层取胜）恰恰是最不容易在代码里看出来的东西。这类缺陷只有把修复点本身钉成断言才防得住 —— 见 `scripts/check-performance.ts` |

### 7.25 两处没有上限的缓存

| 项目 | 说明 |
| --- | --- |
| 现象 | 模块多开、在市场里来回浏览之后，常驻内存只涨不落 |
| 根因 | 模块组件缓存只有全局 `clear()`，从不逐条释放（不变量应当是「条目数 = 当前挂载数」，实际是「曾经打开过的模块数」）；市场 README 与图标缓存各存几十 KB 的字符串与 base64 文本，**一条上限都没有**，每浏览一个新版本就多一条 |
| 处理 | 组件缓存的释放挂在 `tabStore` 的**唯一写入点** `setState` 上（六条关闭/对账路径都经过它 —— 逐条去调必然漏一个）；两个市场缓存加 32 条上限，按插入顺序先进先出 |
| 没有跟着改的 | 后端 `AttemptTracker.attempts` 与 `RateLimiter.requests` 用的是阈值扫描而不是硬上限，这是**刻意**的：它们记录登录失败标识，一个可被任意淘汰的表等于让攻击者用泛洪把自己的封锁记录挤出去 |
| 说清楚的部分 | 已加载的 JS chunk 不会释放（浏览器模块注册表在文档生命周期内保留求值结果，只有整页重载会重置）；插件模块是同域内联脚本，卸载后要等没有引用才会被回收。这两条不是泄漏，但会让人觉得「内存没降下来」 |
| 教训 | 「有没有上限」要逐个对象问一遍，而不是问「有没有回收机制」—— 后者很容易答"有"，因为回收机制确实存在，只是漏了几个对象 |

### 7.26 一次独立审阅触发的安全收口与文档校正

本轮由一次外部审阅触发。四处代码问题都是同一个形状 ——**能力存在，但检查只挂在一半调用点上**；另有一批是纯粹的文档漂移。

#### `export_plugin` 的 `dest` 曾是任意文件覆盖原语

| 项目 | 说明 |
| --- | --- |
| 现象 | `export_plugin(id, dest)` 无权限检查，`dest` 直接交给 `normalize_export_path`，最终 `File::create(dest)` **截断覆盖**目标文件；`export` 还会先 `create_dir_all(parent)`。插件因而可以覆盖 `auth.json`、`settings.json` 或任意路径的文件 |
| 为何危险 | 插件可直接 `invoke` 这条命令（同 JS 上下文、后端无从知道调用者），而它不需要任何权限声明。§4.1 曾断言 `filesystem-write`"完全没有对应的命令"——**那是不准确的**，这条命令正是它的语义 |
| 处理 | `dest` 收口为**默认导出目录内的裸文件名**（新增纯函数 `export_file_name`），且目标**已存在时拒绝覆盖**。默认导出目录是用户的下载目录、不是应用专有目录，所以"只允许新文件"这一条不能省 |
| 前端影响 | 无。`Plugins.tsx` 只传 `dest: null`（走原生保存对话框），没有任何既有调用受影响 |
| 测试 | `export_target_must_be_a_bare_file_name`（覆盖带目录、盘符、`..`、`.` 等写法） |

#### `install_plugin_url*` 不受 network 权限约束

| 项目 | 说明 |
| --- | --- |
| 现象 | `install_from_url_verified` 只做 `is_http_url`（前缀检查），**既没有宿主白名单，也没有 `require_permission`**；`install_plugin_url` 是它的无哈希包装 |
| 为何是矛盾 | `fetch_registry_text` 上写着一整段论证："插件与宿主同处一个 JS 上下文、能触达 IPC 桥，若这里放开宿主限制，一个没有声明 `network-external` 的插件就能借它发出任意外部请求。" 而**同一威胁模型下的另一个入口没有施加任何约束** |
| 处理（市场路径） | `install_from_url_verified` 现在施加 `ensure_registry_url_allowed`（宿主白名单 + https）。市场地址由 `registrySources` 生成，只可能是两个白名单宿主，因此不破坏功能；用户配置的加速源由后端在 `fetch_via_sources` 内部拼接，不在校验范围内 |
| 处理（用户粘贴路径） | `install_plugin_url` 保留任意宿主（用户可能从自建服务器或内网安装），但收紧为 `ensure_https_or_loopback`：**明文 http 一律拒绝** |
| **未解决，如实记录** | 这条命令**仍然无法识别调用者** —— 插件可以直接 invoke 它去下载任意地址的内容。命令签名里没有插件 id，而在同 JS 上下文的模型下后端无从知道调用者是谁。保留它是因为「从 URL 安装」是真实功能；这个缺口属于模型局限，不是靠加检查能消除的 |
| 顺带修正 | `Plugins.tsx` 的弹窗文案原写"应用会下载并校验后再安装"——这条路径**不校验哈希**，已改为如实说明"不会校验来源" |
| 测试 | `registry_url_requires_allowlisted_host`、`user_pasted_url_allows_any_https_host_but_not_plain_http` |

#### 解压体积上限用的是压缩包自己声明的值

| 项目 | 说明 |
| --- | --- |
| 现象 | 总量上限累加 `entry.size()`（中央目录**声明**值），而实际字节只按**单条目**比较。条目数上限 5000 ⇒ 可写到约 5000 × 64 MiB，且没有压缩比检查 |
| 处理 | 保留声明值作为廉价预检，**新增按实际写入字节累计的 `written_total`**，超限立即中止。解压炸弹不再能靠撒谎的中央目录绕过 |
| 测试 | 未新增。构造"声明小、实际大"的 zip 需要手工篡改中央目录，成本高于收益；实际累计是一段直读即可确认的线性逻辑 |

### 7.27 窗口内分屏、开机自启动与全屏

三个功能在同一轮加入。它们的共同点是**都不改动已有的核心抽象**，而是把已有能力往前推一步。

#### 窗口内分屏（两个标签组）

| 项目 | 说明 |
| --- | --- |
| 形态 | **两个标签组**：左（`primary`）与右（`split`），每组有自己的标签列表、自己的激活标签、**自己的标签栏**。分屏状态由 `splitTabs` 是否为空表达，没有额外的布尔量 —— 两者因此不会出现「标记为分屏但右边是空的」 |
| 为什么是「组」而不是「右边多显示一个」 | 第一版把分屏做成「共享一个标签列表 + 右边多渲染一个标签」，结果右边既不能切标签也不能关标签，用户的原话是「我还不能更改」。一个钉死的预览不算分屏 |
| 入口 | 标签右键菜单「在右侧分屏打开 / 移回左侧」、`Ctrl+\`（**把焦点组的当前标签搬走**；再按一次收回）、**把标签拖到内容区的另一半**（拖动期间左右两半都是落点区） |
| 拖拽 | **用指针事件自己实现，不用 HTML5 拖放** —— 后者在本应用里整体不可用（见本节第 3 条教训）。`tabDrag.ts` 跟踪 `pointermove`、按落点元素自己判定目标，并画一个跟随指针的幽灵标签（没有浏览器自带的拖动影像，不给反馈就看不出在拖东西） |
| 焦点组 | `focusedGroup` 记录"用户正在操作哪一半"。**点进哪一半就聚焦哪一半**（内容区按坐标判定，标签栏点击即聚焦）；它决定：侧边栏高亮、`Ctrl+W` 关哪个标签、`Ctrl+Tab` / `Ctrl+1..9` 在哪个组内轮转、以及**从侧边栏新开的模块落进哪一组**。没有它这些会固定作用在第一组，而用户可能在右半工作 —— 表现为「按 Ctrl+W 关掉了左边那个」「新开的模块跑到另一半去了」。没有焦点那一组的激活指示条调浅一档，作为可见线索。运行时状态，不持久化 |
| 分屏的方向 | 在标签 X 上分屏 = 把 X **移动**到右组（不是复制）：复制会带来两份组件实例、两套定时器与两套存储写入，而「同时看两个不同的东西」才是分屏的用途 |
| 第一组不能空 | `openInSplit` 拒绝把第一组搬空，`setState` 里还有反向兜底（第一组空了而第二组有内容时，把第二组的激活标签补回来）。入口与出口各挡一次 —— 左边空白、右边有内容不像分屏，像界面坏了 |
| 可调比例 | 分隔条用**指针事件 + 指针捕获**（HTML5 拖放只有离散的 dragover，做出来是跳的；捕获则保证拖出窗口也不断），比例夹在 `[0.2, 0.8]`，双击回 50%，并持久化 |
| 保活 | 所有面板仍在**同一个父容器**里，横向位置由「属于哪一组」算出。这一点是刻意的：跨组移动只改 `left` / `width`，React 复用同一个元素（key 与父节点都没动），滚动位置与未提交的表单因此不丢。若按组分两个容器渲染，跨组移动就会重新挂载 —— 而那正是最不该丢的东西 |
| 持久化 | `settings.json` 的 `splitTabs` / `splitActive` / `splitRatio`。上限按**两组之和**校验：每个标签都是一个常驻的模块实例，分屏不该成为绕过上限的口子 |

**这一节记录三次做错，比记一次成功更有用。**

1. **第一版**：`openInSplit` 复用了 `openTab()`，而后者会 `activate()` 目标 —— 目标被设为左格后 `splitTab === activeTab`，立刻被 `setState` 的不变量清洗成 `null`。**入口全都接上了，但每一次都被自己的不变量清掉**，表现为「点了没反应」而且不报错。教训与 §7.19 的「快捷键从未接线」同类：把不变量收在一处是对的，但**新加的写入路径必须验证它确实能通过那道不变量**。
2. **第二版**：不变量通过了，但**模型选错了** —— 把它理解成「共享标签列表 + 右边多显示一个」。用户随即指出右边不能切换、不能关闭，那半等于装饰。这一次是**没先确认「分屏」到底指什么就动手**，代价是整块重做。
3. **第三版**：拖动分屏只有落点提示能出现，`drop` 不触发、光标是"禁止"。我先把原因归到 `dragstart` 没声明 `effectAllowed` —— **那个归因是错的**：`宿主API参考.md` 与 §7.16 早就写明，本应用里 **WebView 内的 HTML5 拖放整体不可用**（Tauri 的 `dragDropEnabled` 默认 `true` 会拦截系统拖放）。那次修复改的是一个**永远不会被执行**的路径。正确做法是用**指针事件**自己实现（`services/tabDrag.ts`：跟踪 `pointermove`、自己算落点、自己画幽灵标签）。同一个原因还解释了为什么**标签拖拽排序此前从来没能用过** —— 它用的是同一套 HTML5 API，而没人试过。

**`useModuleActive()` 的语义在这一轮变准确了，插件作者需要注意。** 宿主传给模块的 `isActiveTab` 现在是「是否位于某个可见的组」而不是「是否为唯一被选中的标签」—— 分屏时两组各有一个可见标签，两个都为真。

#### 开机自启动

| 项目 | 说明 |
| --- | --- |
| 实现 | 自己写（`settings/autostart.rs`），不引 `tauri-plugin-autostart`：需要的是「当前用户、单个值、一条命令行」，而 `windows-sys` 已在依赖里（图标提取在用同一份）。与「为什么不用 tauri-plugin-log」是同一个判断 |
| 写入位置 | 只写 `HKCU\...\CurrentVersion\Run`，**不写 HKLM** —— 后者会让安装或首次运行要求提权，而自启动不需要那种权限 |
| 唯一真相 | **注册表**。`settings.json` 里刻意不存这份状态：用户能在任务管理器的「启动」页里直接改它，存一份副本必然与实际不符 |
| 命令行 | `"<exe>" --autostart`。引号防含空格的路径被系统按空格拆开；`--autostart` 标记用于区分「系统拉起」与「用户双击」—— 静默与全屏只该作用于前者 |
| 平台 | 目前仅 Windows。其他平台返回明确的「不支持」而不是假装成功 |
| 启动行为 | 「静默」（最小化）/「全屏」/「最大化」三选一，优先级 **静默 > 全屏 > 最大化**。三者都想决定「窗口一出来是什么样」，同时开两个必须有确定答案，否则用户面对的是「到底哪个生效」的不确定性。**它们只在自启动开启时可用**：关掉自启动后三项显示为关且不可选 —— 它们描述的是"被系统拉起时窗口怎么出现"，没有那次启动就无从谈起，摆着可点只会让人以为设置没生效 |
| **静默启动的语义收窄** | 实现为**最小化**，不是隐藏窗口：本应用没有托盘图标，隐藏之后用户只能靠任务管理器找回它。设置界面里也如实写作「最小化启动」。要做到真正的后台常驻需要引入托盘，属于另一件事 |

#### 全屏（F11）

| 项目 | 说明 |
| --- | --- |
| 入口 | **只有 F11**（与浏览器一致），不做界面按钮。全局右键菜单里另有一项，退出同样靠 F11 |
| 隐藏范围 | 全屏时标题栏与二级标题栏一并隐藏、内容区上沿归零 —— 留着一条 40px 的标题栏等于没全屏。**侧边栏保持显示但上移贴合**（`top-0 h-full`）：它的定位里写死了标题栏高度，不跟着变会在顶部留出空隙、底部溢出 40px。选择贴合而不是自动隐藏，是为了不改变用户原本的展开 / 折叠状态，且全屏时仍可导航（想更沉浸按 Ctrl+B 自己收起） |
| 代价（已知） | 窗口是无边框的（`decorations: false`），标题栏承载最小化 / 关闭按钮。全屏时它们不可见，退出方式是再按一次 F11。这是「只由 F11 进入全屏」的配套代价，已在设置界面与本文中说明 |
| 状态归属 | 全屏状态在**前端**（`Home`），因为它不只是窗口属性：还要同时隐藏两级标题栏。因此快捷键经 `fullscreenBridge` 转发，而不是直接调 Tauri —— 否则会得到「窗口全屏了、标题栏还在」 |
| 失败回滚 | `setFullscreen` 抛错时把界面状态回滚，避免界面显示「已全屏」而窗口其实没有 |

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 解锁界面的两个装饰球在最大化窗口后「各据一角」，不再交叉重叠 | 尺寸是固定的（`w-96` = 384px），位置却是百分比（`top-1/4 left-1/4` 与 `bottom-1/4 right-1/4`）。两球重叠的条件是 `384 > 0.25 × 窗口宽`，而 1920 宽时需要 480 —— 窗口一大就分开 | 尺寸与模糊半径改为跟随窗口：`36vmax` / `3.5vmax`，重叠关系因此与窗口大小无关（960×560 上是 345px，3840×2160 上是 1382px，两端都保持部分重叠）。这是**既有**缺陷（非本轮引入），一并修掉 |

#### 顺带修掉：「恢复上次打开的模块」只生效了一半

| 项目 | 说明 |
| --- | --- |
| 现象 | 该开关关着，重启后仍然回到关闭前那一刻（标签、当前标签、分屏都在） |
| 根因 | 这个开关**只被 `resolveInitialModule()` 读**（决定"默认打开哪个模块"），而 `tabStore` 无条件把 `openTabs` / `activeTab` / `splitTabs` 写进设置、又在启动时无条件恢复。于是"窗口状态"这条通路完全绕过了它 |
| 处理 | 把这个开关的语义扩成**窗口状态**（标签页 + 当前标签 + 分屏 + 上次停留的模块），并且**同时管"存"与"取"**：关闭时既不写、也不读。默认值由 `false` 改为 `true`（恢复现场是这个应用的主要卖点，替用户关掉它没有道理） |
| 一个必须一起处理的细节 | 只在"取"这一侧加判断是不够的：关闭期间不写盘，设置里留着的是更早的布局；用户重新打开开关后一重启就会回到**那个陈旧布局**，而他记得的是"我刚刚开着这几个标签"。因此开关**从关切到开**的那一刻会立刻写入当前状态（`persistWindowStateNow`） |
| 这是同一类错误的第四次 | 与 §7.19（快捷键从未接线）、§7.26（`filesystem-write` 没有强制点）、以及本节的分屏前两版一样：**检查/开关只覆盖了一部分通路**。判断标准应当是"这个设置影响哪些写入点与读取点"，而不是"在哪一处加个 if 就完事" |

### 7.28 毛玻璃开关、通知提示音、备份机制，以及一批深色模式缺口

五项改动在同一轮完成。它们的共同点是**都在既有结构上补一个出口**，而不是引入新的
架构：毛玻璃补的是一个被性能模式顺带管着的开关，提示音补的是通知缺失的听觉通道，
备份补的是"数据带不走"的缺口，另外两项是缺陷修复。

#### 毛玻璃：从"性能模式的一部分"变成它自己的开关

原状：`backdrop-filter` 的存废只由 `.lc-performance` 决定，也就是只有打开性能模式
才能去掉它 —— 而那要连带付出装饰模糊、合成层与动画三份代价。想只去毛玻璃的用户
没有这个选项。

改动：新增「毛玻璃效果」开关（`glassEffect`，默认开），只控制**浮层**；三个常驻
亚层（标题栏、标签栏、侧边栏）**永久**去掉 `backdrop-filter` 并改为半透明纯色。

**亚层为什么不做成选项。** 它们背后永远是应用的纯色底：内容区从 `top: 76px` 开始、
且带 `paddingLeft` 给侧边栏让位，没有任何内容会滚到它们下面。没有内容可以模糊，
`backdrop-filter` 就只剩每帧重新合成的开销；深色模式下这三处本来就被强制成不透明，
模糊连"看起来有区别"都做不到。一个"开着也没有收益"的开关只会让用户以为自己选错了。

合并仍然只发生在一处：新增 `utils/glassPreference.ts` 的 `isGlassEnabled`，与
`isMotionReduced` 同构；性能模式**包含**关闭毛玻璃，反向不成立。

#### 顺带修掉的四个真实缺陷

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 深色模式下设置界面（以及插件页、开发指南）的背景是**纯黑**，而浅色模式下是半透明 | `dark-theme.css` 把 `bg-gray-900` 与 `bg-gray-900/40` 合并成一条规则，一起映射成**不透明的** `#0b0d14`。前半段是对的（实心深色按钮），后半段把 40% 的遮罩变成了实心近黑板。插件市场用的是 `bg-gray-900/30`，恰好不在表里，所以那里反而是对的 —— 这就是为什么只有设置界面看得出来 | 拆成两条：`bg-gray-900` 保持实心色，`bg-gray-900/NN` 与 `bg-black/NN` 各档映射成**真正的半透明黑**（并保留档位之间的深浅差） |

**这四个是同一种失败：`dark-theme.css` 是一张按类名精确匹配的覆盖表，漏一档就退回浅色，不报错、类型检查也过。** 因此这一轮加了 `scripts/check-theme.ts`：它把 `src/` 里实际用到的半透明背景 token 全部扫出来逐个核对映射，并要求遮罩必须保持半透明。写这个脚本的过程中它当场又抓出上面第 2、3 条与两档 `bg-black` 遮罩。

#### 侧边栏折叠按钮"悬浮不上"

**现象。** 鼠标放在按钮上（尤其是图标上）没有任何反应，必须往下移一段才行。

**根因与全屏无关**，虽然现象看起来像：标签栏行是 `fixed left-0 right-0 z-40`，靠
`paddingLeft` 把**内容**推到侧边栏右边让位 —— 但 `padding` 不会缩小元素盒子，那个
透明盒子仍然横跨整窗，而一个没有背景的 div 照样参与命中测试。它与侧边栏同为 `z-40`
且在 DOM 里更靠后，于是正好压在侧边栏头部：折叠按钮 y∈[56,84)，其中 56~76 被这条
带子吃掉，只剩底部 8px 可点。全屏时本行整个不渲染，所以那个按钮在全屏下反而是好的
—— 这也解释了为什么它看起来"和全屏有关"。

**处理。** 容器加 `pointer-events-none`（它纯粹是布局壳），需要交互的 TabBar 自己
声明 `pointer-events-auto`。比"把侧边栏的 z-index 抬上去"更准：真正的错误是**透明的
布局盒子本就不该命中测试**，抬高 z 只是掩盖它，压在下面的其它元素还会再中一次。

#### 通知提示音

新增「设置 → 通知」分页：开关、五种内置音色（每种可当场试听）、自定义音效、音量。

三个决定：

- **音色用加性合成，不打包音频文件。** 项目此前刻意避免新增二进制资源与依赖，而
  敲击音（钟 / 马林巴）用几个非谐分音就能做出辨识度。分音峰值在 `strike()` 里
  按总数**自动归一化**，因此"换音色就换了音量"这件事在结构上不会发生。
- **自定义音效是被复制进来的。** 后端只认 `<app_data>/sounds/custom.<白名单扩展名>`
  这一个文件名，设置里存文件名而不是路径 —— 存路径会让"读取任意用户文件"变成一条
  常驻能力，而它只需要在用户主动选择的那一刻发生一次。
- **声音与浮层同进同出。** `presentNotification()` 里同时做这两件事，因此不存在
  "弹了但没响"或"响了却找不到是什么"。被合并计数的重复通知不响 —— 否则重试循环
  会把它变成骚扰。

**一个无法自动验证的地方，如实记下：** 音色"好不好听"没有人能替用户判断。因此
`scripts/check-sounds.ts` 用桩音频上下文**真的跑一遍**每种音色的合成，检查的是
可以判断的部分：包络从 0 起振（否则有"啪"声）、指数衰减目标不为 0（否则真实实现
会抛错）、每个振荡器都 start 且 stop、以及**每个音色的瞬时振幅峰值落在 [0.5, 1.0]**
—— 这条下限正是"别太轻"，上限则是"别把压缩器逼出来把起振压扁"。听感仍需要人听。

#### 备份机制

新增 `backup` 模块（后端 8 个模块之一）与「设置 → 备份」分页：按类别导出标准 zip，
或从备份按类别恢复。类别为软件设置、侧边栏与模块偏好、通知记录、已安装插件、
插件数据、运行日志，外加默认不勾选的授权与安全数据。

**安全模型是白名单，而且是唯一的一份。** 导出只可能产出白名单里的路径，导入只接受
白名单里的路径 —— 也就是**能被接受的名字恰好是导出能产生的名字**。这条不变量比
"做了路径校验"强：它不依赖任何路径规范化技巧的正确性，因为可构造出的合法名字本来
就只有一个有限集（形状是 `data/<appdata|logdir>/<白名单相对路径>`）。

其余四条：

- **前端从不把路径交给后端去读写。** 导出与打开都经过系统对话框，恢复只能作用于
  后端记住的那个刚打开的文件。否则白名单只能约束包内路径，约束不了包从哪来。
- **恢复是替换，且先校验后删除。** 校验通过之后才动手删，因此"包有问题"永远不会以
  "数据被删了但没恢复回来"收场。`restore_validates_before_deleting_anything` 测试
  专门构造了"第一条合法、第二条越界"的包来锁这个顺序。
- **体积与条目数按实际写出的字节判定。** 压缩包里声明的大小可以被伪造成"声明很小、
  实际很大"，声明值只用于廉价预检。
- **敏感数据要两道门。** 导出时要点开高级开关，恢复时**还要再点一次**；后端
  （`resolve_selection`）与界面各自执行同一条规则。"我导出时愿意"与"我现在愿意覆盖
  本机凭据"是两个不同的决定。

日志类别**只导出不恢复**：日志文件由日志器持有着打开的句柄，Windows 上删不掉打开
中的文件。与其做一套"先关日志器、恢复完再开"的编排（那会在恢复失败时把日志系统
留在不确定状态），不如让它的用途收窄到"拿到另一台机器上排查"。

#### 顺带修掉：`restoreLastModule` 的两处默认值不一致

**类别：** 缺陷（已修复）

`AppSettings` 有两条独立的默认值路径：字段缺失时走 `#[serde(default = "...")]`，
文件缺失或损坏时走 `AppSettings::default()`。`restore_last_module` 的后者一直是
`false` 而前者是 `true` —— 于是**全新安装**（没有 settings.json）与**手工改坏的
settings.json** 都会让「恢复上次打开的模块与标签页」静默变成关闭，而界面与文档上的
默认值都写着开启。这是 v1.1.6 改默认值时只改了一处的遗留。

处理：改用同一个默认值函数，并新增 `impl_default_matches_serde_defaults` —— 它把
两处序列化后**逐字段**比对，因此将来新增字段时只补一处会被立刻发现，而不是等到某天
有人发现某个开关在两个本该相同的情形下一个开一个关。

### 7.29 发行版毛玻璃失效、插件说明的 Markdown 渲染，以及一处新发现的注入面

#### 只在发行版复现：毛玻璃开关完全失效

**类别：** 缺陷（已修复）

**现象。** `pnpm tauri dev` 里开关毛玻璃一切正常；**打包出来的安装版**里，开启或关闭它都没有任何反应。

**根因在构建阶段，不在运行逻辑。** `index.css` 里那一对声明原本写作：

```css
backdrop-filter: none !important;
-webkit-backdrop-filter: none !important;
```

CSS 压缩器把它们判定为"同一件事的两种写法"并去重，而它删掉的是**标准的那一份**。产物里于是只剩 `-webkit-backdrop-filter`：

```css
:root.lc-no-glass *,:root.lc-no-glass :before,:root.lc-no-glass :after{-webkit-backdrop-filter:none!important}
```

开发服务器不做这层压缩，两份都在，所以开发时看不出任何问题。

**为什么是"我手写前缀"导致的。** 压缩器本来就会按目标浏览器自己补前缀 —— 产物里 Tailwind 的工具类两份都在（各 6 处），就是它补的。**手写前缀等于替工具做决定，而工具会因此删掉另一份。** 去掉手写的那一行之后，产物里两行都回来了：

```css
:root.lc-no-glass *,:root.lc-no-glass :before,:root.lc-no-glass :after{-webkit-backdrop-filter:none!important;backdrop-filter:none!important}
```

**处理。** 源码里只写标准声明；新增两个断言：`check:performance` 要求源码里**不出现**手写的 `-webkit-backdrop-filter`，`check:theme` 的第 7 节**直接读 `dist/assets/*.css`**，要求产物里两份声明都在。

**这条教训比修复本身更值得记住：「源码里写了」不等于「产物里有」。** 压缩、tree-shaking、按目标浏览器降级都会改写产物，而它们失败时是静默的 —— 不报错、类型检查也过。因此 `check:theme` 成了全项目第一处对 **Vite 的 `dist/` 产物**做断言的检查（`check:samples` 检查的 `.lcp` 是仓库里手工打包的示例，不是构建产物）。它的代价是必须先 `pnpm build`（否则那一节会显式打印"跳过"，不会伪装成成功）。

#### 插件说明改为 Markdown 渲染

**类别：** 已实现

市场（以及已安装插件的详情页）此前把 README 直接铺在 `<pre>` 里，`#`、`**`、`- `、表格竖线全部原样露出，长说明基本没法读。现在按 Markdown 渲染。

**安全模型是这次的要点，而不是顺手做的样式改动。** README 是从插件仓库按 tag 取回的**远程内容**，而插件与宿主运行在同一个 WebView、同一个 JS 上下文里（第 4.4 节）。因此这里**没有**采用"把 Markdown 拼成 HTML 再交给消毒库"的常见做法，而是：

- 解析成 AST，由 React 渲染成元素。源码里的 `<script>`、`<img onerror=…>` 之类**在结构上只能作为文本显示** —— 不是"记得消毒"的约定，而是类型上没有那条通路。
- 只承认 `http` / `https` / `mailto`，其余协议（`javascript:`、`data:`、`file:`…）按原文显示：既可读，也不可点。
- 链接点击一律 `preventDefault()` 后交给系统浏览器。否则点一下说明里的链接会让**整个应用界面被替换掉**，比打不开更糟。
- 说明里的图片不自动加载，而是显示为可点击的链接 —— 直接渲染 `<img>` 等于让"打开插件详情"这个动作隐式向第三方主机发一次请求。

**子集是按实测数据划的**（9 个 README、53.7 KB）：标题 86、粗体 81、行内代码 113、围栏代码块 18、表格 106 行、无序列表 29、有序列表 9、引用 6、链接 11、图片 0，**没有嵌套列表、没有列表续行**。因此不支持嵌套列表与引用块内的多段落 —— 遇到时会降级为纯文本显示，而不是消失。**内联 HTML 有意不支持**（理由见上）。

**为什么自己写而不是引库。** 一是安全：常见库的产物是 HTML 字符串，等于把上面那条结构性保证换成一条需要长期维护的消毒链路。二是子集足够小。`scripts/check-markdown.ts` 有 86 项断言盯着它，其中最重要的一组针对的是**"静默吞掉一段文字"**这类失败 —— 例如 `plugin_storage_get`、`sidebar_config.json` 这类标识符绝不能被下划线强调规则吃掉（插件 README 里到处是这种名字）。

（顺带一提，解析器**没有增大入口 chunk**：它只被市场与插件页引用，而那两个模块本身是懒加载的，因此自然落进一个 8.9 KB 的独立 chunk。）

#### 顺带修掉：一个 `private_interfaces` 警告

`backup::archive` 的 `collect_entries` 是 `pub` 而返回类型 `CollectedEntry` 是私有的。这个警告指出的其实是真实的设计问题：一个只在本模块内使用、且带着磁盘绝对路径的内部表示，被暴露在了模块边界上。已改为私有。

#### 新发现、**未处理**：图标的内联 SVG 注入

**类别：** 设计取舍（当前模型下不构成提权，但有值得处理的理由）

`ModuleIcon.tsx` 与 `PluginIcon.tsx` 各有一次 `dangerouslySetInnerHTML`，用来注入模块与插件的**内联 SVG 图标**。唯一的判据是 `isSvgMarkup`，而它只检查字符串是否以 `<svg` 开头 —— **不检查 `<script>`、`on*=` 事件属性或 SVG 内的外部引用**。

**为什么当前不算提权。** 这两处注入的内容来自内建模块的 `module.toml`（随应用发布）与**已安装**插件的清单。而已安装插件的 bundle 本来就已经在这个 JS 上下文里执行过了（4.4 节），给它一个注入点并不增加它能做的事。市场（**未安装**的插件）刻意绕开了这条路：把 SVG 转成 `data:` URL 交给 `<img>`，而 `<img>` 里的 SVG 不执行脚本。

**但有两条理由值得处理：**

1. **这个判据有 4 份副本，且已经漂移了。** `ModuleIcon.tsx`、`pluginRuntime.ts`、`pluginMarket.ts` 都是 `trimStart().toLowerCase().startsWith('<svg')`，而 `PluginIcon.tsx` 那份**漏了 `toLowerCase()`**。后果是同一个插件图标在插件卡片与侧边栏的表现可能不一致（大写 `<SVG` 在一处被识别、在另一处不被识别）。这与项目自己反复记录过的「复制一份必然漂移」是同一件事。
2. **这条注入面一旦被新路径复用就会变成真问题**：只要将来有一处让**未安装**插件的 `iconSvg` 走到这两个组件，它就是一个可执行的注入点。`scripts/check-markdown.ts` 现在把「注入 HTML 的文件集合恰好是这两处」钉成了断言，因此**新增**的注入会失败；但这两处**已有**的注入仍只受一个弱判据保护。

**建议。** 把 4 份 `isSvgMarkup` 收敛成一处共享实现，并在那里把判据从"以 `<svg` 开头"加强为"以 `<svg` 开头，且不含 `<script`、`<foreignObject`、`on<字母>=`、`javascript:`"。这不改变当前模型的信任边界，但把"图标渲染"从"依赖调用方自觉"变成"判据自己就够用"。属于独立的一小轮。

### 7.30 插件不再是模块：贡献模型与按需激活

**类别：** 架构调整（兼容，MINOR）

#### 解决的具体问题

**「功能性插件」此前不可能存在。** 加载成功的判据是「至少注册了一个模块」（`pluginRuntime.ts`），于是：

- 一个只往命令面板加几条动作的插件；
- 一个只做后台监听、没有任何界面的插件；
- 一个只贡献设置项的插件；

都会被判为**加载失败**，在插件页显示为「异常」。侧边栏因此等于插件列表 —— 装 500 个插件就是 500 行。

#### 做法：把「声明」与「执行」分开

`contributes` 与 `activationEvents` 两个字段**此前已被解析、但没有任何消费方**（见 4.6 节）。这一轮把它们变成真：

| 阶段 | 做什么 | 是否执行插件代码 |
| --- | --- | --- |
| 第一趟 | 读清单 → 模块条目进目录、命令条目进面板、设置项登记、右键菜单项登记 | **否** |
| 第二趟 | 只对 `eager` 的插件执行 bundle | 是 |

`eager` 的判据：旧式插件（没有 `contributes`）、显式声明 `onStartup`、或声明了 `contributes` 但没有可用激活事件。

#### 兼容规则（为什么它是 MINOR 而不是 MAJOR）

| 清单 | 结果 |
| --- | --- |
| 没有 `contributes` | **与 1.2.0 之前逐字一致** |
| 有 `contributes` + `activationEvents` | 声明式 + 按需激活 |
| 有 `contributes` + 没有 `activationEvents` | 声明式，但**降级为加载期激活** |

第三行是刻意的取舍：**忘写激活事件只应该损失「懒」，不应该让插件坏掉。** 反过来（默认不激活）会把一个配置疏漏放大成「点开是空白」。

这一条由 `scripts/check-contributions.ts` 第 8 节对着**已有插件仓库里的全部 9 个 manifest** 实测：全部归类为「旧式 / 加载期执行」。

#### 落地的四个贡献点

| 贡献点 | 宿主消费位置 | 需要新 API 吗 |
| --- | --- | --- |
| `modules` | 侧边栏、搜索、深链 | 否 —— `registerModule({ id, component })` 只是把组件交给已声明的 ID |
| `commands` | 全局搜索（Ctrl+K） | 否 —— 声明期登记条目，激活期 `registerCommand` 绑定 handler |
| `settings` | 设置 →「插件设置」 | **否，零代码贡献** —— 宿主照声明渲染，值走已有的 `plugin_storage_*` |
| `contextMenus` | 外壳右键菜单 | 否 —— 菜单项执行的是**一条已声明的命令** |

新增的宿主 API 只有两样：**`ctx.disposables` / `Modulith.onDeactivate()`**（收尾）与 **`Modulith.capabilities`**（特性探测）。

#### 顺带补上的一个真空：卸载时的收尾

此前项目里**没有任何 teardown 路径**：`types/plugin.ts` 的 `activate`/`deactivate` 是明写的草案、Rust 的 `Module::stop()` 从未被调用、`cleanupPluginResources` 只清宿主**知道**的东西。

这对模块型插件无所谓，对功能型插件是致命的：后台服务创建的定时器、窗口监听、观察者、连接，宿主一个都不知道，禁用之后全部泄漏。现在它们由 `ctx.disposables.add()` 登记，宿主在卸载时**逆序**执行、单个抛错不牵连其余、每个只执行一次。

#### 为架构级更新做了什么准备

这一轮**不是**沙箱，但它解掉了沙箱的结构性阻塞点：

1. **`registerModule` 传的是 React 组件对象，`registerCommand` 传的是函数对象 —— 这两样跨不了 realm。** 声明式贡献把它们变成「清单里的 ID + 按 ID 调用的 handler」，这是它们能跨进程的唯一形态。
2. **宿主不再需要「先执行插件才知道它有什么」。** 隔离之后「执行」是一次远程调用，而界面必须在它之前就画得出来。
3. **离真正隔离只剩两处需要动：** 把这两个函数改成 RPC、把 `ctx` 服务改成可序列化调用。其余 API（storage / http / notifications / events / launcher / icons / shell / fileDrop / audio / settings）本来就是「传值进来、返回值出去」的形态。

#### 仍未做的（如实记录）

- **顶层同步死循环仍然无法被中断。** 错峰激活只是把执行摊开，不是沙箱。这条要等独立进程 / Web Worker。
- **稳定性夹具已建立，但只覆盖了机制、没有覆盖规模。** 见 7.31 节 —— 它验证的是「未激活就不执行」「按需激活」「收尾」「冲突拒绝」这些**机制**；「500 个插件装上去会怎样」需要一套**生成出来**的夹具，而不是手写的 8 个。
- **声明式模块的 SVG 图标是后台补的。** 建立目录时不读图标文件（500 个插件就是 500 次 IPC），改由错峰 pass 读回并通知目录。在此之前侧边栏显示回退图标。
- **`isSvgMarkup` 的 4 份副本**（见 7.29 节）仍未收敛 —— 这一轮没有碰它。

#### 一处被顺手修正的文档不实

`清单文件参考` 此前写 `activationEvents` / `contributes` 是「预留字段，当前无消费方」，`插件系统架构` 的宿主 API 表也漏了 `registerCommand` 与 `useModuleActive`。两处都已按代码事实更新，并由 `check-contributions` 对源码断言以防再次漂移。

### 7.31 插件运行时稳定性夹具

**类别：** 测试基础设施（新增）

#### 背景：此前没有一条途径能验证「插件代码到底跑没跑」

1.2.0 的贡献模型把「插件存在」与「插件执行」拆成了两件事，而这件事**只能靠运行来验证**：目录里有没有某个条目、命令面板里有没有某条命令、卸载之后定时器还在不在。静态阅读看不出，纯逻辑断言（`check-contributions.ts`）也够不到。

因此新增 `scripts/check-plugin-runtime.ts`：把**真实的** `pluginRuntime` 装进 Node，配一套手写的浏览器垫片与桩后端，用 9 个合成插件去撞边界。共 66 项断言。

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 解析 | `scripts/harness/loader.mjs` + `resolve-hook.mjs` | 给省略扩展名的相对 import 补 `.ts` |
| 环境 | `scripts/harness/dom-shim.ts` | 最小浏览器环境；**`<script>` 的 textContent 会被真正执行** |
| 后端 | `scripts/harness/plugin-host.ts` | `list_plugins` / `read_plugin_asset` / `plugin_storage_*` 的桩 |
| 夹具 | `scripts/fixtures/plugins/*` | 9 个合成插件（清单 + 代码） |

#### 三条值得单独记下来的决定

**一、不用 jsdom / vitest，而是手写垫片。** 依赖里没有它们，而夹具的价值恰恰在于能在零网络、零安装动作的环境里跑起来。**代价必须说清楚：夹具测的是「运行时在这套垫片上的行为」，不是「在真实浏览器里的行为」。** 因此垫片刻意照抄浏览器语义 —— 最典型的一处是 `<script>` 里的异常**不会**从 `appendChild` 抛出，而是走 `window` 的 error 事件；插件运行时正是靠那条路径把"插件坏了"反映到界面上，若垫片让异常直接冒出来，那条路径就永远测不到，而那恰恰是它存在的唯一理由。

**二、桩后端必须如实拒绝。** `plugin_storage_*` 的桩照 Rust 侧的 `require_permission("storage")` 拒绝没有声明该权限的插件。**一个比真实宿主更宽松的桩比没有桩更糟** —— 它会让夹具显示"没有权限也能读写设置"，而那正是真实运行时不成立的事。这条纪律对将来接入网络出站管控同样成立：那时网络桩要照抄的是**策略**，而不是放行。

**三、（为夹具拆了一处源码）`ModuleRuntimeContext.tsx` 拆成两个文件。** `pluginRuntime` 经 `useModuleActive` 静态依赖到它，而 Node 无法擦除 JSX，于是整条运行时依赖图都没法在无构建步骤的环境里加载。拆开之后类型与 Hook 在 `contexts/moduleRuntime.ts`（无 JSX），Provider 留在原文件并再导出全部既有名字 —— 因此**没有任何调用方需要改 import**。这不是为测试而测试：它把「读取模块可见性」与「把可见性放进 React 树」分成了两件事。

#### 覆盖与未覆盖

覆盖的边界（详见 `scripts/harness/README.md`）：旧式插件行为不变、声明式按需激活（含"未激活时一个 bundle 都没执行"）、纯命令插件、后台服务插件的收尾三保证、顶层抛错的隔离、空贡献仍判失败、模块 ID 抢占被拒、卸载后命令声明仍在、设置读取时机与权限、以及 8 个插件里只有 5 个被执行。

**未覆盖：**

- **React 渲染。** 断言止于「拿到了组件」，没有真的渲染 —— 那需要 DOM 与 React 渲染器。模块崩溃会不会被错误边界接住，不在这里验。
- **规模。** 9 个手写夹具证明的是机制，不是「500 个插件」的行为。后者需要一套生成的夹具。
- **顶层同步死循环。** 它无法被中断，因此不可能"测过去"。

### 7.32 图标在目录重建后丢失，与残留在缓存里的旧图标

**类别：** 缺陷（已修）＋ 夹具覆盖

#### 两个症状

1. **插件删除重装后，侧边栏图标不出现** —— 时好时坏，有时要刷新。
2. **侧边栏用的图标不是插件自带的那个**。

#### 根因：一处「后补」的机制没有覆盖所有入口

模块图标是**后补**进目录的：清单期只拿得到图标**路径**（`icon.svg`），内容要用 `read_plugin_asset` 异步读回来，再由 `setModuleIconSvg` 写进目录条目。

而目录在**每一次** `reloadPluginRuntime()` 时都被 `clearDynamicModules()` 清空重建。于是"图标已经补过一次"这个状态，在下一次重建之后就失效了。三处叠加：

**一、补图标的入口只有一个。** `prefetchDeclaredIcons()` 原先只在 `loadPluginsInBackground()` 里被调用，而「安装 / 卸载 / 启用 / 禁用」这四条路径只调 `reloadPluginRuntime()` —— 重建完目录就没有下文。这是症状 1。

**二、缓存被当成了目录状态。** `prefetchDeclaredIcons()` 里有一句"已经有图标就整个跳过"。它想省的是**读盘**，结果把 `setModuleIconSvg` 一起省了 —— 而后者才是让新建的目录条目拿到图标的那一步。只要进程内还留着这份缓存，重建后的条目就永远补不上。这也是症状 1 的一部分。

**三、卸载时漏清缓存。** 清理循环原先只遍历 `injectedAssets`，而那张表**只有执行过代码的插件**才有条目。声明式插件在按需激活之前不写它，但它的图标已经被预取进了 `pluginIcons`。卸载时缓存留了下来，重装后这份**旧图标**被当成"已经有了"继续用 —— 这就是症状 2。

#### 修法与验证

- 补图标移进 `reloadPluginRuntime()` 的末尾（`listOnly` 除外），四条生命周期路径自动覆盖；`loadPluginsInBackground` 里那次重复调用删掉。
- 缓存只用来省读盘：`pluginIcons.has()` 短路的是 `prefetchPluginIcon`，不是 `setModuleIconSvg`。
- 清理改成拿「所有已知插件 ID」（`injectedAssets` ∪ `pluginIcons` ∪ `loadStates` ∪ `activationStates`）与活跃集合做差。
- 顺带删掉一段**死代码**：那个遍历 `contracts.keys()` 的清理循环，其上方几行刚刚 `contracts.clear()`，条件永远不成立。它唯一的效果是让 `unregisterPluginSettings` 看起来有调用方 —— 那个函数其实是死导出，一并删除。也就是说，「按插件清理设置」这个粒度**从来没有真正生效过**，一直被 `clearPluginSettings()` 的全清掩盖着。

新增夹具 `declarative-icon`（声明式 + 按需激活 + `icon.svg`）与 6 项断言。**两个半边都单独验证过会红**：临时注释掉补图标调用 → 4 项失败；临时去掉清理里的三个来源 → 恰好 1 项失败（"重新启用后重新读了图标文件"），而后者正是症状 2 的机制。

**未覆盖：** 真实浏览器里的渲染。夹具断言的是"目录条目的 `iconSvg` 是对的"，不是"侧边栏画出来的像素是对的"。
### 7.33 出站管控漏掉了插件市场：一条必须靠"记得写"才生效的纪律

**类别：** 功能缺陷（已修）＋ 架构收口

#### 现象

「设置 → 网络」把出站策略改成「禁止出站」、或打开离线模式，刷新之后**插件市场照样能正常加载**。界面上那个开关看起来完全没生效。

#### 根因：判定被手写在调用点上，而调用点不止一个

第一版的出站策略与流量日志是**手写**在 `plugins/manager.rs` 的 `plugin_http_request` 里的（判一次 `decide`、记一条日志、再发请求）。而同一个文件里的 `fetch_once` —— 插件索引、索引签名、README、市场图标、`.lcp` 包下载全都走它 —— 一个字的判定都没有。

所以真实情况是：**插件的 `network` 请求受管控，而插件市场不受管控**。后者恰恰是用户最常触发联网的那条路，也是他最容易用来验证开关是否生效的那条路。

问题不在于"谁忘了写那一段"。**那种写法要求每一个新调用点都记得写一次**，而它当时看起来是对的 —— 手写的那一处功能完整、注释齐全、还带了测试。真正缺的是一条让"漏掉"变得不可能的机制。

#### 做法：把裸客户端收进唯一门面

新增 `modules/net/client.rs`：

- `NetClient` **私有持有** `reqwest::Client`，且**不提供任何把它交出去的方法**；
- 判定（`policy::decide`）、记录（`log::record`）与发送（`Client::execute`）只在 `execute()` 一处发生；
- 调用方拿到的唯一入口是 `get_and_send()` / `execute()`。

于是"绕过策略发一个请求"不再是纪律问题，而是类型问题：拿不到裸客户端就发不出去。`PluginManager` 的 `client` 字段直接删除，`probe.rs` 与 `updater` 一并改用门面。

**顺带修掉的两处不一致：**

1. **`decide` 从来没有看过地址。** 而「禁止出站」的档位说明里写着"本地回环地址不受影响" —— 文案说的是行为，实现里没有。现在 `decide(mode, offline, loopback)` 收下这个维度，回环在任何档位（含离线）下放行，并有断言钉死。第一次跑这条断言时它是红的。
2. **更新的检查与下载根本不经过门面。** `tauri-plugin-updater` 用自己的传输，我们无法在传输层拦它。能覆盖的是命令入口：离线或禁止出站时 `check_app_update` / `install_app_update` 在发起前直接拒绝，并记一条日志。**这是入口拦截，不是传输层拦截，两者不能混为一谈。**

#### 门禁：让"绕过"编译不过，也让文本检查兜住

`pnpm check:network` 新增两条静态断言（已在真实违规上验证过会红）：

- `reqwest::Client` 的持有者**恰好**是 `net/client.rs`（断言"恰好"而不是"其它地方没有"：后者在有人换用别的 HTTP 库时会安静通过）；
- `.send()` **不允许出现在任何地方** —— 门面用的是 `Client::execute`，所以它一旦出现就意味着有人自己建了客户端。

#### 仍未覆盖（必须说清楚）

- **WebView 里插件自己发的 `fetch`。** 插件与宿主共享同一个 JS 上下文，它可以直接调 `fetch()`，那条路根本不经过 Rust。约束它只能靠 CSP 的 `connect-src`。**在这一条补上之前，"所有出站都被记录"是不成立的。**
- **应用更新的传输层。** 见上：只有入口拦截，流量日志里不会出现更新的请求。
- **本机代理是绕道。** 回环地址不受管控是刻意的（原因见文档），代价是：如果用户把下载源/代理指向本机，流量会经由它出去，而策略与离线模式都不会拦。

完整说明见[网络访问与下载源](../02-开发指南/网络访问与代理.md)第 8 节。

### 7.34 界面文案里的 Markdown 星号

**类别：** 显示缺陷（已修）＋ 新增门禁

文案从文档里抄进 JSX 时，`**强调**` 会**原样显示**成一串星号 —— 更新卡片的纯文本说明早就有这条检查（`check-markdown.ts` 查 `release/notes.md`），但界面本身没有。

真实的笔误是三处：网络设置页的"本地回环地址不受影响"与"它是诊断用的，不是审计"，以及备份恢复页的"覆盖本机当前的凭据"。

`check:markdown` 现在多查一项：扫描全部 `.tsx`，剥掉注释后不允许出现字面 Markdown 粗体。**剥注释是这条检查能成立的前提** —— 本仓库大量在注释里刻意使用 `**` 写法，第一版没剥干净时 53 个文件报了 24 处，其中 23 处是注释。

### 7.35 插件能自己联网：CSP 与前端门面

**类别：** 安全边界（新增）＋ 可观测性

#### 问题

`plugin_http_request` 那套管控（权限、策略、日志）只覆盖**走后端**的请求。插件与宿主共享同一个 JavaScript 上下文，它可以直接 `fetch('https://…')` —— 权限检查、出站策略、流量日志，三者一起被绕过去，而且连"是谁发的"都无从知道。

在 7.32 那次收口之后，这是"所有出站都被记录"唯一还站着不成立的地方。

#### 两层，分工不同

| 层 | 位置 | 作用 |
| --- | --- | --- |
| CSP `connect-src` | `tauri.conf.json` | **真正的边界**。由浏览器引擎执行，JS 改不掉 |
| 前端门面 | `src/services/netGuard.ts` | **可读性与可观测性**。包装 `fetch` / `XMLHttpRequest` / `WebSocket` / `sendBeacon`，给出"是谁、要去哪、为什么"并落进流量日志 |

`connect-src` 只留 IPC 与回环。**回环是刻意的**：它不出本机，而"插件连本地开发服务器"是正当场景。门面与 CSP 的口径必须一致，否则会出现"门面放行、CSP 挡下"这种最难解释的组合。

#### 为什么门面不是安全边界（写在它自己的文件头上）

同一个 realm 里还有 `<img src>`、`<script src>`、`<link rel=preload>`、`import()`、`EventSource` —— 它们不经过任何被包装的函数。被包装的函数本身也挡不住刻意绕行。

所以门面的定位是：**让老实插件守规矩，并且让"不守规矩"这件事在日志里看得见**。真正的边界只有 CSP。这一点写进了 `netGuard.ts` 的文件头、`网络访问与代理.md` 的 §8.6，以及宿主 API 参考里 `ctx.http` 的开头 —— 因为"我们加了防护"这句话最容易被读成"我们是安全的"。

#### 一处真实缺陷：`new URL(url, location.href)` 把拼错的地址变成放行

门面第一版用 `new URL(url, window.location.href)` 解析地址。后果是 `new URL('不是地址', base)` **不会抛错** —— 它把任何相对路径或拼错的东西解析成同源地址，而应用的宿主正是 `localhost`，于是它们全部落进"回环放行"那一支。**拼错等于放行。**

夹具里那条"解析不了的地址一律拒绝"第一次跑就是红的，改法是去掉 base、只认绝对地址（`ctx.http` 本来也只接受完整地址）。这条断言现在留着。

#### 唯一无法自动化验证的改动

CSP 的失败模式是运行期的：构建、类型检查、全部 13 个 check 脚本都不会因为它变红。因此 `网络访问与代理.md` §8.7 有一份**必须人工跑的八项清单**（IPC、插件加载、插件样式、提示音、图标、HMR、`ctx.http`、门面拒绝），并写明"1 至 5 中任何一条失败都说明那条指令需要放宽，放宽时只动相关的那一条并在这里补一句为什么"。

已知的脆弱点：`dangerousDisableAssetCspModification` 里钉死了 `script-src` 与 `style-src` —— 插件是宿主在运行期注入的 `<script>` / `<style>`，拿不到 Tauri 在编译期追加的 nonce/hash。不钉死它们，`'unsafe-inline'` 会因为同策略里出现 nonce 而**整体失效**，症状是插件一个都加载不了。
