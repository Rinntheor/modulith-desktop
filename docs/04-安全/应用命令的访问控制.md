# 应用命令的访问控制

本文件说明**宿主自己的 Tauri 命令**是怎么被授权的。它与[认证与安全](认证与安全.md)是两件事：那一册讲"谁能进入应用"，这一册讲"进入之后，哪一段界面代码能调哪些后端命令"。

---

## 1. 一句话

**在 `src-tauri/build.rs` 声明应用级 ACL 清单之前，Tauri 对应用自己注册的命令完全不检查权限 —— 任何一个 webview 都能调全部 120 条。**

这不是"配置写宽了"，是"根本没查"。当前已经声明，因此语义是**默认拒绝**：每条命令必须被某个 capability 明确授权。

---

## 2. 为什么默认放行（以及它是怎么被堵上的）

判定发生在 `tauri/src/webview/mod.rs` 的 `on_message()`（本仓库锁定的是 `tauri 2.11.5`，行号约 1823）：

```rust
if (plugin_command.is_some() || has_app_acl_manifest || !is_local)
  && request.cmd != crate::ipc::channel::FETCH_CHANNEL_DATA_COMMAND
  && invoke.acl.is_none()
{
    // 拒绝
}
```

三个条件只要有一个成立，就要求 `invoke.acl` 有值：

| 条件 | 什么时候成立 |
| --- | --- |
| `plugin_command.is_some()` | 命令形如 `plugin:<插件>|<命令>`，即**插件**提供的命令 |
| `has_app_acl_manifest` | 应用声明过**应用级 ACL 清单** |
| `!is_local` | 请求来自**非本机来源**（远端 URL） |

本应用界面跑在 `tauri://localhost` / `http://tauri.localhost` 上，属于 `is_local`；应用的命令又不带 `plugin:` 前缀。于是**第三个条件都不成立时，这条 if 整个被跳过** —— 权限表里写什么都没用。

`has_app_acl_manifest` 的完整推导链（都已在本仓库锁定的依赖里逐行核对过）：

```
tauri-build 生成 acl-manifests.json，其中含 "__app-acl__"
   → tauri_utils::acl::has_app_manifest()  = acl.contains_key("__app-acl__")
   → RuntimeAuthority.has_app_acl
   → on_message() 里的 has_app_acl_manifest = true
```

所以"声明应用级 ACL 清单"不是一个可选的整洁度改进，它是**这条判定路径的开关**。

当前声明在 `src-tauri/build.rs`：

```rust
tauri_build::try_build(
    tauri_build::Attributes::new()
        .app_manifest(tauri_build::AppManifest::new().commands(&[ /* 120 条 */ ])),
)
```

`tauri-build` 会为每条命令自动生成两个权限：`allow-<命令名，下划线换成连字符>` 与 `deny-...`。

---

## 3. 三份列表必须一致

这是这套机制唯一容易出事的地方，因为**不一致只在运行期暴露**：

| 谁 | 内容 | 少一条的后果 |
| --- | --- | --- |
| `src-tauri/src/lib.rs` 的 `generate_handler!` | 真正注册的命令 | 命令不存在，前端调用报"命令未找到" |
| `src-tauri/build.rs` 的 `AppManifest::commands` | 生成权限的命令 | **没有任何 capability 能授权它** → 对所有人不可用 |
| `capabilities/app-commands.json` 的 `allow-*` | 实际授权 | 那条命令对主界面不可用 |

由 `pnpm check:acl` 逐条比对三处（21 项断言），任何一处漂移都会失败。

它同时盯住另一件更隐蔽的事，见下一节。

---

## 4. `windows` 与 `webviews` 不是同义词

capability 的两个作用域键语义不同（Tauri 官方文档原话）：

| 键 | 语义 |
| --- | --- |
| `webviews` | 只发给标签匹配的那些 **webview** |
| `windows` | 发给该窗口下的**所有 webview**，与 `webviews` 怎么写无关 |

现在只有 `main` 与 `tray-menu` 两个 webview，两者看起来等价。**插件沙箱（v2.0）落地后它们不再等价**：插件 webview 会被放进主窗口，那一刻任何一处写成 `"windows": ["main"]` 都会把整份宿主授权 —— 包括全部 120 条应用命令 —— 送给插件，而**构建、类型检查、其余门禁全都不会变红**。

因此本仓库的约定是：**capability 一律使用 `webviews`**。`check:acl` 有一条断言：任何 capability 出现 `windows` 键即失败。

---

## 5. 当前的授权分布

| capability 文件 | 作用域 | 授权 |
| --- | --- | --- |
| `capabilities/default.json` | `webviews: ["main"]` | `core:default`、`opener:default`、`opener:allow-open-path`（带路径范围）、11 条 `core:window:*` |
| `capabilities/app-commands.json` | `webviews: ["main"]` | 全部 120 条应用命令 |
| `capabilities/tray-menu.json` | `webviews: ["tray-menu"]` | 只有 `allow-tray-menu-state`、`allow-tray-menu-action` |

托盘菜单那一行值得单独说：**它此前一条 capability 都没有，却一直能用** —— 正是因为它调用宿主命令时根本不经过检查。清单一旦声明就会变成默认拒绝，所以这两条是补上的。

它只有两条，且由门禁保证**不多不少**：多给一条就是"一个只负责显示菜单的窗口拿到了没有依据的能力"，少给一条就是"某个开关点了没反应，而这只在运行期暴露"。

`capabilities/` 目录下每个窗口都被覆盖这一点也由门禁保证 —— 一个没有任何 capability 的窗口，在清单声明之后**连 IPC 都用不了**。

---

## 6. 生成物不进仓库

`tauri-build` 每次构建会把每条命令的两个权限写进 `src-tauri/permissions/autogenerated/`，一条命令一个文件（当前 120 个）。

**它被 `.gitignore` 忽略**，真源是 `build.rs`。理由不是体积，是 diff 会被淹没：改一条命令名会带出 120 个文件的变更，而其中任何一个都不会有人真的去读。

`capabilities/` 相反 —— 它是手写的、要被审阅的，必须进仓库。

---

## 7. 怎么加一条新命令

1. 在 `lib.rs` 里写命令并加进 `generate_handler!`；
2. 在 `build.rs` 的 `AppManifest::commands(&[...])` 里加同名的**下划线形式**；
3. 在 `capabilities/app-commands.json` 里加 `"allow-<连字符形式>"`；
4. 跑 `pnpm check:acl`。

漏掉第 2 步或第 3 步，门禁都会失败并指出是哪一条。若这条命令是给某个**非主界面**窗口用的，那么它不该进 `app-commands.json` —— 应当放进那个窗口自己的 capability，并同步更新 `check:acl` 里托盘菜单那一段的比对对象。

---

## 8. 它与插件隔离的关系（**不要读错**）

这一层买到的是**宿主自身命令的默认拒绝**，它本身**不改变插件的处境**：

插件代码今天仍与宿主跑在同一个 JS realm、同一个 `main` webview 里，因此它仍然调用全部 120 条命令 —— 那正是"同 realm 无法区分谁在调用"的直接后果，见[插件系统架构](../02-开发指南/插件开发/插件系统架构.md)第 6 节。

**它的价值在于它是沙箱的前置条件**：插件一旦被挪进自己的 webview（标签是另一个），ACL 只要没给那个标签授权，插件就真的调不动任何应用命令。没有 `AppManifest::commands`，即使把插件挪出去，它照样能调 —— 因为那条判定路径根本没开。

所以它可以被独立交付、独立验证，但它**不是**"插件已经安全了"。

---

## 9. 尚未验证的部分

**应用在本机跑不起来**（有一条先于应用任何代码的启动阻塞，见[已知问题与技术债](../06-项目/已知问题与技术债.md)）。因此：

| 已验证 | 怎么验证的 |
| --- | --- |
| 命令列表三处一致 | `pnpm check:acl`（21 项断言） |
| capability 里的权限标识符**真实存在** | `tauri-build` 在构建期校验 capability，未知权限会让构建失败 |
| `__app-acl__` 真的被写进了运行时清单 | 检查构建产物 `gen/schemas/acl-manifests.json`：`__app-acl__` 下 240 条（120 `allow` + 120 `deny`） |
| capability 用的是 `webviews` 而非 `windows` | 检查 `gen/schemas/capabilities.json` |
| 其余功能未被波及 | 24 个 `check:*` 门禁、`tsc`、398 个 Rust 测试全绿 |

| **未验证** | 为什么 | 怎么补 |
| --- | --- | --- |
| 应用运行期是否一切照旧（尤其是托盘菜单） | 应用跑不起来 | 能启动之后，逐项走一遍：解锁、托盘右键菜单、设置页各分页、插件安装与存储 |
| 一条**未被授权**的命令被调用时的实际表现 | 同上 | release 下应返回 `Command <命令名> not allowed by ACL`；debug 下是带 capability 归属的详细诊断 |
| `core:default` 是否覆盖了主界面真正用到的全部核心 API | 静态无法穷举运行期调用 | 同上；若某处报 `core:...` 被拒，说明需要补一条 `core:` 权限 |
