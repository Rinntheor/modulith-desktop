# 认证与安全

Modulith 提供访问授权能力，用于在应用启动时验证使用者身份。本文描述其实现机制、参数取值与威胁模型。

## 1. 设计目标

| 目标 | 实现方式 |
| --- | --- |
| 不保存明文密钥 | Argon2id 派生后仅存 PHC 哈希串 |
| 不设默认密钥 | 首次使用由用户创建，长度下限 8 字符 |
| 不可判定即拒绝 | 配置损坏时回落到「需要授权且未初始化」 |
| 硬件绑定 | 自动登录凭据的加密密钥由硬件指纹派生 |
| 抵御暴力破解 | 失败尝试计数与请求限流 |
| 可审计 | 登录记录与已知设备列表 |

第一条与第三条是安全敏感组件的核心取舍：**宁可让用户重新设置密钥，也不静默放行**。

## 2. 访问密钥

### 2.1 派生与存储

密钥使用 Argon2id 派生，采用 crate 的默认参数，输出 PHC 格式字符串：

```
$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>
```

PHC 字符串自带算法标识、参数与随机盐，因此验证时无需额外存储参数，且同一密钥每次派生的结果都不同。

派生后的字符串保存在 `<app_data>/auth.json`。**明文密钥不写入磁盘，也不出现在任何日志中。**

### 2.2 长度约束

| 约束 | 值 | 原因 |
| --- | --- | --- |
| 最小长度 | 8 字符 | 前端与服务端共同校验 |
| 最大长度 | 256 字符 | 防止超长输入拖慢 Argon2 派生 |

长度按字符数而非字节数计算，因此中文等多字节字符可正常使用。

### 2.3 校验流程

```
接收明文密钥
      |
      v
查询该标识是否处于封锁期 ---- 是 ---> 拒绝并返回剩余时间
      |
      v
检查请求频率是否超限 -------- 是 ---> 拒绝
      |
      v
Argon2id 派生并与已存哈希比对
      |
      |-- 匹配 ---> 清零失败计数，签发会话
      |
      `-- 不匹配 --> 失败计数加一
                     |
                     `-- 达到阈值 ---> 封锁
```

比对使用常量时间比较，避免通过响应时间推断哈希内容。

## 3. 会话

会话在内存中维护，不落盘。签发的令牌通过 `sessionStorage` 保存在前端。

| 参数 | 值 |
| --- | --- |
| 有效期 | 24 小时 |
| 存储位置 | 前端 `sessionStorage`，键名 `modulith.auth.token` |
| 服务端状态 | 内存中的会话表 |

选择内存而非磁盘保存会话，意味着应用重启后需要重新解锁。

会话校验统一由一份错误信息表示：

```
未授权的操作：会话无效或已过期，请重新解锁
```

`get_auth_status` 与 `verify_session` 两条命令不接受会话守卫，因为它们本身用于回答「当前是否需要解锁」。其余涉及敏感数据的命令在签名中要求 `token` 参数。

### 3.1 主动锁定

用户点标题栏的「锁定」后，`logout` 命令会：

1. 结束**全部**会话（不是只结束调用方那一个）；
2. 置上**「本进程已锁定」标记**（`AuthState` 内的 `locked`）。

第 2 步是修一个真实漏洞所必需的，值得单独说明。

**漏洞：只删会话不足以锁定。** `sessionStorage` 会在 WebView 重载时被清空。如果 `logout` 只删会话，那么用户点「锁定」之后，**任何人按一下 Ctrl+R 就能直接进去** —— 启动流程会发现「未认证但 `autoLogin` 为真」，而「记住我」凭据仍然有效，于是自动放行。锁定形同虚设。

**修法：区分「冷启动」与「运行中主动锁定」。** 这两件事对「是否允许自动登录」的答案相反：

| 场景 | 是否允许自动登录 | 理由 |
| --- | --- | --- |
| 应用冷启动（关掉再开） | **允许** | 这正是「记住我」的目的 |
| 运行中主动锁定（含 Ctrl+R 重载） | **不允许** | 用户明确表达了「我要离开一下」 |

因此不能用「作废凭据」来实现（那样冷启动的自动登录也没了，「记住我」会退化成「只在同一次运行内有效」）。正确做法是记一个**跨越页面重载、但不跨越进程重启**的标记，而这个位置恰好是 Rust 进程内存：

| 存储位置 | 跨 Ctrl+R | 跨应用重启 | 可用 |
| --- | --- | --- | --- |
| JS 内存变量 | 否 | 否 | 不够 |
| `sessionStorage` | 否（重载即清） | 否 | 不够 |
| `localStorage` | 是 | 是 | 会永久禁掉自动登录 |
| **`AuthState`（Rust 进程内存）** | **是** | **否** | **正确** |

`try_auto_login` 因此多了一道前置检查：`locked` 为真时直接返回失败（不带 `message`，因为这只是一次"没自动登录成功"，不是错误）。

**解除条件。** 任何「用户亲手证明身份」的成功路径都会清除该标记：输入访问密钥、首次创建密钥、用恢复码重置。漏掉任何一处都会让「记住我」永久失效。

**前端配合。** `boot.ts` 会读 `AuthStatus.lockedByUser` 并提前短路（省一次 IPC），解锁界面也会说明「你已主动锁定本应用，本次运行期间需要输入访问密钥」，避免用户以为「记住我」坏了。但**真正的门闩在后端**，前端判断被绕过也进不去。

### 3.2 会话与插件

这一设计有必要单独说明：**插件与宿主运行在同一个 WebView 中**，因此插件代码能够读取 `sessionStorage`，也就能够取得当前会话令牌。会话守卫可以阻止命令被随意调用，但无法在恶意插件面前保护令牌本身。

因此当前的信任模型是：安装插件视同运行本机程序。详见第 8 节。

## 4. 自动登录

「记住我」让用户在一段时间内免于重复输入密钥。它的实现分三步。

### 4.1 派生加密密钥

以硬件指纹为输入，通过 HKDF-SHA256 派生 AES-256-GCM 密钥：

| 参数 | 值 |
| --- | --- |
| 派生函数 | HKDF-SHA256（RFC 5869） |
| 输入密钥材料（IKM） | **已经过 SHA-256 的**硬件指纹摘要 |
| HKDF salt | `crypto_salt`（随机生成，与哈希一起落盘） |
| HKDF info（域分隔标签） | `modulith_remember_token_key_v1` |
| 输出 | 32 字节 AES-256 密钥 |

域分隔标签把该密钥限定在「记住我」这一用途上，即使同一份指纹被用于其他派生，密钥也不相同。

HKDF 使用 `hmac` 与 `sha2` 手工实现，未引入额外的 `hkdf` crate。

**指纹到 IKM 的转换。** `HardwareFingerprint::derive_binding_key` 把 `modulith_hardware_binding_v1` 这个域标签与各字段（MAC、主机名、OS、CPU 型号、核心数）**依次喂给同一个 SHA-256**，得到 32 字节摘要。注意两点：

- 这是**连续 `update()` 调用，没有插入任何分隔符**。域标签的作用是避免与其他用途的指纹派生相撞，而不是字段分隔。
- 它不同于设备标识（device_id）的生成：后者在 `modules/auth/device.rs` 中处理，那里**确实**使用 `\u{1f}`（单元分隔符）拼接由前端上报的字段。

### 4.2 加密凭据

凭据使用 AES-256-GCM 加密后保存：

| 参数 | 值 |
| --- | --- |
| 算法 | AES-256-GCM |
| nonce 长度 | 12 字节，**每次加密随机生成**，与密文一起拼接后 base64 编码 |
| 附加认证数据（AAD） | **不使用** |
| 存储形式 | `base64(nonce ‖ ciphertext)` |

**关于 AAD。** 当前实现调用 `cipher.encrypt(nonce, plaintext)`，**没有传附加认证数据**。因此完整性保护的依据是 GCM 自身的认证标签，而不是「密文与域标签绑定」。

这不构成实际弱点：密钥已经由硬件指纹派生，换机器或改硬件时密钥不同，解密直接失败——域区分由**密钥派生**承担，不需要再叠加 AAD。但如果将来出现「同一把密钥加密多种用途数据」的情况，就必须补上 AAD，否则不同用途的密文可以互相替换。

### 4.3 解密与校验

```
读取凭据 -> 采集当前硬件指纹 -> 派生密钥 -> 解密
      |
      |-- 失败 ---> 视为凭据无效，要求输入密钥
      |
      `-- 成功 ---> 与存储的摘要比对
                     |
                     |-- 不一致 ---> 拒绝
                     `-- 一致 -----> 签发会话
```

两步校验的作用不同：解密成功证明凭据来自本机（因为密钥由硬件派生），摘要比对证明凭据内容是完整的。解密本身已提供认证（GCM 标签），摘要比对是**第二道**独立检查——它拦的是「密文可解但内容不是当初存的那把」这类情形，例如有人用同一台机器的指纹重新加密了一个自己构造的令牌。

更换硬件（如更换主板、网卡）会导致指纹变化，自动登录随之失效，用户需重新输入密钥。这是预期行为。

## 5. 硬件指纹

指纹由多项硬件与系统信息组合而成：

| 来源 | 说明 |
| --- | --- |
| 网络接口 MAC | 主要熵来源（全零地址会被忽略） |
| 主机名 | 辅助区分 |
| OS 标识 | 辅助区分 |
| CPU 型号 | 辅助区分 |
| 物理核心数 | 辅助区分 |

这些字段被**依次拼入哈希**（`crypto.rs` 的 `derive_binding_key`），字段之间不插入分隔符。由于每个字段的前后都有固定标签或定长编码（核心数以小端字节写入），拼接不会产生歧义。

指纹采集使用 `sysinfo`，代价较高（数十毫秒），因此用 `OnceLock` 缓存，进程内只采集一次。

指纹计算结果在进程内缓存，并通过 `OnceLock` 复用，避免每次校验都重新采集。指纹会附加一段可读标签用于界面展示。

## 6. 抗暴力破解

两层独立机制：

### 6.1 失败尝试跟踪

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `max_attempts` | 5 | 触发封锁的失败次数 |
| `block_minutes` | 15 | 封锁时长 |
| `reset_minutes` | 30 | 失败计数窗口 |

计数按标识分组，窗口内失败次数达到阈值即封锁。窗口过期后计数自动重置。封锁期间即使输入正确密钥也会被拒绝。

跟踪的标识数量上限为 256，超出后清理已过期条目，避免内存无限增长。

### 6.2 请求限流

| 参数 | 值 |
| --- | --- |
| 窗口内最大请求数 | 10 |
| 窗口长度 | 60 秒 |

限流独立于失败计数，作用于所有请求。它防止高频探测，即使尝试的密钥都不同也会被拦截。

两层机制的区别：失败计数针对「猜错密钥」，限流针对「请求过多」。

## 6A. 恢复码

访问密钥只保存 Argon2id 哈希，因此**不存在任何形式的「找回」**。为了让用户忘记密钥时不至于永久失去本机授权状态，系统提供恢复码作为自救通道。

### 6A.1 形态与强度

**一次生成 3 枚互不相干的短恢复码，每枚各能用一次。**

| 项目 | 取值 | 代码位置 |
| --- | --- | --- |
| 字母表 | Crockford Base32：`0123456789ABCDEFGHJKMNPQRSTVWXYZ`（32 种） | `crypto::RECOVERY_ALPHABET` |
| 单枚长度 | 20 个字符（展示时按 5 字符分 4 组，用 `-` 连接） | `RECOVERY_CODE_LEN` / `RECOVERY_GROUP_LEN` |
| 单枚熵 | 20 × log₂(32) = **100 bit** | |
| 数量 | **3 枚** | `RECOVERY_CODE_COUNT` |
| 存储 | 每枚各存一个 Argon2id PHC 字符串（`recoveryHash` 数组） | `AuthConfig::recovery_hash` |

**为什么是 3 枚。** 枚数越多，「抄漏一枚仍可用」的容错越强，但收益递减；3 枚足以覆盖「抄漏一枚」与「分两处存放」这两件真实会发生的事，同时不让设置页的列表变得冗长。

字母表刻意排除了 `I`、`L`、`O`、`U`：

- `I`/`L` 与 `1` 形近，`O` 与 `0` 形近，排除后抄写不会产生歧义；
- `U` 是 Crockford 为降低随机串意外拼出脏词的概率而排除的。

归一化函数（`crypto::normalize_recovery_code`）会进一步把用户可能写错的 `I`/`L` 折叠为 `1`、`O` 折叠为 `0`、`U` 折叠为 `V`，并忽略大小写、空格与连字符。因此「照抄原件」「全小写」「不带连字符」都能通过。归一化后长度不足 12（`RECOVERY_MIN_INPUT_LEN`）的输入直接判否，不进入 Argon2——避免用极短输入消耗算力。

**为什么是多枚短码，而不是 1 枚长码。** 最初的实现是单枚 32 字符的长码，界面上按 4 字符分组显示。结果是用户把它读成"多个恢复码"，只输入其中一组，于是每次都报错；而且他无法自行判断到底该输整串还是输一组。**歧义的根源是形态本身**——一整串按组分隔的字符既像一个码，也像几个码。

改成多枚短码之后：

| 好处 | 说明 |
| --- | --- |
| 无歧义 | 每个恢复码是列表里的一行、一份完整凭据，不存在"要不要全输"的疑问 |
| 部分容错 | 丢了几枚还有其余可用，不必因为抄漏一枚就作废全部 |
| 心智一致 | 与 GitHub / Google 的备份码形态相同，用户已有现成模型 |

**关于熵。** 三枚合计**不等于** 300 bit：攻击者只需猜中任意一枚即可。因此有效强度由单枚的 100 bit 决定，这远超暴力搜索能力。配合"用掉即失效"与请求限流，实际强度足够。

### 6A.2 生命周期

```
创建访问密钥 ──→ 生成 3 枚恢复码（明文只返回这一次）
                    │
                    └─→ 用户离线保存

用其中一枚重置 ──→ 只删除被用掉的那一枚，其余保留
                    │
                    └─→ 不换发新码

手动「重新生成」──→ 整套作废，换发新的 3 枚
```

- **用掉一枚只作废那一枚，其余保留。** 这是**安全性质，不是偷懒**：早期实现是「重置成功后整套换发」，它有致命缺陷——若攻击者先用一枚恢复码重置了访问密钥，整套就会换成**攻击者手里**的新码，而用户手中的纸全部作废，攻击者不仅拿到访问权还把合法用户永久锁在门外。只删除被用掉的那一枚，用户**始终保留夺回控制权的能力**。
- **整套换发只发生在「重新生成」时**：`generate_recovery_code` 会作废全部旧码，只保留最新一批。
- **成功后清空全部会话**：任何已登录的窗口都会退回解锁界面，因为密钥已经换了。
- 审计日志会记录命中的是第几枚（`recovery-reset#2`）。

代价需要说明清楚：不再有「一次重置就自动清空所有旧纸」的行为。要主动作废旧纸，必须去「设置 → 安全 → 密钥恢复」点「重新生成」。这意味着若攻击者拿到了纸却还没用，在你手动重新生成之前它们一直有效。取舍的结论是：**主动作废优于被攻击者替你作废**。

### 6A.3 重置流程为何不需要会话

恢复入口（`verify_recovery_code` 与 `reset_access_key_with_recovery_code`）是本模块中**唯一**不要求有效会话的密钥变更通道。

原因很直接：用户忘记访问密钥时应用正处于锁定状态，不可能先提供一个有效会话——那等于没有恢复通道。因此安全性完全由恢复码本身承担，并叠加了以下约束：

| 约束 | 作用 |
| --- | --- |
| 单枚 100 bit 熵 | 即便 `auth.json` 泄露，也只能对 Argon2id 哈希暴力搜索，不存在口令字典空间 |
| 请求限流 | 避免被当作 Argon2 算力放大器（与密钥校验共用同一个限流器） |
| 失败计数与设备锁定 | 连续失败达阈值即临时锁定（见第 6 节） |
| 一次性使用 | 每枚用掉即失效 |
| 新密钥通过长度校验 | 不能借恢复流程把密钥设成空串 |
| 全程写入登录审计 | `recovery-verified` / `recovery-reset#N` / `bad-recovery-code` / `recovery-token-invalid` / `recovery-rate-limited` / `recovery-unavailable` |

匹配过程（`crypto::match_recovery_code`）逐个比对哈希、命中即停；**全部不匹配时才会算满 3 次 Argon2**。这让失败尝试天然比成功尝试更慢，对暴力枚举不利。

### 6A.3.1 两步流程与一次性凭据

重置刻意拆成两步，而不是一个包含多个输入框的表单：

| 步骤 | 命令 | 作用 |
| --- | --- | --- |
| 1 | `verify_recovery_code` | 只核验恢复码，**不修改任何状态**；通过后签发一个一次性令牌 |
| 2 | `reset_access_key_with_recovery_code` | 用令牌设置新密钥，消费令牌，**只作废被用掉的那一枚** |

**为什么拆开。** 合成一步时，任何错误都会让提示与自动聚焦落在第一个输入框上——用户看到"恢复码"被标红就会怀疑自己恢复码抄错了，而实际可能是下面新密钥的格式问题。拆开后每个屏幕只有一个待完成的动作，提示必然指向真正出错的那一项。

**令牌的性质。** 它解决的是"如何证明恢复码已经验证通过"这个问题：

- 直接用恢复码原文不行——后端只保存 Argon2id 哈希，每次哈希都不同，无法逐字节比对；把原文留在前端又等于多存一份。
- 因此令牌只记下**命中了第几枚恢复码**（`AuthState` 内的 `RecoveryGrant { matched_index, expires_at }`），**不保存恢复码本身，也不保存它的摘要**；
- 单次使用，消费即删除，无法重放；
- 10 分钟过期（`RECOVERY_GRANT_TTL_SECS`），足够完成"输入新密钥"这一步；
- 重置成功后作废全部待用令牌；
- 签发新令牌时顺手清理过期条目，避免长期运行后无限增长。

这**不构成额外攻击面**：拿到令牌需要先通过恢复码核验，而核验成功后本来就能直接重置密钥。

### 6A.4 没有可用恢复码的情况

| 情形 | 表现 |
| --- | --- |
| 从未生成过，或已全部用尽 | `recoveryHash` 为空。命令返回明确错误，且前端**不显示**「忘记访问密钥」入口——避免把用户引向一条走不通的路 |
| 从旧版本升级 | 旧的单枚长码格式无法迁移到新结构，见下 |

**升级路径。** 恢复码字段从 `Option<String>` 变成 `Vec<String>`，旧值无法解析。这里刻意**不让整个 `auth.json` 解析失败**——那会连访问密钥一起丢失，用户会被要求重新设置密钥，等同于数据灾难。`config::load_from_with_reason` 的做法是：先尝试"只移除恢复码字段"后重新解析，成功则只清除恢复码、保留密钥/设备/日志，并立刻回写文件。

因此升级后用户只需在已解锁状态下重新生成一套恢复码，其余状态完好。

此时唯一的出路（若确实没有任何恢复码）是删除 `auth.json` 重新初始化，代价是同时丢失设备白名单与登录记录。

## 7. 审计

### 7.1 登录记录

记录每次登录的时间、设备与结果。上限 100 条，超出后移除最旧记录。可通过 `clear_login_logs` 清空。

### 7.2 已知设备

记录使用过的设备，上限 32 台。每条记录包含设备 ID、可读标签与最后使用时间。

移除某台设备时，其对应会话会被一并注销。这保证「移除设备」的效果不只是从列表消失，而是该设备上的登录确实失效。

## 8. 威胁模型

### 8.1 已防护的威胁

| 威胁 | 防护 |
| --- | --- |
| 配置文件被读取 | 密钥以 Argon2id 哈希存储，无法还原明文 |
| 暴力猜测密钥 | 失败计数与请求限流 |
| 凭据被复制到其他设备 | 加密密钥由硬件指纹派生，换机即失效 |
| 凭据内容被篡改 | GCM 认证标签与摘要比对 |
| 配置损坏导致放行 | 回落到「需要授权且未初始化」 |
| 通过响应时间推断哈希 | 常量时间比较 |
| 内存中的密钥残留 | 使用 `zeroize` 主动擦除 |
| 用户遗忘访问密钥 | 恢复码（单枚 100 bit，一次性，仅存哈希），见 6A 节 |

### 8.2 残余风险

以下风险在当前架构下**无法通过认证模块本身消除**，需要在设计上接受或另行解决：

| 风险 | 说明 |
| --- | --- |
| 同源脚本可读取令牌 | 插件与宿主共享 WebView，插件代码可访问 `sessionStorage` |
| 令牌存在于 JS 字符串中 | `zeroize` 只能擦除 Rust 侧副本，IPC 传输与 JS 侧字符串无法触及 |
| 无代码签名 | 插件包没有签名校验，无法确认来源 |
| 本机恶意程序 | 攻击者若已能以当前用户身份执行代码，可直接读取应用数据目录 |
| 无 macOS 钥匙串集成 | 凭据保存在应用数据目录，未使用系统凭证存储 |
| 恢复码若与设备同存 | 恢复码的明文由用户自行保管；若用户把它和电脑放在一起（或存在本机未加密的文件里），则恢复能力与设备同时丢失或同时泄露 |

因此认证模块的定位是**防止未授权使用**，而不是抵御本机上已获得执行权限的攻击者。

## 9. 配置与文件

认证配置保存在 `<app_data>/auth.json`，采用原子写入（先写临时文件再重命名），避免中途失败留下损坏文件。

读取时对损坏内容采取失败关闭策略：

| 情况 | 处理 |
| --- | --- |
| 文件不存在 | 视为未初始化，引导用户设置密钥 |
| JSON 解析失败 | 回落到「需要授权且未初始化」 |
| 缺少必要字段 | 同上 |

这是本项目中唯一采取失败关闭的配置读取路径。其余模块（设置、侧边栏偏好）在损坏时回落到默认值，因为它们不涉及访问控制。
