# 后端架构

后端是 Rust 编写的 Tauri 应用，承担模块注册、状态托管、认证与插件管理。本文描述模块抽象、注册表算法、启动时序与命令组织方式。

## 1. 目录结构

```
src-tauri/src/
  main.rs              进程入口，仅调用 modulith_desktop_lib::run()
  lib.rs               应用装配（生成文件）
  prelude.rs           公共导入
  core/
    module.rs          Module trait 与事件枚举
    registry.rs        ModuleRegistry，注册、校验与初始化
  modules/
    mod.rs             模块声明与注册汇总（生成文件）
    auth/              访问授权
    logging/           运行日志与崩溃记录
    notifications/     应用内通知
    plugins/           插件管理
    settings/          应用设置（含网络与下载源）
    sidebar/           侧边栏与模块偏好
    updater/           应用更新（清单与安装包地址按网络设置改写）
```

`lib.rs` 与 `modules/mod.rs` 由 `scripts/generate-backend-module.ts` 生成，头部标注「请勿手动编辑」。任何手工改动都会在下一次 `pnpm gen:backend update` 时被覆盖。

## 2. 核心抽象

### 2.1 Module trait

`core/module.rs` 定义后端模块的统一接口。除 `id` 与 `name` 外，其余方法都有默认实现，因此最小模块只需实现两个方法。

| 方法 | 必需 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `id()` | 是 | - | 模块唯一标识，使用 snake_case |
| `name()` | 是 | - | 面向用户的模块名 |
| `version()` | 否 | `"0.1.0"` | 模块自身版本，与应用版本无关 |
| `description()` | 否 | `""` | 模块描述 |
| `dependencies()` | 否 | 空 | 依赖的其他模块 ID |
| `setup(&app)` | 否 | 无操作 | 初始化，通常在此托管状态 |
| `start(&app)` | 否 | 无操作 | 在 `setup` 之后调用 |
| `stop(&app)` | 否 | 无操作 | 预留的停止钩子，当前框架未调用 |
| `handle_event(event, data)` | 否 | 无操作 | 响应框架广播的事件 |

`ModuleEvent` 定义了四个事件：`Loaded`、`Activated`、`Deactivated`、`ConfigUpdated`。

需要说明当前的使用状况：框架提供了 `dependencies`、`stop`、`handle_event` 与事件广播能力，但现有五个内建模块都只使用默认实现。这些是预留给后续扩展的接口，目前不影响运行。详见[已知问题与技术债](../06-项目/已知问题与技术债.md)。

### 2.2 ModuleRegistry

`core/registry.rs` 实现模块注册表。

```rust
pub struct ModuleRegistry {
    modules: HashMap<String, Box<dyn Module>>,
    init_order: Vec<String>,
}
```

对外方法：

| 方法 | 说明 |
| --- | --- |
| `register(module)` | 注册单个模块，ID 重复时返回 `ModuleAlreadyRegistered` |
| `register_all(modules)` | 逐个注册，任一失败即整体失败 |
| `get(id)` | 按 ID 取得模块引用 |
| `all()` | 取得全部模块引用 |
| `ids()` | 取得全部模块 ID |
| `setup_all(app)` | 校验依赖后按拓扑序调用各模块的 `setup` |
| `broadcast_event(event, data)` | 向所有模块广播事件 |
| `len()` / `is_empty()` | 容量查询 |

错误类型由 `RegistryError` 统一表示：`ModuleNotFound`、`ModuleAlreadyRegistered`、`DependencyNotFound`、`CircularDependency`、`SetupFailed`。

### 2.3 依赖校验与初始化顺序

`setup_all` 分两步：

1. **环检测**。对每个未访问节点执行深度优先搜索，用递归栈判定回边。发现环返回 `CircularDependency`；引用了未注册的模块返回 `DependencyNotFound`。
2. **拓扑排序**。再次深度优先搜索并采用后序收集，得到依赖先于被依赖者的顺序，按此顺序调用 `setup`。

成功初始化的模块 ID 会依次记录到 `init_order`，可用于诊断实际初始化顺序。

需要注意：拓扑排序的输入是 `HashMap` 的键集合，因此在依赖关系未完全确定顺序时，同层模块的相对次序是不确定的。当前模块之间没有声明依赖，实际顺序取决于哈希布局。若将来模块的初始化产生顺序敏感行为，应通过 `dependencies()` 显式声明依赖，而不是依赖插入顺序。

## 3. lib.rs：应用装配

`lib.rs` 的 `run()` 是后端唯一的装配点，流程如下：

```
ModuleRegistry::new()
      |
      v
modules::register_all(&mut registry)      注册所有模块
      |  失败仅打印日志，不中断
      v
tauri::Builder::default()
  .plugin(tauri_plugin_opener::init())
  .plugin(tauri_plugin_dialog::init())
      |
      v
.setup(|app| {                            应用启动回调
      registry.setup_all(&handle)         失败则返回 Err，启动中止
      for module in registry.all() {
          module.start(&handle)           失败仅记日志
      }
      app.manage(registry)                将注册表托管给 Tauri
  })
      |
      v
.invoke_handler(generate_handler![ ... ]) 注册全部命令（生成）
      |
      v
builder.run(generate_context!())
```

设计取向说明：

- 模块**注册**失败不阻断启动。注册表可能不完整，但应用仍可运行，缺失的能力会在调用时表现为命令不存在。
- 模块**初始化**失败会阻断启动。`setup` 承担状态托管，失败意味着模块不可用，此时继续运行会导致后续命令在解构状态时失败，因此选择快速失败。
- 模块**启动**失败不阻断。`start` 用于启动后台任务等可降级的工作。
- 注册表通过 `app.manage` 托管，命令若需要跨模块访问可通过 `State<ModuleRegistry>` 取得。

## 4. 命令组织

所有 Tauri 命令集中在各模块的 `commands.rs` 中，由生成器扫描 `#[tauri::command]` 标注汇总到 `lib.rs` 的 `invoke_handler`。

约定如下：

- 命名使用 snake_case，动词在前，例如 `get_plugin`、`set_plugin_enabled`。
- 返回值统一为 `Result<T, String>`，错误信息是可直接展示给用户的中文描述。无失败可能的命令（如 `get_app_info`）可直接返回结构体。
- 状态通过 `State<'_, XxxState>` 注入；需要跨 `await` 的命令写成 `async fn`，而 notifications 模块的 7 条命令全是同步 `fn`（理由见该模块的说明）。
- 需要文件系统或路径能力的命令接收 `AppHandle` 参数。
- 敏感命令的签名中包含 `token` 参数，由认证模块校验会话。

当前共注册 76 个命令，按模块分布：

| 模块 | 命令数 | 覆盖范围 |
| --- | --- | --- |
| `auth` | 18 | 状态查询、密钥设置与更换、会话、主动锁定、恢复码、设备、日志 |
| `logging` | 5 | 日志目录、读取尾部、清空、前端日志与前端崩溃上报 |
| `notifications` | 7 | 列表、推送、单条与全部已读、移除、清空、未读概览 |
| `plugins` | 26 | 列表、安装、启停、卸载、导出、资源读取、存储、HTTP、启动程序、图标、文件定位、音频导入 |
| `settings` | 6 | 设置读写、应用信息、数据目录、网络诊断 |
| `sidebar` | 12 | 偏好、顺序、可见性、置顶、收藏、最近使用 |
| `updater` | 2 | 按当前网络设置检查更新、下载并安装 |

模块数与命令数都可以直接用生成器问出来，不必依赖本文的数字：

```bash
pnpm gen:backend list
```

完整签名见[后端命令参考](../03-参考/后端命令参考.md)。

## 5. 状态托管

后端状态统一在模块的 `setup` 中通过 `app.manage()` 托管，命令通过 `State` 取出。共享可变状态按访问模式选择同步原语：

| 模式 | 原语 | 适用场景 |
| --- | --- | --- |
| 短临界区、无 `await` | `std::sync::Mutex<T>` | 认证模块、通知模块、侧边栏模块、更新模块（纯内存读写加小文件落盘） |
| 需要跨 `await` 持有 | `tokio::sync::RwLock<T>` | 设置模块、插件模块 |

实际分布（4 用同步锁、2 用异步锁、1 个无状态）：`auth`、`notifications`、`sidebar`、`updater` 使用 `std::sync::Mutex`；`settings`、`plugins` 使用 `tokio::sync::RwLock`；`logging` **不托管任何状态** —— 它的日志器是一个进程级单例（`log` 门面只能装一个后端），因此没法也不该挂在 Tauri 的 state 上，见[日志系统](../02-开发指南/日志系统.md)。

**认证模块与通知模块刻意全部使用 `std::sync::Mutex`**：两者的临界区都只是「改内存数据加落盘」，全程没有 `await`，因此 `MutexGuard`（`!Send`）永远不会跨越 `await` 点。认证模块的命令层遵循「先取数据、释放锁、再 `await`」的写法；通知模块更进一步，7 条命令都是同步 `fn`，在同一线程上跑到结束，两次调用不会交错，也就不存在落盘顺序错乱的可能。这样比用异步锁更简单，也从结构上排除了「持锁等待」的死锁可能。恢复码核验令牌同样存放在 `AuthState` 的内存 `HashMap` 中，理由相同。

在 `tokio::sync::RwLock` 上持有写锁跨越 `await` 是允许的（设置模块正是如此），但应尽量缩短持有时间以避免命令之间互相阻塞。反过来说，若把通知模块的命令改成 `async fn`，同步 `Mutex` 的守卫跨越 `await` 连编译都过不去，届时必须一并换成异步锁。

## 6. 持久化

各模块按职责维护独立的数据文件。

**原子替换的实际覆盖范围是 3/6，不是全部。** 采用「写临时文件后重命名」的有：

| 文件 | 实现位置 |
| --- | --- |
| `settings.json` | `modules/settings/settings.rs` |
| `auth.json` | `modules/auth/config.rs` |
| `notifications.json` | `modules/notifications/store.rs` |

**未采用**原子替换、仍为直接 `fs::write` 的有：`sidebar_config.json`（`modules/sidebar/config.rs`）、插件注册表 `plugins/registry.json` 与插件键值存储（`modules/plugins/manager.rs`）。这三处的取舍是「单次小写入的失败窗口可接受」，但不应被读成「全项目统一原子写」—— 若日后要求所有持久化都具备崩溃安全性，需要把这三处一并改掉。

| 模块 | 文件 | 位置 |
| --- | --- | --- |
| `settings` | `settings.json` | 应用数据目录 |
| `sidebar` | `sidebar_config.json` | 应用数据目录 |
| `auth` | `auth.json` | 应用数据目录 |
| `notifications` | `notifications.json` | 应用数据目录 |
| `plugins` | 目录结构即索引 | `<app_data>/plugins/<id>/<version>/` |
| `plugins`（注册表） | `registry.json` | `<app_data>/plugins/registry.json` |
| `plugins`（插件数据） | 每个键一个文件 | `<app_data>/plugin_data/<id>/<key>.json` |

读取时对损坏内容采取宽容降级：解析失败则回落到默认值。唯一的例外是认证模块，它回落到「需要授权且未初始化」，即失败关闭。

通知文件值得单独说明两点。它没有并入 `settings.json`：通知是**事件记录**（损坏时正确的降级是「没有通知」，而不是凭空生成一条默认通知），写入频率远高于设置（每条通知都落盘），数量级也不同（上限 200 条对几十个字段）。因此 `notifications` 复制了设置模块的原子写入写法，共用的是「怎么写文件」，不共用「文件里是什么」。容量上限为 `MAX_STORED_NOTIFICATIONS = 200`，超出后优先丢弃**已读且最旧**的记录，只有在全部未读时才动最旧的未读记录——已读记录的剩余价值最低，而未读记录一旦被丢就是真实的信息损失。

**认证文件的一个特例。** `auth.json` 中恢复码字段的结构变更（单值 → 数组）如果直接导致整份文件解析失败，会连访问密钥一起回落到默认值——那等同于用户被要求重新设置密钥，属于数据灾难。因此 `config::load_from_with_reason` 会先尝试「只移除恢复码字段」后重新解析，成功则只清除恢复码、保留密钥/设备/日志，并立刻回写。**这是唯一一处「部分字段损坏、部分保留」的读取策略**，其他模块仍是全有或全无。

## 7. 内建模块职责

| 模块 | 职责 | 关键设计 |
| --- | --- | --- |
| `auth` | 访问密钥、会话、设备白名单、登录审计 | Argon2id 派生密钥，AES-256-GCM 保护绑定信息，失败关闭 |
| `notifications` | 应用内通知的推送、未读状态与持久化 | 同键未读合并为一条，上限 200 条优先丢弃已读且最旧的 |
| `plugins` | 插件安装、启停、卸载、导出、资源与存储服务 | 解压时校验路径安全，按 `<id>/<version>` 归档 |
| `settings` | 应用设置与应用信息 | 设置项经 `validate()` 校验后落盘 |
| `sidebar` | 模块顺序、可见性、置顶、收藏、最近使用 | 单一偏好文件承载全部模块元数据 |

认证细节见[认证与安全](../04-安全/认证与安全.md)，插件细节见[插件系统架构](../02-开发指南/插件开发/插件系统架构.md)。

## 8. 遗留目录

仓库中存在两个不会被编译的目录：

- `src-tauri/src/sidebar/`
- `src-tauri/src/module_config/`

`lib.rs` 只声明了 `prelude`、`core`、`modules` 三个模块，因此这两个目录不是编译单元的一部分，其中的代码永远不会被执行。它们与 `modules/sidebar/` 功能重叠，属于重构过程中的残留。

处理建议记录在[已知问题与技术债](../06-项目/已知问题与技术债.md)。在删除前应确认没有外部工具或脚本引用这些路径。
