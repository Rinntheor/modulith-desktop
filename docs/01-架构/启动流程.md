# 启动流程

本文描述应用从进程启动到进入主界面的完整时序。启动逻辑集中在 `src/services/boot.ts`，进度计算隔离在 `src/services/bootProgress.ts`。

## 1. 设计目标

启动界面要回答用户一个问题：**现在进行到哪了，还要多久**。要让这个回答可信，只有一条路：进度必须来自真实完成的工作量。

因此本实现遵守三条约束：

1. 每个步骤都执行真实工作，不存在只为填进度而设的等待。
2. 进度由各步骤上报的完成量按权重折算，不使用定时器模拟推进。
3. 未就绪前进度上限为 99，只有全部完成才到达 100，避免出现「卡在 100% 不动」的观感。

## 2. 门禁结构

应用入口的渲染结构为：

```
main.tsx
  React.StrictMode
    BootGate
      |-- 未就绪：BootChrome + ( AuthScreen | BootScreen )
      `-- 就绪：  Router -> Home
```

`BootGate` 订阅启动状态。只要阶段不是 `ready`，它就渲染启动界面或解锁界面，而不渲染主界面。这样主界面中的组件可以无条件假定初始化已完成，无需各自处理「数据还没准备好」的情况。

`BootChrome` 是启动与解锁阶段专用的窗口标题栏。由于窗口以 `decorations: false` 创建，在自定义标题栏挂载之前窗口无法拖动，因此 `BootChrome` 与主界面的 `Titlebar` 都独立提供拖拽区域与窗口按钮。

## 3. 阶段与步骤状态

启动阶段是一个状态机：

| 阶段 | 含义 |
| --- | --- |
| `idle` | 尚未开始 |
| `running` | 正在执行步骤 |
| `awaiting-auth` | 暂停，等待用户解锁 |
| `ready` | 全部完成，可以进入主界面 |
| `failed` | 关键步骤失败，等待重试 |

单个步骤的状态：

| 状态 | 含义 |
| --- | --- |
| `pending` | 尚未开始 |
| `running` | 正在执行 |
| `done` | 已完成 |
| `skipped` | 被跳过，按整步计入进度 |
| `failed` | 失败 |

## 4. 步骤定义

五个步骤按固定顺序执行，顺序体现了真实的依赖关系。

| 序号 | ID | 名称 | 权重 | 关键 | 主要工作 |
| --- | --- | --- | --- | --- | --- |
| 1 | `preferences` | 读取应用设置 | 10 | 是 | 读取 `settings.json`，确定默认模块与侧边栏折叠状态 |
| 2 | `authorization` | 检查访问授权 | 15 | 是 | 查询授权状态；必要时尝试自动解锁；未解锁则暂停 |
| 3 | `modules` | 初始化模块管理器 | 10 | 是 | 载入模块偏好，完成编目同步 |
| 4 | `plugins` | 加载插件运行时 | 35 | 否 | 刷新版本号、注入宿主 API；默认只同步插件清单，bundle 在进入应用后于后台加载 |
| 5 | `preload` | 预热资源与模块 | 30 | 否 | 预加载图标映射表与首个模块的组件 |

权重合计 100。插件步骤权重最高，因为它涉及磁盘读取与逐个执行插件代码，是耗时最长且可细分的环节。

### 4.1 读取应用设置

调用 `loadAppSettings()` 读取设置。此步骤权重较低但被标记为关键，因为后续的模块选择依赖它的结果。

### 4.2 检查访问授权

这一步是启动流程中最特殊的一环。它的行为取决于授权状态：

```
读取授权状态
      |
      |-- 已设置密钥且已有会话 ---------> 继续
      |
      |-- 已设置密钥、无会话、开启了「记住我」
      |         |
      |         |-- 自动解锁成功 -------> 继续
      |         `-- 自动解锁失败 -------> 记录告警，进入暂停
      |
      `-- 未设置密钥 或 需要解锁 -------> 进入暂停
```

暂停通过 `ctx.waitForUnlock()` 实现，它让整个启动流程停在 `awaiting-auth` 阶段，并把界面交给 `AuthScreen`。用户完成解锁后，流程从断点继续，**不会重新加载页面**。

不采用 `window.location.reload()` 的原因有两点：整页重载会让已经完成的前述步骤白做，并且会丢失启动过程中已经累积的进度与告警。

### 4.3 初始化模块管理器

调用 `moduleManager.initialize()`，从后端读取模块偏好并完成首次编目同步。该步骤上报可用模块数量。

### 4.4 加载插件运行时

这一步的行为取决于设置项 `deferPluginLoading`（默认开启），两条路径的耗时差别很大。

**开启「延迟加载插件」（默认）**：只调用 `reloadPluginRuntime(undefined, { listOnly: true })`，同步到「拿到插件清单」为止——构建插件编目、注入 `window.Modulith`，但**不执行任何插件 bundle**。清单到手后立刻 `void loadPluginsInBackground()`，**不 await**，启动流程继续往下走；每个插件加载完成时通过 `moduleCatalog` 的通知实时出现在侧边栏。

因此在这一路径下，本步骤上报的进度是「已拿到清单」而非「已加载完插件」，`detail` 会显示「N 个插件将在进入应用后于后台加载」。插件全部加载完成时启动界面通常已经消失——这是刻意的取舍：插件是可选扩展，让用户对着进度条等第三方代码执行完没有意义。

**关闭该设置**：走完整路径，`await reloadPluginRuntime(回调)`，逐个加载已启用插件，每加载完一个上报一次进度，`detail` 携带当前插件名，启动界面因此可以显示「正在加载 xxx」。此时步骤耗时会随插件数量线性增长，`pluginLoadTimeoutMs` 决定单个插件的加载超时（默认 5000ms）。

此步骤被标记为非关键。插件是可选扩展，某个插件加载失败不应把用户挡在应用之外。失败时通过 `ctx.warn()` 记录，界面在进入主界面后以可关闭的提示条呈现。

插件运行时的加载流程详见[插件系统架构](../02-开发指南/插件开发/插件系统架构.md)。

### 4.5 预热资源与模块

预热的目标只有两项，都是**内建**资源：

| 目标 | 说明 |
| --- | --- |
| 图标映射表 | `import('../generated/iconMap')`，模块图标解析依赖它 |
| 首个模块的组件 | 通过模块描述符上的 `preload()` 预取其代码分块 |

**这里不预热插件资源。** 插件代码是在步骤 4 中以 `<script>` 注入执行的，不存在可按需预取的模块分块；插件的图标与样式由 `read_plugin_asset` 在加载该插件时读取，属于步骤 4 的工作。因此本步骤的进度单位数只有 1 或 2（目标不存在时更少），与其他步骤的细分程度不同。

预热失败不影响功能（真正打开模块时会重新加载），只记录一条告警。

## 5. 进度计算

进度计算位于 `src/services/bootProgress.ts`，是一个不依赖 React、Tauri 或浏览器环境的纯函数。这样隔离的目的是让「进度没有骗人」这一承诺可以被独立验证。

```ts
computeBootProgress(steps, weights, phase): number
```

算法如下：

1. 求权重总和。若总和不为正，返回 100（就绪）或 0。
2. 对每个步骤计算完成比例：
   - 状态为 `done` 或 `skipped` 的步骤，比例记为 1。
   - 其余步骤，比例为 `unitsDone / unitsTotal`，并夹取到 `[0, 1]`。
   - `unitsTotal` 为 0 表示该步骤不可细分，比例记为 0。
3. 进度为各步骤「比例乘权重」之和除以权重总和，再乘以 100。
4. 若阶段为 `ready`，返回 100；否则取整后上限为 99。

该算法保证两件事：进度单调不回退，且在真正就绪之前不会显示 100。

## 6. 启动结果

流程结束后，`BootResult` 被交给主界面。它包含主界面需要的全部启动期事实：

| 字段 | 说明 |
| --- | --- |
| `defaultModule` | 设置中的默认模块 |
| `lastModule` | 上次打开的模块；未开启恢复时为 `null` |
| `initialModule` | 实际要打开的模块，取 `lastModule` 优先 |
| `collapsed` | 侧边栏初始是否折叠 |
| `moduleCount` | 就绪的模块数 |
| `pluginCount` | 成功加载的插件数 |
| `pluginModuleCount` | 插件注册的模块数 |
| `warnings` | 非关键步骤的告警 |
| `elapsedMs` | 整个初始化的耗时 |

`Home` 通过 `getBootResult()` 同步读取该结果。`BootGate` 已保证只有就绪后才渲染 `Home`，因此 `Home` 内部无需处理结果为空的情况（仅保留类型收窄兜底）。

## 7. 失败与重试

关键步骤失败时，阶段转为 `failed`，`BootScreen` 展示失败步骤与错误原因，并提供重试入口。

重试调用 `retry()`，它会整体重跑流程。为此所有步骤都设计为幂等：

| 步骤 | 幂等保障 |
| --- | --- |
| 读取设置 | 纯读取 |
| 检查授权 | `getAuthStatus()` 可重复调用 |
| 模块管理器 | `initialize()` 内有 `initialized` 守卫 |
| 插件运行时 | 重载前先清理动态模块与已注入资源 |
| 预热 | 组件加载有缓存 |

## 8. 并发安全

`start()` 返回缓存后的 Promise。React StrictMode 在开发模式下会执行两次 effect，缓存保证初始化逻辑只运行一次，避免出现重复注册模块或重复加载插件。
