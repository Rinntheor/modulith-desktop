# 前端架构

本文描述渲染层的组织方式：模块编目如何合并两个来源、状态如何在组件间流动、组件如何被解析与渲染。

## 1. 分层

```
src/
  main.tsx                 应用入口，挂载 BootGate
  pages/Home.tsx           主界面外壳，编排标题栏、侧边栏与内容区
  components/              通用与布局组件
  contexts/                React 上下文
  services/                无 UI 的业务逻辑与后端调用
  types/                   类型定义
  utils/                   纯函数工具
  generated/               构建期生成，请勿手工编辑
  modules/                 内建模块的前端实现
  features/                与具体页面绑定的复合功能（启动页、认证页）
  router/                  路由配置
```

依赖方向自下而上：`components` 与 `pages` 依赖 `services` 与 `contexts`，`services` 不依赖任何组件。`modules` 下的模块组件只依赖 `services`、`types`、`utils` 与通用组件。

## 2. 模块编目

模块有两个来源：构建期生成的静态注册表，以及插件在运行期注册的动态模块。二者由 `src/services/moduleCatalog.ts` 统一管理。

### 2.1 静态来源

`src/generated/moduleRegistry.ts` 由构建脚本生成，导出 `getModuleRegistry()`，返回按 `priority` 升序排列的 `ModuleDescriptor[]`。前端不直接引用它，而是通过 `moduleCatalog` 间接读取。

### 2.2 动态来源

插件调用 `Modulith.registerModule()` 时，最终进入 `registerDynamicModule(module, pluginId)`。该函数执行三项校验：

1. 模块必须具有非空字符串 `id`。
2. `id` 不得与内建模块冲突。
3. `id` 不得与已注册的动态模块冲突。

任一校验失败都会拒绝注册并输出错误日志。这条规则保证插件无法通过同名模块劫持内建模块的入口。

每个动态模块都记录其所属 `pluginId`，卸载插件时可以按来源批量撤销。

### 2.3 合并视图

| 函数 | 返回 | 用途 |
| --- | --- | --- |
| `getCatalogModules()` | 内建模块与动态模块合并后的有序数组 | 侧边栏、路由生成 |
| `getCatalogFlatMap()` | `Map<moduleId, ModuleDescriptor>`，包含子模块 | 按 ID 快速解析 |
| `isDynamicModule(id)` | 该模块是否来自插件 | 界面标注来源 |
| `getModuleOwner(id)` | 该动态模块所属的插件 ID | 归属查询 |
| `getDynamicModuleCount()` | 动态模块数量 | 统计与调试 |

### 2.4 变更通知

编目是一个可订阅的数据源。`subscribeCatalog(listener)` 注册回调，注册或注销动态模块时通过 `notifyCatalog()` 广播。

这一机制解决过一个具体缺陷：插件模块注册后界面不刷新。现在的链路是 `registerDynamicModule` 触发通知，`moduleManager` 订阅并转发，`useModuleList` 以同步初值读取，因此首次启动即可看到插件模块。

**`useModuleList` 的同步初值是关键，不是写法偏好。** 该 Hook 的初始 state 用惰性求值直接读取 `moduleManager.getActiveModules()` / `getHiddenModules()`，而不是 `useState([])` 再在 effect 里拉取。原因是后者存在一个竞态窗口：

```
渲染 #1：state = []          （空列表）
   …此处插件完成注册并广播通知…
effect：订阅 moduleManager    （太晚，通知已经过去）
   …列表永远停在 []…
```

表现为「插件装好了但侧边栏看不到，必须去设置里打开插件页才出现」。同步初值消除了「渲染」与「订阅」之间的空窗；此外 effect 内还会先补一次同步再建立订阅，堵住「订阅建立前发生变化」这一侧。两处措施针对的是同一个竞态的两种触发顺序。

## 3. 状态管理

框架不使用全局状态库，状态按归属划分为两类。

### 3.1 前端内存状态

`SidebarContext` 持有界面状态，同时维护一个前进/后退历史栈：

| 成员 | 类型 | 说明 |
| --- | --- | --- |
| `isOpen` | `boolean` | 侧边栏是否在视口内可见 |
| `isCollapsed` | `boolean` | 侧边栏是否折叠为窄条 |
| `activeModule` | `string \| null` | **来自 `tabStore` 的当前激活标签**，这里不再自己持有 |
| `expandedModules` | `Set<string>` | 已展开的子模块分组 |
| `canGoBack` / `canGoForward` | `boolean` | 历史栈边界状态 |
| `setActiveModule` | `(id) => void` | 打开该模块的标签并写入历史 |
| `goBack` / `goForward` | `() => void` | 沿历史栈移动并激活对应标签 |
| `toggleExpandModule` | `(id) => void` | 展开或收起子模块分组 |

历史栈以 `useRef` 保存，同时用 state 镜像边界标志，避免每次移动都重建栈。

**`activeModule` 为什么不再由这里持有。** 加入标签栏之后，同一个模块可能被三条途径激活：侧边栏点击、标签栏点击、命令面板。三处各自维护一份「当前模块」必然漂移，表现为「点了侧边栏但标签高亮没变」这类问题。因此 `tabStore` 成为唯一事实来源，`setActiveModule` 只是往它写。

历史栈与标签顺序是两件事，刻意分开：标签顺序是用户拖出来的排列，历史顺序是他实际去过的地方。混在一起会让「后退」跳到标签栏上的相邻位置，那不是用户期望的语义。走到一个已经被关闭的标签上时（历史里有、标签栏里没有），`openTab` 会把它重新打开 —— 历史记录的是「去过哪里」，而不是「现在开着什么」。

### 3.2 标签状态

`src/services/tabStore.ts` 持有打开的标签与激活项，是「当前显示哪个模块」的唯一来源。

| 成员 | 说明 |
| --- | --- |
| `initializeTabs(initialModule)` | 幂等初始化：从设置恢复标签，恢复不出来时用启动模块兜底 |
| `openTab(id)` | 打开并激活；达到上限时拒绝并提示 |
| `closeTab(id)` | 关闭；关闭激活标签时激活右邻，没有右邻则激活左邻 |
| `closeOtherTabs` / `closeTabsToTheRight` / `closeAllTabs` | 标签栏右键菜单的三个批量操作 |
| `moveTab(from, to)` | 拖拽排序 |
| `activateTabAt(n)` / `activateRelativeTab(offset)` | `Ctrl+1..9` 与 `Ctrl+Tab` 使用 |
| `subscribeTabs(listener)` / `getTabState()` | 订阅与读取 |

三个必须记住的实现约束：

1. **惰性挂载 + 保活**。`mountedTabs` 记录「被激活过」的标签，只有它们会被渲染，且切走后不再卸载。重启恢复十个标签不会一次挂载十个模块。
2. **目录对账不能在插件加载期间进行**。启动时插件模块尚未注册，此时对账会把所有插件标签判定为「不存在」并删除，表现为「重启后插件标签全没了」。`reconcile()` 因此在 `isPluginCatalogLoading()` 为真时直接返回，等 `setPluginCatalogLoading(false)` 触发的那次目录通知再做。
3. **不订阅 `subscribeSettings` 自动接管**。`saveAppSettings` 是乐观更新、会同步通知订阅者，自动接管会形成「自己写 → 自己收到通知 → 再接管」的回路。改为由明确的外部改动点（「恢复默认设置」）显式调用 `resyncTabsFromSettings()`。

### 3.3 后端持久状态

模块的可见性、顺序、置顶、收藏与最近使用记录由后端 `sidebar` 模块持有。前端通过 `moduleManager` 访问，所有变更都是异步 IPC 调用，成功后由后端返回最新状态。

`RuntimeModuleManager` 是单例，提供：

| 方法 | 说明 |
| --- | --- |
| `initialize()` | 从后端载入偏好，完成首次同步 |
| `reloadCatalog()` | 重新读取模块编目 |
| `subscribe(listener)` | 订阅状态变化 |
| `getActiveModules()` | 取得可见且已排序的模块列表 |
| `getHiddenModules()` | 取得被隐藏的模块列表 |
| `hideModule` / `showModule` | 隐藏或恢复模块 |
| `moveModuleToIndex` / `moveModule` | 调整顺序或上下移动一位 |
| `togglePinModule` | 置顶或取消置顶 |
| `toggleFavoriteModule` | 收藏或取消收藏 |
| `recordModuleOpen` | 记录一次打开，用于「最近使用」 |
| `getFavoriteModules` / `getRecentModules` | 取得收藏与最近使用列表 |
| `resetAll()` | 恢复默认偏好 |

该服务内部对输入做校验（模块存在性、索引范围、方向取值），非法输入会被拒绝而不是传给后端。

### 3.4 应用设置

`src/services/appSettings.ts` 封装通用设置：以模块级缓存持有完整的 `AppSettings` 快照，通过 `subscribeSettings()` 通知订阅者。暴露 `getCachedSettings()`（同步读缓存）、`loadAppSettings()`、`saveAppSettings(patch)`、`resetAppSettings()` 与 `getAppDataDir()`。

`saveAppSettings()` 采用**乐观更新 + 失败回滚**：先改内存缓存并通知订阅者（界面立即响应），再调用后端 `update_app_settings`；成功则用后端返回值规范化缓存，失败则恢复改动前的快照并抛出异常。这样做的理由是设置项大多是开关，等待一次 IPC 往返再更新界面会产生可感知的延迟；而回滚保证了写盘失败时界面不会停在一个并未持久化的状态上。注意它**没有防抖**——每次调用都会发起一次 IPC，调用方若要避免高频写入需要自行合并。

它承载的字段为 `defaultModule`、`sidebarCollapsed`、`confirmBeforeUninstall`、`restoreLastModule`、`lastModule`、`theme`、`reduceMotion`、`deferPluginLoading`、`pluginLoadTimeoutMs`、`accent`、`openTabs`、`activeTab`。主题与配色虽然也在这里持久化，但**应用**它们的是 `services/theme.ts` 与 `services/accent.ts`：`ThemeProvider` 订阅设置变化后再调用这两个服务去改 `document`。这样「权威来源」始终是后端 `settings.json`，而 `localStorage` 里的同名字段只作为首帧缓存。

侧边栏底部的外观快捷开关也走这条路径（`saveAppSettings({ theme })`）而不是直接调 `theme.ts`，否则设置页读到的缓存不会更新，会出现「开关改了但设置页还显示旧值」。

`openTabs` / `activeTab` 是标签页的持久化形式，由 `tabStore` 写入（防抖 400ms）。后端只校验数量上限（`MAX_OPEN_TABS = 12`）与 ID 格式，**不校验模块是否存在** —— 模块清单一部分来自构建期生成的内建注册表、一部分来自运行期注册的插件，后端复制一份必然漂移。失效的标签由前端在目录同步时剔除。

`normalize()` 对恢复出来的 `openTabs` 还会做一次**去重**。这不是洁癖：重复的标签 ID 会让 React 的 `key` 冲突，表现为其中一个标签永远无法激活。

## 4. 渲染管线

### 4.1 主界面编排

`Home.tsx` 的职责是编排三层布局与渲染已挂载的标签：

```
Titlebar   fixed top-0      h-10  z-50   全宽（含窗口按钮、全局搜索、通知铃铛）
TabBar     fixed top-10     h-9   z-40   内容区宽度（随侧边栏让位）
main       fixed top-[76px]  —          内容区宽度，内部是各标签的独立滚动区
```

**侧边栏折叠后的「展开」入口在标签栏内部，不是浮在它上面。** 标签栏占据 40~76px，而原先的浮动按钮是 `fixed top-14`（56px，高约 36px，横跨 56~92px）配 `z-50`，既压住标签栏又探进内容区，直接盖住了第一个标签。现在它是标签栏左端的一个固定槽位（仅在折叠态出现），与标签栏同层同高。

不采用「折叠时显示一个常驻窄侧边栏」的替代方案：那会永久占用内容区宽度，所有模块都少一块画布，与模块的全屏/沉浸式体验直接冲突。折叠态下标签栏与内容区都是 `ml-0`，画布是满宽的。

内容区不是「一个滚动容器」，而是「一层视口 + 每个标签一个滚动容器」。`main` 本身 `overflow-hidden` 不滚动，每个已挂载的标签是一个 `absolute inset-0 overflow-y-auto` 的独立滚动区。这是保活的必要条件：只有每个标签自己持有滚动位置，切走再切回才能回到原处。

非激活标签用 `invisible pointer-events-none` 隐藏，**不是** `display:none`。后者会让元素失去盒子，多数浏览器随之丢失 `scrollTop`，那样「滚动位置保留」这个目标就落空了。`visibility: hidden` 同时把内容移出键盘 Tab 顺序，因此不需要额外处理焦点。

**但只隐藏是不够的：动画必须在切走时停住。** `visibility: hidden` 只让元素不参与最终绘制，**并不暂停动画** —— CSS 动画与 framer-motion 的 JS 动画都会继续推进，中间帧可能被合成器画到屏幕上。实际表现是「从仪表盘切走后，还有几张卡片停留一小会儿才消失」：仪表盘统计卡片的入场延迟是 `0.15 + i*0.06` 秒，index 2/3/4 分别延迟 0.27/0.33/0.39 秒，切走时它们刚播到前几帧，用户看到停留的正是延迟最长的那三张。

所以非激活标签要额外做三件事（`.lc-tab-panel[data-active='false']`）：

| 措施 | 位置 | 作用 |
| --- | --- | --- |
| `animation-play-state: paused` | `index.css` | 暂停 CSS 动画，停在当前帧而非跳到终态（后者会在切回来时看到跳变） |
| `initial={false}` | `Home.tsx` → `ModuleRenderer` | 让包裹层跳过初始态、直接以终态渲染，非激活标签里不存在「进行中的入场动画」 |
| `opacity: 1 !important` / `transform: none !important` | `index.css` | 最后一道收口：framer-motion 写的是**行内样式**，行内样式压不过带 `!important` 的样式表规则，因此这能把非激活子树钉死在终态 |

**一个与直觉相反的实测结论：`MotionConfig reducedMotion="always"` 解决不了这个问题。** framer-motion 12 的 `motion-dom` 源码里是 `shouldReduceMotion && positionalKeys.has(key) ? { type: false } : transition`，而 `positionalKeys` 只含 width/height/top/left/right/bottom 与 transform 系列 —— **`opacity` 不在其中**。卡片残留的可见表现恰恰是 opacity 淡入，所以只靠 reducedMotion 会留下这个 bug。该机制目前仅用于「关闭界面动画」这一设置项（它能正确关掉位移类动画）。

初始化时机上有一处刻意安排：`initializeTabs()` 在 `Home` 的**渲染期间**同步调用，而不是放进 `HomeContent` 的 effect。放进 effect 会让第一帧读到空的 `openTabs`，界面先闪一下「没有打开的标签页」再跳到真正的模块。`initializeTabs` 是幂等的（有 `initialized` 守卫），因此 StrictMode 的双次渲染不会重置用户已打开的标签。

`Home` 自身不承担初始化，真正的启动流程全部位于 `src/services/boot.ts`，详见[启动流程](启动流程.md)。`HomeContent` 里的 effect 只做三件事：载入通知、注册宿主命令、安装快捷键。

**标签保活与刷新按钮的关系**：刷新是显式动作，语义就是「把一切都重来」，因此 `refreshToken` 会进入每个标签的 `key`，让**所有**标签一起重挂载（包括非激活的那些）。这确实会丢掉它们的界面状态，但那正是用户点刷新时想要的。

### 4.2 模块渲染

`ModuleRenderer` 接收 `moduleId`，按以下顺序解析：

1. 查询 `ComponentCacheManager` 是否已缓存该模块的组件引用。
2. 未命中则从 `getCatalogFlatMap()` 取描述符并写入缓存。
3. 描述符不存在时渲染 `ModuleNotFound`，并列出当前可用模块 ID 以便排查。
4. 命中则渲染组件，外层包裹 `Suspense` 以承接懒加载。

`ComponentCacheManager` 是一个按 `moduleId` 索引的 `Map`，提供 `get` / `set` / `delete` / `clearAll`。对外只暴露 `clearModuleComponentCache()`，供刷新流程在重载插件后丢弃陈旧引用。

### 4.3 懒加载

`src/utils/lazyLoad.ts` 提供 `createLazyComponent()`，包装 `React.lazy` 并在加载失败时输出错误日志。生成器为每个模块产出 `createLazyComponent(() => import('...'))` 形式的引用，因此模块代码按需加载。

### 4.4 刷新语义

标题栏的刷新按钮执行三步：重载插件运行时、重载模块编目、清空组件缓存，最后通过递增 `key` 强制重挂载。这使得插件在磁盘上的变更无需重启应用即可生效。因为 `refreshToken` 进入每个标签的 `key`，这一步会让**所有**标签一起重挂载 —— 包括非激活的那些。

## 5. 通知、搜索与事件

这三个能力都在「外壳层」，不与任何具体业务模块耦合。它们共同支撑同一个目标：让信息与入口主动到达用户，而不是让用户去各个模块里找。

### 5.1 通知

| 文件 | 职责 |
| --- | --- |
| `services/notifications.ts` | 后端通知的缓存与订阅；`pushNotification` / `markNotificationRead` / `dismissNotification` / `clearNotifications` |
| `services/toast.ts` | 不持久化的一次性反馈队列（「已复制」「标签页已达上限」） |
| `components/Notifications/ToastLayer.tsx` | 右下角浮层，悬停暂停、按剩余时间继续 |
| `components/Notifications/NotificationCenter.tsx` | 标题栏铃铛打开的未读中心 |
| `hooks/useUnreadCount.ts` | 按模块订阅未读数，供侧边栏与标签栏徽标使用 |

分成两个系统是刻意的：把「已复制」写进磁盘并在通知中心留一条记录是明显的噪音；而把「插件加载失败」做成 3 秒就消失的提示则会让用户错过它。分工见两个文件头的说明。

浮层与通知中心**不是**两条并行的展示路径 —— 推送一条通知时，它进入通知中心（持久化），同时被放进 toast 队列（浮层）。唯一的例外是 `silent: true` 与「合并键命中已有未读」：前者不弹，后者只增加计数不弹。后者的理由很具体：模块很容易在重试循环里反复产生同一条通知，每次都弹会让浮层盖满屏幕。

未读徽标出现在三处，都按来源模块归属：标题栏铃铛（总数）、侧边栏模块项（该模块及其子模块）、标签页（该模块）。点击通知中心里的一条会标记已读并跳到来源模块；来源模块已被卸载时不提供跳转入口。

### 5.2 全局搜索

| 文件 | 职责 |
| --- | --- |
| `services/commandRegistry.ts` | 命令注册表、匹配打分、宿主内置命令、模块条目派生 |
| `components/Titlebar/GlobalSearch.tsx` | 标题栏正中的输入框与结果面板 |
| `services/searchFocus.ts` | `Ctrl+K` 聚焦搜索框的事件通道 |
| `hooks/useGlobalShortcuts.ts` | 快捷键注册 |

模块类条目**不注册进表**，而是在 `searchCommands` 里从目录派生。理由：模块目录是动态的（插件随时注册/注销），镜像成命令列表就需要一套同步逻辑，而同步逻辑正是本项目反复踩坑的地方（见 `useModuleList` 的注释）。派生是纯函数，永远与目录一致。

匹配打分是纯函数（`scoreMatch`），刻意导出以便独立验证：完全相同 1000 分、前缀 800、包含 500、子序列 200 起。子序列匹配是模糊搜索的核心（输入 `dsh` 命中 `dashboard`），但必须排在精确匹配之后，否则输入完整模块名时会被一堆松散匹配挤下去。

插件命令通过 `Modulith.registerCommand()` 进入同一张表，ID 带 `plugin:<插件ID>:` 前缀，卸载时按前缀批量摘除。

### 5.3 跨模块事件

`services/eventBus.ts` 是进程内的事件总线，同步投递、按来源批量注销、主题名有白名单字符集。它让模块之间可以协作（任务模块的待办出现在仪表盘上），而不必都去读写同一个后端命令。

它带来的是「模块之间可以协作」，**不是**「模块之间互相隔离」—— 总线上没有权限隔离，声明了 `plugin-communicate` 权限的插件可以订阅任意主题。

### 5.4 模块可见性

标签保活意味着切走的模块不会卸载，其定时器与轮询会照常运行。宿主对此外提供**感知**而非强制：

| 文件 | 职责 |
| --- | --- |
| `contexts/ModuleRuntimeContext.tsx` | 向模块提供「我是谁、我在不在前台」 |
| `hooks/useModuleActive.ts` | 组合「标签是否激活」与「窗口是否可见」 |

宿主无法代为暂停模块的后台工作：JS 里拿不到模块创建的 `setTimeout` / `setInterval` 句柄，重写全局定时器会影响包括宿主与 React 在内的所有代码。因此这是一个约定，由模块（与插件）自己在 `useModuleActive()` 为 false 时停掉后台工作。**它没有强制机制**，这一点记录在[已知问题与技术债](../06-项目/已知问题与技术债.md)第 7.7 节。

## 6. 路由现状

`src/router/` 下存在 `Router.tsx`、`dynamicRouter.ts` 与 `contexts/RouteContext.tsx`，但当前应用的导航**不经过 URL 路由**：

- 切换模块时只调用 `tabStore.openTab()`，它更新标签状态并激活；`SidebarContext.activeModule` 读的是 `tabStore.activeTab`。整个过程不修改地址栏。
- 代码库中没有任何 `useNavigate`、`navigate()`、`<Link>`、`useParams` 或 `useLocation` 调用。
- `DynamicRouter.initialize()` 只在模块被导入时执行一次，生成的是启动时刻的静态快照，不含之后由插件注册的模块。

实际生效的路径有四类：`/`（重定向到 `/home`）、`/home`、启动快照里每个内建模块生成的一条动态路由（例如 `dashboard` → `/dashboard`），以及兜底的 404。

注意最后那两类之间的差异：动态路由**确实被注册**（`Router.tsx` 把 `DynamicRouter.getRoutes()` 的结果渲染成真实的 `<Route>`），因此手动访问 `/dashboard` 会落到 `ModuleRenderer` 上。但日常导航不走 URL —— 切模块只调用 `tabStore.openTab()`，地址栏不变。所以「路由存在」与「路由被用作导航机制」是两件事：前者成立，后者不成立。

`dynamicRouter.ts` **不是死代码**：`Router.tsx` 以值导入方式引用它。若按「删掉 dynamicRouter.ts」的建议直接删除，会导致编译失败；它同时被 `types/core.ts` 再导出（`RouteConfig`）。`RouteContext.tsx` 才是完全没有引用方的死代码。

这一状态属于已知技术债，影响与处理建议记录在[已知问题与技术债](../06-项目/已知问题与技术债.md)。在改动导航机制前，请先阅读该章节。

## 8. 样式约定

样式使用 Tailwind CSS 4，通过 `@tailwindcss/vite` 插件接入，没有独立的 `tailwind.config.js`。全局样式位于 `src/styles/global/index.css`，导入顺序为 `tailwindcss` → `dark-theme.css` → `accent.css`，末尾是未分层的 `@media print` 块。顺序不可调换，原因见[设计规范](../05-设计系统/设计规范.md)。

组件里写的品牌色工具类至今仍是 `indigo-*`，但它们不再表示「靛蓝」，而是**主题配色的占位名**：`accent.css` 把这些类名重定向到 `--accent-*` 变量，变量的值由当前选中的配色方案决定。默认配色为 `indigo`，共 10 套可选（见 `src/config/accentTheme.ts`）。因此改主题色不需要动任何组件类名。

强调渐变已不再是设计的一部分：早期版本用 `indigo-500 → violet-600` 的渐变，现在统一为单色强调色（`--accent-500`、`--accent-600`）。具体规范见[设计规范](../05-设计系统/设计规范.md)，配色的实现与扩展方式见[主题与配色](../02-开发指南/主题与配色.md)。
