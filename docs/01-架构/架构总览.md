# 架构总览

本文描述 Modulith 的整体结构、双扩展体系与关键设计决策。具体的实现细节见分册文档。

## 1. 设计意图

Modulith 的出发点是一个判断：**桌面应用的通用外壳是稳定的，而具体功能是高度发散的**。因此框架把两者彻底分离。

框架负责的部分是固定的：

- 窗口与标题栏外壳
- 模块生命周期与注册表
- 模块编目、导航与渲染管线
- 访问认证
- 插件运行时（安装、加载、隔离、卸载）

框架不负责的部分全部下沉为模块或插件：仪表盘、插件管理本身都是模块，而不是硬编码在框架里。框架代码中不存在任何对具体业务模块的引用。

这一划分带来两个直接结论：

1. 删除任意内建模块，框架仍能编译并运行。
2. 插件与内建模块在渲染层走同一条路径，插件模块可以获得与内建模块一致的能力。

## 3. 分层结构

```
+---------------------------------------------------------------+
|                        应用外壳层                              |
|  main.tsx -> BootGate -> Router -> Home                       |
|  BootGate: 启动与解锁门禁    Home: 标题栏 + 侧边栏 + 内容区       |
+---------------------------------------------------------------+
|                        模块编排层                              |
|  tabStore         标签页唯一事实来源：打开 / 激活 / 保活集合       |
|  SidebarContext   导航入口与前进/后退历史                        |
|  moduleManager    可见性、排序、置顶、收藏、最近使用              |
|  moduleCatalog    内建模块与插件模块的统一编目                    |
|  ModuleRenderer   按 moduleId 解析组件并渲染                     |
+---------------------------------------------------------------+
|                        服务层                                  |
|  boot  bootProgress  auth  authStore  appSettings              |
|  theme  accent  pluginRuntime  moduleCatalog                   |
|  moduleManager  tabStore  notifications  toast                 |
|  commandRegistry  eventBus  searchFocus  globalErrorHandlers    |
+---------------------------------------------------------------+
|                        IPC 边界（Tauri invoke）                 |
+---------------------------------------------------------------+
|                        后端模块层                              |
|  lib.rs（生成） -> ModuleRegistry -> 各模块 setup / start        |
|  auth 模块   plugins 模块   settings 模块   sidebar 模块          |
|  notifications 模块                                            |
+---------------------------------------------------------------+
|                        核心抽象层                              |
|  core::Module（trait）   core::ModuleRegistry（注册表与拓扑排序） |
+---------------------------------------------------------------+
```

分层的约束是单向的：上层可以调用下层，下层不得反向依赖。渲染层不直接访问文件系统，所有持久化都经由 IPC 交给后端。

图中的「模块编排层」不是另一套实现：`tabStore`、`moduleManager`、`moduleCatalog` 本身就是 `src/services/` 下的文件，单独列出是因为它们承担模块编排职责；服务层则按 `src/services/` 的实际文件全部列出，共 17 个。

## 4. 双扩展体系

框架支持两种扩展方式，它们在**生效时机**与**隔离强度**上不同。

### 4.1 内建模块

内建模块随应用一起编译，由生成器在构建期登记。它的 manifest 是一份 `module.toml`：

```toml
[module]
id = "notePad"
name = "笔记"
description = "随手记录与检索"
icon = "FileText"
path = "/note-pad"
priority = 20
category = "tools"
component = "NotePad.tsx"
```

构建期由 `scripts/generate-modules.ts` 扫描所有 `module.toml`，产出 `src/generated/moduleRegistry.ts`。前端通过 `moduleCatalog` 读取这份注册表。

内建模块可以同时拥有前端组件与后端模块：前端部分放在 `src/modules/<id>/`，后端部分放在 `src-tauri/src/modules/<id>/`。两者通过模块 `id` 关联，但没有强制的同名要求。

### 4.2 插件

插件在运行期安装，不参与编译。它以 `.lcp`（一个 zip 容器）分发，解包后的目录结构为：

```
<plugin>/
  manifest.json      清单，声明入口、权限、引擎要求
  dist/index.js      IIFE 格式的代码包
  dist/index.css     可选样式
  icon.svg           可选图标
```

安装由后端完成：解压、校验路径安全、校验清单、按 `<id>/<version>` 归档。加载由前端完成：读取 `main` 指向的 JS，以 `<script>` 注入执行，插件在 IIFE 顶层调用 `window.Modulith.registerModule()` 注册模块。

插件与内建模块的差异集中在三点：

| 维度 | 内建模块 | 插件 |
| --- | --- | --- |
| 生效时机 | 构建期 | 运行期，可装可卸 |
| 后端能力 | 可注册 Tauri 命令 | 只能使用宿主已暴露的服务 |
| 隔离 | 与应用同权限 | 只能使用宿主暴露的服务；实际约束来自 `permissions` 中网络相关的声明，清单的 `sandboxLevel` 字段当前不被读取 |
| 分发 | 随应用发布 | `.lcp` 包，支持导出 |

### 4.3 统一的编目

两条路径在 `src/services/moduleCatalog.ts` 汇合。它维护两份数据：来自生成器的静态注册表，以及插件在运行时注册的动态模块。对外暴露的 `getCatalogModules()` 返回二者的合并结果。

因此 `ModuleRenderer`、动态路由与侧边栏都无需区分模块来源。插件模块在界面上的表现与内建模块完全一致。

## 5. 关键设计决策

### 5.1 生成优于手写

框架中有四份文件由脚本生成，文件头部均标注「请勿手动编辑」（两个生成器各产出两份）：

| 生成文件 | 生成器 | 触发时机 |
| --- | --- | --- |
| `src/generated/moduleRegistry.ts` | `scripts/generate-modules.ts` | Vite 启动/构建，或 `pnpm gen:modules` |
| `src/generated/iconMap.ts` | 同上 | 同上 |
| `src-tauri/src/lib.rs` | `scripts/generate-backend-module.ts` | `pnpm dev` / `pnpm build`，或 `pnpm gen:backend update` |
| `src-tauri/src/modules/mod.rs` | 同上 | 同上 |

这样做的理由是消除一类特定缺陷：新增模块时忘记登记。注册表、命令注册与模块声明三者由同一份事实推导，不存在遗漏的可能。

### 5.2 单一事实来源

版本号只在 `version.toml` 中维护一次，由 `scripts/version-manager.ts` 同步到各处配置。运行时需要版本号时，一律通过后端命令 `get_app_info` 获取，而不是在前端保留副本。详见[版本管理](../02-开发指南/版本管理.md)。

### 5.3 认证失败关闭

当认证配置损坏或不可读时，系统退化为「需要解锁」而不是「放行」。这是安全敏感组件的默认取向：不可判定等同于不可信。

### 5.4 启动分级的失败策略

启动流程区分关键步骤与非关键步骤：

- 关键步骤失败会导致启动进入失败态并提供重试，例如读取偏好、模块管理器初始化。
- 非关键步骤失败只记录告警并继续，例如某个插件加载失败。

插件是可选的扩展能力，它的故障不应该把用户挡在应用之外。启动完成后，告警会在主界面以可关闭的提示条呈现。

### 5.5 进度只反映真实工作

启动进度由各步骤上报的真实完成量加权计算，不使用定时器模拟。进度在流程上界封顶，只有全部完成才到达 100%。

## 6. 主要数据流

### 6.1 模块导航

```
用户点击侧边栏 / 标签栏 / 命令面板条目
      |
      v
tabStore.openTab(moduleId) 并激活该标签
      |  同时写入 SidebarContext 的前进/后退历史栈
      v
Home 渲染 mountedTabs 中的全部模块，仅激活标签可见
      |  已挂载过的标签保活，切走不卸载
      v
getCatalogFlatMap() 解析 moduleId 得到描述符
      |
      v
渲染 descriptor.component（懒加载 + Suspense）
```

导航由 React 状态驱动，不经过 URL 路由。这一决策的影响记录在[已知问题与技术债](../06-项目/已知问题与技术债.md)。

### 6.2 插件从安装到可用

```
用户在设置中安装 .lcp
      |
      v
后端 install_plugin_package
  解压 -> 路径安全校验 -> 清单校验 -> 归档到 <plugins_dir>/<id>/<version>/
      |
      v
前端 reloadPluginRuntime()
  刷新版本号 -> 注入 window.Modulith -> 列出已启用插件
      |
      v
逐插件加载 main 指向的 JS
  注入 <script> -> IIFE 执行 -> Modulith.registerModule() -> 进入动态编目
      |
      v
模块出现在侧边栏，可像内建模块一样打开
```

### 6.3 一次 IPC 调用

```
React 组件
      |
      v
src/services/*.ts 中的封装函数
      |
      v
invoke('command_name', { args })
      |
      v
Tauri 分发到 #[tauri::command]
      |
      v
后端模块处理，访问由 app.manage 托管的共享状态
      |
      v
返回 Result<T, String>，前端封装层转为异常或默认值
```

## 7. 三项新能力

模块标签页、全局搜索与应用内通知是在同一轮里加进来的。它们分别补上了此前没有出口的三个问题，共同点是都不改变「框架外壳 + 模块」的划分：三项能力都放在外壳侧，模块不需要为此改写。

### 7.1 模块标签页与保活

在此之前，「当前显示哪个模块」只是一个字符串，切换即卸载：切走再切回，滚动位置、未提交的表单、正在编辑的草稿全部丢失，重建现场的成本比切窗口还高。标签页把模块实例保活下来——标签只有被激活过才挂载，挂载后不再卸载，直到标签被关闭。`tabStore` 是标签状态的唯一事实来源，侧边栏点击、标签栏点击与命令面板三个入口都往它写，因此不会出现「点了侧边栏但标签高亮没变」。保活的代价是后台模块的定时器仍在运行，因此由 `ModuleRuntimeContext` 把「我现在是不是用户看得见的那个」告知模块，由模块自己决定是否暂停轮询；宿主无法强制停止（JS 里拿不到模块创建的 timer 句柄）。同时打开的标签上限为 12，约束的正是这些常驻的模块实例数。

### 7.2 全局搜索与命令面板

功能一多，「我知道有这个功能，但它在哪个模块里」就变成一种新的切换成本，而且是最烦的那种来回点。标题栏正中的搜索框把「打开模块」与「执行动作」放进同一个入口：模块条目按需从目录派生（目录是动态的，镜像成命令列表就需要一套同步逻辑，派生是纯函数），动作条目由 `commandRegistry` 注册。默认快捷键是 Ctrl+K，请求通过 DOM 事件（`searchFocus`）而不是 Context 传递，因为触发方是挂在 window 上的全局监听器，不在 React 树内。

### 7.3 应用内通知

在此之前所有信息流都是「用户去点模块」，后台发生的事情没有通道浮到眼前——插件加载失败只写进开发者工具控制台，用户完全看不到。通知模块把这类信息变成一等数据：落盘、有未读状态、可按来源模块聚合出徽标，并用 `dedupeKey` 把重试循环里反复产生的同一件事合并成一条。它与右下角的浮层提示是两条独立通道：浮层是一次性反馈、不持久化（例如「已复制」），通知是事件记录、重启后仍在。需要如实标注的是，当前只做**应用内**通知：系统级通知要新增 `tauri-plugin-notification` 依赖，本轮刻意不引入，因此应用关闭时收不到提醒。

## 8. 状态归属

明确状态归属可以避免多处副本。当前约定如下：

| 状态 | 归属 | 持久化位置 |
| --- | --- | --- |
| 打开的标签页与当前激活标签 | `tabStore`（前端内存） | 防抖后写入 `settings.json` 的 `openTabs` / `activeTab`，并同步 `lastModule` 供「恢复上次模块」使用 |
| 导航前进/后退历史 | `SidebarContext`（前端内存） | 不持久化 |
| 侧边栏折叠状态 | `SidebarContext` | `settings.json` |
| 模块顺序、隐藏、置顶、收藏、最近 | 后端 `sidebar` 模块 | `<app_data>/sidebar_config.json` |
| 应用设置（含深浅模式、主题配色、动效开关、插件加载策略） | 后端 `settings` 模块 | `<app_data>/settings.json` |
| 认证配置与会话 | 后端 `auth` 模块 | `<app_data>/auth.json`，会话在内存 |
| 应用内通知与未读状态 | 后端 `notifications` 模块 | `<app_data>/notifications.json` |
| 已安装插件 | 后端 `plugins` 模块 | `<plugins_dir>/` 目录结构即索引 |
| 插件数据 | 后端 `plugins` 模块 | 按插件 ID 隔离的存储区 |

**注意 `<app_data>/sidebar_preferences.json`。** 用户数据目录里可能存在这个文件，但**当前代码不读写它** —— 它来自更早的版本（由 `src-tauri/src/module_config/` 写入，而该目录已不属于编译单元，见[已知问题与技术债](../06-项目/已知问题与技术债.md)第 2.1 节）。属于升级遗留，可以安全删除；删除不影响任何功能。

外观相关的状态值得单独说明：深浅模式与配色的**权威来源都是 `settings.json`**，而 `localStorage`（`modulith.theme` / `modulith.accent`）只是**首帧缓存**。这么分是因为 WebView 在 JS bundle 求值前就会绘制一次，等后端返回再决定外观会看到明显闪烁。缓存丢失只会让首帧闪一下，不会丢设置。
