## 0. 一句话结论

**v1.5 把「谁在调用」写成了已知缺陷；这一阶段要做的是让宿主终于能回答这个问题。**

手段只有一个：**让每个插件的界面代码跑在一个与宿主不同源的文档里**，并把宿主
自己的命令从那条 IPC 通道上**关掉**。数据层、中大型插件的开发体验，都建立在这条
边界之上 —— 因为在边界建立之前，"插件能存多少、能算什么"这类问题都没有可靠的执行者。

**落地时换了载体：用跨源 iframe，不用原生子 WebView。** 下面（以及 §2.1 的表）
原本写的是"候选主干 = 每插件一个子 WebView"，§2.3 还专门论证了"iframe 出局"。
**那个结论被推翻了**，理由与源码位置写在 §2.3 的引用块里。改动的直接原因是一条
无法在应用层解决的引擎行为：原生子 WebView 被合成在父窗口**之上**，宿主自己每一块
浮层都会被它盖住；而 iframe 的隔离并不更弱 —— 它有三重，且第一重就断了 IPC。

**性能是唯一一条不依赖沙箱、可以立刻单独交付的线**：入口 chunk 767 KB 全阻塞首帧，
根因是静态导入图，改配置就能拆（§6.2）。**这一条至今没做** —— 见 §7 第 2、3 步。

### 2.2 硬边界靠什么：Tauri 自己的 ACL，不是我们手写的门面

这一条是整份方案的支点，**已经在本地依赖里核实过，不是推断**：

1. Tauri 官方文档（[Capabilities](https://v2.tauri.app/zh-cn/security/capabilities/)）写明：
   > By default, all commands that you registered in your app (using `invoke_handler`)
   > are allowed to be used by all the windows and webviews of the app.
   > To change that, consider using `AppManifest::commands`.

2. 本仓库锁定的 `tauri-build 2.6.3` 里，这个 API 真实存在：
   `tauri-build-2.6.3/src/acl.rs:100` `AppManifest::commands(&'static [&'static str])`，
   文档注释是"autogenerate permissions for each of the app commands, in the format of
   `allow-$command` and `deny-$command`"。

3. 同一个文件 `acl.rs:400-440` 的 `build()` 会把应用自己的权限以 `__app__` 命名空间
   放进 ACL，并调用 `generate_allowed_commands` —— 也就是**按 capability 逐条算出
   "这个窗口/WebView 允许调哪些命令"**。

4. **IPC 入口那一侧的条件也核对了**（`tauri-2.11.5/src/webview/mod.rs:1742-1852`
   的 `on_message()`）。放行一条 invoke 需要同时满足：invoke key 正确、以及
   `invoke.acl` 里有对应条目 —— 而只要应用声明过 app ACL manifest
   （`has_app_acl_manifest`），**每一条应用命令都必须有 ACL 条目才可能通过**：

   ```
   if (plugin_command.is_some() || has_app_acl_manifest || !is_local)
      && … && invoke.acl.is_none()
   { … reject("Command … not allowed by ACL") }
   ```

   也就是说：`AppManifest::commands` 一旦填上，**"默认放行"就变成"默认拒绝"**，
   而 `invoke.acl` 是按 WebView 标签解析的。

于是硬边界的形态是：

```
主 WebView ("main")            → capability 里列出全部 120 条 allow-*
插件 WebView ("plugin:kanban") → **不匹配任何 capability** → 一条 IPC 权限都没有
```

**这是 Rust 侧、在 IPC 入口处执行的拒绝**，不是 JS 里包一层 `fetch`。
插件即使拿到 `window.__TAURI_INTERNALS__` 也没有可调的动词 —— 这正是与
`netGuard.ts`（§7.35 已自认"不是安全边界"）的本质区别。

> **状态：这一层已落地（第 1 步）。** `build.rs` 已声明 120 条命令的 app ACL 清单，
> capability 已全部改用 `webviews` 作用域，`pnpm check:acl` 盯住三处列表一致，
> 并断言**没有任何 capability 把插件 webview 纳入作用域**。
> 但**插件今天仍在 `main` 这个 webview 里**，那上面挂着全部 120 条授权 ——
> 所以这一步对插件的处境**没有影响**，它是第 9 步的前置，不是成果。
> 详见[应用命令的访问控制](../04-安全/应用命令的访问控制.md)。

通信方式：**自定义协议，不是事件通道。**

初稿打算用 Tauri 的 `emit` / `listen`。研究中途换掉了，因为
`UriSchemeContext::webview_label()` 能做一件事件通道做不到的事：

| | 事件通道 | 自定义协议（采用） |
| --- | --- | --- |
| 插件 webview 需要的 IPC 权限 | `core:event:allow-emit` / `allow-listen` | **一条都不需要** |
| 插件能监听与伪造的事件名 | 任意，包括宿主内部的 | 不存在事件面 |
| 身份来源 | 消息里插件自报的 id | **webview 标签，由引擎给出** |

于是 `ctx.storage` / `ctx.http` / `ctx.logger` … 变成
"`fetch(modulith-plugin://…/rpc/<方法>)` → 宿主从 **webview 标签**解析出插件 id
→ 校验路径与标签一致 → 宿主执行 → 返回"。
**"谁在调用"由此第一次有了可靠答案**，而且答案不来自插件。
协议处理器按 webview 注册（`tauri-runtime-wry/src/lib.rs:5177`），子 webview 同样适用。

**CSP 把网络变成真的边界**：插件文档由宿主生成并附上
`connect-src <插件自己的来源>`，于是插件无法直接 `fetch` 外网 ——
联网只能走宿主的通道。宿主界面今天做不到这一点（`netGuard.ts` 自认不是边界）。

> ⚠️ **但 CSP 不是承重的那一道。** 实测发现 Tauri 的 IPC 有两条传输
> （`tauri/scripts/ipc-protocol.js`）：`fetch('http://ipc.localhost/<命令>')` 受
> `connect-src` 管辖，而它在失败后会**回退到 `window.ipc.postMessage`** ——
> 那是一条原生桥，不受 CSP 管辖。因此**真正挡住插件调宿主命令的是 ACL**，
> CSP 只是额外一层（它挡住了 fetch 那条路，也挡住了插件自己的出站网络）。
>
> 这条区别的后果很具体：**删掉 `build.rs` 里的 `AppManifest::commands`，插件会
> 重新拿到全部 120 条命令**，而构建、类型检查与其余门禁都不会变红 ——
> 所以 `check:acl` 对这件事单独有一条会真的失败的断言。

### 2.3 ~~为什么不用跨源 iframe~~ → **为什么最终用了它**（原标题：已在源码层面否掉，不是存疑）

> ⚠️ **这一节的小标题与下面三段是 1.6.0 之前的判断，已经被推翻。** 保留原文是为了
> 记住错在哪，而**下面那个引用块才是结论**。直接读这三段会得出与代码相反的答案。

原先的备选是"跨源 iframe"：它便宜、是纯 DOM、布局与浮层天然可用。
**它不成立，理由是源码级的，三条互相独立：**

1. **Tauri 的 IPC 引导脚本会被注入进每一个子框架。**
   Tauri 把 `__TAURI_INTERNALS__` 的引导脚本包成 `main_frame_script(...)`
   （`tauri-2.11.5/src/manager/webview.rs:159-200`），但 Windows 后端
   **完全忽略 `for_main_frame_only`** —— 所有脚本一律走
   `AddScriptToExecuteOnDocumentCreated`（`wry-0.55.1/src/webview2/mod.rs:492-495`）。
   `wry` 自己把这件事写在文档里（`wry-0.55.1/src/lib.rs:990`）：
   > **Windows:** scripts are always added to subframes regardless of the
   > `for_main_frame_only` option.

   微软侧同样明确：注入脚本适用于"所有后续的顶层文档**与子框架**导航"。

2. **Tauri 把自定义协议来源当作"本机"，不是"远端"。**
   `tauri-2.11.5/src/webview/mod.rs:1698-1739` 的 `is_local_url()`：Windows 上，
   只要 scheme 是应用协议、且域名去掉 `.localhost` 后落在注册过的
   `uri_scheme_protocols` 里，就算 `Origin::Local`。因此一个跑在我们自己协议上的
   插件 iframe，**拿到的是与宿主界面完全相同的授权** —— 一点没少。
   真正会被降级成 `Origin::Remote` 的，是 Tauri **不认识**的来源
   （例如真实的 `http://127.0.0.1:<port>` 本地服务）。

3. **capability 按窗口/WebView 标签授权，iframe 与宿主同属 `main`。**
   所以 §2.2 那条硬边界对 iframe **根本无法表达** —— 粒度就不对。

一个附带的、意外但真实的障碍：`sandbox` 属性去掉 `allow-same-origin` 的 iframe
发出的 `Origin` 是 `null`，而 Tauri 解析 invoke 请求时会 `Url::parse("null")` 失败并
直接拒绝（`src/ipc/protocol.rs:488-496`）。这在 fetch-IPC 这条路上确实挡住了，
但它是**巧合**，不是设计，不构成可依赖的隔离；
postMessage 那条回退路径不走 `Origin` 头，是否同样被挡住**未验证**。

**唯一一个 iframe 形态的真边界**（记录下来，不作为主干）：把插件内容从
**真实的 `http://127.0.0.1:<port>` 本地服务**提供 —— 那个 origin 在
`is_local_url()` 里算 `Origin::Remote`，于是 Tauri 会**拒绝一切没有显式
remote capability 的命令**。代价是：我们要自己起一个 HTTP 服务、自己做 CORS、
自己管端口与生命周期，而这是 Tauri **既不文档化也不作为特性支持**的路子。
它换来的是 iframe 的布局与浮层便利，但把"安全"建立在"一个未文档化的分类函数之上"。

**结论：iframe 出局。** 想要真边界，就必须是宿主能按标签区分的**独立 WebView** ——
§2.2 那条路是官方文档 + 本地源码双重核实过的。
**（↑ 这句话是错的。真正的结论见下面这个引用块。）**

### 2.5 顺带解决的两件事

1. **§4.4「插件顶层同步死循环无法中断」** —— 有了独立 WebView，宿主可以 `close()`
   掉那个 WebView 再重建。v1.5 文档写着"只有 v2.0 的独立进程能解决"，
   这里是它第一次真的被解决。
2. **重计算不再卡住界面** —— 插件在另一个渲染进程里，宿主 UI 的帧率不再被它拖累。

### 2.6 也评估过、并明确不采用的两条

> **第一段已经被现实部分推翻：** Node 后台宿主**确实被用作无界面插件的执行位置**了
> （`contributes.background.entry` → 一个 Node 子进程），而它**没有**被当作沙箱来
> 承诺 —— 这个分寸是原文的结论，保留。变更的是"本阶段不使用"那半句。

**Node 的 `--permission`（拿后台宿主当沙箱）—— 不作为沙箱承诺，但作为执行位置用了。**

| 事实 | 后果 |
| --- | --- |
| **网络那一项是版本相关的。** `--help` 实测：本机 Node **24.15.0** 的权限能力只有 `--allow-addons` / `--allow-child-process` / `--allow-fs-read` / `--allow-fs-write` / `--allow-inspector` / `--allow-wasi` / `--allow-worker`，**没有 `--allow-net`**；而官方文档（v26）明确写着"To allow network access, use `--allow-net`" | Node 24：不授予也没用，那个 scope 不存在，网络**完全不受管**。Node ≥25：`--permission` 默认拒绝一切，而宿主**从不传** `--allow-net` —— 于是那时它是一道真的边界 |
| 本机实测（`staging/probe-node-net.cjs`，Node 24.15.0，`--permission --allow-fs-read=<dir>`）：`dns.lookup('example.com')` **成功**、`net.connect` 得 `ECONNREFUSED`、`fetch` 得 `fetch failed` —— **三项都不是 `ERR_ACCESS_DENIED`** | 结论不是读文档得出的：在 Node 24 上，权限模型**一项网络操作都没拦** |
| **`process.permission.has('net')` 不能用来判版本。** 实测：它对 `'net'` 返回 `false`，对 `'definitely-not-a-scope'` **也返回 `false`**，对 `'fs.read'` 同样返回 `false`（哪怕入口文件本来就允许读） | 它回答的是"整个 scope 被授予了吗"，不是"这个 scope 存在吗"。**因此不能用它做诚实的运行时探测**；可靠且无副作用的判据是 `<node> --help` 里有没有 `--allow-net` |
| 官方自己的定位是"seat belt"，原话："**Malicious code can bypass the permission model**"、"does not provide security guarantees in the presence of malicious code" | 它**不是**针对恶意代码的边界 |
| 已文档化的旁路：已打开的 fd、指向授权路径之外的符号链接、`--env-file` / `--openssl-config` / `setFlagsFromString` 在模型初始化**之前**生效、`process._debugProcess(pid)` 不受任何 scope 约束 | 每一项都需要 OS 级手段（不同用户、seccomp/AppArmor）来补 |
| 权限模型**不继承到 worker thread** | 插件里 `new Worker(...)` 即脱离约束 |

结论（**修订**）：它**可以**作为"无界面插件的执行位置"，因为它给的是一条真实的
**进程边界**（独立 OS 进程、`process.env` 已被清空、文件读被限制在插件目录内）；
但**不能**拿它当"沙箱"承诺，而且 **`network` / `network-external` 这两项在后台
插件那一侧不成立** —— 见 §7.2。

**Tauri 自带 Isolation Pattern —— 不是沙箱，是消息闸门。**

它是真的代码级闸门（`src/ipc/protocol.rs:461-478`：Isolation 模式下每条非空载荷
必须是能被解密的 `RawIsolationPayload`，绕过 hook 直接 `postMessage` 会因解密失败被拒）。
但它**不隔离内存** —— 插件仍与宿主同 realm、仍能读宿主的 React 状态与内存里的凭据。
它防的是"前端代码被投毒"，不是"第三方恶意插件"。**本阶段不采用它作为替代方案**，
但可以将来与独立 WebView **叠加**（各管一层）。

## 3. 执行模式是一等公民

沙箱不可能一夜之间覆盖全部插件。因此**每个插件必须公开它的执行模式**，
并且这个模式必须出现在权限列表旁边 —— 因为它决定那份列表**有没有约束力**。

| 模式 | 含义 | 权限列表的效力 |
| --- | --- | --- |
| `in-process` | 与宿主同 realm（今天全部插件） | **仅"诚实"**，无约束 |
| `sandboxed` | 独立 WebView，宿主命令在 IPC 层被拒 | 有约束 |

界面上的措辞必须是"这个插件**有**隔离"而不是"这个插件**需要**这些权限"。
两块信息分开呈现，不能合成一句话。

这一条是 v1.5 §1 的延伸，不是新立场：**列表要说真话，而"有没有执行者"是这句话的一部分。**

## 4. 数据层

### 4.1 现状的天花板

`ctx.storage` 今天是一键一 JSON 文件，8 MB 总量。这对"应用平台"级插件不是"不够宽裕"，
是**到不了终点**：

| 症状 | 根因 |
| --- | --- |
| 记录一多就写不进去 | 总量 8 MB 硬上限 |
| 列表页要全量读进内存才能筛选 | 没有查询，`all()` 还限 500 键 |
| 一次多键写入中途崩溃会留下不一致状态 | 没有事务 |
| 图片/导出文件只能塞进 JSON | 没有二进制、没有私有文件区 |
| 数据只能在 C 盘 | 数据根目录写死在 `app_data_dir()` |

### 4.2 三层存储，按用途分，不按"大小"分

| 层 | 形态 | 用途 | 上限 |
| --- | --- | --- | --- |
| **`ctx.storage`**（保留，语义不变） | 现有一键一 JSON | 配置、小状态、迁移期兼容 | 维持 8 MB |
| **`ctx.db`**（新增） | **每个插件一个 SQLite 文件** | 结构化数据、查询、事务、中大数据量 | 引擎级硬上限（见下） |
| **`ctx.dataDir`**（新增） | 插件私有目录，可自由读写 | 图片、缓存、导出、附件 | 目录总量上限 |

`ctx.storage` **不改语义**：9 个已发布插件都靠它，改语义等于让它们全部重测。
新的东西走新的门。

### 4.3 SQLite 放在哪一侧

**放在 Rust 侧，用 `rusqlite`（`bundled` 特性）。** 理由：

- 插件侧不能自带原生模块（`native-module` 权限已确认"宿主不提供这项能力"）；
- 走 Node 后台宿主意味着"用数据库的插件都依赖 Node 运行时"，而 85.6 MB 的 Node
  至今没有随包分发（见 `内存基线与架构升级方案.md` §14.8）—— 那是在数据能力上
  绑一个尚未解决的发布问题；
- `bundled` 把 SQLite 编进二进制，无外部依赖，代价是安装包增大若干 MB。

**`ctx.db` 的形态：原始 SQL，但带一道宿主 SQLite authorizer。**

选原始 SQL 而不是"结构化集合 API"，是因为后者永远追不上"应用平台"的需求，
最后一定会被人绕过或者半途废弃。原始 SQL 的代价要用引擎自己的能力堵：

| 风险 | 堵法 |
| --- | --- |
| `ATTACH DATABASE` 把库挂到别处，读出别的插件的库 | authorizer 拒绝 `SQLITE_ATTACH` / `SQLITE_DETACH` |
| 单条语句写爆磁盘 | `PRAGMA max_page_count = N` 是**引擎自己执行**的硬上限，不需要我们在写路径上追着算 |
| 一次调用提交多条语句 | 一次调用只编译一条语句，多余的直接拒绝 |
| 插件想看库文件在哪 | **路径从不跨边界**。插件只拿到句柄式接口，位置由宿主决定，因此"搬家"对插件透明 |

### 4.4 用户自定义数据位置：可以，且这一条要做得比"能改路径"多

用户问的是"我们是不是可以让用户自定义插件数据库的位置"。答案是可以，但**难点不在改路径**，
而在改路径之后的四件事：

| 必须处理 | 不处理会怎样 |
| --- | --- |
| **目录不可用时是状态，不是空库** | 移动硬盘没插 → 插件读到空库 → 用户以为**数据没了**，然后开始重建。这是本方案里最危险的一条：必须让插件**拒绝激活**并显示"数据目录不可用" |
| 迁移要显式、可回滚 | 复制 → 校验 → 切换 → **旧目录先留着**，由用户确认后删。静默移动 = 一次失败就丢全部 |
| 备份要跟着走 | `backup/categories.rs` 的模型是"两个根 + 静态相对路径"，数据根一旦由用户决定，这个模型就不成立了。需要第三种根，或者明确把外置数据排除在备份外并**在界面上说清楚** |
| 目标是网络盘 / 可移动盘时要提示 | SQLite 在网络文件系统上的锁语义不可靠；这一点不能只写在文档里 |

形态（初值，待定）：全局 `plugin_data_root`，加**每插件覆盖**（一个应用平台插件独享一块大盘，
其余留在默认位置）。

### 4.5 一个必须现在就说清的取舍：插件的浏览器存储

独立 WebView 拥有自己的 origin，因此插件**可以**用 `localStorage` / `IndexedDB` ——
我们**没有 API 能禁止它**。三条路：

1. 允许，但明确标注"插件自管存储，**不参与配额、不参与备份、不参与搬家**"；
2. 给每个插件 WebView 指定 `dataDirectory`（`WebviewBuilder::data_directory` 已确认存在，
   `tauri-2.11.5/src/webview/mod.rs:963`），让这块数据落在一个我们知道的目录里，
   至少能进备份与搬家；
3. 让插件 WebView 持有一个**不透明 origin**（`sandbox` 属性去掉 `allow-same-origin`），
   于是浏览器存储是临时且不落盘的 —— 持久化只能走宿主的门。

3 最干净，但它要求用 iframe（`sandbox` 是 iframe 属性，不是 WebView 属性）。
方案 D 下只能在 1 与 2 之间选。**这是一个待你决定的点，见 §11。**

### 4.6 分期已定：先 `ctx.dataDir` + 数据根目录，`ctx.db` 推后

**这一节的结论是与人逐条对出来的，不是估的。**

#### 先回答一个该被问的问题：为什么要 SQLite？

因为它只解决**五个问题里的一个**。逐条对齐：

| 问题 | 真正解决它的是什么 | 和 SQLite 有关吗 |
| --- | --- | --- |
| 大数据、文档放哪 | `ctx.dataDir` | **无关** |
| 数据只能在 C 盘 | 数据根目录可配置 | **无关** |
| 卸载时数据会没 | 已修（保留 + 显式删除，见 §7.47） | **无关** |
| 单值 1 MB / 总量 8 MB 上限 | `ctx.dataDir`；或调整那两个常量 | **无关**（它们是 `ctx.storage` 的策略常量，不是架构限制） |
| **记录一多就无法查询/排序/分页，只能全读进内存** | **只有这一条需要数据库** | ✅ |

也就是说：提供 `ctx.db` 的理由**只有一条**——"可查询的大记录集"。它成立，但当时并没有
任何一个插件在撞那道墙（9 个已发布插件都没有）。

#### 定下来的顺序

1. **`ctx.dataDir` + 数据根目录**（本轮）。这是实际痛点，且**无论做不做数据库都要做**。
2. **`ctx.db` 推后到"有一个插件真的需要它"时。**

推后的成本是零，因为后加 `ctx.db` 是**纯新增**：新 API、不动任何已有语义。
反过来先做数据库，就得在**没有真实用例**的情况下猜配额、事务与备份语义——
而"写引擎"恰恰是这件事里最便宜的部分。

> 已经实测过依赖可用：`rusqlite 0.32.1` + `libsqlite3-sys 0.30.1` 拉取并编译通过，
> **38.69 秒**（`bundled` + `hooks`）。所以"要做"随时能做，这不是不可逆的决定。
> 依赖已撤回，树上不留用不上的原生依赖。

#### 将来要做的插件形态（**这决定了 `ctx.dataDir` 的形态**）

明确会做：**思维导图、笔记、文档**。它们对 `ctx.dataDir` 的要求不是"能存一段文本"：

| 形态 | 它要什么 | 因此 `ctx.dataDir` 必须 |
| --- | --- | --- |
| 思维导图 | 一张图可能是一份大 JSON；多张图 | 支持较大文件，且**不经 JSON 转义** |
| 笔记 | 很多条记录、要搜索/排序/标签 | 目录可枚举、可 stat；**并且为将来接 `ctx.db` 留好位置** |
| 文档 | 真正的大二进制（PDF、图片） | **二进制读写**，且不能靠 base64（+33% 体积、双份内存峰值） |

**一条由此定下的设计决定：文件内容走自定义协议的二进制 body，不走 JSON + base64。**

现协议处理器（`sandbox.rs` 的 `dispatch_rpc`）把 body 一律按 JSON 解析，那只适合控制
消息。文件内容必须走 `POST /<id>/rpc/data.write` 这样的二进制 body（协议处理器收到的
本来就是 `Vec<u8>`，改成直接取字节即可）——**否则每个 MB 都要多付 33% 的网络与一次
额外的字符串拷贝**，而这正好是笔记/文档插件的主路径。

#### 数据根目录的语义（本轮必须做对的那一条）

默认 `%LOCALAPPDATA%`，设置里可改（用户已确认这个默认值，理由：**默认值不该在用户
还不知道自己要不要大数据的时候打断他**）。

**"目录不可用"必须是状态，不是空目录。** 移动硬盘没插、网络盘断开、权限被改时，
插件必须**拒绝激活**并显示"数据目录不可用"；绝不能读到一个空目录让用户以为
**数据没了**然后开始重建。这是整个数据层里最危险的一条 —— 它毁掉的不是一次请求，
而是用户对"东西还在不在"的判断。

## 5. 中大型插件的开发体验

### 5.1 已经解决的

上一阶段做到了：`src/<插件名>/` 多文件 → esbuild 打包 → `plugins/<插件名>/index.js`，
带类型检查、sourcemap、watch、宿主侧自动重载。看板已经从 3084 行单文件迁到 11 个模块。

**但这只解决了一半。** 剩下的一半是：多文件之后，插件的**界面**仍然必须用宿主的 React 实例渲染。

### 5.2 沙箱顺手带来的 DX 提升（这才是"能开发中大型插件"）

独立 WebView 意味着插件**自带运行时**：

- 可以用自己的 React / Vue / Svelte / 原生 DOM，**不必与宿主的 React 同版本**；
- 有自己的路由、自己的状态管理、自己的构建配置；
- 界面崩溃不带走宿主；
- 可以有自己的 `index.html`（或由宿主合成一份标准骨架）。

代价：每个插件的界面包会各自带一份框架（React 约 45 KB gzip）。
对一个**按需加载**的插件是划算的。

### 5.3 因此要新增的插件侧形态：`api: 3`

| | `api: 2`（v1.5，`Modulith.run`） | `api: 3`（本阶段） |
| --- | --- | --- |
| 界面 | `registerModule({ component })` —— 宿主的 React 组件 | 声明一个**界面入口**，宿主把它挂进独立 WebView |
| 与宿主通信 | 直接调用 `ctx.*`（同 realm） | 事件请求 / 响应 |
| 清理 | `disposables` | 页面销毁即清理 |

**关键的分期技巧：`api: 3` 先以 `in-process` 模式落地，再切到 `sandboxed`。**
先让插件把"声明界面入口"这件事做完（这一步不改变任何安全属性，风险低），
再在下一个版本把它们搬进独立 WebView。**插件的迁移与隔离的落地因此可以分两次发布**，
而不是一次到位的硬切换。

旧插件（`api: 1/2`）继续以 `in-process` 运行，**不强制迁移** —— 与 v1.5 的兼容策略一致。

## 6. 性能

### 6.1 实测到的瓶颈（按优先级，数字都是本机量出来的）

> 说明：`dist/` 是 9/23 08:51 的产物，比当前 HEAD 陈旧（10 个源文件更新），
> 但构成与量级可信 —— 文档里 v1.1.8 记录的"入口 chunk ~795 KB"与实测的 767 KB 吻合。

| # | 瓶颈 | 证据 | 与沙箱的关系 |
| --- | --- | --- | --- |
| 1 | **入口 chunk 767 KB，首屏阻塞 1.06 MB** | `dist/index.html` 只有三个引用：`main-*.js` 767.09 KB + `index-*.js` 193.28 KB（被 `modulepreload` 提前）+ `index-*.css` 96.76 KB，合计 **297.1 KB gzip**，首帧前必须全部下载解析执行 | **无关**，可独立修 |
| 2 | **插件 bundle 同步求值在主线程** | `pluginRuntime.ts:2061-2074`：把 bundle 文本塞进内联 `<script>` 再 `appendChild`，那一行同步跑完第三方 IIFE。而 `loadPluginsInBackground` 是在 boot 步骤 4 **内部** fire-and-forget 起的（`boot.ts:227`），会与步骤 5 的 `preload`、`Home` 首次渲染抢同一个线程。超时（默认 5000 ms）**不能抢占同步死循环** | **沙箱天然解决**：插件在自己的 WebView 里求值，宿主主线程不再被它占用 |
| 3 | **1663 个 lucide 图标 chunk** | `dist/assets` 1671 个文件里 1663 个 < 4 KB（合计 0.57 MB），来自 `ModuleIcon.tsx:32` 对 `lucide-react/dynamic` 的 `dynamicIconImports` 静态导入。首屏运行成本≈0，但**文件数放大 4 倍**（安装包解包、杀软扫描） | 无关，可独立修 |
| 4 | WebView2 固有基线 347.4 MB 私有 | 文档 §1.1 实测（v1.3.2） | 本方案会**增加**它，见 §6.2 |
| 5 | 后台宿主空闲回收**没有接线** | `reap_if_idle` 全仓只有定义（`background/mod.rs:520`），**没有任何调用方**，`IDLE_TIMEOUT = 300s` 形同虚设 | 无关 |

### 6.2 入口 chunk 为什么这么大（根因是静态导入图，不是依赖太多）

`vite.config.ts` 的 `build` 里**没有 `manualChunks`**，所以拆分完全由 Rollup 对 `import()`
的默认处理决定。而静态导入图是这样的：

```
main.tsx  ──静态──> ThemeProvider            （→ framer-motion，被 31 个文件引用，全静态）
Router.tsx ─静态──> Home.tsx
Home.tsx   ─静态──> ToastLayer / NotificationCenter / SettingsDialog
SettingsDialog.tsx ─静态──> 全部 9 个设置分页（含 845 行的 PerformanceSettings）
```

结果：**整个设置面板与外框全在入口 chunk 里**，只有 3 个业务模块
（`dashboard` / `plugins` / `pluginMarket`）被 `React.lazy` 拆了出去。
**这是"改配置 + 挪边框"的活，不需要动任何业务逻辑。**

### 6.3 本方案自己新增的开销，必须量

1. **浮层与 WebView 的 hide/show** —— 唯一用户能直接感觉到的新增开销。
   判据：打开命令面板的耗时与"闪一下"是否可接受。
2. **每插件 WebView 的进程数与内存** —— 必须有上限与 LRU，不能随插件数量增长。
   判据见 §10 第 2 条。
3. **110 条命令全部经 ACL** 会给每次 `invoke` 增加一次权限查表。
   当前最热的路径（插件存储、网络）本来就有后端判定，预期影响小，但要确认。

### 6.4 两处需要重新审的既有机制

- **`TrySuspendAsync` 会暂停脚本执行。** 插件各自在自己的渲染进程之后，
  宿主窗口被挂起时它们是否也停、停了以后插件还有没有"活着"的语义 —— 要实测。
- **后台宿主至今没有插件执行能力**（`内存基线与架构升级方案.md` §14.7 刻意留空）。
  本阶段**不顺手补它**，只把"界面插件的隔离"做完。

### 6.5 第 2 条还有一个不依赖沙箱的临时修法

插件 bundle 之所以会和首屏抢线程，是因为 `loadPluginsInBackground()` 是在
**boot 步骤 4 内部**就 fire-and-forget 起来的（`boot.ts:227`）。
把它推迟到首帧之后（`requestIdleCallback` / 一次 `setTimeout(0)` 让出）是一个
**几行就能做、且立刻可量**的改动。它不解决"插件求值在主线程"这个根因 ——
那个只有沙箱能解决 —— 但能让默认路径下的首屏不再被它拖。

### 7.2 还剩什么（**实施之后写的，这一段才是现状**）

1. **性能那三步（第 2、3 步）** —— 与本阶段其余内容无关，随时可做。证据与改法在 §6.1、§6.2。
2. **单插件的真实内存与体验（第 4 步）** —— **只能由人来量**，代理环境建不了窗口。
   判据：单个插件 iframe 的私有内存增量，以及"切标签回来"的主观感受。若增量过大，
   §8 里"用更弱的隔离换更小的开销"才需要重新讨论。
3. ~~**`ctx.*` 的三个成员还没补**~~ —— **已补齐，这一条作废（2026-10-07 核对）**。
   原本的三个洞是 `ctx.manifest`（沙箱侧没有）、`Modulith.capabilities`（沙箱侧用
   `has(权限)` 代替）、`Modulith.run`（`api: 2` 的入口）。现在：
   `bridge_script` 把**已解析好的清单**原样注入（`__PLUGIN_MANIFEST__`，
   `sandbox-bridge.js:2377`）；`capabilities` 改成沙箱**自描述**（枚举自己，见桥接层
   末尾那段说明）；`run` 补上了，`bootstrap.settings` 由入口文档注入。

   判据不是"我记得改了"，而是 `scripts/check-sandbox.ts` 里的两条期望清单——
   `EXPECTED_IN_PROCESS_ONLY` 与 `EXPECTED_HOST_ONLY` **现在都是空数组**，
   而它们**刻意留空**：下一次有人搬走一个成员，`pnpm check:sandbox` 会红。
   "同一个插件两侧都能跑"这句承诺在**成员层面**已经没有洞了（行为层面的差别见第 5 条）。
4. **数据根的用户可配置（第 7 步的另一半）** —— `set_configured_root` 是死代码。
5. **同一份插件两侧的降级语义不一致。** `pluginRuntime.ts` 在缺权限时**降级为空实现**
   （`modulith.d.ts` 写明的契约），而沙箱桥接层对 `storage` / `settings` / `dataDir` /
   `db` / `http` **直接发 RPC**，于是同样的插件在 in-process 安静降级、在沙箱抛
   `权限不足: xxx`。当前 9 个插件都没踩到（都声明了 `storage`），是潜伏的。
6. **`network` / `network-external` 在后台插件那一侧不成立**（§2.6）：宿主只传
   `--permission --allow-fs-read=<dir>`，**从不传** `--allow-net` —— 在 Node ≥25 上
   这是一道真的边界，而在 Node 24 上那个 scope 根本不存在，网络完全不受管。
   可靠的判据是 `<node> --help` 里有没有 `--allow-net`（`process.permission.has('net')`
   **不能**用，实测它对不存在的 scope 也返回 `false`）。

   **这一条现在会被如实报出来，而不是留在文档里**：`BackgroundStatus` /
   `BackgroundPluginStatus.netRestricted` 由「权限模型开着 **且** 那个 scope 存在」
   算出，没探测到时报 `false`（"没被管住"）；拉起子进程时若发现管不住网络会留一条
   警告日志；插件详情页与启动日志**分别**说"已隔离"与"网络不受管"。
   强制层面**没有变**——变的只是它不再被一句绿色的"已隔离"盖住。
7. **无界面（功能性）插件：路径已被真实插件走通，但还没在应用里跑过。**
   形态在（`contributes.background.entry` → 独立 Node 进程），而这个形态此前
   **一次都没有被证实过** —— 9 个插件全是界面插件。

   现在有了第一个：`modulith-plugins` 的 `plugins/stand-up`（久坐提醒，没有界面）。
   `staging/verify-headless-plugin.cjs` 用**与应用同一组旗标**拉起同一个
   `background-host.mjs`，加载它的 `background.js`，投递 `start` / `interval`，
   并如实回答它反问了宿主的那几条 `ctx.*`。跑出来的顺序是：

       ctx.storage.get → ctx.log → ctx.storage.get → ctx.notify → ctx.storage.set → ctx.log

   也就是：插件被加载、`ctx.background.on` 登记的回调真的会跑、它发出的每一条
   `ctx.*` 都到达了宿主。**仍未验证**的是应用那一层：`sync_startup` 真的把它拉起来、
   插件详情页那个"正在运行／网络不受管"显示正确 —— 那需要人跑一次应用。

   顺带查出一处**形状分歧**（未修，见 §7.3）。

### 7.3 后台宿主与界面侧的 `ctx` 方法名不是同一套（未修）

后台宿主给插件的 `ctx` 与界面侧对不上：

| | 后台（`background-host.mjs`） | 界面（桥接层 / in-process） |
| --- | --- | --- |
| 通知 | `notifications.notify({title, body, level, dedupeKey})` | `notifications.show(title, body, dedupeKey)` + `isAvailable()` |
| 事件 | `events.emit(name, payload)` / `events.on(name, handler)` | `events.publish` / `subscribe` + `isAvailable()` |

这与白屏过两次的那个 bug 是**同一类**（`ctx.notifications.isAvailable is not a
function`）。`staging/audit-plugin-methods.cjs` 当初只核对了 9 个界面插件与桥接层，
**没有核对后台宿主**，因此这一处从来没被查过。

为什么没有顺手改：后台插件的代码本来就与界面代码分开（`background.js` 是另一个
文件），它不需要"两侧同一份代码"；而改它要动协议面向插件的部分，值得单独一次带着
完整门禁与变异验证来做。

### 7.1 第 1 步为什么排在最前（而不是"顺手做掉"）

因为它不是一个整洁度改进，而是**判定路径的开关**。Tauri 对应用自己注册的命令默认
不检查权限（`on_message()` 里 `has_app_acl_manifest` 那个分支），因此在这一步之前，
**把插件挪进独立 WebView 也挡不住它调用宿主命令** —— 那条判定根本没开。

它同时补掉当前架构里一个能直接看见的缺口：托盘菜单窗口一条 capability 都没有，
却一直在调用两条应用命令。详见[应用命令的访问控制](../04-安全/应用命令的访问控制.md)。

**它买到的是宿主自身命令的默认拒绝，不是插件的安全。** 插件今天仍在 `main` 这个
webview 里，那上面挂着全部 120 条授权，所以插件什么都没少。这一层改变的是第 9 步
之后的事情。

第 4 步（实测）是第 9 步的硬前置：单插件 WebView 的真实内存增量如果超过约 150 MB，
方案 D 要重做。

## 10. 实施前必须实测的事

**没有一条能靠读文档确定。**

1. **一个子 WebView 的真实成本是多少进程、多少内存？**（第 9 步的硬前置）
   判据：如果单个插件 WebView 的私有内存超过约 150 MB，方案 D 需要重做。
   测法：与 `内存基线与架构升级方案.md` §1.1 同一套差集测量法。
   ⚠️ WebView2 官方进程模型提到"**同一 user data folder** 的多个实例共享渲染进程"，
   因此这个数字**可能比 §1.1 的归因小得多** —— 但如果它没有共享，方案 D 就要重新算。

2. **`hide()` / `show()` 一个覆盖在内容区上的子 WebView，主观上能不能接受？**
   这是本方案唯一直接伤害体验的地方，没有数字能替代"看一眼"。

3. **`tauri/unstable` 打开后 `add_child` 在 Windows/WebView2 上的实际行为**：
   能否在运行期创建/销毁、`set_bounds` 跟手不跟手、`data_directory` 是否照常生效。

4. **应用运行期是否一切照旧。** 第 1 步已经落地（ACL 清单 + capability 收口），
   构建期能验的都验了（capability 由 `tauri-build` 校验、`acl-manifests.json` 里有
   `__app-acl__`、24 个门禁与 398 个 Rust 测试全绿），但运行期要人工走一遍：
   解锁、托盘菜单、设置页、插件安装与存储。

> **验证的形态（重要）。** 应用本身运行正常 —— 曾把它记成"本机有一个先于任何代码的
> 启动阻塞"，那个归因是错的（更正见 `内存基线与架构升级方案.md` §10.5）。
> 真正的限制是**代理的沙箱环境创建不了窗口**（对照：`notepad.exe` 在那里启动后
> `MainWindowHandle` 也是 0），因此 Tauri 会停在建窗口处。
> 于是分工是：**改动由代理写，应用由人启动，结论从日志读。**
> 这意味着一件事 —— 后续每一步都应当做成"人能跑一次、日志能读出结论"的粒度，
> **而不是一次交付一大块无法验证的代码**。

另外两条是"如果将来要用才需要"的（本阶段不用）：
- 跨源 iframe 是否真能拿到 `__TAURI_INTERNALS__`（§2.3 已从源码判定为能，
  但若将来想走"真实回环服务"那条备选，需要验证 `Origin::Remote` 分支与
  postMessage 回退路径的判定）；
- `crypto.subtle` 在不透明 origin 的 iframe 里是否可用
  （规范说不可用，而 Tauri 自己的 Isolation Pattern 似乎依赖它可用 —— 结论矛盾，
  只有实测能定）。
