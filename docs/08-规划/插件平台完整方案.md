# 插件平台完整方案（v2.0 规格）

> 这份文档取代"一次做一小块"的做法。它是一次性把**目标形态、完整 API 表面、
> 隔离模型、数据层、界面形态、生命周期、执行顺序与验收标准**全部定下来。
>
> 定下来的东西不再逐条征求确认；实现按本文档一次推进，中途**不要求人工验证**，
> 全部完成之后交付一个可测的构建。

---

## 0. 一句话结论

**每一个插件都是一个独立的应用：它有自己的 webview、自己的前端框架、自己的数据、
自己的界面；宿主提供它所需的一切能力，并且**只能通过一条受管的通道**提供。**

---

## 1. 目标形态

一个"中大型应用插件"必须能做到的事，这份方案必须全部支持：

| 能力 | 具体表现 |
| --- | --- |
| 自带前端运行时 | 自己的 React / Vue / Svelte / 原生 DOM，**不与宿主同版本** |
| 多界面 | 一个插件可以声明多个可打开的界面（列表、详情、设置、独立的工具窗） |
| 无界面 | 后台服务型插件：定时任务、文件监听、同步。**不为了它建一个渲染进程** |
| 大容量数据 | 键值、文件目录、结构化数据库三层，装得下笔记、文档、图库 |
| 完整系统能力 | 网络、文件、剪贴板、通知、外部程序、事件总线 |
| 崩溃隔离 | 插件界面崩溃不带走宿主，宿主也不因它卡住 |
| 可迁移 | **9 个已发布插件全部能迁进来**，不是只有 hello |

## 2. 隔离模型（已成立，不再改）

```
宿主主 webview（标签、侧边栏、设置…）
  │  全部 135 条宿主命令只授权给这一个 webview
  │
  ├── plugin-<id> 子 webview   ← 每个插件一个，0 条 capability
  │     · IPC 层被拒（拿不到任何宿主命令）
  │     · CSP 由宿主写死（连不出去）
  │     · 与宿主的**全部**通信走自定义协议 modulith-plugin
  │     · 身份来自引擎给的 webview 标签，插件伪造不了
  │
  └── plugin-<id>#<surface>    ← 同一插件的第 2..n 个界面
```

**一条铁律（血的教训，见技术债 §7.44）**：创建 webview 只能发生在
`surface.rs` 的所有者线程上。同步命令里创建 webview 会让整个应用假死。

### 3.2 数据（三层，按用途分）

| 成员 | 方法 | 状态 |
| --- | --- | --- |
| `ctx.storage` | `get` `set` `delete` `keys` `list` `usage` `all` `clear` | ✅ |
| `ctx.dataDir` | `available` `list` `stat` `read` `readText` `write` `writeText` `mkdir` `remove` `used` | 🔧（后端已完成） |
| `ctx.db` | `query` `queryRaw` `exec` `transaction` | ✅ |

`ctx.db`：每插件一个 SQLite 文件，宿主侧 `rusqlite`（`bundled` + `hooks`），文件是
数据目录里的 `plugin.db`（**保留名**：`ctx.dataDir` 不能覆盖或删除它，读可以）。
`ATTACH`/`DETACH` 与六个危险 PRAGMA 的**设值**由 authorizer 拒绝 —— 那是
**引擎级**的，文本过滤挡不住注释、大小写与字符串字面量。`PRAGMA max_page_count`
做引擎级配额（数据目录配额的一半：数据库与文件共用同一个池子，而数据库独占全部

`transaction` 是**一批语句**，没有跨调用的 `begin`/`commit`（那是会泄漏的写事务
状态，而插件那一侧拿不到 `finally`）。

## 4. 无界面（功能性）插件：跑在 Node 后台宿主里

**形态：插件代码跑在 Node 后台宿主进程里。不建渲染进程。**

> **这一节被改过。** 原方案写的是"隐藏的沙箱 webview"。改成 Node 宿主是一个
> **明确的产品决定**（2026-02）：后台插件必须有真正的后台能力，而"隐藏 webview"
> 在这件事上从一开始就是将就 —— 它会被浏览器降级与冻结，而托付给它的恰恰是
> "凌晨三点要准时醒过来"这类事。
>
> 接受的前提也随之明确：**Node 运行时不随包分发，由用户自己安装。**
> 这不是缺陷，是这个选择的代价，因此必须把"没有 Node 时是什么状态"说清楚，
> 而不是让插件半可用。

### 4.1 Node 从哪来

复用既有的一套查找（`background/mod.rs::resolve_node`，五级顺序）：

| 顺序 | 位置 | 谁会用 |
| --- | --- | --- |
| 1 | 设置 → 性能 里手工指定的路径 | 普通用户：选一次就记住 |
| 2 | 环境变量 `MODULITH_NODE` | 开发与排障 |
| 3 | `<应用目录>/runtime/node.exe` | 愿意随包分发的发行版 |
| 4 | 官方安装程序的默认落点 | 绝大多数机器 |
| 5 | 系统 `PATH` | 已经装过 Node 的机器 |

**没有 Node 时**：设置页与插件详情页显示**具体原因**，后台插件标为"需要 Node
运行时"。不静默降级、不假装可用。这与 `ctx.db`、`ctx.http.download` 一样，
属于"宿主明确说清楚它现在做不到什么"。

### 4.2 一个后台插件长什么样

```json
{
  "runtime": "sandboxed",
  "contributes": {
    "background": {
      "entry": "background.js",
      "onStartup": true,
      "interval": 60,
      "events": ["onCommand:sync", "onPluginEvent:notes/changed"]
    }
  }
}
```

后台插件**仍然是一个普通插件**：同一份清单、同一套权限、同一个 `ctx` 形状。
区别只有两处：

* 它有一个 `background.entry`（一个独立的 JS 文件，与 `main` 分开 ——
  后台入口不该被迫加载界面代码）；
* 它拿到的 `ctx` 是**界面 ctx 的子集**，去掉所有 DOM 相关成员。

| 有 | `storage` `dataDir` `db` `http` `settings` `events` `logger` `notifications` `disposables` `launcher` `shell.revealInFolder` |
| 无 | `ui` `theme` `clipboard` `fileDrop` `icons` `audio`（这些要么是 DOM，要么是窗口级） |

### 4.3 进程模型：**一个后台插件一个进程**

不是"一个宿主进程里跑所有后台插件"，而是**每个后台插件各自一个 Node 子进程**。

理由与 webview 沙箱是同一条：**崩溃隔离**。一个后台插件写出死循环或吃掉几百 MB
内存时，它只该弄死自己 —— 而"共享一个进程"意味着任何一个后台插件的失控都会
拖走其余全部后台插件，连带让宿主报出"后台功能不可用"。这与 §6 的驻留淘汰是
同一件事的两个方向：**资源要么被隔离，要么被限制**。

进程的生命周期与 webview 界面一致：

| 状态 | 触发 | 动作 |
| --- | --- | --- |
| 声明 | 安装 | 只读清单，**不执行任何代码** |
| 拉起 | `onStartup` / 定时到点 / 命令 / 事件 | 起子进程，加载 `background.js` |
| 运行 | —— | 常驻（后台插件本来就要一直在），但受引擎级资源上限约束 |
| 回收 | 用户停止 / 空闲超时 / 应用退出 | 先发 `shutdown` 让它收尾，超时再强杀 |

### 4.4 隔离强度：**这一层比 webview 沙箱弱，必须说清楚**

webview 沙箱那一层是**引擎边界**：另一个渲染进程、0 条 capability、身份来自
webview 标签。后台这一层**不是**同一件事，它由三部分组成：

1. **进程边界** —— 崩溃、内存、CPU 不互相影响；
2. **`node:vm` 上下文** —— 插件代码在自己的 global 里，拿不到 `require` /
   `import` / `process`，只有一个冻结的桥接对象；
3. **引擎级的文件系统权限** —— 子进程用 `--permission` 启动，只放开
   **这个插件自己的代码目录与数据目录**。

第 3 条是这里最实在的一层：它不是我们写的检查，是 Node 自己执行的。一个逃出
`vm` 的插件仍然读不到别的插件的数据，也写不到数据根之外 —— 因为它没有那个
文件系统权限。

**它挡不住的**：Node 官方明确说 `vm` 不是安全机制。一个蓄意逃逸、又恰好拿到
了某个宿主对象引用的插件，可以在这个进程内为所欲为。它能动的范围被第 3 条
限制在"这个插件自己的目录"，但**不是一个通用安全边界**。

因此：后台插件仍然受完整权限模型约束，且这些判定都在**宿主侧**做（插件调的是
宿主的方法，不是自己实现的）。需要更强隔离的后台插件应当使用 webview 沙箱，
而不是 Node 宿主 —— 这条写进插件开发文档。

### 4.5 声明式激活（与回收相容）

后台插件**可以**持有定时器（这正是它存在的理由），但清单里的
`background.interval` / `events` 仍然是必要的：宿主据此知道"要不要为它拉起进程"。

没有 `background` 声明的插件**不会**被拉起 —— 一个装了但从不运行的插件不该
占用一个进程。

## 5. 多界面（`api: 3`）

```js
Modulith.ui.openSurface('detail', { width: 480 });   // 宿主决定位置
```

* 每个界面一个 `plugin-<id>#<surface>` 标签，`SandboxSurfaces` 的键从"插件 id"扩成
  "(插件 id, 界面名)"；
* 入口文档按界面名加载不同入口（清单里 `surfaces: [{id, name, entry}]`）；
* 布局仍由前端量、宿主摆 —— 沿用现有 `measureSurface` 一条路径；
* 驻留上限按**界面**计数，不按插件。

### 5.1 落定之后的形状（实现与上面那版草稿的差别）

清单里的界面写在 **`contributes.surfaces`**（与 `contributes.background` 一致），
而不是顶层：

```json
{
  "contributes": {
    "surfaces": [
      { "id": "main",   "name": "笔记", "entry": "dist/index.js",  "style": "dist/index.css" },
      { "id": "detail", "name": "详情", "entry": "dist/detail.js" }
    ],
    "modules": [
      { "id": "notes",         "name": "笔记" },
      { "id": "notes-setting", "name": "笔记设置", "surface": "main" }
    ]
  }
}
```

**三条必须记住的规则：**

1. **`main` 是必需的主界面**，不是"第一个就是主界面"。顺序定义主界面的话，调整
   清单顺序就会改变 webview 标签 —— 而所有关于标签的推理（日志、断言、驻留表）
   都建立在"名字是稳定的"之上。缺 `main` 时整份清单被拒，且错误消息说清缺什么。
2. **主界面拿不带 `#` 的标签**（`plugin-<id>`），次级界面拿带名字的
   （`plugin-<id>#<detail>`）。这是"已发布的单界面插件一字不改"的全部依据 ——
   它们的标签、入口文档、路由与多界面之前逐字节相同。
3. **界面 id 走白名单**（字母数字与 `-` `_`，不以数字/`-`/`_` 开头，长度 ≤32），
   而且**不净化**。插件 id 可以净化（它允许 `.`），界面 id 不行：净化会把 `a.b`
   与 `a-b` 映射到同一条标签，而两个界面互相覆盖的症状是"其中一个打开后显示的是
   另一个的内容"。

**打开一个界面不由宿主建 webview。** 只有前端知道界面该摆在哪（标签栏多高、
侧边栏是否展开、分屏开没开），因此：

```
插件 → ui.openSurface('detail') → 宿主广播 modulith://open-surface
     → 前端开一个标签 → 标签里的占位量出矩形
     → sandbox_surface_open(插件, 界面, 矩形) → 宿主建 webview
```

次级界面在宿主里被登记成一个 **`hidden` 模块**（id 形状 `plugin:<插件>#<界面>`，
与清单模块 id 的字符集不可能撞上）：能按 id 打开、能进标签、能被驻留淘汰，
但不出现在侧边栏 / 仪表盘 / 命令面板里。被 `contributes.modules` 声明过的界面
**不再造**隐藏模块 —— 造了的话同一个界面会有两块 webview，而标签是唯一的。

停用或卸载插件时，宿主**主动关掉它还开着的全部界面**（在命令那一层做，三条
停用路径因此不会漏掉一条）。

## 6. 生命周期与资源

| 状态 | 触发 | 动作 |
| --- | --- | --- |
| 声明 | 安装 | 只读清单，**不执行任何插件代码** |
| 激活 | 打开模块 / 命令 / 事件 / `onStartup` | 建 webview，跑入口 |
| 隐藏 | 切标签、宿主浮层、窗口收起 | `hide()`，**不销毁** |
| 回收 | 超过驻留上限 / 空闲超时 | 销毁最久未用的**隐藏**界面 |
| 卸载 | 用户操作 | 删代码，**保留数据** |

**驻留上限**：默认 `max(2, 内存等级对应值)`。上限数字必须**实测**校准
（方案 §10 的实测项），而不是拍一个。

## 7. 执行顺序（一次性推进，中途不要人工验证）

按**依赖**排，不按"哪个最显眼"排：

1. ~~**沙箱 RPC 全量**~~ **已完成** —— §3 里除 `ctx.http.download` /
   多界面 / 主题 / 快捷键 / 右键菜单之外的全部成员都已接进自定义协议，
   含**原始字节通道**（`GET`/`PUT /<id>/data/<rel>`，不走 base64）。
   同时把 ctx 的**语义**抽成了 `plugins/rpc.rs`：沙箱与 Node 后台两条路径共用它，
   因此"能不能做这件事"只有一处定义（两套实现一定会漂，见技术债 §7.40）。
2. ~~**主题 / 输入 / 浮层**~~ **主体已完成**：
   * **主题** —— 宿主设计令牌（遍历 computed style，而不是维护一张会漂的清单）
     经前端推给宿主，注入插件入口文档 + 推给已打开的界面；带 `color-scheme`；
     减少动效由宿主压掉；推送是换样式表文本，不是重载界面。
   * **快捷键** —— 整张表注入插件文档，桥接层在**冒泡阶段**判断该不该转发
     （插件自己的处理器优先），输入框里的规则由宿主的 `allowInInput` 说了算，
     Rust 复核转发的组合。
   * **浮层** —— 独立的 `overlay` 窗口（不能是 DOM：沙箱插件是原生子 webview，
     盖得住宿主的任何元素）。`ctx.ui.dialog` / `ctx.ui.contextMenu` 走它，
     请求/回答配对 + 5 分钟超时 + 失焦撤销。
   * **未做**：无。
   * **状态指示与命令**（本轮补上）—— `ui.splash` / `ui.badge` / `ui.progress`
     三条都由**宿主渲染**（徽标与进度在侧边栏/标签栏上，插件文档碰不到；
     启动占位要覆盖插件那一块位置，因此先把 webview 收起来再画）。
     启动占位有**自动清除**（桥接层在文档 `load` 之后撤，除非插件已经接管）
     与 **8 秒超时兜底**（文档根本没加载起来时，不能让占位永远挂着）。
     `contributes.contextMenus` 的接线也补上了：`ui.contextMenu` 默认把清单声明的
     条目并进宿主渲染的那个菜单；选中它们时**沙箱插件走"推一条命令进它的界面"**
     （函数引用过不了 realm 边界），in-process 插件走一条广播回到前端。
3. ~~**多界面与 `api: 3`**~~ **已完成** —— 见 §5.1。清单里 `contributes.surfaces`
   声明多个界面；主界面保留不带 `#` 的标签（单界面插件一字不改）；打开界面走
   "广播给前端 → 前端开标签 → 前端量矩形 → 宿主建 webview"；次级界面登记成
   `hidden` 模块；停用/卸载插件时宿主主动关掉它的全部界面。
   `ctx.ui.openSurface` / `closeSurface` / `listSurfaces` 三条都在桥接层与
   `rpc.rs` 里，`check:sandbox` 第 15 节有 40 条断言（全部做过变异验证）。
4. ~~**无界面插件**~~ **已完成** —— 见 §4。一个后台插件一个 Node 子进程，
   协议升到 2 支持子进程**反向**发起 `ctx.*` 调用，`--permission` 提供引擎级
   隔离，`env_clear` 补上 `process.env` 那个洞。
   端到端验证在 `background::live_tests::a_background_plugin_can_call_back_into_the_host`。
5. ~~**`ctx.db`**~~ **已完成** —— 见 §3.2 与 `db.rs`。每插件一个 SQLite
   （`rusqlite`，`bundled` + `hooks`），文件是数据目录里的 `plugin.db`。
   边界全部由**引擎**执行：`ATTACH`/`DETACH`、六个危险 PRAGMA 的设值、
   `load_extension` 由 authorizer 拒绝；`PRAGMA max_page_count` 做引擎级配额；
   一次调用只编译一条语句；外键默认打开。`transaction` 是**一批语句**
   （没有跨调用的 `begin`/`commit` —— 那是会泄漏的写事务状态）。
6. ~~**`ctx.http.download`**~~ **已完成** —— 见 §3.3。响应的字节流由宿主**直接写进**
   插件数据目录（`bytes_stream`，全程只有一个固定缓冲区），先写同目录的 `.part`
   再改名收尾，配额边写边判，非 2xx 不落盘，进度走推送通道并强制补发最后一次。
   `check:sandbox` 第 18 节 38 条断言，23 个变异全部验过会打红。
7. **9 个插件全部迁移** —— 宿主侧的前置条件**已完成**（见 §7.2：宿主把自己的
   React 送给沙箱插件）。剩下的是 8 份清单各加一行 `"runtime": "sandboxed"`，
   以及 `quick-launch` 的 `ctx.fileDrop` 这一处真实差异。**插件尚未迁移。**
8. **实测与校准**：单插件内存增量、驻留上限、启动耗时。

**每完成一步只跑静态门禁与测试，不交付中间构建。** 全部完成之后交付一次。

### 7.1 进度说明（诚实版）

"已完成"指的是**代码与断言都在，门禁与单元测试全绿**。它**不**意味着下面这些：

* 9 个插件里只有 `hello` 是真的沙箱插件，其余 8 个仍是 in-process，**迁移未开始**；
* 单插件 webview 内存**从未实测**（§8 的验收项，也是驻留上限的依据）；
* 后台插件这条路径**没有在真实应用里跑过一次** —— 它有的是一组真的启动子进程、
  真的加载代码、真的回环一次 `ctx.*` 的集成测试，以及静态门禁。**GUI 那一层
  只能由人跑**（见 §10）；
* 主题 / 快捷键 / 浮层 / 多界面 / 状态指示同理：链路每一环都有断言守着，
  但**没有人看过它长什么样**。浮层与多界面尤其明显 —— 前者新加了一个窗口、
  一个 Vite 入口、一个 capability；后者新加了一条"插件开标签"的反向事件链。
  "在屏幕上真的发生"静态检查证明不了。
* **多界面的驻留上限仍然是一个占位值**（`MAX_RESIDENT = 3`，而且它数的是界面）。
  多界面落地之后这个数字更容易被撞到 —— 第 8 步的实测因此更急了。

**步骤 2、5、6 已经没有未做项；剩下第 7、8 项。**

### 7.2 第 7 步为什么不是"清单改一行"

1.6.0 起了个头（宿主版本、`engines.modulith`、下限 `>=1.6.0`、删掉死字段
`sandboxLevel`、给这条契约补上 135 条断言与 10 个变异），但**迁移本身没做**。

原因是 sandbox 与 in-process 的**渲染模型不同**，而不只是清单字段不同：

| | in-process | sandboxed |
| --- | --- | --- |
| React | 宿主给（`Modulith.React`），全应用同一个实例 | **没有** —— 插件在自己的文档里 |
| 挂载 | `Modulith.registerModule({ component })` | 自己写进 `#modulith-root` |
| 宿主 CSS | 共享宿主的样式表与 `.dark` 类 | 只有宿主注入的主题令牌（同名变量，见 `theme.rs`） |
| `Modulith.createContext` / `useModuleActive` | 有 | 没有 |
| `ctx.fileDrop` | 有 | **没有，且补不了**（拖放是窗口级事件，子 webview 收不到） |

现有 8 个插件全部依赖前四行的 in-process 形态（逐个体检过：`Modulith[createContext,
React, registerModule, useModuleActive]`），合计约 12,000 行 JS 与 6,800 行 CSS，
`quick-launch` 还用到第五行那个补不了的能力。

因此第 7 步要先回答**沙箱插件从哪来 React**。这个问题**已经定了，并且宿主侧做完了**
（1.6.0）：**由宿主把自己那一份送过去**，而不是每个插件各打一份。

理由不是省事：插件仓库的构建把 `react` / `react/jsx-runtime` 接到
`globalThis.Modulith.React` 与 `globalThis.Modulith` 上，那条约定的前提是
**一个文档里只有一个 React 实例**。各打一份会直接违背它，而且会变成"某个插件
钉着 18、某个钉着 19"这种只在其一里复现的 bug。

宿主侧现在有：`scripts/build-plugin-react.ts` 生成
`src-tauri/resources/react-runtime.js`（入库、压缩到 189.7 KB、保留 MIT 声明），
`sandbox.rs` 在插件协议上提供 `GET /<id>/react.js` 并把它排在桥接层**之前**，
桥接层交出 `React` / `jsx` / `jsxs` / `jsxDEV` / `Fragment` / `createContext`，
并把 `registerModule` 改成"把自己挂到 `#modulith-root`"、`useModuleActive` 恒为
`true`。`check:sandbox` 第 19 节 22 条断言，13 个变异全部验过会打红。

**因此剩下的是：8 份清单各加一行 `"runtime": "sandboxed"`，加上一条真实的差异** ——
`ctx.fileDrop` 沙箱里补不了（拖放是窗口级事件，子 webview 收不到），
`quick-launch` 用到它，要么去掉那个功能，要么单独想办法。做完之后必须
**在真机上逐个看过**：这一步的断言守的是"宿主发对了、桥接层接对了"，
"屏幕上真的出现界面"静态检查证明不了。

## 8. 验收标准

一份方案"做完"的判据，全部可机械核对：

- [ ] `check:sandbox` 断言：§3 表里每一个成员都在桥接层里有实现，无遗漏；
- [ ] 9 个插件的清单里 `runtime: "sandboxed"`，且都能正常加载；
- [ ] 一个能建多界面、能写大文件、能跑后台定时的**示例插件**通过；
- [ ] 宿主 135 条命令里，**没有任何一条**对插件 webview 可见（ACL 断言）；
- [ ] 单插件 webview 内存增量实测值记录在案，驻留上限由它推出；
- [ ] 主题、快捷键、右键菜单在插件内与宿主内**表现一致**。

## 9. 明确不做（与既有判断一致）

| 项 | 理由 |
| --- | --- |
| OS 级沙箱（Job Object / AppContainer） | 本方案是**进程内隔离**。那是另一层 |
| `filesystem-write`（任意写） | 没有边界，补它等于制造假的管控点 |
| `native-module` | 这一能力不存在 |
| 插件代码签名 | 独立的一条线 |
| 移动端 | Windows 优先 |

## 10. 我必须说清楚的一条环境限制

**我无法启动 GUI 窗口**（这个 agent 环境里 `notepad.exe` 都拿不到 `MainWindowHandle`）。
因此：

* 我能做到的是**把整件事一次做完**，并用单元测试 + 门禁把能静态验证的全部钉住；
* 最终"它看起来对不对、用起来顺不顺"只能由你跑一次。

这就是为什么本文档把验收标准写成**可机械核对**的清单 —— 让那一次验证尽可能短，
