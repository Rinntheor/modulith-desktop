# 插件平台完整方案（v2.0 规格）

> 这份文档取代"一次做一小块"的做法。它是一次性把**目标形态、完整 API 表面、
> 隔离模型、数据层、界面形态、生命周期、执行顺序与验收标准**全部定下来。
>
> 定下来的东西不再逐条征求确认；实现按本文档一次推进，中途**不要求人工验证**，
> 全部完成之后交付一个可测的构建。

---

## 0. 一句话结论

**每一个插件都是一个独立的应用：它有自己的 webview、自己的前端框架、自己的数据、
自己的界面；宿主提供它所需的一切能力，并且**只能通过一条受管的通道**提供。**

---

## 1. 目标形态

一个"中大型应用插件"必须能做到的事，这份方案必须全部支持：

| 能力 | 具体表现 |
| --- | --- |
| 自带前端运行时 | 自己的 React / Vue / Svelte / 原生 DOM，**不与宿主同版本** |
| 多界面 | 一个插件可以声明多个可打开的界面（列表、详情、设置、独立的工具窗） |
| 无界面 | 后台服务型插件：定时任务、文件监听、同步。**不为了它建一个渲染进程** |
| 大容量数据 | 键值、文件目录、结构化数据库三层，装得下笔记、文档、图库 |
| 完整系统能力 | 网络、文件、剪贴板、通知、外部程序、事件总线 |
| 崩溃隔离 | 插件界面崩溃不带走宿主，宿主也不因它卡住 |
| 可迁移 | **9 个已发布插件全部能迁进来**，不是只有 hello |

## 2. 隔离模型（已成立，不再改）

```
宿主主 webview（标签、侧边栏、设置…）
  │  宿主命令只授权给这一个 webview（当前 153 条，见后端命令参考）
  │
  ├── <iframe>  ← 每个插件界面一个，来源 modulith-plugin，0 条 capability
  │     · 子框架拿不到 IPC（Tauri 的内部初始化脚本都带 for_main_frame_only）
  │     · CSP 由宿主写死（连不出去）
  │     · 与宿主的**全部**通信走自定义协议 modulith-plugin
  │     · 身份是**每个界面一个不可猜的令牌**（URL 第一段），插件伪造不了
  │
  └── 同一插件的第 2..n 个界面 = 另一个 iframe、另一个令牌
```

**v1.6.0 的改动**：这一层从前是**原生子 webview**（`Window::add_child`），
理由是 iframe 拿不到真隔离。那个判断在核对了 Tauri/wry 源码之后被推翻，
而子 webview 付出的代价（引擎把它合成在父窗口客户区之上，CSS 完全碰不到它）
是不可接受的。完整推导、源码位置与代价见 §7.3。

**一条仍然成立的铁律（血的教训，见技术债 §7.44）**：**从命令里创建 webview
会假死** —— 同步命令的函数体在 IPC 线程（主线程）上就地执行，而它要等一个
只有主线程才能送达的完成通知。这条约束与沙箱无关，适用于任何建窗口的地方：
现在仓库里唯一还会建窗口的是**沙箱自检**，因此 `sandbox_self_test` 必须保持
`async`。

## 4. 无界面（功能性）插件：跑在 Node 后台宿主里

**形态：插件代码跑在 Node 后台宿主进程里。不建渲染进程。**

> **这一节被改过。** 原方案写的是"隐藏的沙箱 webview"。改成 Node 宿主是一个
> **明确的产品决定**（2026-02）：后台插件必须有真正的后台能力，而"隐藏 webview"
> 在这件事上从一开始就是将就 —— 它会被浏览器降级与冻结，而托付给它的恰恰是
> "凌晨三点要准时醒过来"这类事。
>
> 接受的前提也随之明确：**Node 运行时不随包分发，由用户自己安装。**
> 这不是缺陷，是这个选择的代价，因此必须把"没有 Node 时是什么状态"说清楚，
> 而不是让插件半可用。

### 4.1 Node 从哪来

复用既有的一套查找（`background/mod.rs::resolve_node`，五级顺序）：

| 顺序 | 位置 | 谁会用 |
| --- | --- | --- |
| 1 | 设置 → 性能 里手工指定的路径 | 普通用户：选一次就记住 |
| 2 | 环境变量 `MODULITH_NODE` | 开发与排障 |
| 3 | `<应用目录>/runtime/node.exe` | 愿意随包分发的发行版 |
| 4 | 官方安装程序的默认落点 | 绝大多数机器 |
| 5 | 系统 `PATH` | 已经装过 Node 的机器 |

**没有 Node 时**：设置页与插件详情页显示**具体原因**，后台插件标为"需要 Node
运行时"。不静默降级、不假装可用。这与 `ctx.db`、`ctx.http.download` 一样，
属于"宿主明确说清楚它现在做不到什么"。

### 4.2 一个后台插件长什么样

```json
{
  "runtime": "sandboxed",
  "contributes": {
    "background": {
      "entry": "background.js",
      "onStartup": true,
      "interval": 60,
      "events": ["onCommand:sync", "onPluginEvent:notes/changed"]
    }
  }
}
```

后台插件**仍然是一个普通插件**：同一份清单、同一套权限、同一个 `ctx` 形状。
区别只有两处：

* 它有一个 `background.entry`（一个独立的 JS 文件，与 `main` 分开 ——
  后台入口不该被迫加载界面代码）；
* 它拿到的 `ctx` 是**界面 ctx 的子集**，去掉所有 DOM 相关成员。

| 有 | `storage` `dataDir` `db` `http` `settings` `events` `logger` `notifications` `disposables` `launcher` `shell.revealInFolder` |
| 无 | `ui` `theme` `clipboard` `fileDrop` `icons` `audio`（这些要么是 DOM，要么是窗口级） |

### 4.3 进程模型：**一个后台插件一个进程**

不是"一个宿主进程里跑所有后台插件"，而是**每个后台插件各自一个 Node 子进程**。

理由与 webview 沙箱是同一条：**崩溃隔离**。一个后台插件写出死循环或吃掉几百 MB
内存时，它只该弄死自己 —— 而"共享一个进程"意味着任何一个后台插件的失控都会
拖走其余全部后台插件，连带让宿主报出"后台功能不可用"。这与 §6 的驻留淘汰是
同一件事的两个方向：**资源要么被隔离，要么被限制**。

进程的生命周期与 webview 界面一致：

| 状态 | 触发 | 动作 |
| --- | --- | --- |
| 声明 | 安装 | 只读清单，**不执行任何代码** |
| 拉起 | `onStartup` / 定时到点 / 命令 / 事件 | 起子进程，加载 `background.js` |
| 运行 | —— | 常驻（后台插件本来就要一直在），但受引擎级资源上限约束 |
| 回收 | 用户停止 / 空闲超时 / 应用退出 | 先发 `shutdown` 让它收尾，超时再强杀 |

### 4.4 隔离强度：**这一层比 webview 沙箱弱，必须说清楚**

webview 沙箱那一层是**引擎边界**：另一个渲染进程、0 条 capability、身份来自
webview 标签。后台这一层**不是**同一件事，它由三部分组成：

1. **进程边界** —— 崩溃、内存、CPU 不互相影响；
2. **`node:vm` 上下文** —— 插件代码在自己的 global 里，拿不到 `require` /
   `import` / `process`，只有一个冻结的桥接对象；
3. **引擎级的文件系统权限** —— 子进程用 `--permission` 启动，只放开
   **这个插件自己的代码目录与数据目录**。

第 3 条是这里最实在的一层：它不是我们写的检查，是 Node 自己执行的。一个逃出
`vm` 的插件仍然读不到别的插件的数据，也写不到数据根之外 —— 因为它没有那个
文件系统权限。

**它挡不住的**：Node 官方明确说 `vm` 不是安全机制。一个蓄意逃逸、又恰好拿到
了某个宿主对象引用的插件，可以在这个进程内为所欲为。它能动的范围被第 3 条
限制在"这个插件自己的目录"，但**不是一个通用安全边界**。

因此：后台插件仍然受完整权限模型约束，且这些判定都在**宿主侧**做（插件调的是
宿主的方法，不是自己实现的）。需要更强隔离的后台插件应当使用 webview 沙箱，
而不是 Node 宿主 —— 这条写进插件开发文档。

### 4.5 声明式激活（与回收相容）

后台插件**可以**持有定时器（这正是它存在的理由），但清单里的
`background.interval` / `events` 仍然是必要的：宿主据此知道"要不要为它拉起进程"。

没有 `background` 声明的插件**不会**被拉起 —— 一个装了但从不运行的插件不该
占用一个进程。

## 5. 多界面（`api: 3`）

```js
Modulith.ui.openSurface('detail', { width: 480 });   // 宿主决定位置
```

* 每个界面一个 `plugin-<id>#<surface>` 标签，`SandboxSurfaces` 的键从"插件 id"扩成
  "(插件 id, 界面名)"；
* 入口文档按界面名加载不同入口（清单里 `surfaces: [{id, name, entry}]`）；
* 布局仍由前端量、宿主摆 —— 沿用现有 `measureSurface` 一条路径；
* 驻留上限按**界面**计数，不按插件。

### 5.1 落定之后的形状（实现与上面那版草稿的差别）

清单里的界面写在 **`contributes.surfaces`**（与 `contributes.background` 一致），
而不是顶层：

```json
{
  "contributes": {
    "surfaces": [
      { "id": "main",   "name": "笔记", "entry": "dist/index.js",  "style": "dist/index.css" },
      { "id": "detail", "name": "详情", "entry": "dist/detail.js" }
    ],
    "modules": [
      { "id": "notes",         "name": "笔记" },
      { "id": "notes-setting", "name": "笔记设置", "surface": "main" }
    ]
  }
}
```

**三条必须记住的规则：**

1. **`main` 是必需的主界面**，不是"第一个就是主界面"。顺序定义主界面的话，调整
   清单顺序就会改变 webview 标签 —— 而所有关于标签的推理（日志、断言、驻留表）
   都建立在"名字是稳定的"之上。缺 `main` 时整份清单被拒，且错误消息说清缺什么。
2. **主界面拿不带 `#` 的标签**（`plugin-<id>`），次级界面拿带名字的
   （`plugin-<id>#<detail>`）。这是"已发布的单界面插件一字不改"的全部依据 ——
   它们的标签、入口文档、路由与多界面之前逐字节相同。
3. **界面 id 走白名单**（字母数字与 `-` `_`，不以数字/`-`/`_` 开头，长度 ≤32），
   而且**不净化**。插件 id 可以净化（它允许 `.`），界面 id 不行：净化会把 `a.b`
   与 `a-b` 映射到同一条标签，而两个界面互相覆盖的症状是"其中一个打开后显示的是
   另一个的内容"。

**打开一个界面不由宿主建 webview。** 只有前端知道界面该摆在哪（标签栏多高、
侧边栏是否展开、分屏开没开），因此：

```
插件 → ui.openSurface('detail') → 宿主广播 modulith://open-surface
     → 前端开一个标签 → 标签里的占位量出矩形
     → sandbox_surface_open(插件, 界面, 矩形) → 宿主建 webview
```

次级界面在宿主里被登记成一个 **`hidden` 模块**（id 形状 `plugin:<插件>#<界面>`，
与清单模块 id 的字符集不可能撞上）：能按 id 打开、能进标签、能被驻留淘汰，
但不出现在侧边栏 / 仪表盘 / 命令面板里。被 `contributes.modules` 声明过的界面
**不再造**隐藏模块 —— 造了的话同一个界面会有两块 webview，而标签是唯一的。

停用或卸载插件时，宿主**主动关掉它还开着的全部界面**（在命令那一层做，三条
停用路径因此不会漏掉一条）。

## 6. 生命周期与资源

| 状态 | 触发 | 动作 |
| --- | --- | --- |
| 声明 | 安装 | 只读清单，**不执行任何插件代码** |
| 激活 | 打开模块 / 命令 / 事件 / `onStartup` | 建 webview，跑入口 |
| 隐藏 | 切标签、宿主浮层、窗口收起 | `hide()`，**不销毁** |
| 回收 | 超过驻留上限 / 空闲超时 | 销毁最久未用的**隐藏**界面 |
| 卸载 | 用户操作 | 删代码，**保留数据** |

**驻留上限**：默认 `max(2, 内存等级对应值)`。上限数字必须**实测**校准
（方案 §10 的实测项），而不是拍一个。

### 7.2 第 7 步为什么不是"清单改一行"

**它在 1.6.0 做完了 —— 9 个插件全部 `runtime: "sandboxed"`。** 但过程说明了为什么
它不只是一行清单：动手之前先做了一次**逐个审计**，而那次审计挡住了一个会让插件
**加载失败**的缺口（`kanban` 用的 `Modulith.registerCommand`，见下）。

原因是 sandbox 与 in-process 的**渲染模型不同**，而不只是清单字段不同：

| | in-process | sandboxed（1.6.0） |
| --- | --- | --- |
| React 实例 | 宿主给（`Modulith.React`），全应用同一个实例 | **宿主也给**（走 `react.js`）—— 同一个版本、同一个实例 |
| 挂载 | `Modulith.registerModule({ component })` | 同一个名字，含义是"把我这个组件挂到本界面上" |
| 宿主 CSS | 共享宿主的样式表与 `.dark` 类 | 只有宿主注入的主题令牌（同名变量，见 `theme.rs`） |
| `Modulith.createContext` / `useModuleActive` | 有 | **有**（`useModuleActive()` 恒为 `true`，见下） |
| `ctx.fileDrop` | 有 | **有**（宿主按位置筛，语义见下面的说明） |
| `Modulith.platform` / `registerCommand` / `onDeactivate` | 有 | **有**（1.6.0 补上，见下） |
| `ctx.manifest` | 有 | **没有** —— 宿主只送 id / 名称 / 版本 / 权限 / 界面表 |
| `Modulith.capabilities` / `Modulith.run` | 有 | **没有** —— 两条都写在插件文档里，理由见下 |

**这张表在 1.6.0 之前是不完整的，而不完整的地方藏着一个会让插件加载失败的缺口。**
`check:sandbox` 的两侧比对只读了 `ctx.*`（`CONTEXT_MEMBERS`），`Modulith.*`
（`HOST_MEMBERS`）那一侧**从来没有比过**。于是一整类缺失一直没人知道 —— 其中
`kanban` 在 bundle 顶层调用 `Modulith.registerCommand({ id, title, run })`，
迁到沙箱不是"某个功能失效"，是**整个插件加载时抛 TypeError**。

这一节因此补了两件事：宿主表面缺的三个（`platform` / `registerCommand` /
`onDeactivate`）都实现了；门禁改成**两张表都比**，并把剩下的缺口钉成
"已知且被承认"的清单。

剩下那两条的性质不同，都不是能力：

* **`Modulith.capabilities`** —— 那张表由**前端**从 `pluginBoundary.ts` 派生
  （`HOST_CAPABILITIES`），而桥接层是 Rust 渲染的。把它送进去需要前端在建界面时
  交给宿主、宿主存在令牌旁边、再注入桥接层：可行，但 9 个插件一个都没读过它，
  因此没有先做。
* **`Modulith.run`** —— 显式引导入口。它在 in-process 侧的价值是**去掉隐式全局**
  （v1 靠"当前正在加载哪个插件"决定归属，那个全局跨不过 realm）；而沙箱里这份
  文档从头到尾只属于一个插件，那个全局根本不存在，"引导"没有对应的问题要解决。

**`useModuleActive()` 在沙箱里恒为 `true`**，这不是偷懒：插件界面只有被选中时才
会拿到令牌、才会被渲染，因此"我在不在前台"由宿主那一次的渲染决定，而不是一个
要轮询的状态。

现有 8 个插件（加 `hello` 共 9 个）**逐个审计过**：把它们用到的每一个
`Modulith.*` 成员与沙箱实际交出的成员对了一遍，**9 个全部没有缺口**。
审计脚本是 `staging/audit-sandbox-migration.cjs`（它也是发现上面那个
`registerCommand` 缺口的东西）。合计约 12,000 行 JS 与 6,800 行 CSS。

因此第 7 步要先回答**沙箱插件从哪来 React**。这个问题**已经定了，并且宿主侧做完了**
（1.6.0）：**由宿主把自己那一份送过去**，而不是每个插件各打一份。

理由不是省事：插件仓库的构建把 `react` / `react/jsx-runtime` 接到
`globalThis.Modulith.React` 与 `globalThis.Modulith` 上，那条约定的前提是
**一个文档里只有一个 React 实例**。各打一份会直接违背它，而且会变成"某个插件
钉着 18、某个钉着 19"这种只在其一里复现的 bug。

宿主侧现在有：`scripts/build-plugin-react.ts` 生成
`src-tauri/resources/react-runtime.js`（入库、压缩到 189.7 KB、保留 MIT 声明），
`sandbox.rs` 在插件协议上提供 `GET /<id>/react.js` 并把它排在桥接层**之前**，
桥接层交出 `React` / `jsx` / `jsxs` / `jsxDEV` / `Fragment` / `createContext`，
并把 `registerModule` 改成"把自己挂到 `#modulith-root`"、`useModuleActive` 恒为
`true`。`check:sandbox` 第 19 节 22 条断言，13 个变异全部验过会打红。

**8 份清单各加一行 `"runtime": "sandboxed"` —— 已经加了**（连同
`engines.modulith` 抬到 `>=1.6.0` 与一次 PATCH 升版重打包，见
`modulith-plugins` 的提交 `f778210`）。它**没有任何能力差异需要先补**：动手前
那次逐个审计的结果是 9 个插件全部通过（`ctx.fileDrop` 与
`Modulith.platform/registerCommand/onDeactivate` 都是这一轮补的）。

做完之后必须**在真机上逐个看过**：这一步与它的前置（iframe 重写）都只在静态检查
里验过，"屏幕上真的出现界面"证明不了。

**`ctx.fileDrop` 的结论在 1.6.0 变了，而且已经补上了。** 从前它被记为"沙箱里
补不了"，理由是拖放是窗口级事件、子 webview 收不到。核对 wry 之后发现那个理由
只对了一半：wry 在 Windows 上把拖放处理器注册在 **webview 自己的 HWND 及其全部
子窗口**上（`wry-0.55.1/src/webview2/drag_drop.rs:50`）。子 webview 有自己的 HWND
且没注册处理器，路径因此从根上断掉。**换成 iframe 之后指针底下始终是主 webview
的 HWND**，处理器照常触发，事件里还带指针位置。

实现是三段，缺一段插件就收不到，而三种缺法的症状都是"拖进去没反应"：

1. **权限由宿主判定。** `sandbox_surface_open` 的返回值多了一个 `fileDrop` 位，
   由 `sandbox.rs` 从清单的 `filesystem-read` 算出来。前端**不自己查清单** ——
   拖放送来的是本机路径，让一个还能被插件影响的那一层去判，等于没有判定；
2. **前端按位置筛。** 拖放是窗口级事件，而 `Home.tsx` 里各标签面板是叠在一起、
   靠 `visibility: hidden` 藏的 —— 只按"我在不在前台"过滤，一次拖放会转给屏幕上
   那块**以及藏在它下面的那一摞**。因此命中测试是必需的：物理像素除以
   `devicePixelRatio`，再与占位块的矩形比。`leave` 不带坐标，靠"上一次真的进来了"
   那个标记认领；
3. **桥接层扇出。** `Modulith.fileDrop = { isAvailable, subscribe }`，形态与
   in-process 的 `ctx.fileDrop` 逐字一致；未声明权限时降级为空订阅 + 一次告警。

**一处语义差别，是更好的那种**：in-process 的拖放是窗口级的，插件必须自己用
`useModuleActive()` 判断当前可不可见，否则后台插件会抢走本该属于别人的拖放；
沙箱里宿主已经按位置筛过了，**收到就是拖到了我这一块上**。这一条写进插件文档。

## 7.3 渲染方式的决定：放弃原生子 webview，改用跨源 iframe

**决定日期：1.6.0 开发期。触发原因是一次真实使用**：用户报告沙箱插件界面会盖住
宿主的侧边栏边缘模糊与标题栏的搜索展开。

### 为什么那不是可以修的 bug

原生子 webview 是一个**独立的 HWND**，由 WebView2 合成在父窗口的客户区之上。
CSS 的 `z-index`、`position: fixed`、`backdrop-filter` 对它**一律无效**。
这不是实现缺陷，是合成模型。因此受影响的不止那两处 —— 盘点之后，宿主主 webview 里
**所有浮在内容之上的界面**都在插件界面之下：

| 宿主界面 | 定位 | 与插件界面矩形相交 |
| --- | --- | --- |
| 标题栏的搜索展开 | `absolute top-9 z-66`（从 40px 的标题栏往下掉） | 会 |
| 宿主自己的右键菜单 | `fixed z-50` | 会 |
| 通知中心 | `fixed right-3 top-11 z-66` + `inset-0 z-65` 遮罩 | 会 |
| 轻提示（toast） | `fixed bottom-4 right-4 z-[70]` | 会 |
| 设置对话框 | `fixed inset-0 z-60` | 会（全屏） |

其中"设置"与"通知中心"看起来还能用，只是因为它们的覆盖率超过了遮挡阈值，
插件界面被**收起来了** —— 那不是修好，那是用"插件界面消失"换来的。

原有的 `isCovered` 几何轮询（第 21 节）保留为兜底，但它天生有延迟
（150ms 轮询 + 两次确认），阈值调小又会让普通提示条把插件界面闪掉。

### 可行为什么成立：三条独立的安全边界，都已核对到源码

换 iframe 的**唯一**顾虑是隔离会不会变弱。核对 Tauri 2.11.5 的源码之后，
答案是**不会**，而且是三重：

1. **子框架拿不到 IPC。** `tauri-2.11.5/src/manager/webview.rs:159-200`：
   Tauri 注入的**每一个**内部初始化脚本 —— `__TAURI_INTERNALS__`、
   invoke 脚本、metadata、IPC 脚本 —— 都经过 `main_frame_script()` 包装，
   而它设的是 `for_main_frame_only: true`。iframe 里因此**没有 `invoke`**。
2. **手工拼请求也不行。** `tauri-2.11.5/src/webview/mod.rs:1744-1762`：
   IPC 处理器**第一件事**就是比对 `invoke_key`（每次运行随机生成、只注入主框架），
   不匹配就 `return`（**静默丢弃**）。iframe 无法知道这个键。
3. **同源策略。** 插件 origin 是自定义协议的
   `http://modulith-plugin.localhost`，与宿主 origin 不同源 ——
   iframe 摸不到 `parent` 的任何东西，因此也枚举不出兄弟界面。

**引擎那一侧本来就是支持 iframe 的。** wry 注册自定义协议时优先用
`AddWebResourceRequestFilterWithRequestSourceKinds(..., SOURCE_KINDS_ALL)`
（wry-0.55.1/src/webview2/mod.rs:936），那个重载的注释写明了它的用途是让
**Shared Worker 与 iframe** 也能走自定义协议（对应 WebView2Feedback#1114）。
这条比推理更硬：它是实现里的一句显式意图。

**iframe 的 `sandbox` 属性怎么设。** 用
`sandbox="allow-scripts allow-same-origin"`，其余默认全拒绝（表单、弹窗、
模态框、顶层跳转、下载、指针锁定、自动播放）。两条必须放开的原因不同：
前者是插件代码本身；后者不放开的话文档会退化成**不透明来源**，连它自己那份
`fetch`（到 `modulith-plugin.localhost`）都算跨源，而宿主没有为它准备 CORS 头。

"`allow-scripts` + `allow-same-origin`"那条经典警告在这里**不适用**：它说的是
被嵌文档与父文档**同源**，而插件来源与宿主不同源，因此插件够不到 `parent`，
也就删不掉这个属性。反面方案（去掉 `allow-same-origin`，靠 CORS 让 fetch 通）
被否掉的原因是它把一条**引擎级**的边界换成了一条**宿主配置**的边界。

### 但有一条依赖必须被钉住

`tauri-2.11.5/src/webview/mod.rs:1698-1739` 的 `is_local_url`：
**自定义协议的 `.localhost` 也算 Local**。也就是说 ACL 那一侧会把插件 origin
判成 `Origin::Local`，主窗口的 capability **在形式上适用**。
真正拦住它的是上面第 2 条（`invoke_key`）。

**推论：沙箱的安全性实际上依赖"Tauri 继续要求 invoke_key"这一件事。**
Tauri 哪天改了它，沙箱会**静默**变成假的 —— 没有报错、没有症状，
直到有人发现插件能调宿主命令。

这条依赖**已经钉住了**（`resources/sandbox-bridge.js` 的 `assertNoHostIpc`）：
每一份插件文档在加载时都会检查 `__TAURI_INTERNALS__` / `__TAURI__` /
`isTauri` / `window.ipc` 四者是否都不存在，存在就写一条 `error` 进宿主日志，
并把它交给自检页显示。它**不是一道拦截**（插件也不该靠它），它是一盏灯 ——
正常运行时什么都不做，边界塌了的时候立刻说出来。

### 一件原计划里没有、但同一个来源逼出来的事

全部插件界面共享 `http://modulith-plugin.localhost` 这**一个来源**，
因此 `localStorage` / `sessionStorage` / `indexedDB` / `caches` 是**公用**的：
插件 A 写进去的东西插件 B 读得到。子 webview 时代它们同样是同一个来源，
只是那时没人去想这件事。

桥接层因此在插件代码之前把它们封成**不可重定义的抛错访问器**
（`freezeOriginStorage`）。"不可重定义"是关键：插件跑在同一个 realm 里，
一个可配置的属性它自己 `delete` 一下就没了，那样封了等于没封。
`document.cookie` 单独处理 —— 读返回空串（读它的人多半是某个捆绑进来的库在做
特性探测，让它们抛会把一个无关的插件打挂），**写**必须失败（写才是那条
"把数据留给下一个插件"的路）。

### 实际改了什么

**删掉**：

* `plugins/surface.rs` **628 行** —— 所有者线程、几何测量、`add_child`、
  驻留上限、`MAX_RESIDENT` 占位值。**整块消失**；
* `SandboxSurface.tsx` 里的测量与遮挡轮询（`measureSurface` / `isCovered` /
  `COVERAGE_THRESHOLD` / 150ms 轮询）—— 变成一行 CSS 布局；
* `sandbox_surface_hide` 与 `sandbox_surface_bounds` 两条命令（含 `build.rs`
  的 ACL 清单、`lib.rs` 的 `generate_handler!`、以及前端的门面）——
  **这两条命令已删除**（`build.rs` 现在只有 `sandbox_surface_open` /
  `sandbox_surface_close` / `sandbox_self_test`）。当时记的"命令总数 152 → 150"
  是**当时那一刻**的账，此后又新增过命令，**实测当前总数为 153 条**
  （`pnpm check:acl` 的输出：`app-commands.json` 150 + `overlay.json` 3，见[后端命令参考](../03-参考/后端命令参考.md)）；
* `check:sandbox` 里几何、生命周期、遮挡那几节。

**没有删的一件**（这里更正本文档初稿里的一句话）：

初稿把 `desktop/overlay.rs` 486 行也列进了"要删的"，理由是"它存在的唯一理由
就是原生子 webview 盖得住宿主 DOM"。**那个理由不成立。** overlay 是一个
**独立的 `alwaysOnTop` 窗口**，它悬在主窗口**整体之上** —— 子 webview 在它
下面，iframe 也在它下面。它服务的是插件的 `ctx.ui.showDialog` /
`ctx.ui.contextMenu`，从头到尾没有被这次改动动到，也**不需要**动。

真正的收益是：宿主**自己**那些 DOM 浮层（标题栏搜索展开、通知中心、轻提示、
设置对话框、宿主右键菜单）不再需要"让位"了 —— 它们与 iframe 是同一个文档树里
的兄弟节点，`z-index` 就此生效。把 overlay 拆掉改写成 DOM 对话框是**另一件事**，
与本次迁移正交，因此没有混进来。

**新增**：

* `sandbox.rs` 的**身份模型**：从 `UriSchemeContext::webview_label()`
  换成**每个界面一个不可猜的令牌**（`uuid` v4，122 位随机，建立界面时签发）。
  令牌出现在该界面每一条请求的**路径第一段**：
  `/<token>/`、`/<token>/bridge.js`、`/<token>/react.js`、`/<token>/asset/…`、
  `/<token>/data/…`、`/<token>/rpc/<方法>`。
  **这一条是安全关键**：iframe 的 webview label 是 `main`，
  不改的话所有插件会塌成同一个身份 —— 插件 A 能读插件 B 的数据。
  令牌**幂等**（同一个界面永远只签发一个），否则重复渲染会在注册表里留下
  一条指向已不存在 iframe、却仍然有效的凭据；
* `SandboxSurface.tsx` 渲染 `<iframe>`，并加一层**失败提示** ——
  iframe 模型的失效方式是一块白面板，而白面板不告诉任何人它为什么白；
* **推送通道从 `eval` 换成 `postMessage`**：Rust 发一条事件到主窗口
  （`sandbox::PUSH_EVENT`），前端按令牌找到 iframe 再 `postMessage` 进去，
  桥接层按 `channel` 分派。主题、快捷键、命令、下载进度、跨插件事件五条都换掉了。
  转发时 `targetOrigin` 是**从地址算出来的**，不是 `'*'`；
* **就绪信号**：桥接层挂好后主动向父窗口发一条 `{channel:'ready'}`。宿主不用
  iframe 的 `load` 事件判断成功 —— 那在一个**加载失败**的文档上照样会触发；
* **自检加了一项**：自检页现在自己嵌一个同源 iframe（`/<token>/probe`），
  问"真插件界面那个模型里到底有没有 IPC"。只验自检窗口是不够的 ——
  那个窗口是主框架，Tauri 会给它注入引导脚本，它被 ACL 挡住只能证明 ACL 生效。

**原样保留**（安全工作的主体）：协议处理器、入口文档合成、桥接层、
`react.js`、静态资源、原始字节通道、RPC 分派、`ctx.db`、配额、`ctx.http.download`。
`overlay.rs` 也在保留之列。

### 代价与诚实说明

* 主 webview 现在要同时承载 N 个 iframe 的渲染，内存的账要重新算 ——
  第 8 步的实测因此更必要，不是更不必要。而且**"驻留上限"这个概念本身变了**：
  从前淘汰的是原生 webview（每个一套控制器），现在淘汰的是一个 iframe
  （卸载 = 插件界面状态一起没）。上限要按新的代价重新定，不能照搬 `3`。
* `zoom` 与 DPI：iframe 与宿主同一缩放，几何问题整类消失。
* 宿主 CSP **必须**放开 `frame-src http://modulith-plugin.localhost`
  （已加在 `tauri.conf.json`）。漏了它的表现是**每一块插件界面都是空白**，
  而引擎只在控制台里说一句 —— 这条因此进了门禁。
* **这一步仍然只能由人在真机上看**：我把守卫与断言都做出来了，
  但"界面真的画对了"静态检查证明不了。

## 8. 验收标准

一份方案"做完"的判据，全部可机械核对：

- [ ] `check:sandbox` 断言：§3 表里每一个成员都在桥接层里有实现，无遗漏；
- [ ] 9 个插件的清单里 `runtime: "sandboxed"`，且都能正常加载；
- [ ] 一个能建多界面、能写大文件、能跑后台定时的**示例插件**通过；
- [ ] 宿主 153 条命令里，**没有任何一条**对插件 webview 可见（ACL 断言）；
- [ ] 单插件 webview 内存增量实测值记录在案，驻留上限由它推出；
- [ ] 主题、快捷键、右键菜单在插件内与宿主内**表现一致**。

## 9. 明确不做（与既有判断一致）

| 项 | 理由 |
| --- | --- |
| OS 级沙箱（Job Object / AppContainer） | 本方案是**进程内隔离**。那是另一层 |
| `filesystem-write`（任意写） | 没有边界，补它等于制造假的管控点 |
| `native-module` | 这一能力不存在 |
| 插件代码签名 | 独立的一条线 |
| 移动端 | Windows 优先 |

## 10. 我必须说清楚的一条环境限制

**我无法启动 GUI 窗口**（这个 agent 环境里 `notepad.exe` 都拿不到 `MainWindowHandle`）。
