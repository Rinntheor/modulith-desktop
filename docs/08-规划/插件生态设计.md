> **本文性质：设计稿。**
>
> `docs/` 的其余部分描述**当前代码的实际行为**，本文不同 —— 它描述的是**尚未实现**的目标
> 形态与实现顺序。本文不承诺与代码一致。
>
> 约定：每完成一个阶段，该阶段内容迁出本文、进入对应的正式文档（架构 / 插件开发 /
> 安全），并在第 11 节标记为已完成。本文因此会随实施逐步变短。

## 1. 现状与缺口

插件系统在**能力**上已经可用：有清单、有权限、有安装流水线、有运行时、有可安装的示例插件。
缺的不是能力，是**生态**。

一个生态的最小闭环是四件事：**发现 → 分发 → 信任 → 更新**。当前四件全缺，而且其中三件
不在插件系统内部，而在它下面 —— 它们是基础设施。

| 环节 | 当前状态 |
| --- | --- |
| 发现 | 无。用户不知道有哪些插件存在 |
| 分发 | 手工。用户从某处下载 `.lcp` 再手工导入 |
| 信任 | 仅声明式权限。清单说「我只读剪贴板」，宿主无法核实 |
| 更新 | 无。应用与插件都要用户自己重新下载 |

因此本设计的主线是：**先补基础设施，再加功能插件**。在闭环跑通之前新增任何功能插件，
都只是往一个封闭容器里继续加东西。

### 1.1 非目标

以下明确不做，列出是为了避免将来反复讨论：

- 评分、评论、下载量排行。它们需要服务端与活跃用户，两者当前都不存在。
- 账号体系与云同步。与「本地优先的桌面框架」定位冲突，且引入隐私与运维负担。
- 插件付费。需要支付与授权服务端。
- 自动化投稿流水线。等真的收到投稿请求再做，过早建设会维护一套没人用的门禁。

## 2. 已经具备的基础（不要重复造）

勘察代码后确认，以下能力**已经存在**，本设计直接复用而不重新发明。这一点很重要：
早期计划曾打算新增一个 `minHostVersion` 字段，而实际上 `engines.loopcore` 已经承担了这个
职责，新增字段只会制造两个互相矛盾的兼容性声明。

| 已具备 | 位置 | 在本设计中的角色 |
| --- | --- | --- |
| 兼容性声明 `engines.loopcore` | `manifest.json` | **就是**兼容性字段，不新增 |
| 权限权威 | Rust `PluginPermission` 枚举（12 项） | 权限的唯一真实来源 |
| 未知权限拒绝安装 | `serde` 反序列化失败 | 天然的准入控制，无需额外校验 |
| 版本比较语义 | `SemVer` / 比较符解析 | 索引中的版本判定直接复用 |
| 分发格式 `.lcp` | zip 容器 | 生态分发包格式不变 |
| 安装流水线 | `PluginManager::install_from_lcp` | 市场页安装复用，不新写 |
| 开发链接 | `source_path` / `dev_source` | 本地开发已可用 |

结论：**本设计不引入新的包格式、不引入新的权限语法、不引入新的兼容性字段。**

## 3. 阶段 0：权限模型

### 3.1 原则

**宿主是权限的唯一权威。** 插件只声明权限的**标识符**，不描述自己的风险等级、严重性
或后果。理由有三条：

1. 风险是安全信息，不能由被审查的一方提供。
2. 同一权限在插件 A 与插件 B 里必须是同一个等级，否则用户无法比较。
3. 远程索引可能被篡改，若风险等级来自索引，攻击者可以把 `process-spawn` 标成「低风险」。

### 3.2 发现的问题：三处独立维护的权限清单

当前存在三份互相独立的权限清单：

| 位置 | 内容 | 性质 |
| --- | --- | --- |
| Rust `PluginPermission` 枚举 + `ALL` | 12 个标识符 | 权威，但只有标识符 |
| TS `PluginPermission` 联合类型 | 12 个标识符 | 手写副本，注释里还记着「哪七项已强制」 |
| TS `PERMISSION_INFO` | 12 项的标签、描述、**风险等级** | 手写副本，风险等级只存在于前端 |

后果是：新增一个权限要改三处，漏掉任何一处都不会报错。`PERMISSION_INFO` 里的风险等级
尤其危险 —— 它是**安全信息**，却只存在于前端、由人工逐条填写、无人校验。

**这就是「风险分级希望是自动化系统」的落点。** 自动化的关键不是把人工填写换成人工填写，
而是让风险等级**成为推导结果而不是输入**。

### 3.3 设计：由效果与作用域推导风险

每一项权限在 Rust 中声明三个客观属性，风险等级由这三者**计算**得出：

| 属性 | 取值 | 含义 |
| --- | --- | --- |
| `effect` | `none` / `read` / `write` / `network` / `execute` | 对目标做了什么 |
| `scope` | `plugin` / `app` / `device` / `remote` / `system` | 影响到哪里 |
| `reversible` | `true` / `false` | 后果能否撤销 |

推导规则（`derive_risk`，单一纯函数）：

```
scope  == system                                   -> high     // 能触及系统层面
effect == execute                                  -> high     // 能跑代码就等于拿到用户账户
scope  == device && effect == write && !reversible -> high     // 设备上不可逆的数据损失
scope  == device || scope == remote                -> medium   // 触及设备资源，或数据离开本机
其余                                                -> low
```

规则按上表**从高到低**短路匹配，第一条命中即返回。这样规则的优先级是显式的，不存在
「两个条件都成立时以哪个为准」的歧义。

第三条规则为什么要带上 `scope == device`：不可逆的写入如果只作用于插件自己的数据
（`scope == plugin`），那是插件对自身数据的处置权，不该因为是「不可逆」就升级为高危。
写成只判断 `effect == write && !reversible` 会把这类情况一并升到 high —— 这是设计过程中
实际出现过的错误版本，公式本身也需要测试，不能只测 12 项权限的快照。

另有一处刻意保留的冗余：当前 12 项权限中 `effect == execute` 规则**不会单独命中** ——
三项 execute 权限同时是 system 作用域，已被更高优先级的规则拦下。保留它是因为两者
正交：将来的代码执行能力若作用于应用内而非系统层面，它必须自动成为 high，而不需要
有人记得回来补一条规则。

### 3.4 设计：公式覆盖不到的地方用显式覆盖，且必须写明理由

纯公式必然有覆盖不到的风险类型。已发现一类：**混淆代理（confused deputy）**。

`plugin-communicate` 的效果是应用内通信、作用域是应用内、可逆 —— 按公式是 `low`。但它
允许一个**没有**文件权限的插件去请求一个**有**文件权限的插件代为操作，从而绕过权限模型。
这类风险不在 `(effect, scope, reversible)` 三个轴的表征能力之内。

因此每一项权限允许一个可选的 `risk_override`，且**必须同时提供一句理由**：

```rust
RiskOverride { risk: Risk::Medium, reason: "可构成混淆代理：无权限插件可借有权限插件代为操作" }
```

测试强制要求：覆盖必须带非空理由。这样「为什么这项特殊」永远有答案，不会退化成随手改。

**公式覆盖 12 项中的 11 项，只有 1 项需要覆盖。** 这个比例本身是公式是否够用的体检指标：
若将来覆盖数量持续上升，说明轴选错了，应当修公式而不是继续加覆盖。

### 3.5 推导结果全表

下表由 `PluginPermission::risk()` 产出，并由快照测试锁定。任何改动（改公式、改某项属性、
加新权限）都会让测试失败，从而强制人工确认 —— 这是「自动化」的安全网。

| 权限 | effect | scope | reversible | 推导 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `storage` | none | plugin | 是 | low | 仅插件私有键值数据 |
| `network` | network | app | 是 | low | 仅回环地址 |
| `network-external` | network | remote | 是 | medium | 数据离开本机 |
| `notification` | write | app | 是 | low | 应用内提示 |
| `clipboard` | write | device | 是 | medium | 读写系统剪贴板 |
| `filesystem-read` | read | device | 是 | medium | 读取文件信息 |
| `filesystem-write` | write | device | **否** | high | 可造成不可逆的数据丢失 |
| `filesystem-scoped` | write | device | 是 | medium | 限定在授权目录内 |
| `plugin-communicate` | network | app | 是 | low → **medium** | **覆盖项**：混淆代理 |
| `native-module` | execute | system | 否 | high | 可绕过全部宿主约束 |
| `dev-tools` | execute | system | 否 | high | 可读写运行时内部状态 |
| `process-spawn` | execute | system | 否 | high | 权限等同于用户账户 |

与旧的手写表相比有两处变化，都是修正而非退步：

- `filesystem-write`：`high` 保持不变，但现在由 `reversible = false` **推导**出来，而不是
  人工标注。
- `plugin-communicate`：`medium` 保持不变，但现在有了明确理由。

也就是说：**手工表里的等级一个都没变，变的是它们从输入变成了输出。** 这是本次改造
行为等价的证据。

### 3.6 强制状态也必须是元数据

权限除了「多危险」，还有「宿主到底管不管」。当前文档用散文说明「七项已强制、五项未强制」，
代码里则是散落的 `require_permission` 调用。两者会漂移。

因此在同一份元数据里记录 `enforcement`：

| 取值 | 含义 |
| --- | --- |
| `host` | 后端命令检查，前端绕不过去 |
| `frontend` | 前端接口检查，可降级为空实现 |
| `none` | 已解析但当前不改变任何行为 |

`enforcement == none` 必须在界面上如实标注。**让用户以为某项权限受管控，而它其实不受管控，
比不告诉他更危险** —— 他会基于一个错误的前提做决定。

### 3.7 粗粒度优先，细粒度如何演进

当前权限标识符是粗粒度的，且已发布，因此**标识符本身不可变**。

关键约束：清单的 `permissions` 是 `Vec<PluginPermission>` 枚举反序列化，**使用冒号分隔的
写法（`filesystem:read`）会导致整份清单解析失败**。因此细粒度**不能**通过给标识符加命名空间
来实现。

演进方式：**新增字段，永不修改已有标识符的含义。**

```jsonc
{
  "permissions": ["filesystem-read"],          // 粗粒度能力，保持原义
  "permissionScopes": {                         // 将来新增，可选
    "filesystem-read": ["${DOCUMENTS}"]         // 限定到具体范围
  }
}
```

这样：旧插件不含 `permissionScopes`，等价于「不限定」；新宿主能表达细粒度；两者共存于
同一清单版本，无需破坏性变更。`filesystem-scoped` 这个已有权限正是该方向的雏形。

### 3.8 权限升级策略

插件更新时，新版本的权限集合可能与已安装版本不同。策略：

| 情形 | 行为 |
| --- | --- |
| 权限集合是旧集合的**子集**（权限变少） | 静默更新。减少权限无须确认 |
| 权限集合**完全相同** | 静默更新 |
| 新增了 `low` 权限 | 静默更新，但在更新记录中标注 |
| 新增了 `medium` / `high` 权限 | **弹窗列出新增项与各自风险，需明确确认** |
| 用户拒绝确认 | **不安装新版本，保留旧版本**。不卸载、不回滚、不部分应用 |

「拒绝则保持旧版本」意味着更新流程必须是**原子的**：确认发生在下载与安装之前，或在安装
提交之前。半个新版本（代码已换、权限未确认）是必须避免的状态。

另外，新增权限的**数量**不决定是否确认，**等级**才决定。新增十个 `low` 权限的插件不应该
比新增一个 `high` 权限的插件更受阻拦。

### 3.9 未知权限的失败安全

遇到宿主注册表里没有的权限标识符时，一律按 **`high`** 处理，并显示原始标识符与
「宿主未提供该权限的元数据」说明。

理由：未知权限既可能是拼写错误，也可能是来自更新版宿主的、当前宿主尚未理解的权限。
两种情况下都不应该给出「低风险」这一安慰性判断。失败方向必须是保守的。

注意这与 Rust 侧的现状不同：**Rust 会直接拒绝安装含未知权限的清单**，因此这个前端兜底
主要服务于**市场页**（展示尚未安装的插件，其索引可能来自更新的宿主）。

## 4. 阶段 1：索引格式 `index.json`

### 4.1 设计目标

索引是**整个生态的公共接口**。一旦有插件发布出去，改它就是破坏性变更，因此必须在发布
任何插件之前定对。这是它排在实现之前的原因。

索引要回答的问题只有：**有哪些插件、各自有哪些版本、从哪里下载、完整性如何。**

索引**不**回答：风险等级、权限语义、兼容性是否成立。这三者由宿主根据自己的注册表判断。

### 4.2 结构

```jsonc
{
  "schemaVersion": 1,
  "plugins": [
    {
      "id": "com.modulith.sample.notes",
      "displayName": "文本速记",
      "summary": "随手记下想法、待办与片段。",
      "author": { "name": "环理论", "url": "https://github.com/Rinntheor" },
      "license": "MIT",
      "categories": ["效率"],
      "keywords": ["notes", "memo"],
      "icon": "plugins/notes/icon.svg",
      "source": "plugins/notes",          // 省略表示仅分发 .lcp，源码不公开
      "latest": "1.0.1",
      "versions": [
        {
          "version": "1.0.1",
          "tag": "notes-v1.0.1",
          "engines": { "loopcore": ">=1.0.0" },
          "permissions": ["storage"],
          "package": {
            "path": "dist/com.modulith.sample.notes-1.0.1.lcp",
            "size": 8123,
            "sha256": "…64 位十六进制…"
          }
        }
      ]
    }
  ]
}
```

字段设计要点：

- **路径而非完整 URL。** 索引只记仓库内相对路径，完整 URL 由客户端按 CDN 模板拼接。
  这样换 CDN、加镜像、切测试环境都不需要改索引内容。
- **`tag` 逐版本记录。** 因为 jsDelivr 对 tag URL 的缓存是永久的（见 4.4），每个版本必须
  有自己的不可变 tag，否则改一个插件会污染其它插件的缓存。
- **`source` 的有无决定「源码可见」标记。** 这对应「非重要插件源码可见」的决策：公开源码
  的插件填该字段，市场页显示「源码可见」并可跳转；不填则只分发 `.lcp`。用一个字段的存在性
  表达两种分发形态，不需要额外的枚举。
- **`permissions` 只记标识符。** 不记标签、不记风险等级 —— 见 3.1。
- **`sha256` 必须有。** 见 4.5。
- **`schemaVersion` 必须有。** 将来结构变更时，客户端才能识别并给出可读提示，而不是
  解析失败后表现成「网络错误」。
- **没有时间字段。** 早期草案里的 `generatedAt` 与 `publishedAt` 在实现时都去掉了，
  理由见 4.6。

### 4.3 索引由清单生成，不手工维护

`index.json` 必须是**构建产物**：读取各插件目录的 `manifest.json`，加上分发信息（路径、
大小、哈希、tag）生成。

手工维护索引的错误模式是可预测的：改了清单版本忘了改索引、算了哈希忘了更新、删了插件
忘了删条目。这些都会表现为客户端行为异常，而排查方向会指向客户端代码。

**没有任何字段是只在索引里存在的** —— 除分发信息外，其余全部从清单抄来。这条约束保证了
索引永远不可能成为第二份真相。

### 4.4 分发与访问：GitHub + jsDelivr，双路

存储用 GitHub 仓库（免费、有版本历史、可回溯），加速用 jsDelivr（免费 CDN，国内有节点）。

关于 jsDelivr 的缓存语义，两类文件必须走**不同的 URL 形式**：

| 文件 | URL 形式 | 缓存 | 原因 |
| --- | --- | --- | --- |
| `index.json` | `…/gh/Rinntheor/modulith-plugins@main/index.json?t=<时间戳>` | 不缓存 | 几 KB，必须即时反映新插件与新版本 |
| `.lcp` 包 | `…/gh/Rinntheor/modulith-plugins@<tag>/dist/xxx.lcp` | 永久 | 内容不可变，永久缓存是最优解 |

关键点：tag URL 在 jsDelivr 上被当作不可变内容永久缓存，因此**发布后绝对不能移动 tag**。
索引附带查询串是为了让每次请求构成不同的缓存键，从而绕过缓存 —— 索引文件很小，不需要
CDN 缓存收益，而「发布后立刻可见」对它至关重要。

> **待实机验证**：jsDelivr 对「分支引用 + 查询串」的确切缓存键行为未经实测。若实测发现
> 查询串不能绕过缓存，退路是索引改从 `raw.githubusercontent.com` 拉取（无 CDN 缓存，
> 但国内可能不可达），或保留 jsDelivr 并接受最长 12 小时的延迟。这个取舍需要真实网络
> 环境才能定，不应凭推测写死。

同时保留**直连 GitHub** 作为兜底：CDN 不可用时降级到原始地址，宁可慢也不要完全不可用。

### 4.5 完整性与它保护不了的东西

索引里每个包记录 `sha256`，客户端下载后本地计算并比对。

必须如实说明它的边界：**哈希保护的是传输过程，不是索引本身。** 若索引被篡改，攻击者可以
同时改掉哈希。也就是说，哈希能挡住 CDN 缓存污染与下载损坏，**挡不住索引被替换**。

真正解决「索引可信」需要**对索引签名**，而这需要一对密钥。这正是阶段 6（应用自动更新）
必须引入的东西 —— Tauri 的更新签名机制用的是 minisign 密钥对。因此：

**索引签名与应用更新签名共用同一套密钥与同一个信任根**，而不是各自维护一套。这条已经
落地，见 9.5。

### 4.6 打包必须可复现

索引里的 `sha256` 只有在**打包输出确定**时才有意义：同一份源码重复构建必须得到同一串
字节。否则哈希只能证明「这个包没被改动过」，不能证明「这个包就是这份源码构建出来的」——
而后者才是它的用途，让用户能核对下载到的东西确实来自公开的源码。

因此打包器必须做到：条目按名称排序、时间戳固定（不用当前时间）、压缩级别固定、对压不小的
数据回退为不压缩。

对应的纪律：**不要在包内写入任何随时间变化的字段**（构建时间、构建主机、修订号）。一旦写了，
上面全部努力作废，而症状是「每次构建哈希都不一样」，很容易被当成随机故障而不是设计缺陷。

插件仓库的构建脚本每次打包时会**连打两次并比对字节**，把这条性质从「期望」变成每次构建
都验证的不变量。

**同理，索引里也没有时间字段。** 早期草案有 `generatedAt`（索引生成时间）与 `publishedAt`
（每个版本的发布时间），实现时都去掉了：

- `publishedAt` 在本流程里**取不到**。发布顺序是「生成索引 → 提交 → 打 tag」，索引生成时
  tag 还不存在，那个时间自然也不存在；改成从 git 读又会让同一份仓库在不同机器上产出不同
  的索引（时区、tag 是否已存在），`--check` 随之失去意义。
- `generatedAt` 一旦写入「当前时间」，索引会在每次重新生成时都产生差异，于是「索引是否
  已经过期」这个判断失去了依据 —— 而那正是 `--check` 要回答的问题。

需要「更新于」这类信息时，应当由客户端根据它自己看到的变化推导，或等将来有了真正的发布
流水线再由流水线提供，而不是让索引记录一个它无法负责的时间戳。

## 5. 阶段 2：插件仓库规范

### 5.1 两个仓库

按决策，应用与插件生态分仓：

| 仓库 | 内容 |
| --- | --- |
| `Rinntheor/modulith-desktop` | 应用本体（现有仓库，不变） |
| `Rinntheor/modulith-plugins` | 插件源码、构建产物、索引 |

分仓的理由：Release 列表与 issue 各自独立；插件生态可以有自己的贡献者与许可证；
应用仓库不会被插件二进制文件污染。代价是索引要跨仓库引用 —— 但因为索引只记**相对路径**
（4.2），客户端只需知道「插件仓库地址」这一个常量，跨仓成本极小。

### 5.2 目录结构

```
modulith-plugins/
  index.json                 构建产物，入库（客户端唯一入口）
  package.json               只为声明 type=module 与两条脚本，无依赖
  .gitattributes             强制 LF，见 5.5
  README.md
  CONTRIBUTING.md
  docs/                      目录规范、发布流程
  scripts/
    build.ts                 打包、并入索引、复核；--check 只校验
    manifest.ts              清单的形状校验
    zip.ts                   确定性 zip 写入器
  plugins/
    hello/                   参考插件，目录规范的可执行形式
      manifest.json          权威清单（沿用现有格式）
      index.js
      index.css
      icon.svg
      README.md
      LICENSE
  dist/                      构建产物 .lcp，入库
    com.rinntheor.modulith.hello-1.0.0.lcp
```

**源码与产物都入库。** 产物入库是为了让 jsDelivr 能直接代理（它只能代理仓库内容，不能
代理 Release 附件），也为了让「某个版本到底发了什么」永远可 `git checkout` 复查。

### 5.3 tag 约定

每个插件的每个版本一个不可变 tag：

```
<插件短名>-v<版本号>        例如 notes-v1.0.1
```

插件短名取 `manifest.json` 中 `name` 的最后一段（`com.modulith.sample.notes` → `notes`）。
不用完整反向域名是因为 tag 里出现多个点会引起工具混淆。

**已发布的 tag 永不移动、永不删除。** 索引里的 `tag` 字段直接对应缓存键，移动 tag 会让
新老用户拿到不同内容却看到同一个版本号。

### 5.4 公开与非公开

`plugins/` 目录下的插件源码可见，是默认形态。不公开源码的插件**不放进这个仓库** ——
它可以是另一个私有仓库，只需把 `.lcp` 与索引条目以相同结构发布，客户端无需区分。

这一点是刻意的：**客户端不对「源码是否可见」做任何信任假设。** 源码可见是给用户的便利，
不是安全机制 —— 用户不会去读代码，而读得懂代码的人本来就能自己构建。

### 5.5 行尾必须是 LF

仓库根有一份 `.gitattributes`，强制所有文本文件以 LF 存储与检出：

```
* text=auto eol=lf
*.lcp binary
```

这不是风格偏好，是 4.6 的直接推论。仓库承诺「仓库里的文件」与「用户装到的 `.lcp`」逐字节
一致；而 Windows 上 `core.autocrlf=true` 是常见默认值，它会在检出时把 LF 转成 CRLF。于是
打包出来的 `index.js` 与仓库内容不是同一串字节，客户端校验 `sha256` 失败 —— 表现成一个
「文件可能已被篡改」的安全告警，真实原因只是换行符。

这类问题的排查成本远高于预防成本：告警指向安全，实际是构建环境差异。

## 6. 阶段 3：打包与索引生成（已实现）

插件仓库的 `scripts/` 下有三个文件，零依赖，由 Node 直接执行 TypeScript：

| 文件 | 职责 |
| --- | --- |
| `build.ts` | 校验清单、打包、并入索引、复核；`--check` 只校验不写盘 |
| `manifest.ts` | 清单的**形状**校验 |
| `zip.ts` | 确定性 zip 写入器 |

`build.ts` 做四件事，任何一步失败都不写出产物：

1. **校验全部清单**，问题一次性列全，而不是「改一个跑一次」。
2. **打包**为 `dist/<插件 ID>-<版本号>.lcp`，用自写的 zip 写入器（4.6）。
3. **并入索引**：保留历史版本条目。工作区里已不存在的插件目录会被整体移出索引并打印警告 ——
   静默消失是最难排查的一类问题。
4. **复核**：索引引用的每个包都必须存在，且哈希与记录一致。这一步能抓住「手工改过索引」与
   「`dist/` 里的包被删或被换」两类问题。

发布流程：

```bash
node scripts/build.ts
git add -A && git commit
git tag hello-v1.0.0
git push origin main --tags
```

**清单校验只查形状，不查权限成员资格。** 权限名是否真实存在，由宿主的权限注册表决定
（`PluginPermission` 枚举，未知权限导致清单反序列化失败）。在本仓库再维护一份权限名单就是
第二份副本，必然漂移。本仓库只拦「写法不可能合法」的情况，其中最重要的是冒号写法
（`filesystem:read`）—— 它会让宿主整份清单解析失败，而用户看到的只是「清单非法」，排查
成本与错误本身不成比例。

**没有自动化 CI。** 当前规模下（个位数插件、单一维护者）CI 的收益低于它带来的密钥管理与
调试成本。等需要多人投稿时再引入。`--check` 的存在就是为了那一天：它可以直接当门禁。

## 7. 阶段 4：客户端市场页（已实现）

内建模块 `src/modules/pluginMarket/`，作为设置的第四个分页（设置 → 市场）挂载，与「插件」
并列。它**不是插件** —— 需要网络与索引解析，属于框架能力。

| 职责 | 实现 |
| --- | --- |
| 拉取索引 | 后端 `fetch_registry_text`，按 4.4 的双路策略优先 jsDelivr 带查询串，失败自动降级直连 |
| 渲染列表 | 关键词搜索 + 分类筛选。**不做评分与排行** |
| 权限展示 | 由**本地**宿主的权限注册表渲染标签与风险，索引提供的 `permissions` 只提供标识符 |
| 详情页 | 右侧抽屉，视觉与动效对齐已安装插件的详情抽屉：完整权限说明、版本与来源信息、发布者的 README |
| 安装 | 后端 `install_plugin_url_verified`：下载 → 校验 `sha256` → 安装，一步完成 |
| 源码入口 | `source` 字段存在时提供跳转链接 |

三处在实现时与本节原计划不同，都是刻意的：

**1. 安装没有复用 `install_plugin_package`，而是新增了 `install_plugin_url_verified`。**

原计划是「下载 → 校验 → 调用已有的安装命令」，但那要求先把字节写到临时文件、再把路径回传，
多一次 IPC 与一次磁盘往返，而且校验与安装之间存在一个可被替换的窗口。新命令把下载、校验、
安装合成一个原子操作，校验失败时不产生任何落盘文件。

**2. 兼容性不做客户端判定，只展示声明范围。**

原计划是「用本地 `engines.loopcore` 解析器判断」。实现时放弃了：Rust 侧已经有权威的
`EngineRange` 解析器，在前端再写一个必然漂移；更重要的是现有设计**刻意不把引擎不匹配当作
阻断**（见[清单文件参考](../02-开发指南/插件开发/清单文件参考.md)第 5 节：「语法错误是错误，
兼容性猜测不是」）。市场页显示「需要宿主 >=1.0.0」，真正的判定留给安装时的后端。在一个
刻意不给硬结论的地方加一个硬结论，会与既有取向冲突。

**3. 索引拉取放在后端，不经过 WebView 的 `fetch`。**

后端的 reqwest 客户端已有超时与体积上限，而且不依赖 WebView 的 CORS 与安全上下文行为 ——
那两者在本项目里没有任何自动化覆盖，出问题时的表现是「市场页一片空白」，排查方向会指向
插件系统，而真实原因在网络层。

失败路径：

| 失败 | 表现 |
| --- | --- |
| 索引拉取失败 | 显示可重试的错误，并说明已安装插件不受影响 |
| CDN 失败 | 自动降级直连 GitHub 重试 —— 两条路指向同一个不可变 tag，且后端强制校验哈希，因此切换来源不会拿到不同内容 |
| `sha256` 格式非法 | 报「包非法」：索引写错了 |
| `sha256` 内容不符 | 报「下载失败」，**拒绝安装**，不提供「仍然安装」 |
| 索引 `schemaVersion` 高于宿主支持 | 提示客户端需要更新，不尝试解析 |
| 索引结构非法 | 整体失败并指明是哪个插件的哪一项 —— 索引是脚本生成的，坏条目说明上游真的坏了；跳过只会让问题以「少了一个插件」的形式安静存在，而那种现象会被归因于网络 |

### 7.1 详情页的说明来自发布者写的 README

详情页的「说明」按该版本的**不可变 tag** 从仓库里取 `README.md`，而**不是**新增一个索引
字段。这是刻意的：描述性内容只能有一个来源，发布者改那个文件就等于改详情页。若在索引里
再放一份长描述，两者必然漂移 —— 而「用户在详情页看到的」与「发布者以为用户看到的」不一致，
是最难被发现的一类问题。

因此分工是：

| 内容 | 来源 | 用途 |
| --- | --- | --- |
| `summary` | 清单的 `description` | 列表里的一句话，保持短 |
| 长说明 | 仓库里的 `README.md` | 详情页 |
| 权限、版本、体积、哈希 | 索引 + 本地权限注册表 | 列表与详情页 |

三处实现细节：

- **按 tag 取，不按 `main` 取。** 显示的是"这个版本的说明"，与版本号标识一份确定内容
  的约定一致。
- **纯文本展示，不渲染 Markdown。** 与已安装插件的详情抽屉保持一致 —— 项目里没有 Markdown
  渲染依赖，只给市场加一个渲染器会让同一个 README 在两处长成两个样子。渲染 Markdown 是
  一个需要同时改两处的独立决定，不在本阶段。
- **取不到时显示「暂无说明」，不让详情页失败。** 安装决策所需的信息（权限、版本、来源）
  在索引里已经齐了，说明只是补充。源码不公开的插件本来就没有 README。

这条也反过来约束了发布侧：**`README.md` 是插件的用户可见页面**，不是给开发者看的附带
文件。目录规范里已经要求每个插件必须提供它，现在它的用途变得具体了。

### 7.2 安装前的权限确认

安装前的权限确认是**唯一**让用户做出判断的时机：插件代码以本应用的权限运行，而权限是
声明式的。确认框把每项权限的标签、说明与风险等级摊开，中高风险单独高亮，并明确写出
「宿主尚未强制这一项」以及「权限只能由插件代码自行遵守」。

顺带修正：`ModuleEmbed` 原先的 glob 写死了文件名 `Plugins.tsx`，因此只能内嵌入口文件恰好
叫这个名字的模块。现在改为「显式登记表 + 显式 glob 列表」，并去掉了按模块 ID 分支的
`switch`。新增一个可内嵌模块需要在登记表与 glob 列表**两处**各加一项 —— 这是 Vite 要求
glob 模式为字面量带来的重复，无法消除，已在代码注释里写明。

## 8. 阶段 5：插件更新（已实现）

复用阶段 4 的索引与校验逻辑，增加「比对已安装版本」。更新完成后调用现有的
`reloadPluginRuntime()`，不新写重载路径。

**不做自动静默更新。** 插件能执行任意代码，静默替换用户已信任的代码是不可接受的风险，
而用户对「更新」的心理预期本来也包含知情。

### 8.1 五种状态，而不是「有新版本 / 没有」

市场页把本机版本与索引最新版本的关系分成五类，因为把它们合并成两类会误导用户：

| 状态 | 界面 | 为什么单独成一类 |
| --- | --- | --- |
| 未安装 | 显示「安装」 | —— |
| 与索引一致 | 「已安装 x.y.z」 | —— |
| 索引更新 | 「可更新 a → b」+「更新」 | —— |
| **本机更新** | 「已安装 x.y.z（比仓库里的新）」 | 用户可能从 `.lcp` 装了比索引更新的版本。不区分的话，「重新安装」会被当成升级，实际是**降级** |
| **开发链接** | 说明文字，**不提供**更新按钮 | 从市场更新会把它从「实时读取源目录」换成「安装目录里的副本」，静默丢掉用户刻意选择的工作方式。它本来也不需要更新 —— 改了源码点刷新即生效 |

### 8.2 权限差异决定是否打断用户

规则见 3.8，实现落在 `planUpdate()` 一处：权限变少、不变、或只新增**低风险**权限时不打断；
只要新增了中/高风险权限就弹确认框，且拒绝时保留旧版本。

判断依据是**等级而非数量**：新增十个低风险权限不该比新增一个高风险权限更受阻拦。

更新确认框只把**新增**的权限放在显眼位置，完整列表退到下面。理由是那些既有权限用户已经
同意过了，把它们一并算进「需要注意」只会稀释真正新增的那几项 —— 而那个判断正是这次确认
要用户做的。

「静默」指不打断，**不是不告诉**：低风险权限的更新完成后，提示里会列出新增了哪几项。
权限集合变了而用户完全不知情，下次他看到权限列表时会以为一直是那样。

### 8.3 版本比较放在前端，并配一个可运行的验证脚本

判断「有没有更新」需要比较版本号，而前端没有现成的实现（后端有一份，用于清单校验与
引擎范围）。重新实现一份是刻意的：semver 的优先级规则是一份**公开标准**，不是本项目的
约定 —— 真正会出问题的是「其中一份实现写错了」，而不是「规则变了」。

这个问题用测试解决，而不是用共享代码解决。前端没有测试框架，因此
`scripts/check-semver.ts` 就是它的测试（`pnpm check:semver`），用例取自 **semver.org 的
官方优先级链**，另加两条防退化用例（`2.0.0 < 10.0.0`、`1.9.0 < 1.10.0` —— 按字典序比较
的实现会在这里失败）。与哈希校验用公开向量是同一个思路：拿实现校验实现，在规则理解错的
时候会一起错，测试照样全绿。

### 8.4 检查时机：目前由市场页触发

进入「设置 → 市场」时才拉取索引并比对，**没有后台轮询，也没有在启动时拉取**。

理由：应用启动不该依赖网络。阶段 4 之后启动流程已经不再有网络请求，为更新提示加一个会
让「断网时启动变慢或卡住」成为一个真实问题，而收益只是早几秒知道有更新。

代价是明确的：**从不打开市场页的用户看不到更新提示。** 这与第 12 节记的「应用内更新检查
的触发时机未定」是同一个问题，此处只是给出了一个保守的临时答案 —— 等真的需要主动提示时
（例如用户反馈"不知道有新版本"），再决定是启动时拉一次、还是提供手动检查入口。

## 9. 阶段 6：应用自动更新（已实现）

用 Tauri 2 官方的 updater 插件。机制：应用内置**公钥**，发布方用**私钥**签名一个
`latest.json`（含新版本号与安装包地址），客户端拉取、比对版本、下载、验签、安装。

实现落在四处：`tauri.conf.json` 的 `plugins.updater`（endpoints 与 pubkey）、
`capabilities/default.json` 的 `updater:default`、生成器模板里的插件注册、
`src/services/appUpdater.ts` 与「设置 → 关于 → 软件更新」卡片。发布侧是
`scripts/release-manifest.ts`（清单怎么生成）与 `scripts/release.ts`（发布准备一条命令，
`pnpm release`）。

还有一处配置容易漏：`bundle.createUpdaterArtifacts` **默认为 false**，此时构建根本不会
产出 `.sig`。它的症状出现在很远的地方（生成清单时才报缺少签名），因此被显式写进配置，
并在缺签名时的报错里直接点名。

密钥的处置方式（备份、口令、轮换、泄露）写在
[版本管理](../02-开发指南/版本管理.md)第 7 节 —— 那是需要照着做的流程，不属于设计文档。

### 9.1 什么时候检查更新

「应用内置了更新能力」和「用户知道有新版本」是两件事：不主动查，用户就得自己想起来去
「关于」页点一次，而那几乎不会发生。

因此**启动时自动检查一次**，发现新版本就发一条通知（见
[前端架构](../01-架构/前端架构.md) 5.1.1：更新通知与普通通知是分开呈现的）。

三条边界是刻意划的：

| 决定 | 理由 |
| --- | --- |
| 默认开启，但用户可关（设置 → 关于） | 关掉就**不发任何请求**，而不是"发了但不提示"。检查本身只是向 GitHub 的 release 地址发一次 GET，不携带本机信息，因此默认开启是合理的；但决定权留给用户 |
| 24 小时内不重复 | 启动是高频动作，没有节流就变成对 release 地址的轮询。判断逻辑是纯函数，单独放在 `src/utils/updateCheck.ts` 并有 13 条断言（`pnpm check:update`） |
| **检查失败不发通知** | 用户没有发起这个动作。把一次网络抖动变成「检查更新失败」只会训练用户忽略通知，而通知一旦被忽略，那条真正重要的也就没了。失败只写日志，手动检查才在界面上报错 |

时间戳只记录「**得到结论**」的时刻，不记录「尝试过」：断网时留空，下次启动会重试 ——
反过来的话，一次离线启动就会让自动检查静默失效一整天。而时间戳在**未来**（时钟被回调、
或文件被手工改过）时按「没检查过」处理，不是「刚检查过」：后者会让自动检查被永久跳过。

检查**不在启动步骤表里**，而是在应用界面就绪之后触发。这一步要联网，放进 boot 会让启动
界面多等一次网络超时，而"有没有新版本"不该拖慢进入应用。

「查看更新」只把用户送到「设置 → 关于」的更新卡片，**不替他点下载安装**：安装会关闭并
重启应用，那不该由一次通知点击触发。

### 9.2 唯一不可逆的东西是密钥

一旦发布了带公钥的应用版本，那个公钥就固化在所有已安装用户那里。

**私钥丢失 = 再也无法向老用户推送更新**，只能让他们手工重装。因此私钥必须在第一次发布
**之前**就确定备份方式（离线介质 + 至少一份异地副本），而不是发布之后再补。

这一步没有技术补救手段，属于流程纪律。

有一个反直觉的推论值得单独说：**旧密钥不能销毁。** 密钥泄露时，唯一能把用户迁移到新密钥
的办法是再用旧密钥签一个「迁移版本」；如果旧密钥已经毁掉，就连这条路也没有了。

### 9.3 为什么排在插件分发之后

应用更新与插件分发走的是同一套基础设施：GitHub 存储 + 哈希/签名校验 + 版本比对 + 网络
失败处理。

先用插件分发把这条路走通、踩完坑（缓存延迟、下载失败、校验不通过如何提示），再拿这份
经验改应用更新。反过来做的话，会在**发布流程改造**这个最麻烦的环节上第一次遇到这些
问题，而此时出错的代价是「用户更新不了」，而不是「插件装不上」。

### 9.4 更新清单只写具体的安装包类型键

`latest.json` 的 `platforms` 里只写 `windows-x86_64-msi` 与 `windows-x86_64-nsis`，
**不写 `windows-x86_64` 兜底键**。

理由来自一个容易忽略的实现细节：tauri 在构建时把安装包类型以**二进制补丁**写进可执行
文件（`__TAURI_BUNDLE_TYPE`），因此真实安装的应用一定知道自己是被哪个安装器装的。兜底键
一旦被用到，说明类型未知（开发构建）——那时按兜底键装另一种安装器，会让用户机器上留下
两份安装记录。**失败要响亮，而不是静默装错。**

### 9.5 索引签名（已实现）

应用更新引入的签名密钥，同时解决了 4.5 遗留的「索引可信」问题：**用同一对密钥对
`index.json` 签名**，客户端验签通过才信任索引内容。哈希保证传输完整，签名保证来源可信。

实现分三处：

| 环节 | 位置 |
| --- | --- |
| 生成签名 | 插件仓库根目录的 `index.json.sig`，由 `tauri signer sign index.json` 产出 |
| 校验签名 | 后端 `verify_plugin_index`（`signature.rs`），公钥取自 `tauri.conf.json` 的 `plugins.updater.pubkey` |
| 拒绝不可信索引 | 前端在**解析之前**验签，失败则整个市场拒绝加载 |

四处刻意的设计：

**一、公钥只有一份。** 它已经随应用发布在 `tauri.conf.json` 里，因此 `signature.rs` 从
运行时配置读取，而不是在代码里再写一份。两处保存必然漂移，而漂移的表现是「应用更新能用、
插件市场打不开」这种极难归因的组合。

**二、缺公钥报错，不放行。** 只要有一种情况能让校验静默通过，构造那种情况就是绕过校验的
方法。测试覆盖了缺失、空串、纯空白、类型不对四种。

**三、验签在解析之前。** 索引是信任根（它同时给出「装什么」与「校验哪个哈希」），先解析
一份不可信的内容等于让攻击者的输入先进入解析器。而且解析失败与验签失败要给不同的提示，
混在一起会让排查方向跑偏。

**四、`allow_legacy` 与 updater 保持一致。** 两者接受的是同一个 `tauri signer` 的产物，
一处严格一处宽松就会出现「更新包能验、索引验不了」这种只在一半路径上失败的现象。

**排序要求（会真的踩到）**：客户端要求签名之后，**未签名的索引会让市场对所有人打不开**。
因此插件仓库的构建脚本 `--check` 会把「索引改了但没重新签名」当作错误拦下来，写模式也会
打印签名命令。发布顺序必须是：**先签索引、再发要求验签的客户端。**

### 9.6 一处无法自动验证的地方

验签的**通过路径**无法用单元测试覆盖：`minisign-verify` 只验不签，构造一个合法签名需要
私钥。因此单测只覆盖了失败路径（base64 非法、非 minisign 内容、公钥缺失）。

通过路径的验证方式是**真实索引**：签名之后由应用校验一次，再把签名换成另一把密钥的产物
确认被拒绝。这一段由人工完成，记在这里以免被当成"已经测过"。

## 10. 安全边界与阶段划分

### 10.1 声明式与强制式的区别

当前权限是**声明式**的：能**告知**用户、能作为**准入**依据，但**拦不住**恶意插件。原因是
插件以 IIFE bundle 形式经 `<script>` 注入，与宿主界面代码运行在同一个 realm 里，能接触到
宿主暴露的一切。

要真正隔离，需要把插件放进 Web Worker / iframe / 独立进程，通过消息通道通信。这意味着
一整套宿主 API 的 RPC 协议，且**现有插件全部需要改造**。

因此纪律是：**只有真的开始接受第三方投稿时，才做强制式隔离。**

在只有维护者自己的插件时做沙箱，是为一个尚不存在的第三方生态付出重构全部插件的代价。

**1.2.0 的贡献模型把这件事的成本结构改了（见[已知问题与技术债](../06-项目/已知问题与技术债.md)第 7.30 节）。** 此前「现有插件全部需要改造」这句话是真的：宿主必须先执行插件，才知道它注册了什么，而这件事在跨 realm 之后就是一次远程调用。声明式贡献把「界面形状」搬进了清单，于是宿主在任何执行发生之前就画得出完整界面。

因此阶段 7 的剩余工作量比这段话写下的要小 —— 但它**没有变成零**：

| 仍然要做的 | 为什么 |
| --- | --- |
| `registerModule` / `registerCommand` 改成 RPC | 它们传的是 React 组件与函数，跨不了 realm。声明式贡献已经把它们变成「按 ID 调用」，但 RPC 本身还得写 |
| `ctx` 服务改成可序列化调用 | storage / http / notifications / events / launcher / icons / shell / fileDrop / audio / settings 本来就是「传值进、返回值出」，改造量小 |
| 存量插件补 `contributes` | 它们目前仍走旧式路径（9 个，全部实测归类为「旧式 / 加载期执行」） |

**不变的判断：在只有维护者自己的插件时不做强制式隔离。** 上面这份清单描述的是「将来要做时能少做多少」，不是「现在可以开始做」。

### 10.2 分阶段的信任模型

| 阶段 | 信任对象 | 采取的措施 | 明确承认挡不住的 |
| --- | --- | --- | --- |
| 一 | 只有维护者自己的插件 | 哈希、HTTPS、tag 不可变、人工审查索引 | 索引被替换、维护者账号被盗 |
| 二 | 少量受邀投稿者 | 增加：索引签名、投稿审查、插件来源可追溯 | 恶意代码（仍是声明式权限） |
| 三 | 开放投稿 | 增加：强制式沙箱、按权限隔离 | —— |

**关键纪律：不要用阶段三的措施去解决阶段一的问题，也不要在阶段一就假装拥有了阶段三的
保障。** 当前所有权限都是声明式的，界面上不应出现任何暗示「宿主已限制该插件」的措辞。

### 10.3 交付形态的信任边界

必须向用户说清：**应用安装包带有签名（阶段 6 之后），插件包不带签名。** 插件的可信度
取决于它的来源，以及「谁在维护索引」。把这两件事混为一谈，会让用户高估插件的可信度。

## 11. 阶段与分支计划

每阶段一个分支，**合完再开下一个**。理由：阶段 2 到 4 耦合紧密（仓库结构决定打包脚本，
打包脚本决定市场页如何解析），并行开发会让冲突集中爆发。串行慢一点，但每一步都干净。

| 阶段 | 分支 | 内容 | 前置 |
| --- | --- | --- | --- |
| 0 | `feat/plugin-ecosystem` | 权限元数据与自动推导 + 本文档 | 无 |
| 1 | 同上 | 索引格式定义（本文档第 4 节） | 无 |
| 2 | `chore/plugin-repo-bootstrap` | 新建插件仓库与目录规范 | 阶段 0 |
| 3 | `feat/plugin-build-script` | 打包与索引生成脚本 | 阶段 2 |
| 4 | `feat/plugin-market` | 客户端市场页 | 阶段 3 |
| 5 | `feat/plugin-update-check` | 插件更新检查 | 阶段 4 |

阶段 0 与 1 是**纸面工作**，不产出可见功能，容易被低估。但它们的产物是**接口**，接口错了

## 12. 未决问题

诚实记录当前没有答案的问题，避免它们被默认当作已解决：

1. **jsDelivr 的缓存键行为未经实测**（4.4）。若查询串不能绕过缓存，需要重新选择索引的
   获取路径。
2. **索引签名放在阶段 6 是否太晚 —— 已实现，但留下了代价。** 在此之前发布的客户端不验签，
   而验签要求索引已签名。因此**必须先签索引、再发要求验签的客户端**，顺序反了会让市场对
   所有人打不开。这条顺序约束由插件仓库的 `build.ts --check` 兜住（它把「索引改了但没
   重新签名」当作错误）。
3. **跨仓库的清单规则复用 —— 已解决。** 插件仓库只校验清单的**形状**，不校验权限的成员
   资格：成员资格由宿主的权限注册表决定。两边因此不需要共享代码，也不会漂移。代价是权限名
   拼错要到安装时才被发现。真正的跨仓库契约测试做不到（没有 CI、没有网络），这一点如实
   记在这里，不要以为它被覆盖了。
4. **权限确认弹窗的措辞未定。** 它需要在用户不理解权限模型的前提下传达风险，是纯产品问题。
5. **应用内更新检查的触发时机未定**（启动时 / 手动 / 定时）。定时需要一个常驻调度，
   而当前架构没有这个能力。
