# 插件架构与 API：v1.5.0 范围

> 状态：**已定稿，待实施**。本文件是 v1.5.0 的范围与取舍依据。
> 定稿时确认的三个分叉见文末「决策记录」。

---

## 0. 一句话结论

**v1.5.0 只买「诚实」，不买「隔离」。** 权限列表要说真话，跨进程能传的东西要提前立好规矩；
真正的访问控制留给 v2.0 的进程/WebView 隔离。

---

## 1. 为什么不能承诺隔离

这不是保守，是这个项目自己已经写下的账。见
[已知问题与技术债](../06-项目/已知问题与技术债.md) §4.1 与 §4.4：

> 它**不是**插件之间的隔离边界 —— 命令的 `id` 参数来自调用方，插件直接
> `invoke('plugin_storage_get', { id: '别的插件', key: 'x' })` 仍能读取他人数据。
> 要堵住它，后端必须知道「谁在调用」，而这在「插件与宿主共享同一个 WebView 与
> JS 上下文」的模型下无法实现。

同一条道理对**每一项**权限都成立，不是存储特有的：

| 权限 | 名义上的管控点 | 实际绕过方式 |
| --- | --- | --- |
| `network` | `ctx.http` | 直接 `fetch`（回环地址甚至在 CSP 里就是放行的） |
| `process-spawn` | `ctx.launcher` | 直接 `invoke('plugin_launch_program')` |
| `filesystem-read` | `ctx.icons` / `ctx.audio` | 同上，`id` 参数由调用方给 |
| `plugin-communicate` | `ctx.events` | 直接操作 `window` 上的宿主对象 |

**根因只有一个：插件代码与宿主代码在同一个 JS realm 里，宿主无法区分「谁在调用」。**
这也解释了 §4.2 里 `SandboxLevel`（L0–L3）为什么被删掉，原话是：

> 不要在阶段一就假装拥有了阶段三的保障。

v1.5 若承诺「访问控制」，就是换个名字把 `SandboxLevel` 请回来。

## 2. 五个目标

### 目标 1（最高优先）：跨边界数据必须可结构化克隆

**这是唯一一条「现在不守、v2 必炸」的约束。**

沙箱化的本质是插件与宿主之间只剩**消息传递**，而消息只能携带结构化克隆能表达的东西 ——
**不能带函数、类实例、原型链、DOM 节点**。因此今天跨边界传的每一个成员，要么现在改成
可克隆的，要么 v2 时推倒重来。

当前违反项（穷举）：

| 现状 | 位置 | 为什么传不过去 |
| --- | --- | --- |
| `Modulith.React` —— **宿主那个 React 实例** | `pluginContributions.ts` `HOST_CAPABILITIES.host` | 类实例，且带闭包 |
| `jsx` / `jsxs` / `Fragment` | 同上 | 函数 |
| `registerModule({ component })` | `PluginModuleRegistration.component` | 函数 |
| `ctx.settings.get()` / `getAll()` —— **同步** | `types/modulith.d.ts` | 跨进程不可能同步 |
| `isAvailable()` —— 同步判定（通知 / 事件 / 拖放 / 设置） | 同上 | 同步 |
| `ctx.disposables.add(fn)` / `Modulith.onDeactivate(fn)` | 同上 | 函数 |
| `useModuleActive()` —— 同步 hook | 同上 | 同步 |
| `ctx.events.subscribe(topic, handler)` | 同上 | 函数（但**返回**的是函数，入参的 handler 本身允许） |

改写方向（两条，举例说明而非最终形态）：

- **同步 → 激活参数里的快照。**
  `ctx.settings.get()` 现在能顶层同步读，是因为设置值在激活前就随贡献目录读好了。
  把这个「预取」从「随时可同步调用」改成 **`activate()` 的参数** —— 既保住「顶层可用」，
  又不要求跨边界同步调用。
- **`isAvailable()` → 读 `capabilities`。**
  `Modulith.capabilities` **已经存在**，文档还写着「用它做特性探测，而不是比较 version」，
  但今天没有任何一处真的用它做判定。换过去就把跨边界调用变成了快照读取。

**这条目标的验收手段不是「改完了」，而是一份清单 + 一道门禁：**

- 建立**边界清单**：每个跨边界成员标注它的可克隆性；
- 门禁断言 **新增跨边界成员时必须显式回答「它可克隆吗」**。

这与项目既有做法一致：靠门禁，不靠记得。

### 目标 2：贡献点改声明式，解掉 IIFE 顶层约束

今天 `createContext()` / `registerCommand()` / `onDeactivate()` **必须**在 IIFE 顶层同步调用，
因为归属靠的是「当前正在加载的插件」这个**隐式全局**。代价有两层：

1. **开发体验**：中大型插件无法把激活逻辑拆成模块，只能把注册代码堆在入口顶层；
2. **与沙箱天然冲突**：沙箱里没有那个「当前插件」的全局可读。

目标形态：

```ts
export function activate(ctx: PluginContext, bootstrap: PluginBootstrap): PluginContributions {
  return {
    modules: [{ id: 'board', component: Board }],
    commands: [{ id: 'new-card', run: () => { /* ... */ } }],
    disposables: [() => { /* ... */ }],
  };
}
```

`bootstrap` 携带**快照数据**（插件 id、版本、设置值、能力表、本次激活事件）。

兼容策略：清单声明 `api: 2` 走新路，否则走旧路；**旧路保留到 v2.0**，不强制迁移。

### 目标 3：补能力，但只补「不假装隔离」的那部分

| 能力 | v1.5 决定 | 理由 |
| --- | --- | --- |
| `clipboard` | **已补**（5a） | 剪贴板是前端能力，同 realm 下**能真的做到**。今天插件得自己用 `navigator.clipboard`，反而绕过了权限列表 —— 补上它让列表更诚实，不是更不诚实。**但它买到的只是"诚实"**：插件仍可直接调 `navigator.clipboard` |
| `filesystem-scoped` | **推迟，不在 v1.5** | 原计划补它。审计后确认它的核心工作量在**授权模型与界面**（授权 UI、持久化、撤销、撤销后的行为），而不在便宜的路径判定。授权模型一旦发布就难以更改，且 v2.0 的进程隔离会改变"授权"能被怎样强制 —— 应与 v2.0 一起做 |
| `filesystem-write` | **不补** | 它没有边界，「任意写」在当前架构下无法约束。补它等于制造一个**假的管控点** |
| `native-module` | **移除** | 宿主做不到，留着只会让用户以为它受管控 |
| `dev-tools` | **移除** | 同上 |

`filesystem-scoped` 的局限必须写进界面文案，不能只写进文档：

> 它约束的是**经由宿主通道**的读写。插件用 `process-spawn` 起一个进程仍可绕过。

**「这约束的是宿主提供的通道，不是插件的全部能力」** —— 不写这句话，它就会变成 §4.2 那种
「界面上的一句空话」。

### 目标 4：插件开发体验（插件仓库内，零宿主改动）

| 缺口 | 现状 | 做法 |
| --- | --- | --- |
| 无类型检查 | esbuild **只擦除类型、不检查类型**，唯一的类型检查靠手动跑 `pnpm typecheck` | **构建本身跑类型检查**，让「类型错了」和「构建成功」不可能同时发生 |
| 无 sourcemap | 产物是拼出来的单文件，报错行号对不上源码 | `sourcemap: 'inline'`（行号还原，且不产生额外文件） |
| 无 watch | 改一行 → 手动 `pnpm build` → 刷新插件 | `pnpm dev`：监听 `src/` 与 `types/`，重建并**打印一句时间戳** |
| 单入口 | 已在 `11a1bd9` 解决一部分（`src/` 多文件） | 补文档：`main` **可以**指向子目录（`validator.rs` 的单测早已用 `dist/index.js`） |

### 目标 5：开发模式热重载（要改宿主，放最后）

`devSource` 机制**已经存在**：目录安装的插件从那个目录实时读取。在它之上加目录监听与自动重载。

**顺序必须是先跑完全部 dispose 再重新求值。** 已发布插件里有模块级缓存
（`kanban` 有 12 个模块级 `Map`），不清会跨重载累积。

⚠️ **已知天花板，必须先讲明：插件的顶层同步死循环无法被中断。**
JS 单线程，宿主救不回卡住的主线程（§4.4）。热重载解决不了这一类，
**只有 v2.0 的独立进程能解决** —— 这恰好是 v2 最硬的理由。

### 第 1 步的实际落地（插件仓库）

| 交付物 | 说明 |
| --- | --- |
| `scripts/watch.ts`（`npm run dev`） | 轮询 `src/` 与 `types/`（400 ms），每次改动**先查类型再重建产物**，打印时间戳。**第一轮只报告、不写盘** |
| `scripts/typecheck.ts` | 用 TypeScript 编译器 API **在进程内**做全量类型检查（~250 ms），供 watch 每轮调用；也是 `node scripts/typecheck.ts` 的入口 |
| `scripts/tsconfig.json` | 脚本自己的类型配置，带 Node 类型 |
| `bundle.ts` inline sourcemap | `sourcemap: 'inline'` + `sourcesContent: true` |
| `bundleAll({ dryRun })` | watch 启动阶段"只看不写" |

三条值得记住的判断：

1. **类型检查不放进 `bundleText`。** 那是 esbuild 唯一的快路径，而类型检查是全量的；
   正确的位置是**构建的调用方**，它才知道这一次值不值得查。
2. **不做增量类型检查。** 增量依赖一份 `.tsbuildinfo` 缓存，而那份缓存在「改了东西但没
   触发重建」时会给出一个陈旧的"通过" —— 那正是 watch 最不能犯的错。
3. **用轮询而非 `fs.watch`。** Windows 上编辑器「先写临时文件再改名」的保存方式会漏事件，
   而插件作者最常用的正是这种保存方式。轮询慢 400 ms，但不会漏。
4. **`scripts/tsconfig.json` 必须与根部分开。** 脚本要用 `process`，而 `src/` 刻意
   `"types": []`。合成一份的话，给脚本加 Node 类型就会让 `src/` 里的 `process.exit()`
   变成合法写法 —— 权限模型的核心是"插件做不到什么"，类型层不该把它自己的防线拆掉。

### 第 1 步的连带代价（**需要一次插件发布**）

inline sourcemap **改变了已构建插件的产物字节**。这是件好事而不是麻烦：仓库的
`findVersionRewrites` 守卫当场拒绝了它：

```
✘ com.rinntheor.modulith.kanban 1.0.2: 该版本已在索引里发布过，但当前源码打包出的哈希不同
```

按 `CONTRIBUTING.md` 自己的规矩（「升版本的判据是**包的内容变了**」），
`kanban` 已升到 **1.0.3**，`index.json` 已重新生成。

> ⚠️ **`index.json.sig` 需要重新签名，这一步需要私钥，脚本刻意不代签。**
> 在签名完成之前，插件仓库的 `npm run check` 会以「索引改过但没有重新签名」失败 ——
> 这是**预期**的，不是缺陷。签名与推送由维护者完成。

代价量化：`kanban` 产物 367 KB（原 ~342 KB），`.lcp` 105 KB。接受它的理由是产物本来
就不压缩，而「能不能在 DevTools 里按源码调试」比几十 KB 重要。

### 第 2 步的实际落地（应用仓库）

**先说一件之前没发现的事：这次我要做的"边界清单"已经有一半存在了。**

`scripts/check-contributions.ts` 里已经有一份 `REFERENCE_PASSING` / `VALUE_PASSING`，
它守的正是本文目标 1 的那条纪律，注释还写着：

> 传值进、传值出；传引用的，将来都得改。
> 新增成员会让断言失败 —— 这不是禁止你加，而是要求你先回答"它将来怎么跨 realm"。

所以第 2 步不是"从零建立纪律"，而是修它三个具体的洞：

| 洞 | 后果 |
| --- | --- |
| **只覆盖宿主表面** | `ctx` 的 17 个成员**一个都没被回答过**。而 `ctx` 才是边界主体 —— 权限的载体（`http` / `launcher` / `icons` / `shell` / `audio`）全在那里 |
| **没有"迁移去向"** | 只说"它传引用"，不说"v2 拿它怎么办"。而"将来再说"不是一种设计 |
| **是两份副本** | 成员名单在 `pluginContributions.ts`，分类在 `check-contributions.ts`。新增成员的人只会更新其中一份 |

交付物：

| 交付物 | 说明 |
| --- | --- |
| `src/services/pluginBoundary.ts` | 29 个跨边界成员的**唯一真源**：`kind`（value / handle / callable）+ `migration`（as-is / rpc / message / bootstrap-snapshot）+ 一句话说明 |
| `scripts/check-plugin-boundary.ts`（`pnpm check:plugin-boundary`） | 60 项断言，分四层：成员名单对着实际接线、单一真源、能力方法逐条、文档一致 |
| `HOST_CAPABILITIES` 改为派生 | 不再手写成员数组，从清单派生；门禁断言它**确实在调用派生函数**，防止有人把字面量抄回去 |

**实际分布**（这就是 v2 的迁移面）：

| 表面 | `value` | `handle` | `callable` |
| --- | --- | --- | --- |
| `Modulith.*`（12 项） | 3 | 2 | **7** |
| `ctx.*`（17 项） | 5 | **12** | **0** |

两条值得记住的结论：

1. **`ctx` 上一个函数形态都没有。** 这意味着 `ctx` 的整体形状对 v2 是安全的：12 个能力对象可以逐个换成 JSON-RPC 式的代理。**这是第 4 步（声明式 `api: 2`）能成立的前提** —— 如果 `ctx` 现在有函数成员，代理方案当场不成立。
2. **要重新设计的只有 7 个，全在宿主表面**，其中 4 个是 React 那一组（`React` / `jsx` / `jsxs` / `Fragment`），也就是分叉 A 要做的取舍。

### 第 2 步里被自己写错的两处

门禁第一次运行就抓出 4 个问题，其中两个是我在**这一步里**写下的：

**一、我把 `React` 判成了安全。** 清单初版把 `React` / `Fragment` 归到 `handle`，而当时的判据函数叫 `crossesRealmAsData(kind)`，对 `handle` 返回 `true` —— 于是 React 被判定"跨得过去"，从迁移面里消失。

真实的错在**函数名**：`crossesRealmAsData` 读起来像"今天已经能跨了"，而它实际表达的只是"形态是值而不是函数"。一个活的 class 实例显然跨不过去。改名 `isValueShaped`，并新增一条断言：**`callable` 与 `migration: 'as-is'` 不可能同时成立** —— 它挡的正是这类"把有迁移面的东西标成原样可用"的写法。

**二、`PluginSettingsAPI.onChange` 真的漏了。** 它的签名是
`onChange(handler: (id, value) => void): () => void` —— 入参和返回值**都是函数**。这说明"从类型定义里扫出含函数的方法"这件事是有效的：漏掉的那一个是被扫出来的，不是被想起来的。

由此得到 5 条必须逐条豁免的方法，每条都写明 v2 的替代方案（见 `FUNCTION_OVERRIDES`）。**豁免必须逐条列，不能写成"忽略所有函数"** —— 前者要求新增的人做一次决定，后者会让这一整层变成装饰。而且豁免表里出现"已经不再含函数的条目"也会失败，防止一个人拿着过期的豁免掩盖将来真的改动。

### 门禁是能失败的

写完立刻验证了一次：把清单里的 `pluginId` 改名成 `pluginIdRENAMED_TO_TEST_THE_GATE`，门禁同时报出两条 ——

```
✘ 上下文表面（ctx.*）：实际暴露的每个成员都在边界清单里（未登记：pluginId）
✘ 上下文表面（ctx.*）：清单里没有已经消失的成员（幽灵条目：pluginIdRENAMED_TO_TEST_THE_GATE）
```

一个不会失败的门禁是装饰，所以这条验证本身也是交付物的一部分。

### 顺带修掉的一处失效引用

`docs/02-开发指南/插件开发/插件系统架构.md` 新增第 6.4 节「边界清单」，把这张表与它的
读法（"它描述的是形态与迁移面，不是当前的隔离强度"）写在了插件作者会看到的地方。

### 第 3 步：先审计，再决定做什么（**范围因此改了**）

原计划这一步是"把跨边界成员改成可克隆形态"。开工前的实测审计推翻了它的前提，
所以实际做的事与计划不同 —— 这里如实记录。

**审计发现（每一条都是查出来的，不是猜的）：**

| 成员 | 实际使用情况 |
| --- | --- |
| `ctx.settings` + `contributes.settings` | **9 个已发布插件里 0 个声明、0 处调用**。宿主侧的 `pluginSettings.ts`、`PluginSettingsSection.tsx`、`registerPluginSettings` 全都在 —— 整个设置面是**休眠**的 |
| `ctx.disposables.add` / `Modulith.onDeactivate` | **0 个插件使用**，尽管类型文档写着"功能型插件必须用它" |
| `isAvailable()` | 只有 kanban（4 处）与 pomodoro（3 处）用 |
| `ctx.http` | **0 处调用，0 个插件声明 `network` 权限** |
| `Modulith.useModuleActive()` | **9 个里 8 个在用** |

最后一行是关键：**v2 最大的阻塞项是 React 那一组，不是 `ctx` 的能力对象。** 而它正是
分叉 A 要做的取舍，v1.5 刻意不碰。在共享 React 实例保持不变的前提下，"让跨边界成员
可克隆"能做的部分就只剩能力层 —— 而能力层的问题要**先量准**，否则改动是盲目的。

**所以这一步实际交付的是"量准"，而不是"改掉"：**

| 交付物 | 说明 |
| --- | --- |
| 边界清单升到**方法级** | 新增 `CAPABILITY_METHODS`：12 个能力对象、40 个方法，逐条登记 `io` 形态（value / handle / callable / host-object）与 v2 的 migration |
| 新增 `host-object` 形态 | 原先只有三类，装不下 `ctx.http` 返回的原生 `Response`。它与 `callable` 的关键区别是**有明确出路**（剥出数据），不是死路 |
| 门禁方法层改用 **TypeScript 编译器 API** | 见下 |
| 交付物总断言数 | 87 项 |

**量出来的结果：40 个方法里 10 个要动。**

| 方法 | 形态 | v2 出路 |
| --- | --- | --- |
| `ctx.http.*`（5 个） | `host-object` | 后端本来就只回 `{status, headers, body}`，v2 直接给数据，别包成 `Response` |
| `ctx.logger.trace` | `callable` | 返回计时函数 → 改成带 token 的两个方法 |
| `ctx.events.subscribe` | `callable` | 入参是处理函数 → 宿主推、按 ID 认领 |
| `ctx.fileDrop.subscribe` | `callable` | 同上 |
| `ctx.settings.onChange` | `callable` | 同上 |
| `ctx.disposables.add` | `callable` | 清理函数 → 宿主记录插件持有什么 |

其余 30 个方法的参数与返回值都是值，换代理是机械的。

**为什么"改动"被推迟到 v2，而不是在这一步做掉：**

1. **`ctx.http` 改成数据形态会改插件侧写法**（`res.json()` 变成对数据的操作），那是一次产品取舍 —— 而它 0 调用，早改与晚改成本相同；
2. **`ctx.settings` 的同步读取**要等第 4 步的 `activate(ctx, bootstrap)` 才有承接处。现在把它改成"激活时给快照"，等于先删掉再补上，中间没有合法路径；
3. **`disposables` / `onDeactivate` 的替代方案**同样依赖第 4 步的贡献返回结构。

也就是说：**第 3 步的结论是"接口形状对 v2 安全，真实工作量是 10 条"，而其中 7 条的正确改法在第 4 步的结构里。** 现在硬改会让第 4 步返工。

### 第 3 步里踩到的三个坑（都是我自己写出来的）

**一、`isValueShaped` 的语义有歧义，我借它把 React 放行了两次。**
第一步已经因为同一类问题改过一次名字，这次新增 `host-object` 后，判断式
`isValueShaped(kind) === (kind === 'callable')` 又漏掉了新类别。断言改成显式枚举
`kind === 'value' || kind === 'handle'`，不再用它去反推。

**二、手写的源码解析器连续被真实代码打穿两次。**
第一版按缩进猜，把方法体里的 `if (...)`、`for (...)` 与解构出的 `title` / `body` / `url`
当成了方法名，报出十几条"未登记"。第二版改用括号深度，又被
`invoke<T>(...)` 的泛型尖括号与多行箭头参数表打穿。

**真正的教训不是"再修一次正则"，而是：手写解析器会给出"看起来检查过了"的假通过与假失败，
那比不检查更糟。** 最终改用 TypeScript 自己的 parser（`ts.createSourceFile` + AST 遍历），
一次拿准全部 17 个对象字面量与它们的真实顶层键。顺带地，旧的手写
`memberNames` / `keysAtIndent` 现在也可以退役了。

**三、噪音的代价被低估了。** 那十几条假失败出现时，我第一反应是"加个白名单过滤掉" ——
而正确的判断是：**一条会喊狼来了的检查，会让人连真的那一条一起忽略。**

### 门禁这次也验证了"能失败"

- 成员级：把 `pluginId` 改名 → 报出"未登记"与"幽灵条目"两条。
- 方法级：在 `pluginAudio` 里加一个 `__gateProbe()` → 报出
  `✘ ctx.audio：运行时每个方法都登记了 io 形态（未登记：__gateProbe）`。

两次都验证后立即还原，`git diff src/services/pluginRuntime.ts` 为空 ——
**这一整步没有改任何运行时行为。**

### 第 4 步：`Modulith.run` —— 把隐式全局换成显式参数

**这一步第一次改了宿主行为。** 交付物是 `Modulith.run(fn)`：宿主把插件身份与数据
作为**参数**交进去，插件在回调里干活。

#### 它解决的是哪一件事

当前插件代码依赖一个**隐式全局** —— "当前正在加载哪个插件"（`loadingPluginId`）。
`createContext()` / `registerModule()` / `onDeactivate()` 都靠它决定归属，代价有两层：

1. **写起来别扭**：中大型插件无法把激活逻辑拆成模块再调用，注册代码只能堆在顶层；
2. **与沙箱天然冲突**：插件挪进独立 realm 之后**没有那个全局可读** ——
   归属必须由宿主显式告诉插件，而不是让插件去读一个环境变量。

`run` 把第 2 条堵上，顺带缓解第 1 条。

#### 它**不**解决什么（这一点必须写清楚）

**回调是同步执行的，它不是生命周期钩子。** 名字里的 "run" 很容易被读成
"延迟到激活事件再执行"，而实际上：**什么时候执行整段 bundle 仍然由清单的
`activationEvents` 决定。** 回调只是把"身份从哪来"从隐式改成显式。

真正的延迟激活在这之前就有了，而且不需要这个 API。

#### 兼容策略

| | 身份来源 | 行为 |
| --- | --- | --- |
| `createContext()`（既有） | 隐式全局 | **一个字都没变** |
| `run(bootstrap)`（新增） | 显式参数 | `bootstrap.ctx` 与 `createContext()` 返回**同一个对象** |

两条路并存，现有 9 个插件不需要任何改动。**插件不需要在清单里声明 API 版本** ——
用哪个入口由插件自己决定；`Modulith.capabilities.api` 描述的是"宿主认识哪些成员"，
不是"这个插件用第几版"。

#### 反"新 API 无人使用"

一个新入口如果只有文档、没有真实调用方，会在**第一次有人用的时候**才暴露问题。
所以：

1. **`samples/reference/index.js` 迁移到 `run`** —— 它是仓库里唯一逐个示范核心接口的
   地方，插件作者会照抄它。让它继续用 `createContext()`，等于每个照抄的人都继承那个
   将来必须改掉的形状。
2. **门禁钉住这件事**（`check-plugin-boundary.ts` 第 7 节）：参考示例必须调用
   `Modulith.run`、**不得**调用 `Modulith.createContext`、且必须真的用到至少一项
   只有 `run` 能给的数据。

#### 这一步踩到的坑：断言在"解释为什么不调用它"的地方失败了

写上门禁后它当场失败：

```
✘ 参考示例不再调用 Modulith.createContext()
```

而示例里 `Modulith.createContext()` 只出现在**注释**中（那段注释正在解释为什么改用
`run`）。按文本匹配把注释当成了真实调用。

这是本项目**同一类坑的第三次**登场（构建脚本曾因为"按文本计数、对注释视而不见"
而算错命令数）。修法不是把那个名字从注释里删掉 —— 那只是让断言看不见自己该看的东西；
而是加了一个 `identifierText()`：用 AST 取出源码里出现的**标识符**，注释被自然排除。

#### 门禁的数字变化

| | 之前 | 之后 |
| --- | --- | --- |
| `Modulith.*` 成员 | 12 | 13（+`run`） |
| 其中 `callable` | 7 | 8 |
| 边界断言总数 | 87 | 90 |

`run` 的 `migration` 是 `message` 而不是 `as-is` —— 我最初写了 `as-is`，
被门禁当场拒绝，**而拒绝是对的**：它入参是一个函数，而"怎么把一个函数交给宿主"
本身就是消息传递要解决的事（与 `events.subscribe` 同一类）。
这一条说明那条"函数不许标成原样可用"的断言真的在起作用，而不是摆设。

**界面层依旧没碰**：`run` 的回调返回值被**忽略**，贡献仍然通过 `registerModule()` 登记。
让"返回值即贡献"要求插件把组件作为值交出来，而组件是函数、跨不过 realm ——
那是分叉 A 的取舍，不属于这一步。

### 顺带交付：`scripts/check-source-ast.ts`（19 项自检）

上一步引入的 AST 解析逻辑是**其它所有校验脚本的眼睛**，而它出错的方式在真实代码里
已经出现过两次。因此给它配了自检：用构造出来的、形状已知的源码把行为钉死，
每个用例都对应一个曾经出错或极易出错的形状 —— 方法体里的 `if`/`for`、泛型尖括号、
模板字符串里的花括号、多行解构参数、变量声明形状、嵌套函数归属、以及
**"找不到"必须返回 `null` 而不是空数组**。

解析逻辑同时抽到 `scripts/source-ast.ts`，由 `check-plugin-boundary` 与
`check-contributions` 共用 —— 同一份逻辑的第二份副本必然漂移，而这两个脚本要核对的
正是"声明与实际是否一致"。

### 第 5a 步：`clipboard` 能力（**并收窄了原计划**）

原计划的第 5 步是"`clipboard` + `filesystem-scoped`"两项。开工前的又一次审计把它拆开了。

#### 交付物

`ctx.clipboard`（`readText` / `writeText` / `isAvailable`），未声明权限时降级为空实现
并记录警告 —— 与 `notification` / `plugin-communicate` 同一处理方式。
`permissions.rs` 里 `clipboard` 的 `enforcement` 从 `None` 变成 `Frontend`。

强制分组因此变化（由 Rust 测试锁定）：`Host` 5 / `Frontend` 3 / `None` 4。

#### 关键判断：它**没有**变强，只是变诚实了

**剪贴板是浏览器 API。** 插件绕过 `ctx.clipboard` 直接调 `navigator.clipboard`
**仍然完全可行**。所以这一项买到的是：

- 插件不必各写各的剪贴板访问方式；
- 调用会被记录；
- **忘记声明的插件会被降级** —— 权限列表里这一项不再形同虚设。

而不是"插件拿不到剪贴板"。这句话写进了权限描述、宿主 API 参考、清单文件参考与
已知问题文档的**四处**，因为它是这一项最容易被误解的地方。

**为什么不在 Rust 侧加门。** 剪贴板没有可关的"授权开关"。对比 `capabilities/default.json`
里刻意不授权 `updater:default` —— 那是对**宿主自己命令**的授权，前端不给就真的不可达。
剪贴板加后端门只会制造"更难绕过"的假象，而那正是本文档反复记录过的那类问题。

#### 顺手挡掉一个很自然的错误改动

有人看到 `clipboard` 是 `Frontend`，会觉得"其它设备级权限都在 Rust 侧，这个也该补上"，
于是加一条 `plugin_clipboard_*` 命令并标成 `Host`。**那会让权限表声称一项它并未提供的
保障** —— 正是 `sandboxLevel` 被删掉的理由。

所以加了一条断言（`check-plugin-boundary.ts` 第 8 节）：`clipboard` 的 enforcement
必须是 `Frontend`、**不得**是 `Host`、且它的说明里必须写明原因。验证过它能失败：
把 `F::Frontend` 改成 `F::Host` 后当场报出两条。

#### 为什么把 `filesystem-scoped` 推迟

审计发现它比表面看起来大：

| 需要的东西 | 现状 |
| --- | --- |
| 用户授权的目录要能被选择 | 需要一个授权 UI |
| 授权要持久化并对后端可见 | 后端目前不知道任何"授权目录"概念 |
| 目录可撤销 | 需要一个撤销 UI 与撤销时的行为定义 |
| 路径必须在授权目录内 | 纯逻辑，可单测 —— **只有这一块是便宜的** |

也就是说，它的核心工作量在**授权模型与界面**，而不在路径判定。
`filesystem-scoped` 目前 **0 个插件使用**，而这个周期已经在四处收窄范围；
更重要的是**授权模型一旦发布就难以更改**（用户已经授权过的目录怎么迁移？），
而 v2.0 的进程隔离会改变"授权"能被怎样强制。

因此推迟的理由与 §5 列出"不做的事"是同一条：**没有想清楚的授权模型，不要先发布。**
它应当与 v2.0 的隔离设计一起做 —— 那时"授权目录"才真的是一项能被强制的约束，
而不是又一条界面上的承诺。

**目标 3 因此记为"完成一半"**：`clipboard` 已交付，`filesystem-scoped` 有明确理由延后。

### 第 6 步：开发模式自动重载（HMR）

改完源码 → 插件仓库的 `pnpm dev` 编出产物 → **宿主自己重新加载插件**。
作者不再需要去插件页点刷新，也不需要重启应用。

| 交付物 | 说明 |
| --- | --- |
| `src/services/pluginDevWatch.ts` | 监听器：1.5 秒轮询、冷静期、累积变化、失败退避与自动停止 |
| `dev_plugin_fingerprints`（Rust 命令） | 一次 IPC 取回所有开发链接插件的产物 `(长度, 修改时间)` |
| `devPluginIds()`（运行时导出） | 判断有没有开发链接的插件 —— 没有就连定时器都不建 |
| `boot.ts` 接线 | 在清单到手**之后**启动监听（放早了会看到空列表） |

四个设计判断：

1. **只对开发链接的插件生效。** 从 `.lcp` 安装的插件，代码来自安装目录的副本 ——
   改别的地方不该影响它。这是唯一说得通的语义。
2. **指纹不读文件内容。** 多文件构建出来的产物是几百 KB（看板 367 KB），
   按秒轮询还把内容读回前端比一遍是纯浪费。指纹也不是校验和，不参与信任决策。
3. **变化要累积，不能丢。** 构建工具常常"先截断再写"，一次保存会在两次轮询之间
   留下两个指纹。立刻重载会读到半成品，而半成品的表现是**加载失败** ——
   作者会以为自己改坏了。冷静期取两倍轮询间隔。
4. **没有开发链接插件时不建定时器。** 普通用户不该为开发模式付出代价。

#### 顺带修掉一个真实缺陷

`reloadPluginRuntime()` **不清空已加载插件的激活状态**，而 `activatePlugin()` 在开头
对 `active` 直接早退。因此重载之后，**懒激活插件**的 bundle 永远不会再执行 ——
而它的 DOM、组件缓存与模块描述符都已经在重载里被清掉了。

表现是「重载之后点开那个模块是空白」，只有重启才恢复。eager 插件看不出来，
因为它们紧接着被重新执行了一遍。这既是自动重载生效的前提，也是一个独立的缺陷。

#### 它替换不掉什么（写进了文档）

- **插件 bundle 顶层的同步死循环无法被中断**（JS 单线程，§4.4）。只有 v2 的进程隔离能解决。
- **它只重载插件，不重载宿主。** 改宿主代码仍走前端热更新或重启。

### 第 6 步里发现的一个我自己的流程漏洞

`cargo test` 里有这个测试：

```
extracts_and_validates_real_sample_lcps
  → 逐字节比对 samples/reference/ 与 reference.lcp 内的文件
  → 注释：「这个错误我已经犯过两次（改完插件忘记重新打包）」
```

**第 4 步我改了 `samples/reference/index.js` 与 `README.md`，却没有重新打包 `reference.lcp`。**
它在我跑 `cargo test` 之前一直是红的 —— 而我前几步只跑了前端门禁与 `tsc`，**没跑 Rust 测试**，
所以这个陈旧包一路带到了第 6 步才被自己的全面验证抓到。

这暴露的是我的验证流程漏洞，不是代码问题：**改动跨了两个技术栈时，只跑一侧的门禁等于没验证。**
项目早就为此写好了测试，我却没有把它放进循环。

已按文档记录的方式重新打包（`Compress-Archive`），398 个 Rust 测试全绿。

**顺带得到的一个性质**：把 `samples/reference` 以开发链接装进应用，现在改完源码
**立刻**就能看到效果 —— 参考插件成了一个可以实时改的活文档。

#### 更正：第 7 步的一条事实错误（**已实测**）

分叉 B 的原判断里写着：

> 现有插件清单若声明了这两项会被**静默忽略**（`PluginManifest` 没有 `deny_unknown_fields`，§4.2 已确认），
> 因此**不需要为它发一轮插件版本**。

**这句话是错的。** 它把"结构体没有 `deny_unknown_fields`"当成了"枚举值也能被忽略" —— 而
`permissions` 是 `Vec<PluginPermission>`，**值**必须与枚举匹配。

用单元测试实测（构造 `serde_json::from_value`）：

```
已知项（对照）   = "storage"              → 解析成功
枚举里不存在的项 = "totally-bogus-perm"   → **解析失败**
    unknown variant `totally-bogus-perm`, expected one of `storage`, … `dev-tools`, `process-spawn`
```

也就是说：**从枚举里删掉 `native-module`，会让任何声明了它的清单整份解析失败**，
插件被标记为清单无法读取而**装不上**，而用户看到的是一句 serde 的英文长列表。
那不是"静默忽略"，是"响亮地坏掉"。

因此第 7 步**暂停**，改为先确认：这个收益值不值得迁移成本。见"待定"一节。

#### 第 7 步的实际做法（选择 C：保留 + 描述清楚）

确认后采取的是 **C**：枚举值一个不删，把「为什么不改变行为」讲清楚。

**关键发现：真正的缺陷不在那两行表格，而在界面上的一句文案。**

安装确认页对**每一项** `enforcement: none` 的权限都显示：

> 宿主**尚未**强制这一项：声明它不会带来额外限制

**「尚未」是一个承诺** —— 它暗示"以后会强制，所以先声明着没坏处"。它对四项都成立得勉强，
而对这两项**恰好相反**：

| 权限 | 界面那句话错在哪 |
| --- | --- |
| `native-module` | 宿主**不会**强制它，因为**没有这个能力**可强制。让用户等一个永远不会来的东西 |
| `dev-tools` | 更糟：它暗示声明它**能得到**什么。而真相是**人人都有**，声明它什么也不增加 |

所以 C 的交付是三件事：

1. **后端描述**（`permissions.rs`）：`native-module` 写明「这一能力不存在」，
   `dev-tools` 写明「这一项是冗余的 —— 插件本来就具备」。两项都点出**原因不同**。
2. **界面文案**：`尚未强制` → `当前不强制 —— 其原因见上面的说明`。去掉承诺，
   并把"为什么"指向那条具体的描述（描述里已经写清楚了）。
3. **清单文件参考**：新增一张表，把四个 `None` 权限的**原因**分开列
   （缺检查点 / 缺授权模型 / 能力不存在 / 冗余）—— 混为一谈会让作者做出错误判断。

**为什么这一项值得单独说：** `native-module` 与 `dev-tools` 的读法**恰好相反**，
一个是真的拿不到，一个是不需要授权。把两者都写成"否"就是在抹平这个区别。

**一个仍然存在的边界**：`enforcement` 只有 `host` / `frontend` / `none` 三个取值，
表达不了"为什么不强制"。现在这个信息在**描述文字**里。要把它变成结构化的字段
（例如给每项加一个 `unenforcedReason`），需要同时改 Rust 类型、前端类型与界面 ——
当前不值得，但这是一条已知的债。

### 分叉 B 的连带改动

移除两项会撞上一条**故意设置**的门禁：

```rust
assert_eq!(count(F::None), 5, "未强制的权限数量变化");
```

它会让这次改动**失败** —— 这是好事，它逼着人同步文档。需要一并改：

1. `src-tauri/src/modules/plugins/permissions.rs` 的 `spec()` 分支、`EXPECTED` 快照、`count(F::None)` 断言；
2. `src-tauri/src/modules/plugins/types.rs` 的枚举与 `ALL`；
3. `docs/02-开发指南/插件开发/清单文件参考.md` 第 4 节；
4. `types/modulith.d.ts` 的 `PluginPermission` 联合类型（插件仓库侧）。
