# 清单文件参考

`manifest.json` 是插件的唯一必需文件，声明插件的身份、入口、权限与兼容范围。本文列出全部字段与取值规则。

## 1. 最小清单

```json
{
  "name": "com.example.my-plugin",
  "version": "1.0.0",
  "main": "dist/index.js"
}
```

只有 `name` 与 `version` 是必需的，其余字段缺失时会退化为默认值。但 `main` 若不填写则默认为 `dist/index.js`，因此实际可用的最小清单需要该文件真实存在。

## 2. 字段总览

字段使用小驼峰命名。未知字段会被静默忽略，不会导致安装失败。

### 2.1 基本信息

| 字段 | 类型 | 必需 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `name` | string | 是 | - | 插件唯一标识，见第 3 节命名规则 |
| `displayName` | string | 否 | 空 | 界面显示名，为空时使用 `name` |
| `version` | string | 是 | - | 插件版本，必须是 `MAJOR.MINOR.PATCH` 三段式，可带 `-预发布` 与 `+构建` 后缀 |
| `description` | string | 否 | 空 | 一句话描述 |

### 2.2 作者与许可

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `author` | object | `{ name, email?, url? }` |
| `license` | string | 许可证标识，例如 `MIT` |
| `homepage` | string | 项目主页 |
| `repository` | object | `{ type, url }`，例如 `{ "type": "git", "url": "..." }` |

**`license` 字段是元数据，不是法律约束。** 它会被解析并保留（前端类型与后端 `PluginManifest` 都有该字段），但宿主**不做任何校验或强制** —— 填 `MIT` 不会让你获得 MIT 以外的任何东西，填 `Proprietary` 也不会被拒绝。它只是一条给用户看的声明。

**你可以自由选择插件的授权方式。** 框架是 GPL-3.0，但 GPL-3.0 第 7 条附加的插件例外明确规定：仅通过公开插件接口交互的插件不被视为框架的衍生作品。因此 MIT、Apache-2.0、专有许可都可以 —— 前提是不复制框架的实现代码。详见[版权与授权](../../07-法务/版权与授权.md)。

### 2.3 分类与检索

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `keywords` | string[] | 关键词 |
| `categories` | string[] | 分类标签，展示在插件详情中 |

这些字段目前仅用于展示，没有检索或筛选逻辑依赖它们。

### 2.4 兼容性

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `engines` | object | `{ "modulith": "*" }` | `modulith` 字段声明兼容的宿主版本范围 |

### 2.5 入口文件

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `main` | string | `dist/index.js` | 代码包路径，相对插件根目录 |
| `style` | string | 无 | 样式表路径，会被注入到页面 |
| `icon` | string | 无 | 图标，可为 `.svg` 文件路径或 lucide-react 图标名 |
| `iconSvg` | string | 无 | 内联 SVG 源码，优先级高于 `icon` |

这三个字段的路径处理并不相同：

- `main`：安装时校验。必须是不含 `..`、非绝对路径的安全相对路径，且指向的文件必须真实存在，否则**安装被拒**。
- `style`、`icon`：安装时只检查文件是否存在，缺失仅记录一条警告，**不阻止安装**。路径安全在**读取时**才校验：前端通过 `read_plugin_asset` 读取这三个路径，该命令会对路径做 `is_safe_relative` 检查（非绝对、无 `..`、无盘符前缀），非法路径返回「非法的相对路径」错误。因此写 `../x.css` 的插件能装上，但样式不会被注入。

也就是说，「路径必须是插件目录内的相对路径」这条约束对三者都成立，但只有 `main` 在安装阶段强制执行，`style` 与 `icon` 的违规表现为加载期失败而非安装期拒绝。

路径校验只是第一道；`read_plugin_asset` 在拼接路径后还会调用 `is_within` 做规范化前缀比较，确认解析结果确实落在插件目录内。任一侧无法规范化时保守拒绝。

### 2.6 权限与运行位置

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `permissions` | string[] | `[]` | 权限声明，取值见第 4 节 |
| `runtime` | string | `"in-process"` | 代码跑在哪里，见下 |

> `sandboxLevel` 曾在这里。**它已被删除**，连同详情页上那行「沙箱级别」的展示 —— 理由见第 6 节。**`runtime` 不是它换了个名字**，两者差在能不能核实，见下。

#### 2.6.1 `runtime`

| 取值 | 含义 |
| --- | --- |
| `"in-process"` | 缺省。插件与宿主跑在**同一个 webview、同一个 JS 上下文**里。宿主区分不了它的调用与宿主自己的调用 |
| `"sandboxed"` | 插件跑在一个**跨源 iframe** 里（来源是自定义协议）:独立 realm、**拿不到任何 IPC**、身份与资源都由宿主按**每个界面一个不可猜的令牌**决定 |

两者都是**宿主能核实**的位置，不是插件自己声明、宿主无从核对的等级 —— 这正是 `sandboxLevel` 被删而 `runtime` 可以存在的原因（第 6 节）。

- **沙箱插件与宿主通信走自定义协议**，不走 Tauri 的 IPC。桥接层（`window.Modulith`）由宿主提供，插件改不了它。
- **插件包不必自带 HTML。** 入口文档由宿主按 `main` / `style` 合成，CSP 也由宿主写死（`script-src 'self'`），因此插件不能靠内联脚本绕过。
- **未知取值会让整份清单不合法，安装直接失败。** 这是刻意的：把 `"sandboxed"` 静默当成 `in-process` 跑起来，是一次**声明了隔离而实际没有**的降级，比安装失败危险得多。
- 本版只有界面插件走这条路。**功能性（无界面）插件走的是另一条路：`contributes.background`**
  —— 它拿到的是一个**独立的 Node 进程**（`--permission` + `--allow-fs-read=<插件目录>`、
  `process.env` 已清空），因此不需要为了执行一点逻辑而付出一个渲染进程。
  那块界面确实不必存在，而不是"暂时没做"。
  ⚠️ 但那条路的边界与 iframe 这条**不一样**，最重要的一条：**`network` /
  `network-external` 在后台插件那一侧不成立**（宿主只传 `--allow-fs-read`、从不传
  `--allow-net`；这在 Node ≥25 上是真边界，在 Node 24 上那个 scope 根本不存在）。
  见[插件系统架构](插件系统架构.md)第 6 节与本仓库 `docs/08-规划/插件沙箱与数据-v2.0范围.md` §2.6。

#### 2.6.2 `runtime` 与**安装策略**（作者必须知道的一条）

从 1.6.x 起，宿主**默认不允许安装未隔离的插件**。这不是措辞，是一条会拦住你的规则：

> 清单里没有 `runtime`（或写成 `"in-process"`）的插件，在「设置 → 插件」的
> 「允许安装未隔离插件」打开之前，装不上 —— 市场里那个按钮会显示「不允许安装」，
> 从 `.lcp`、从目录、从 URL 装也一样会被拒绝。

三条要知道的：

1. **拒绝发生在写入磁盘之前**，因此被拒的插件不会在插件目录里留下半份东西。
   错误信息里写着插件 id、清单里的 `runtime` 取值，以及去哪个设置里打开那个开关。
2. **已经装上的插件不受影响。** 这条策略只管**安装**：把设置关掉不会禁用或卸载
   任何东西 —— 那会让升级应用变成一次静默的插件下线，而用户只会以为插件坏了。
3. **索引里也带着这个值。** 插件仓库打包时会把它从清单派生进 `index.json`
   （与 `kinds` / `permissions` 同一位置），市场据此在**下载之前**就把话说清楚。
   索引里没有这个字段时，宿主会放行到安装阶段、由后端打开包读清单来核实 ——
   也就是说"知道"与"不知道"都拦得住，只是后者要多走一步。

> 为什么默认关着：未隔离插件与宿主共享同一个 JS 上下文，因此**它申请的权限只是
> 声明，不是约束**（第 4 节）。装一个这样的插件，等于把沙箱对它的作用全部取消 ——
> 而那件事在界面上没有任何症状。默认关着，用户要装就显式打开，那一刻他知道自己
> 在放弃什么。纯计算型、不需要宿主能力的插件请写 `"sandboxed"`：它反而是**最省事**
> 的那条路，装上不会有任何额外阻力。

### 2.7 贡献点与激活

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `contributes` | object | 声明这个插件往宿主里加了什么，见 2.7.1 |
| `activationEvents` | string[] | 声明宿主可以在什么时候执行这个插件的代码，见 2.7.2 |

这两个字段从 1.2.0 起**会被真正消费**。它们一起决定了插件是「旧式」还是「声明式」：

| 清单 | 宿主行为 |
| --- | --- |
| 没有 `contributes` | **旧式插件**。目录条目由加载期的 `Modulith.registerModule()` 建立；代码在后台加载阶段执行。与 1.2.0 之前逐字一致 |
| 有 `contributes` + 有 `activationEvents` | **声明式插件**。目录从清单建立（插件未执行代码时侧边栏、命令面板、设置页、右键菜单里就已经有它）；代码按事件激活 |
| 有 `contributes` + 没有 `activationEvents` | 声明式，但降级为「后台加载期激活」。**忘写它只损失「懒」，不会坏** |

#### 2.7.1 `contributes`

五个成员都是可选的。宿主只消费下面这几个；**不认识的键会被静默忽略**（这是有意的：将来新增贡献点时，旧宿主会忽略它，而不是让整份清单解析失败）。

| 键 | 作用 |
| --- | --- |
| `modules` | 侧边栏模块（`id` / `name` / `icon` / `sidebar` / `parent` / `priority` / `badge` / `surface`） |
| `commands` | 全局搜索（Ctrl+K）里的动作（`id` / `title` / `subtitle` / `keywords` / `icon`） |
| `settings` | 设置 →「插件设置」里的控件（`id` / `label` / `type` / `default` / …）。**零代码贡献** |
| `contextMenus` | 外壳右键菜单里的条目（`id` / `label` / `command`）。`command` 必须指向本插件已声明的命令 |
| `surfaces` | **多界面**：这个插件有几块界面，各自的入口脚本是什么（见 2.7.3） |
| `background` | **无界面**：后台入口与它要订阅的事件（见 2.7.4） |

清单里声明的是**数据**，代码里提供的是**行为**：模块的组件与命令的处理函数仍然在插件加载期通过 `Modulith.registerModule()` / `Modulith.registerCommand()` 交出，`id` 与清单对齐。

三条容易踩的规则：

1. **`contributes` 一旦出现，插件就是声明式。** 一个空对象 `{}` 加一个 `onStartup` 是合法的 —— 那就是一个**后台服务插件**（有行为、无界面）。
2. **`settings` 需要 `storage` 权限。** 设置值存在插件自己的存储命名空间里；没声明该权限时宿主读不到值，设置界面会把它标为不可用，而不是让用户对着一个改了不生效的开关。
3. **`contextMenus[].command` 会被交叉校验。** 指向不存在的命令时宿主在加载清单的阶段就报错，而不是等你点下去才发现什么都没发生。

#### 2.7.2 `activationEvents`

只有下面四种会被消费：

| 事件 | 触发时机 |
| --- | --- |
| `onStartup` | 应用进入可用状态后，由宿主在空闲时激活 |
| `onModule:<模块 id>` | 打开该模块时 |
| `onCommand:<命令 id>` | 执行该命令时（写**本地** id） |
| `onContextMenu:<菜单项 id>` | 点击该右键菜单项时 |

语义是「宿主**可以**在这些时刻激活我」，而不是「立刻执行我」—— 宿主有权把一个 `onStartup` 的插件推迟到机器空闲。

`onModule` / `onCommand` / `onContextMenu` 的参数会被对着清单交叉校验；写错了会在加载清单时报出来，因为那样的事件**永远不会触发**，而症状（点开是空白）离原因很远。

> 早期草案里的 `onView` / `onFile` / `onPlugin` / `onRestore` **没有实现**。写了不会有任何效果，宿主会在控制台给出警告。

#### 2.7.3 `surfaces`（多界面）

只对 `runtime: "sandboxed"` 的插件有意义：它决定这个插件有**几块界面**，每一块各自的入口脚本是什么。沙箱插件的一块界面就是一块独立的 webview —— 想同时看见两块界面，就必须有两个 webview。

```json
{
  "runtime": "sandboxed",
  "contributes": {
    "surfaces": [
      { "id": "main",   "name": "笔记", "entry": "dist/index.js", "style": "dist/index.css" },
      { "id": "detail", "name": "详情", "entry": "dist/detail.js" }
    ],
    "modules": [
      { "id": "notes", "name": "笔记", "surface": "main" }
    ]
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✅ | 界面 id。字母数字与 `-` `_`，首字符不能是数字或 `-` `_`，长度 ≤32 |
| `entry` | ✅ | 入口脚本，插件目录内的相对路径 |
| `name` | | 标签页标题。主界面缺省用插件的显示名，次级界面缺省用 `id` |
| `style` | | 这块界面自己的样式表，相对路径 |

四条规则：

1. **`main` 是必需的。** 声明 `surfaces` 就必须有一个 `id: "main"` —— 缺了的话整份清单被拒，而不是"拿第一个当主界面"。理由是**界面 id 的稳定性**：`contributes.modules[].surface` 与 `ctx.ui.openSurface()` 都按 id 指认界面，而宿主按 `(插件 id, 界面 id)` 签发令牌；用顺序定义主界面会让"调整清单顺序"改变一件被外部引用的东西。
2. **不写 `surfaces` 时退化成一块隐式主界面**，入口取顶层的 `main` / `style`。已发布的单界面插件因此一个字都不用改。
3. **写了 `surfaces` 之后，顶层的 `main` / `style` 不再参与。** 两个来源会漂，而漂开的方向是"清单里写着 a.js、实际加载的是 b.js"。
4. **`contributes.modules[].surface`** 把某个侧边栏模块指向某块界面（缺省 `main`）。多块界面共用一个模块入口是允许的 —— 界面是重的那一半，入口是轻的。

代码这一侧：`Modulith.plugin.surface` 告诉你"我这份代码现在被当成哪块界面加载"，`Modulith.surfaces` 是清单的投影（同步可读）：

```js
if (Modulith.plugin.surface === 'detail') {
  renderDetail();
} else {
  renderList();
}

// 打开另一块界面。**位置由宿主决定**，这里只说要哪一个。
await Modulith.ui.openSurface('detail');

// 哪些界面开着（读的是宿主那一侧的真源，不是本页的猜测）
const open = (await Modulith.ui.listSurfaces()).filter((s) => s.open);
await Modulith.ui.closeSurface('detail');
```

> `openSurface` **不等界面建好**再返回：它是一次"我请求了"。要确认它开着，用 `listSurfaces()`。
>
> 界面 id 会在宿主里变成 `plugin:<插件 id>#<界面 id>` 这样一个**隐藏模块**（能开成标签，但不进侧边栏与命令面板）。被 `contributes.modules` 声明过的界面不会再造这个隐藏模块。

#### 2.7.4 `background`（无界面）

见 [Node 运行时与后台功能](../Node运行时与后台功能.md)。一个后台插件一个 Node 子进程，`entry` 是它的入口；`interval` 与 `events` 决定宿主在什么时候把它拉起来。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `preview` | boolean | 标记为预览版 |
| `deprecated` | boolean | 标记为已弃用 |
| `replacedBy` | string | 替代插件的 ID，与 `deprecated` 配合使用 |

## 3. 命名规则

`name` 同时承担三个角色：插件唯一标识、安装目录名、数据存储命名空间。规则为：

- 长度 1 至 64 字符。
- 首字符必须是字母或数字。
- 其余字符可以是字母、数字、`.`、`_`、`-`。

推荐使用反向域名风格，例如 `com.example.my-plugin`，以避免与其他作者的插件冲突。

版本号的解析器比 `version.toml` 的校验器宽松，实际接受范围如下：

| 写法 | 是否接受 | 原因 |
| --- | --- | --- |
| `1.0.0` | 是 | 标准形式 |
| `1.0` | 否 | 点分段不足三段 |
| `v1.0.0` | 否 | 首段含非数字字符 |
| `1.0.0-beta.1` | 是 | 允许 `-` 后缀，解析进 `prerelease` 并参与比较（低于同号正式版） |
| `1.0.0+build.5` | 是 | `+` 之后的内容在解析时被丢弃，不参与比较 |
| `01.0.0` | 是 | 各段只要求全为数字，不检查前导零 |

需要注意的是最后一行：**插件清单不强校验前导零**，而 `version.toml` 的 `version` 字段是强校验的（脚本会以「非合法 SemVer」拒绝）。两者规则不同，写插件时用规范写法即可。

另外，`SemVer` 只比较三段数字与预发布标识，**构建元数据不影响比较结果**，因此 `1.0.0+a` 与 `1.0.0+b` 被视为同一个版本。

## 4. permissions 取值

权限名使用小写 kebab-case。**使用冒号分隔的写法（例如 `filesystem:read`）会导致清单反序列化失败，进而以「清单非法」拒绝安装。**

| 取值 | 含义 | 当前是否强制 |
| --- | --- | --- |
| `storage` | 使用插件私有存储 | 是（Rust 侧检查） |
| `plugin-data` | 在插件自己的数据目录里读写文件（图片、文档、缓存），出不了这个目录 | 是（Rust 侧检查） |
| `network` | 发起网络请求 | 是（Rust 侧检查） |
| `network-external` | 访问非回环地址 | 是（Rust 侧检查） |
| `notification` | 应用内通知 | 是（前端检查） |
| `plugin-communicate` | 跨模块事件总线 | 是（前端检查） |
| `clipboard` | 读写剪贴板 | 是（前端检查，见下） |
| `filesystem-read` | 读取文件信息（图标、所在位置），并接收拖入的文件路径 | 是（Rust 侧，另有一处前端检查） |
| `filesystem-write` | 写入文件 | 否 |
| `filesystem-scoped` | 限定目录的文件访问 | 否 |
| `native-module` | 加载原生模块 | 否（**且这一能力不存在**，见下） |
| `dev-tools` | 开发者工具能力 | 否（**且这一项是冗余的**，见下） |
| `process-spawn` | 启动外部程序 | 是（Rust 侧检查） |

关于「当前是否强制」：真正生效的是上表中标注为「是」的九项。`storage`、`plugin-data`、`network`、`network-external`、`process-spawn`、`filesystem-read` 在 Rust 侧检查（存储文件、数据目录、进程、文件图标都由 Rust 操作，前端都绕不过去；`filesystem-read` 另有一处前端检查，见 `ctx.fileDrop`），`notification`、`plugin-communicate` 与 `clipboard` 在前端检查（这三项不发生 IPC 之外的动作）。其余权限目前不影响行为，声明它们不会带来额外限制，不声明也不会被阻止。

> `plugin-data` 与 `filesystem-write` 的区别值得单独说一句：后者是"任意写"，**没有边界因而被拒绝**
> （补它等于制造一个假的管控点）；前者是"在**自己那一块目录**里写"，边界由宿主提供并强制。
> 这也是为什么它是单独一条权限，而不是把 `filesystem-write` 悄悄放宽 —— 后者会让每一个
> 已经声明过它的插件在无人察觉的情况下获得一个可写目录。

#### 「不强制」不是同一种情况

上表里有四项标着「否」，而它们**不强制的原因各不相同** —— 把它们混为一谈会让插件作者做出错误判断：

| 取值 | 不强制的原因 | 插件实际能做什么 |
| --- | --- | --- |
| `filesystem-write` | 有语义、**缺检查点** | 目前没有受管的写文件通道；导出功能已收口为「导出目录内的新文件名」 |
| `filesystem-scoped` | **缺授权模型**（不属于 1.5 的范围） | 同上 |
| `native-module` | **这一能力不存在** | 什么也做不了。Tauri 插件必须随应用一起编译，插件包无法在运行期引入原生模块 |
| `dev-tools` | **这一项是冗余的** | 什么也不需要做 —— 插件与宿主共享同一个页面环境，**本来就**能打开控制台 |

后两项值得单独说，因为它们的读法恰好相反：

- **`native-module` 是真的拿不到。** 声明它不会让你获得任何东西，因为宿主**没有**这个能力可以提供。这是一项历史遗留的枚举值，保留它只是为了旧清单能继续安装。
- **`dev-tools` 是人人都有的。** 声明它同样不会改变什么 —— 但原因不是"做不到"，而是"不需要授权"。不要把它理解成"宿主答应给我调试能力"。

因此这一项在权限列表里的正确读法是：**它既不增加能力，也不构成限制。**

> **为什么保留而不是删掉？** 删除一个枚举值会让声明了它的清单**整份反序列化失败**、插件直接装不上（`permissions` 是 `Vec<PluginPermission>`，未知**值**不会被忽略），而用户看到的会是一句 serde 的错误。收益（列表短两行）不值得这个代价。

**`clipboard` 的强制程度比其它项弱，这一点必须说清楚。** 剪贴板是浏览器 API —— `navigator.clipboard` 在页面脚本里本来就可达，因此宿主**无法**真正拦住一个铁了心绕过 `ctx.clipboard` 的插件。这一项管住的是"插件按约定走宿主通道"，而不是"插件拿不到剪贴板"。

它仍然值得提供与声明：调用会被记录、行为统一，而且**权限列表里这一项是真的会拦下忘记声明的插件的** —— 未声明时 `ctx.clipboard` 降级为空实现并记录警告。这与 `notification` / `plugin-communicate` 的处理方式一致。

> 为什么不像 `updater` 那样在后端加门？因为那在 `capabilities/default.json` 里是可行的：`updater:default` 是对**宿主自己命令**的授权，前端不授权就真的不可达。剪贴板没有这样的开关，后端加门只会制造一种"更难绕过"的假象。

`storage` 是后补上强制的：此前它「声明与否都不改变行为」，权限列表因此在这一点上形同虚设。现在**未声明 `storage` 的插件调用 `ctx.storage` 的任意方法都会被拒绝**，错误信息为「插件 X 未声明 storage 权限」。仓库内的示例插件一直声明着它，因此不受影响；若你的旧插件依赖「不声明也能用」，需要补上这一项。

未声明 `notification` / `plugin-communicate` / `clipboard` 时**不会拒绝安装**，也不会让插件加载失败：对应接口降级为空实现并记录一条控制台警告，插件可用 `isAvailable()` 查询后自行降级。这一点与网络、存储权限不同——后两者会直接拒绝操作。

需要发起网络请求的插件必须同时声明：

```json
"permissions": ["network", "network-external"]
```

只声明 `network` 时，仅能访问本机回环地址。

### 4.1 风险等级由宿主推导，清单不提供

界面上每个权限显示的标签、说明与**风险等级**都不来自清单，而由宿主从权限本身推导
（`src-tauri/src/modules/plugins/permissions.rs`），前端通过 `list_plugin_permissions`
取回。清单里写的永远只是权限标识符。

这一点是刻意的：风险是安全信息，不能由被审查的一方提供。若等级来自清单或远程索引，
一个被篡改的索引就能把 `process-spawn` 标成低风险。

推导基于三项客观属性 —— 权限对目标做了什么（`effect`）、影响到哪里（`scope`）、后果
能否撤销（`reversible`）：

| 规则（自上而下短路匹配） | 等级 |
| --- | --- |
| `scope == system` | high |
| `effect == execute` | high |
| `scope == device && effect == write && !reversible` | high |
| `scope == device` 或 `scope == remote` | medium |
| 其余 | low |

十二项权限中，`plugin-communicate` 一项无法由公式覆盖 —— 它可构成混淆代理：没有文件
权限的插件能借有文件权限的插件代为操作，从而绕过权限模型。因此它带一条写明理由的显式
覆盖。**完整推导表就是 `permissions.rs` 里的 `PluginPermission::spec()`**：每项给出
`effect` / `scope` / `reversible`，公式覆盖不到的项带一个 `risk_override` 并写明理由。
它的输出由 `metadata_snapshot_is_locked` 测试钉住 —— 改元数据会让测试失败并要求同步
本文档，而不是安静地改掉界面上显示的等级。

**新增权限时你不需要做任何事。** 元数据由宿主维护，推导是自动的，且新增枚举值会让 Rust
侧因匹配不穷尽而编译失败 —— 忘记维护会报错，而不是安静地退化成一个没有依据的等级。

### 4.2 强制程度也是元数据

本节开头表格里的「当前是否强制」一栏，以宿主的 `enforcement` 元数据为准，取值为
`host`（后端检查）、`frontend`（前端检查）、`none`（已解析但不改变任何行为）。这三组的
数量由测试锁定，改动强制程度会让测试失败，提醒同步本文档。

`none` 必须在界面上如实标注。让用户以为某项权限受管控、而它其实不受管控，比不告诉他
更危险 —— 他会基于一个错误的前提做决定。

## 5. engines 语法

`engines.modulith` 声明插件兼容的宿主版本。解析规则是**恰好一个比较符**（或没有比较符）加一个三段式版本号：

| 写法 | 含义 |
| --- | --- |
| `*` | 任意版本 |
| `1.2.3` | 精确等于 |
| `^1.2.3` | 大于等于 1.2.3 且主版本相同 |
| `^0.2.3` | 大于等于 0.2.3 且主次版本相同（即 0.2.x） |
| `~1.2.3` | 大于等于 1.2.3 且主次版本相同（即 1.2.x） |
| `>=1.0.0` | 大于等于 |
| `<=1.0.0` | 小于等于 |
| `>1.0.0` | 大于 |
| `<1.0.0` | 小于 |
| `=1.0.0` | 精确等于 |

**不支持复合范围**。形如 `">=0.2.0 <0.4.0"` 的 npm 风格写法无法被解析。**语法非法会以「清单非法」拒绝安装**——连解析都做不到，说明清单确实写错了。

语法合法但与当前宿主版本不匹配时，**不会阻止安装**，只在插件列表中显示一条提示。这个区别很重要：

| 情况 | 结果 |
| --- | --- |
| 未声明 / `*` | 不做任何提示 |
| 语法非法（复合范围、`1.x`） | 拒绝安装 |
| 语法合法但不匹配 | 正常安装与加载，界面显示一条琥珀色提示 |

**为什么"不匹配"不阻止安装。** `engines.modulith` 在 0.x 阶段是高度脆弱的约束：`^0.2.0` 按 semver 的 caret 规则（与 npm 一致）等价于 `>=0.2.0 <0.3.0`，也就是说宿主只要升一个小版本，所有写 `^0.2.x` 的插件就不满足声明范围了。早期实现把这种不匹配当成安装失败的硬错误，实际后果是：已安装的插件在升级应用后依然能加载（列表不做引擎校验），但用户**再也无法重装或安装该插件的新版本**，界面只给一句"插件要求 Modulith ^0.2.0，当前版本为 0.3.0"——看起来就像升级应用把插件全废了。

现在的判断标准是：**语法错误是错误，兼容性猜测不是**。插件的实际兼容性由它的代码决定，声明范围只是作者的保守估计；真的不兼容时，加载会失败并在列表中标记为"异常"，用户看得到。用一个事前猜测去否定事后可验证的事实，代价是用户完全无法使用插件。

因此**建议写法是只带下界的范围**，例如 `>=1.6.0`：它既表达了"需要这个版本以上"的意图，又不会因为宿主升了一个次版本就产生提示。注意 1.0 之后 caret 的语义与 0.x 不同 —— `^1.0.0` 等价于 `>=1.0.0 <2.0.0`，因此升到 1.1 不会失配；但升到 2.0 会产生提示，而只带下界的写法连那次提示也不会有。下限本身应当写**插件真正需要的那个版本**，而不是习惯性的 `1.0.0`。

执行 `pnpm ver check` 会扫描仓库内的清单并对过窄或语法不支持的范围给出提示。

## 6. 已移除：`sandboxLevel`

这里曾有一张「沙箱等级 L0–L3」的取值表。**该字段已从宿主中删除**，因为它描述的是一种**宿主做不到的事**：插件与宿主运行在同一个 WebView、同一个 JS 上下文里，宿主无法按等级限制它。它是插件自己声明、宿主无法核实的字段 —— 与权限风险同理，一个无法核实的自述不该被当作管控手段。

**它不只是一个死字段。** 插件详情页此前真的把它渲染成一行「沙箱级别 L1」，也就是说它同时是**界面上的一句空话**：用户会据此以为宿主能对插件分级管控。

**删除是向后兼容的**：清单解析没有 `deny_unknown_fields`，因此旧清单里残留的 `sandboxLevel` 会被静默忽略，不会让安装失败。**但不要在新插件里写它。**

替代它的是两样真东西：`permissions`（见第 4 节，正在逐步从"声明"变成"真强制"）与出站网络策略。

## 7. 完整示例

以下取自仓库中的参考插件 `samples/reference/manifest.json` —— 只用三项能力的典型形态：

```json
{
  "name": "com.modulith.sample.reference",
  "displayName": "宿主接口参考",
  "version": "1.0.0",
  "description": "不提供功能，只把不需要危险权限的核心宿主接口逐个示范一遍：模块注册、存储、通知、事件、窗口级监听与日志。",
  "author": {
    "name": "环理论",
    "url": "https://github.com/Rinntheor"
  },
  "license": "MIT",
  "homepage": "https://github.com/Rinntheor/modulith-desktop/tree/main/samples/reference",
  "repository": {
    "type": "git",
    "url": "https://github.com/Rinntheor/modulith-desktop.git"
  },
  "categories": ["示例"],
  "keywords": ["sample", "reference", "api", "demo"],
  "engines": {
    "modulith": ">=1.6.0"
  },
  "main": "index.js",
  "style": "index.css",
  "icon": "icon.svg",
  "permissions": ["storage", "notification", "plugin-communicate"]
}
```

需要更多宿主能力的插件会声明更多项。插件仓库
[`modulith-plugins`](https://github.com/Rinntheor/modulith-plugins) 里的完整示例就是例子：
`plugins/pomodoro` 用 `["storage", "notification", "filesystem-read"]`（计时存储、到点提醒、
导入自定义提示音），`plugins/quick-launch` 用 `["storage", "process-spawn", "filesystem-read"]`。
**声明了什么，就应该真的用到什么** —— 权限列表是给用户看风险用的，多写一项就多一分误导。

该插件的 `engines.modulith` 使用 `>=1.6.0`（只带下界）。下限取 1.6.0 而不是 `1.0.0`，是因为 1.6.0 才引入本插件示范的这些接口所依赖的平台能力。只带下界的范围不会因为宿主升版本而产生提示，而那条提示对用户没有实际价值。

## 8. 常见错误

| 报错 | 原因 | 是否阻止安装 |
| --- | --- | --- |
| 插件名非法 | `name` 为空、超过 64 字符或首字符不是字母数字 | 是 |
| version 非法 | 点分段不是三段，或某段含非数字字符（例如 `1.0`、`v1.0.0`） | 是 |
| engines.modulith 非法 | 使用了复合范围或通配写法（语法无法解析） | 是 |
| main 必须是插件目录内的相对路径 | 路径包含 `..` 或为绝对路径 | 是 |
| main 入口文件不存在 | `main` 指向的文件未随包提供，或路径拼写有误 | 是 |
| 清单非法（反序列化失败） | `permissions` 中使用了冒号写法等非法枚举值 | 是 |
| 引擎范围不匹配（琥珀色提示） | 声明的范围语法正确但当前宿主不在其中 | 否，仅提示 |
| 加载失败（红色提示） | 插件 bundle 抛错、超时，或没有注册任何模块 | 否，插件被标记为异常 |
