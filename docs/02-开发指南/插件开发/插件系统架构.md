# 插件系统架构

插件系统让用户在不重新编译应用的前提下扩展功能。本文描述包格式、安装流水线、运行时加载模型与当前的隔离边界。

## 1. 定位

框架的两种扩展方式分工如下：

| 维度 | 内建模块 | 插件 |
| --- | --- | --- |
| 生效时机 | 编译期 | 运行期，可安装与卸载 |
| 后端能力 | 可注册任意 Tauri 命令 | 只能使用宿主暴露的服务 |
| 隔离 | 与应用同权限 | 受权限声明约束（见第 6 节的实际边界） |
| 分发形态 | 随应用发布 | `.lcp` 包 |

插件适合承载「用户自己需要的功能」。它无法突破宿主提供的接口，因此能力上小于内建模块；换来的是不必重新编译与分发整个应用。

**版权与授权：插件归插件作者所有，授权方式由作者自行决定。** 框架以 GPL-3.0 发布，但依据 GPL-3.0 第 7 条附加了**插件例外**：仅通过公开插件接口交互的插件不被视为框架的衍生作品，因此可以用 MIT、Apache-2.0，也可以闭源 —— 前提是不复制框架的实现代码。完整条款见 [PLUGIN-EXCEPTION.md](../../../PLUGIN-EXCEPTION.md)，中文说明见[版权与授权](../../07-法务/版权与授权.md)。

## 2. 包格式

`.lcp` 是一个 zip 容器，扩展名仅用于标识与文件选择对话框的过滤。解包后的有效结构为：

```
<plugin>/
  manifest.json       清单，必需
  dist/index.js       代码包，路径由清单的 main 指定
  dist/index.css      可选样式，路径由清单的 style 指定
  icon.svg            可选图标，路径由清单的 icon 指定
  README.md           可选说明，安装后展示在插件详情中
```

只有 `manifest.json` 是必需的。其余文件是否存在取决于清单如何声明。

关于图标：`icon` 字段要么指向插件目录内以 `.svg` 结尾的文件，要么填写一个 lucide-react 图标名。清单还提供 `iconSvg` 字段，可直接内联 SVG 源码。`read_plugin_asset` 以 UTF-8 文本读取资源，因此 `.png` 等二进制格式不受支持——填写 `.png` 会退化为按 lucide 名查找并最终显示为首字母色块。

关于代码包：`main` 指向的文件必须是一个自执行脚本（IIFE），它在执行时调用 `Modulith.registerModule()`。宿主通过注入 `<script>` 元素执行它，而不是作为 ES 模块导入，因此代码中不能使用 `import` 语句。

## 3. 安装流水线

安装在后端完成，入口是三条命令之一：

| 命令 | 来源 |
| --- | --- |
| `install_plugin_package` | 本地 `.lcp` 文件路径 |
| `install_plugin_folder` | 已解包的目录 |
| `install_plugin_url` | 远程地址，下载后安装 |

处理流程：

```
接收来源（路径或 URL）
      |
      v
解压到暂存目录
  · 校验条目路径不逃出目标目录（防 zip-slip）
  · 限制条目数量与总体积
      |
      v
读取并解析 manifest.json
      |
      v
校验清单
  · name 合法（字母数字开头，允许 . _ -，最长 64）
  · version 可解析为 SemVer
  · engines.modulith 语法合法（不匹配只提示，不拒绝）
  · main 是插件目录内的相对路径，且文件真实存在
      |
      v
归档到 <plugins_dir>/<id>/<version>/
      |
      v
写入注册信息
```

安装过程中任何一步失败都会拒绝整个包，不会留下部分安装的插件。

### 3.1 引擎范围不是安装门槛

`engines.modulith` 的校验刻意分成两件事：

| 判断 | 处理 |
| --- | --- |
| 范围**语法**是否可解析 | 不可解析 → 拒绝安装（清单确实写错了） |
| 范围是否**匹配**当前宿主 | 不匹配 → 仅记录提示，照常安装与加载 |

这不是宽容，而是修正了一个真实缺陷。`engines.modulith` 在 0.x 阶段极其脆弱：`^0.2.0` 按 semver 的 caret 规则等价于 `>=0.2.0 <0.3.0`，宿主升一个小版本就会让所有写 `^0.2.x` 的插件"声明不匹配"。早期实现把不匹配当硬错误，后果是**用户升级应用后无法再安装任何旧插件**——已安装的仍能加载（`list()` 不做引擎校验），但重装与升级全被拒，界面提示看起来像"插件被新版本废掉了"。

提示会随每次列表查询按**当前宿主版本**重新计算（不落盘），因此升级应用后提示会自动更新，也不需要在 `registry.json` 里加字段而引出旧注册表兼容问题。界面用琥珀色展示它，措辞是"仍会正常加载"；插件真的跑不起来时会以独立的红色加载失败提示呈现。

路径安全校验使用规范化后的路径比较，确保解压产生的每个条目都落在目标目录内。这一检查防止构造特制 zip 覆盖应用目录外的文件。

插件 ID 取自清单的 `name` 字段。同一 ID 重复安装相同版本时会直接覆盖。

## 4. 运行时加载模型

安装只把文件放到磁盘，真正生效需要前端加载。加载入口是 `reloadPluginRuntime()`。

从 1.2.0 起，加载分成**两趟**，中间那条分界线是整个插件模型的关键：

```
第一趟：清单 → 贡献目录（**不执行任何插件代码**）

refreshHostVersion()                     从后端取回权威版本号
      |
      v
installHostGlobals()                     注入 window.Modulith
      |
      v
list_plugins                             取回已安装插件列表
      |
      v
清理旧的贡献目录 / 动态模块 / 已注入资源
      |
      v
对每个「已启用且状态正常」的插件，解析清单得到**装载契约**
      1. contributes.modules      -> 模块条目进目录（组件留到激活时）
      2. contributes.commands     -> 命令条目进全局搜索（handler 留到激活时）
      3. contributes.settings     -> 设置项登记，并读回当前值
      4. contributes.contextMenus -> 右键菜单项（与已声明命令交叉校验）
      |
      v
此时侧边栏、命令面板、设置页、右键菜单**已经完整** —— 而一个 bundle 都还没跑

第二趟：按装载契约执行代码

对每个 eager 的插件（旧式插件，或声明了 onStartup / 没有可用激活事件的）
      1. 若声明了 style，读取 CSS 并注入 <style>
      2. 读取 main 指向的代码
      3. 注入 <script> 并执行
      4. 代码在 IIFE 顶层调用 Modulith.registerModule() / registerCommand()
      5. 记录加载状态与注册到的模块 ID / 绑定的命令

其余插件（声明式且未声明 onStartup）一直等到被真正用到
```

调用时机包括应用启动（启动流程的第四步）、插件管理界面的操作、以及标题栏的刷新按钮。因此插件在磁盘上的变更无需重启应用。

**为什么要拆成两趟。** 拆开之后，宿主在**一行插件代码都没执行**的前提下就知道了这个插件往界面里加了什么。由此得到三件事：

1. **功能性插件成立。** 一个只加三条命令、一个只做后台监听的插件，不再需要为了「证明自己存在」而注册一个侧边栏模块。
2. **按需激活成立。** 插件代码等到用户真的用到它才跑 —— 「装了 500 个插件」不再等于「进了 500 段第三方代码」。
3. **它是将来强制式沙箱的前提。** 插件挪到独立进程 / Web Worker 之后，「先执行它、再问它有什么」本身就是一次远程调用，而且失败时界面是空的。声明式目录让宿主在任何执行发生之前就画得出完整界面。

### 4.1 加载期上下文

`Modulith.createContext()` 返回绑定到当前插件的服务集合，包括存储、日志与 HTTP。它只能在插件代码执行期间调用——具体说是在 `loadingPluginId` 被设置的窗口内，也就是 `<script>` 注入所触发的同步执行过程中。在插件之外调用会抛出异常。

这一限制是有意设计的：服务需要绑定插件 ID，而插件 ID 只在加载那一刻确定。

`ctx.activationEvent` 告诉插件**这次是为什么被激活的**（`onModule:xxx` / `onCommand:xxx` / `onContextMenu:xxx` / `onStartup` / 旧式插件的 `'legacy'`）。一个声明了多条激活事件的插件常常只需要为被用到的那部分做准备，没有这个字段就只能全部初始化一遍 —— 那等于把按需激活省下的钱又花回去。

### 4.2 注册模块

`Modulith.registerModule()` 接收一个模块描述符，其中 `component` 是一个 React 组件。注册进入动态编目后，该模块在界面上的表现与内建模块一致：出现在侧边栏、可被搜索、可通过 `ModuleRenderer` 渲染。

注册有**两种语义**，取决于插件是不是声明式：

| 插件 | `registerModule({ id, component })` 的含义 |
| --- | --- |
| 旧式（清单里没有 `contributes`） | 条目在这里**建立**，ID 冲突在此时被拒绝 |
| 声明式（清单里有 `contributes.modules`） | 条目在**读清单**时就建立好了，这里只是把组件交给那个 ID |

声明式插件注册一个未在清单里声明的模块时，宿主会宽容地把它补进目录并记一条警告 —— 「声明」的价值是让宿主不必执行代码就能画界面，而不是限制插件能注册什么。代价是那个模块在插件未激活时不会出现在侧边栏。

注册有三项约束，对两种语义都成立：

1. `id` 必须是非空字符串。
2. 不得与内建模块 ID 冲突。
3. 不得与已注册的其他动态模块冲突。

冲突时注册被拒绝并输出错误日志。这条规则阻止插件通过同名模块劫持内建模块的入口。

### 4.3 加载失败的处理

以下情形会被判为加载失败：

- 读取资源失败或文件缺失。
- 脚本执行期间抛出错误。宿主通过临时监听 `window` 的 `error` 事件捕获，因此失败会反映在界面上而不只是开发者工具里。
- 脚本执行完毕，但**既没有贡献任何东西，也没有声明激活事件**。

第三条在 1.2.0 之前写作「没有注册任何模块」。旧判据把「插件是什么」与「插件往侧边栏放了什么」焊死在一起，于是只加命令的插件、只做后台监听的插件都会被判为失败。新判据是「**至少贡献了一样东西**」，而那样东西可以是清单里的声明 —— 一个后台服务插件只要声明了 `activationEvents` 就合法。

这条检查仍然保留，是因为它抓的是另一个真实错误：bundle 不是预期的 IIFE（打包配置错了、入口文件写错了）—— 那种情况下插件确实什么都没做。

失败时已注入的样式与脚本会被清理，该插件的加载状态记为 `error`，其模块不出现在编目中。其他插件不受影响。

### 4.4 卸载与收尾

插件被禁用 / 卸载 / 重新加载时，宿主会清理四样东西：图标 SVG 缓存、事件总线上的全部订阅、它注册到命令注册表的命令，以及**它自己登记的清理函数**（`ctx.disposables` / `Modulith.onDeactivate()`）。

最后一样是**功能型插件的前提**。一个只注册模块的插件不需要它 —— 宿主清掉 DOM 与目录条目就够了；但一个后台服务会创建定时器、窗口监听、MutationObserver、WebSocket，**宿主没有别的途径知道它们存在**。把它们交到 `ctx.disposables.add()` 之后，宿主会在卸载时逆序执行，单个抛错不牵连其余，每个只执行一次。

**声明式插件有一条例外：命令的「声明」要在清理之后贴回去。** 那些条目本来就该在插件未激活时也存在（它们是清单的一部分，不是运行期的产物）；不贴回去的话，禁用一次再启用就会让命令面板少掉几条。

## 5. 宿主 API 概览

`window.Modulith` 是插件与宿主交互的唯一入口。这个对象是**普通对象，没有冻结**：宿主在注入后仍会写入 `version`（拿到后端版本号时），也没有做只读保护。约定是插件不得修改它，但这是约定而非强制——宿主不检测、也不因此拒绝加载。

| 成员 | 说明 |
| --- | --- |
| `version` | 宿主版本号，取自后端 `get_app_info` |
| `platform` | 固定为 `tauri` |
| `React` | 宿主使用的 React 实例 |
| `jsx` / `jsxs` / `Fragment` | 宿主的 JSX 运行时 |
| `registerModule(registration)` | 注册（或为清单里声明的模块提供）一个模块 |
| `registerCommand(command)` | 注册（或为清单里声明的命令绑定）一个动作 |
| `createContext()` | 取得当前插件的服务集合 |
| `onDeactivate(fn)` | 登记卸载时的清理函数（见 4.4） |
| `useModuleActive()` | 判断本模块当前是否真的对用户可见 |
| `capabilities` | 宿主能力表，供插件做特性探测 |

`capabilities` 的存在理由是**版本号不该被用来判断能力**：`engines.modulith` 只表达「我要求宿主至少多新」，而且它只提示、不阻断。插件应当问「宿主有没有 `settings` 这个贡献点」，而不是「宿主是不是 ≥ 1.2.0」。

```js
if (Modulith.capabilities.contributions.includes('settings')) { /* … */ }
```

**插件不得自行导入 React**。JSX 打包时必须把 `react` 与 `react/jsx-runtime` 设为外部依赖，映射到 `Modulith.React` 与 `Modulith`（`jsx`/`jsxs`/`Fragment` 直接挂在 `Modulith` 上）。共用同一份 React 实例是必需的：如果插件引入自己的 React 副本，Hooks 会因实例不一致而失效。

**`react-dom` 不要外部化，也不要用。** 宿主不提供 `ReactDOM`，插件应通过 `registerModule` 交出组件、由宿主负责渲染。把它外部化只会得到一个指向不存在全局成员的引用。

`createContext()` 返回的服务集合包含：

| 服务 | 成员 |
| --- | --- |
| 插件信息 | `pluginId`、`pluginVersion`、`manifest`、`version`（宿主版本）、`activationEvent`（本次为什么被激活） |
| `storage` | `get`、`set`、`delete`、`clear`、`keys`、`all` |
| `http` | `fetch`、`get`、`post`、`put`、`delete` |
| `logger` | `debug`、`info`、`warn`、`error`、`trace` |
| `notifications` | `show`、`info`、`success`、`warn`、`error`、`isAvailable`（需 `notification` 权限） |
| `events` | `publish`、`subscribe`、`isAvailable`（需 `plugin-communicate` 权限） |
| `launcher` | 启动外部程序（需 `process-spawn`） |
| `icons` | 从可执行文件提取图标（需 `filesystem-read`） |
| `shell` | 在文件管理器中定位（需 `filesystem-read`） |
| `fileDrop` | 订阅窗口级文件拖放（需 `filesystem-read`） |
| `audio` | 选择本机音频文件（需 `filesystem-read`） |
| `settings` | 读取 `contributes.settings` 的当前值（需 `storage` 权限） |
| `disposables` | 登记卸载时的清理函数（见 4.4） |

**上表是完整集合。** 各服务的完整签名、权限门槛与拒绝时的行为见[宿主 API 参考](宿主API参考.md)。`Modulith.capabilities` 把这份集合同样列了出来，并由 `scripts/check-contributions.ts` 对着源码断言 —— 因此「文档里写了、实际没接线」这类漂移会直接让检查失败。

## 6. 隔离边界

这一节描述**当前代码实际强制的限制**，而不是设计目标。区分二者很重要，因为插件的隔离强度直接影响是否应当信任一个来源不明的插件。

### 6.1 实际生效的限制

| 限制 | 实现位置 | 说明 |
| --- | --- | --- |
| 安装路径安全 | 解压阶段 | 条目不得逃出目标目录 |
| 包体积上限 | 解压阶段 | 解压后累计不超过 64 MB（`MAX_PLUGIN_BYTES`） |
| 包条目数上限 | 解压阶段 | 不超过 5000 条（`MAX_ZIP_ENTRIES`），防止资源耗尽型压缩包 |
| 资源读取上限 | `read_plugin_asset` | 单个文件不超过 8 MB（`MAX_ASSET_BYTES`） |
| README 读取上限 | 插件详情 | 最多读取 64 KB（`MAX_README_BYTES`） |
| HTTP 响应体上限 | `http` 服务 | 不超过 2 MB（`MAX_HTTP_BODY_BYTES`） |
| 存储键名合法性 | `storage` 服务 | 只允许字母数字与 `.` `_` `-`，最长 128 字符 |
| 存储值合法性 | `storage` 服务 | `set` 的值必须是合法 JSON |
| 存储访问权限 | `storage` 服务（Rust） | 未声明 `storage` 时拒绝一切存储读写 |
| 启动外部程序 | 启动服务（Rust） | 未声明 `process-spawn` 时拒绝 `ctx.launcher.launch`；且只接受绝对路径、已存在的文件 |
| 文件图标提取 | `icons` 服务（Rust） | 未声明 `filesystem-read` 时拒绝；路径必须是绝对路径且为文件 |
| 文件管理器定位 | `shell` 服务（Rust） | 未声明 `filesystem-read` 时拒绝；只定位，不打开文件本身 |
| 文件拖放接收 | `fileDrop` 服务（前端） | 未声明 `filesystem-read` 时订阅被忽略并记录警告 |
| 音频导入 | `audio` 服务（Rust） | 未声明 `filesystem-read` 时拒绝；按扩展名白名单与 2 MB 上限校验，只返回 data URL |
| 插件 ID 合法性 | 所有接收 `id` 的命令 | 走 `is_valid_plugin_name`（字母数字开头，只含字母数字与 `.` `_` `-`，最长 64 字符）。ID 会被直接 `join` 到插件目录与插件数据目录之下，因此这道校验同时是**路径安全**防线：`id = ".."` 这类取值会让目标解析到应用数据目录本身 |
| 清单合法性 | 校验阶段 | 名称、版本、入口文件、引擎范围 |
| 网络访问控制 | HTTP 服务（Rust） | 未声明 `network` 时拒绝一切请求 |
| 外部网络控制 | HTTP 服务（Rust） | 未声明 `network-external` 时仅允许回环地址 |
| 通知能力 | `ctx.notifications`（前端） | 未声明 `notification` 时返回空实现并记录警告 |
| 跨模块通信 | `ctx.events`（前端） | 未声明 `plugin-communicate` 时发布被忽略、订阅返回空函数 |
| 模块 ID 冲突 | 编目注册 | 插件不能覆盖内建模块 |
| 卸载清理 | 卸载流程 | 移除注入的样式、脚本与模块，删除插件目录与其数据目录，并摘掉它注册的全部事件订阅与命令 |

这些上限都是**硬拒绝**：超过时命令返回错误而不是截断内容，因此插件不会悄悄拿到半份数据。

权限检查分布在两侧，取决于该能力实际由谁执行：

- **网络**在 Rust 侧检查（`plugin_http_request`）—— 请求由 Rust 发起，前端无法绕过。
- **存储**在 Rust 侧检查（`PluginManager::require_permission`，经 `checked_storage_dir` 统一调用）—— 存储文件由 Rust 读写，且五个存储方法共用同一个检查点。
- **启动外部程序**在 Rust 侧检查（同 `require_permission`）—— 进程由 Rust 创建，前端无法代为 `spawn`。
- **文件图标与文件管理器定位**在 Rust 侧检查（同 `require_permission`）—— 图标由 Shell 与 GDI 提取，前端拿不到本机文件的图标。
- **音频导入**也在 Rust 侧检查（同 `require_permission`）—— 原生选择框与文件读取都由 Rust 完成，因此扩展名与体积上限只有一个执行点。
- **文件拖放**在前端检查（`pluginFileDrop`）—— 事件本身不产生 IPC 之外的动作，但它送来的是**本机路径**，因此与上一条同归 `filesystem-read`。
- **通知**与**跨模块通信**在前端检查（`pluginNotifications` / `pluginEvents`，见 `pluginRuntime.ts`）—— 这两项不发生 IPC 之外的动作，因此前端就是执行点。

两处都只认 kebab-case 权限名。清单里写冒号形式（`filesystem:read`）会在反序列化阶段就被拒绝，因此运行时不必兼容错误拼写。

未声明权限时**不抛错**，而是降级为空实现加一条 `console.warn`。理由是：通知与通信是可选的附加能力，让插件因为一个没声明的选项而整体加载失败，代价远大于收益；而完全静默又会让作者对着「代码跑了但界面没反应」发懵。插件可以用 `ctx.notifications.isAvailable()` / `ctx.events.isAvailable()` 主动查询，自行决定是否降级。

### 6.2 声明但未强制的部分

以下能力在类型与清单中已定义，但当前代码没有据此限制行为。位于「插件开发」相关文档中的权限表若声称这些限制已生效，属于过时描述：

| 项目 | 现状 |
| --- | --- |
| ~~`sandboxLevel`（L0 至 L3）~~ | **已删除**。它描述的是宿主做不到的事（同 realm 无法按等级限制插件），而且此前还会被渲染进插件详情页 —— 一句界面上无法兑现的话。见[清单文件参考](清单文件参考.md)第 6 节 |
| `permissions` 中余下的枚举值 | `filesystem-write`、`filesystem-scoped`、`native-module`、`dev-tools` 声明与否都不改变行为。真正生效的目前是 `storage`、`network`、`network-external`、`process-spawn`、`filesystem-read`（Rust）与 `notification`、`plugin-communicate`、`clipboard`（前端）八项 |
| 代码签名 | 无签名校验逻辑，包结构与清单中也没有签名相关字段 |
| 资源限额 | 无内存或 CPU 限制。模块保活（标签页）会延长插件代码的存活时间，因此这一点的影响比之前更大 |
| 依赖管理 | 清单中没有依赖字段，不存在依赖解析 |

`clipboard` 是 1.5.0 补上的第八项，也是**强制程度最弱**的一项 —— 剪贴板是浏览器 API，插件本来就能直接调 `navigator.clipboard`，因此宿主管住的是"按约定走宿主通道"而不是"拿不到剪贴板"。这一条写进了权限描述，让用户在安装确认页就能看到它和其他项的区别。

这一栏的「是否强制」现在有了机器可读的来源：宿主在 `src-tauri/src/modules/plugins/permissions.rs` 中为每项权限声明 `enforcement`（`host` / `frontend` / `none`），前端通过 `list_plugin_permissions` 取回，三组的数量由测试锁定。界面据此如实标注「声明了但宿主暂不强制」—— 让用户以为某项权限受管控、而它其实不受管控，比不告诉他更危险。

`src/types/plugin.ts` 中还有一批**尚未实现的设计草案**（`PluginContext` 的 `commands` / `views` / `menus` / `fs` / `plugins`、插件生命周期钩子、`PluginAPI` 等）。它们只是记录方向，照它写会直接失败 —— 该文件头部列出了「已实现 / 设计草案」的分界，插件作者应以 `ModulithHost`（`pluginRuntime.ts`）为准。

### 6.3 隔离的实质

插件代码与宿主运行在**同一个 WebView 与同一个 JavaScript 上下文**中。这意味着：

- 插件可以访问 `window` 上的任意内容，包括宿主注入的其他接口。
- 插件可以通过常规 Web 手段发起网络请求，`http` 服务的权限检查只约束经由它发起的请求。
- 插件之间没有相互隔离。
- 插件可以读取宿主已加载的数据。

因此当前模型下，**插件的信任级别等同于应用本身**。安装插件应当视同运行一个本机程序。在引入真正的进程级隔离之前，这一结论不会改变。

#### 一条已经补上的前置：宿主命令默认拒绝

上面这段结论今天**仍然成立**（插件与宿主同 realm，这一点没变），但其中一条最基础的缺口已经堵上：Tauri 对应用自己注册的命令**默认不设门禁**，因此在本轮改动之前，任何一个 webview —— 包括插件 —— 都能调用全部 120 条后端命令，而**权限表里写什么都无关**。

现在 `src-tauri/build.rs` 声明了应用级 ACL 清单，语义反转为默认拒绝，授权按 window / webview 标签匹配。这对 in-process 插件**没有影响**（它们仍在 `main` 这个 webview 里，那上面挂着全部授权），但它曾经是沙箱的**前置条件**。

**1.6.0 之后它不再是沙箱的承重墙。** 插件界面改成跨源 iframe 之后，挡住 IPC 的是"Tauri 不给子框架注入引导脚本"与"IPC 要求 `invoke_key`"这两条（见下面那一节）。ACL 仍然重要 —— 自检窗口就是靠它被挡住的 —— 但**沙箱的安全性不再只依赖它**，这反而是好事：ACL 是配置，前两条是引擎行为。

详见[应用命令的访问控制](../../04-安全/应用命令的访问控制.md)。

#### 已经做到的：插件界面跑在跨源 iframe 里

沙箱的通道已经通了（`src-tauri/src/modules/plugins/sandbox.rs`）：

> **同一个插件代码在两侧能不能不改一行？** 现在**只剩两处差异**，都不是能力：
> `ctx.manifest`（宿主只送 id / 名称 / 版本 / 权限 / 界面表）与
> `Modulith.capabilities` / `Modulith.run`（理由见
> [插件平台完整方案](../../08-规划/插件平台完整方案.md) §7）。9 个已发布插件
> **逐个审计过**，它们用到的每一个成员两侧都有。
>
> 这件事之所以值得写在这里：`Modulith.*` 那一张表**长期没有任何门禁核对过** ——
> `check:sandbox` 的两侧比对只读了 `ctx.*`，于是 `kanban` 用的
> `Modulith.registerCommand` 一直缺着，而它的症状是**整个插件加载时抛
> TypeError**。现在两张表都比。

- 插件界面是宿主页面上的一个 `<iframe>`，来源是自定义协议
  `http://modulith-plugin.localhost`，与宿主**不同源**；
- **它拿不到 IPC**：Tauri 注入的每一个内部初始化脚本都带
  `for_main_frame_only`，子框架里因此没有 `__TAURI_INTERNALS__`、也没有 `invoke`。
  桥接层会主动检查这一点，查到了就写一条 error 进日志（见下）；
- 插件与宿主之间的通信走自定义协议，身份是**每个界面一个不可猜的令牌**
  （`uuid` v4，出现在该界面每条请求的路径第一段）—— 插件伪造不了，也猜不到别人的；
- 插件文档由**宿主合成**（插件包不必自带 HTML），CSP 由宿主写死，
  真插件是 `script-src 'self'`；
- 桥接层（`resources/sandbox-bridge.js`）把 `ctx.*` 变成对宿主的 RPC；
- 资源从插件目录读，判据是"`canonicalize` 之后仍在插件目录之下、且是普通文件"。

界面也已经**接进了标签页**：`SandboxSurface.tsx` 向宿主换一个令牌，然后渲染
`<iframe sandbox="allow-scripts allow-same-origin">`。位置与尺寸由 CSS 决定 ——
宿主这一侧不再测量、不再摆放、不再判断遮挡。

> 📌 v1.6.0 之前这里写的是"界面跑在自己的 webview 里"。那个方案被推翻了：
> 原生子 webview 由引擎合成在父窗口客户区**之上**，CSS 的 `z-index` /
> `position: fixed` / `backdrop-filter` 对它一律无效，于是宿主自己每一块浮起来
> 的界面（标题栏搜索展开、通知中心、轻提示、设置对话框、右键菜单）都会被插件
> 界面盖住。完整推导与源码位置见[插件平台完整方案](../../08-规划/插件平台完整方案.md) §7.3。

已验证：边界四项（无 IPC、令牌身份、通道可用、CSP 生效）在**真实运行**里验过的是
其中三项，第 5 项（"iframe 里到底有没有 IPC"）由自检页里的一个同源探针回答。
记录见[已知问题与技术债](../../06-项目/已知问题与技术债.md) §7.39、§7.40、§7.44。

> ⚠️ **从命令里创建 webview 会让整个应用假死。**
> 同步命令的函数体在 IPC 线程（主线程）上就地执行，而它要等一个只有主线程才能
> 送达的完成通知 —— 于是主线程再不出来。窗口按钮、托盘、其余插件的 IPC 会一起
> 失去响应，而且一处错误都不报。完整推导见 §7.44。
>
> 这条约束与沙箱无关：**任何**建窗口的地方都适用。仓库里现在只剩沙箱自检会建窗口，
> 因此 `sandbox_self_test` 必须保持 `async`；`pnpm check:sandbox` 有断言守着。

> ⚠️ **沙箱的安全性依赖"Tauri 不给子框架注入 IPC"这一件事。**
> 它会**静默**失效：没有报错、没有症状，直到有人发现插件能调宿主命令。
> `check:sandbox` 因此断言桥接层里有一条守卫（`assertNoHostIpc`），
> 而自检页会把它验的东西显示出来。

**但插件今天跑的还是老路**：`ctx.*` 只有 `log` 与 `storage` 有对应的 RPC，
`api: 3` 不存在，9 个已发布插件里**只有 `hello` 迁移过去了**。上面"信任级别等同于
应用本身"这句话对**其余 8 个**仍然成立 —— 不要因为这一段就以为插件已经安全了。

界面上**不再假装**这件事：权限列表旁边会并列显示"已隔离 / 未隔离"，并说明这份
列表在两种模式下分别是"约束"还是"声明"。

#### 功能性插件呢

上面说的是**界面插件**。只有命令、右键菜单、设置、事件而没有自己界面的插件（功能性插件）
**不该得到一个 webview** —— 那会为了一个渲染进程而建一个渲染进程。

它的形态是**按需激活**，而这条路的基础是 v1.5 那轮"贡献点改声明式"买来的东西：
宿主从清单就知道它贡献了什么，因此**不需要运行它的代码**就能把命令、设置、菜单注册好；
代码只在真的要用（命令被调用、事件到达）时才拉起，用完可以回收。

**这一形态在 1.6.0 落地了，承载方是 Node 后台宿主。** 当时留的两个待定点，第一个
已经定了：**不用隐藏的沙箱 webview，用一个独立的 Node 进程** —— 见
[清单文件参考](清单文件参考.md) 2.6 的 `contributes.background`。这样"无界面插件
不该为得到一个 webview 而付出一个渲染进程"那句话就真的成立了，而不是靠一个看不见的
webview 绕过去。

⚠️ **但那条路的边界与 iframe 不是同一个，有一处必须如实告诉用户：**
**`network` / `network-external` 在后台插件那一侧不成立。** 宿主只传
`--permission --allow-fs-read=<插件目录>`、从不传 `--allow-net`，而那个 scope
**只在较新的 Node 里存在**（本机 Node 24.15.0 的 `--help` 里没有它，实测网络完全
不受管）。`ctx.http` 仍然每次都在宿主侧判权限，但插件可以直接 `fetch` 绕过去。

第二个待定点（"插件想活着"与空闲回收的冲突）仍在：`reap_if_idle` 全仓**只有定义、
没有调用方**，`IDLE_TIMEOUT = 300s` 目前形同虚设。理由与它为什么难，见
[已知问题与技术债](../../06-项目/已知问题与技术债.md) §7.41 与 §7.40 的邻近条目。

### 6.4 边界清单：跨过去的是什么

第 6.3 节说的是"今天没有隔离"。这一节说的是**做隔离时会遇到什么** —— 因为一旦插件挪进独立的 realm，入口就只剩消息传递，而消息只能携带结构化克隆能表达的东西：不能带函数、类实例、原型链、DOM 节点。

每一个跨边界成员都登记在 `src/services/pluginBoundary.ts`，并按**形态**分三类。这张表是那个文件的机器可读结果的摘要，由 `scripts/check-plugin-boundary.ts` 对着实际接线断言（新增成员而不登记会让 `pnpm check:plugin-boundary` 失败）：

| 形态 | 含义 | 迁移代价 |
| --- | --- | --- |
| `value` | 纯数据，结构化克隆原样送过去 | 无 |
| `handle` | 对象形态（能力对象）。**今天跨不过去**，但代表的是一组消息往返，换成代理即可 | 机械：对象换代理、方法换消息 |
| `callable` | 函数形态。**没有代理能救** —— 结构化克隆明确拒绝函数 | 要重新设计 |

当前的实际分布：

| 表面 | `value` | `handle` | `callable` | `host-object` |
| --- | --- | --- | --- | --- |
| `Modulith.*`（13 项） | 3 | 0 | 8 | 2 |
| `ctx.*`（17 项） | 5 | 12 | 0 | 0 |

两处值得单独指出：

- **`Modulith.React` / `Fragment` 是 `host-object`，而它们不是能力对象。** 它们是一个活的类实例，v2 要么让插件自带 UI 运行时（9 个已发布插件全部重写），要么让插件交出可序列化的界面描述、宿主负责渲染。这是迁移里最大的一块，取舍见 `docs/08-规划/插件架构与API-v1.5范围.md` 的"分叉 A"。
- **`ctx` 上一个 `callable` 都没有**，这很重要：它意味着 `ctx` 的整体形状对 v2 是安全的。承载权限的那 12 个能力对象可以逐个换成代理。

#### 方法层面：真正的工作量

成员级的 `handle` 只说明"它代表的是一组消息往返"。能不能真的换成往返，取决于**每个方法**的参数与返回值 —— 那由 `src/services/pluginBoundary.ts` 里的 `CAPABILITY_METHODS` 逐条登记，门禁对着**运行时实现**（不是类型声明）核对方法名。

`ctx` 的 12 个能力对象共 40 个方法，其中 **10 个需要改动**：

| 方法 | 形态 | v2 的出路 |
| --- | --- | --- |
| `ctx.http.fetch` / `get` / `post` / `put` / `delete` | `host-object` | **返回的是原生 `Response`** —— 带方法、body 是流，不可克隆。后端本来就只回 `{ status, headers, body }`，v2 应当把数据直接交给插件 |
| `ctx.logger.trace` | `callable` | 返回计时结束函数。改成两个方法（带 token）或宿主侧按 label 计时 |
| `ctx.events.subscribe` | `callable` | 入参是处理函数。改成"宿主推事件、插件按 ID 认领" |
| `ctx.fileDrop.subscribe` | `callable` | 同上 |
| `ctx.settings.onChange` | `callable` | 入参是回调、返回值是取消订阅函数。同上 |
| `ctx.disposables.add` | `callable` | 入参是清理函数。改成"宿主记录插件持有什么" |

其余 30 个方法的参数与返回值都是值，换成消息往返是机械的。

> **读这张表时请不要把它当成"宿主已经做到了什么"。** 它描述的是形态与迁移面，不是当前的隔离强度。当前的隔离强度看第 6.1 与 6.2 节，结论是：只有经由宿主通道的调用受权限约束，其余一律不受约束。

**顺带一提：`ctx.http` 与 `ctx.settings` 目前的使用情况。** 前者在 9 个已发布插件里有 0 处调用、也 0 个插件声明 `network` 权限；后者的 `contributes.settings` 被 0 个插件声明。也就是说这两处的改动**没有现存的迁移成本** —— 这也是为什么它们的重新设计可以放到 v2，而不必在 v1.5 里抢跑。

相关内容记录在[已知问题与技术债](../../06-项目/已知问题与技术债.md)。

### 6.5 开发模式的自动重载

改完插件源码之后，宿主**自己**会重新加载插件 —— 不需要去插件页点刷新，也不需要重启应用。

完整的闭环是两段，分别由两个仓库负责：

| 谁 | 负责 | 怎么开 |
| --- | --- | --- |
| 插件仓库 | 源码 → 产物（`plugins/<插件>/index.js`） | `pnpm dev`（监听 `src/` 与 `types/`） |
| 宿主 | 发现产物变了 → 重新加载插件 | 自动，无需操作 |

宿主这一侧只对**开发链接**的插件生效 —— 即从本地目录安装的插件（`devSource` 非空）。
从 `.lcp` 安装的插件代码来自安装目录的副本，改任何别的地方都不该影响它，这是唯一
说得通的语义。

**它是怎么知道"变了"的。** 每 1.5 秒问一次后端（`dev_plugin_fingerprints`），
拿回每个开发链接插件产物的 `(长度, 修改时间)` 指纹。**不读文件内容** ——
一个多文件构建出来的产物是几百 KB（看板现在是 367 KB），按秒轮询还读回内容
纯属浪费。指纹也不参与任何信任决策，它不是校验和。

变化会**累积**到一个冷静期（两倍轮询间隔）之后才重载。理由：构建工具写产物通常
是"先截断再写"，一次保存在两次轮询之间会留下两个不同的指纹；立刻重载可能读到
半成品，而半成品的表现是**加载失败** —— 作者会以为是自己改坏了。

**没有开发链接插件时，宿主不建这个定时器。** 普通用户装上几个 `.lcp` 插件之后，
不该因为宿主里住着一段轮询而付出代价。

#### 它替换不掉什么

- **插件 bundle 顶层的同步死循环无法被中断。** JS 单线程，宿主救不回卡住的主线程
  （见[已知问题](../../06-项目/已知问题与技术债.md) §4.4）。自动重载解决不了这一类 ——
  只有把插件挪进独立进程才能解决，那是 v2.0 的事。
- **它只重载插件，不重载宿主。** 改了宿主自己的代码（`src/` 下的应用代码）仍然需要
  按前端的热更新或重启应用来处理；自动重载管的是"插件产物变了"。
- **懒激活插件由"谁被用到"决定何时重新执行。** 重载会清空激活状态，因此一个当前
  打开的模块会立刻重新执行；而一个没打开的模块，要等它下次被打开。

#### 一个被顺带修掉的缺陷

`reloadPluginRuntime()` 此前**不清空已经加载过的插件的激活状态**，而
`activatePlugin()` 在开头对 `active` 状态直接早退。因此重载之后，**懒激活插件**的
bundle 永远不会再执行 —— 而它的 DOM、组件缓存与模块描述符都已经在重载里被清掉了。

表现是「重载之后点开那个模块是空白」，只有重启应用才恢复。eager 插件看不出来，
因为它们紧接着就被重新执行了一遍。这是自动重载能生效的前提，所以一并修了。

## 7. 数据结构
后端为每个已安装插件维护一条注册信息：

| 字段 | 说明 |
| --- | --- |
| `id` | 清单的 `name`，同时是目录名与存储命名空间 |
| `version` | 插件版本 |
| `enabled` | 是否启用 |
| `installedAt` | 安装时间 |
| `source` | 来源描述 |

前端侧的运行时状态包含每个插件的加载结果：`loaded` 或 `error`，以及加载失败的原因和注册到的模块 ID 列表。

### 7.1 磁盘布局

```
<app_data>/
  plugins/<id>/<version>/        解压后的插件本体（manifest.json、dist/…）
  plugin_data/<id>/<key>.json    插件通过 storage 写入的键值数据
```

键值存储是「**一个键一个文件**」，文件名由键名加 `.json` 得到。这样做的代价是键很多时目录会变得宽散，但换来三点：写入是单文件操作、不需要维护一份索引文件、某个键损坏不会连累其他键。`storage.keys()` 直接枚举目录并按文件名排序返回（`file_stem` 去掉 `.json`），因此键名不区分大小写这类文件系统差异会反映到枚举结果上。

键名必须通过校验：非空、不超过 128 字符、只含字母数字与 `.` `_` `-`。校验不通过返回沙箱违规错误而不是降级处理。值必须是合法 JSON——`storage.set` 会先 `serde_json::from_str` 解析一遍，再以**格式化 JSON**写回，因此写入的字符串会被规范化（键顺序、空白都可能与传入时不同），插件不应依赖读取到的字符串与写入时逐字节相同。

**卸载插件会同时删除 `plugins/<id>/` 与 `plugin_data/<id>/`**，不再是「数据保留以便重装恢复」的语义。`storage.clear()` 只清空该插件的数据目录，保留插件本体。

## 8. 日志与诊断

插件日志通过 `ctx.logger` 输出，统一带有 `[plugin:<id>]` 前缀，便于在开发者工具中过滤。

加载失败的详细信息展示在插件管理界面中。应用启动阶段插件加载失败不会阻断启动，而是作为告警在主界面顶部呈现。
