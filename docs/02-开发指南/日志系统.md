# 日志系统

本文说明应用把日志写到哪、谁能开关它、崩溃记录为什么单独成一个文件，以及如何在界面上查看。

## 1. 起点：一份从来没有输出过的日志

后端一直依赖 `log`（`Cargo.toml` 里有它），代码里也一直有几十处 `log::info!` / `log::warn!` / `log::error!`。但 `log` 只是一个**门面**：没有安装后端时，每条记录都被直接丢掉。

于是实际情况是：

- `log::warn!("读取应用设置文件失败，使用默认设置: {}")` 这样的句子写了很久，一次也没出现过；
- release 版是 `windows_subsystem = "windows"`，连 `eprintln!` 都没有出口（`src-tauri/src/lib.rs` 里四处 `eprintln!` 同样不可见）；
- 前端的错误只进 devtools 控制台，而用户打不开 devtools。

结果就是「软件更新连接失败」这类问题没有任何证据。日志系统的第一目标因此不是「加日志」，而是**让已经写好的日志真的存在**。

## 2. 结构

| 文件 | 职责 |
| --- | --- |
| `src-tauri/src/modules/logging/logger.rs` | 文件日志器本体、轮转、崩溃记录、panic 钩子、全局安装 |
| `src-tauri/src/modules/logging/commands.rs` | 目录/内容/清空三条命令，以及前端日志与前端崩溃的两条入口 |
| `src-tauri/src/modules/logging/mod.rs` | 模块注册、启动时按设置配置、设置变化时套用 |
| `src/services/logger.ts` | 前端到后端日志文件的那条通道 |

不引入 `tauri-plugin-log` 的原因有两个，都是需求直接决定的：**运行期开关**（用户要能随时关闭实时记录，而插件的目标在启动时就固定了）与**崩溃记录独立成一个开关和一个文件**。

## 3. 安装与配置分成两步

日志目录要通过 `AppHandle` 解析（`app.path().app_log_dir()`），而 `AppHandle` 只有在 Tauri 的 setup 阶段才有。偏偏最早的那几条记录最有用（授权模块就绪、插件目录在哪）。

因此：

1. `src-tauri/src/main.rs` 在 `run()` **之前**调用 `logging::install_early()`：安装 logger 与 panic 钩子，此时没有目录，记录进入内存队列（上限 512 条，满了丢掉最早的并在落盘时补一条说明）。
2. `LoggingModule::setup()` 解析出目录后调用 `configure()`，队列按原顺序补写到文件开头，并写一行会话头（时间、版本、平台、日志路径）。

模块顺序取自目录名的字母序，`auth` 排在 `logging` 前面，因此 `auth` setup 里那几行一定会进入队列而不是被丢掉。

## 4. 文件与轮转

日志目录是 `app.path().app_log_dir()`：Windows 上是 `%LOCALAPPDATA%\<identifier>\logs`，macOS 上是 `~/Library/Logs/<identifier>`。

| 文件 | 大小上限 | 保留个数 |
| --- | --- | --- |
| `modulith.log` | 1 MB | 3（含当前文件：`modulith.log`、`modulith.1.log`、`modulith.2.log`） |
| `crash.log` | 256 KB | 2 |

轮转在上限处发生：删掉最旧的一个，其余依次后移。运行日志的总上限因此是 3 MB —— 日志的价值随时间迅速衰减，而一个几百 MB 的日志文件本身就是新的问题（用户没法把它发出来）。

**写入是同步的，而且一定不 panic。** 日志器在 `Mutex` 后面直接写文件，不另开写线程（量小，且多一个线程就多一处「日志线程自己挂了没人知道」的可能）。拿不到锁（持锁线程 panic 了）时用 `into_inner()` 继续；写盘失败静默放弃。日志系统在「上一条日志写崩了」之后必须仍然能工作。

## 5. 两个开关为什么是分开的

| 字段 | 默认 | 作用 |
| --- | --- | --- |
| `fileLoggingEnabled` | `true` | 是否把运行日志写入文件 |
| `crashLoggingEnabled` | `true` | 是否把崩溃写入 `crash.log` |

- 默认开启实时记录：日志是出问题时唯一的证据，而用户不会为了排查问题提前打开它 —— 默认关闭等于默认没有证据。
- 两者相互独立：关掉实时记录正是为了少写磁盘，而崩溃是低频事件，几乎不占资源，却恰恰是崩溃后唯一能拿到的线索。
- **关掉实时记录后 release 版完全不再写任何日志**；调试构建仍然镜像到 stderr（`tauri dev` 的终端），因为那是加文件日志之前唯一能用的东西，不该因为加了这个功能就失去。
- 两个开关都是**运行期生效**的：`update_app_settings` / `reset_app_settings` 在保存之后调用 `logging::apply()`。让用户「关掉实时记录」却要重启才生效，等于这个开关是假的。

## 6. 崩溃记录

两个来源写进同一个 `crash.log`：

**Rust 侧**：`install_panic_hook()` 保留原有钩子并继续调用它（默认钩子会打印带回溯的信息，开发时有用），同时把「线程名 + 位置 + panic 载荷」写进崩溃日志。release 版 GUI 进程没有 stderr，写文件才是真正的价值所在。

**前端侧**：`report_frontend_crash` 命令。调用点有四处：

| 位置 | 覆盖的现象 |
| --- | --- |
| `services/globalErrorHandlers.ts` | `window.onerror`、`unhandledrejection` |
| `components/AppErrorBoundary.tsx` | 根级渲染崩溃（用户看到错误页） |
| `components/ModuleRenderer.tsx` | 单个模块渲染失败（用户看到某个页面坏了） |
| `components/ModuleEmbed.tsx` | 设置里内嵌的「插件」「市场」两页加载失败 |

四处都保留原有的 `console.error`：控制台那份带可展开的堆栈，是开发时定位问题的第一手材料；文件那份是用户唯一能发出来的材料。

## 7. 前端日志通道的三条约束

`src/services/logger.ts`：

1. **永不抛错、永不 reject。** 一个日志调用失败不该影响任何业务逻辑，因此 `invoke` 的结果被丢弃而不是 await。
2. **失败一次就闭嘴。** 后端不可用时每次调用都会失败；若无脑重试并 `console.error`，会被全局错误处理器接住再回来调用它 —— 形成无限回环。因此一旦发现通道不可用，就永久回落到控制台。
3. **不 await。** 调用方是错误处理器与插件代码，它们不该因为写日志而变成异步。

插件的 `ctx.logger` 也接到这条通道上（target 为 `plugin:<id>`）：插件作者的 `logger.info(...)` 此前同样只进 devtools，于是「插件不工作」既没有插件自己的证据，也没有宿主的证据。

## 8. 界面

「设置 → 日志」：

- 两个开关；
- 日志目录的完整路径 + 「打开文件夹」（走 `@tauri-apps/plugin-opener`，作用域已在 `capabilities/default.json` 里覆盖 `$APPLOCALDATA/**`）；
- 最近一段日志（`read_log_tail`，默认 32 KB、上限 128 KB）。只读尾部是因为日志上限 3 MB，全量传给 WebView 再渲染进 `<pre>` 会让设置页卡住，而用户真正要看的是最新的一段；
- 「清空」。它由日志器自己完成（`FileLogger::clear()`）而不是让调用方删文件：Windows 上删除一个仍被打开的文件会失败，必须先关句柄再删、再重新打开。

读取尾部时从第一个换行之后开始，避免把一条被截断的记录（半行、半个 UTF-8 字符）当成第一行显示 —— 那看起来像是日志本身坏了。

## 9. 级别

`log::set_max_level(LevelFilter::Debug)`，不分构建类型。

原因是 `tauri-plugin-updater` 自己会在 debug 级别打出 `checking for updates {url}` —— 那正是「更新连不上」时最需要的一行，而它不在我们的代码里，没法把它提到 info。文件有轮转上限，量是可控的；我们自己的网络相关记录则一律写在 `info` / `warn` / `error` 上。

## 10. 隐私

日志只写在本机，不会自动上传。内容可能包含插件 ID、文件路径与联网地址（含用户配置的下载源地址），因此界面在日志区的末尾明确提示：分享前请自行确认。

`githubProxy` 的校验拒绝带用户名密码的地址（`https://user:pw@host`），理由之一就是它会被写进日志 —— 一条会漏密码的日志比没有日志更糟。
