# 模块开发

本文说明如何为 Modulith 新增一个内建模块。内建模块随应用编译发布，与运行期安装的[插件](插件开发/插件系统架构.md)不同。

## 1. 模块形态

内建模块有两种形态，按是否需要后端能力选择。

| 形态 | 组成 | 适用场景 |
| --- | --- | --- |
| 仅前端 | `module.toml` + 组件 | 纯界面功能，不需要读写文件或访问系统能力 |
| 前后端 | 上述内容，外加 `src-tauri/src/modules/<id>/` | 需要持久化、系统调用或后台任务 |

两种形态对前端是透明的：模块注册表只关心前端部分，后端部分通过 Tauri 命令独立暴露。

## 2. 目录布局

**前端部分**

```
src/modules/<folder>/
  module.toml          模块清单，必需
  <Component>.tsx      入口组件，文件名由清单的 component 字段指定
  ...                  其余组件、hooks 与工具
```

`<folder>` 是目录名，与模块 `id` 可以不同。现有模块中两者一致。

**后端部分**

```
src-tauri/src/modules/<id>/
  mod.rs               模块声明，实现 Module trait
  commands.rs          Tauri 命令与状态定义
  ...                 按需拆分的其余文件
```

后端目录名必须等于模块 `id`，因为生成器通过目录名推导模块类型名。

## 3. module.toml 参考

```toml
[module]
id = "notePad"
name = "笔记"
description = "随手记录与检索"
icon = "FileText"
path = "/note-pad"
priority = 20
category = "tools"
component = "NotePad.tsx"
```

| 字段 | 类型 | 必需 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | string | 是 | - | 模块唯一标识 |
| `name` | string | 是 | - | 侧边栏显示名 |
| `description` | string | 是 | - | 一句话描述 |
| `icon` | string | 是 | - | lucide-react 图标名 |
| `path` | string | 是 | - | 逻辑路径 |
| `component` | string | 是 | - | 入口组件文件名 |
| `priority` | number | 否 | `999` | 排序权重，升序 |
| `category` | string | 否 | - | 分组名 |
| `visible` | boolean | 否 | `true` | 是否进入导航视图 |
| `disabled` | boolean | 否 | `false` | 是否禁用 |
| `badge` | string | 否 | - | 角标文本 |

关于 `description`：生成器的必填校验只覆盖 `id`、`name`、`icon`、`path`、`component` 五项，但类型定义要求 `description` 存在。缺失时生成的注册表中该字段为 `undefined`，界面会显示为空白。因此应始终填写。

关于 `component`：必须写出具体文件名，例如 `NotePad.tsx`。生成器不接受省略，也不会自动回退到 `index.tsx`。

关于 `icon`：填 lucide-react 的组件名（如 `FileText`）。生成器会把它收进 `src/generated/iconMap.ts`，因此**改完 icon 必须重新运行一次生成**（`pnpm gen:modules`，或直接 `pnpm dev` / `pnpm build`，两者都会触发）。若名字不在生成器的图标白名单中，只会打印告警而不中断构建，此时运行时的图标解析会退化为按需加载或通用图标兜底。

`visible = false` 的模块不会出现在侧边栏与仪表盘等导航视图中，但仍可通过代码打开。`plugins` 模块即采用此设置，其入口位于设置的「插件」分页。

## 4. 命名规则

| 对象 | 规则 | 强制来源 |
| --- | --- | --- |
| 前端模块 `id` | 字母、数字、`-`、`_`，长度 1 至 64 | 运行时校验 `isValidModuleId` |
| 前端模块 `path` | 以 `/` 开头，不含 `..`，长度小于 256 | 运行时校验 `isValidModulePath` |
| 后端模块目录名与 `id` | 小写字母开头，只含小写字母、数字、下划线 | 生成器 `pnpm gen:backend new` |

后端要求 snake_case 是因为目录名会被转换为 Rust 类型名（`my_module` 转为 `MyModule`）。使用驼峰或连字符会导致生成的代码不符合 Rust 命名规范。

建议前后端统一使用 snake_case，并在 `path` 中使用连字符形式（例如 `id = "note_pad"` 时 `path = "/note-pad"`）。现有内建模块的前端 `id` 采用小驼峰（`dashboard`、`plugins`），与后端 ID 不同，这是允许的：两者通过各自目录独立管理，没有强制的同名要求。

## 5. 新增仅前端模块

以创建一个名为 `notePad` 的模块为例。

**第一步：创建目录与清单**

```bash
mkdir src/modules/notePad
```

写入 `src/modules/notePad/module.toml`：

```toml
[module]
id = "notePad"
name = "便签"
description = "临时记录一些文本"
icon = "FileText"
path = "/note-pad"
priority = 30
category = "tools"
component = "NotePad.tsx"
```

`FileText` 在生成器的图标白名单中。若使用白名单之外的图标名，生成时会输出告警，但仍会正常生成——白名单只用于发现拼写错误。

**第二步：创建组件**

写入 `src/modules/notePad/NotePad.tsx`。模块组件是一个普通 React 组件，接收空 props：

```tsx
import React from 'react';

const NotePad: React.FC = () => {
  return (
    <div className="p-6">
      <h1 className="text-xl font-semibold text-gray-900">便签</h1>
      <p className="mt-2 text-sm text-gray-500">在这里实现你的功能。</p>
    </div>
  );
};

export default NotePad;
```

组件必须提供默认导出。生成器生成的是 `lazy(() => import('...'))`，依赖默认导出。

**第三步：生成注册表**

开发服务器运行时通常无需手动操作，Vite 插件会检测到变化并自动重新生成。若要立即生成：

```bash
pnpm gen:modules
```

生成成功后会输出模块清单，失败则返回非零退出码并指出具体问题。

**第四步：验证**

`pnpm tauri dev` 启动后，侧边栏应出现「便签」。若未出现，检查启动界面与终端输出，并查看 `src/generated/generation.log.json`。

## 6. 新增带后端的模块

在上一节的基础上增加后端能力。

**第一步：生成后端骨架**

```bash
pnpm gen:backend new note_pad "便签"
```

该命令创建 `src-tauri/src/modules/note_pad/{mod.rs,commands.rs}`，并自动刷新 `modules/mod.rs` 与 `lib.rs`。

返回包中的模块名（`id`）必须使用 snake_case。

**第二步：编写命令**

编辑 `src-tauri/src/modules/note_pad/commands.rs`。生成的骨架已包含一个状态结构体与示例命令，按实际需要替换：

```rust
use crate::prelude::*;
use tauri::State;
use std::sync::Mutex;

/// 模块的全局状态
pub struct NotePadState(pub Mutex<Vec<String>>);

impl NotePadState {
    pub fn new() -> Self {
        Self(Mutex::new(Vec::new()))
    }
}

#[tauri::command]
pub fn list_notes(state: State<'_, NotePadState>) -> Result<Vec<String>, String> {
    let notes = state.0.lock().map_err(|e| format!("锁失败: {}", e))?;
    Ok(notes.clone())
}

#[tauri::command]
pub fn add_note(state: State<'_, NotePadState>, text: String) -> Result<Vec<String>, String> {
    if text.trim().is_empty() {
        return Err("内容不能为空".to_string());
    }
    let mut notes = state.0.lock().map_err(|e| format!("锁失败: {}", e))?;
    notes.push(text);
    Ok(notes.clone())
}
```

命令约定见[后端架构](../01-架构/后端架构.md)第 4 节。要点是：返回 `Result<T, String>`，错误信息为可直接展示的中文，状态通过 `State` 注入。

**第三步：刷新注册**

```bash
pnpm gen:backend update
```

`pnpm dev` 与 `pnpm build` 会自动执行该步骤。生成器扫描 `commands.rs` 中的 `#[tauri::command]` 标注并汇总到 `lib.rs`。

若修改了模块的 `setup` 或新增了状态托管，`mod.rs` 中的内容不会被生成器覆盖——生成器只负责 `modules/mod.rs` 与 `lib.rs` 两个汇总文件，模块自身文件不会被改动。

**第四步：前端调用**

```ts
import { invoke } from '@tauri-apps/api/core';

const notes = await invoke<string[]>('list_notes');
await invoke<string[]>('add_note', { text: '第一条' });
```

参数名使用 camelCase 或 snake_case 均可，Tauri 2 会自动转换。

**验证**

```bash
cd src-tauri && cargo test --offline --lib
cd src-tauri && cargo check --offline --lib
```

## 7. 子模块

一个模块可以包含子模块，它们会作为可展开的分组出现在侧边栏。

```toml
[module]
id = "reports"
name = "报表"
description = "数据报表"
icon = "BarChart3"
path = "/reports"
component = "Reports.tsx"

[[children]]
id = "daily"
name = "日报"
description = "每日汇总"
path = "/reports/daily"
component = "Daily.tsx"

[[children]]
id = "monthly"
name = "月报"
description = "每月汇总"
path = "/reports/monthly"
icon = "FileText"
component = "Monthly.tsx"
```

子模块的完整 ID 为 `<父模块 id>/<子模块 id>`，例如 `reports/daily`。子模块的 `path` 若不填写，默认为 `<父模块 path>/<子模块 id>`。

子模块的图标可选，未提供时使用父模块图标。

## 8. 模块的生命周期

前端模块没有生命周期钩子。组件由 `ModuleRenderer` 在需要时渲染，模块的可见性、排序等状态由后端的 `sidebar` 模块统一管理。

后端模块实现 `Module` trait，生命周期为：

| 阶段 | 时机 | 典型用途 |
| --- | --- | --- |
| `setup` | 应用启动早期 | 读取配置、通过 `app.manage()` 托管状态 |
| `start` | 所有模块 `setup` 完成之后 | 启动后台任务 |
| `stop` | 预留 | 当前框架未调用 |

`setup` 按依赖拓扑序执行。若模块之间存在初始化顺序要求，通过 `dependencies()` 声明，不要依赖注册顺序。细节见[后端架构](../01-架构/后端架构.md)第 2.3 节。

## 9. 移除模块

**后端**

```bash
pnpm gen:backend delete note_pad
```

该命令删除模块目录并刷新汇总文件。

**前端**

删除 `src/modules/<folder>` 目录，然后运行 `pnpm gen:modules`。生成器会重新扫描，被删除模块从注册表消失。

前端部分没有对应的删除命令，因为它不涉及生成文件的引用清理。

## 10. 排查

| 现象 | 可能原因 |
| --- | --- |
| 生成时报「Duplicate module ID」 | 两个模块使用了相同 `id` |
| 生成时报「Missing required fields」 | 清单缺少 `id`、`name`、`icon`、`path` 或 `component` |
| 生成时报「Icon not found in lucide-react」 | 仅是告警，图标名可能拼写有误 |
| 模块出现但界面空白 | 组件缺少默认导出，或渲染时抛错；检查浏览器控制台 |
| 后端命令调用报「command not found」 | 未运行 `pnpm gen:backend update`，命令未注册到 `lib.rs` |
| 后端编译报命名规范警告 | 模块目录名不是 snake_case |
