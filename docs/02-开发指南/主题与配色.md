# 主题与配色

本文说明界面外观系统的实现：深浅模式、主题配色（强调色）、动效开关，以及如何新增一套配色。

涉及的源文件：

| 文件 | 职责 |
| --- | --- |
| `src/services/theme.ts` | 深浅模式（`light` / `dark` / `system`）与动效开关 |
| `src/services/accent.ts` | 由基色推导整套配色变量 |
| `src/config/accentTheme.ts` | 内置配色表 |
| `src/styles/global/dark-theme.css` | 深浅映射层 |
| `src/styles/global/accent.css` | 配色变量定义与工具类重定向 |
| `src/components/ThemeProvider.tsx` | 把上述服务接入 React 树 |
| `src/components/Sidebar/ThemeToggle.tsx` | 侧边栏底部的深/浅快捷切换 |
| `index.html` 内联脚本 | 首帧预置（避免启动闪色） |

## 1. 两个正交的维度

外观由两个**互相独立**的设置决定：

| 设置项 | 取值 | 决定 |
| --- | --- | --- |
| `theme` | `light` / `dark` / `system` | 明暗 |
| `accent` | 配色 id（见第 4 节） | 色相 |

因此「深色 + 蓝色」「浅色 + 灰色」等组合都成立。两者互不影响，各自可以独立修改。

## 2. 为什么不用 `dark:` 变体

深色模式**没有**在组件里写 `dark:` 变体，而是由 `dark-theme.css` 用属性选择器匹配工具类名：

```css
:root.dark [class~='bg-white'] {
  background-color: #1a1e2b;
}
```

`[class~='bg-white']` 与 `.bg-white` 等价（都是单类选择器），但**不会命中** `bg-white/90` 这类带透明度修饰符的类——正好避免误伤半透明浮层（侧边栏、标题栏）。

**决定性理由是插件。** 插件由第三方编写，不可能配合补 `dark:` 变体。若深色只靠组件内的变体实现，任何插件界面在深色模式下都会是白底黑字，与宿主割裂。全局映射让插件只要使用常规 Tailwind 工具类就能自动跟随主题。

代价是**必须维护映射表**：引入新的颜色工具类时要补一条，否则深色下会漏掉（该处会保持浅色取值，通常表现为深色界面上一块刺眼的白）。

## 3. 配色也是变量重定向

主题配色沿用了同一思路，但更进一步——把品牌色工具类重定向到 CSS 变量：

```
组件：bg-indigo-600（写法固定，不随配色变）
  ↓
accent.css：[class~='bg-indigo-600'] { background-color: var(--accent-600); }
  ↓
accent.ts：由基色推导出 --accent-50 … --accent-900
```

**为什么不逐个改组件类名。** 项目有 50 种品牌色工具类、约 178 处使用。全部改成 `bg-accent-600` 之类的自定义类，改动面大、评审困难，且以后再换方案还要再改一遍。变量重定向让组件保持原样，**新增一套配色只需在 `accentTheme.ts` 加一行**。

**只声明基色，其余推导。** 界面用到 `-50` 到 `-700` 以及深色模式的 `-200` 到 `-900` 共十余档。若每套配色手写这些值，配色表会膨胀到数百行且极易出现某档不一致，实际不会有人认真维护。`buildAccentVariables` 按 HSL 明度规律推导，各档必然协调。

无彩色主题（`gray`）单独处理：饱和度归零、浅底改用中性灰，否则会与界面自身的灰阶撞色。

## 4. 内置配色

10 套，定义在 `src/config/accentTheme.ts`：

| id | 名称 | 基色 | 备注 |
| --- | --- | --- | --- |
| `indigo` | 靛蓝 | `#4f46e5` | 默认 |
| `violet` | 紫罗兰 | `#7c3aed` | |
| `blue` | 蓝色 | `#2563eb` | |
| `cyan` | 青色 | `#0891b2` | |
| `teal` | 蓝绿 | `#0d9488` | |
| `emerald` | 翠绿 | `#059669` | |
| `amber` | 琥珀 | `#d97706` | 与警告语义色相近 |
| `orange` | 橙色 | `#ea580c` | |
| `rose` | 玫红 | `#e11d48` | 与危险语义色相近 |
| `gray` | 灰白 | `#4b5563` | 无彩色 |

**语义色不参与配色。** 红（错误）/ 琥珀（警告）/ 绿（成功）保持固定。这意味着选择相近色相时，品牌色与警示色的区分会变弱——这是配色功能的固有取舍，已在设置页向用户说明，而不是通过限制可选配色来回避。

## 5. 新增一套配色

**只需两步，不必碰 CSS。**

第一步，在 `src/config/accentTheme.ts` 的 `ACCENT_THEMES` 里加一行：

```ts
export const ACCENT_THEMES: AccentTheme[] = [
  // …
  { id: 'sky', label: '天蓝', base: '#0284c7' },
];
```

第二步，在 `index.html` 的内联脚本里同步一行（原因见第 6 节）：

```js
var ACCENT_BASES = {
  // …
  sky: ['#0284c7', 0]
};
```

`id` 需要用 `[a-z0-9-]`（后端只校验格式，见第 7 节）。`label` 是设置页显示名。

**不需要改 `accent.css`。** 那层是把工具类重定向到变量，与具体配色无关。

如果新增的配色需要「无彩色」处理（浅底应当是中性的灰而不是纯白），加上 `neutral: true`，并在内联脚本里把第二项写成 `1`。

## 6. 首帧：为什么有两份实现，以及必须同步

WebView 在解析到 `<head>` 时就开始绘制，而 React 挂载要等 JS bundle 求值完成。如果等设置加载完再写配色变量，用户会先看到一帧默认靛蓝再跳到自己选的颜色。

因此 `index.html` 的**内联脚本**会在首帧前：

1. 读 `localStorage` 缓存（`modulith.theme` / `modulith.accent`）决定深浅与配色；
2. 就地推导并写入 `--accent-*` 变量；
3. 设置 `data-theme` / `data-resolved-theme` / `data-accent` 与背景色。

**代价是配色表与推导算法有两份实现**：

| 位置 | 内容 |
| --- | --- |
| `src/config/accentTheme.ts` + `src/services/accent.ts` | 权威实现（TypeScript） |
| `index.html` 内联脚本 | 首帧副本（纯 JS，不能用模块系统） |

**改一处必须改两处**，否则首帧与后续渲染会出现色差（表现为启动瞬间颜色不对，随后跳正）。两处代码注释都标注了这一点。

## 7. 后端只做格式校验

`settings.json` 的权威性由后端持有，但配色 id 的**有效性**不在这里校验：

| 后端校验 | 前端处理 |
| --- | --- |
| 非空、长度 ≤ 32、字符集 `[a-z0-9-]` | 是否为已知配色：未知 id 由 `getAccentTheme()` 回退到默认 |

理由：配色表定义在前端，后端复制一份清单必然漂移，而漂移的后果是「前端加了新配色、后端拒绝保存」。未知 id 回退是安全降级，不会导致界面异常。

## 8. 动效开关

设置中的「关闭界面动画」（`reduceMotion`）通过两条路径生效，**缺一不可**：

| 路径 | 覆盖范围 | 实现 |
| --- | --- | --- |
| CSS | CSS 动画与过渡 | 根元素加 `.lc-reduce-motion`，把 `animation-duration` 与 `transition-duration` 压到 `0.001ms` |
| JS | framer-motion 动画（含 spring 与 layout 动画） | `<MotionConfig reducedMotion="always">`，位于 `ThemeProvider` |

只做其中一件都会留下明显还在动的部分。

用 `0.001ms` 而不是 `0` 或 `transition: none`：部分浏览器在 `transition: none` 下不会触发 `transitionend`，会让依赖该事件结束的逻辑卡住。

**不覆盖**手写的 `setTimeout` / `setInterval` 驱动的变化（提示条自动消失、启动界面计时刷新）。那些是功能行为，不是装饰动画。

## 9. 快捷切换

侧边栏底部有深/浅色快捷切换（`ThemeToggle`）。它**不走**主题服务直连，而是写回 `appSettings`：

```
点击 → saveAppSettings({ theme }) → 后端落盘 + notify()
                                    ↓
                              ThemeProvider 订阅 → setThemeMode() → document
                                    ↓
                              设置页订阅 → 三选一高亮同步
```

一条链路、两个消费者，因此侧边栏切换后设置页会同步更新，反之亦然。

当前模式为「跟随系统」时，点击切换的是**当前实际呈现颜色的相反值**（系统深色 → 点一下变浅色并固定），而不是在 dark/light 之间盲翻。
