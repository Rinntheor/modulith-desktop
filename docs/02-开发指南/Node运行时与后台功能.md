# Node 运行时：怎么让后台功能在用户机器上可用

这份文档回答一件具体的事：**后台宿主需要 Node，而 Node 不是应用的依赖。**
它怎么进到用户机器上、怎么被找到、出问题时怎么查。

对应代码：`src-tauri/src/modules/desktop/background/mod.rs` 的 `resolve_node()`。

---

## 一、为什么需要 Node

应用要有「窗口关掉之后仍然继续工作」的能力（后台插件、设备使用监测）。
界面插件跑在主窗口的 WebView 里，而那个环境会被隐藏、被降级（内存目标等级设为
Low）、脚本会被浏览器冻结 —— 把「凌晨三点准时提醒」托付给它，等于托付给一个
随时可能被挂起的执行环境。

因此后台能力跑在一个**独立的 Node 进程**里（`resources/background-host.mjs`），
与宿主用 stdio 上的行分隔 JSON 通信。

代价就是这一份文档要解决的问题：**那个进程需要在用户机器上有一个 Node。**

---

## 二、查找顺序（这就是"软件怎么调用到 node"）

`resolve_node()` 按下面顺序找，**第一个存在的就用**：

| 顺序 | 位置 | 谁会用 |
|---|---|---|
| 1 | 设置 → 性能 里手工指定的路径 | 普通用户：选一次就记住，不用碰环境变量 |
| 2 | 环境变量 `MODULITH_NODE` | 开发与排障 |
| 3 | `<应用目录>/runtime/node.exe`<br>`<应用目录>/resources/runtime/node.exe` | 随包分发（见第五节） |
| 4 | `C:\Program Files\nodejs\node.exe`、`%ProgramFiles(x86)%`、<br>`%LOCALAPPDATA%\Programs\nodejs`、`%APPDATA%\nodejs` | 官方安装程序的默认落点 |
| 5 | 系统 `PATH` 上的每一个目录 | 用户已经装过 Node 的情况 |

第 4 条还可以用环境变量 `MODULITH_NODE_SEARCH_BASES` **替换**（`;` 分隔）。
它是给两种真实情况准备的：测试要造出「哪里都没有 Node」的前提；以及用户把 Node
装在非常规前缀下（企业环境、便携部署）。

### 为什么以前会「cmd 里有、软件里没有」

因为**原实现只有第 2、3 条，没有第 4、5 条**。而 cmd 会走 `PATH`，应用不会。

```
cmd:  node --version  →  v24.9.0        （走的 PATH）
旧版: 后台宿主探测     →  未找到 Node   （只看了环境变量与应用目录）
```

用户会以为是自己环境变量没配好，而其实是应用少找了一个地方。**第 4、5 条就是
为这个缺陷补的。**

## 三、Windows 上有一个坑：`node` 可能只是一个 `.cmd`

`where node` 在一台装了 Node 版本管理器（或 Electron 的 `ELECTRON_RUN_AS_NODE`）
的机器上会给出**多行**：

```
C:\Users\...\dsh-desktop\harness\.desktop-bin\node.cmd     ← .cmd 包装脚本
D:\...\resources\app\node_modules\node\bin\node.exe        ← 真实文件
C:\Program Files\nodejs\node.exe                            ← 真实文件
```

`.cmd` 是**批处理脚本**，不是可执行文件。`Command::new()` 不能直接执行它
（它需要 `/c` 走 `cmd.exe`，那会引入一层进程与一次引号地狱）。

因此**查找代码里逐目录检查 `node.exe` 是否存在**，而不是把裸 `node` 交给系统去
解析 —— 后者在 Windows 上会命中的是那个 `.cmd`。

这也是那一节手动输入框里提示「取以 `.exe` 结尾的那一行」的原因。

---

## 四、体积：单文件就够（实测）

`node.exe` 在 Windows 上是**自包含**的（所需运行库静态链接）。实测：

```
空目录里只放一个 node.exe：
  node.exe --version                    → v24.15.0
  管道喂一行握手给它 + background-host.mjs
    → {"v":2,"runtime":"node/v24.15.0","pid":16140}
    → [background] 宿主已启动 pid=16140 node=v24.15.0 协议=2
```

也就是说，**不需要**同目录的 `npm`、`npx`、`node_modules`。

| | 大小 |
|---|---|
| 单个 `node.exe`（v24，x64，未压缩） | 约 87 MB |
| 完整 nodejs 目录 | 200 MB 以上 |

**不要复制整个安装目录。** 只有 `node.exe` 是需要的。

## 五、随包分发（让用户零配置）

### 5.1 放文件

```
src-tauri/runtime/node.exe
```

从官方发行版 `node-vXX.X.X-win-x64.zip` 的根目录取，只要那一个文件：

```powershell
Copy-Item .\node-v24.15.0-win-x64\node.exe src-tauri\runtime\node.exe
```

### 5.2 它怎么进安装包

`tauri.conf.json` 的 `bundle.resources` 里有一条：

```json
"runtime/*": "resources/runtime/"
```

打包后落在安装目录的 `resources/runtime/node.exe`。

**`*` 通配是刻意的**：目录为空时构建照常成功。写成固定的 `runtime/node.exe`
会让「没有放 Node」变成构建错误，而那与「它是可选的」矛盾。

### 5.3 两个必须匹配的东西

- **架构**：x64 的应用配 x64 的 `node.exe`。放错架构的表现是「后台宿主启动后
  立即退出」，而原因不会自己出现在日志里。
- **版本**：需要 Node 16 以上（宿主脚本用了 `node:` 前缀的内置模块）。
  当前用 v24 验证通过。

协议版本 `PROTOCOL_VERSION` 与 Node 版本**无关** —— 它是脚本与宿主之间的约定，
两侧都在同一次发布里。

### 5.4 为什么它没有进这个仓库

87 MB 的二进制不适合放进 git（每次发布都会让仓库历史永久膨胀）。因此
`src-tauri/runtime/` 在仓库里只有一个 `.gitkeep`，实际的 `node.exe` 由**发布流程**
在打包前放进去。

## 六、三种分发策略的取舍

| 做法 | 安装包 | 用户要做什么 | 适合 |
|---|---|---|---|
| **随包带上 `node.exe`** | +约 87 MB | 什么都不用做 | 想让后台功能对所有人开箱可用 |
| **不带**，靠自动查找 | 不变 | 机器上要有 Node；没有就在设置里指定一次 | 想控制体积；或用户群体本来就装了 Node |
| **开发/测试** | 不变 | `MODULITH_NODE` 指向一个 node.exe | 只在本机验证 |

目前仓库的状态是**中间那条**：不带，但自动查找已经覆盖了绝大多数机器
（第 4、5 条），并且设置页提供了一次性指定。要不要换成第一条是一个发布决策，
不是代码问题 —— 代码两侧都已经就绪。

---

## 七、出问题时怎么查

**设置 → 性能 → Node 运行时** 那一节会直接显示：

- 是否找到；
- 找到的是哪一个路径（`正在使用：...`）；
- 没找到时的**具体原因**；
- 是否手工指定过（以及指定的是什么）。

### 常见症状与原因

| 症状 | 原因 |
|---|---|
| 「未找到 Node 运行时」 | 五条路径都没命中。点「重新查找」，或手工指定 |
| 「指定的 Node 路径不存在」 | 设置里或 `MODULITH_NODE` 指的路径没有文件 |
| 「后台宿主启动后立即退出」 | 架构不匹配，或 `node.exe` 不完整（比如被杀毒软件截断） |
| 「协议版本不匹配」 | 宿主脚本与应用不是同一次发布（升级时漏了资源文件） |
| cmd 里有 node，应用里没有 | 旧版本的行为；现已修好。若仍出现，看那一节显示的「正在使用」 |

### 手工验证一条路径是否可用

```powershell
# 换成你要验的路径
'{"v":2,"id":1,"method":"ping"}' | & 'C:\path\to\node.exe' src-tauri\resources\background-host.mjs
```

期望输出两行：一行问候 `{"v":2,"runtime":"node/..."}`，一行对 `ping` 的回答。
**能看到这两行，就说明这个 Node 能跑我们的宿主脚本。**

## 八、为什么不用别的方案

| 方案 | 为什么没选 |
|---|---|
| **再开一个隐藏 WebView** 当后台环境 | 隐藏 WebView 依然是一整套浏览器进程（实测 6~8 个、几百 MB），而这条路子的目标是「别让后台能力占这么多」。Node 是一个进程，而且能在不需要时被完全关掉 |
| **把 Node 编进应用（`deno_core` / `boa` / QuickJS）** | 要么绑定一个 V8 的构建与维护成本，要么需要一个与 Node 不完全兼容的运行时。宿主脚本用了 `node:fs`、`node:timers` 这些 Node 语义，换引擎意味着重写它 |
| **让用户装 Node** | 这是当前的兜底（第 4、5 条），但可以作为**主要**方式时体验很差：用户装了个应用，发现后台功能用不了，还要自己去装一个开发工具 |
| **Windows 服务 / 计划任务** | 权限、安装复杂度、以及"卸载时清不干净"都远高于一个受管子进程 |
