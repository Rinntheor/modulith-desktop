# 构建与代码生成

Modulith 的构建过程包含一个代码生成阶段。理解生成器的作用范围是安全修改本项目的前提：部分源文件由脚本产出，手工编辑会在下一次构建时丢失。

## 1. 脚本清单

全部脚本位于 `scripts/`，使用 TypeScript 编写，由 Node.js 直接运行。

| 脚本 | 职责 | 直接运行 |
| --- | --- | --- |
| `generate-modules.ts` | 扫描前端模块，生成模块注册表与图标映射 | `pnpm gen:modules` |
| `generate-backend-module.ts` | 生成后端模块声明与命令注册，并支持新建/删除模块 | `pnpm gen:backend <子命令>` |
| `version-manager.ts` | 版本号同步、升级、校验与变更日志 | `pnpm ver <子命令>` |
| `check-samples.ts` | 校验示例插件的清单与代码、`.lcp` 是否一致 | `pnpm check:samples` |
| `check-semver.ts` | 用 semver 官方用例校验前端的版本比较实现 | `pnpm check:semver` |
| `check-update-throttle.ts` | 校验自动检查更新的节流判断（含"时间戳在未来"这类坏数据） | `pnpm check:update` |
| `check-network.ts` | 校验联网方式与下载源：前后端常量的镜像是否漂移、地址校验与拼接的行为 | `pnpm check:network` |
| `generate-latest-json.ts` | 生成应用更新清单 `latest.json`（发布时用） | `pnpm release:manifest` |
| `release-manifest.ts` | 清单生成的全部决策，被上面两个入口共用 | 不作为入口 |
| `release.ts` | 一条命令走完发布准备：预检 → 清理 → 签名构建 → 生成清单 | `pnpm release` |
| `vite-plugin-generate-modules.ts` | 将前端生成器接入 Vite 生命周期 | 由 Vite 加载 |
| `colors.ts` | 终端输出样式，被上述脚本共用 | 不作为入口 |

关于运行方式：项目使用 Node.js 22 及以上版本，脚本直接以 `node scripts/xxx.ts` 运行，依赖 Node 对 TypeScript 的类型擦除能力，不需要 `tsx` 或 `ts-node`。因此脚本内部的相对导入必须写明 `.ts` 扩展名，例如 `import { c } from './colors.ts'`。这一点与 `src/` 下的代码不同，后者由 Vite 打包，可省略扩展名。

## 2. 前端模块生成器

`scripts/generate-modules.ts` 扫描 `src/modules/*/module.toml`，产出四个文件。

### 2.1 输入

每个模块目录包含一份 `module.toml` 与其组件文件：

```
src/modules/<folder>/
  module.toml         模块清单
  <Component>.tsx     模块入口组件
  ...                 其余组件与逻辑
```

`module.toml` 的字段：

| 字段 | 必需 | 默认 | 说明 |
| --- | --- | --- | --- |
| `id` | 是 | - | 模块唯一标识 |
| `name` | 是 | - | 显示名 |
| `description` | 是 | - | 一句话描述 |
| `icon` | 是 | - | lucide-react 图标名 |
| `path` | 是 | - | 逻辑路径，用于路由生成 |
| `component` | 是 | - | 入口组件文件名 |
| `priority` | 否 | `999` | 排序权重，升序 |
| `category` | 否 | - | 分组名 |
| `visible` | 否 | `true` | 是否出现在导航中 |
| `disabled` | 否 | `false` | 是否禁用 |
| `badge` | 否 | - | 角标文本 |

子模块通过 `[[children]]` 数组声明，字段为 `id`、`name`、`description`、`icon`、`path`、`badge`、`disabled`、`component`。

### 2.2 输出

| 文件 | 内容 |
| --- | --- |
| `src/generated/moduleRegistry.ts` | 按 `priority` 升序的 `ModuleDescriptor[]`，含三种查询函数 |
| `src/generated/iconMap.ts` | 从 `lucide-react` 按需导入的图标集合 |
| `src/generated/moduleRegistry.sourceMap.json` | 模块 ID 到源文件的映射，便于定位 |
| `src/generated/generation.log.json` | 本次生成的统计、错误与告警 |

`moduleRegistry.ts` 导出三个函数：`getModuleRegistry()` 返回注册表，`getFlatModuleMap()` 返回含子模块的扁平映射，`getGroupedModules()` 按 `category` 分组。

### 2.3 校验

生成前会执行校验，发现错误即中止并返回非零退出码：

- 必需字段缺失。
- 模块 `id` 重复。
- 模块 `path` 重复。
- 子模块 ID 或路径重复。

图标名不在内置白名单中时只输出告警，不中断构建。白名单用于发现拼写错误，不限制实际可用的图标。

### 2.4 Vite 集成

`vite.config.ts` 通过 `vitePluginGenerateModules()` 接入生成器，其行为为：

| 时机 | 行为 |
| --- | --- |
| `buildStart`（首次） | 无条件执行一次生成 |
| `buildStart`（后续） | 计算模块目录指纹，仅在变化时重新生成 |
| 开发服务器文件变更 | 监听 `src/modules/**/*.{toml,tsx,ts,css}`，防抖 120 毫秒后按指纹判断是否重新生成，需要时触发整页刷新 |

指纹由模块目录下所有相关文件的「相对路径、大小、修改时间」拼接后排序得到。这一设计避免了两类问题：仅在 `module.toml` 变化时才重新生成（会漏掉组件文件的新增与删除），以及每次构建都无条件重新生成。

生成失败会让构建失败，而不是带着陈旧的注册表继续打包。

## 3. 后端模块生成器

`scripts/generate-backend-module.ts` 维护后端模块的声明与命令注册。

### 3.1 子命令

| 子命令 | 行为 |
| --- | --- |
| `new <id> [name]` | 创建 `src-tauri/src/modules/<id>/{mod.rs,commands.rs}`，随后刷新注册 |
| `delete <id>` | 删除模块目录，随后刷新注册 |
| `update` | 仅刷新 `modules/mod.rs` 与 `lib.rs` |
| `list` | 列出所有后端模块及其命令 |

`new` 会校验 ID 格式，要求匹配 `^[a-z][a-z0-9_]*$`。

### 3.2 生成的模板

`new` 产出两个文件。模块声明实现 `Module` trait：

```rust
pub struct ExampleModule;

impl Module for ExampleModule {
    fn id(&self) -> &'static str { "example" }
    fn name(&self) -> &'static str { "example" }
    fn version(&self) -> &'static str { "0.1.0" }
    fn description(&self) -> &'static str { "example 模块" }

    fn setup(&self, app: &AppHandle) -> Result<(), Box<dyn std::error::Error>> {
        app.manage(commands::ExampleState::new());
        Ok(())
    }
}
```

`commands.rs` 提供一个状态结构体与一条示例命令。

### 3.3 输出

**`src-tauri/src/modules/mod.rs`** 汇总所有模块：`pub mod` 声明、`register_all()` 中的注册调用、`list_all_module_ids()` 的 ID 列表。

**`src-tauri/src/lib.rs`** 装配整个应用：模块导入语句、`invoke_handler` 中的命令列表、`run()` 函数的完整实现。

模块的处理顺序取自 `readdirSync`，即字母序。命令的顺序取自其在 `commands.rs` 中的出现顺序。

命令通过正则 `#\[tauri::command\]\s*(?:pub(?:\s*\([^)]*\))?\s+)?(?:async\s+)?fn\s+(\w+)` 提取，因此支持 `pub`、`pub(crate)` 与 `async` 修饰。

### 3.4 重要约束

这两个文件是生成产物，**不要手工编辑**。所有变更应通过以下方式表达：

- 新增或删除模块：使用 `pnpm gen:backend new` / `delete`。
- 修改命令集合：编辑对应模块的 `commands.rs`，再运行 `pnpm gen:backend update`。
- 修改应用装配逻辑：编辑 `scripts/generate-backend-module.ts` 中的模板字符串，再运行 `update`。

`pnpm dev` 与 `pnpm build` 都会自动执行 `gen:backend update`，因此正常开发流程下无需手动运行。

## 4. 构建流水线

`package.json` 中定义的脚本：

| 命令 | 展开后 |
| --- | --- |
| `pnpm dev` | `pnpm ver check && pnpm gen:backend update && pnpm gen:modules && vite` |
| `pnpm build` | `pnpm ver check && pnpm gen:backend update && pnpm gen:modules && tsc && vite build` |
| `pnpm gen:modules` | `node scripts/generate-modules.ts` |
| `pnpm gen:backend` | `node scripts/generate-backend-module.ts` |
| `pnpm check:samples` | `node scripts/check-samples.ts` |
| `pnpm check:semver` | `node scripts/check-semver.ts` |
| `pnpm check:update` | `node scripts/check-update-throttle.ts` |
| `pnpm release` | `node scripts/release.ts` |
| `pnpm release:manifest` | `node scripts/generate-latest-json.ts` |
| `pnpm ver` | `node scripts/version-manager.ts` |
| `pnpm ver:fix` | `node scripts/version-manager.ts sync` |
| `pnpm tauri` | `tauri` |
| `pnpm preview` | `vite preview` |

两个 `check:*` 脚本**不在** `dev` / `build` 链路里，需要单独运行。

两次构建都先执行 `ver check`，即版本一致性校验。这是一个门禁：如果版本文件与配置不一致，构建失败并提示运行 `pnpm ver:fix`。这样可以避免构建过程静默改写源文件，详见[版本管理](版本管理.md)。

`pnpm build` 在打包前执行 TypeScript 类型检查（`tsc`），类型错误会中断构建。

默认的 `tsc` 只检查 `src/`，脚本不在其中。脚本的类型检查用 `tsc -p tsconfig.node.json` 单独运行（该 project 的 `include` 覆盖 `scripts/**/*.ts`）。

Tauri 侧的构建通过 `pnpm tauri build` 触发，它会在 `beforeBuildCommand` 中调用 `pnpm build` 先完成前端产物。

## 5. 常见操作

**新增一个内建模块**

```bash
# 前端部分
mkdir src/modules/myModule
# 编写 module.toml 与组件，然后重新生成注册表
pnpm gen:modules

# 后端部分（如需要）
pnpm gen:backend new my_module "我的模块"
```

**只重新生成前端注册表**

开发服务器已在运行时通常不需要手动执行，Vite 插件会按指纹自动处理。仅当在编辑器之外修改了模块文件、或需要刷新诊断输出时手动执行：

```bash
pnpm gen:modules
```

**查看后端模块与命令**

```bash
pnpm gen:backend list
```

**排查生成结果**

`src/generated/generation.log.json` 记录了本次生成的模块数、错误与告警；`src/generated/moduleRegistry.sourceMap.json` 记录了每个模块对应的源文件路径。

## 6. 生成文件的版本控制

`.gitignore` 中排除了 `src/generated/*`。生成产物不入库，因为它们可由 `module.toml` 完整重建。

`src-tauri/src/lib.rs` 与 `src-tauri/src/modules/mod.rs` 则是入库的，这样做的好处是克隆仓库后可以直接查看应用装配结果，无需先运行生成器。
