# 性能与内存

本文说明「性能模式」到底关掉了什么、为什么「关闭界面动画」曾经不够用，以及模块多开时的内存到底会怎样。

## 1. 起点：一个只在没看的标签上生效的开关

用户报告：**已经打开「关闭界面动画」，界面仍然卡。**

排查后发现两层原因，都是结构性的，而不是某一处写错了：

### 1.1 标签层的 MotionConfig 把全局开关重新打开了

`ThemeProvider` 在应用根部套了一层 `MotionConfig`，按设置给出 `reducedMotion="always"`。但 `Home` 给**每一个标签面板**又套了一层：

```tsx
// 修复前
<MotionConfig reducedMotion={isActive ? 'never' : 'always'} ...>
```

framer-motion 的合并规则是**子层覆盖父层**（`config = { ...parentConfig, ...config }`）。于是激活标签永远拿到 `"never"` —— 而那恰好是用户唯一在看的那个标签。这个开关的真实效果是「关掉没在看的标签的动画」。

修复后必须与全局状态取并集：

```tsx
<MotionConfig reducedMotion={isActive && !reduceMotion ? 'never' : 'always'} ...>
```

`reduceMotion` 在这里是**有效值**（见第 2 节），由 `subscribeTheme` 驱动，设置一改立即生效。

### 1.2 `reducedMotion="always"` 管不到透明度

framer-motion 12 的短路只对**位置类**属性生效（`positionalKeys`：transform 系列与 width/height/inset）。`opacity`、`backdrop-filter`、`box-shadow`、`background`、`filter` **不在其中**，它们照旧逐帧计算。

最直接的例子是授权界面的粒子背景：18 个粒子各自带一条 `repeat: Infinity` 的 `y / opacity / scale` 循环。`y` 与 `scale` 会被停掉，**`opacity` 不会** —— 于是 18 条 rAF 动画与 18 个合成层会永远跑下去，而授权界面默认每次启动都会出现。

因此它必须由代码显式关掉，而不能指望 `reducedMotion`：

```tsx
{!reduceMotion && <ParticleBackground />}
```

### 1.3 CSS 开关本身也不完整

原来的 `:root.lc-reduce-motion` 只压了 `animation-duration` / `animation-iteration-count` / `transition-duration` / `scroll-behavior`，漏掉两件事：

- **选择器不含根元素自身**（`*` 匹配后代），因此根元素在切深浅色时的 `transition: background-color` 仍在跑；
- **没有归零 delay**：一个 `animation-delay: 2s` 的动画仍会在 2 秒后闪出一帧（duration 被压到 0.001ms 的那一帧）。

## 2. 三个开关，两个有效值

| 设置项 | 默认 | 作用 |
| --- | --- | --- |
| `reduceMotion`（关闭界面动画） | `false` | 停用全部过渡与动效 |
| `performanceMode`（性能模式） | `false` | 在上一项的基础上，再去掉装饰性大半径模糊、成片的合成层提升提示与持续循环的装饰背景，并关闭毛玻璃 |
| `glassEffect`（毛玻璃效果） | `true` | 单独控制**浮层**的毛玻璃。窗口亚层不受它影响，见第 3 节 |

**性能模式包含关闭动画与关闭毛玻璃，反向都不成立。** 打开性能模式会把有效动效与毛玻璃一并置为「已关闭」：它要解决的问题正是「关了动画还是卡」，而它的代价（界面变朴素）用户已经付过一次了 —— 此时再要求他把三个开关都拨到位，只会让一部分用户得到一部分效果，然后断定这个功能没用。反过来，关闭动画或关闭毛玻璃都不会打开性能模式：去装饰模糊与收回合成层是有明显视觉代价的取舍，不该被作用域更窄的开关顺手做掉。

合并只发生在一处：`src/utils/motionPreference.ts` 的 `isMotionReduced(reduceMotion, performanceMode)` 与 `src/utils/glassPreference.ts` 的 `isGlassEnabled(glassEffect, performanceMode)`，由 `services/theme.ts` 的两个 `apply*Preference()` 调用，结果分别喂给 CSS 类（`.lc-reduce-motion` / `.lc-no-glass`）与 `MotionConfig`。散在多处判断的后果就是 1.1 节那个缺陷。

这三个纯逻辑文件单独成文件是为了能被 `scripts/check-performance.ts` 直接断言真值表 —— `services/theme.ts` 要操作 `document`，进不了只带 ES2022 的脚本 project。

## 3. 性能模式具体关掉了什么

全部写在 `src/styles/global/index.css` 里。排序按收益：

1. **装饰性大半径模糊（`filter: none`，仅 `blur-2xl` / `blur-3xl`）。** 授权页与启动页各有两个 384px 色块配 64px 模糊。小半径模糊通常是内容的一部分（例如图标底板），不动它。
2. **合成层提升提示（`will-change: auto`）。** 侧边栏给**每一个**条目都写了 `willChange: 'transform'`，几十个常驻图层。收回它的代价是侧边栏拖动/排序时可能重新栅格化 —— 那正是性能模式愿意换的东西。
3. **持续循环的装饰背景。** 粒子背景在性能模式（或关闭动画）下不再挂载（见 1.2 节）。

### 3.1 毛玻璃：常驻亚层永久关，浮层交给开关

毛玻璃的规则不在这一节，而在 `:root.lc-no-glass`（见 index.css）。分成两件事：

| 表面 | 处理 |
| --- | --- |
| 窗口亚层：标题栏、标签栏、侧边栏（带 `lc-chrome` 语义类） | **永久不使用 `backdrop-filter`**，改用半透明纯色 |
| 浮层：对话框、菜单、抽屉、下拉面板 | 由「毛玻璃效果」开关控制；性能模式会连带关闭它 |

亚层不加开关，是因为它背后**永远是应用的纯色底** —— 内容区从 `top: 76px` 开始、且带 `paddingLeft` 给侧边栏让位，没有任何内容会滚到它下面。没有内容可以模糊，`backdrop-filter` 就只剩代价：合成器每帧都要把下层读回来做一次高斯模糊。深色模式下这三处本来就已经被强制成不透明，模糊连"看起来有区别"都做不到。而浮层背后是会变化的内容，模糊在那里才有意义。

**这件事顺带修掉了一个真实的深色缺陷。** `dark-theme.css` 原先用 `[class~='backdrop-blur-xl']` 当"这是窗口亚层"的判据，而那个类并非亚层独有：全局右键菜单、模块右键菜单、隐藏模块面板、插件卡片的下拉、插件页的下拉**全都**同时带 `bg-white/95` 与 `backdrop-blur-xl`。它们因此被当成亚层，拿到了更暗的底色与近黑的描边 —— 而那张表里紧挨着的注释恰好写着「深色下给浮层描一道近黑边，会让它看起来像一块硬邦邦的补丁」。改用语义类 `lc-chrome` 之后，规则与注释终于一致。

**没有做的事，以及为什么：**

- **没有用 `content-visibility: hidden` 隐藏非激活标签。** 它的收益是让非激活子树彻底不参与布局与绘制，但同样会让子树内部的滚动容器失去布局，威胁「切个标签回来还在原处」这个保活的核心目标 —— 那个目标比省下几个非激活标签的布局开销重要得多。（`Home.tsx` 的注释一度声称用了它，实际代码从来没用过；那句话已改正。）
- **没有接入系统级 `prefers-reduced-motion`。** 只做用户显式开关。接入它需要同时处理 CSS 与 `MotionConfig` 两侧的一致性，否则会出现「CSS 停了但 JS 还在动」的半生效状态；那属于下一轮。
- **没有拆包。** 入口 chunk 在 v1.1.8 实测为 ~795 KB（v1.1.7 时 ~814 KB，v1.1.4 时 ~770 KB），`framer-motion` 被 30 个模块引用且没有被单独拆出来。它有确定的收益（首屏少下载），但属于构建配置而非"性能模式"这个运行期开关，混在一起会让两者都难以验证。
  值得记一笔：v1.1.8 新增的 Markdown 渲染器**没有增大入口 chunk** —— 它只被模块市场与插件页引用，而那两个模块本身就是懒加载的，因此它自然落进了一个 8.9 KB 的独立 chunk（`Markdown-*.js`）。**按使用位置懒加载比手工拆包更省事**，入口里那 ~795 KB 的主体是外壳与 `framer-motion`。

## 4. 内存：模块多开会不会越来越占内存

先把结论说完：**宿主侧的常驻内存是有界的，而且这一点不依赖用户行为。**

| 常驻对象 | 上限 | 依据 |
| --- | --- | --- |
| 挂载的模块实例 | 12 | `MAX_OPEN_TABS`，达到上限**拒绝再开标签并提示**，而不是悄悄淘汰 |
| 模块组件缓存 | = 已挂载的模块数 | `releaseCachedModuleComponent`（见下） |
| 市场 README / 图标缓存 | 各 32 条 | `MAX_CACHED_ENTRIES`，先进先出 |
| 通知 | 200 条 | 后端 `prune()`，先丢已读的最旧 |
| 登录日志 / 已知设备 / 最近模块 | 100 / 32 / 10 | `auth/config.rs`、`sidebar/config.rs` |
| 已安装插件注册表 | = 已安装插件数 | `plugins/registry.json` |

这一轮补上了两处此前**没有上限**的增长：

**模块组件缓存按挂载状态逐条释放。** 缓存的用途是「目录刷新时保持**正在显示**的那个组件的实例稳定」，一旦模块不再挂载，这个保证就没有对象了。此前它只随「曾经打开过的模块」增长（上限是目录里的模块数，不会无限，但不变量的表述应当是「= 当前挂载数」）。释放挂在 `tabStore` 的**唯一写入点** `setState` 上，因为六条关闭/对账路径（`closeTab` / `closeOtherTabs` / `closeTabsToTheRight` / `closeAllTabs` / `reconcile` / `resyncTabsFromSettings`）都经过它 —— 逐条去调必然漏一个，而漏掉的那个就是缺陷。

**市场正文与图标缓存加上限。** 它们是几十 KB 级的字符串与 base64 文本，此前每浏览一个新插件/新版本就多一条，没有任何淘汰。

仍然要说清楚的三件事：

1. **已经加载过的 JS chunk 不会释放。** 浏览器的模块注册表在文档生命周期内保留求值结果，这不是应用能控制的（只有整页重载会重置）。因此「打开过 50 个插件后内存不会降到刚启动时的水平」是正常的，它是 chunk 常驻，不是泄漏。
2. **插件模块不是 iframe，是同域内联脚本**（见[插件系统架构](插件开发/插件系统架构.md)第 6 节）。卸载插件会移除它的 `<script>` 节点并作废组件缓存，但已经编译的代码要等到没有引用才会被回收。
3. **宿主拿不到模块创建的定时器句柄**，因此非激活标签里的定时器不会被停。这是 JS 单线程下无法代劳的事 —— 模块必须自己用 `useModuleActive()` 判断可见性。宿主能做的是把这条要求写进文档与示例（见[宿主 API 参考](插件开发/宿主API参考.md)）。

后端侧还有两处「只在极端情况下增长」的结构：`AttemptTracker.attempts` 与 `RateLimiter.requests`（`auth/security.rs`、`auth/ratelimit.rs`）。它们的清理是**扫描**而不是硬上限，因为硬上限在这里是有害的：它们记录的是登录失败标识，一个可以被任意淘汰的表等于让攻击者用泛洪把自己的封锁记录挤出去。两者限制了扫描的阈值（256），而熵来自本机登录路径。

## 5. 验证

```bash
node scripts/check-memory.ts        # 24 项：缓存语义 + 释放挂钩 + 市场缓存上限
node scripts/check-performance.ts   # 30 项：开关真值表 + 接线 + 两个缺陷的修复点
```

`check-performance` 会**直接跑** `isMotionReduced` 的真值表（它是纯模块），并对 `Home.tsx` / `index.css` / `theme.ts` / `appsettings.ts` / Rust 的 `settings.rs` 做文本核对 —— 那两个缺陷都是「看起来对、实际不生效」的类型，只有把修复点本身钉下来才能防它回来。
