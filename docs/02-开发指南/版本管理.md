# 版本管理

Modulith 的版本号遵循单一事实来源原则：只在 `version.toml` 中维护一次，其余位置全部由脚本派生。本文说明该机制的实现、约束与日常用法。

## 1. 问题背景

版本号容易失控，原因在于它会被复制到多个地方。本项目需要同步的位置有：

| 位置 | 用途 |
| --- | --- |
| `src-tauri/Cargo.toml` | Rust 包的版本，编译期嵌入二进制 |
| `package.json` | 前端包的版本 |
| `src-tauri/tauri.conf.json` | 应用版本、产品名、窗口标题 |

更关键的是**运行时也需要版本号**：插件清单通过 `engines.loopcore` 声明兼容范围，后端校验器需要拿宿主版本与之比对。因此版本号不只是展示信息，而是一份运行期契约。

## 2. 设计决策

### 2.1 运行时版本从后端读取

后端命令 `get_app_info` 返回的版本号来自 `env!("CARGO_PKG_VERSION")`，即编译期从 `Cargo.toml` 嵌入的常量。插件校验器 `crates` 侧的 `validator.rs` 使用同一个来源。

因此前端不再维护版本号副本。前端在插件运行时加载前调用 `refreshHostVersion()`，把后端返回值写入宿主信息，插件通过 `window.Modulith.version` 读到的即为后端真实版本。

这一决策消除了一个具体的失效模式：前端硬编码的版本号与 `Cargo.toml` 偏离，导致「后端按 0.2.1 校验插件，插件却从宿主读到 0.2.0」。前端保留的 `MODULITH_VERSION` 常量只是后端不可用时的占位初值（`0.0.0-unknown`），不参与版本管理。

### 2.2 标记替换采用显式语法

早期实现在全项目范围内替换裸字面量，例如把 `'0.2.0'`、`'1'`、`'dev'` 直接做字符串替换。这种做法在本项目中是危险的：`1` 出现在多数源文件中，`dev` 出现在 `dev-tools` 分类与测试夹具里。执行一次同步就会静默改写大量无关代码。

当前实现只替换显式的占位符：

| 标记 | 取自 `version.toml` | 当前值 |
| --- | --- | --- |
| `{{version}}` | `app.version` | `1.0.0` |
| `{{fullVersion}}` | `build.full_version` | `1.0.0` |
| `{{appName}}` | `app.name` | `Modulith Desktop` |
| `{{buildNumber}}` | `build.build_number` | `1` |
| `{{releaseType}}` | `build.release_type` | `stable` |
| `{{author}}` | `app.author` | `环理论 (Rinntheor)` |
| `{{description}}` | `app.description` | `A modular desktop framework built with Tauri` |

只有写成双花括号形式的内容会被替换，普通代码与文档中的裸版本号永不触碰。扫描时跳过 `node_modules`、`target`、`dist` 等目录，以及版本管理脚本自身所在的 `scripts/` 目录。

参与替换的文件类型为 `.ts`、`.tsx`、`.js`、`.jsx`、`.mjs`、`.cjs`、`.html`、`.css`、`.json`、`.rs`、`.toml`。**`.md` 文档刻意排除在外**：文档需要原样展示标记语法，若把文档纳入替换范围，会改写示例本身，并使 `check` 把语法示例误报为未解析标记。文档若需要显示当前版本，应引用后端 `get_app_info` 而不是嵌入标记。

**标记替换是单向的**：替换后标记消失，同一个位置不会在下次升级时被再次更新。因此标记只适合「写入一次即固定」的场景。需要持续同步的运行时值应改为通过 `get_app_info` 从后端读取，而不是依赖标记。

### 2.3 版本文件自洽性校验

`version.toml` 中 `full_version` 必须与 `version`、`release_type`、`build_number` 推导出的值一致。若不一致，脚本直接报错并打印推导过程，而不是静默修正。字段之间互相矛盾时（例如 `release_type = "dev"` 但 `full_version = "1.0.0"` 缺少 `-dev.1` 后缀），界面上展示的版本会与实际构建类型不符。

### 2.4 版本号必须是合法 SemVer

`version` 字段通过严格校验：`MAJOR.MINOR.PATCH`，各段为不含前导零的数字。

这项校验是必要的，因为后端插件校验器会对宿主版本调用 `SemVer::parse`。若 `Cargo.toml` 中的版本号非法，解析失败会中断插件安装，而错误现场看起来像是插件的问题。校验在写入配置文件之前完成，因此非法版本不会进入构建流程。

### 2.5 构建门禁而非自动改写

`pnpm dev` 与 `pnpm build` 执行的是 `ver check` 而非 `ver sync`。不一致时构建失败并提示运行 `pnpm ver:fix`。

这样选择是为了避免构建过程静默修改工作区文件。构建应当是只读操作；版本升级应当是一次显式的、可提交的变更。

## 3. 文件格式

`version.toml`：

```toml
[app]
name = "Modulith Desktop"
version = "1.0.0"
author = "环理论 (Rinntheor)"
description = "A modular desktop framework built with Tauri"

[build]
release_type = "stable"
build_number = 1
full_version = "1.0.0"
```

`release_type` 取值限定为 `dev`、`beta`、`rc`、`stable`。`full_version` 的生成规则为：`stable` 时等于 `version`，其余情况为 `<version>-<release_type>.<build_number>`。当前处于 `stable`，因此 `full_version` 与 `version` 相同、不带预发布后缀；切回 `dev` 后会自动变成 `1.0.0-dev.1` 这种形式。

## 4. 命令参考

### 4.1 查看当前版本

```bash
pnpm ver show
```

输出应用名、完整版本、基础版本、发布类型、构建号与作者。

不带子命令执行 `pnpm ver` 会打印用法说明。

### 4.2 同步

```bash
pnpm ver sync              # 写入全部同步目标
pnpm ver sync --dry-run    # 只报告将要修改的内容
pnpm ver:fix               # 等价于 pnpm ver sync
```

同步依次处理配置文件与源码标记：

1. `Cargo.toml`：仅替换 `[package]` 段内的 `version`，依赖项的 `version` 不会被误改。
2. `Cargo.lock`：仅替换本包自己那个 `[[package]]` 条目的 `version`。它是 cargo 生成的，但本包的版本号只是 `Cargo.toml` 的镜像 —— 不同步它，`pnpm ver bump` 之后工作区就是脏的（下一次 cargo 构建会顺手改回来），而发布前的「工作区必须干净」检查会因此失败，症状看起来与版本号毫无关系。
3. `package.json`：替换 `version`。
4. `tauri.conf.json`：替换 `version`、`productName`，以及 `app.windows[0].title`。
5. 扫描源码中的 `{{...}}` 标记并替换。

写入前会比对内容，无变化则不改动文件，因此该命令是幂等的。

### 4.3 升级版本

```bash
pnpm ver bump major     # 1.0.0 -> 2.0.0，转为 stable，构建号归零
pnpm ver bump minor     # 1.0.0 -> 1.1.0，转为 stable，构建号归零
pnpm ver bump patch     # 1.0.0 -> 1.0.1，转为 stable，构建号归零
pnpm ver bump beta      # 转为 beta，构建号加一
pnpm ver bump rc        # 转为 rc，构建号加一
pnpm ver bump stable    # 转为 stable
```

省略类型时默认为 `patch`。

完整的升级流程为：

```
检查工作区是否干净（仅告警）
      |
      v
记录当前最新的 git tag（用于计算变更区间）
      |
      v
计算新版本号 -> 写入 version.toml
      |
      v
同步配置文件
      |
      v
替换源码标记
      |
      v
依据 git 提交生成 CHANGELOG 段落
```

工作区不干净时只输出告警而不中断，因为升级会同时修改多个文件，开发者可能有意将它们合并到一次提交中。若 git 不可用（非仓库环境），CHANGELOG 步骤会跳过，版本升级本身仍然完成。

**bump 不打 tag。** 这一点值得单独说明：bump 只改文件、不提交，此刻 `HEAD` 仍指向升级前的提交 —— 在这里打 tag 会得到一个「名字对、内容差一代」的 tag，而它从 tag 列表上完全看不出来。tag 由提交之后的 `pnpm ver tag` 创建，见 4.6。

### 4.4 校验

```bash
pnpm ver check
```

校验七项内容，任一项失败返回非零退出码：

| 检查项 | 说明 |
| --- | --- |
| `Cargo.toml` | `[package].version` 是否等于 `version.toml` |
| `package.json` | `version` 是否一致 |
| `tauri.conf.json` 版本 | `version` 是否一致 |
| `tauri.conf.json` 产品名 | `productName` 是否等于 `app.name` |
| SemVer 格式 | `version` 是否为合法的三段式版本号 |
| 未解析标记 | 源码中是否残留 `{{...}}` 占位符 |
| 自洽性 | `full_version` 是否与其余字段一致 |

该命令适合放入持续集成流程作为门禁。

### 4.5 生成变更日志

```bash
pnpm ver changelog
```

依据 git 提交生成或更新 `CHANGELOG.md`。`pnpm ver bump` 会自动执行这一步，该子命令用于补救「已升级但未生成日志」的情况。

提交信息按 Conventional Commits 前缀归类：

| 前缀 | 归类章节 |
| --- | --- |
| `feat` / `feature` | Added |
| `fix` / `bugfix` | Fixed |
| `perf`、`refactor`、`style`、`chore`、`build`、`ci` | Changed |
| `docs` | Documentation |
| `test` | Tests |
| `remove` / `revert` | Removed |
| 无前缀或其他 | Changed |

提交信息中的类型前缀与作用域会被剥离，只保留描述部分。中文提交信息同样适用，无前缀的中文提交会归入 Changed。

新版本段落插入到文件顶部，既有历史保持不变。同一版本重复执行不会产生重复段落。

### 4.6 打 tag

```bash
pnpm ver tag            # 在 HEAD 上创建 v<版本> 附注 tag
pnpm ver tag --force    # 同名 tag 已存在时，把它移到 HEAD
```

必须在**提交之后**执行：tag 要落在包含版本变更的那个提交上。

工作区不干净时会直接拒绝 —— 脏工作区打出的 tag，其指向的提交里并没有这些改动，正是同一个问题的另一种形式。

同名 tag 已存在且不指向 HEAD 时，默认拒绝并打印两边的哈希，而不是悄悄移动：如果那个 tag 已经推到远端，移动它会让远端与本地不一致。`--force` 用于「tag 只存在于本地且打早了」这种情况。

若不知道该不该移动，最稳妥的做法是**换个新版本号**，让旧 tag 留在原处。

## 5. 运行时版本的一致性保障

后端 `settings` 模块中的测试锁定了一条不变量：`get_app_info` 返回的版本必须等于 `env!("CARGO_PKG_VERSION")`，也即插件校验器使用的版本。共四个测试：

| 测试 | 断言 |
| --- | --- |
| `app_info_version_is_valid_semver` | 版本号为三段式且各段为无前导零的数字 |
| `app_info_version_matches_cargo_pkg_version` | 与编译期常量相等 |
| `plugin_validator_and_frontend_share_one_version_source` | 插件校验基准与前端显示版本同源 |
| `app_info_exposes_platform_and_tauri_version` | 平台与 Tauri 版本非空 |

这些测试在版本升级后仍然通过，因为它们比较的是两个动态来源，而不是硬编码的期望值。

## 6. 提交前检查清单

升级版本时的推荐顺序：

1. 确认工作区已提交或暂存，便于回滚。
2. 执行 `pnpm ver bump <类型>`。
3. 检查 `git diff`，确认改动仅包含版本相关文件与 `CHANGELOG.md`。
4. 执行 `pnpm ver check` 确认一致性。
5. 复核 `CHANGELOG.md` 中的归类是否符合预期。
6. 提交，然后 `pnpm ver tag` 在提交上打 tag。
7. 推送：`git push --follow-tags`。

顺序上只有一处不能颠倒：**提交在 tag 之前**。其余步骤都可以重做。

## 7. 发布流程与应用签名

应用自动更新靠一对密钥：**私钥签名，公钥随应用发布**。发布方用私钥给安装包签名，客户端用内置的公钥验签，通过后才安装。

### 7.1 密钥的处置（全项目唯一不可逆的部分）

**公钥一旦随某个版本发布，就永久固化在所有已安装用户那里。** 私钥丢失 = 再也无法向这些用户推送更新，只能让他们手工重装。没有技术补救手段，只能靠流程纪律。

| 事项 | 要求 |
| --- | --- |
| 私钥位置 | **不要放进仓库**。默认位置 `%USERPROFILE%\.tauri\modulith.key`，在仓库之外 |
| 备份 | **离线两份，其中一份异地**，且用不同介质 |
| 口令 | `signer generate` 时会设置。口令与私钥**分开保存**（口令进密码管理器）—— 两者放在一起等于没有加密 |
| 备份验证 | 备份后**立刻用备份签一次名**，确认可用。否则「备份了但用不了」要到紧急时刻才发现 |
| 轮换 | **没有轮换机制**。换密钥 = 老用户再也收不到更新 |
| 泄露处置 | 旧密钥**不要销毁**：唯一能把用户迁移到新密钥的方式，是再用旧密钥签一个「迁移版本」 |

最后两条合起来是一个反直觉的结论：**密钥不是「少留为好」，而是必须长期保存。** 丢了它比泄露它更无法挽回。

`signer generate` 会打印一份**公钥 ID**（形如 `AA1A007C26FB536`）。把它连同「这把密钥负责哪个版本区间」记在项目备忘里 —— 将来有多把密钥时，这是唯一能区分它们的依据。

当前这把的 ID 是 `AA1A007C26FB536`，公钥写在 `src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`。

### 7.2 发布步骤

从 1.1.0 起，整条流程收敛成「两条命令 + 一次网页上传」：

```powershell
# 1. 升级版本：同步四个配置文件（git 可用时顺带更新 CHANGELOG.md）
pnpm ver bump patch

# 2. 提交，然后在这次提交上打 tag
git add -A
git commit -m "chore(release): 版本升至 1.1.2"
pnpm ver tag                 # tag 必须在提交之后打，见 4.6
git push --follow-tags

# 3. 设好签名环境变量，然后一条命令走完 预检 → 构建 → 生成清单
$env:TAURI_SIGNING_PRIVATE_KEY = "$env:USERPROFILE\.tauri\modulith.key"
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = "<口令>"
pnpm release --notes-file release/notes.md

# 4. 按脚本打印出的地址在 GitHub 上建 Release，上传它列出的三个文件
```

第 4 步的 tag 必须与清单里的 `v<版本>` 一致 —— 清单里的下载地址是按它拼的。脚本会把带 tag 的 `releases/new` 地址直接打印出来。

发布说明（`notes`）会显示在应用的「设置 → 关于 → 软件更新」里，因此值得认真写：那是用户决定要不要现在更新的唯一依据。它的来源按 `--notes` → `--notes-file` → `CHANGELOG.md` 里该版本的段落 依次尝试，`pnpm release` 会把最终用了哪一个打印出来：

| 打印出的来源 | 含义 |
| --- | --- |
| `--notes-file release/notes.md` | 手写的说明（`release/` 已被 gitignore，因此这份文件不会弄脏工作区） |
| `CHANGELOG.md 里该版本的段落` | bump 在 git 可用时写好的那一段 |
| `无（更新卡片会显示空白）` | **这次发布的更新说明是空的** —— `CHANGELOG.md` 不存在或没有该版本的段落，而你又没给 `--notes` |

出现第三种时，构建已经做完了，用 `pnpm release --skip-build --notes-file <文件>` 只重建清单即可，不必重跑几分钟的构建。

> **`CHANGELOG.md` 是未跟踪文件，而工作区检查用的是 `git status --porcelain`（包含未跟踪文件）。**
> 因此 `pnpm ver changelog` 的补救要在**提交与打 tag 之前**做（和版本号一起提交），否则它会让
> `pnpm release` 的预检以「工作区不干净」拦下你。手写 `--notes-file` 没有这个问题 ——
> `release/` 整个目录都被忽略了。

#### 7.2.1 `pnpm release` 做了什么

| 阶段 | 做什么 | 为什么必须在这一步 |
| --- | --- | --- |
| 预检 | 版本四处一致、私钥与口令在位、工作区干净、tag 是否指向 HEAD | 构建要几分钟；「忘了设环境变量」最亏的失败方式是等到构建完才发现 |
| 口令自检 | 用 `tauri signer sign` 试签一个临时文件 | 「能不能解密私钥」一秒就能问出来，而构建要到最后一分钟才走到这一步 |
| 清理 | 删掉 `bundle/` 里非当前版本的安装包 | tauri 从不清空该目录，它会跨版本累积（1.0.0 到 1.1.1 会同时躺在那里） |
| 构建 | `tauri build`，带签名 | 产出安装包与旁边的 `<安装包>.sig` |
| 清单 | 写 `release/latest.json`，打印上传清单与地址 | 签名只有构建后才存在，清单只能在构建后生成 |

口令自检值得单独说：**CLI 区分不了「口令记错了」和「口令多了个看不见的空格」**，两种情况报的是同一句 `Wrong password for that key`。所以这一项只回答「这一对能不能用」，原始报错直连终端由你自己看。确认要跳过：`--skip-sign-check`。

它**不做**三件事，都是有意为之：

- **不改版本号。** 版本变更是一次独立的、需要提交和打 tag 的改动（`pnpm ver bump`）。把它混进构建里，会让「这个安装包对应哪个提交」说不清。
- **不提交、不打 tag。** 提交什么内容要人来决定。
- **不上传。** 上传发生在 GitHub 上，脚本没有网络凭据。

常用参数：

| 参数 | 用途 |
| --- | --- |
| `--dry-run` | 只做预检并打印将要执行的动作，不构建、不写文件 |
| `--skip-build` | 复用已有安装包，只重新生成清单 |
| `--skip-sign-check` | 跳过口令自检 |
| `--notes <文字>` / `--notes-file <文件>` | 指定更新说明；都不给时取 `CHANGELOG.md` 里该版本的段落 |
| `--allow-dirty` | 工作区不干净时也继续（仅自测用） |

只想重建清单而不重新构建，用 `pnpm release:manifest`。它与 `pnpm release` 共用同一份清单生成逻辑，两条命令的输出逐字节一致。

参数写在脚本名之后即可（`pnpm release --dry-run`）。若某个参数被 pnpm 自己的同名选项吞掉，直接运行 `node scripts/release.ts <参数>`，效果完全相同。

#### 7.2.2 `createUpdaterArtifacts` 必须为 true

`tauri.conf.json` 的 `bundle.createUpdaterArtifacts` **默认是 `false`**。此时 `tauri build` 不会产出任何 `.sig`：构建成功、安装包齐全，唯独没有签名。

这是整条发布链路上最容易踩的坑，因为它的症状出现在很远的地方（生成清单时才报「缺少签名文件」），原因却在配置里。因此它被显式写进配置，而且缺签名时的报错会直接点出这一条。

该字段只有 `true` / `false` / `"v1Compatible"` 三种取值。本项目用 `true`；`"v1Compatible"` 会额外生成 Tauri 1 时代的 zip 更新包，现在的客户端不需要。

#### 7.2.3 两个容易搞混的环境变量

| 变量 | 含义 |
| --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY` | **用这个**。值可以是密钥文件的**路径**，也可以是**文件内容**，tauri 自己判断 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 私钥口令；私钥没设口令时可省略 |
| `TAURI_SIGNING_PRIVATE_KEY_PATH` | `tauri signer sign` 与 `tauri plugin init` 用的。**`tauri build` / `tauri bundle` 不读它** |

**`TAURI_SIGNING_PRIVATE_KEY_PATH` 是最容易踩的一个**：它的名字看起来更"正确"，但构建链路完全忽略它，于是构建失败并报：

```
A public key has been found, but no private key.
Make sure to set `TAURI_SIGNING_PRIVATE_KEY` environment variable.
```

正确的写法（值填路径，变量名里没有 `_PATH`）：

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = "$env:USERPROFILE\.tauri\modulith.key"
```

这样私钥内容同样不会进入进程环境 —— 传路径就够了。

CLI 的 CHANGELOG 里有一句容易误导的话：它说 `tauri signer sign` 新增这三个变量是为了"与 `tauri build` / `tauri bundle` 已用的变量对齐"。实测并非如此。下面这些结论都是在本仓库上跑出来的，不是从文档推的：

| 设置 | 结果 |
| --- | --- |
| 只设 `TAURI_SIGNING_PRIVATE_KEY` = 密钥路径 | 产出 `<安装包>.sig`，成功 |
| 只设 `TAURI_SIGNING_PRIVATE_KEY_PATH` = 密钥路径 | `A public key has been found, but no private key.` |

复现方式（需要已有构建产物，`tauri bundle` 不会重新编译，几秒钟就能出结果）：

```powershell
node node_modules/@tauri-apps/cli/tauri.js signer generate -w "$env:TEMP\t.key" -p testpass --force --ci
$env:TAURI_SIGNING_PRIVATE_KEY = "$env:TEMP\t.key"
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = "testpass"
node node_modules/@tauri-apps/cli/tauri.js bundle --bundles nsis
```

用一次性密钥即可：报不报 `does not match the public key` 不重要，那说明密钥**已经读进去了**；出现 `no private key` 才是变量没生效。测完记得删掉 `bundle\nsis\` 里那个用错误密钥签出来的 `.sig`。

##### 与应用仓库之外的命令并不一致

`tauri signer sign`（插件仓库给 `index.json` 签名用的就是它）的行为**正好相反**，两处都实测过：

| 命令 | 设 `TAURI_SIGNING_PRIVATE_KEY` = 路径 | 设 `TAURI_SIGNING_PRIVATE_KEY_PATH` = 路径 |
| --- | --- | --- |
| `tauri build` / `tauri bundle` | ✅ 成功 | ❌ `no private key` |
| `tauri signer sign` | ❌ `failed to decode base64 secret key` | ✅ 成功 |

也就是说：**应用构建用第一个变量传路径，插件索引签名用第二个变量传路径。** 看起来应当统一，实则不能 —— 改任何一边都会坏掉另一边。

##### 口令报 Wrong password for that key

```
failed to decode secret key: incorrect updater private key password: Wrong password for that key
```

这句话只有两个含义：口令确实不对，或者口令里带了看不见的字符。**CLI 区分不了这两者** —— 实测口令 `testpass` 与 `testpass`（末尾多一个空格）报的是逐字相同的错。所以不要因为「我明明给对了」而跳过排查。

先在当前会话里看一眼这个变量，不用把它打印出来：

```powershell
$p = $env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD
"长度 $($p.Length) / 前有空白 $($p -match '^\s') / 后有空白 $($p -match '\s$')"
```

后两项为 `True` 就是原因。两个高发来源：

1. **复制粘贴带上了空格或换行** —— 长度会和记忆中的不一致。
2. **PowerShell 双引号展开了口令里的符号**。`"p$word"` 里 `$word` 会被当变量（通常展开成空串），反引号也会被吃掉。**口令一律用单引号赋值**：

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = '你的口令'
```

用 2 秒验证一次（不必构建）：

```powershell
Set-Content "$env:TEMP\probe.txt" "probe"
Remove-Item Env:TAURI_SIGNING_PRIVATE_KEY -ErrorAction SilentlyContinue   # signer sign 与它冲突
$env:TAURI_SIGNING_PRIVATE_KEY_PATH = "$env:USERPROFILE\.tauri\modulith.key"
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = '你的口令'
node node_modules/@tauri-apps/cli/tauri.js signer sign "$env:TEMP\probe.txt"
```

看到 `Your file was signed successfully` 就是口令没问题（确认后删掉 `probe.txt` 与 `probe.txt.sig`）。

`pnpm release` 已经内置了这一步：预检会用 `tauri signer sign` 试签一个临时文件，口令不对时在构建之前就失败。

**变量没设对时并不是"没有签名"那么简单**：`tauri build` 会直接失败（见上面的报错），因为它发现配置里有公钥却没有私钥。所以真正的静默失效只有一种 —— 变量设对了但忘了设口令，那会在构建最后才失败。`pnpm release` 把这两项都前置到构建之前，`pnpm release:manifest` 在缺少签名时也会直接失败。

### 7.3 为什么清单里没有 `windows-x86_64` 兜底键

tauri 在构建时把安装包类型以**二进制补丁**写进可执行文件（`__TAURI_BUNDLE_TYPE`），因此真实安装的应用一定知道自己是被 MSI 还是 NSIS 装的，`windows-x86_64-msi` / `-nsis` 必然匹配得上。

兜底键一旦被用到，说明类型未知（开发构建）。那时按兜底键装上另一种安装器，会在用户机器上留下两份安装记录 —— 比直接报错更糟。因此清单生成只写具体键。

### 7.3.1 为什么要按版本号挑安装包

`tauri build` 从不清空 `bundle/`，它跨版本累积产物。所以生成清单时面对的是「一个目录里躺着好几个版本的安装包」。

这里**按文件名里的 `_<版本>_` 挑，而不是取最新的一个**：按时间挑，在构建时间被复制、还原或系统时间被调整时会静默发布错包 —— 用户更新到 1.1.1，装上的却是 1.0.3 的文件。对不上版本时脚本直接报错，不猜。

`pnpm release` 会在构建前顺手删掉这些旧版本产物，因此正常流程下不会遇到；`pnpm release:manifest` 单独使用时则可能遇到，那时的报错会列出目录里都有什么。


### 7.4 老用户必须手工安装一次

更新器是本次才加入的。**在它之前发布的版本里没有公钥**，那些用户收不到任何自动更新，必须手工安装一次带更新器的版本；自动更新从那之后才生效。

这是「公钥必须先进去」的必然结果，不是缺陷 —— 但它意味着更新器应当尽早加入，而不是拖到以后。

### 7.5 安装包文件名里的空格

`productName` 是 `Modulith Desktop`，安装包文件名因此带空格。GitHub 的资源下载地址必须把空格写成 `%20`，否则 404 —— 而这个问题只在真机上暴露。

`generate-latest-json.ts` 用 `encodeURIComponent` 处理，因此不需要人工注意。但如果你手工拼过下载地址，记得这一点。
