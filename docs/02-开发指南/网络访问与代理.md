# 网络访问与下载源

本文说明应用的两条联网链路（插件市场、软件更新）在哪里发起、用户配置的「下载源」如何生效，以及如何诊断连不上。

## 1. 谁在联网

**前端不发起任何网络请求。** `src/` 下没有 `fetch`、没有 `XMLHttpRequest`、没有指向远程主机的 `<img src>` 或 `<script src>`。所有与网络有关的动作都通过 `invoke` 交给后端，唯一的例外是 `openUrl()`（交给系统浏览器）。

后端只有两个网络执行者：

| 执行者 | 代码位置 | 负责 |
| --- | --- | --- |
| `reqwest::Client` | `src-tauri/src/modules/plugins/manager.rs`（`PluginManager::client`） | 插件索引、索引签名、README、市场图标、`.lcp` 包下载 |
| `tauri-plugin-updater` 的 `Updater` | `src-tauri/src/modules/updater/commands.rs` | 更新清单（`latest.json`）与安装包下载 |

前端的地址模板集中在 `src/config/pluginRegistry.ts` 一个文件里；后端从不构造地址，只校验宿主。

## 2. 两种联网方式

设置项在「设置 → 网络」：

| 字段 | 取值 | 默认 |
| --- | --- | --- |
| `networkMode` | `direct` / `proxy` | `direct` |
| `githubProxy` | 代理根地址，例如 `https://gh-proxy.org` | 空串 |

**两者同时满足才真的走下载源。** 只判模式会让「选了下载源但地址是空的」退化成把一个绝对地址拼到空串上；只判地址会让「切回直连」失效。判断收敛在一处：后端 `settings/network.rs` 的 `proxy_base()`，前端镜像为 `utils/networkSettings.ts` 的 `isProxyEffective()`。

默认直连是刻意的：一个默认打开的第三方加速源会把「装什么插件」交给一个我们无法控制的中间人。

## 3. 下载源的语义：前缀拼接

这类服务（gh-proxy 系）的用法是把原始地址**整条接在自己的域名后面**：

```
https://gh-proxy.org/https://github.com/Rinntheor/modulith-desktop/releases/latest/download/latest.json
└──── 代理根 ────┘└──────────────────────── 原始地址 ────────────────────────────┘
```

拼接由 `settings/network.rs` 的 `join_proxy()` 完成，尾部斜杠可有可无（`https://gh-proxy.org` 与 `https://gh-proxy.org/` 结果相同）。

**只有 GitHub 宿主的地址会被改写**（`GITHUB_HOSTS`：`github.com`、`raw.githubusercontent.com`、`objects.githubusercontent.com`、`codeload.github.com`、`api.github.com`、`gist.github.com`、`release-assets.githubusercontent.com`，以及 `*.githubusercontent.com` 后缀）。`cdn.jsdelivr.net` 不在其中 —— 它是一个独立的 CDN 而不是 GitHub 的镜像，把它的地址拼到 GitHub 加速源上只会换来 404。

## 4. 改写在哪里发生，以及为什么必须在那里

改写**只在后端**发生，而且发生在**地址校验之后**：

```
前端给出原始地址
  → ensure_registry_url_allowed(url)     校验宿主 ∈ ALLOWED_REGISTRY_HOSTS
  → network::rewrite_url(url, proxy)     拼上用户配置的下载源
  → reqwest 发请求
```

这样安排有一个直接的安全后果：**宿主白名单始终作用在我们自己写死的宿主上**。用户填的代理地址从来不作为参数进入校验，因此一个被改坏的代理字段最多让请求失败，不可能把请求导向一个原本不被允许的宿主。若让前端拼好地址再传进来，就等于让被约束的一方自己划定边界 —— 那正是 `manager.rs` 里那条注释在防的事。

同样地，「网络诊断」的探测目标列表里，插件仓库那两条来自前端（因为地址模板在前端），更新清单那几条由后端从 `tauri.conf.json` 追加；两者都要通过同一套宿主校验。

## 5. 应用更新为什么搬进了后端

历史上这一步由前端直接调用 `@tauri-apps/plugin-updater`。它的两处地址都不可配：

1. **清单地址**来自 `tauri.conf.json` 的 `plugins.updater.endpoints`，在插件初始化时固定。
2. **安装包地址**根本不在插件配置里，而是**清单文件自己写的**（`platforms.<target>.url`，指向 `github.com/.../releases/download/...`）。

因此「能检查到新版本，下载却卡住」是这种结构的必然结果：清单可以换个地址取，安装包不行。

现在两步都走 `src-tauri/src/modules/updater/commands.rs`：清单地址经 `UpdaterBuilder::endpoints()` 传入，安装包地址在 `check()` 之后改写 `update.download_url`（该字段是公开的）。下载、签名校验、调起安装程序仍然全部由官方插件完成，公钥仍然取自 `tauri.conf.json` 的同一个 `plugins.updater` 块。

配套的两个决定：

- `src-tauri/capabilities/default.json` 里**移除了 `updater:default`**。插件与应用共用同一个 JS 上下文，若官方插件的命令仍然可达，插件代码就能绕开下载源直接调用它 —— 那样这个设置项就成了「只对守规矩的调用者生效」。
- 前端不再 import `@tauri-apps/plugin-updater`（依赖暂时保留在 `package.json` 里，因为改依赖清单需要重新生成锁文件；见第 8 节）。

## 6. 失败时的行为

**下载源失败会回退直连。** 顺序是「先下载源、后直连」：用户配它就是为了优先用它；而回退保证一个填错或临时挂掉的加速源不会把插件市场与应用更新变成永久不可用。两条路都失败时，日志里会有两次尝试的完整原因。

**候选顺序会随设置变化。** 前端 `pluginRegistry.ts` 的 `registrySources()` / `pluginIndexSources()` 接受一个 `preference`：选了下载源时把 GitHub 那条排到 CDN 前面。理由是受限网络里直连那一步要先等一个连接超时（30 秒）才轮到加速源，那会让「我明明配了下载源，市场还是打不开」成为一个必然的抱怨。谁先谁后不影响装到什么 —— 两条候选指向同一个不可变 tag，包还有索引里的 sha256 兜底。

**地址允许明文 http 的唯一情形是本机回环地址**（`localhost` / `127.0.0.1` / `::1`），用于本地自建加速源调试。注意应用更新比这更严：官方更新器在 release 版拒绝非 https 的清单地址，因此 http 回环加速源只对插件市场有效。

## 7. 诊断

「设置 → 网络 → 网络诊断」逐条实测并把结果并排显示：每条给出 HTTP 状态、响应字节数、耗时与展开后的失败原因（`network::describe_error_chain()` 会把 `reqwest` 藏在 `source()` 里的真正原因 —— DNS 解析失败、证书不受信、连接被重置 —— 一并列出来）。

探测并发执行（`tauri::async_runtime::spawn`），每条 8 秒超时。原因是串行时最坏情况是「条数 × 超时」，用户会以为界面卡死。

失败原因的展开也应用在正常请求上：`PluginError` 的 `From<reqwest::Error>` 会保留整条因果链，因此界面上的「网络错误」不再只有一句 `error sending request for url (...)`。

## 8. 已知限制

- **不支持 HTTP/SOCKS 代理。** 这里实现的是「地址改写」而不是「流量转发」，因此系统级代理、需要认证的代理都不在覆盖范围内。`UpdaterBuilder::proxy()`（真正的 HTTP 代理）没有被使用。
- **只支持前缀式加速源。** 少数服务使用别的形式（例如把域名替换掉、或需要特定的路径前缀），本实现不覆盖。
- **`@tauri-apps/plugin-updater` 仍留在 `package.json` 的依赖里但没有被使用**，因为删除依赖需要重新生成 `pnpm-lock.yaml`。它的权限（`updater:default`）已经移除，因此即使有人重新 import，调用也会因权限不足而失败。
- **内置的加速源预设只是输入建议**，不是「官方支持列表」。它们是第三方服务，可用性、速度与可信度由它们自己负责。
