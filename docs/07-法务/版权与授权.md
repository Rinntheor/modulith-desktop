# 版权与授权

本文说明 Modulith Desktop 的版权归属、授权方式，以及插件作者需要注意的边界。

**这是一份面向开发者的说明，不是法律意见。** 涉及商业决策或纠纷时请咨询律师。

## 1. 一句话结论

| 部分 | 版权归属 | 授权方式 |
| --- | --- | --- |
| 框架（宿主的全部源代码） | 环理论（Rinntheor） | GPL-3.0 |
| 插件 | **插件作者本人** | **由插件作者自行决定**（MIT、Apache-2.0、专有皆可） |
| `samples/` 下的示例插件 | 环理论（Rinntheor） | MIT |

框架用 GPL-3.0 是**刻意的**：防止有人拿这个框架做闭源商业产品。插件不受此约束 —— 见第 3 节。

## 2. 用到的概念

### 2.1 著作权与「衍生作品」

**著作权自作品完成即自动产生，不需要登记，也不由任何声明决定。** 你写的插件代码，著作权归你 —— 这一点与框架用什么许可证无关。

真正决定插件义务的是另一个概念：**衍生作品**（derivative work）。GPL-3.0 的 copyleft 只约束衍生作品 —— 如果你的插件是框架的衍生作品，那它就必须也以 GPL-3.0 授权。

所以问题从来不是「版权归谁」，而是「**插件算不算框架的衍生作品**」。

### 2.2 copyleft 与 GPL-3.0

GPL-3.0 是一种 **copyleft**（著佐权）许可证：它允许自由使用、修改、分发，但要求**衍生作品必须以同样的许可证发布并公开源代码**。

这与 MIT、Apache-2.0 这类**宽松**许可证不同 —— 后者允许衍生作品闭源。

### 2.3 为什么插件的归属天生模糊

本框架的插件与宿主耦合得相当紧密，这在法律上产生了不确定性：

- 运行在**同一个 WebView、同一个 JavaScript 上下文**中；
- 必须复用**宿主的 React 实例**（`Modulith.React`），自带 React 副本会导致 Hooks 失效；
- 通过 `Modulith.registerModule()` 把组件**交给宿主渲染**；
- 可以调用宿主暴露的 Tauri 命令。

这些特征既像「同一程序的组成部分」，也像「通过稳定接口调用的独立程序」。**法律上两种认定都有可能** —— 而这种不确定性对插件作者是不公平的。

### 2.4 GPL-3.0 第 7 条：附加许可

GPL-3.0 **第 7 条**允许版权持有人在 GPL 之上**追加额外许可**。关键限制是：**只能放宽，不能收紧。**

这正是本项目采用的做法，也是业界成熟机制 —— OpenJDK 的 [Classpath Exception](https://openjdk.org/legal/gplv2+ce.html) 用同一机制运作了二十余年。

## 3. 本项目授予的插件例外

完整条款见仓库根目录的 [PLUGIN-EXCEPTION.md](../../PLUGIN-EXCEPTION.md)，核心内容是：

> 任何**仅通过公开插件接口**与 Modulith Desktop 交互的作品，不因该交互而被视为框架的衍生作品，亦不受 GPL-3.0 的 copyleft 义务约束。插件作者可自行选择其插件的授权方式，包括专有许可。

「公开插件接口」指：

| 接口 | 位置 |
| --- | --- |
| `window.Modulith` | `registerModule`、`createContext`、`React`、`jsx` / `jsxs` / `Fragment` |
| 插件上下文服务 | `storage`、`http`、`logger`、`notifications`、`events` |
| 插件清单 | `manifest.json` 的各字段 |
| 宿主命令 | `src-tauri/src/modules/*/commands.rs` 中注册的命令 |
| 公开类型 | `src/types/plugin.ts` 等 |

## 4. 边界：例外不覆盖框架自身的代码

**这是最容易误解的一点。**

| 行为 | 是否被例外覆盖 |
| --- | --- |
| 调用 `Modulith.*` 等公开接口 | 覆盖 |
| 导入公开类型定义 | 覆盖 |
| 以 `samples/` 为起点编写插件 | 覆盖 |
| 打包时把 React 映射为外部依赖 | 覆盖 |
| **复制或修改框架实现代码后闭源分发** | **不覆盖**，仍受 GPL-3.0 约束 |
| **修改框架本身后分发** | 不覆盖，必须遵循 GPL-3.0 |
| **把框架代码内联进插件以规避 GPL** | 不覆盖 |

一句话：**你可以自由地为自己的插件选择许可，但不能把框架的代码搬走再闭源。**

若要以非 GPL 方式使用框架的**实现代码**，需要另行取得授权，请联系仓库维护者。

## 5. 示例代码为什么用 MIT

`samples/` 目录以 **MIT** 授权，而不是 GPL-3.0。

理由很实际：示例的用途就是**被复制**。如果示例是 GPL-3.0，那么每一个照着示例起步的新插件都会从「复制 GPL 代码」开始，作者将陷入不必要的授权纠葛 —— 这恰好是插件例外想要避免的情况。

以示例为起点时，请替换掉其中的名称、作者、`icon` 等信息。

## 6. 插件作者的责任

插件例外解决的是**你与框架之间**的授权关系。以下仍由你自行负责：

1. **第三方库的授权。** 例外不会让 GPL 库变成可用 —— 插件里引入 GPL 库，那个库的义务照旧。
2. **分发时的合规。** 若你选择 GPL 兼容许可，请随附相应许可证文本。
3. **不要暗示官方背书。** 使用「Modulith」描述兼容性是允许的（如「适用于 Modulith Desktop 的插件」），但不应使人误认为官方出品。
4. **如实声明引擎兼容范围。** 见 `manifest.json` 的 `engines.loopcore`。注意该字段当前**不阻止安装**，版本不匹配只产生提示。
5. **`manifest.json` 的 `license` 字段是元数据。** 它会被解析和保留，但**不做任何校验或强制** —— 它不是法律约束，只是声明。

需要与框架自身的许可分开看：这一处素材不改变框架的 GPL-3.0，也不被 GPL-3.0
覆盖 —— 它按自己的许可分发。

## 8. 诚实的技术说明

例外条款是**授予额外许可**：版权持有人承诺不行使 GPL 赋予他的某些权利。这是有效且业界通行的做法。

但需要说清楚：**「插件是否属于衍生作品」最终由版权法与司法机关认定，不由任何声明决定。** 本文与 `PLUGIN-EXCEPTION.md` 的作用是：**即使**某个插件在法律上被认定为衍生作品，我们也额外许可它以任意方式授权。

因此对插件作者而言，实际效果是确定的：**你不必因为使用本框架而改变自己插件的授权方式。**
