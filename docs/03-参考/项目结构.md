# 项目结构

本文列出仓库的目录布局与各文件的职责，用于快速定位代码。

## 1. 顶层布局

```
modulith-desktop/
  docs/                    文档
  samples/                 示例插件
  scripts/                 构建与维护脚本
  src/                     前端源码
  src-tauri/               后端源码与 Tauri 配置
  index.html               前端页面入口
  package.json             前端依赖与脚本
  vite.config.ts           Vite 配置
  tsconfig.json            前端 TypeScript 配置
  tsconfig.node.json       构建工具用的 TypeScript 配置
  version.toml             版本号的唯一事实来源
  pnpm-workspace.yaml      工作区声明
  LICENSE                  许可证
  README.md                项目说明
```

`public/` 下只有 `modulith.svg`（favicon 与标识源文件之一）。模板自带的 `vite.svg` / `tauri.svg` 已删除。

`src/assets/react.svg` 是模板残留（无任何引用方），尚未清理 —— 记录在[已知问题与技术债](../06-项目/已知问题与技术债.md)。

**`assets/` 下只放"必须随应用分发、且由代码 import 的资源"。** 这是 v1.3.2 才出现的第一个真正的二进制资产：默认提示音。之所以放 `src/assets/` 而不是 `public/`，是因为前者经 Vite 的模块图处理 —— 路径写错会在构建期失败，而 `public/` 下的文件即使没人引用也照样被打进产物，一个拼错的路径只会在运行时表现为"提示音不响"。

`src-tauri/icons/source.svg` 是**应用图标的输入文件**（带黑底的标识），`tauri icon` 由它生成 `src-tauri/icons/` 下的整套平台图标。它与 `public/modulith.svg` 是两个不同形态，必须同步修改 —— 见[设计规范](../05-设计系统/设计规范.md)第 12.4 节。

### 2.1 关于 src/types/plugin.ts

该文件在头部注释中声明自己描述的是插件系统的**长期完整接口面**，而当前已实现的运行时契约位于 `src/services/pluginRuntime.ts`。两者差异较大：例如 `plugin.ts` 中的 `PluginContext` 包含命令、视图、通知、事件、配置等成员，而实际提供给插件的是 `pluginRuntime.ts` 中的上下文对象。

编写插件时应以[宿主 API 参考](../02-开发指南/插件开发/宿主API参考.md)与[清单文件参考](../02-开发指南/插件开发/清单文件参考.md)为准。`plugin.ts` 可作为了解设计意图的参考，但不代表可用能力。

### 2.2 两个图标渲染组件的分工

`src/components/ModuleIcon.tsx` 与 `src/modules/plugins/PluginIcon.tsx` 看起来职责重叠，实际面向不同数据：

| 组件 | 输入 | 用途 |
| --- | --- | --- |
| `ModuleIcon` | 模块描述符的 `icon` / `iconSvg` | 侧边栏、子项、仪表盘中的模块图标 |
| `PluginIcon` | 插件清单 `manifest` | 插件管理页中的插件卡片与详情 |

侧边栏与仪表盘原先直接查构建期生成的 `generated/iconMap.ts`，因此插件模块的图标（既不在该映射中，也可能是 `icon.svg` 这样的文件路径）会渲染成空白。现已统一由 `ModuleIcon` 解析，其解析顺序与取舍见该文件的头部注释。

### 2.3 生成文件

`src/generated/` 下全部文件由 `scripts/generate-modules.ts` 产出，`.gitignore` 已排除该目录。不要手工编辑。

```
  generate-latest-json.ts          打印/写出 latest.json
  release.ts                       构建、签名与发布编排
```

脚本以 `node scripts/xxx.ts` 直接运行，依赖 Node 对 TypeScript 的类型擦除。因此脚本内部的相对导入必须带 `.ts` 扩展名。详见[构建与代码生成](../02-开发指南/构建与代码生成.md)。

## 5. samples/

仓库里保留**一个**参考插件：它不提供功能，只把不需要危险权限的核心宿主接口逐个示范一遍。
**源码放在插件根目录**（`main` 指向 `index.js`），因此可以直接阅读、复制与修改 ——
不需要先搭构建工具链。

```
samples/
  LICENSE                          示例代码的许可（MIT，与框架的 GPL 分开）
  reference/                       参考插件：模块注册 / 存储 / 通知 / 事件 / 可见性 / 样式
    manifest.json                  声明 storage / notification / plugin-communicate
    icon.svg
    index.js                       每个接口调一遍，并把「用了什么、需要什么权限」显示出来
    index.css                      插件自带样式，含深色模式
    README.md
    LICENSE                        随包分发，因此装到的插件是自包含的
  reference.lcp                    打包好的插件，可直接安装
```

另外三个**完整示例**（可用的插件，也是可以照着读的源码）已经迁到插件仓库
[`modulith-plugins`](https://github.com/Rinntheor/modulith-plugins)，可以从应用的插件市场
直接安装，源码在 `plugins/<名称>/`：

| 示例 | 侧重 | 参与的宿主能力 |
| --- | --- | --- |
| `notes` | 一个完整插件的基本形态，只用一项权限 | `ctx.storage` |
| `pomodoro` | 后台计时、应用内通知、自定义提示音 | `ctx.storage`、`ctx.notifications`、`ctx.audio` |
| `quick-launch` | 需要原生能力的插件怎么写 | `ctx.storage`、`ctx.launcher`、`ctx.icons`、`ctx.shell`、`ctx.fileDrop` |

它们的插件 ID 是 `com.modulith.sample.notes` / `pomodoro` / `quick-launch`。
`reference` 的逐行解析见[示例插件解析](../02-开发指南/插件开发/示例插件.md)。

`.lcp` 只是把对应目录压缩后改扩展名。**它必须与源码目录逐字节一致** ——
改完插件忘记重新打包，用户装到的就还是旧代码。这条由
`extracts_and_validates_real_sample_lcps` 测试守着：

```powershell
Compress-Archive -Path .\samples\reference\* -DestinationPath .\samples\reference.lcp -Force
```
