# 后端命令参考

本页列出全部注册的 Tauri 命令。命令由各模块的 `commands.rs` 定义，经生成器汇总注册到 `lib.rs`，共 76 条。

## 1. 调用约定

前端通过 `invoke` 调用：

```ts
import { invoke } from '@tauri-apps/api/core';

const status = await invoke<AuthStatus>('get_auth_status', {
  deviceFingerprint: fp,
  token,
});
```

| 约定 | 说明 |
| --- | --- |
| 参数命名 | JavaScript 侧使用小驼峰，Tauri 自动映射到 Rust 侧的蛇形命名 |
| 返回值 | 统一为 `Result<T, String>`；`String` 是可直接展示给用户的错误描述 |
| 异常 | 返回 `Err` 时 `invoke` 的 Promise 进入 rejected 状态 |
| 状态 | Rust 侧的 `State<'_, XxxState>` 参数不需要前端传递 |
| `AppHandle` | Rust 侧的 `AppHandle` 参数同样不由前端传递 |
| `token` | 出现在签名中的 `token` 是会话令牌，由认证模块校验 |

约定中「不需要前端传递」的参数指 Rust 侧由 Tauri 注入的上下文，前端调用时省略即可。

### 2.1 关键命令说明

**`setup_access_key`** 仅在尚未设置密钥时可用。密钥长度下限为 8 字符，由前端与服务端共同校验。密钥使用 Argon2id 派生后存储，不保存明文。

该命令同时生成**一组 3 枚**恢复码并**在返回值中明文返回一次**（`KeySetupResponse.recoveryCodes`）。此后只剩 Argon2id 哈希，无法再取回，因此界面必须在这一步展示给用户。每枚 20 字符、100 bit 熵、各能用一次；**重新生成会换发整套，而用掉一枚只作废那一枚**（其余保留，理由见[已知问题与技术债](../06-项目/已知问题与技术债.md)第 4.7 节）。

**`verify_access_key`** 的失败受尝试次数限制。连续失败达到阈值后会锁定一段时间，锁定时长随失败次数递增。返回的 `AuthResponse` 中包含 `securityInfo`，其中的 `message` 字段描述锁定原因，可直接展示。

**`try_auto_login`** 使用硬件指纹派生的密钥解密凭据，因此更换设备后自动失效。凭据解密成功还需通过摘要比对，防止配置被篡改。

**`reset_access_key_with_recovery_code`** 与 `verify_recovery_code` 是唯一不需要会话的密钥变更通道。用户忘记访问密钥时应用正处于锁定状态，不可能先提供有效会话。安全性由恢复码本身承担（每枚 100 bit 熵、一次性、仅存 Argon2id 哈希），并叠加请求限流。

重置被拆成两步：`verify_recovery_code` 只核验恢复码、**不修改任何状态**，通过后签发一个 10 分钟有效的一次性令牌（只保存归一化恢复码的 SHA-256 摘要）；`reset_access_key_with_recovery_code` 消费该令牌并设置新密钥。拆分的原因是可用性而非安全：三步合一时任何错误都会把提示与聚焦落在第一个输入框，用户会误以为恢复码抄错了。

若本机没有恢复码（`recoveryHash` 为空），两个命令都返回明确错误而非静默失败。

**`get_auth_status`** 是唯一无需会话即可获取授权信息的命令，因为它需要回答「是否需要解锁」这个问题本身。它返回的信息不包含敏感内容，但会告知 `hasRecoveryCode`——前端据此决定是否显示「忘记访问密钥」入口。

### 2.2 数据结构

| 类型 | 主要字段 |
| --- | --- |
| `DeviceFingerprint` | 设备标识、平台、主机名等硬件信息 |
| `HardwareFingerprint` | 指纹值与可读标签 |
| `AuthResponse` | `success`、`token`、`securityInfo` 等 |
| `KeySetupResponse` | 同上，另含一次性 `recoveryCodes: string[]`（一组 8 枚） |
| `RecoveryVerification` | `verified`、`token`（一次性）、`message`、`blockedUntil` |
| `AuthStatus` | `initialized`、`authenticated`、`requireAuth`、`autoLogin`、`hasRecoveryCode`、`remainingRecoveryCodes` |
| `SecurityOverview` | 安全设置汇总，另含 `hasRecoveryCode`、`remainingRecoveryCodes`、`recoveryCreatedAt` |
| `KnownDevice` | 设备 ID、标签、最后使用时间 |
| `LoginLogEntry` | 时间、设备、结果 |

所有结构在 JSON 中使用小驼峰命名。

## 3. plugins 模块：插件管理

共 27 条。

### 3.1 列表与查询

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `list_plugins` | 无 | `InstalledPlugin[]` | 列出全部已安装插件 |
| `get_plugin` | `id` | `InstalledPlugin \| null` | 查询单个插件 |
| `list_plugin_permissions` | 无 | `PermissionDescriptor[]` | 全部插件权限的元数据 |
| `fetch_registry_text` | `url` | `string` | 拉取插件仓库里的文本文件（索引或 README） |
| `verify_plugin_index` | `index`, `signature` | 无 | 校验插件索引的签名 |
| `read_plugin_asset` | `id`, `rel` | `string` | 以 UTF-8 文本读取插件内的资源文件 |
| `read_plugin_readme` | `id` | `string \| null` | 按需读取插件的 README（只有详情页用） |

`read_plugin_readme` **与 `list_plugins` 分开是刻意的**：README 只在用户真的打开插件详情时才有价值，而列表在每次启停插件、每次进插件页时都会重新拉一遍。500 个插件一起列出时，那些文本会被逐个读出来再跨 IPC 传过去 —— 十几 MB，而列表页一个字节都用不到。返回 `null` 表示这个插件没有 README，那不是错误。

`read_plugin_asset` 用于读取代码包、样式与 SVG 图标。路径必须是插件目录内的相对路径。由于按文本读取，二进制资源不受支持。

`list_plugin_permissions` 不接收参数、不读状态：它描述的是宿主**自己**的权限注册表，与装了哪些插件无关，因此前端只需在启动时取一次。权限的标签、描述与**风险等级**都由宿主推导（`src-tauri/src/modules/plugins/permissions.rs`），不来自插件清单、也不来自远程索引 —— 风险是安全信息，不能由被审查的一方提供。设计理由见[插件生态设计](../08-规划/插件生态设计.md)第 3 节。

`fetch_registry_text` 只负责取回一段文本，解析、缓存与渲染都在前端。四点约束：

- **宿主白名单**：只允许 `cdn.jsdelivr.net` 与 `raw.githubusercontent.com`。这是一条**安全边界**，不是便利性检查 —— 插件与宿主同处一个 JavaScript 上下文、能够触达 IPC 桥（见[插件系统架构](../02-开发指南/插件开发/插件系统架构.md)第 6.3 节）。若这里不限制宿主，一个没有声明 `network-external` 的插件就能借它发出任意外部请求，把权限模型整个绕过去。白名单里的两个域名与 `src/config/pluginRegistry.ts` 的 CDN 模板是一对，改一处必须改另一处。
- **必须 https**，唯一的例外是本机回环地址可以用 http，便于本地调试。

`verify_plugin_index` 校验索引的 minisign 签名，**必须在解析索引之前调用**。

索引是插件分发的信任根：它同时给出「装什么」与「校验哪个哈希」。一个被替换的索引可以连同包和它记录的哈希一起换掉，因此 sha256 只挡得住传输损坏，挡不住有意的替换 —— 索引本身必须能验证来源。先解析一份不可信的索引，等于让攻击者的内容先进入解析器。

公钥取自 `tauri.conf.json` 的 `plugins.updater.pubkey`：**与应用更新共用同一对密钥**，因此代码里不再保存一份（两处保存必然漂移，而漂移的表现是「应用更新能用、插件市场打不开」）。缺公钥会**报错而不是放行** —— 只要有一种情况静默通过，构造那种情况就是绕过校验的方法。

两类失败给出不同的错误：格式问题报「包非法」（文件没取对），验签失败报「下载失败」（来源不可信）。排查方向完全不同 —— 前者查网络与路径，后者查密钥与发布流程。

- **体积上限 1 MB**。索引正常只有几 KB，README 通常几十 KB，上限用于让"地址填错指向了一个大文件"立刻失败。
- **超时由调用方给出**，不接受前端传参：下载整包用 30 秒，而网络诊断用 8 秒 —— 诊断要的是"快"，一次挂住 30 秒会让整张表等上几分钟，用户只会以为界面卡死。

### 3.2 安装

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `install_plugin_package` | `path` | `InstalledPlugin` | 从 `.lcp` 文件安装 |
| `install_plugin_folder` | `path` | `InstalledPlugin` | 从已解包的目录安装 |
| `install_plugin_url` | `url` | `InstalledPlugin` | 从远程地址下载并安装（**不校验哈希**） |
| `install_plugin_url_verified` | `url`, `sha256` | `InstalledPlugin` | 下载并按预期哈希校验后安装 |
| `pick_plugin_package` | 无 | `string \| null` | 打开文件选择对话框，返回所选路径 |
| `pick_plugin_folder` | 无 | `string \| null` | 打开目录选择对话框，返回所选路径 |

安装过程中的校验见[插件系统架构](../02-开发指南/插件开发/插件系统架构.md)第 3 节。两个 `pick_*` 命令只是对话框封装，取消选择时返回 `null`。

`install_plugin_url` 服务于"用户自己粘贴一个地址"的场景：没有可对照的期望值，因此无从校验。**插件市场只用 `install_plugin_url_verified`**，它的 `sha256` 是必需参数而不是可选项 —— 一个"忘了传就静默跳过校验"的接口早晚会在某条调用路径上被漏传，而失败方式是安静的：插件装上了，校验没发生。

校验发生在**写盘与解压之前**。哈希不符时错误信息区分两种情况：索引里的哈希**格式非法**报「包非法」，**内容不符**报「下载失败」。两者都拒绝安装，但原因不同 —— 前者是索引写错了，后者才可能意味着下载链路有问题，共用一条信息会让排查方向跑偏。

### 3.6 网络

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `plugin_http_request` | `id`, `method`, `url`, `headers?`, `body?` | `HttpResponse` | 代插件发起 HTTP 请求 |

请求前会检查该插件的权限声明：未声明 `network` 时拒绝一切请求；目标不是回环地址且未声明 `network-external` 时拒绝。请求由后端发出，不受浏览器同源策略约束。

### 3.7 启动外部程序

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `plugin_launch_program` | `id`, `program`, `args?` | 无 | 启动一个外部程序 |

未声明 `process-spawn` 时拒绝。`program` 必须是**绝对路径**且指向一个已存在的文件；`args` 作为独立参数传递，不经过 shell（因此不存在引号与管道注入）。启动后不等待子进程退出。

这是插件能拿到的最强能力，因此在插件详情里标记为高风险。详见[插件系统架构](../02-开发指南/插件开发/插件系统架构.md)第 6 节。

### 3.8 文件访问

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `plugin_extract_icon` | `id`, `path` | `string` | 提取文件图标，返回 PNG data URL |
| `plugin_reveal_in_folder` | `id`, `path` | 无 | 在系统文件管理器中定位文件或目录 |
| `plugin_pick_audio` | `id` | `PickedAudio \| null` | 弹出音频选择框，读入并返回 data URL |

三条都要求 `filesystem-read` 权限。前两条的 `path` 必须是绝对路径。

`plugin_extract_icon` 只接受**文件**（目录不行），目标没有图标资源时返回错误，且**目前只在 Windows 上实现**。`plugin_reveal_in_folder` 接受文件与目录，它**只定位、不打开文件本身**。

`plugin_pick_audio` 把「选择 + 读取 + 编码」合成一步：插件拿到的是可直接播放的
data URL，**接触不到原始字节或路径**。扩展名白名单（`mp3` / `wav` / `ogg` / `m4a` /
`aac` / `flac` / `opus` / `webm`）与 2 MB 体积上限都在这一个执行点强制，返回 `null`
表示用户取消。详见[插件系统架构](../02-开发指南/插件开发/插件系统架构.md)第 6 节。

文件拖放没有对应的命令 —— 它走 Tauri 的窗口事件，由前端 `src/services/fileDrop.ts` 订阅后转发给插件。

### 4.1 AppInfo

```ts
interface AppInfo {
  version: string;        // 取自 CARGO_PKG_VERSION
  name: string;           // 取自 CARGO_PKG_NAME
  tauriVersion: string;   // Tauri 运行时版本

```

`version` 与插件校验器使用的版本同源，因此前端显示、插件读到的 `Modulith.version`、以及 `engines.loopcore` 的校验基准三者不会出现偏差。详见[版本管理](../02-开发指南/版本管理.md)。

### 4.2 AppSettings

```ts
interface AppSettings {
  defaultModule: string | null;         // 启动后默认打开的模块

  lastModule: string | null;            // 上次打开的模块，由前端写入
  theme: 'light' | 'dark' | 'system';   // 界面深浅模式
  reduceMotion: boolean;                // 关闭界面动画
  deferPluginLoading: boolean;          // 插件是否后台加载
  pluginLoadTimeoutMs: number;          // 单个插件加载超时（毫秒）
  accent: string;                       // 主题配色 id（强调色）
  openTabs: string[];                   // 打开的模块标签页，按显示顺序，由前端写入
  activeTab: string | null;             // 当前激活的标签页，零标签时为 null
  tabBarVisible: boolean;               // 是否显示二级标题栏（标签栏）
  autoCheckUpdates: boolean;            // 启动时是否自动检查应用更新
  lastUpdateCheckAt: string | null;     // 上次得到结论的检查时间（RFC3339），由前端写入
  networkMode: 'direct' | 'proxy';      // 直连 GitHub 还是经由下载源
  githubProxy: string;                  // 下载源根地址，空串表示还没填
  fileLoggingEnabled: boolean;          // 是否把运行日志写入文件
  crashLoggingEnabled: boolean;         // 是否把崩溃写入 crash.log
  performanceMode: boolean;             // 性能模式（包含 reduceMotion 的效果）
}
```

`update_app_settings` 在校验失败时返回错误而不写入，不做静默纠正——静默纠正会让前端收到的值与它提交的值不一致，反而更难排查。

各字段的校验规则：

| 字段 | 约束 |
| --- | --- |
| `defaultModule` / `lastModule` | 等价于 `^[a-zA-Z0-9][a-zA-Z0-9._/-]{0,127}$`，拒绝空串、`..`、以 `/` 开头 |
| `theme` | 必须是 `light` / `dark` / `system` 之一 |
| `pluginLoadTimeoutMs` | 500 至 60000（含）；`0` 会被拒绝而不是当作「永不超时」 |
| `accent` | 长度 1 至 32，字符集 `[a-z0-9-]` |
| `openTabs` | 最多 12 项（`MAX_OPEN_TABS`），每项等价于 `^[a-zA-Z0-9][a-zA-Z0-9._/-]{0,127}$` |
| `activeTab` | 同上格式；不要求必须属于 `openTabs` |
| `lastUpdateCheckAt` | 必须是合法的 RFC3339 时间戳；**不校验是否为未来时间**（见下） |
| `networkMode` | 必须是 `direct` / `proxy` 之一 |
| `githubProxy` | 空串合法；非空时必须是 https 的 URL（本机回环允许 http），不得含空白、查询串、片段或用户名密码，长度不超过 200 |

**`accent` 只校验格式，不校验是否为已知配色。** 配色表定义在前端（`src/config/accentTheme.ts`，10 套），后端复制一份清单必然漂移，而漂移的后果是「前端加了新配色、后端拒绝保存」。未知 id 由前端 `getAccentTheme()` 回退到默认值，是安全的降级。详见[主题与配色](../02-开发指南/主题与配色.md)第 7 节。

**`openTabs` 只校验数量上限与每个 ID 的格式，不校验模块是否真实存在。** 模块清单一部分来自构建期生成的内建注册表、一部分来自运行期注册的插件，后端复制一份必然漂移；失效的标签由前端在目录同步时对账剔除（插件被卸载后它的标签必须消失）。

数量上限 `MAX_OPEN_TABS = 12`（前后端各有一份，必须一致）的实际含义是约束**常驻内存的模块实例数**，因为每个打开的标签都会被挂载保活。这个上限必须校验：如果后端放行任意长度，一份被手工改坏的 `settings.json` 就能让前端在启动时尝试挂载上千个模块。

**`activeTab` 不强制要求属于 `openTabs`。** 读取时若两者不一致，由前端丢弃该值，这是安全的降级；在这里报错只会让一次无害的状态错位变成保存失败。

除 `confirmBeforeUninstall`（默认 `true`）、`theme`（默认 `system`）、`deferPluginLoading`（默认 `true`）、`pluginLoadTimeoutMs`（默认 `5000`）、`accent`（默认 `"indigo"`）、`tabBarVisible`（默认 `true`）、`autoCheckUpdates`（默认 `true`）、`networkMode`（默认 `"direct"`）、`fileLoggingEnabled`（默认 `true`）、`crashLoggingEnabled`（默认 `true`）与 `performanceMode`（默认 `false`）外，其余字段缺失时回落到零值。老版本 `settings.json` 缺少新字段时能正常加载。

`performanceMode` 的默认值是 `false`，因此它在**前端**的 normalize 里用的是与两个日志开关相反的方向（只有显式为 `true` 才开启）。两者的目标其实是同一个：老设置文件缺字段时落到默认行为上 —— 日志的默认是「开」，性能模式的默认是「关」。详见[性能与内存](../02-开发指南/性能与内存.md)第 2 节。

**`githubProxy` 的格式始终校验，即使当前是直连模式。** 理由是「切换模式」这个动作不该有额外的失败点：如果只在代理模式下校验，用户可以先存下一个坏地址、切到直连（保存成功），再切回代理时才发现存不进去 —— 那时报错指向的是一个他刚刚没碰过的输入框。详见[网络访问与下载源](../02-开发指南/网络访问与代理.md)。

**`update_app_settings` 与 `reset_app_settings` 会在保存之后立刻套用日志开关**（`logging::apply`）。日志开关是运行期生效的，让用户「关掉实时记录」却要重启才生效等于这个开关是假的。

**`lastUpdateCheckAt` 的时间戳只校验格式，不在后端拒绝未来时间。** 判断「该不该再查一次」由前端 `src/utils/updateCheck.ts` 负责，而它把未来时间戳当作「没检查过」处理——那才是安全的方向。放在后端拒绝反而是错的：系统时钟被往回调一下就会让整份设置无法保存。

## 5. net 模块：出站管控与流量日志

共 5 条。它们只读 / 清进程内的状态，或写一条日志，都不落盘。

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `net_policy_modes` | 无 | `PolicyMode[]` | 三档出站策略的标签、说明与**是否可用** |
| `net_log_list` | `limit` | `NetLogEntry[]` | 最近的出站记录，**最新的在前** |
| `net_log_clear` | 无 | 无 | 清空日志 |
| `net_log_len` | 无 | `number` | 当前条数 |
| `net_note_frontend_outbound` | `url`, `method`, `source` | `boolean` | WebView 门面拦下一次直接出站时上报；后端**自己重判**并记日志 |

`net_note_frontend_outbound` 的判定权在后端：前端传来的只是"发生过这件事"（地址、方法、声称的来源），不是结果。让调用方决定日志写什么，等于让日志变成它自己的说法。它走的规则与 `decide` 不同——**即使策略是"放行"，WebView 里的直接请求也不行**（它是"走错了通道"，不是"被策略允许"），唯一例外是回环地址。理由见[网络访问与下载源](../02-开发指南/网络访问与代理.md)第 8.6 节。

日志是**进程内的 500 条环形缓冲，应用重启即清空**。这是刻意的：落盘要先回答轮转、体积上限与隐私（URL 的查询串里可能带令牌）三个问题。界面上也如实写着"它是诊断用的，不是审计"。

**策略判定与日志写入不在这四个命令里**，而在 `net::client::NetClient`：所有 `reqwest` 出站都必须经过它，裸 `reqwest::Client` 由它私有持有。这一点有静态门禁守着（`pnpm check:network`）。完整说明见[网络访问与下载源](../02-开发指南/网络访问与代理.md)第 8 节。

## 7. notifications 模块：应用内通知

共 7 条。

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `list_notifications` | 无 | `Notification[]` | 列出全部通知，新的在前 |
| `push_notification` | `input` | `Notification[]` | 推送一条，返回推送后的完整列表 |
| `mark_notification_read` | `id` | `Notification[]` | 标记单条已读 |
| `mark_all_notifications_read` | 无 | `Notification[]` | 全部标记已读 |
| `dismiss_notification` | `id` | `Notification[]` | 移除一条 |
| `clear_notifications` | 无 | `Notification[]` | 清空全部，返回空列表 |
| `get_notification_summary` | 无 | `NotificationSummary` | 未读概览，返回 `{ total, unread }` |

`push_notification` 的 `input` 为 `PushNotificationInput`，字段是 `title`、`body`、`level`、`category`、`source` 与 `dedupeKey`；`level` 取 `info` / `success` / `warning` / `error`，`category` 取 `general` / `app-update`（省略为 `general`），`source` 省略或只含空白时按 `host` 处理。

### 6.1 同步命令与同步锁

这 7 条命令都是同步 `fn`，状态用 `std::sync::Mutex<Vec<Notification>>` 托管，而不是 `tokio::sync::RwLock`。理由与 auth 模块的取向相同：临界区是「改一个内存 `Vec` 加写一个小 JSON 文件」，全程没有 `await`，因此不存在 `MutexGuard`（`!Send`）跨 `await` 点的问题；同步命令在同一个线程上执行到结束，两次调用也不会交错，内存顺序与落盘顺序自然一致。反过来，一旦改成 `async fn` 就必须换成异步锁——同步 `Mutex` 的守卫跨越 `await` 连编译都过不去。settings 模块用 `tokio::sync::RwLock`，是因为它确实需要跨 `await` 持有；两者的分野就在临界区里有没有 `await`。

### 6.2 写命令返回完整列表

所有会改动数据的命令都返回**当前完整列表**，而不是只返回被改动的那一条。这是刻意的取舍：只返回一条会让前端必须自己维护「新条目插到哪、合并键命中时改哪一条、裁剪时删哪些」，三处逻辑都要与后端保持一致，一旦漂移就是界面与磁盘不一致。列表上限 200 条、实际通常只有个位数，多传几十 KB 换取「前端只需整个替换缓存」是划算的。

`mark_notification_read` 与 `dismiss_notification` 在 ID 不存在时**不报错**，仍然返回最新列表：通知可能刚被 `clear_notifications` 删掉，这属于正常的竞态，让界面拿到最新列表即可。

### 6.3 合并键 dedupeKey

`dedupeKey` 相同且**未读**的通知不会新增，而是合并进已存在的那一条：标题、正文、级别与创建时间取新的，`count` 递增。**已读的同键记录不参与合并**——用户已经看过那件事，再发生一次应当是新的一条。

存在的理由很具体：模块很容易在循环或重试里连续产生同一件事的通知（例如「网络不可用」反复触发），没有合并键时通知中心会被同一条信息刷满，用户反而看不到真正重要的那一条。

### 6.4 Notification

| 字段 | 说明 |
| --- | --- |
| `id` | 进程内唯一，格式 `<毫秒时间戳>-<序号>` |
| `title` | 标题，不能为空 |
| `body` | 正文，可为空串 |
| `level` | `info` / `success` / `warning` / `error` |
| `category` | `general` / `app-update`；缺省 `general`（老文件缺这个字段也能解析） |
| `source` | 来源模块 ID；宿主自身的通知固定为 `host` |
| `createdAt` | 创建时间，RFC3339（UTC） |
| `read` | 是否已读 |
| `dedupeKey` | 合并键，无键时为 `null` |
| `count` | 被合并的次数，首条为 1 |

`title` 为空会返回错误，这是唯一无法补救的情况——一条没有标题的通知在界面上只能显示成一个空行。其余超长字段（`title`、`body`、`source`、`dedupeKey`）按字符**截断而不是拒绝**：通知是「顺带告诉你一件事」，因为标题长了几个字就让整条通知消失是错的。

`NotificationSummary` 只有 `total` 与 `unread` 两个字段。

`category` 与 `level` **正交**：`level` 说的是这条信息有多严重，`category` 说的是它是不是一类需要特殊呈现与后续动作的通知。之所以用新字段而不是往 `level` 里加一个值：`level` 是严格反序列化的枚举，加值会让**整份旧通知文件解析失败**（`NotificationsFile` 解析失败即整份丢弃），而「应用更新」只是一个呈现层的需求，不值得付出那个代价。

### 4.3 ProbeReport

`probe_network` 的返回。`targets` 只包含**插件仓库**那几条地址（模板在前端 `src/config/pluginRegistry.ts`），更新清单那几条由后端从 `tauri.conf.json` 追加 —— 那份地址的真源在配置文件里，让前端再抄一遍只会制造一个会漂移的副本。

```ts
interface ProbeReport {
  mode: 'direct' | 'proxy';   // 当前联网方式
  proxy: string;              // 当前生效的下载源地址（直连时为空串）
  rows: Array<{
    label: string;            // 界面上显示的名字，例如「插件索引 · CDN」
    via: 'direct' | 'proxy';  // 这一行走的是哪条路
    url: string;              // 实际请求的地址（代理那条已按下载源改写）
    ok: boolean;
    status: number | null;    // 连都没连上时为 null
    bytes: number | null;
    elapsedMs: number;
    error: string | null;     // 已展开成因链
  }>;
}
```

**安全边界：目标地址由前端提供，但可探测的宿主由后端决定。** 每条地址的宿主必须属于插件仓库白名单（`ALLOWED_REGISTRY_HOSTS`）或更新清单配置里的宿主，而这两个集合都来自后端自己的常量与配置文件，前端无法扩大；「经下载源」那一版由后端用 `network::rewrite_url` 现场拼出，不接受前端传入任何已改写的地址。因此它能探测的宿主集合与「应用正常运行时会访问的宿主集合」完全相同。

单条 8 秒超时、并发执行、最多 6 个目标。理由见[网络访问与下载源](../02-开发指南/网络访问与代理.md)第 7 节。

共 5 条。

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `get_log_dir` | 无 | `string` | 日志目录的完整路径，必要时创建 |
| `read_log_tail` | `maxBytes?` | `LogTail` | 读取运行日志的尾部（默认 32 KB，上限 128 KB） |

`log_frontend` 与 `report_frontend_crash` **刻意不返回 `Result`**：它们唯一的失败方式是把日志写不进去，而让「写日志失败」变成一个 JS 侧的未处理 Promise 拒绝，会把一次无害的日志故障升级成用户可见的错误 —— 甚至可能自己触发全局错误处理器再次调用它们，形成回环。

`clear_logs` 由日志器自己完成（`FileLogger::clear()`），因为 Windows 上删除一个仍被打开的文件会失败 —— 必须先关句柄、再删、再重新打开。清空之后立刻写一行，否则用户看到的是一个空文件，分不清「清空了」还是「日志坏了」。

## 9. updater 模块：应用更新

共 2 条。

| 命令 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `check_app_update` | 无 | `AppUpdateCheck` | 按当前网络设置检查新版本 |
| `install_app_update` | `onEvent` | 无 | 下载并安装已检查到的更新；Windows 上会结束本进程 |

这两条命令取代了前端直接调用 `@tauri-apps/plugin-updater`。原因写在 `src-tauri/src/modules/updater/commands.rs` 的文件头：官方前端 API 的清单地址在插件初始化时固定，安装包地址更是由清单文件自己写的，两处都无法按用户设置改写 —— 那正是「能检查到新版本、下载却卡住」的成因。`capabilities/default.json` 里的 `updater:default` 也已移除，因此插件代码无法绕开下载源去调用官方插件的命令。

```ts
interface AppUpdateCheck {
  currentVersion: string;
  available: {
    version: string;
    date: string | null;      // 发布时间；发布方没写时为空
    notes: string | null;     // 发布说明
    downloadUrl: string;      // 实际会去下载的地址（已按下载源改写）
    source: string;           // 本次使用的联网方式描述
  } | null;
  endpoints: string[];        // 本次请求的清单地址（按顺序尝试）
  source: string;
}
```

`onEvent` 是一个 `Channel`，事件形状与官方插件一致：`{ event: 'Started', data: { contentLength } }`、`{ event: 'Progress', data: { chunkLength } }`、`{ event: 'Finished' }`。

清单地址只从 `tauri.conf.json` 读取，不接受前端传参 —— 允许调用方指定清单地址等于让它决定去哪里取更新包，而公钥只能证明「这是同一个签发者」，不能证明「这是官方发布的那个版本」。
